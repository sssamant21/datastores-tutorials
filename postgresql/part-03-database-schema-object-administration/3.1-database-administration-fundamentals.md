# Part 3.1 — Database Administration Fundamentals

**Status:** Revised Final / Canonical Edition  
**Target:** PostgreSQL 18  
**Audience:** PostgreSQL administrators, DBREs, SREs, platform engineers, and application-support engineers

## Learning objectives

By the end of this tutorial, you should be able to:

- distinguish cluster, database, schema, and object scope;
- verify the server, database, and role before administrative work;
- inspect database inventory, ownership, connection policy, size, and activity;
- interpret database statistics without confusing counters, current values, and rates;
- explain the privilege boundaries of monitoring queries;
- distinguish database-specific settings from cluster configuration;
- recognize the safeguards required for destructive database administration.

## 1. The administrative hierarchy

A running PostgreSQL server manages a **database cluster**. A cluster contains one or more databases. Each database contains schemas, and schemas contain objects such as tables, views, sequences, and functions.

```text
PostgreSQL cluster
├── Database A
│   ├── Schema 1
│   │   └── Tables, views, sequences, functions
│   └── Schema 2
└── Database B
```

Databases provide strong logical separation of SQL objects, but databases in the same cluster are not independent infrastructure units. They share cluster-level facilities and resources, including the server processes, storage platform, WAL architecture, configuration, roles, and compute capacity.

This distinction matters for high availability, backup and recovery, replication, security, and capacity planning.

## 2. Scope: cluster, database, schema, and object

| Scope | Examples |
|---|---|
| Cluster | roles, WAL, server resources, shared configuration, replication architecture |
| Database | ownership, connection policy, database defaults, schemas |
| Schema | namespace and contained objects |
| Object | table, index, view, sequence, function |

An administrator must identify the scope before choosing a command. A database-level change is not automatically cluster-wide, and a database owner is not automatically a PostgreSQL superuser.

## 3. Verify the target first

Database names are not globally unique. Separate clusters may each contain a database named `production`, `postgres`, or `application`.

Use an identity check before administrative work:

```sql
SELECT
    current_database()  AS database_name,
    current_user        AS current_user,
    session_user        AS session_user,
    inet_server_addr()  AS server_address,
    inet_server_port()  AS server_port,
    pg_is_in_recovery() AS in_recovery;
```

`inet_server_addr()` can return `NULL` when the connection uses a Unix-domain socket. That result is not automatically an error. Confirm the environment and endpoint using the connection method, service inventory, DNS, cloud console, or other approved source of truth.

Use this sequence:

```text
Verify environment → Verify endpoint/cluster → Verify database
→ Verify role → Verify operation → Execute
```

## 4. Database inventory with `pg_database`

`pg_database` is a cluster-shared system catalog containing one row per database.

```sql
SELECT
    oid,
    datname,
    pg_get_userbyid(datdba) AS owner,
    datallowconn,
    datconnlimit,
    datistemplate
FROM pg_database
ORDER BY datname;
```

From `psql`, `\l` or `\list` provides a convenient database listing. SQL is preferable for automation and repeatable operational checks.

## 5. Database ownership

`datdba` identifies the database owner. `pg_get_userbyid(datdba)` resolves its OID to a role name.

Ownership grants meaningful authority over the database and must be treated as security-sensitive. It does **not** make the owner a cluster superuser.

A common production model separates responsibilities among:

- application login roles;
- object-owner or application-owner roles;
- migration/deployment roles;
- monitoring roles;
- DBA or administrative roles.

Avoid arbitrary ownership assignments and routine use of superuser credentials.

## 6. Template and administrative databases

Typical clusters include:

| Database | Purpose |
|---|---|
| `template0` | Preserved clean template; normally does not allow connections |
| `template1` | Default source used when creating a database |
| `postgres` | Conventional administrative connection database |

Changes made deliberately to `template1` may appear in databases subsequently created from it. Do not modify template databases casually.

## 7. Connection policy

Two useful `pg_database` fields are:

- `datallowconn`: whether connections to the database are permitted;
- `datconnlimit`: database-specific concurrent connection limit.

```sql
SELECT datname, datallowconn, datconnlimit
FROM pg_database
ORDER BY datname;
```

`datconnlimit = -1` means there is no database-specific limit. It does **not** mean the server has unlimited connection capacity, and it is not a safe application capacity recommendation. Server-wide settings, reserved slots, pooling, memory, CPU, and workload concurrency still matter.

## 8. Database size

Inspect the current database:

```sql
SELECT
    pg_database_size(current_database()) AS size_bytes,
    pg_size_pretty(pg_database_size(current_database())) AS size_pretty;
```

Inspect connectable databases:

```sql
SELECT
    datname,
    pg_size_pretty(pg_database_size(datname)) AS database_size
FROM pg_database
WHERE datallowconn
ORDER BY pg_database_size(datname) DESC NULLS LAST;
```

In PostgreSQL 18, observing another database's size requires `CONNECT` privilege on that database or membership in `pg_read_all_stats`. A permission error is an authorization condition to investigate; it does not prove that PostgreSQL is unhealthy.

Database size supports capacity, backup, migration, and abnormal-growth investigations. A single measurement does not establish a trend. Collect measurements over time to calculate growth.

## 9. SAFE-READ is not zero cost

An observational query does not intentionally change database state, but it still consumes resources. Catalog scans, statistics queries, and size calculations should be used thoughtfully on large or heavily loaded systems.

```text
SAFE-READ ≠ ZERO OPERATIONAL COST
```

## 10. Runtime database statistics

`pg_stat_database` exposes database-level observations from PostgreSQL's cumulative statistics system.

```sql
SELECT
    datname,
    numbackends,
    xact_commit,
    xact_rollback,
    blks_read,
    blks_hit,
    tup_returned,
    tup_fetched,
    tup_inserted,
    tup_updated,
    tup_deleted,
    stats_reset
FROM pg_stat_database
WHERE datname IS NOT NULL
ORDER BY datname;
```

Monitoring access is privileged access. Visibility varies by view, field, and role. Use the least privilege required; do not respond to an observational permission error by automatically switching to superuser.

## 11. Current connections

`numbackends` reports the number of backends currently connected to the database. It is a current-state value, not a cumulative counter.

```sql
SELECT datname, numbackends
FROM pg_stat_database
WHERE datname IS NOT NULL
ORDER BY numbackends DESC, datname;
```

Connected does not mean actively executing:

```text
100 connected backends ≠ 100 queries executing concurrently
```

Use `pg_stat_activity` for detailed session state. That view is covered separately.

## 12. Transactions and tuple activity

`xact_commit`, `xact_rollback`, and the tuple fields are cumulative observations. They describe PostgreSQL activity, not precise business events.

```sql
SELECT
    datname,
    xact_commit,
    xact_rollback,
    tup_inserted,
    tup_updated,
    tup_deleted
FROM pg_stat_database
WHERE datname IS NOT NULL
ORDER BY datname;
```

A counter value is not automatically a rate. To calculate a rate:

```text
Snapshot T1 → wait for a known interval → Snapshot T2
Delta = T2 − T1
Rate = Delta / elapsed seconds
```

Account for `stats_reset` and server or statistics restarts when comparing observations.

## 13. Blocks read and buffer hits

`blks_read` counts blocks read by PostgreSQL, while `blks_hit` counts blocks already found in PostgreSQL's buffer cache.

Do not treat a high apparent buffer-hit ratio as proof of healthy performance. Investigate it alongside query latency, execution plans, storage latency, CPU, working-set size, concurrency, locks, checkpoints, and WAL activity.

## 14. Database-level configuration

`ALTER DATABASE ... SET` stores a database-specific session default. Subsequent sessions connecting to that database inherit the setting when applicable; existing sessions are not automatically rewritten.

```sql
ALTER DATABASE application_db
SET statement_timeout = '30s';
```

This example is explanatory and is not executed by the lab.

Do not confuse the scopes:

| Command | Scope and behavior |
|---|---|
| `ALTER DATABASE ... SET` | Database-specific default for subsequent sessions |
| `ALTER SYSTEM SET` | Cluster configuration written to `postgresql.auto.conf`; activation may require reload or restart |

Both require testing, impact analysis, approval, validation, and a rollback plan. `ALTER SYSTEM` is not a transactional substitute for a configuration-management process.

## 15. Observe before changing

Production administration should follow:

```text
Observe → Verify → Understand impact → Change → Validate → Monitor
```

Examples of observational operations include querying `pg_database`, `pg_stat_database`, and identity functions. Commands such as `CREATE DATABASE`, `ALTER DATABASE`, and `DROP DATABASE` change state and require a separate operational path.

## 16. Destructive database administration

`DROP DATABASE` removes the database's catalog entries and stored data. It cannot be undone by another SQL statement, cannot run while connected to the target database, and cannot run inside a transaction block.

Therefore, this is **not** a valid safety technique:

```sql
BEGIN;
DROP DATABASE production_db;
ROLLBACK;
```

Never test destructive administration against production. A backup may provide a recovery path, but recovery is not immediate transactional rollback. Validate backup integrity, RPO, RTO, WAL availability, dependencies, restore time, and the recovery procedure before destructive work.

## 17. `DROP DATABASE ... WITH (FORCE)`

`WITH (FORCE)` attempts to terminate eligible connections; it does not guarantee that everyone will be disconnected or that the drop will succeed. Prepared transactions, active logical replication slots, subscriptions, or connections the executing role cannot terminate can remain blockers.

Use this production gate:

```text
Verify target and environment
→ Review dependencies and ownership
→ Stop or drain application traffic
→ Inspect sessions and prepared transactions
→ Inspect replication dependencies
→ Validate tested recovery path
→ Obtain approval and coordinate maintenance
→ Execute
→ Validate and monitor
```

`FORCE` is not a substitute for dependency analysis. The lab does not execute any form of `DROP DATABASE`.

## 18. Managed PostgreSQL services

The core concepts apply to Amazon RDS for PostgreSQL, Amazon Aurora PostgreSQL-Compatible Edition, Azure Database for PostgreSQL, Google Cloud SQL for PostgreSQL, and self-managed PostgreSQL. Administrative privileges, host access, provider roles, configuration controls, backups, replication management, and monitoring integrations can differ.

Consult the applicable provider documentation before translating a self-managed procedure directly to a managed service.

## 19. DBA pre-change checklist

- [ ] Correct environment and endpoint verified
- [ ] Correct PostgreSQL cluster verified
- [ ] Correct database verified
- [ ] Correct role and least privilege verified
- [ ] Change scope and dependencies understood
- [ ] Expected impact understood
- [ ] Backup and tested recovery requirements reviewed
- [ ] Rollback or recovery plan available
- [ ] Monitoring and validation plan available
- [ ] Required approval and maintenance coordination completed

Destructive changes require stronger controls than routine observational work.

## 20. Hands-on lab

Run the companion artifact:

```bash
psql -X -v ON_ERROR_STOP=1 -d postgres -f labs/database-admin-check.sql
```

The lab performs read-only inspection of:

- session and server identity;

Some observations may fail for a restricted role. Diagnose privileges rather than escalating automatically. Run the lab first in an authorized non-production environment.

## 21. Expected outcomes

After the lab, you should be able to answer:

- Which server endpoint and database am I using?
- Which role am I using, and is the server a primary or standby?
- Which databases exist and who owns them?
- Which databases allow connections, and what limits apply?
- Which databases are largest among those visible to my role?
- How many backends are connected to each database?
- What cumulative transaction and tuple activity has PostgreSQL recorded?
- When were the statistics last reset?

## 22. Production takeaways

1. Distinguish cluster, database, schema, and object scope.
2. Verify environment, endpoint, database, role, and operation before change.
3. Prefer evidence-driven observation before administration.
4. Treat ownership and monitoring access as security-sensitive.
5. Do not confuse connected backends with actively executing queries.
6. Calculate rates from timed deltas; do not label cumulative counters as rates.
7. Treat SAFE-READ as observational, not free of operational cost.
8. Put destructive operations behind recovery, approval, and dependency gates.
9. Account for managed-service differences.

## 23. Summary

PostgreSQL database administration starts with knowing the target, scope, authority, and evidence. `pg_database` describes database metadata, `pg_stat_database` provides database-level runtime observations, and administrative functions such as `pg_database_size()` add capacity information subject to privilege rules.

The foundational production habit is:

```text
Observe → Verify → Understand → Change → Validate → Monitor
```
