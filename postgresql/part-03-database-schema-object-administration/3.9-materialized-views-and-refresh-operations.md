# Part 3.9 — Materialized Views and Refresh Operations

**Status:** Revised Final / Canonical Edition

**Target:** PostgreSQL 18

**Audience:** PostgreSQL administrators, DBREs, SREs, developers, platform engineers, and data engineers

## Learning objectives

By the end of this tutorial, you should be able to:

- distinguish materialized views from tables and ordinary views;
- explain freshness, staleness, and population state;
- create populated and unpopulated materialized views;
- choose between ordinary and concurrent refresh;
- design the unique index required by concurrent refresh;
- inspect definitions, indexes, population state, ownership, and size;
- plan refresh scheduling, capacity, failure handling, and monitoring;
- change or remove materialized views without surprising consumers;
- run an isolated lab that leaves no persistent objects.

## 1. What is a materialized view?

A PostgreSQL materialized view stores the rows produced by a query:

```sql
CREATE MATERIALIZED VIEW reporting.daily_event_summary AS
SELECT
    occurred_at::date AS event_day,
    status,
    count(*) AS event_count
FROM clinical.patient_event
GROUP BY occurred_at::date, status;
```

Queries read the stored result rather than rerunning the defining query on every access. PostgreSQL also stores the defining query so the result can later be replaced with `REFRESH MATERIALIZED VIEW`.

The stored result is a snapshot, not an automatically maintained cache. Changes to base relations do not appear until a successful refresh.

## 2. Table, view, and materialized view

| Object | Stores rows | Automatically reflects base changes | Normal direct DML |
|---|---:|---:|---:|
| Table | Yes | Not applicable | Yes |
| Ordinary view | No | Yes, when queried | Sometimes translated to base relations |
| Materialized view | Yes | No | No |

A materialized view is useful when repeated computation is expensive and consumers can tolerate a defined freshness delay. It is not a replacement for a table when the application must directly maintain rows.

## 3. Freshness is an application contract

PostgreSQL does not know how fresh the result must be. The system that owns the materialized view must define that contract.

Useful questions include:

- How old may the result be?
- What event or schedule triggers refresh?
- How long may refresh run?
- What should consumers see after a failed refresh?
- Who is alerted when the freshness objective is missed?
- Is an unavailable result acceptable during initial population or maintenance?

`pg_matviews.ispopulated` reports whether the object is populated. It does not report when its data was refreshed or whether it satisfies a business freshness objective. Record successful refresh timestamps and outcomes in an external scheduler or deliberately designed control table.

## 4. Create with data

The default creation mode executes the query immediately:

```sql
CREATE MATERIALIZED VIEW reporting.daily_event_summary AS
SELECT
    occurred_at::date AS event_day,
    status,
    count(*) AS event_count
FROM clinical.patient_event
GROUP BY occurred_at::date, status
WITH DATA;
```

`WITH DATA` is optional because it is the default. Creation time, locks, storage, WAL, I/O, CPU, and replica impact should be planned for a large result.

The creating role needs `CREATE` on the target schema and the privileges required to execute the defining query.

## 5. Create without data

Use `WITH NO DATA` to create the definition without initially executing the query:

```sql
CREATE MATERIALIZED VIEW reporting.daily_event_summary AS
SELECT
    occurred_at::date AS event_day,
    status,
    count(*) AS event_count
FROM clinical.patient_event
GROUP BY occurred_at::date, status
WITH NO DATA;
```

The materialized view is unpopulated and cannot be scanned until a data-populating refresh succeeds:

```sql
REFRESH MATERIALIZED VIEW reporting.daily_event_summary;
```

`WITH NO DATA` is useful when definition deployment and expensive population must be separated. Deployment must prevent consumers from querying the object prematurely.

## 6. Creation options

`CREATE MATERIALIZED VIEW` supports an access method, storage parameters, and a tablespace. These choices affect storage placement and behavior rather than freshness semantics.

PostgreSQL does not support temporary materialized views. Use a deliberately named isolated schema for experiments.

`IF NOT EXISTS` only suppresses an error when the name already exists. It does not prove that the existing relation has the intended definition, owner, indexes, storage options, or grants. Treat desired-state verification as a separate deployment step.

## 7. Index the stored result

Indexes on a materialized view can support consumer queries just as indexes support table queries:

```sql
CREATE INDEX daily_event_summary_status_idx
ON reporting.daily_event_summary (status, event_day);
```

Design indexes for actual access paths and validate plans after realistic population. Every index also increases storage and refresh work.

One unique index may serve two purposes:

- enforce a row identity for the stored result;
- make the materialized view eligible for concurrent refresh.

Those purposes are related but not identical. A unique index required for refresh may not be the best index for every reader.

## 8. Ordinary refresh

```sql
REFRESH MATERIALIZED VIEW reporting.daily_event_summary;
```

An ordinary refresh completely replaces the stored contents with a new execution of the defining query. It can block concurrent reads of the materialized view. It often uses fewer resources and can finish faster than concurrent refresh.

Use ordinary refresh when the blocking window is acceptable, including initial population or controlled maintenance periods.

## 9. Concurrent refresh

```sql
REFRESH MATERIALIZED VIEW CONCURRENTLY
    reporting.daily_event_summary;
```

Concurrent refresh allows concurrent readers to continue selecting from the materialized view while PostgreSQL produces and applies the new result. Readers may continue to see the prior stored result until the refresh completes.

It is not a zero-lock, zero-I/O, or zero-WAL operation. Plan capacity and validate its effect under representative load.

PostgreSQL notes that concurrent refresh can be faster when only a small number of rows differ. Ordinary refresh generally tends to use fewer resources and finish more quickly. Neither outcome should be assumed: measure both modes with representative data, indexes, concurrency, and storage.

## 10. Exact concurrent-refresh prerequisites

`CONCURRENTLY` is permitted only when:

1. the materialized view is already populated; and
2. it has at least one qualifying `UNIQUE` index.

The qualifying index must:

- use only materialized-view column names;
- include all rows;
- contain no expression; and
- contain no `WHERE` predicate.

For example:

```sql
CREATE UNIQUE INDEX daily_event_summary_refresh_uidx
ON reporting.daily_event_summary (event_day, status);
```

An expression index or partial unique index can still be useful to queries, but it does not satisfy the concurrent-refresh prerequisite.

The defining query and unique key must agree. If two result rows can share `(event_day, status)`, index creation fails.

Concurrent-refresh identity columns should normally be `NOT NULL`. A regular unique index can permit multiple null values. If nullable identity is intentional, explicitly evaluate `NULLS NOT DISTINCT` and validate that the index represents a true one-row identity for the complete result.

## 11. Incompatible refresh options

These options cannot be combined:

```sql
REFRESH MATERIALIZED VIEW CONCURRENTLY reporting.summary
WITH NO DATA;
```

Concurrent refresh requires a populated result, while `WITH NO DATA` deliberately makes the object unpopulated and frees its stored result.

`REFRESH MATERIALIZED VIEW ... WITH NO DATA` is therefore an availability-affecting administrative operation. Consumers cannot scan the materialized view until a later population refresh succeeds.

Production use requires dependency review, consumer coordination, a controlled maintenance window, sufficient repopulation capacity, a tested population command, alert handling, and post-population validation. Do not use it casually as a storage-reclamation shortcut.

## 12. Only one refresh at a time

PostgreSQL allows only one refresh at a time for a given materialized view. Schedulers should prevent overlapping attempts rather than relying on sessions to queue indefinitely.

Use bounded `lock_timeout` and `statement_timeout` values appropriate to the workload, and make scheduler behavior explicit:

- skip an overlapping run;
- wait for a bounded interval;
- fail and alert; or
- retry with controlled backoff.

Application-level advisory locks can coordinate multiple schedulers, but lock-key design and failure behavior must be standardized.

Session-level advisory locks must be released reliably. Transaction-level advisory locks end with the transaction. Lock keys must be stable and collision-safe across databases and refresh jobs, and the design must account for crashed workers, duplicate deliveries, scheduler failover, retries, and manual refreshes.

## 13. Refresh is complete replacement

Native PostgreSQL refresh reevaluates the defining query and replaces the materialized result. It is not a general incremental-refresh engine.

Do not estimate refresh cost only from the number of recently changed base rows. Cost can include:

- scanning and joining base relations;
- sorting or hashing aggregates;
- writing a replacement result;
- maintaining indexes;
- temporary-file use;
- WAL generation and replication traffic;
- cache churn and storage latency.

Measure with production-like data and representative concurrency.

## 14. Row order is not guaranteed

Even if the defining query contains `ORDER BY`, a later refresh does not guarantee preservation of physical or returned row ordering.

Consumers that require ordering must use `ORDER BY` in their own query:

```sql
SELECT event_day, status, event_count
FROM reporting.daily_event_summary
ORDER BY event_day, status;
```

Indexes may support the ordering efficiently, but an index still does not make unordered SQL results a contractual order.

## 15. Creation and refresh security context

During creation, PostgreSQL executes the defining query as a security-restricted operation and temporarily uses `pg_catalog, pg_temp` as `search_path`. Functions that attempt prohibited operations, such as creating temporary tables, fail in that creation context. Refresh also temporarily uses `pg_catalog, pg_temp` as its `search_path`.

Operational implications:

- schema-qualify referenced objects in definitions;
- review all invoked functions and their owners;
- review `SECURITY DEFINER`, volatility, extension dependencies, external calls, and function-level timeouts;
- avoid unsafe dynamic SQL and ambient `search_path` assumptions;
- treat function changes as materialized-view dependency changes;
- test creation and refresh using the actual deployment or refresh role.

## 16. Privileges and ownership

In PostgreSQL 18, refreshing a materialized view requires the `MAINTAIN` privilege on it. Ownership or a role membership path may confer the necessary authority, but routine refresh workers should receive only the privileges they need.

Granting `MAINTAIN` authorizes the refresh command; it does not grant the scheduler general direct access to the base relations. The defining query is refreshed using the materialized-view ownership context, so owner-role access must remain valid.

The materialized-view owner needs durable access to objects used by its definition. Avoid personal or superuser ownership. Prefer a managed non-login owner and a separate scheduler login with narrowly scoped authority.

Changing auxiliary properties or dropping the object requires ownership. Review grants after owner changes, schema moves, and definition-replacement deployments.

Monitoring access is also privileged access: definitions, names, sizes, and workload timing can expose operational information.

A materialized view is also a stored-data security boundary. Consumers read its stored rows directly; do not assume that base-table row-level security is reevaluated for every consumer query against the materialized view. Review which sensitive rows and columns are copied, grant `SELECT` narrowly, test with real consumer roles, and include the stored result in backup, replica, retention, encryption, and deletion reviews. A materialized view can otherwise become a second, less-restricted copy of protected data.

## 17. Inspect materialized views

The `pg_matviews` system view exposes useful metadata:

```sql
SELECT
    schemaname,
    matviewname,
    matviewowner,
    tablespace,
    hasindexes,
    ispopulated,
    definition
FROM pg_matviews
ORDER BY schemaname, matviewname;
```

`hasindexes` is a general indicator that the materialized view has, or recently had, indexes. It does not prove that a valid qualifying unique index exists for concurrent refresh. Inspect `pg_index` and the index definition separately.

Inspect indexes separately:

```sql
SELECT
    indexname,
    indexdef
FROM pg_indexes
WHERE schemaname = 'reporting'
  AND tablename = 'daily_event_summary'
ORDER BY indexname;
```

Inspect storage:

```sql
SELECT
    pg_size_pretty(pg_relation_size('reporting.daily_event_summary')) AS heap_size,
    pg_size_pretty(pg_indexes_size('reporting.daily_event_summary')) AS index_size,
    pg_size_pretty(pg_total_relation_size('reporting.daily_event_summary')) AS total_size;
```

Permissions can limit visibility or size inspection. A permission failure is not proof of corruption.

## 18. Statistics and query plans

A refreshed materialized view is queried like a stored relation, so planner statistics and indexes matter. Inspect `pg_stat_user_tables`, `pg_stat_user_indexes`, and query plans after representative refreshes.

If planner statistics are absent or unsuitable for the workload, schedule `ANALYZE` under controlled conditions:

```sql
ANALYZE reporting.daily_event_summary;
```

`ANALYZE` changes statistics state and consumes resources. It is not included in the transaction-contained acceptance lab. Validate whether automatic or explicit analysis meets the freshness needs of query plans in the target environment.

## 19. Monitor the refresh system

PostgreSQL does not provide a built-in business freshness timestamp in `pg_matviews`. A production refresh system should record or expose:

- requested, started, and completed timestamps;
- success or failure;
- duration;
- ordinary or concurrent mode;
- rows or result size where useful;
- timeout and lock-wait outcomes;
- scheduler identity and deployment version;
- consecutive failures and last successful completion.

Monitor both execution and consumer freshness. A scheduler can report success while a downstream cache, replica, or export remains stale.

Avoid embedding a volatile “refreshed at” expression such as `clock_timestamp()` in every result row merely to track freshness. Prefer one authoritative control record per refresh.

## 20. Failure behavior

A failed refresh should not be treated as a partial business success. Capture the database error and preserve enough context to diagnose it without logging sensitive query data.

For concurrent refresh, existing populated data remains available when the refresh fails, but it remains stale. Availability is not freshness.

Failure handling should define:

- whether and when to retry;
- maximum staleness before paging or disabling a consumer;
- how to prevent retry storms;
- how to handle base-schema changes;
- how to verify storage headroom before retrying;
- who owns recovery.

## 21. Definition changes require deliberate replacement

PostgreSQL has no `CREATE OR REPLACE MATERIALIZED VIEW`. `ALTER MATERIALIZED VIEW` changes auxiliary properties such as ownership, name, schema, storage parameters, access method, tablespace, statistics targets, and clustering metadata; it does not replace the defining query.

To change the result contract, use a reviewed migration. A low-risk pattern is:

1. create a versioned materialized view with the new definition;
2. create and validate its indexes;
3. populate and analyze it;
4. compare counts, keys, and business invariants;
5. update consumers through a coordinated cutover;
6. retain the old object for a bounded recovery window where appropriate;
7. remove it only after dependency verification.

Account for the temporary storage required to hold both versions.

## 22. Dependencies and removal

Drop requires ownership:

```sql
DROP MATERIALIZED VIEW reporting.daily_event_summary;
```

`RESTRICT` is the default and prevents removal when dependent database objects exist. `CASCADE` recursively removes dependent objects and must not be used as a discovery shortcut.

PostgreSQL dependency tracking does not know every external consumer, including application SQL, BI dashboards, ETL jobs, exports, ORM mappings, and documentation. Inventory those consumers separately.

Dropping a materialized view is transactional PostgreSQL DDL, but rollback is not a substitute for dependency analysis or tested recovery.

## 23. Capacity and replication planning

Before a large refresh, estimate and monitor:

- result and index size;
- free space in the target and temporary tablespaces;
- base-query CPU, memory, and I/O;
- temporary-file growth;
- WAL generation;
- physical-replica replay lag;
- backup overlap;
- autovacuum and foreground-workload contention;
- lock waits and consumer latency.

“Read-only for consumers” does not mean zero operational cost. A refresh mutates stored database state and can materially affect the whole cluster.

A failed or rolled-back refresh can still consume CPU, memory, temporary storage, I/O, lock time, and WAL-related resources. Transaction rollback removes transactional state changes; it does not erase operational impact already generated.

## 24. Scheduling strategy

Choose a schedule from the freshness contract and measured refresh duration, not from a convenient clock interval alone.

If refresh normally takes 18 minutes, a 15-minute schedule creates overlap pressure and cannot deliver a 15-minute freshness objective. Include runtime variance, retries, maintenance, failover, replica lag, and upstream-data arrival.

Event-driven refresh can reduce unnecessary work, but it still needs deduplication, backpressure, overlap control, and periodic reconciliation.

## 25. Managed PostgreSQL services

Core SQL semantics are broadly portable, but managed platforms can differ in:

- available roles and privilege delegation;
- scheduler integration;
- extension availability;
- tablespace and storage controls;
- monitoring and log access;
- replica and backup behavior;
- maintenance windows and resource limits.

Validate the procedure against the provider, service tier, and PostgreSQL major version. Do not assume self-managed superuser workflows are available.

## 26. Production refresh checklist

Before creating or refreshing a production materialized view, confirm:

- [ ] correct environment, endpoint, database, schema, and role;
- [ ] freshness objective and consumer behavior are documented;
- [ ] defining query and called functions are reviewed;
- [ ] ownership and least-privilege refresh authority are correct;
- [ ] stored rows, sensitive columns, grants, and RLS assumptions are reviewed;
- [ ] expected result identity and unique index are valid;
- [ ] ordinary versus concurrent refresh is intentional;
- [ ] population state is compatible with the chosen mode;
- [ ] runtime, locks, storage, temporary space, WAL, and replica impact are measured;
- [ ] overlapping refreshes are prevented or bounded;
- [ ] timeouts, retries, alerts, and escalation are defined;
- [ ] dependent database objects and external consumers are known;
- [ ] recovery and versioned rollback paths are tested;
- [ ] post-refresh freshness, business invariants, replica state, and query performance will be validated.

## 27. Hands-on lab

The companion lab is:

```text
labs/materialized-views-refresh-lab.sql
```

Classification:

```text
[LAB-ONLY — MUTATING — TRANSACTIONALLY CONTAINED]
```

It creates an isolated schema, base table, populated materialized view, qualifying unique index, and unpopulated materialized view. It proves staleness before refresh, ordinary and concurrent refresh behavior, population state, metadata, and cleanup.

Run it only in an authorized disposable, non-production database:

```bash
psql -X --set=ON_ERROR_STOP=1 \
  --set=lab_confirm=I_UNDERSTAND \
  --dbname=postgres \
  --file=labs/materialized-views-refresh-lab.sql
```

The lab rejects recovery servers and ends with `ROLLBACK`. Transaction containment reduces cleanup risk but does not make the lab read-only, free of locks, free of WAL-related work, or free of resource use. Do not add `COMMIT`.

## 28. Summary

A materialized view trades automatic freshness for stored query results. Its safe operation depends on an explicit freshness contract, correct unique-key design, suitable indexes, controlled refresh authority, overlap prevention, capacity planning, and meaningful monitoring.

Use ordinary refresh when reader blocking is acceptable. Use concurrent refresh only when continued reads justify its additional requirements and resource profile. Treat `WITH NO DATA`, definition replacement, and removal as availability or compatibility changes rather than routine query tuning.

The operational cycle is:

```text
Define freshness → Design identity → Measure refresh → Schedule safely
→ Observe outcome → Validate consumers → Improve
```
