# Part 3.2 — Schema Design and Administration

**Status:** Revised Final / Canonical Edition  
**Target:** PostgreSQL 18  
**Audience:** PostgreSQL administrators, DBREs, SREs, platform engineers, developers, and data engineers

## Learning objectives

By the end of this tutorial, you should be able to:

- explain what a PostgreSQL schema is and is not;
- distinguish database, schema, role, and object ownership;
- design schemas around durable application boundaries;
- inspect schemas, owners, privileges, and contained objects;
- understand name resolution and `search_path` safely;
- use schema-qualified names in administrative and security-sensitive work;
- plan schema creation, ownership changes, renames, and removal;
- recognize managed-service and extension considerations.

## 1. What is a PostgreSQL schema?

A schema is a namespace inside one database. It organizes database objects and allows the same unqualified object name to exist in different schemas.

```text
PostgreSQL cluster
└── Database: application_db
    ├── Schema: clinical
    │   ├── table: patient
    │   └── view: active_patient
    ├── Schema: billing
    │   └── table: patient
    └── Schema: audit
        └── table: event_log
```

`clinical.patient` and `billing.patient` are different objects because their qualified names differ. Schemas cannot be nested. Within one schema, relation-like objects—including tables, sequences, indexes, views, materialized views, and foreign tables—share a namespace, so some different object types cannot reuse the same name.

A schema is **not**:

- a separate PostgreSQL server;
- a separate database;
- an operating-system directory to administer manually;
- a complete security boundary by itself;
- an automatic performance or storage-isolation boundary.

Objects in different schemas of the same database still share that database's transactional and infrastructure context.

## 2. Why schemas matter

Schemas support several production needs:

- logical organization of objects;
- stable application or domain boundaries;
- control of naming collisions;
- ownership and privilege design;
- staged migrations and versioned interfaces;
- separation of application, reporting, audit, integration, and extension objects.

Schemas should represent durable operational boundaries—not arbitrary folders created for every developer, microservice method, or temporary experiment.

## 3. Schema design principles

### Use business or platform boundaries

Useful examples include:

```text
clinical
billing
audit
integration
reporting
platform
```

Avoid names that become meaningless quickly, such as `misc`, `temp2`, or a person's name in a shared production database.

### Keep names predictable

Prefer lowercase, unquoted identifiers:

```sql
clinical.patient
```

Quoted mixed-case names create persistent quoting requirements:

```sql
"Clinical"."Patient"
```

### Avoid duplicating security architecture accidentally

A schema can help define access boundaries, but safe access also depends on object ownership, schema privileges, object privileges, default privileges, role membership, and `search_path`. Part 4 covers the full privilege model.

### Define ownership deliberately

Production objects should normally be owned by controlled non-login or deployment roles rather than by individual user accounts. The exact model depends on organizational requirements.

## 4. Built-in schemas you will commonly see

### `public`

Every new database normally contains a `public` schema. Do not assume its effective privileges are identical across all clusters or upgraded environments. PostgreSQL 15 and later use a safer default posture, while a database upgraded from PostgreSQL 14 or earlier may still grant `CREATE` on `public` to `PUBLIC`. Template history and local policy can introduce further differences. Always inspect before changing privileges.

### `pg_catalog`

`pg_catalog` contains PostgreSQL system catalogs and built-in objects. It participates specially in name resolution. Do not create application objects there.

### `information_schema`

`information_schema` provides standards-oriented metadata views. It is useful for portable inspection, although PostgreSQL catalogs expose additional PostgreSQL-specific detail.

### Temporary schemas

PostgreSQL uses session-specific temporary schemas, commonly visible with names such as `pg_temp_3`. Their exact suffix is implementation-managed. Do not hard-code it. When an existing temporary schema is not explicitly positioned, PostgreSQL searches it before `pg_catalog` for relation and data-type names. It is never searched for function or operator names.

Schemas beginning with `pg_` are reserved for system purposes and should not be used for ordinary application namespaces.

## 5. Inspect schema inventory

From `psql`:

```text
\dn+
```

Using PostgreSQL catalogs:

```sql
SELECT
    n.oid,
    n.nspname AS schema_name,
    pg_get_userbyid(n.nspowner) AS owner
FROM pg_namespace AS n
ORDER BY n.nspname;
```

Using `information_schema`:

```sql
SELECT schema_name, schema_owner
FROM information_schema.schemata
ORDER BY schema_name;
```

These interfaces serve different purposes. `information_schema.schemata` is a privilege-filtered, standards-oriented view: it shows schemas the current role owns or can access. It can therefore contain fewer rows than `pg_namespace`, which exposes PostgreSQL-specific catalog information.

## 6. Schema ownership

A schema has an owner recorded in `pg_namespace.nspowner`.

```sql
SELECT
    n.nspname,
    pg_get_userbyid(n.nspowner) AS owner
FROM pg_namespace AS n
ORDER BY n.nspname;
```

Ownership is security-sensitive. A schema owner has significant authority over the namespace, but does not automatically own every existing object inside it. Objects have their own owners. However, the schema owner can drop the schema and, with `CASCADE`, remove contained objects even when other roles own some of them.

This distinction is fundamental:

```text
schema owner ≠ automatic owner of every contained object
```

Changing schema ownership therefore does not replace a deliberate contained-object ownership review.

## 7. Schema privileges

The two primary schema privileges are:

- `USAGE`: permits resolving and accessing objects in the schema, subject to privileges on those objects;
- `CREATE`: permits creating new objects in the schema.

`USAGE` alone does not grant `SELECT` on every table. `CREATE` does not grant ownership of unrelated existing objects.

Inspect access with:

```sql
SELECT
    n.nspname AS schema_name,
    pg_get_userbyid(n.nspowner) AS owner,
    n.nspacl
FROM pg_namespace AS n
ORDER BY n.nspname;
```

`nspacl` is useful catalog evidence, but ACL text requires careful interpretation. For role-specific checks, use privilege functions:

```sql
SELECT
    n.nspname,
    has_schema_privilege(current_user, n.oid, 'USAGE')  AS has_usage,
    has_schema_privilege(current_user, n.oid, 'CREATE') AS has_create
FROM pg_namespace AS n
ORDER BY n.nspname;
```

An effective privilege can come from direct grants, role membership, ownership, or superuser authority. Do not infer the source from a Boolean result alone.

## 8. Name resolution and `search_path`

When an SQL statement uses an unqualified name such as:

```sql
SELECT * FROM patient;
```

PostgreSQL must determine which schema contains `patient`. `search_path` controls the ordered namespace search.

Inspect it with:

```sql
SHOW search_path;
```

Inspect the effective path:

```sql
SELECT current_schemas(true);
```

The configured path and effective path are related but not identical concepts. A nonexistent schema, or one for which the role lacks `USAGE`, is silently ignored. If `pg_catalog` is not explicitly listed, it is searched before configured path entries; when explicitly listed, it is searched in that position. An existing temporary schema that is not explicitly positioned is searched first for relation and data-type names, but never for function or operator names.

## 9. `$user` in `search_path`

The default configuration commonly includes:

```text
"$user", public
```

`"$user"` is a placeholder for a schema whose name matches the current role. If no such schema exists or the role cannot use it, that entry does not become a usable namespace.

Do not interpret `$user` as a literal schema name to create automatically.

## 10. The current schema

Use:

```sql
SELECT current_schema;
```

This reports the first valid schema in the effective search path. It is also the default destination for unqualified object creation when the role has the required authority.

This is why a `search_path` mistake can affect both lookup and object creation.

## 11. Security implications of `search_path`

Adding a schema to `search_path` trusts users who can create objects in that schema. An attacker or accidental actor may create an object with a name that shadows an expected object.

Production rules:

1. Use schema-qualified names for migrations, administration, and security-sensitive routines.
2. Do not place writable-by-untrusted-roles schemas early in privileged search paths.
3. Review `CREATE` privilege on every schema in privileged paths.
4. Set a deliberate safe path for privileged routines and automation.
5. Do not assume `public` has the same privilege posture in every environment.

This tutorial introduces the risk; `SECURITY DEFINER` hardening belongs in Part 4.

## 12. Qualified names

Prefer:

```sql
SELECT * FROM clinical.patient;
```

over:

```sql
SELECT * FROM patient;
```

when correctness depends on a specific object.

Schema qualification improves predictability in:

- database migrations;
- deployment scripts;
- operational runbooks;
- monitoring queries;
- cross-team databases;
- privileged functions and procedures.

It does not replace privilege checks or safe identifier handling.

## 13. Creating a schema

Conceptually:

```sql
CREATE SCHEMA clinical AUTHORIZATION application_owner;
```

This is state-changing DDL. Creating a schema requires `CREATE` privilege on the current database. Creating it with another role as owner additionally requires the ability to `SET ROLE` to that role. User-created schema names cannot begin with `pg_`.

Before creating a production schema, confirm:

- correct cluster and database;
- naming and ownership standard;
- role existence and intended login posture;
- privilege and default-privilege design;
- deployment and rollback plan;
- expected objects and dependencies.

## 14. Renaming and changing ownership

Examples:

```sql
ALTER SCHEMA clinical RENAME TO clinical_core;

ALTER SCHEMA clinical_core OWNER TO application_owner;
```

These changes are not cosmetic. A rename can break applications, SQL, views outside dependency tracking, configuration, ETL jobs, monitoring, permissions automation, or external tooling that refers to a textual qualified name.

The executing role must own the schema. Renaming also requires `CREATE` on the database. Changing ownership requires the ability to `SET ROLE` to the new owner, and the new owner must have `CREATE` on the database. Changing the schema owner is security-sensitive and does not automatically reassign ownership of contained objects. A new schema name cannot begin with `pg_`.

## 15. Moving an object between schemas

Many object types support a form of:

```sql
ALTER TABLE staging.patient SET SCHEMA clinical;
```

Moving an object changes its qualified name. Review application references, privileges, ownership, dependent objects, replication and publication configuration, migration tooling, and operational queries before the change.

Do not use schema moves as an improvised production cleanup mechanism.

## 16. Dropping a schema

```sql
DROP SCHEMA schema_name;
```

Without `CASCADE`, PostgreSQL refuses to drop a nonempty schema. That refusal is useful dependency protection.

```sql
DROP SCHEMA schema_name CASCADE;
```

can remove contained objects and their dependents—even dependencies located in other schemas. It must not be used as a generic cleanup shortcut. The schema owner or a superuser can drop the schema; the owner can thereby remove contained objects owned by other roles.

Production decommissioning requires:

```text
Verify target → inventory objects → trace dependencies
→ confirm ownership and consumers → validate recovery path
→ obtain approval → execute controlled change → validate
```

A backup is a recovery path, not a transactional rollback for careless destructive DDL.

## 17. Schema object inventory

For an introductory inventory of relations:

```sql
SELECT
    n.nspname AS schema_name,
    c.relkind,
    count(*) AS object_count
FROM pg_class AS c
JOIN pg_namespace AS n ON n.oid = c.relnamespace
GROUP BY n.nspname, c.relkind
ORDER BY n.nspname, c.relkind;
```

`relkind` distinguishes relation-like object types. It does not inventory every possible schema-contained object. Later tutorials cover complete catalog-based inventory and dependency analysis.

## 18. Managed PostgreSQL considerations

Schema SQL semantics are broadly consistent across self-managed PostgreSQL, Amazon RDS/Aurora PostgreSQL, Azure Database for PostgreSQL, and Google Cloud SQL for PostgreSQL. Provider-created databases, roles, extensions, monitoring objects, and administrative restrictions can differ.

Never alter or remove an unfamiliar provider- or extension-managed schema merely because it is not part of the application design. Identify its owner and purpose first.

## 19. Production schema checklist

- [ ] Environment, endpoint, and database verified
- [ ] Schema purpose and owner documented
- [ ] Lowercase naming standard followed
- [ ] `USAGE` and `CREATE` privileges reviewed
- [ ] Contained-object privileges and default privileges planned
- [ ] `search_path` behavior tested with the intended roles
- [ ] Administrative SQL uses qualified names
- [ ] Provider- and extension-managed schemas identified
- [ ] Rename, move, and drop dependencies reviewed
- [ ] Recovery, rollback, validation, and monitoring plans available

## 20. Hands-on lab — disposable database only

The following exercise is intentionally state-changing and must run only in an authorized disposable, non-production database through a dedicated `psql` session. It uses one transaction and ends with `ROLLBACK`, so the tutorial objects are not intentionally preserved.

```text
[LAB-ONLY — MUTATING]
```

### Step 1 — Enable error handling and verify the target

```sql
\set ON_ERROR_STOP on

SELECT
    current_database(),
    current_user,
    inet_server_addr(),
    inet_server_port(),
    pg_is_in_recovery();
```

Stop unless the verified endpoint and database are explicitly approved for disposable lab work.

### Step 2 — Preflight collisions and begin

```sql
SELECT
    to_regnamespace('tutorial_clinical') AS existing_clinical_schema,
    to_regnamespace('tutorial_audit')    AS existing_audit_schema;
```

Both results must be `NULL`. Do not repurpose or remove pre-existing schemas.

```sql
BEGIN;
```

### Step 3 — Create isolated schemas

```sql
CREATE SCHEMA tutorial_clinical;
CREATE SCHEMA tutorial_audit;
```

### Step 4 — Create same-named objects

```sql
CREATE TABLE tutorial_clinical.tutorial_schema_event (
    event_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_name text NOT NULL
);

CREATE TABLE tutorial_audit.tutorial_schema_event (
    event_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_name text NOT NULL
);
```

### Step 5 — Compare qualified resolution

```sql
SELECT to_regclass('tutorial_clinical.tutorial_schema_event');
SELECT to_regclass('tutorial_audit.tutorial_schema_event');
```

### Step 6 — Test a transaction-local path

```sql
SET LOCAL search_path = tutorial_clinical, pg_catalog;
SELECT current_schema, current_schemas(true);
SELECT to_regclass('tutorial_schema_event');
```

`SET LOCAL` limits the setting to the current transaction. The example still uses a dedicated session and qualified names for lifecycle operations.

### Step 7 — Inventory before cleanup

```sql
SELECT
    n.nspname,
    c.relname,
    c.relkind,
    pg_get_userbyid(c.relowner) AS owner
FROM pg_class AS c
JOIN pg_namespace AS n ON n.oid = c.relnamespace
WHERE n.nspname IN ('tutorial_clinical', 'tutorial_audit')
ORDER BY n.nspname, c.relname;
```

### Step 8 — Practice explicit cleanup

```sql
DROP TABLE tutorial_clinical.tutorial_schema_event;
DROP TABLE tutorial_audit.tutorial_schema_event;
DROP SCHEMA tutorial_clinical;
DROP SCHEMA tutorial_audit;
```

The cleanup deliberately avoids `DROP SCHEMA ... CASCADE`.

### Step 9 — Validate cleanup, then roll back the lab transaction

```sql
SELECT
    to_regnamespace('tutorial_clinical') AS clinical_after_cleanup,
    to_regnamespace('tutorial_audit')    AS audit_after_cleanup;

ROLLBACK;

SELECT
    to_regnamespace('tutorial_clinical') AS clinical_after_rollback,
    to_regnamespace('tutorial_audit')    AS audit_after_rollback;

SHOW search_path;
```

All schema checks must return `NULL`. The transaction boundary also protects against leaving partially created tutorial objects when a later step fails; ending the dedicated session remains the final containment measure.

## 21. Companion SAFE-READ acceptance lab

The companion `labs/schema-admin-check.sql` performs observational checks only. It inventories schemas, owners, ACLs, current-role effective privileges, configured and effective search paths, and relation counts. In very large databases, broad catalog output may need an approved schema filter.

Run it with:

```bash
psql -X -v ON_ERROR_STOP=1 -d postgres -f labs/schema-admin-check.sql
```

SAFE-READ does not mean zero cost, and visibility can differ by role.

## 22. Production takeaways

1. A schema is a namespace inside one database—not an independent server or database.
2. Schema ownership and contained-object ownership are separate.
3. `USAGE`, `CREATE`, and object privileges solve different problems.
4. `search_path` affects both lookup and unqualified creation.
5. Writable schemas in privileged paths create a security risk.
6. Use qualified names when correctness or security matters.
7. Inspect dependencies before rename, move, or drop operations.
8. Never use `CASCADE` as routine cleanup.
9. Identify provider- and extension-managed schemas before changing them.

## 23. Summary

PostgreSQL schemas organize objects, control namespaces, and participate in ownership, privileges, and name resolution. Safe administration requires more than creating a folder-like name: it requires deliberate owners, least privilege, predictable `search_path`, qualified operational SQL, dependency review, and controlled lifecycle changes.

The key mental model is:

```text
Database → Schema namespace → Owned objects
              ↓
       privileges + search_path
              ↓
        predictable resolution
```
