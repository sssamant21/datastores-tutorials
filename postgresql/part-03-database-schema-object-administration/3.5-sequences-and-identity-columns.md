# Part 3.5 — Sequences and Identity Columns

**Status:** Revised Final / Canonical Edition  
**Target:** PostgreSQL 18  
**Audience:** PostgreSQL administrators, DBREs, SREs, developers, platform engineers, and data engineers

## Learning objectives

By the end of this tutorial, you should be able to:

- explain what a PostgreSQL sequence is and what it does not guarantee;
- distinguish standalone sequences, legacy `serial`, and SQL identity columns;
- choose between `GENERATED ALWAYS` and `GENERATED BY DEFAULT`;
- use `nextval`, `currval`, `lastval`, and `setval` correctly;
- inspect sequence definitions, ownership, dependencies, privileges, and exhaustion risk;
- recognize gaps, caching, concurrency, crash, replication, and failover implications;
- detect and repair sequence-to-table drift safely;
- run an isolated lab without leaving persistent objects.

## 1. What is a sequence?

A PostgreSQL sequence is a database object that atomically generates successive numeric values. Multiple sessions can call `nextval` concurrently and receive distinct values.

```text
Sequence object → nextval() → numeric value → inserted row
```

A sequence is not:

- a row counter;
- a guarantee of gapless numbering;
- proof of insert or commit order;
- a uniqueness constraint;
- a replacement for a primary key;
- a business invoice or audit-number generator.

## 2. Creating a standalone sequence

```sql
CREATE SEQUENCE clinical.patient_activity_id_seq
    AS bigint
    START WITH 1
    INCREMENT BY 1
    NO MINVALUE
    NO MAXVALUE
    CACHE 1
    NO CYCLE;
```

Valid sequence data types are `smallint`, `integer`, and `bigint`; `bigint` is the default. The type controls the default range, but sequence arithmetic cannot exceed the signed eight-byte integer range.

Use schema-qualified names in DDL and operational SQL.

## 3. Sequence parameters

| Parameter | Purpose |
|---|---|
| `AS` | Selects `smallint`, `integer`, or `bigint` range |
| `START` | Initial returned value |
| `INCREMENT` | Positive for ascending, negative for descending |
| `MINVALUE` / `MAXVALUE` | Bounds generated values |
| `CACHE` | Preallocates values per session |
| `CYCLE` | Wraps at the configured bound |
| `OWNED BY` | Associates lifecycle with a table column |

`CYCLE` is usually inappropriate for surrogate keys because wrapped values can collide with existing keys. `CACHE` improves throughput but increases the number of values that may be lost when sessions end, servers restart, or failover occurs. With a cache larger than one, concurrent sessions still receive distinct allocations, but values are not guaranteed to be returned in numerical order across sessions.

## 4. Sequence functions

### `nextval`

```sql
SELECT nextval('clinical.patient_activity_id_seq');
```

Atomically advances and returns the next value. It requires `USAGE` or `UPDATE` on the sequence.

### `currval`

```sql
SELECT currval('clinical.patient_activity_id_seq');
```

Returns the value most recently obtained through `nextval` for that sequence in the current session. It fails if this session has not called `nextval` for the sequence. It requires `USAGE` or `SELECT`.

### `lastval`

```sql
SELECT lastval();
```

Returns the value most recently obtained from any sequence in the current session. It can be ambiguous in code that uses multiple sequences; prefer `INSERT ... RETURNING` for row identifiers.

### `setval`

```sql
SELECT setval('clinical.patient_activity_id_seq', 100, true);
```

With `is_called = true`, the next `nextval` advances before returning a value. With `false`, the next `nextval` returns exactly the value supplied to `setval`. `setval` requires `UPDATE` privilege.

## 5. Sequence changes are not transactional allocations

Values returned by `nextval` are not reclaimed when a transaction or savepoint rolls back. `setval` changes are also immediately visible and are not undone by transaction rollback.

Gaps can result from:

- rolled-back transactions;
- failed inserts;
- `INSERT ... ON CONFLICT`;
- session termination with cached values;
- server restart or crash;
- promotion or failover;
- manual `setval` or restart operations;
- application-side allocation without a completed insert.

Therefore sequence-generated identifiers must be treated as unique technical identifiers, not as gapless business numbering.

## 6. Identity columns

An identity column is backed by an implicit sequence and declared as part of the table definition:

```sql
CREATE TABLE clinical.patient_activity (
    activity_id bigint
        GENERATED ALWAYS AS IDENTITY,
    patient_reference text NOT NULL,
    CONSTRAINT patient_activity_pk PRIMARY KEY (activity_id)
);
```

Identity automatically adds `NOT NULL`, but it does not add uniqueness. Declare a primary key or unique constraint separately.

## 7. `ALWAYS` versus `BY DEFAULT`

### `GENERATED ALWAYS`

```sql
activity_id bigint GENERATED ALWAYS AS IDENTITY
```

Explicit values are rejected unless the insert deliberately uses:

```sql
INSERT INTO clinical.patient_activity
    (activity_id, patient_reference)
OVERRIDING SYSTEM VALUE
VALUES (9001, 'MIGRATION-ROW');
```

This protects normal application writes from accidentally overriding generated values.

### `GENERATED BY DEFAULT`

```sql
activity_id bigint GENERATED BY DEFAULT AS IDENTITY
```

An explicit value takes precedence. This can help migrations and replication workflows, but it creates more opportunity for sequence drift or collisions.

Prefer `ALWAYS` unless a reviewed workflow requires routine explicit values.

When copying rows through `INSERT ... SELECT`, the opposite directive is also available:

```sql
INSERT INTO clinical.patient_activity
    (activity_id, patient_reference)
OVERRIDING USER VALUE
SELECT activity_id, patient_reference
FROM staging.patient_activity;
```

`OVERRIDING USER VALUE` ignores supplied identity values and generates replacements. For updates, an `ALWAYS` identity normally accepts only `DEFAULT`; a `BY DEFAULT` identity can be assigned explicitly.

## 8. `COPY FROM` identity exception

`COPY FROM` uses identity-column values supplied in its input regardless of whether the column is `GENERATED ALWAYS` or `GENERATED BY DEFAULT`.

```text
GENERATED ALWAYS
        ≠
protection from COPY-supplied identifiers
```

Every bulk-load, restore, or import workflow that supplies identifiers must validate uniqueness and sequence alignment before normal writes resume.

## 9. Identity sequence options

Identity sequence properties can be declared inline:

```sql
activity_id bigint GENERATED ALWAYS AS IDENTITY (
    START WITH 1000
    INCREMENT BY 1
    CACHE 32
    NO CYCLE
)
```

The correct cache size is workload-specific. Larger caches reduce synchronization overhead but increase potential gaps and make observed `last_value` less intuitive.

## 10. Identity, `serial`, and explicit defaults

Legacy shorthand:

```sql
activity_id bigserial
```

roughly creates an integer column, a sequence, a `nextval` default, and an ownership dependency. `serial` is not a true data type.

Modern schema design normally prefers:

```sql
activity_id bigint GENERATED ALWAYS AS IDENTITY
```

Identity has explicit SQL semantics, exposes `ALWAYS`/`BY DEFAULT`, and is represented directly in column metadata. Existing `serial` schemas remain valid and do not need conversion merely for style.

## 11. Retrieving generated identifiers

Prefer:

```sql
INSERT INTO clinical.patient_activity (patient_reference)
VALUES ('LAB-PATIENT-001')
RETURNING activity_id;
```

`RETURNING` ties the value to the inserted row. It avoids ambiguity from triggers, additional sequence calls, connection pooling, or other statements in the session.

Do not use `SELECT max(id)` to discover the row just inserted. Concurrent transactions make that unsafe.

## 12. Ownership and dependencies

For a standalone sequence:

```sql
ALTER SEQUENCE clinical.patient_activity_id_seq
OWNED BY clinical.patient_activity.activity_id;
```

The sequence and target table must have the same owner and schema. The dependency causes the sequence to be dropped if the associated column or table is dropped.

`OWNED BY` is lifecycle dependency, not a privilege grant. Table privileges do not automatically imply every sequence privilege needed by an application.

## 13. Privileges

Sequence privileges are separate from table privileges:

| Operation | Required sequence privilege |
|---|---|
| `nextval` | `USAGE` or `UPDATE` |
| `currval` / `lastval` | `USAGE` or `SELECT` |
| `setval` | `UPDATE` |
| `ALTER SEQUENCE` | Ownership |

Grant the runtime role only what it needs. `UPDATE` permits `setval`, so it is substantially more powerful than ordinary allocation through `USAGE`.

`INSERT` on a table does not automatically grant the sequence privilege needed to generate an identity or serial value. Provision table and sequence privileges deliberately.

## 14. Inspecting sequences

```sql
SELECT
    schemaname,
    sequencename,
    sequenceowner,
    data_type,
    start_value,
    min_value,
    max_value,
    increment_by,
    cycle,
    cache_size,
    last_value
FROM pg_sequences
ORDER BY schemaname, sequencename;
```

`pg_sequences.last_value` is the last value written to disk. With caching it can be ahead of the last value actually returned. It can be null if the sequence has not been read, the role lacks `USAGE`/`SELECT`, or an unlogged sequence is inspected on a standby.

Identity metadata is visible through `information_schema.columns`:

```sql
SELECT
    table_schema,
    table_name,
    column_name,
    is_identity,
    identity_generation,
    identity_start,
    identity_increment,
    identity_cycle
FROM information_schema.columns
WHERE is_identity = 'YES';
```

## 15. Finding the associated sequence

`pg_get_serial_sequence` works with serial-style and identity columns:

```sql
SELECT pg_get_serial_sequence(
    'clinical.patient_activity',
    'activity_id'
) AS associated_sequence;
```

Despite its name, it returns the sequence associated through the relevant dependency and is not limited to the `serial` shorthand.

Do not hard-code PostgreSQL-generated identity sequence names. For identity administration, prefer the table-level interface:

```sql
ALTER TABLE clinical.patient_activity
ALTER COLUMN activity_id RESTART WITH 5000;
```

## 16. Monitoring capacity and exhaustion

For an ascending sequence, monitor remaining range rather than only the current value:

```sql
SELECT
    schemaname,
    sequencename,
    last_value,
    max_value,
    max_value - last_value AS approximate_remaining
FROM pg_sequences
WHERE last_value IS NOT NULL
  AND increment_by > 0;
```

Because `last_value` can reflect cached reservations, this is capacity evidence rather than an exact count of emitted values.

Production monitoring should alert early enough to permit type enlargement, migration, or architectural remediation before exhaustion.

The sample query covers ascending sequences only. A complete monitor must handle negative increments, custom bounds, cycling, remaining percentage, and time-to-exhaustion at the observed allocation rate.

## 17. Detecting sequence drift

Drift commonly occurs after:

- bulk imports that preserve explicit identifiers;
- `COPY` into a table;
- migrations using `OVERRIDING SYSTEM VALUE`;
- manual inserts into a `BY DEFAULT` identity;
- restore or replication workflows;
- incorrect `setval` usage.

A collision can occur when the next generated value already exists in the table.

Inspect table maximum and sequence state separately. Do not treat a difference as automatically incorrect: cached or unused values can put the sequence ahead of table data legitimately.

## 18. Repairing drift safely

A common repair shape is:

```sql
SELECT setval(
    pg_get_serial_sequence('clinical.patient_activity', 'activity_id'),
    COALESCE(max(activity_id), 1),
    max(activity_id) IS NOT NULL
)
FROM clinical.patient_activity;
```

For an empty table, this example makes the next value `1`; for a nonempty table, the next value advances beyond the maximum.

Do not run this blindly. Correctness depends on the sequence start, increment direction, bounds, data type, and whether concurrent writes can occur. A safe repair requires:

1. verified table and sequence identity;
2. an approved write-control or locking strategy;
3. confirmed maximum or minimum according to sequence direction;
4. explicit `is_called` semantics;
5. post-repair insertion validation;
6. replication and failover review.

`setval` is not rolled back if a later operation fails.

## 19. `START WITH`, `RESTART WITH`, and `setval`

```sql
ALTER SEQUENCE clinical.patient_activity_id_seq
START WITH 5000;
```

`START WITH` changes the recorded start used by a future restart; it does not move the current value.

```sql
ALTER SEQUENCE clinical.patient_activity_id_seq
RESTART WITH 5000;
```

`ALTER SEQUENCE ... RESTART` is transactional and blocks concurrent `nextval` calls until the transaction ends. By contrast, `setval` is immediately visible, is not rolled back, and does not prevent sessions from using already cached values.

Changing increment, bounds, type, cache, cycle, ownership, or restart position is a production change requiring impact analysis.

## 20. Replication, backup, and failover

Sequence behavior depends on architecture:

- physical replication carries WAL-logged sequence state, but failover can still introduce gaps or apparent jumps;
- logical replication does not replicate sequence data; subscriber sequence state must be synchronized explicitly before promotion or writable cutover;
- restored tables and sequences must be checked together;
- unlogged sequences are reset after an unclean shutdown and are not replicated to standbys;
- externally published identifiers should be used only after the transaction allocating them commits.

Never assume that a promoted node or logical subscriber has the correct next sequence value without validation.

## 21. Partitioning and inheritance

Partitions inherit the identity column from the partitioned parent and cannot define independent identity columns for that inherited column. Identity properties remain consistent across the partition hierarchy.

Traditional inheritance differs: identity properties are not automatically inherited by child tables. Inspect the actual relation targeted by inserts.

## 22. Production checklist

- [ ] Correct endpoint, database, schema, table, column, and sequence verified
- [ ] Identity or sequence ownership and dependency understood
- [ ] `ALWAYS` versus `BY DEFAULT` justified
- [ ] Primary key or unique constraint exists where required
- [ ] Runtime sequence privileges follow least privilege
- [ ] Cache and gap expectations documented
- [ ] Exhaustion monitoring exists
- [ ] Explicit-value import workflow includes drift validation
- [ ] Repair accounts for empty tables, direction, bounds, and concurrency
- [ ] Replication, backup, restore, and failover behavior reviewed
- [ ] Application uses `INSERT ... RETURNING`
- [ ] Change, rollback, and recovery procedures tested
- [ ] `COPY` and explicit-value workflows include post-load alignment checks
- [ ] Logical-replication cutover includes explicit sequence synchronization

## 23. Hands-on lab — disposable database only

The companion lab is intentionally state-changing:

```text
[LAB-ONLY — MUTATING — TRANSACTIONALLY CONTAINED]
```

It requires explicit acknowledgement, fails closed on collisions, creates an isolated schema, demonstrates `ALWAYS` and `BY DEFAULT`, proves sequence gaps after savepoint rollback, inspects metadata, and ends by rolling back all created objects.

Because sequence allocations are not rolled back, the lab never calls an existing sequence. It creates every sequence it touches inside the isolated transaction and removes it when the outer transaction rolls back.

Run:

```bash
psql -X -v ON_ERROR_STOP=1 \
  -v lab_confirm=I_UNDERSTAND \
  -d disposable_database \
  -f labs/sequences-identity-lab.sql
```

## 24. Managed PostgreSQL services

The SQL semantics apply broadly to RDS for PostgreSQL, Aurora PostgreSQL-Compatible Edition, Azure Database for PostgreSQL, and Cloud SQL for PostgreSQL. Promotion workflows, replica behavior, logical-replication controls, backup/restore mechanisms, monitoring privileges, and supported engine versions differ. Verify the provider-specific procedure before sequence repair, restore, or failover.

## 25. Summary

Sequences provide concurrency-safe allocation, not gapless or commit-ordered numbering. Identity columns provide clearer table-level generation semantics but still require a primary or unique constraint when uniqueness matters.

```text
Generate → insert with RETURNING → monitor range
→ validate after imports/failover → repair only with write control
```
