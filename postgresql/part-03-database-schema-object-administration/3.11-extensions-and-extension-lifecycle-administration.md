# Part 3.11 — Extensions and Extension Lifecycle Administration

**Status:** Revised Final / Canonical Edition

**Target:** PostgreSQL 18

**Audience:** PostgreSQL administrators, DBREs, SREs, platform engineers, developers, and data engineers

**Companion lab:** `labs/extensions-lifecycle-lab.sql`

## Learning objectives

By the end of this tutorial, you should be able to:

- explain what a PostgreSQL extension is and what it can contain;
- distinguish extension files available on a server from extensions installed in a database;
- inventory installed extensions, versions, owners, schemas, dependencies, and members;
- interpret trusted, superuser, relocatable, required-extension, and version metadata;
- plan controlled extension installation, update, relocation, and removal;
- understand why `IF NOT EXISTS` and `CASCADE` are not desired-state validation;
- account for managed-service, replica, backup, binary, and failover constraints;
- run an isolated lifecycle lab without modifying a pre-existing extension.

## 1. What is a PostgreSQL extension?

A PostgreSQL extension packages related database objects so PostgreSQL can manage them as one logical unit. Depending on the extension, those objects can include:

- functions and procedures;
- data types and domains;
- operators and operator classes;
- casts;
- tables, views, and sequences;
- access methods;
- procedural languages;
- foreign-data wrappers and servers;
- configuration tables.

Installing an extension is not merely enabling a flag. `CREATE EXTENSION` runs the extension's installation script, creates its component objects, and records their membership so lifecycle operations can treat them as a unit.

Extensions can execute privileged SQL or native code. Treat them as software deployed inside the database trust boundary.

## 2. Available is not installed

These states are different:

```text
Extension files present on this server
                ≠
Extension installed in this database
```

`pg_available_extensions` lists extensions whose control files are available to this PostgreSQL server:

```sql
SELECT
    name,
    default_version,
    installed_version,
    comment
FROM pg_available_extensions
ORDER BY name;
```

`installed_version` is null when the extension is available but not installed in the current database.

`pg_extension` records extensions installed in the current database:

```sql
SELECT
    e.extname,
    e.extversion,
    pg_get_userbyid(e.extowner) AS owner,
    n.nspname AS extension_schema,
    e.extrelocatable
FROM pg_extension AS e
JOIN pg_namespace AS n
  ON n.oid = e.extnamespace
ORDER BY e.extname;
```

Extension installation is database-local. Installing an extension in one database does not automatically install it in every database in the cluster.

## 3. Supporting files are a host or service prerequisite

Before `CREATE EXTENSION` can work, the server must have the extension's supporting files. For self-managed PostgreSQL, these may come from PostgreSQL-supplied contrib packages, operating-system or vendor packages, approved third-party PGXS builds, or approved internal builds. These sources have different support, vulnerability-management, and licensing obligations.

For managed PostgreSQL, the provider controls which extensions and versions are offered. An extension listed in an upstream PostgreSQL distribution is not automatically available in every managed service, region, engine release, or service tier.

Do not copy unreviewed extension files directly into a production installation. Package provenance, checksums or signatures, compiler flags, PostgreSQL major-version compatibility, operating-system libraries, patching ownership, and upgrade behavior must be controlled.

## 4. Inspect installable versions and control metadata

`pg_available_extension_versions` exposes version-specific metadata:

```sql
SELECT
    name,
    version,
    installed,
    superuser,
    trusted,
    relocatable,
    schema,
    requires,
    comment
FROM pg_available_extension_versions
ORDER BY name, version;
```

Important fields include:

| Field | Administrative meaning |
|---|---|
| `installed` | This exact version is installed in the current database. |
| `superuser` | Installation is normally restricted to a superuser. |
| `trusted` | A non-superuser with `CREATE` on the database may install it under PostgreSQL's trusted-extension rules. |
| `relocatable` | The extension can be moved to another schema. |
| `schema` | Required installation schema, when fixed by the control file. |
| `requires` | Prerequisite extensions declared by the extension. |

This metadata is evidence, not approval. Visibility in these views proves only that the server can see the extension control files. It does not prove organizational approval, security, supportability, or license compliance. The extension's source, package, documentation, behavior, and organizational policy still require review.

## 5. Ownership and trusted extensions

The role executing `CREATE EXTENSION` becomes the owner of the extension object.

For a trusted extension installed by a non-superuser, the contained objects can be owned by the bootstrap superuser even though the calling user owns the extension. This allows the caller to drop the extension without granting unrestricted modification of its privileged members.

Avoid personal-account ownership. Prefer a controlled deployment or non-login owner role where the provider and privilege model allow it.

Before installation, verify:

- the exact deployment role;
- database `CREATE` privilege;
- whether superuser or provider-specific elevated authority is required;
- expected ownership of the extension and members;
- who will perform future updates or removal.

## 6. Secure installation schemas

Extension installation scripts can resolve object names through `search_path`. PostgreSQL warns that installing unreviewed extension scripts as superuser can be vulnerable to trojan-horse objects placed in schemas visible during installation.

Use a target schema where untrusted roles do not have `CREATE`. Apply the same review to schemas containing prerequisite extensions.

Example secure-schema inspection:

```sql
SELECT
    n.nspname,
    pg_get_userbyid(n.nspowner) AS owner,
    n.nspacl,
    has_schema_privilege('PUBLIC', n.oid, 'CREATE') AS public_can_create
FROM pg_namespace AS n
WHERE n.nspname = 'extensions';
```

Do not assume the schema is safe merely because it has a familiar name.

## 7. Plan installation explicitly

Conceptual installation for a reviewed extension whose schema contract permits this placement:

```sql
CREATE EXTENSION hstore
    WITH SCHEMA extensions
    VERSION '1.8';
```

Specify a version when reproducible deployment requires it and the exact version is available. Otherwise, PostgreSQL selects the control file's default version.

The target schema must already exist when `SCHEMA` is used. A fixed schema declared by the extension cannot normally be overridden, and not every extension is eligible for caller-selected schema placement.

Pre-installation checks should cover:

- extension package provenance and vulnerability review;
- PostgreSQL major and minor compatibility;
- available and approved version;
- required extensions and libraries;
- required server preload or restart settings;
- schema ownership and write privileges;
- database and object privileges;
- expected objects and data footprint;
- WAL, replica, backup, failover, and disaster-recovery behavior;
- rollback and uninstall limitations;
- application compatibility and observability.

## 8. `IF NOT EXISTS` is not validation

```sql
CREATE EXTENSION IF NOT EXISTS hstore;
```

suppresses the error when an extension with that name already exists. PostgreSQL does not guarantee that the existing installation matches the desired version, schema, owner, dependencies, member objects, or security posture.

Use explicit desired-state checks after deployment.

## 9. Dependency installation and `CASCADE`

`CREATE EXTENSION ... CASCADE` automatically installs missing prerequisite extensions recursively. Automatically installed prerequisites use their default versions; other options are not applied to them in the same way.

Do not use `CASCADE` merely to make an installation succeed. Review the complete dependency graph, versions, schemas, ownership, privileges, licensing, native libraries, and removal impact first.

## 10. Inventory extension dependencies

Extension-to-extension dependencies can be inspected through PostgreSQL dependency catalogs:

```sql
SELECT
    dependent.extname AS extension_name,
    required.extname AS required_extension
FROM pg_depend AS d
JOIN pg_extension AS dependent
  ON dependent.oid = d.objid
JOIN pg_extension AS required
  ON required.oid = d.refobjid
WHERE d.classid = 'pg_extension'::regclass
  AND d.refclassid = 'pg_extension'::regclass
  AND d.deptype = 'n'
ORDER BY dependent.extname, required.extname;
```

Catalog details require careful interpretation and can evolve. Confirm results against the extension documentation and tested deployment behavior.

This is a focused query for normal extension-to-extension dependencies, such as declared requirements. It is not a complete inventory of extension members or external application dependencies. Member relationships use dependency type `e` and are inspected separately.

## 11. Inspect extension members

`pg_depend` links extension members to the owning extension using dependency type `e`:

```sql
SELECT
    e.extname,
    d.classid::regclass AS catalog,
    d.objid,
    pg_describe_object(d.classid, d.objid, d.objsubid) AS member
FROM pg_extension AS e
JOIN pg_depend AS d
  ON d.refclassid = 'pg_extension'::regclass
 AND d.refobjid = e.oid
 AND d.deptype = 'e'
ORDER BY e.extname, member;
```

Member inventory can be large. Apply an approved extension filter in large environments.

Do not directly drop or redefine extension-owned objects as ordinary application objects. Their lifecycle belongs to the extension and its update scripts.

## 12. Configuration tables

`pg_extension.extconfig` and `extcondition` identify extension tables whose contents may need special handling during logical dump and restore.

Inspect them without assuming every extension has configuration tables:

```sql
SELECT
    e.extname,
    e.extconfig,
    e.extcondition
FROM pg_extension AS e
ORDER BY e.extname;
```

Backups must include both extension definitions and the required configuration data. Restore targets must have compatible extension files available.

## 13. Update planning

An extension update uses an update script supplied by the extension:

```sql
ALTER EXTENSION hstore UPDATE TO '1.8';
```

PostgreSQL must have a valid direct or chained update path from the installed version to the target. Never assume that the default available version is an approved target.

Before updating:

1. record installed version, owner, schema, dependencies, and members;
2. identify the exact target version and update path;
3. read vendor release notes and security advisories;
4. test with a production-like schema, data set, workload, and roles;
5. confirm backup and recovery procedures;
6. assess locks, runtime, WAL, replica lag, and application compatibility;
7. coordinate binaries on every server or service node that may host the database;
8. define post-update validation and rollback or forward-fix strategy.

Extension updates can execute arbitrary DDL and data migration supplied by the update scripts. Treat them as production changes, not metadata-only commands.

Do not assume an update is reversible. Many extensions provide no supported downgrade path. Define and test the appropriate recovery strategy—such as backup/restore, forward-fix, or a vendor-supported versioned migration—before the change.

## 14. Binary rollout and failover safety

For extensions with native libraries, SQL catalog state and server binaries form one compatibility contract.

All nodes that might execute extension code—including primary, standbys after promotion, restored hosts, and disaster-recovery targets—need compatible binaries. Rolling host replacement, failover, point-in-time recovery, and major-version upgrades must preserve this contract.

An extension can appear installed in `pg_extension` while its required shared library is missing or incompatible on a node. Validate actual load and representative behavior in approved non-production and post-change checks.

## 15. Relocation

Only relocatable extensions can be moved:

```sql
ALTER EXTENSION hstore SET SCHEMA extensions;
```

The operation requires ownership of the extension, `CREATE` privilege on the destination schema, and control metadata that permits relocation.

Relocation changes object qualification and can affect application SQL, `search_path`, permissions, security assumptions, views, functions, and operational tooling. Confirm the extension documentation and test consumers before moving it.

## 16. Adding or removing members

`ALTER EXTENSION ... ADD` and `ALTER EXTENSION ... DROP` change extension membership. They are primarily intended for extension authors and update scripts.

Removing a member from an extension does not drop the object; it disassociates it. Adding a member causes the object to follow extension lifecycle rules and prevents independent dropping.

Do not use membership changes as routine production repair without vendor or extension-owner guidance.

## 17. Removal

Default removal is restrictive:

```sql
DROP EXTENSION hstore RESTRICT;
```

Dropping an extension always drops its member objects. `RESTRICT` blocks removal when other objects depend on the extension beyond the allowed extension/member relationships.

`DROP EXTENSION ... CASCADE` can recursively drop dependent application objects. Never use it as a discovery shortcut.

Before removal, inventory:

- extension members;
- database dependencies;
- tables using extension-defined data types;
- indexes using extension operator classes or access methods;
- views, routines, casts, triggers, and generated expressions;
- application queries, drivers, ORMs, ETL, BI, and monitoring;
- backup/restore and replication dependencies;
- scheduled jobs and operational scripts.

A successful backup does not make immediate removal a safe rollback. Restoring can require compatible extension packages and meaningful downtime.

## 18. Transaction behavior and operational impact

Extension DDL is transactional when the extension scripts permit normal transactional execution. A rollback can remove transactional catalog changes, but it cannot erase CPU, memory, I/O, temporary-space, lock, log, WAL-related work, monitoring events, or audit evidence already produced.

Some extensions interact with external systems, background workers, shared libraries, preload settings, or nontransactional resources. Review extension-specific documentation instead of assuming database rollback is complete operational cleanup.

## 19. Managed PostgreSQL services

Managed services can restrict:

- the allowlist of extensions;
- available extension versions;
- installation roles;
- preload libraries and restart operations;
- filesystem access and custom builds;
- background workers;
- logical-decoding plugins;
- upgrade timing;
- cross-region replicas and disaster-recovery targets.

Use provider documentation for the exact service, engine version, and region. Do not translate a self-managed superuser procedure directly into RDS, Aurora PostgreSQL, Cloud SQL, AlloyDB, Azure Database for PostgreSQL, or another service without validation.

## 20. Monitoring and drift detection

Maintain an approved extension inventory containing:

- database and cluster identity;
- extension name and installed version;
- approved target version;
- owner and schema;
- trusted/superuser and relocatable classification;
- prerequisite extensions;
- package or service source;
- native-library requirements;
- business owner and technical owner;
- last review and update date;
- known vulnerabilities and exceptions.

Alert or review when installed versions drift, files disappear, unexpected extensions appear, ownership changes, schemas change, required preload configuration changes, or restore/failover validation fails.

## 21. Troubleshooting

### Extension is not available

If `CREATE EXTENSION` reports that the extension is unavailable, inspect `pg_available_extensions`. On self-managed systems, verify the correct package for the server's PostgreSQL major version. On managed services, verify provider support. Do not copy control or SQL files from another version as a shortcut.

### Permission denied

Check trusted/superuser metadata, current role, database `CREATE`, target-schema privileges, service-specific administrative roles, and the privileges required by member objects. Do not grant broad superuser-equivalent access merely to clear the error.

### No update path

Inspect installed and available versions and the extension's supported update paths. Do not edit `pg_extension.extversion` manually. Install the required package version or follow the vendor's supported staged-update procedure.

### Library cannot be loaded

Verify that the correct binary exists on the executing node, matches the PostgreSQL major version and platform, has its runtime dependencies, and is present on failover targets. Avoid symlink or library-path workarounds that bypass package governance.

### Removal blocked by dependencies

Keep `RESTRICT`, inspect dependencies, identify external consumers, and build a migration plan. Do not switch automatically to `CASCADE`.

## 23. Hands-on lab

The companion lab is:

```text
labs/extensions-lifecycle-lab.sql
```

Classification:

```text
[LAB-ONLY — MUTATING — TRANSACTIONALLY CONTAINED]
```

The canonical lab is locked to the PostgreSQL-supplied `hstore` extension and runs only after explicit lab and non-production acknowledgements. It also requires the operator to supply the exact expected database name. It refuses recovery servers, non-PostgreSQL-18 servers, database mismatches, a pre-existing target schema, an already-installed `hstore`, unavailable supporting files, incompatible schema metadata, and insufficient detected authority.

Before mutation, it captures the available default `hstore` version and the controlling security/schema metadata. It creates and hardens an isolated schema, installs that exact version, validates the name, version, owner, schema, relocatable state, and members, removes it with `RESTRICT`, rolls back, and verifies cleanup.

Run only in an authorized disposable, non-production database:

```bash
psql -X --set=ON_ERROR_STOP=1 \
  --set=lab_confirm=I_UNDERSTAND \
  --set=environment_confirm=NON_PRODUCTION \
  --set=expected_database=postgres \
  --dbname=postgres \
  --file=labs/extensions-lifecycle-lab.sql
```

The lab does not use `CASCADE`, does not update or adopt a pre-existing extension, and does not modify extension packages or server configuration. Substituting a different extension creates a different experiment that requires separate technical, security, operational, transaction-behavior, and licensing review.

The containment claim applies only to this reviewed `hstore` scenario. Rollback removes its transactional database changes; it does not erase the resource use or operational evidence described in Section 18, and it must not be generalized to arbitrary third-party extension scripts.

Static review is complete. Runtime implementation validation remains pending until the exact lab artifact is executed in an authorized disposable PostgreSQL 18 environment with evidence of its checksum, command line without secrets, server version, database and role, controlling metadata, PASS/ERROR transcript, exit status, and before/after absence of both `hstore` and `tutorial_extension_admin`.

## 24. Summary

PostgreSQL extensions are versioned software components inside the database trust boundary. Safe administration requires control of both database catalog state and the files or managed-service capabilities that make the extension executable.

Use read-only inventory before every lifecycle action. Install only reviewed packages into secure schemas, manage ownership deliberately, test exact update paths, align binaries across failover and recovery targets, and use restrictive dependency handling. Never treat `IF NOT EXISTS`, default versions, or `CASCADE` as substitutes for desired-state validation.
