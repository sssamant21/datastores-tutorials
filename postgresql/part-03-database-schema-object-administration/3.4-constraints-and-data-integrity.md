# Part 3.4 — Constraints and Data Integrity

**Status:** Revised Final / Canonical Edition  
**Target:** PostgreSQL 18  
**Audience:** PostgreSQL administrators, DBREs, SREs, developers, platform engineers, and data engineers

## Learning objectives

By the end of this tutorial, you should be able to:

- explain why database constraints are part of the data contract;
- use `NOT NULL`, `CHECK`, `UNIQUE`, `PRIMARY KEY`, and `FOREIGN KEY` correctly;
- distinguish constraint semantics from supporting-index behavior;
- choose intentional referential actions;
- understand immediate, deferred, validated, and not-yet-validated states;
- inspect constraint definitions and validation status;
- plan constraint changes safely for populated production tables;
- validate integrity without modifying application data.

## 1. Constraints are executable data contracts

Application validation improves usability, but it is not a substitute for database integrity. Data can also arrive through migrations, batch jobs, administrative SQL, integrations, CDC recovery, and multiple application versions.

A constraint makes a rule authoritative at the database boundary:

```text
request → application validation → database constraint → durable row
```

Constraints should represent stable invariants. Workflow rules that change frequently or depend on external state may belong elsewhere.

## 2. Constraint types

| Constraint | Purpose |
|---|---|
| `NOT NULL` | Reject a missing value in one column |
| `CHECK` | Require a row-level Boolean expression to be true or null |
| `UNIQUE` | Prevent duplicate constrained values or combinations |
| `PRIMARY KEY` | Declare the table's principal unique, non-null row identity |
| `FOREIGN KEY` | Require referenced values to exist |
| `EXCLUDE` | Prevent conflicting rows according to operators |

Use explicit, stable names such as `patient_activity_type_ck` or `patient_activity_patient_fk`. Names improve error messages, migrations, monitoring, and incident communication.

## 3. `NOT NULL`

```sql
patient_id bigint NOT NULL
```

`NOT NULL` is the clearest and most efficient declaration that a column must contain a value. It does not ensure that text is nonempty or that a number is positive; those require separate rules.

Before adding `NOT NULL` to a populated column, find violations:

```sql
SELECT count(*) AS null_rows
FROM clinical.patient_activity
WHERE patient_id IS NULL;
```

Exact counts can be expensive on large tables. Production validation should use an approved query plan, bounded execution controls, and workload-aware timing.

## 4. `CHECK` constraints and three-valued logic

```sql
CONSTRAINT patient_activity_type_ck
CHECK (activity_type IN ('ENCOUNTER', 'CLAIM', 'LAB'))
```

A check succeeds when its expression is `TRUE` or `NULL`; it fails only when the result is `FALSE`. Therefore the rule above does not reject a null `activity_type`. Use both constraints when a value is required:

```sql
activity_type text NOT NULL,
CONSTRAINT patient_activity_type_ck
    CHECK (activity_type IN ('ENCOUNTER', 'CLAIM', 'LAB'))
```

A table-level check can compare columns in the same row:

```sql
CONSTRAINT activity_time_order_ck
CHECK (completed_at IS NULL OR completed_at >= occurred_at)
```

Do not use a `CHECK` constraint to query other rows or tables. PostgreSQL assumes its result is stable for the same row and does not continuously re-evaluate existing rows when referenced functions or external data change. Use a key, foreign key, exclusion constraint, or carefully governed trigger for the appropriate cross-row rule.

## 5. `UNIQUE` constraints

```sql
CONSTRAINT patient_external_reference_uq
UNIQUE (source_system, external_reference)
```

PostgreSQL creates a unique B-tree index to enforce a unique constraint. The constraint is the data contract; the index is its enforcement mechanism.

By default, null values are distinct, so multiple rows containing null in a constrained column can be accepted. PostgreSQL can instead treat them as equal:

```sql
UNIQUE NULLS NOT DISTINCT (external_reference)
```

A partial uniqueness rule cannot be expressed as a normal unique constraint. A unique partial index can enforce it, but it remains an index-based rule and does not appear as a unique constraint in `pg_constraint`.

## 6. Primary keys

```sql
CONSTRAINT patient_activity_pk PRIMARY KEY (activity_id)
```

A primary key combines uniqueness and non-nullability and identifies the principal row key. PostgreSQL permits a table without a primary key, but most application tables should have one.

A table can have only one primary key, though it can contain multiple unique constraints. Composite keys are valid when identity is naturally composed of multiple attributes:

```sql
PRIMARY KEY (tenant_id, activity_id)
```

Key width affects every referencing foreign key and supporting index. Choose keys deliberately.

## 7. Foreign keys

```sql
CONSTRAINT patient_activity_patient_fk
FOREIGN KEY (patient_id)
REFERENCES clinical.patient (patient_id)
```

The child is the referencing table; the parent is the referenced table. The referenced columns must be backed by a non-deferrable primary key or unique constraint, or by a suitable non-partial unique index.

PostgreSQL does not automatically create an index on the referencing columns. Parent deletes and referenced-key updates may scan the child table, and common joins often need the same index:

```sql
CREATE INDEX patient_activity_patient_id_idx
ON clinical.patient_activity (patient_id);
```

An index is not automatically required for every foreign key. Validate the workload and query patterns, but make the decision explicitly.

## 8. Referential actions

| Action | Meaning |
|---|---|
| `NO ACTION` | Default; reject if integrity is not restored when checked |
| `RESTRICT` | Reject immediately and do not allow deferral |
| `CASCADE` | Propagate referenced delete or key update |
| `SET NULL` | Set selected referencing values to null |
| `SET DEFAULT` | Set referencing values to their defaults |

`CASCADE` is a business-lifecycle decision, not a convenience switch. It can turn one statement into a large delete or update operation, increasing locks, WAL, replica lag, trigger activity, CDC volume, and recovery complexity.

Choose actions based on ownership semantics:

- a component that cannot exist independently may justify `CASCADE`;
- an independent business record commonly uses `NO ACTION` or `RESTRICT`;
- optional attribution may justify `SET NULL`.

`SET NULL` and `SET DEFAULT` can still fail if another constraint rejects the resulting value.

Referential actions execute as part of the data-changing statement even when the foreign-key constraint itself is deferred.

## 9. Composite foreign keys and nulls

With the default `MATCH SIMPLE`, a composite foreign key is exempt when any referencing column is null. `MATCH FULL` permits either all columns null or all columns non-null and matching; a mixed null/non-null key fails.

If every relationship is required, declare each referencing column `NOT NULL` rather than relying only on foreign-key behavior.

Although `MATCH PARTIAL` appears in PostgreSQL syntax, PostgreSQL 18 does not implement it.

## 10. Immediate and deferred checking

Constraint timing depends on type. `NOT NULL` and `CHECK` constraints are checked when a row is inserted or modified. Non-deferrable uniqueness and exclusion constraints are also checked immediately. Eligible `UNIQUE`, `PRIMARY KEY`, `EXCLUDE`, and `FOREIGN KEY` constraints can be declared `DEFERRABLE` and checked later in the transaction.

```sql
CONSTRAINT example_fk
FOREIGN KEY (parent_id)
REFERENCES parent (parent_id)
DEFERRABLE INITIALLY IMMEDIATE
```

The transaction may then use:

```sql
SET CONSTRAINTS example_fk DEFERRED;
```

Deferral is not a performance toggle. It changes transaction semantics and can move an error from one statement to transaction completion. `NOT NULL` and `CHECK` constraints are not deferrable.

Deferrable constraints cannot be used as conflict arbiters by `INSERT ... ON CONFLICT`. Applications must also handle the possibility that individual statements succeed but `COMMIT` fails and rolls back the transaction.

## 11. Exclusion constraints

Exclusion constraints prevent pairs of rows from conflicting according to specified operators. They are useful for rules such as preventing overlapping reservations:

```sql
EXCLUDE USING gist (
    room_id WITH =,
    reservation_period WITH &&
)
```

They create an index of the declared access method and may require an extension-provided operator class. Treat extension installation and exclusion-index cost as separate reviewed decisions.

## 12. Constraint metadata

Portable inspection begins with `information_schema.table_constraints`, `key_column_usage`, `referential_constraints`, and `check_constraints`.

PostgreSQL-specific inspection uses `pg_constraint`:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    con.conname AS constraint_name,
    con.contype,
    con.conenforced,
    con.convalidated,
    con.condeferrable,
    con.condeferred,
    con.conperiod,
    con.conindid,
    pg_get_constraintdef(con.oid, true) AS definition
FROM pg_constraint AS con
JOIN pg_class AS c ON c.oid = con.conrelid
JOIN pg_namespace AS n ON n.oid = c.relnamespace
ORDER BY n.nspname, c.relname, con.conname;
```

Important `contype` values include `c` check, `f` foreign key, `n` not-null, `p` primary key, `u` unique, and `x` exclusion.

`conname` is not globally unique. Identify a constraint together with its schema, table, and catalog identity.

## 13. Enforced, validated, and documented states

PostgreSQL 18 distinguishes enforcement from validation:

| State | Existing rows | New or changed rows |
|---|---|---|
| Valid and enforced | Verified | Enforced |
| `NOT VALID` and enforced | Not yet fully verified | Enforced |
| `NOT ENFORCED` | Not guaranteed | Not enforced |

`NOT ENFORCED` is currently supported for check and foreign-key constraints. It can document an intended rule, but it is not a database-enforced integrity control. It is not equivalent to `NOT VALID`, and a not-enforced constraint cannot be validated while it remains not enforced.

## 14. Adding constraints to populated tables

Adding a constraint may scan existing rows, acquire strong locks, wait behind active transactions, and block other work. The exact behavior depends on constraint type, table state, PostgreSQL version, and chosen migration method.

For eligible foreign-key, check, and PostgreSQL 18 not-null constraints, a staged pattern is:

```sql
ALTER TABLE clinical.patient_activity
ADD CONSTRAINT patient_activity_type_ck
CHECK (activity_type IN ('ENCOUNTER', 'CLAIM', 'LAB'))
NOT VALID;

ALTER TABLE clinical.patient_activity
VALIDATE CONSTRAINT patient_activity_type_ck;
```

`NOT VALID` skips the initial full-table validation while enforcing the rule for subsequent inserts and updates. It does not mean the historical data is valid. `VALIDATE CONSTRAINT` must still be completed and monitored.

This staged technique is not available identically for every constraint type. Do not append `NOT VALID` blindly.

Validation acquires `SHARE UPDATE EXCLUSIVE` on the altered table. Foreign-key validation also requires a `ROW SHARE` lock on the referenced table. Validation permits ordinary row changes but can still consume substantial I/O and CPU.

## 15. Constraint changes and locking

Most `ALTER TABLE` forms acquire `ACCESS EXCLUSIVE` unless PostgreSQL documents a weaker lock. Even a fast catalog change can wait indefinitely behind a conflicting transaction unless operational boundaries are set.

A production migration should define:

```sql
SET lock_timeout = '5s';
SET statement_timeout = '30min';
```

Values are environment-specific. A timeout is a containment control, not proof that the operation is safe. Test the complete change against representative data and concurrency.

Most `ADD CONSTRAINT` operations require `ACCESS EXCLUSIVE`. `ADD FOREIGN KEY` instead takes `SHARE ROW EXCLUSIVE` on both the referencing and referenced tables. When several `ALTER TABLE` subcommands are combined, PostgreSQL uses the strongest lock required by any of them.

For a large populated table, an eligible primary or unique constraint can reuse a concurrently created index:

```sql
CREATE UNIQUE INDEX CONCURRENTLY patient_activity_id_uidx
ON clinical.patient_activity (activity_id);

ALTER TABLE clinical.patient_activity
ADD CONSTRAINT patient_activity_pk
PRIMARY KEY USING INDEX patient_activity_id_uidx;
```

The index must be unique, non-partial, expression-free, and a B-tree with default ordering. Primary-key columns must already be `NOT NULL` to avoid a validation scan. `CREATE INDEX CONCURRENTLY` cannot run inside a transaction block; monitor `pg_index.indisvalid`, handle failed builds explicitly, and schedule the final locking step.

## 16. Preflight validation

Before adding rules, search for violations. Examples:

```sql
-- Required value
SELECT activity_id
FROM clinical.patient_activity
WHERE activity_type IS NULL
LIMIT 100;

-- Duplicate business key
SELECT source_system, external_reference, count(*)
FROM clinical.patient_activity
GROUP BY source_system, external_reference
HAVING count(*) > 1
LIMIT 100;

-- Orphan foreign key
SELECT a.activity_id, a.patient_id
FROM clinical.patient_activity AS a
LEFT JOIN clinical.patient AS p
  ON p.patient_id = a.patient_id
WHERE a.patient_id IS NOT NULL
  AND p.patient_id IS NULL
LIMIT 100;
```

Bounded output does not necessarily bound the work needed to find rows. Review execution plans and resource cost first.

## 17. Constraint failure handling

Constraint violations are expected protective failures, not evidence that the database is malfunctioning. Applications should preserve the PostgreSQL SQLSTATE and constraint name in controlled telemetry without leaking sensitive values.

Examples include:

- `23502` — not-null violation;
- `23503` — foreign-key violation;
- `23505` — unique violation;
- `23514` — check violation.
- `23P01` — exclusion violation.

Do not solve repeated violations by disabling integrity. Identify whether the defect lies in input validation, concurrency handling, migration ordering, stale application assumptions, or the data contract itself.

## 18. Partitioned tables

Constraints on partitioned tables require extra review. A primary or unique constraint must include the partition-key columns of the target partitioned table and every descendant partitioned level because uniqueness is enforced through individual partition indexes. Foreign keys, attached partitions, and inherited checks must be validated across the hierarchy.

Do not infer whole-hierarchy integrity from inspecting only the parent. Inventory the parent and every partition.

## 19. PostgreSQL 18 temporal constraints

PostgreSQL 18 supports temporal uniqueness with `WITHOUT OVERLAPS` and temporal foreign keys with `PERIOD`:

```sql
UNIQUE (resource_id, valid_period WITHOUT OVERLAPS)
```

The temporal column must be a range or multirange, and empty ranges are not permitted. A temporal foreign key must reference a primary or unique key whose final column uses `WITHOUT OVERLAPS`, and its supported referential actions are more limited. Treat these as advanced, PostgreSQL 18-specific designs requiring workload and extension/operator-class review.

## 20. Replication, CDC, and bulk loading

Constraint changes can affect:

- publisher and subscriber DDL compatibility;
- logical replication apply order and failures;
- CDC schemas and downstream contracts;
- bulk-load throughput and error handling;
- restore ordering;
- ORM metadata and generated code.

PostgreSQL logical replication does not automatically reproduce arbitrary schema changes. Coordinate DDL explicitly across participants.

## 21. Production checklist

- [ ] Correct endpoint, database, schema, and table verified
- [ ] Business invariant and owner documented
- [ ] Existing violations measured safely
- [ ] Constraint and index names follow standards
- [ ] Null semantics reviewed
- [ ] Foreign-key actions approved by data owners
- [ ] Referencing-column indexing decision documented
- [ ] Lock, scan, WAL, and replica impact assessed
- [ ] Partition hierarchy and replication/CDC impact reviewed
- [ ] Rollout, rollback, and recovery paths tested
- [ ] Application error handling validated
- [ ] Post-change validation and monitoring defined
- [ ] Unvalidated or not-enforced constraints have an approved owner and deadline
- [ ] Sensitive rejected-row values are excluded from operational logs

## 23. Managed PostgreSQL services

The SQL concepts apply broadly to RDS for PostgreSQL, Aurora PostgreSQL-Compatible Edition, Azure Database for PostgreSQL, and Cloud SQL for PostgreSQL. Exact engine versions, feature availability, monitoring access, extension support, DDL tooling, replication topology, and timeout policies differ. Verify provider documentation before using PostgreSQL 18-specific temporal or not-enforced constraints.

## 24. Summary

Constraints are durable database-side contracts. Their design must account for null semantics, supporting indexes, referential lifecycle, validation state, concurrency, locking, partitioning, and replication.

```text
Define invariant → inspect existing data → choose semantics
→ test migration → deploy with boundaries → validate → monitor
```
