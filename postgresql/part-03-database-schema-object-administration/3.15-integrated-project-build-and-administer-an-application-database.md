# Part 3.15 — Integrated Project: Build and Administer an Application Database

## Revised Final / Canonical Edition

**Target:** PostgreSQL 18

**Track:** Part 3 — Database, Schema, and Object Administration

**Safety class:** Isolated-lab build plus read-only acceptance validation

**Companion lab:** `labs/application-database-acceptance.sql`

## Learning outcome

By the end of this project, you will be able to turn an application contract into an isolated PostgreSQL database, evolve and inspect its objects, validate its final state from system catalogs, and prepare a dependency-aware decommission plan.

## 1. Project brief

Build a small scheduling database for a fictional clinic. The database stores fictional patients, appointments, and appointment lifecycle events. It also exposes a scheduling view, a daily materialized summary, a calculation function, and a cancellation procedure.

This is an administration project, not a medical-record system design. Never use real patient information. Authentication, runtime-role grants, row-level security, encryption, audit policy, backup design, high availability, capacity planning, and production performance engineering require separate designs and reviews.

The fictional names, identifiers, birth dates, reasons, and event notes in this lab must remain synthetic. Do not substitute protected health information, production identifiers, exported records, or realistic data copied from a regulated system. A healthcare production design also requires approved data classification, minimum-necessary access, retention, encryption, audit, incident-response, and legal/compliance controls that this tutorial does not implement.

The project has two safety domains:

| Domain | Marker | Rule |
| --- | --- | --- |
| Build and evolution | `[LAB-ONLY — MUTATING]` | Run only in a disposable, authorized lab |
| Acceptance | `[TUTORIAL-ACCEPTANCE — SAFE-READ]` | Reads catalogs and project tables; makes no intentional database changes |

## 2. Final application contract

The canonical example uses these identifiers:

| Item | Required value |
| --- | --- |
| Database | `clinic_app_lab` |
| Schema | `clinic` |
| Owner role | `clinic_owner` |
| Tables | `patients`, `appointments`, `appointment_events` |
| View | `appointment_schedule_v` |
| Materialized view | `daily_appointment_summary_mv` |
| Function | `appointment_duration_minutes(timestamp with time zone, timestamp with time zone)` |
| Procedure | `cancel_appointment(bigint, text)` |

The owner role must already exist. Role creation, login policy, membership, and application grants belong to Part 4. Run the object-building statements as `clinic_owner` or through an approved deployment role that uses `SET ROLE clinic_owner`.

## 3. Preflight the isolated environment

`CREATE DATABASE` requires `CREATEDB` or superuser authority and cannot run inside a transaction block. Have a platform administrator create the lab database if you do not hold that authority.

```sql
-- [LAB-ONLY — MUTATING]
-- Run while connected to an administrative database, not clinic_app_lab.
CREATE DATABASE clinic_app_lab
    OWNER clinic_owner
    TEMPLATE template0
    ENCODING 'UTF8';
```

Connect explicitly, then fail closed if the connection is wrong:

```sql
\connect clinic_app_lab

SELECT current_database() = 'clinic_app_lab' AS correct_database,
       current_user,
       session_user,
       current_setting('server_version_num') AS server_version_num;
```

Do not continue unless `correct_database` is true and the server major is PostgreSQL 18. Database creation and deletion are intentionally separate from the transactional object build.

When converting the displayed snippets into a `psql` build script, use `--no-psqlrc` and `--set=ON_ERROR_STOP=1`, preserve the process exit code, and require an operator to verify the database and role before mutation. Do not concatenate the database-creation, object-build, expected-failure, acceptance, and decommission stages into one unattended script.

## 4. Build the schema and base tables

Use explicit names for governed constraints. Names make migration review, catalog inspection, and failure diagnosis less ambiguous.

```sql
-- [LAB-ONLY — MUTATING]
BEGIN;
SET LOCAL lock_timeout = '5s';
SET LOCAL statement_timeout = '60s';

CREATE SCHEMA clinic AUTHORIZATION clinic_owner;

CREATE TABLE clinic.patients (
    patient_id bigint GENERATED ALWAYS AS IDENTITY,
    external_patient_id text NOT NULL,
    first_name text NOT NULL,
    last_name text NOT NULL,
    display_name text GENERATED ALWAYS AS
        (last_name || ', ' || first_name) STORED,
    date_of_birth date NOT NULL,
    created_at timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT patients_pkey PRIMARY KEY (patient_id),
    CONSTRAINT patients_external_patient_id_key UNIQUE (external_patient_id),
    CONSTRAINT patients_external_patient_id_check
        CHECK (external_patient_id ~ '^P-[0-9]{4}$')
);

CREATE TABLE clinic.appointments (
    appointment_id bigint GENERATED ALWAYS AS IDENTITY,
    patient_id bigint NOT NULL,
    starts_at timestamp with time zone NOT NULL,
    ends_at timestamp with time zone NOT NULL,
    status text NOT NULL DEFAULT 'scheduled',
    reason text NOT NULL,
    created_at timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT appointments_pkey PRIMARY KEY (appointment_id),
    CONSTRAINT appointments_patient_id_fkey
        FOREIGN KEY (patient_id)
        REFERENCES clinic.patients (patient_id)
        ON DELETE RESTRICT,
    CONSTRAINT appointments_time_order_check CHECK (starts_at < ends_at),
    CONSTRAINT appointments_status_check
        CHECK (status IN ('scheduled', 'checked_in', 'completed', 'cancelled'))
);

CREATE TABLE clinic.appointment_events (
    event_id bigint GENERATED ALWAYS AS IDENTITY,
    appointment_id bigint NOT NULL,
    event_type text NOT NULL,
    event_note text,
    occurred_at timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT appointment_events_pkey PRIMARY KEY (event_id),
    CONSTRAINT appointment_events_appointment_id_fkey
        FOREIGN KEY (appointment_id)
        REFERENCES clinic.appointments (appointment_id)
        ON DELETE CASCADE,
    CONSTRAINT appointment_events_event_type_check
        CHECK (event_type IN ('created', 'checked_in', 'completed', 'cancelled'))
);

COMMIT;
```

Identity columns delegate key generation to PostgreSQL. The generated `display_name` is derived from other columns and cannot be supplied independently. Defaults provide values when an insert omits a column; they do not override an explicit value.

## 6. Prove integrity failures safely

Expected failures should not abort the build or leave data behind. Use savepoints and roll back each attempted violation.

```sql
-- [LAB-ONLY — MUTATING]
BEGIN;

SAVEPOINT duplicate_patient_test;
INSERT INTO clinic.patients
    (external_patient_id, first_name, last_name, date_of_birth)
VALUES ('P-1001', 'Duplicate', 'Example', DATE '2000-01-01');
-- Expect patients_external_patient_id_key to reject the insert.
ROLLBACK TO SAVEPOINT duplicate_patient_test;

SAVEPOINT invalid_time_test;
INSERT INTO clinic.appointments
    (patient_id, starts_at, ends_at, reason)
VALUES (:patient_avery, TIMESTAMPTZ '2030-01-16 11:00:00+00',
        TIMESTAMPTZ '2030-01-16 10:00:00+00', 'Invalid interval');
-- Expect appointments_time_order_check to reject the insert.
ROLLBACK TO SAVEPOINT invalid_time_test;

ROLLBACK;
```

In interactive `psql`, an error marks the transaction failed until the client processes `ROLLBACK TO SAVEPOINT`. For automated demonstrations, use separate invocations or a test harness designed to assert expected SQLSTATE values.

## 7. Evolve the schema with validation

Adding a check constraint as `NOT VALID` can separate installation from validation. New writes are still checked; existing rows are scanned when the constraint is validated. The final project contract requires no unvalidated constraints.

```sql
-- [LAB-ONLY — MUTATING]
BEGIN;
SET LOCAL lock_timeout = '5s';
SET LOCAL statement_timeout = '60s';

ALTER TABLE clinic.appointments
    ADD COLUMN check_in_at timestamp with time zone;

ALTER TABLE clinic.appointments
    ADD CONSTRAINT appointments_check_in_window_check
    CHECK (check_in_at IS NULL OR check_in_at <= ends_at) NOT VALID;

ALTER TABLE clinic.appointments
    VALIDATE CONSTRAINT appointments_check_in_window_check;

COMMIT;
```

Production migrations need workload-specific lock, scan, rollback, and observability plans. A short lab timeout is not a universal production value.

## 8. Add query-facing objects

The ordinary view always reads its underlying relations. The materialized view stores query results and must be refreshed deliberately.

```sql
-- [LAB-ONLY — MUTATING]
BEGIN;

CREATE VIEW clinic.appointment_schedule_v AS
SELECT
    a.appointment_id,
    p.external_patient_id,
    p.display_name,
    a.starts_at,
    a.ends_at,
    a.status,
    a.reason,
    a.check_in_at
FROM clinic.appointments AS a
JOIN clinic.patients AS p USING (patient_id);

CREATE MATERIALIZED VIEW clinic.daily_appointment_summary_mv AS
SELECT
    (a.starts_at AT TIME ZONE 'UTC')::date AS appointment_date,
    count(*) AS appointment_count,
    count(*) FILTER (WHERE a.status = 'cancelled') AS cancelled_count
FROM clinic.appointments AS a
GROUP BY (a.starts_at AT TIME ZONE 'UTC')::date
WITH NO DATA;

CREATE UNIQUE INDEX daily_appointment_summary_mv_date_uidx
    ON clinic.daily_appointment_summary_mv (appointment_date);

COMMIT;

REFRESH MATERIALIZED VIEW clinic.daily_appointment_summary_mv;
```

The explicit UTC conversion makes the reporting date independent of the session `TimeZone`. A real application must replace UTC with its approved reporting-zone contract when local business dates are required.

The unique index supplies a stable uniqueness contract and is also a prerequisite if a later operational design chooses `REFRESH MATERIALIZED VIEW CONCURRENTLY`. PostgreSQL requires the materialized view to have been populated before a concurrent refresh, so this lab performs a non-concurrent first refresh.

## 9. Add a function and a procedure

The function is a pure calculation. The procedure performs a small transactional business change when explicitly called. Neither uses `SECURITY DEFINER`.

```sql
-- [LAB-ONLY — MUTATING]
CREATE FUNCTION clinic.appointment_duration_minutes(
    start_time timestamp with time zone,
    end_time timestamp with time zone
)
RETURNS integer
LANGUAGE sql
IMMUTABLE
STRICT
PARALLEL SAFE
SECURITY INVOKER
SET search_path = pg_catalog
RETURN (EXTRACT(EPOCH FROM (end_time - start_time)) / 60)::integer;

CREATE PROCEDURE clinic.cancel_appointment(
    target_appointment_id bigint,
    cancellation_note text
)
LANGUAGE plpgsql
SECURITY INVOKER
SET search_path = pg_catalog
AS $procedure$
DECLARE
    changed_rows integer;
BEGIN
    IF cancellation_note IS NULL OR btrim(cancellation_note) = '' THEN
        RAISE EXCEPTION 'cancellation_note must not be blank';
    END IF;

    UPDATE clinic.appointments
       SET status = 'cancelled'
     WHERE appointment_id = target_appointment_id
       AND status <> 'cancelled';

    GET DIAGNOSTICS changed_rows = ROW_COUNT;
    IF changed_rows <> 1 THEN
        RAISE EXCEPTION 'appointment % was not cancellable',
            target_appointment_id;
    END IF;

    INSERT INTO clinic.appointment_events
        (appointment_id, event_type, event_note)
    VALUES
        (target_appointment_id, 'cancelled', cancellation_note);
END;
$procedure$;
```

`SET search_path = pg_catalog` reduces accidental name resolution, while schema-qualified application relations remain explicit. It does not convert the procedure into a privileged boundary. Part 4 must define who may execute routines and modify tables.

To exercise the procedure, use a savepoint or a disposable data copy, review the changed appointment and event rows, then decide whether to commit. The SAFE-READ acceptance artifact never calls it.

The example procedure demonstrates routine administration, not a complete cancellation workflow. Production behavior needs authorization, concurrency, idempotency, audit, notification, retention, and application-state requirements agreed with the application and data owners.

## 10. Inspect extension state without changing it

This application contract requires no extension. Record what is already installed:

```sql
SELECT e.extname,
       e.extversion,
       pg_catalog.pg_get_userbyid(e.extowner) AS owner,
       n.nspname AS schema_name,
       e.extrelocatable
FROM pg_catalog.pg_extension AS e
JOIN pg_catalog.pg_namespace AS n ON n.oid = e.extnamespace
ORDER BY e.extname;
```

Install an extension only when the application contract requires it, the PostgreSQL 18/platform compatibility matrix approves it, and the isolated lab permits it. Do not modify extension-owned objects directly.

## 11. Inventory ownership, metadata, and dependencies

Use catalogs as evidence, not as objects to edit. Useful review questions include:

- Does every project relation and routine have the expected owner?
- Does the database itself have the expected owner?
- Are all constraints enforced and validated?
- Are all indexes live, ready, and valid?
- Is the materialized view populated after the final refresh?
- Which sequence backs each identity column?
- Which objects depend on the base tables?
- Are routine kind, volatility, parallel safety, security mode, and configuration expected?

PostgreSQL records internal dependencies so that destructive DDL can reject unsafe operations under `RESTRICT` or propagate them under `CASCADE`. Catalog dependency rows do not describe every external consumer, SQL string, report, job, application, or operational process.

## 12. Run the acceptance artifact

```bash
psql --no-psqlrc \
  --dbname='postgresql://metadata_reader@db.example/clinic_app_lab' \
  --set=expected_database=clinic_app_lab \
  --set=expected_schema=clinic \
  --set=expected_owner=clinic_owner \
  --file=labs/application-database-acceptance.sql \
  --output=clinic-app-acceptance.txt
```

Use an approved password file, service definition, or secret mechanism rather than embedding a password. Preserve standard error and the process exit code. Exit `0` means the defined hard gates passed; exit `4` means one or more gates failed.

The acceptance artifact requires catalog visibility plus `USAGE` on schema `clinic` and `SELECT` on the three project tables. Use a dedicated metadata-validation role with only the access needed for these checks; do not use the application owner merely to avoid permission errors. A failure caused by insufficient access is not evidence that the database is unhealthy—it means the run did not establish acceptance.

The transcript contains roles, object names, configuration metadata, extension versions, dependencies, and row counts. Treat it as internal operational evidence, store it in an approved location, apply retention requirements, and remove connection details before broader sharing. The sample-data checks return counts only and do not export patient rows.

The artifact uses a `REPEATABLE READ`, `READ ONLY` transaction so its catalog observations share one database snapshot. It still takes ordinary read locks and retains its snapshot until completion. Run it as a bounded check, monitor unexpected duration, and cancel it through an approved process rather than leaving an idle transaction open.

## 13. Prepare, but do not casually execute, decommissioning

Before removing anything:

1. identify the exact target and owner;
2. inventory PostgreSQL dependencies;
3. identify external consumers that catalogs cannot see;
4. preserve required backups and evidence;
5. obtain application, data, security, and platform approvals;
6. stop traffic and scheduled work through an approved change plan;
7. rehearse `DROP ... RESTRICT` in a faithful non-production environment;
8. define recovery criteria and validate restoration;
9. use `CASCADE` only after reviewing every dependent object it will remove.

Destructive command shape for an approved lab rehearsal only:

```sql
-- [LAB-ONLY — MUTATING — DECOMMISSION REHEARSAL]
-- Intentionally non-executable in this tutorial.
-- DROP DATABASE clinic_app_lab;
```

Dropping a database is irreversible from PostgreSQL's perspective, terminates the application's database boundary, and requires a tested, restorable backup if recovery is needed. This tutorial deliberately omits `WITH (FORCE)`: forcibly terminating sessions must never substitute for application shutdown, connection draining, dependency review, approvals, and a rollback plan.

## 15. Success criteria

You can explain and demonstrate that:

- the work occurred only in the intended PostgreSQL 18 lab database;
- all required objects exist with the expected kinds and owner;
- identity, generated, defaulted, and evolved columns match the contract;
- required constraints exist and are enforced and validated;
- the materialized view is populated and its unique index is healthy;
- the required function and procedure have exact identities and are invoker-security routines;
- the fictional dataset meets the acceptance minimums;
- the acceptance script performs no intentional writes or routine execution;
- extension state and dependency data were reviewed rather than guessed;
- decommissioning remains a reviewed plan, not an ad hoc command.

## 16. Review questions

1. Why is the database boundary created outside the object-build transaction?
2. What is the difference between an identity column, a default, and a generated column?
3. Why must the staged `NOT VALID` constraint be validated before final acceptance?
4. Why does a materialized view need an explicit refresh?
5. Why does the acceptance artifact inspect the procedure but refuse to call it?
6. What dependency classes can PostgreSQL catalogs not discover?
