## 1. Learning Objectives

By the end of this tutorial, you should be able to:

- explain PostgreSQL functions and procedures;
- identify when a function or procedure is appropriate;
- inspect routines through PostgreSQL system catalogs;
- understand routine signatures and overloading;
- distinguish `SECURITY INVOKER` from `SECURITY DEFINER`;
- safely manage routine ownership and `EXECUTE` privileges;
- understand function volatility;
- understand parallel-safety classifications;
- understand procedure transaction-control restrictions;
- safely deploy changes to production routines;
- troubleshoot common function/procedure problems;
- validate routine configuration without changing production state.

# 2. What Is a PostgreSQL Function?

A PostgreSQL function is a database routine that accepts zero or more arguments and returns a result.

A function can return:

- a scalar value;
- a composite value;
- a set of rows;
- a table;
- `void`.

Example:

```sql
CREATE FUNCTION app.add_numbers(
    p_a integer,
    p_b integer
)
RETURNS integer
LANGUAGE sql
IMMUTABLE
AS $$
    SELECT p_a + p_b;
$$;

```

It can be invoked as part of SQL:

```sql
SELECT app.add_numbers(10, 20);

```

Result:

```text
30

```

Functions can therefore participate directly in queries and expressions.

---

# 3. What Is a PostgreSQL Procedure?

A procedure is another type of PostgreSQL routine.

Unlike a function, it is normally invoked with:

```sql
CALL schema.procedure_name(...);

```

Example:

```sql
CREATE PROCEDURE app.refresh_application_data()
LANGUAGE plpgsql
AS $$
BEGIN
    -- administrative/application work
    NULL;
END;
$$;

```

Invocation:

```sql
CALL app.refresh_application_data();

```

Procedures are useful when an operation represents procedural work rather than a value that needs to participate in a SQL expression.

---

# 4. Function vs Procedure

A useful administrative mental model is:

| CharacteristicFunctionProcedure |                                                     |                                                    |
| ------------------------------- | --------------------------------------------------- | -------------------------------------------------- |
| Typical invocation              | `SELECT` / SQL expression                           | `CALL`                                             |
| Returns a SQL value             | Yes                                                 | Not through a function-style return value          |
| `OUT` / `INOUT` parameters      | Supported                                           | Supported                                          |
| Used inside SQL expressions     | Yes                                                 | No                                                 |
| Transaction control             | No                                                  | Possible only in permitted contexts                |
| Common use                      | calculations, transformations, reusable query logic | procedural workflows and administrative operations |

Do not choose a procedure merely because the operation is complicated.

Choose the routine type according to its SQL and transaction semantics.

---

# 5. Languages

PostgreSQL routines can use different procedural languages.

Common examples include:

```text
SQL
PL/pgSQL

```

Inspect installed languages with:

```sql
SELECT
    lanname,
    lanpltrusted
FROM pg_language
ORDER BY lanname;

```

A language being available does not mean every user should be permitted to create arbitrary routines using it.

Production environments should apply normal privilege and change-management controls.

---

# 6. Routine Identity

A PostgreSQL routine is not identified by name alone.

For functions and procedures, the input argument types participate in routine identity.

For example:

```text
app.calculate_score(integer)
app.calculate_score(bigint)
app.calculate_score(integer, integer)

```

can represent different routines.

This capability is called **overloading**.

Therefore, production administration should use exact signatures whenever ambiguity is possible.

For example:

```sql
DROP FUNCTION app.calculate_score(integer);

```

is substantially safer than assuming the name uniquely identifies the object.

The same principle applies to administrative operations involving:

```text
ALTER
DROP
GRANT
REVOKE
COMMENT

```

# 7. Inspecting Functions and Procedures

PostgreSQL stores routine metadata primarily in `pg_proc`.

A useful read-only query is:

```sql
SELECT
    n.nspname AS schema_name,
    p.proname AS routine_name,
    pg_get_function_identity_arguments(p.oid) AS identity_arguments,
    CASE p.prokind
        WHEN 'f' THEN 'function'
        WHEN 'p' THEN 'procedure'
        WHEN 'a' THEN 'aggregate'
        WHEN 'w' THEN 'window function'
        ELSE p.prokind::text
    END AS routine_kind,
    pg_get_userbyid(p.proowner) AS owner,
    l.lanname AS language
FROM pg_proc AS p
JOIN pg_namespace AS n
    ON n.oid = p.pronamespace
JOIN pg_language AS l
    ON l.oid = p.prolang
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY
    n.nspname,
    p.proname,
    identity_arguments;

```

This is preferable to making assumptions from routine names.

---

# 8. `prokind`

PostgreSQL exposes the routine type through `pg_proc.prokind`.

Important values include:

```text
f = normal function
p = procedure
a = aggregate
w = window function

```

For administrative inventory, always distinguish these object types rather than assuming everything in `pg_proc` is a normal function.

---

# 9. Routine Ownership

Every function and procedure has an owner.

Inspect ownership with:

```sql
SELECT
    n.nspname,
    p.proname,
    pg_get_function_identity_arguments(p.oid),
    pg_get_userbyid(p.proowner) AS owner
FROM pg_proc AS p
JOIN pg_namespace AS n
    ON n.oid = p.pronamespace
WHERE n.nspname = 'app';

```

Ownership is especially important for privileged routines.

The owner can administer the routine, and for a `SECURITY DEFINER` function the owner's privileges become part of the execution security model.

### Production rule

Avoid making ordinary application login roles owners of privileged routines without an explicit design reason.

Prefer controlled ownership and explicit execution privileges.

---

# 10. `SECURITY INVOKER`

Functions use `SECURITY INVOKER` by default.

Conceptually:

```text
caller
   ↓
function
   ↓
caller privileges

```

The function executes using the privileges of the caller.

This should normally be preferred when elevated privileges are unnecessary.

---

# 11. `SECURITY DEFINER`

A `SECURITY DEFINER` function executes using the privileges of the function owner.

Conceptually:

```text
application role
       ↓
SECURITY DEFINER function
       ↓
function-owner privileges
       ↓
controlled operation

```

This can provide a useful privilege boundary.

It can also create a privilege-escalation vulnerability if implemented incorrectly.

---

# 12. Secure `SECURITY DEFINER`

A privileged function must not blindly inherit an unsafe caller-controlled object-resolution environment.

A safer pattern is:

```sql
CREATE FUNCTION admin.some_operation(...)
RETURNS ...
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = admin, pg_temp
AS $$
BEGIN
    ...
END;
$$;

```

The trusted schema should appear before `pg_temp`.

Do not include schemas writable by untrusted users in the trusted resolution path.

Where practical, schema-qualify important objects explicitly:

```sql
SELECT ...
FROM admin.control_table;

```

### Production security gate

```text
SECURITY DEFINER requested
        ↓
Is elevated privilege actually necessary?
        ↓
Controlled owner?
        ↓
Trusted search_path?
        ↓
Objects schema-qualified where appropriate?
        ↓
PUBLIC EXECUTE reviewed?
        ↓
Explicit least-privilege grants?
        ↓
Security review

```

A `SECURITY DEFINER` function should be treated as privileged executable database code.

---

# 13. Default `PUBLIC EXECUTE`

A commonly overlooked PostgreSQL behavior is the initial privilege configuration for newly created functions.

New functions normally receive `EXECUTE` privilege for `PUBLIC`.

For privileged routines, production deployment should explicitly address this.

A useful deployment pattern is:

```sql
BEGIN;

CREATE FUNCTION admin.controlled_operation(integer)
RETURNS integer
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = admin, pg_temp
AS $$
BEGIN
    ...
END;
$$;

REVOKE ALL
ON FUNCTION admin.controlled_operation(integer)
FROM PUBLIC;

GRANT EXECUTE
ON FUNCTION admin.controlled_operation(integer)
TO application_runtime;

COMMIT;

```

Using the same transaction prevents an unintended exposure period between object creation and privilege correction.

Organizations can additionally establish appropriate default privileges where that matches their security model.

---

# 14. Inspect Routine ACLs

Routine privileges can be inspected through `pg_proc.proacl`.

Example:

```sql
SELECT
    n.nspname AS schema_name,
    p.proname,
    pg_get_function_identity_arguments(p.oid) AS identity_arguments,
    p.proacl
FROM pg_proc AS p
JOIN pg_namespace AS n
    ON n.oid = p.pronamespace
WHERE n.nspname = 'app';

```

For operational investigations, also use PostgreSQL privilege-checking functions rather than attempting to interpret every ACL manually.

---

# 15. Function Volatility

PostgreSQL functions have volatility classifications:

```text
VOLATILE
STABLE
IMMUTABLE

```

These are behavioral promises to PostgreSQL's optimizer.

They are **not performance switches**.

## VOLATILE

The broadest classification.

Use it when a function can change database state or its result can vary in ways incompatible with `STABLE` or `IMMUTABLE`.

## STABLE

Indicates that within a single statement the function can be treated according to PostgreSQL's `STABLE` semantics.

## IMMUTABLE

Indicates that the result depends only on its explicit arguments under the required PostgreSQL semantics.

For example:

```sql
CREATE FUNCTION app.double_value(integer)
RETURNS integer
LANGUAGE sql
IMMUTABLE
AS $$
    SELECT $1 * 2;
$$;

```

### Production rule

Never label a function `IMMUTABLE` or `STABLE` merely because doing so appears to improve query performance.

Incorrect volatility classification can produce incorrect optimizer assumptions.

---

# 16. Inspect Volatility

`pg_proc.provolatile` records volatility.

Common values:

```text
i = IMMUTABLE
s = STABLE
v = VOLATILE

```

Read-only inspection:

```sql
SELECT
    n.nspname,
    p.proname,
    pg_get_function_identity_arguments(p.oid),
    CASE p.provolatile
        WHEN 'i' THEN 'IMMUTABLE'
        WHEN 's' THEN 'STABLE'
        WHEN 'v' THEN 'VOLATILE'
    END AS volatility
FROM pg_proc AS p
JOIN pg_namespace AS n
    ON n.oid = p.pronamespace
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema');

```

---

# 17. Parallel Safety

PostgreSQL also classifies functions according to parallel-query safety:

```text
PARALLEL SAFE
PARALLEL RESTRICTED
PARALLEL UNSAFE

```

A user-defined function is treated conservatively unless explicitly classified otherwise.

Do not mark a routine `PARALLEL SAFE` simply to encourage parallel plans.

A function that changes database state, manipulates transaction state, accesses sequences, or performs other parallel-unsafe operations must not be falsely declared safe.

### Production rule

When uncertain:

```text
keep the conservative classification
        ↓
understand every operation
        ↓
validate dependencies
        ↓
only then consider a less restrictive classification

```

Correctness takes priority over planner optimization.

---

# 18. Inspect Parallel Safety

`pg_proc.proparallel` contains this information.

Typical values:

```text
s = SAFE
r = RESTRICTED
u = UNSAFE

```

Example:

```sql
SELECT
    n.nspname,
    p.proname,
    pg_get_function_identity_arguments(p.oid),
    CASE p.proparallel
        WHEN 's' THEN 'SAFE'
        WHEN 'r' THEN 'RESTRICTED'
        WHEN 'u' THEN 'UNSAFE'
    END AS parallel_safety
FROM pg_proc AS p
JOIN pg_namespace AS n
    ON n.oid = p.pronamespace;

```

# 19. Procedure Transaction Control

Procedures introduce an important distinction from functions.

Under permitted invocation conditions, a procedure can perform transaction control.

For example, procedural code may use:

```text
COMMIT
ROLLBACK

```

but this capability is **context-dependent**.

Do not teach:

> Procedures can always commit and rollback.

That statement is incorrect.

---

# 20. `CALL` and Transaction Context

Consider:

```sql
BEGIN;

CALL app.some_procedure();

COMMIT;

```

Because the `CALL` is being executed inside an explicit transaction block, the called procedure cannot independently perform transaction control.

Procedure transaction control is available only under PostgreSQL's permitted invocation conditions.

---

# 21. Nested Procedure Calls

A chain consisting of procedure calls can retain transaction-control capability under the documented conditions:

```text
CALL procedure_a()
   ↓
CALL procedure_b()

```

But an intervening ordinary SQL command changes the situation.

Conceptually:

```text
CALL procedure_a()
   ↓
SELECT function_b()
   ↓
CALL procedure_c()

```

The inner procedure cannot use transaction-control commands through that intervening command chain.

This boundary matters when designing administrative workflows.

---

# 22. Additional Transaction-Control Restrictions

A procedure declared:

```sql
SECURITY DEFINER

```

cannot execute transaction-control statements.

Likewise, a procedure with a `SET` clause attached to its definition cannot execute transaction-control statements.

These restrictions should be reviewed before designing procedures intended to manage transaction boundaries.

---

# 23. `OUT` and `INOUT` Parameters

Functions and procedures can use output parameters, but invocation behavior matters.

For plain SQL `CALL`, arguments must be supplied for parameters that do not have defaults, including `OUT` parameters.

Conventionally, `NULL` is supplied for an `OUT` argument because that input value is not evaluated.

Example conceptually:

```sql
CALL app.lookup_status(1001, NULL);

```

PL/pgSQL procedure invocation has different variable-binding behavior for output parameters.

Do not assume SQL `CALL` and PL/pgSQL procedure invocation are identical.

---

# 24. `CREATE OR REPLACE`

`CREATE OR REPLACE FUNCTION` is useful for compatible routine deployments.

Example:

```sql
CREATE OR REPLACE FUNCTION app.calculate_total(integer)
RETURNS integer
...

```

However, it cannot be used to change every part of routine identity.

For functions, changes such as input argument types or return type can require a different deployment strategy.

Dropping and recreating a routine can affect:

- dependencies;
- permissions;
- ownership assumptions;
- application availability;
- objects referencing the routine.

Therefore:

```text
Do not automatically DROP + CREATE.

```

Prefer:

```text
inspect current definition
        ↓
identify exact signature
        ↓
review dependencies
        ↓
determine replacement compatibility
        ↓
deploy
        ↓
verify owner
        ↓
verify ACL
        ↓
functional validation

```

# 25. View a Routine Definition

PostgreSQL provides:

```sql
pg_get_functiondef()

```

Example:

```sql
SELECT pg_get_functiondef(p.oid)
FROM pg_proc AS p
JOIN pg_namespace AS n
    ON n.oid = p.pronamespace
WHERE n.nspname = 'app'
  AND p.proname = 'calculate_total';

```

This is extremely useful during incident investigation and deployment review.

Be careful when exporting or sharing definitions: routine source code may contain organization-specific logic or sensitive implementation details.

# 26. Dependencies

Before removing or significantly changing a routine, inspect dependencies.

Production problems can occur when a function is referenced by:

- views;
- indexes;
- generated expressions;
- constraints;
- triggers;
- other routines;
- application SQL.

Avoid using:

```sql
DROP ... CASCADE

```

as an exploratory troubleshooting technique.

`CASCADE` can remove dependent objects.

Always determine the dependency impact first.

---

# 27. Safe Production Deployment

A production routine change should follow a controlled sequence.

```text
1. Identify exact routine
        ↓
2. Capture current definition
        ↓
3. Capture owner and privileges
        ↓
4. Review dependencies
        ↓
5. Review security mode
        ↓
6. Validate search_path
        ↓
7. Validate volatility
        ↓
8. Validate parallel classification
        ↓
9. Test in non-production
        ↓
10. Prepare rollback
        ↓
11. Deploy
        ↓
12. Verify definition
        ↓
13. Verify owner and ACL
        ↓
14. Functional validation
        ↓
15. Monitor

```

---

# 28. Rollback Planning

Before changing a production routine, preserve enough information to restore the previous state.

At minimum capture:

```text
exact signature
definition
owner
EXECUTE privileges
security mode
configuration settings

```

Do not assume restoring only the source body restores the complete security configuration.

---

# 29. Safe Logging

PL/pgSQL supports diagnostic messages such as:

```sql
RAISE NOTICE;
RAISE WARNING;
RAISE EXCEPTION;

```

Remember that messages can be returned to clients and/or written to PostgreSQL logs depending on severity and configuration.

Do not expose:

```text
passwords
tokens
credentials
personal information
health information
full sensitive payloads

```

Prefer operational identifiers:

```sql
RAISE NOTICE 'Processed batch_id=%', p_batch_id;

```

rather than logging sensitive row contents.

# 30. Troubleshooting — Function Does Not Exist

Example:

```text
ERROR: function calculate_score(integer) does not exist

```

Check:

```text
schema
search_path
argument count
argument types
casts
routine kind
exact signature

```

Useful query:

```sql
SELECT
    n.nspname,
    p.proname,
    pg_get_function_identity_arguments(p.oid),
    pg_get_function_result(p.oid)
FROM pg_proc AS p
JOIN pg_namespace AS n
    ON n.oid = p.pronamespace
WHERE p.proname = 'calculate_score';

```

---

# 31. Troubleshooting — Permission Denied

For an error involving routine execution, investigate:

```text
caller role
EXECUTE privilege
schema USAGE privilege
routine owner
SECURITY INVOKER / DEFINER
underlying object privileges
role membership

```

Do not immediately solve the issue with broad grants.

For example, avoid reflexively granting privileges to:

```text
PUBLIC

```

or assigning elevated roles.

Determine the missing privilege first.

---

# 32. Troubleshooting — Unexpected Object Resolution

If a routine unexpectedly accesses the wrong relation or function, investigate:

```text
search_path
temporary schema
same-named objects
unqualified object references
SECURITY DEFINER configuration

```

For privileged routines, unsafe object resolution can become a security vulnerability rather than merely a correctness problem.

---

# 33. Troubleshooting — Wrong Function Selected

Overloading plus implicit casting can make routine resolution less obvious.

Inspect all candidates:

```sql
SELECT
    n.nspname,
    p.proname,
    pg_get_function_identity_arguments(p.oid)
FROM pg_proc AS p
JOIN pg_namespace AS n
    ON n.oid = p.pronamespace
WHERE p.proname = 'calculate_score';

```

Then inspect the application call and argument types.

Do not remove overloads merely to diagnose the problem.

---

# 34. Troubleshooting — Performance Regression

When a routine becomes slow, investigate both the routine and the SQL executed by it.

Possible causes include:

```text
query-plan changes
statistics changes
data growth
locking
I/O pressure
bad joins
parameter-sensitive behavior
function volatility
parallel-safety classification
nested routine calls
external dependencies

```

A slow function is not necessarily caused by PL/pgSQL itself.

Inspect the actual workload before changing routine attributes.

# 36. DBRE/SRE Routine Checklist

Before approving a production function or procedure, verify:

- exact schema and routine signature;
- appropriate routine type;
- controlled owner;
- least-privilege execution access;
- whether `PUBLIC EXECUTE` is acceptable;
- `SECURITY INVOKER` versus `SECURITY DEFINER`;
- trusted `search_path` for privileged routines;
- schema qualification where appropriate;
- correct volatility;
- correct parallel classification;
- transaction-control assumptions;
- dependencies;
- logging behavior;
- rollback procedure;
- monitoring/validation plan.

# 37. Operational Mental Model

Think about production routines as executable database objects:

```text
                 PostgreSQL Routine
                        │
        ┌───────────────┼────────────────┐
        │               │                │
     Identity        Security         Behavior
        │               │                │
 schema + name       owner           volatility
 + argument types    EXECUTE         parallel safety
                     invoker/definer  transaction semantics
                     search_path
        │               │                │
        └───────────────┼────────────────┘
                        │
                   Dependencies
                        │
                   Production Risk

```

A routine should not be reviewed only as source code.

Its metadata and privilege configuration are part of its production behavior.

# 39. Key Takeaways

1. Functions participate directly in SQL; procedures are invoked using `CALL`.
2. PostgreSQL supports routine overloading, so exact signatures matter.
3. Routine ownership is part of the security model.
4. `SECURITY INVOKER` should normally be preferred unless elevated execution is required.
5. `SECURITY DEFINER` requires strict `search_path`, ownership, and privilege controls.
6. Newly created functions normally need explicit review of `PUBLIC EXECUTE`.
7. Volatility classifications describe behavior; they are not tuning switches.
8. Parallel-safety classifications must accurately describe routine behavior.
9. Procedure transaction control works only in permitted execution contexts.
10. Production routine changes require dependency, security, rollback, and post-deployment validation.
