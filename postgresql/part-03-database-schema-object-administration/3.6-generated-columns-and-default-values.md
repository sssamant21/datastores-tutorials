# Part 3.6 — Generated Columns and Default Values

**Status:** Revised Final / Canonical Edition  
**Target:** PostgreSQL 18  
**Audience:** PostgreSQL administrators, DBREs, SREs, developers, platform engineers, and data engineers

## Learning objectives

By the end of this tutorial, you should be able to:

- distinguish default values from generated columns;
- explain when default and generation expressions are evaluated;
- choose between stored and virtual generated columns in PostgreSQL 18;
- understand volatility, type, function, trigger, privilege, and partitioning restrictions;
- inspect default and generated-column metadata;
- assess rewrite, locking, storage, indexing, and replication impact;
- evolve these definitions safely on populated production tables;
- run an isolated lab without leaving persistent objects.

## 1. Defaults and generated columns solve different problems

A default supplies a value when an insert does not provide one:

```sql
created_at timestamptz DEFAULT CURRENT_TIMESTAMP
```

A generated column derives its value from other columns:

```sql
line_total numeric
    GENERATED ALWAYS AS (quantity * unit_price) STORED
```

```text
DEFAULT
    evaluated for an omitted or DEFAULT input
    can later be overridden or updated

GENERATED COLUMN
    derived from the current row
    cannot be assigned an ordinary explicit value
```

## 2. Default-value fundamentals

```sql
CREATE TABLE clinical.activity_source (
    source_system text DEFAULT 'unknown',
    received_at timestamptz DEFAULT CURRENT_TIMESTAMP
);
```

A default expression is evaluated when the default is inserted, not when the table is defined. If a column has no declared default, its default is `NULL`.

A default expression must be variable-free: it cannot reference another column in the row or contain a subquery. It can call functions, including volatile functions, when the function result is compatible with the column type and the inserting role can execute it.

A caller can request the default explicitly:

```sql
INSERT INTO clinical.activity_source (source_system, received_at)
VALUES (DEFAULT, DEFAULT);
```

## 3. Omitted value, `DEFAULT`, and explicit `NULL`

These are not equivalent:

```sql
INSERT INTO clinical.activity_source DEFAULT VALUES;

INSERT INTO clinical.activity_source (source_system)
VALUES (DEFAULT);

INSERT INTO clinical.activity_source (source_system)
VALUES (NULL);
```

The first two request the default. The third stores `NULL` if other constraints allow it. A default does not replace an explicitly supplied null.

Use `NOT NULL` separately when a missing stored value is prohibited.

The same distinction applies to `COPY FROM`: a target column omitted from the column list can receive its default, while a supplied null remains null unless a constraint rejects it. Verify the exact file format, null marker, and target column list before a bulk load.

## 4. Default expressions and volatility

Defaults can use volatile expressions such as:

```sql
random()
clock_timestamp()
gen_random_uuid()
```

The function must exist, return a compatible type, and be executable by the inserting role at evaluation time.

Time functions have different semantics. `CURRENT_TIMESTAMP` reflects the current transaction start time, while `clock_timestamp()` reflects wall-clock time when called. Select the expression based on the data contract rather than convenience.

## 5. Defaults do not track later changes

After insertion, a default-supplied value behaves like an ordinary stored value. Changing the default affects subsequent uses of the default; it does not rewrite historical rows:

```sql
ALTER TABLE clinical.activity_source
ALTER COLUMN source_system SET DEFAULT 'application';
```

Existing `'unknown'` values remain unchanged.

## 6. What is a generated column?

PostgreSQL 18 supports stored and virtual generated columns.

```sql
CREATE TABLE billing.invoice_line (
    quantity numeric NOT NULL,
    unit_price numeric(12,2) NOT NULL,
    line_total numeric(14,2)
        GENERATED ALWAYS AS (quantity * unit_price) STORED
);
```

The generation expression is evaluated from the current row. A generated column cannot also have a default or identity definition.

## 7. Stored generated columns

A stored generated column is calculated during insert or update and occupies table storage.

Advantages can include:

- avoiding repeated computation during reads;
- supporting indexes on a materialized derived value;
- predictable built-in or user-defined immutable expressions;
- availability for PostgreSQL 18 logical replication when publication configuration permits it.

Costs can include:

- additional row storage;
- write-time computation;
- WAL and replication volume;
- table rewrite when added to a populated table;
- maintenance when the expression changes.

## 8. Virtual generated columns

A virtual generated column occupies no row storage and is computed when read:

```sql
item_code_upper text
    GENERATED ALWAYS AS (upper(item_code)) VIRTUAL
```

`VIRTUAL` is the PostgreSQL 18 default when neither `VIRTUAL` nor `STORED` is written. Prefer spelling the kind explicitly in production DDL.

Virtual generated columns have additional restrictions:

- their data type cannot be user-defined;
- their expression cannot directly or indirectly use user-defined functions or types;
- only built-in functions and types, including those underlying operators and casts, are allowed.

Virtual columns shift computation to reads and currently are not supported for logical replication of generated values.

## 9. Generation-expression restrictions

A generated expression:

- must use immutable functions;
- cannot contain subqueries;
- cannot reference data outside the current row;
- cannot reference another generated column;
- cannot reference system columns except `tableoid`;
- cannot be used as a partition key;
- cannot coexist with a default or identity definition on the same column.

Function volatility is a correctness contract. Do not mark a function `IMMUTABLE` merely to make it eligible for a generated column.

Changing the behavior of a legitimately declared immutable function is still a data-migration event. Existing stored values retain the old result until rewritten, while a virtual column can expose the new result immediately on the next read. Protect function ownership, source changes, and dependencies through normal schema change control.

## 10. Writing generated columns

An ordinary explicit value is rejected:

```sql
INSERT INTO billing.invoice_line
    (quantity, unit_price, line_total)
VALUES
    (2, 10.00, 999.00);
```

`DEFAULT` may be written as a placeholder:

```sql
INSERT INTO billing.invoice_line
    (quantity, unit_price, line_total)
VALUES
    (2, 10.00, DEFAULT);
```

The derived value remains controlled by PostgreSQL.

## 11. Updating base columns

Generated values follow base-column changes:

```sql
UPDATE billing.invoice_line
SET quantity = 3
WHERE invoice_line_id = 1001;
```

A stored column is recomputed during the write. A virtual column is computed from the current base values when read.

## 12. Defaults versus generated columns

| Behavior | Default | Generated column |
|---|---|---|
| Can reference another column in the row | No | Yes |
| Can use volatile functions | Yes | No |
| Applied when input is omitted or `DEFAULT` | Yes | Always derived |
| Can be overridden by ordinary explicit input | Yes | No |
| Recomputed after base-column update | No | Yes |
| May occupy storage | Yes | Stored: yes; virtual: no |

## 13. Trigger interaction

Generated columns are conceptually updated after `BEFORE` triggers. If a `BEFORE` trigger changes a base column, the generated value reflects that change.

A `BEFORE` trigger must not access generated columns. Trigger design must be tested carefully when both triggers and generated values are present.

## 14. Privileges and security

Privileges on a generated column are separate from privileges on its base columns. A role can potentially read a generated column without being granted access to underlying values.

For a virtual generated column, this separation is fully secure only when the expression uses leakproof functions; PostgreSQL does not enforce that requirement automatically.

Function privileges are checked when the expression executes:

- on write for stored generated columns;
- on read for virtual generated columns.

`SECURITY INVOKER` and `SECURITY DEFINER` behavior of called functions still applies. Generated columns are not an automatic masking or row-security solution.

If a generated expression calls a `SECURITY DEFINER` function, use a trusted non-login owner, a safe function-level `search_path`, schema-qualified object references, and narrowly granted `EXECUTE`. Review row-security behavior using the actual application role.

## 15. Inspecting metadata

Portable inspection:

```sql
SELECT
    table_schema,
    table_name,
    column_name,
    column_default,
    is_generated,
    generation_expression
FROM information_schema.columns
ORDER BY table_schema, table_name, ordinal_position;
```

PostgreSQL catalog inspection:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    a.attname AS column_name,
    a.atthasdef,
    a.attgenerated,
    pg_get_expr(ad.adbin, ad.adrelid) AS expression
FROM pg_attribute AS a
JOIN pg_class AS c ON c.oid = a.attrelid
JOIN pg_namespace AS n ON n.oid = c.relnamespace
LEFT JOIN pg_attrdef AS ad
  ON ad.adrelid = a.attrelid
 AND ad.adnum = a.attnum
WHERE a.attnum > 0
  AND NOT a.attisdropped
ORDER BY n.nspname, c.relname, a.attnum;
```

For `attgenerated`, an empty value means ordinary column, `s` means stored, and `v` means virtual.

`information_schema.columns` is privilege-filtered. Its `is_generated` field reports `ALWAYS` or `NEVER`, but does not distinguish stored from virtual generation; use `pg_attribute.attgenerated` when that PostgreSQL-specific distinction is required.

## 16. Adding defaults to populated tables

Adding a column with a non-volatile default can use PostgreSQL's metadata optimization: the value is evaluated during the `ALTER TABLE`, recorded in metadata, and returned for pre-existing rows without immediately rewriting the whole table. Future inserts evaluate the then-current default normally. This distinction matters for stable expressions such as transaction timestamps, because historical rows can share the value captured by the migration.

```sql
ALTER TABLE clinical.patient_activity
ADD COLUMN source_system text DEFAULT 'unknown';
```

This does not mean the operation has zero cost or zero locking. Most `ALTER TABLE` forms acquire `ACCESS EXCLUSIVE` unless PostgreSQL documents a weaker lock, and the request can wait behind active or idle-in-transaction sessions while also blocking later work.

A volatile default, stored generated column, identity column, or constrained domain can require a table and index rewrite when added. A virtual generated column does not require stored values to be materialized. A rewrite can need substantial temporary disk space, generate heavy WAL, and cause replica lag or replication-slot growth.

## 17. Changing defaults safely

```sql
ALTER TABLE clinical.patient_activity
ALTER COLUMN source_system SET DEFAULT 'application';
```

Changing the default does not backfill old rows. Production plans must separately decide whether historical values require an update.

Use bounded lock acquisition:

```sql
BEGIN;
SET LOCAL lock_timeout = '5s';
SET LOCAL statement_timeout = '30min';
ALTER TABLE ...;
COMMIT;
```

Timeout values are environment-specific. Retrying DDL without diagnosing blockers can cause repeated disruption.

## 18. Changing generation expressions

Changing a generation expression can alter application-visible results. `SET EXPRESSION AS` rewrites a stored generated column using the new expression and removes its column statistics, so plan an appropriate `ANALYZE`. For a virtual column, the new result becomes visible at read time and there are no stored values or column statistics to rewrite.

`DROP EXPRESSION` applies to a stored generated column and converts it to an ordinary column while preserving its currently stored values.

Review:

- function immutability and ownership;
- function `SECURITY DEFINER`, `search_path`, and execution privileges;
- data-type and rounding behavior;
- table size and rewrite duration;
- quantified temporary storage, WAL, replica lag, and replication-slot headroom;
- indexes, constraints, views, functions, and publications using the column;
- consumer compatibility;
- rollback or forward-fix strategy.

Transactional DDL can restore uncommitted database state, but it cannot erase lock waits, consumed I/O, generated WAL, replica pressure, or application timeouts. After commit, changing a stored expression back can require another rewrite. Define a forward-fix and recovery strategy rather than treating `ROLLBACK` as the entire migration plan.

## 19. Partitioning and inheritance

Parent and child columns must agree on whether they are ordinary, stored-generated, or virtual-generated. Their expressions can differ.

For stored columns, the expression of the physical table containing the row is applied during writes. For virtual columns, the expression associated with the table named in the read query is applied.

Defaults behave differently: the default belonging to the table named by the insert applies.

Do not use a generated column as a partition key.

For a partitioned table, inspect every attached and detached partition as well as future partition-creation automation. A parent-only review can miss child-specific expressions, types, collations, or migration ordering requirements.

## 20. Logical replication

PostgreSQL 18 can publish stored generated columns when `publish_generated_columns` is enabled or the publication column list includes them. Replication of generated values is currently supported only for stored generated columns.

Publisher and subscriber schemas, data types, expressions, and publication settings require explicit coordination. DDL is not automatically replicated by PostgreSQL logical replication.

Also validate any CDC connector separately. Connector handling of generated columns, schema changes, and publication column lists can differ from native subscriber expectations.

## 21. Choosing the right mechanism

Use a default when:

- a value should be supplied only when the caller omits it;
- the value can later diverge from the original default;
- a volatile value such as the current time or UUID is needed.

Use a stored generated column when:

- the value must always derive from the row;
- read-time computation is expensive;
- storage and write cost are acceptable;
- the value must be indexed or published as a stored generated value.

Use a virtual generated column when:

- the expression uses only supported built-in immutable behavior;
- read-time computation is acceptable;
- avoiding stored duplication is valuable;
- logical publication of the generated value is not required.

Sometimes an expression index or view is the better design. Do not create a generated column solely to avoid writing an expression in a query.

Treat a generated expression as an application and data contract. A change can affect API output, index keys, uniqueness, reports, extracts, CDC records, and downstream schemas even when PostgreSQL accepts the DDL.

## 22. Production checklist

- [ ] Correct endpoint, database, schema, table, and column verified
- [ ] Default or derivation semantics documented
- [ ] Omitted input versus explicit null behavior tested
- [ ] Function volatility and execution privileges verified
- [ ] Function ownership, source, `search_path`, and security mode reviewed
- [ ] Stored versus virtual choice justified
- [ ] Lock blockers and maintenance-window boundaries identified
- [ ] Rewrite duration and temporary storage headroom quantified
- [ ] WAL, physical-replica lag, and replication-slot headroom quantified
- [ ] Index, constraint, view, function, and publication dependencies inventoried
- [ ] Trigger behavior tested
- [ ] Every partition and partition-creation workflow reviewed
- [ ] Logical replication and CDC behavior reviewed
- [ ] Historical backfill requirement decided separately
- [ ] Application/ORM and bulk-load behavior tested
- [ ] Forward-fix, recovery, verification, and monitoring defined

Managed PostgreSQL services can expose the same SQL semantics with different roles, storage autoscaling, replica monitoring, parameter controls, and maintenance restrictions. Validate the plan against the provider's current documentation rather than copying self-managed capacity assumptions directly.

## 23. Hands-on lab — disposable database only

The companion lab is intentionally state-changing:

```text
[LAB-ONLY — MUTATING — TRANSACTIONALLY CONTAINED]
```

It requires explicit acknowledgement, fails closed on collisions, creates an isolated schema, demonstrates defaults and stored/virtual generated columns, asserts exact derived values and write behavior, verifies metadata, ends with `ROLLBACK`, and enforces cleanup verification.

Transactionally contained does not mean read-only or zero-cost. The lab takes locks, creates catalog entries, writes rows, generates WAL, and intentionally tests a rejected write. Run it only in an authorized disposable, non-production database using a dedicated `psql` session.

Run:

```bash
psql -X -v ON_ERROR_STOP=1 \
  -v lab_confirm=I_UNDERSTAND \
  -d disposable_database \
  -f labs/generated-defaults-lab.sql
```

## 24. Summary

Defaults provide initial values; generated columns maintain derivations. PostgreSQL 18 supports both stored and virtual generated columns, with different storage, execution, security, rewrite, and replication consequences.

```text
Define semantics → choose default/stored/virtual
→ validate expression and privileges → assess migration cost
→ deploy with lock boundaries → verify → monitor
```
