# Part 3.7 — ALTER TABLE and Safe Schema Evolution

**Status:** Revised Final / Canonical Edition  
**Target:** PostgreSQL 18  
**Audience:** PostgreSQL administrators, DBREs, SREs, developers, platform engineers, and data engineers

## Learning objectives

By the end of this tutorial, you should be able to:

- distinguish catalog-only changes, validation scans, index builds, and table rewrites;
- identify the lock and dependency implications of common `ALTER TABLE` operations;
- add columns and defaults without confusing fast metadata changes with zero-impact changes;
- evolve constraints through staged validation;
- change data types with explicit conversion and compatibility analysis;
- use expand-and-contract deployment patterns for application compatibility;
- plan partitioned-table, replication, rollback, and monitoring requirements;
- run an isolated schema-evolution lab without leaving persistent objects.

## 1. Schema evolution is an operational change

`ALTER TABLE` changes an existing table definition. The SQL can be short while the operational consequences are large.

```text
DDL statement
    → lock acquisition
    → catalog change, scan, index build, or rewrite
    → application-visible contract change
    → WAL and replication effects
```

Before execution, answer four separate questions:

1. Which lock is required, and how long might acquisition wait?
2. Does PostgreSQL scan, rewrite, or rebuild anything?
3. Can old and new application versions operate concurrently?
4. How will the change be verified and recovered?

## 2. `ALTER TABLE` scope

PostgreSQL supports many subcommands, including:

```sql
ALTER TABLE clinical.patient_activity ADD COLUMN source_system text;
ALTER TABLE clinical.patient_activity DROP COLUMN obsolete_code;
ALTER TABLE clinical.patient_activity ALTER COLUMN status SET DEFAULT 'new';
ALTER TABLE clinical.patient_activity ALTER COLUMN event_count TYPE bigint;
ALTER TABLE clinical.patient_activity RENAME COLUMN old_name TO new_name;
ALTER TABLE clinical.patient_activity ADD CONSTRAINT ...;
ALTER TABLE clinical.patient_activity VALIDATE CONSTRAINT ...;
```

This tutorial concentrates on changes commonly used during application schema evolution. Ownership, tablespaces, replica identity, partition attachment, trigger state, and row-level security deserve dedicated procedures.

The executing role must own the table. Adding a column or changing a column type also requires `USAGE` on the data type. Schema, tablespace, inheritance, partition attachment, and ownership changes have additional privilege and ownership requirements. Verify the actual migration role rather than assuming that application DML privileges authorize DDL.

## 3. Lock behavior comes first

PostgreSQL acquires `ACCESS EXCLUSIVE` for `ALTER TABLE` unless the documentation explicitly gives a weaker lock for a subcommand. This lock conflicts with ordinary reads and writes.

When several subcommands appear in one statement, PostgreSQL acquires the strictest lock required by any of them:

```sql
ALTER TABLE clinical.patient_activity
    ADD COLUMN source_system text,
    ALTER COLUMN status SET DEFAULT 'new';
```

Combining compatible changes can let PostgreSQL combine multiple scans or rewrites into one pass and reduce repeated lock acquisition. It also combines the failure domain and keeps one transaction and its locks open while all work completes. Group changes only after comparing their physical work, lock duration, failure behavior, and recovery needs.

## 4. Lock queues and transaction age

A DDL request can wait behind an older transaction. Later requests can then wait behind the queued DDL even when they would otherwise be mutually compatible.

Inspect blockers before the change window:

```sql
SELECT
    pid,
    usename,
    application_name,
    state,
    xact_start,
    query_start,
    wait_event_type,
    wait_event,
    pg_blocking_pids(pid) AS blocking_pids,
    query
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY xact_start NULLS LAST, query_start;
```

Observation does not authorize session termination. Coordinate with application owners and follow the incident or change procedure before canceling work.

## 5. Bound lock acquisition

Use transaction-local timeouts appropriate to the environment:

```sql
BEGIN;

SET LOCAL lock_timeout = '5s';
SET LOCAL statement_timeout = '30min';

ALTER TABLE clinical.patient_activity
ADD COLUMN source_system text;

COMMIT;
```

`lock_timeout` limits time spent waiting for a lock. `statement_timeout` limits the whole statement. A retry loop without blocker analysis can create repeated disruption.

## 6. Catalog change, scan, and rewrite are different

Do not classify every `ALTER TABLE` as either "instant" or "rewriting." Useful categories are:

| Work class | Typical example | Main concern |
|---|---|---|
| Catalog-focused | Rename, change default | Lock acquisition and compatibility |
| Validation scan | Validate a check or foreign key | Read I/O and concurrent workload |
| Index build | Unique enforcement | Build duration, space, WAL, conflicts |
| Table rewrite | Volatile default or incompatible type conversion | Long lock, disk, WAL, replica lag |

The exact behavior depends on the subcommand, data types, expressions, constraints, PostgreSQL version, and table structure. Validate the specific command rather than relying on a generic category.

## 7. Adding a nullable column

```sql
ALTER TABLE clinical.patient_activity
ADD COLUMN source_system text;
```

Existing rows read as null. The operation normally changes metadata rather than updating every row, but it still requires the documented DDL lock.

`IF NOT EXISTS` prevents an error when a same-named column exists:

```sql
ALTER TABLE clinical.patient_activity
ADD COLUMN IF NOT EXISTS source_system text;
```

It does not prove that the existing column has the intended type, default, collation, constraints, or meaning. Migration tooling must verify the resulting definition.

## 8. Adding a column with a default

PostgreSQL can optimize a nonvolatile default by evaluating it during `ALTER TABLE` and recording the value in metadata for existing rows:

```sql
ALTER TABLE clinical.patient_activity
ADD COLUMN source_system text DEFAULT 'unknown';
```

Future inserts evaluate the current default normally. The optimization avoids updating every historical row immediately, but it does not remove lock acquisition or application-contract risk.

A volatile default such as `clock_timestamp()` requires a value to be computed for each existing row and can cause a rewrite. For a large table, consider:

```text
add nullable column
→ add future-row default
→ backfill historical rows in controlled batches
→ validate completeness
→ enforce non-null if required
```

## 9. Defaults do not backfill

Changing a default affects future uses of that default:

```sql
ALTER TABLE clinical.patient_activity
ALTER COLUMN source_system SET DEFAULT 'application';
```

It does not update existing rows. Removing a default also leaves stored data unchanged:

```sql
ALTER TABLE clinical.patient_activity
ALTER COLUMN source_system DROP DEFAULT;
```

Treat historical backfill as a separate data migration with its own batching, WAL, vacuum, and replication plan.

## 10. Backfill safely

A single unbounded update can create a large transaction, hold row locks, generate heavy WAL, expand tables and indexes, delay vacuum, and increase replica lag.

Prefer a resumable process that:

- selects bounded batches using a stable key;
- commits between batches;
- updates only rows still requiring migration;
- records progress and error counts;
- throttles using measured primary and replica health;
- tolerates concurrent application writes;
- can restart idempotently.

Define measurable pause thresholds for batch latency, WAL generation, retained WAL, physical and logical replica lag, free storage, dead tuples, and autovacuum health. `OFFSET` is usually a poor progress mechanism on a changing table; prefer a stable key range or another durable checkpoint.

Example shape, not a universal batch implementation:

```sql
UPDATE clinical.patient_activity
SET source_system = 'legacy'
WHERE activity_id > :last_id
  AND activity_id <= :batch_end_id
  AND source_system IS NULL;
```

## 11. Adding constraints normally scans existing data

This command ordinarily verifies existing rows immediately:

```sql
ALTER TABLE clinical.patient_activity
ADD CONSTRAINT patient_activity_count_nonnegative
CHECK (event_count >= 0);
```

If any row violates the condition, the command fails.

For foreign-key, check, and PostgreSQL 18 not-null constraints, `NOT VALID` can separate enforcement for new writes from validation of historical rows. Confirm support for the exact constraint form and engine version.

`NOT VALID` avoids the historical scan, not the initial DDL lock. Most `ADD CONSTRAINT` forms still take `ACCESS EXCLUSIVE`; the objective is to acquire it briefly, install enforcement, and commit before running validation separately.

## 12. Staged check-constraint validation

```sql
ALTER TABLE clinical.patient_activity
ADD CONSTRAINT patient_activity_count_nonnegative
CHECK (event_count >= 0) NOT VALID;
```

New inserts and updates must satisfy the constraint, but PostgreSQL does not yet assume all historical rows comply.

After correcting historical data:

```sql
ALTER TABLE clinical.patient_activity
VALIDATE CONSTRAINT patient_activity_count_nonnegative;
```

Validation acquires `SHARE UPDATE EXCLUSIVE` and permits ordinary reads and writes while the scan runs, although it still consumes I/O and CPU and conflicts with some maintenance and schema operations.

Inspect state through `pg_constraint.convalidated`.

## 13. Adding `NOT NULL` safely

A direct change is simple:

```sql
ALTER TABLE clinical.patient_activity
ALTER COLUMN source_system SET NOT NULL;
```

PostgreSQL must prove no null exists. Ordinarily it scans the table. A valid check constraint proving `source_system IS NOT NULL` can allow PostgreSQL to skip that scan:

```sql
ALTER TABLE clinical.patient_activity
ADD CONSTRAINT patient_activity_source_nn_check
CHECK (source_system IS NOT NULL) NOT VALID;

ALTER TABLE clinical.patient_activity
VALIDATE CONSTRAINT patient_activity_source_nn_check;

ALTER TABLE clinical.patient_activity
ALTER COLUMN source_system SET NOT NULL;

ALTER TABLE clinical.patient_activity
DROP CONSTRAINT patient_activity_source_nn_check;
```

Keep the proof constraint until `SET NOT NULL` succeeds. Dropping it in the same command removes the optimization opportunity.

## 14. Foreign keys and validation

Adding a foreign key normally checks historical rows and locks both referencing and referenced tables. A staged form is:

```sql
ALTER TABLE clinical.patient_activity
ADD CONSTRAINT patient_activity_patient_fk
FOREIGN KEY (patient_id)
REFERENCES clinical.patient(patient_id)
NOT VALID;

ALTER TABLE clinical.patient_activity
VALIDATE CONSTRAINT patient_activity_patient_fk;
```

New writes are enforced after the first statement. Adding the foreign key takes `SHARE ROW EXCLUSIVE` on both the referencing and referenced tables. Validation later takes `SHARE UPDATE EXCLUSIVE` on the referencing table and `ROW SHARE` on the referenced table while checking historical rows. Inventory indexes and workload on both tables; `NOT VALID` is not a substitute for orphan remediation.

## 15. Unique and primary-key evolution

`NOT VALID` is not a general option for unique and primary-key constraints. On a busy nonpartitioned table, one strategy is:

```sql
CREATE UNIQUE INDEX CONCURRENTLY patient_activity_external_id_uidx
ON clinical.patient_activity (external_id);

ALTER TABLE clinical.patient_activity
ADD CONSTRAINT patient_activity_external_id_key
UNIQUE USING INDEX patient_activity_external_id_uidx;
```

`CREATE INDEX CONCURRENTLY` cannot run inside a transaction block and has its own failure and cleanup states. Inspect `pg_index.indisvalid` and the index definition before attaching it. Partitioned tables have additional restrictions and require a partition-aware design.

The index attached through `USING INDEX` must be a valid unique B-tree using default sort ordering, without a predicate or expression columns. Attachment is not currently supported on a partitioned table. A primary-key attachment can still scan the table if its columns are not already `NOT NULL`. After attachment, the constraint owns the index, so dropping the constraint also drops that index.

A concurrent build performs two table scans and waits for relevant transactions and snapshots. If it fails, it can leave an invalid index that consumes storage and write overhead. A failed unique build can continue enforcing uniqueness after its second scan begins even when the index remains invalid. Inspect `indisvalid` and `indisready`, diagnose the exact failure, and use an approved drop or concurrent reindex procedure before retrying.

## 16. Changing a data type

```sql
ALTER TABLE clinical.patient_activity
ALTER COLUMN event_count TYPE bigint;
```

PostgreSQL uses an assignment cast when available. Otherwise provide `USING`:

```sql
ALTER TABLE clinical.patient_activity
ALTER COLUMN external_code TYPE bigint
USING NULLIF(btrim(external_code), '')::bigint;
```

Before execution, test every source value and review:

- lossy conversions and overflow;
- empty strings and malformed values;
- defaults and generated expressions;
- indexes, constraints, views, functions, and prepared statements;
- client-driver and ORM type mappings;
- partition compatibility;
- rewrite, disk, WAL, and replica impact.

Changing a column type removes its statistics; run `ANALYZE` afterward when appropriate. Some binary-compatible changes can avoid a physical rewrite, but compatibility must be established for the exact source and target types.

The `USING` expression is not applied to the column default. If the default cannot be converted independently, drop it before the type change and install a compatible default afterward. Apply the same dependency review to indexes and constraints.

Rewriting forms of `ALTER TABLE` are not MVCC-safe in the usual sense: a concurrent transaction using a snapshot taken before the rewrite can observe the rewritten table as empty afterward. Review long-lived and idle-in-transaction sessions before a rewrite.

## 17. Expand-and-contract type migration

For a risky or long-running conversion, use a compatibility window:

```text
EXPAND
add new column and supporting objects

MIGRATE
dual-write or synchronize, then backfill and verify

SWITCH
move reads to the new representation

CONTRACT
stop old writes, observe, then remove the old column later
```

Dual-write logic must define ordering, retries, failure handling, and the source of truth. A trigger can centralize synchronization but adds write-path behavior that must be load-tested and removed deliberately.

Include a compatibility period long enough to exercise background jobs, retry queues, reporting schedules, ETL, failover procedures, and rollback to the prior application version.

## 18. Renaming columns and tables

```sql
ALTER TABLE clinical.patient_activity
RENAME COLUMN activity_source TO source_system;
```

PostgreSQL updates internal dependencies by object identity, but external consumers are not automatically rewritten:

- application SQL and ORM mappings;
- ETL jobs and BI tools;
- stored query text outside the database;
- CDC schemas and event consumers;
- monitoring, alerts, and runbooks.

For rolling deployments, prefer adding the new interface, migrating consumers, and removing the old interface only after an observation period.

## 19. Dropping columns and constraints

```sql
ALTER TABLE clinical.patient_activity
DROP COLUMN obsolete_code;
```

`RESTRICT` is the default and refuses the operation when external dependencies prevent it. `CASCADE` authorizes PostgreSQL to remove dependent objects:

```sql
ALTER TABLE clinical.patient_activity
DROP COLUMN obsolete_code CASCADE;
```

Do not use `CASCADE` as dependency discovery. Inspect dependencies, identify owners, preserve definitions, and obtain approval before destructive DDL.

Catalog dependency tracking is not omniscient. References embedded in dynamic SQL, external applications, or function bodies stored as unparsed strings might not appear as dependencies. Combine catalog inspection with source, migration, reporting, and consumer searches.

A dropped column becomes invisible to SQL but does not immediately shrink the relation file. New row versions no longer retain its value, allowing space inside table pages to be reused over time. Immediate return of that space to the filesystem requires a later rewrite or table recreation, which is a separate production migration.

## 20. Transactional DDL and recovery

Most ordinary PostgreSQL table DDL is transactional:

```sql
BEGIN;
ALTER TABLE ...;
-- validate
COMMIT;
```

This protects uncommitted database state. It does not undo lock waits, consumed I/O, emitted WAL, replica pressure, or application timeouts. Some operations, including `CREATE INDEX CONCURRENTLY`, cannot run inside a transaction block.

After commit, reversal may be another expensive migration and may not restore discarded data. Define rollback, roll-forward, backup, and application recovery separately.

## 21. Partitioned tables

Schema changes on a partitioned parent can recurse to partitions and acquire locks across the hierarchy. One slow or blocked partition can affect the whole operation.

Before execution, inventory:

- every attached and detached partition;
- default partitions;
- child indexes and constraints;
- future partition templates and automation;
- foreign tables or mixed storage;
- lock acquisition order;
- validation and rollback state per partition.

Parent column additions, renames, and type changes must preserve descendant compatibility. Constraint validity on a parent depends on relevant descendant state, and a nonrecursive `DROP COLUMN` is rejected on a partitioned parent. Use `ONLY` only when its inheritance semantics are deliberately understood.

`CREATE INDEX CONCURRENTLY` is not supported directly on a partitioned parent. A partition-aware procedure can build compatible indexes concurrently on individual partitions and then attach them through the partitioned index hierarchy, with a separately reviewed lock window.

## 22. Replication, CDC, and caches

Physical replicas receive WAL for supported catalog and data changes, but rewrites and index builds can create lag. Logical replication generally does not replicate DDL. Coordinate compatible schemas before rows requiring the new definition arrive.

Review:

- publication column lists and replica identity;
- subscriber DDL order;
- CDC connector schema refresh;
- connection-pool prepared statements;
- server-side prepared plans;
- driver and ORM metadata caches;
- migration-tool transaction behavior;
- read replicas and failover candidates.

Define whether pooled connections must be recycled and monitor for cached-plan or result-type errors after the change.

## 23. Observability during a change

Monitor more than statement completion:

- lock waiters and blockers;
- transaction age;
- query latency and error rate;
- CPU, read/write IOPS, and disk latency;
- WAL generation and retained WAL;
- physical and logical replica lag;
- free storage and temporary space;
- autovacuum progress and dead tuples;
- index validity and constraint validation state.

`pg_stat_progress_create_index` reports supported index-build progress. PostgreSQL does not expose one universal progress view for every table rewrite, so capacity estimates and external monitoring remain important.

## 24. Migration ownership and idempotency

Use one controlled migration path. Avoid simultaneous manual DDL and application migration frameworks against the same objects.

`IF EXISTS` and `IF NOT EXISTS` can make reruns less noisy, but they do not verify semantic equivalence. A safe migration records:

- an immutable migration identifier;
- expected preconditions;
- the exact desired definition;
- execution and verification timestamps;
- the actor and approval reference;
- recovery instructions.

## 25. Production pre-change checklist

- [ ] Correct environment, endpoint, database, schema, and table verified
- [ ] Current owner and executing role verified
- [ ] Required data-type, schema, tablespace, and related-object privileges verified
- [ ] Table, indexes, partitions, and dependent objects inventoried
- [ ] Application and data contracts reviewed with owners
- [ ] Required lock and likely blockers identified
- [ ] Catalog change, scan, index build, or rewrite behavior established
- [ ] Temporary disk, WAL, and replica headroom quantified
- [ ] Historical backfill separated and batch strategy tested
- [ ] Backfill pause thresholds and autovacuum impact defined
- [ ] Logical replication and CDC deployment order defined
- [ ] Old and new application versions tested together
- [ ] Timeouts, monitoring, abort criteria, and change window approved
- [ ] Verification queries and success criteria prepared
- [ ] Rollback, roll-forward, backup, and recovery plans distinguished
- [ ] Partition and managed-service behavior verified
- [ ] Connection-pool and prepared-statement refresh behavior defined

## 26. Hands-on lab — disposable database only

The companion lab is intentionally state-changing:

```text
[LAB-ONLY — MUTATING — TRANSACTIONALLY CONTAINED]
```

It requires explicit acknowledgement, refuses schema collisions, creates isolated objects, demonstrates staged column/default/constraint/type/name evolution, proves that an unvalidated constraint already protects new writes, asserts metadata and data behavior, rolls back, and programmatically verifies cleanup.

The lab deliberately uses `varchar(20)` to `text`, a compatible conversion without a collation change. It does not simulate the duration, disk use, WAL, or snapshot behavior of a rewrite-heavy production conversion.

Transactionally contained does not mean read-only or zero-cost. Run it only in an authorized disposable, non-production database using a dedicated `psql` session:

```bash
psql -X -v ON_ERROR_STOP=1 \
  -v lab_confirm=I_UNDERSTAND \
  -d disposable_database \
  -f labs/alter-table-evolution-lab.sql
```

## 27. Managed PostgreSQL services

The SQL semantics apply broadly to RDS for PostgreSQL, Aurora PostgreSQL-Compatible Edition, Azure Database for PostgreSQL, and Cloud SQL for PostgreSQL. Storage autoscaling, restricted roles, replica topology, monitoring, maintenance controls, and recovery mechanisms differ. Validate the exact engine version and provider behavior before production DDL.

## 28. Summary

Safe schema evolution treats DDL as a coordinated production change rather than isolated syntax.

```text
verify target and dependencies
→ identify lock and physical work
→ design compatibility window
→ execute with bounded waits
→ validate data and metadata
→ monitor applications and replicas
→ contract only after observation
```
