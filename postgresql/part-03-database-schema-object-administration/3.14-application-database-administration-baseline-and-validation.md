# Part 3.14 — Application Database Administration Baseline and Validation

## Revised Final / Canonical Edition

**Target:** PostgreSQL 18

**Track:** Part 3 — Database, Schema, and Object Administration

**Safety class:** Read-only baseline validation

**Companion lab:** `labs/object-baseline-check.sql`

## Learning outcome

By the end of this tutorial, you will be able to define an application-database administration contract, distinguish hard acceptance gates from review signals, validate that contract with PostgreSQL catalogs, and produce evidence without changing database state.

## 1. Why a baseline is more than an inventory

An inventory answers, “What exists?” A baseline answers, “Does the current state match the approved administrative contract?”

For example, an inventory can show that schema `app` exists and that its tables are owned by several roles. A baseline states that:

- the validation must run against database `appdb`;
- schema `app` must exist;
- the schema and its application objects must be owned by `app_owner`;
- constraints must be enforced and validated;
- indexes must be live, ready, and valid;
- no partition detach may be pending;
- deviations must be reviewed before release or handoff.

This lesson integrates the object-administration techniques from Parts 3.1–3.13. It does not replace the detailed security architecture in Part 4, storage and WAL administration in Part 5, or index and query-performance engineering in later parts.

## 2. Define the contract before querying catalogs

A useful baseline begins with explicit expected values. The companion artifact requires:

| Input | Meaning |
| --- | --- |
| `expected_database` | Exact database to which the client must be connected |
| `expected_schema` | Exact application schema to validate |
| `expected_owner` | Expected owner of the schema and its application objects |

The lab intentionally restricts these tutorial inputs to unquoted lowercase identifiers matching `^[a-z][a-z0-9_]*$`. Production systems that use quoted, mixed-case, or punctuation-bearing identifiers need a separately reviewed input policy.

Expected values should come from an approved source such as version-controlled infrastructure code, migration definitions, a configuration registry, or an application service contract. Do not derive the “expected” owner from the live database and then claim that the live database matches itself.

## 3. Separate hard gates from review signals

Not every unusual state is wrong, and not every healthy catalog flag proves production readiness.

### Hard gates in the companion lab

The draft artifact treats these conditions as acceptance gates:

- the server major is PostgreSQL 18;
- `current_database()` matches `expected_database`;
- `expected_schema` exists;
- the schema owner matches `expected_owner`;
- application relations, routines, and explicit user-defined types in that schema match `expected_owner`;
- relation constraints are both enforced and validated;
- indexes are live, ready, and valid;
- no partition or inheritance edge is marked detach-pending.

### Review signals

The artifact reports, but does not automatically reject:

- tables without primary keys;
- unlogged relations;
- row-level security configuration;
- SECURITY DEFINER routines;
- unpopulated materialized views;
- installed extensions;
- schema privileges granted to PUBLIC;
- database connection limits, locale provider, encoding, and tablespace.

These require application and organizational context. For example, a staging table may intentionally lack a primary key, an unlogged table may be an approved rebuildable cache, and a SECURITY DEFINER routine may be properly hardened. Conversely, a catalog-clean database can still be unsafe because external consumers, backup policy, replication, monitoring, or secrets handling are incomplete.

## 4. Validate execution context first

Before inspecting objects, capture:

- full server version and numeric version;
- database name;
- current and session roles;
- whether the server is in recovery;
- transaction isolation and read-only state;
- collection timestamp;
- expected baseline inputs.

The companion artifact fails closed on PostgreSQL majors other than 18. It also aborts before application-object inventory when `current_database()` differs from `expected_database`, preventing a connection-selection error from turning into a broad scan of the wrong database. Catalog layouts and semantics can change across major releases, so a query merely succeeding on another major does not prove it was validated for that version.

## 5. Use one read-only database snapshot

PostgreSQL's default `READ COMMITTED` isolation can give successive statements different snapshots. A multi-query baseline could otherwise report a schema from one committed state and its indexes from a later state.

The lab uses:

```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY;
```

This provides one database snapshot for the validation queries and prevents writes inside the transaction. It does not create a cluster-wide snapshot, freeze managed-service control planes, or eliminate normal lock interaction with concurrent DDL.

Keep the run bounded. A long transaction retains an old snapshot and can create operational costs. Test duration and output volume before routine production use.

## 6. Validate the database boundary

`pg_database` is a shared catalog with one copy per cluster. The baseline reports:

- database name and owner;
- encoding;
- locale provider and locale-related fields;
- default tablespace;
- connection permission and connection limit;
- template status;
- recorded collation version.

The lab makes the database-name match a hard gate but leaves database owner, locale, tablespace, and connection policy as explicit review data. Those values are often governed by a platform-level contract separate from the application's schema owner.

Never treat `datallowconn = true` or a particular `datconnlimit` as universally correct. A production platform may use external connection pooling or provider-enforced limits that are not represented by a single catalog value.

## 7. Validate schema identity and ownership

`pg_namespace` stores schema names, owners, and ACLs. The application schema must exist exactly once by name. Its owner should normally be a controlled, non-personal role.

Schema ownership is administrative authority. It is not equivalent to application runtime access. Full role membership, default privileges, grant design, and effective-access validation belong primarily to Part 4.

The lab also reports PUBLIC privileges on the target schema by expanding the effective ACL representation. PUBLIC access is a review signal rather than an automatic failure because the approved contract may deliberately allow `USAGE`. `CREATE` granted broadly is normally a stronger concern and should receive explicit security review.

## 8. Validate object ownership as a boundary

The baseline checks ownership of application relations, routines, and explicit user-defined types in the target schema. It includes tables, partitioned tables, views, materialized views, sequences, foreign tables, indexes, partitioned indexes, domains, enums, ranges, base types, and free-standing composite types. Automatically generated true-array rows and relation row types are excluded from the concise ownership gate.

The single-owner gate assumes a dedicated application schema whose governed objects are expected to share one owner. Extension members or intentionally separated object-owner domains can make that policy inappropriate. Do not change extension-managed objects merely to satisfy this check; define and review a different contract for that schema.

Ownership drift can happen when:

- migrations run under personal or runtime roles;
- restore tooling recreates objects under the restore role;
- `SET ROLE` is omitted or misconfigured;
- extension or deployment automation uses an unexpected owner;
- manual remediation creates replacement objects.

An ownership match does not prove that ACLs, policies, default privileges, or security-definer boundaries are correct. It only proves the catalog owner matches the declared baseline.

## 9. Validate constraint health

PostgreSQL 18 `pg_constraint` represents check, not-null, primary-key, unique, foreign-key, exclusion, and constraint-trigger metadata. Two important acceptance fields are:

- `conenforced`: whether the constraint is enforced;
- `convalidated`: whether existing rows have been validated.

The lab treats a target-schema relation constraint that is not enforced or not validated as a hard failure. An intentionally staged `NOT VALID` constraint can be a safe migration technique, but it means the declared final baseline has not yet been reached. If the approved release contract permits such a state, revise the baseline explicitly rather than ignoring the result.

## 10. Validate index lifecycle state

`pg_index` and `pg_class` together describe index state. The hard gate looks for indexes that are:

- not live;
- not ready to receive changes;
- not valid for query use.

These flags can expose interrupted or in-progress index lifecycle work. They do not prove that every necessary index exists, that indexes are non-duplicative, or that workload performance is acceptable. Index design and usage analysis require workload evidence and belong to later performance sections.

## 11. Review primary-key coverage

The lab reports ordinary and partitioned tables without a primary key. It does not fail the baseline automatically.

Many transactional tables should have a stable key, and replication or application logic can depend on one. However, PostgreSQL permits tables without primary keys, and staging, append-only, or special-purpose tables may be valid exceptions. Record the reason and downstream implications rather than applying an unreviewed universal rule.

## 12. Review persistence, RLS, and replica identity

For application relations, inspect:

- `relpersistence`: permanent, unlogged, or temporary;
- `relrowsecurity` and `relforcerowsecurity`;
- `relreplident`: replica identity selection;
- `relispopulated`: especially for materialized views;
- `relispartition`: partition membership.

These are review signals. An unlogged table does not survive crash recovery and is not replicated through physical standby recovery in the same way as logged data. Replica identity matters for logical replication and change-data capture. RLS flags indicate that policy review is required; they do not prove policies are complete or effective for every role.

## 13. Review routines and SECURITY DEFINER boundaries

The baseline inventories routines by kind, identity arguments, owner, language, and security mode. SECURITY DEFINER routines require a separate security review of privileges, object references, `search_path`, configuration, and source.

The lab does not export routine bodies or execute user-defined routines. It reports `proconfig` only as metadata so reviewers can see whether routine-local configuration exists. The presence of a `search_path` setting is not by itself proof that the routine is safe.

## 14. Review extensions without managing them

Installed extensions, their versions, owners, relocatability, and exported-object schema are part of the application database baseline. The extension namespace does not mean the extension itself belongs to that schema, and not every member must necessarily reside there.

The lab does not install, update, or remove extensions. Version compliance must be compared with the approved platform and application compatibility matrix.

## 15. Review partition and materialized-view readiness

`pg_inherits.inhdetachpending` exposes a partition detach that has not completed. The lab treats any target-schema detach-pending edge as a hard failure because the hierarchy is in a transitional state.

An unpopulated materialized view is reported as a review signal. Whether it blocks release depends on whether the application expects the materialized view to be queryable and current at handoff time. Refresh operations are intentionally outside this SAFE-READ validation.

## 16. Interpret the final verdict correctly

The artifact returns a hard-gate summary and exits with a nonzero status when any hard gate fails. That behavior makes it suitable for a release checklist or CI validation job, provided the connected role has sufficient visibility and the inputs come from an approved source.

A pass means only:

- the queried PostgreSQL 18 catalog state matched the declared hard gates;
- the current role could observe the relevant rows;
- the checks completed within one database snapshot.

A pass does not prove:

- complete effective privilege correctness;
- absence of external consumers or dependencies;
- backup, restore, replication, or disaster-recovery readiness;
- acceptable query performance or capacity;
- application correctness;
- compliance with every organization-specific standard.

## Hands-On Lab — Validate an application object baseline

### Prerequisites

- an authorized PostgreSQL 18 database;
- an application schema and expected controlled owner role;
- `psql` access through a metadata-review role;
- approved values for the database, schema, and owner;
- a secure destination for the transcript.

### Run

```bash
psql --no-psqlrc \
  --dbname='postgresql://baseline_reader@db.example/appdb' \
  --set=expected_database=appdb \
  --set=expected_schema=app \
  --set=expected_owner=app_owner \
  --file=labs/object-baseline-check.sql \
  --output=appdb-object-baseline.txt
```

Do not place plaintext passwords in the URI or shell history. Use an approved password file, service definition, or secret mechanism.

`--output` captures normal `psql` output, while some connection and error diagnostics can still be written to standard error. In automation, preserve the process exit code and capture standard error through the organization's approved logging mechanism without exposing credentials.

### Exercises

1. Run the baseline with the approved inputs and preserve the exit code.
2. Explain every hard-gate result and every review signal.
3. Run with a deliberately incorrect expected schema and confirm that validation fails safely.
4. Compare results using a less-privileged metadata role and document visibility differences.
5. Identify which review signals require application-owner, security, platform, or data-owner approval.
6. Store the approved baseline inputs beside the migration or infrastructure version that they validate.

### Success criteria

You can:

- distinguish inventory from policy validation;
- explain why expected values must come from outside the live database;
- identify the hard gates implemented by the artifact;
- interpret constraints and index lifecycle state correctly;
- explain why primary-key, RLS, SECURITY DEFINER, extension, and PUBLIC-access findings require context;
- state exactly what a passing baseline does and does not prove.

## Production checklist

- [ ] Exact PostgreSQL 18 endpoint and database confirmed
- [ ] Expected inputs obtained from an approved external source
- [ ] Metadata-review role and visibility boundary documented
- [ ] Transcript destination access-controlled
- [ ] Validation duration and output size tested
- [ ] DDL/change window coordinated where necessary
- [ ] Hard-gate failures investigated rather than bypassed
- [ ] Review signals assigned to accountable owners
- [ ] External application and ETL dependencies considered
- [ ] Backup, restore, replication, monitoring, and DR validated separately
- [ ] Evidence version, timestamp, exit code, and artifact checksum retained
