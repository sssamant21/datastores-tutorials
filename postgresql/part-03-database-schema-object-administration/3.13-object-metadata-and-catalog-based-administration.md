# Part 3.13 — Object Metadata and Catalog-Based Administration

## Revised Final / Canonical Edition

**Target:** PostgreSQL 18

**Track:** Part 3 — Database, Schema, and Object Administration

**Safety class:** Read-only metadata inspection

## Learning outcome

By the end of this tutorial, you will be able to build a repeatable inventory of PostgreSQL objects from `information_schema` and `pg_catalog`, interpret catalog identifiers and status flags correctly, and collect useful administrative evidence without changing database state.

## Why metadata administration matters

An administrator routinely needs to answer questions such as:

- Which schemas and relations exist in this database?
- Which columns, constraints, and indexes define a table?
- Which objects are partitions, views, materialized views, or foreign tables?
- Are indexes valid and ready for use?
- Which extensions and routines are installed?
- Is an inventory complete for the role that collected it?

PostgreSQL stores these facts as data. The SQL-standard `information_schema` presents a portable view of objects in the current database. PostgreSQL's system catalogs expose richer, implementation-specific detail. Neither layer is a substitute for backups, source-controlled DDL, dependency analysis, activity evidence, or authorization review.

## 1. Choose the metadata layer deliberately

### `information_schema`

Use `information_schema` when portability and a stable SQL-standard interface matter. Its views are useful for common tables, columns, constraints, routines, and privileges. They do not represent every PostgreSQL-specific feature, and many views show only objects the current user can access.

### `pg_catalog`

Use `pg_catalog` when PostgreSQL-specific facts matter: relation kinds, partition state, row-security flags, index build state, extension membership, internal object links, or generated definitions. Catalog structure follows PostgreSQL implementation needs and may change between major releases. Pin and test automated queries against every supported major version.

Never modify a system catalog directly. Use supported SQL commands for DDL and administration.

## 2. Understand catalog identity

Many catalogs identify a row with an object identifier, or OID. Other rows refer to that object by storing its OID. For example:

- `pg_class.relnamespace` refers to `pg_namespace.oid`.
- `pg_attribute.attrelid` refers to `pg_class.oid`.
- `pg_index.indrelid` and `indexrelid` identify the indexed relation and index.

OID joins are appropriate inside a live catalog query. Do not use an OID as a durable cross-cluster or long-term business key: objects can be recreated with different OIDs, and an OID alone does not describe its catalog or database context.

For operator-facing output, prefer qualified names plus identity information. PostgreSQL alias types such as `regclass`, `regtype`, and `regprocedure` can render or resolve object identities, but text-to-object resolution follows name visibility and `search_path`. Schema-qualify input whenever ambiguity is unacceptable.

## 3. Define the inventory boundary

PostgreSQL catalogs mix application objects, extension objects, temporary objects, TOAST storage, and PostgreSQL's own objects. Decide what the report means before filtering.

A common user-object boundary excludes:

- `pg_catalog` and `information_schema`;
- schemas whose names begin with `pg_toast`;
- temporary schemas whose names begin with `pg_temp_`.

This boundary is a reporting policy, not a security boundary. An extension may create objects in a user-visible schema, and a managed service may add provider-owned schemas. Record the database, server version, session role, filter policy, and collection time with every export.

## 4. Build the relation inventory

`pg_class` represents relations: tables, indexes, sequences, views, materialized views, composite types, foreign tables, partitioned tables, and internal TOAST relations. Join `pg_namespace` for the schema and map `relkind` explicitly.

Useful fields include:

- `relpersistence`: permanent, unlogged, or temporary;
- `relispartition`: whether a table or index is a partition;
- `relispopulated`: relevant to materialized views;
- `relrowsecurity` and `relforcerowsecurity`: row-security configuration;
- `relreplident`: replica identity selection.

Do not infer exact row counts from `reltuples`; it is a planner estimate. Some `pg_class` Boolean hints are maintained lazily, so use the authoritative supporting catalog when correctness matters. For example, enumerate `pg_index` rather than treating `relhasindex = false` as definitive.

## 5. Inventory columns

`pg_attribute` contains one row for each column-like attribute of each `pg_class` relation. A user-column query normally requires:

```sql
a.attnum > 0 AND NOT a.attisdropped
```

Render the type with `pg_catalog.format_type(a.atttypid, a.atttypmod)` rather than reconstructing it from raw fields. `attidentity` identifies identity columns, and `attgenerated` identifies generated columns. `atthasdef` says a default or generation expression exists; its expression is stored in `pg_attrdef`.

Definition text can disclose literal values, object names, or business logic. A baseline inventory can report only that an expression exists. Retrieve expressions with `pg_get_expr` only for a justified, access-controlled review.

## 6. Inventory constraints and indexes

`pg_constraint` covers check, foreign-key, primary-key, unique, exclusion, not-null, and constraint-trigger metadata. Constraint names are not a safe global key. Qualify them with their relation or domain identity.

Important state includes:

- `convalidated`: whether existing data was validated;
- `condeferrable` and `condeferred`: transaction timing;
- `conparentid`: parent constraint for a partition;
- `conrelid` or `contypid`: the constrained relation or domain.

`pg_index` describes index semantics and lifecycle state. Review at least:

- `indisunique`, `indisprimary`, and `indisexclusion`;
- `indisvalid`: whether the index is valid for queries;
- `indisready`: whether inserts and updates maintain it;
- `indislive`: whether it is being dropped;
- `indisreplident`: whether it supplies replica identity;
- whether `indpred` is non-null for a partial index.

Do not decide that an index is unused from catalog metadata alone. Usage requires an appropriate statistics window and workload context.

## 7. Inventory routines, types, and extensions

`pg_proc` stores functions, procedures, aggregates, and window functions. Overloaded routines require identity arguments, not only a name. Join `pg_language` for implementation language and render the owner with `pg_get_userbyid`.

`pg_type` stores base, composite, domain, enum, range, multirange, and pseudo types. It also contains automatically generated array and relation row types; a naive count therefore overstates user-designed types.

`pg_extension` identifies installed extensions and their versions. Its `extnamespace` value identifies the schema containing most or all exported objects; it does not mean that the extension itself belongs to that schema or prove that every extension-owned object resides there. Extension-owned objects also appear in ordinary catalogs. Do not alter them independently until you have evaluated the extension's supported lifecycle.

## 8. Describe hierarchy without guessing

`pg_inherits` represents both traditional inheritance and declarative partition parent-child links. Join both OIDs to `pg_class` and `pg_namespace`. A hierarchy report identifies structure; it does not reproduce partition bounds. Use PostgreSQL's supported deparser functions for targeted definition review rather than decoding internal `pg_node_tree` values.

## 9. Generated definitions are sensitive evidence

PostgreSQL provides helpers such as:

- `pg_get_expr` for stored expressions;
- `pg_get_constraintdef` for constraints;
- `pg_get_indexdef` for indexes;
- `pg_get_viewdef` for views;
- `pg_get_function_identity_arguments` for routine identity.

These are safer than parsing internal expression trees, but generated text is not necessarily byte-for-byte original DDL. Store it as review evidence, not as the sole backup or deployment source. Limit definition exports to the required schema and protect the result like source code.

## 10. Visibility, consistency, and interpretation limits

Run the same inventory as different roles and the results may differ. `information_schema` deliberately filters many views according to privileges. Direct catalog visibility and access to definition text have their own rules. A successful metadata read does not prove that the role can use, alter, or drop the object.

Each SQL statement observes a database snapshot under PostgreSQL's transaction rules. A multi-query script run in autocommit can therefore see DDL changes between statements. The companion lab uses one `REPEATABLE READ, READ ONLY` transaction so its successive queries share a database snapshot. This does not create a cluster-wide snapshot across databases. Long transactions have operational costs, so coordinate with change control and keep collection bounded.

Also remember:

- most object catalogs are scoped to the connected database;
- cluster-wide objects such as databases, roles, and tablespaces use shared catalogs;
- temporary objects are session-specific;
- catalog metadata does not prove application usage or object safety;
- object definitions and comments can contain sensitive information.

Catalog reads are low-risk, not zero-cost. A broad inventory can generate substantial output and consume database, client, network, and storage resources. Metadata reads also participate in normal locking and can briefly interact with concurrent DDL. Test the query set, run it from an approved host, and retain the export only as long as policy requires.

## Hands-On Lab — Produce a read-only object inventory

### Goal

Run the companion `labs/object-inventory-check.sql` artifact with `psql` to inspect PostgreSQL 18 metadata without creating, altering, dropping, executing, or granting access to user objects.

### Prerequisites

- PostgreSQL 18 target database;
- `psql` access with a metadata-review role;
- permission to store the output securely;
- a maintenance/change window if you require stable results while DDL may occur.

The artifact fails closed on server majors other than PostgreSQL 18.

### Run

```bash
psql --no-psqlrc --dbname='postgresql://inventory_reader@db.example/appdb' \
  --file=labs/object-inventory-check.sql \
  --output=object-inventory.txt
```

Use a service file, password file, or approved secret mechanism rather than embedding a password in shell history. Review the output location and retention policy before collecting metadata.

### Exercises

1. Record the database, server version, current role, and collection timestamp.
2. Compare relation counts from the catalog inventory with `information_schema.tables`.
3. Select one table and trace it from `pg_class` to its `pg_attribute`, `pg_constraint`, and `pg_index` rows.
4. Identify any invalid or not-ready indexes. Treat the result as a review trigger, not an instruction to drop or rebuild.
5. Find partition or inheritance edges and confirm parent and child names.
6. Run the artifact with a less-privileged role and explain any differences.

### Success criteria

You can explain:

- why `information_schema` and `pg_catalog` produce different views of metadata;
- why OIDs are join keys rather than durable external identifiers;
- why relation, column, constraint, and index state require different catalogs;
- why a catalog inventory does not prove usage, privilege, or safe removal;
- how role visibility and concurrent DDL affect the evidence.

## Operational checklist

- [ ] Pin the query set to supported PostgreSQL major versions.
- [ ] Select explicit columns; do not automate `SELECT *` against catalogs.
- [ ] Record database, server version, role, time, and filters.
- [ ] Schema-qualify object resolution and avoid ambient `search_path` assumptions.
- [ ] Exclude system, TOAST, and temporary namespaces intentionally.
- [ ] Treat OIDs as contextual catalog identifiers.
- [ ] Use authoritative catalogs instead of lazy hint flags.
- [ ] Protect definitions, comments, ACLs, and exported evidence.
- [ ] Coordinate for consistent multi-query snapshots when required.
- [ ] Correlate metadata with privileges, dependencies, workload, and source-controlled DDL before acting.
