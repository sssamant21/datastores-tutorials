# Part 3.3 — Table Design and Lifecycle Administration

**Status:** Revised Final / Canonical Edition  
**Target:** PostgreSQL 18  
**Audience:** PostgreSQL administrators, DBREs, SREs, developers, platform engineers, and data engineers

## Learning objectives

By the end of this tutorial, you should be able to:

- explain a PostgreSQL table's logical and physical responsibilities;
- design a clear table contract before writing DDL;
- choose column names and initial data types deliberately;
- distinguish ordinary, partitioned, foreign, and temporary relations;
- inspect table ownership, persistence, access method, tablespace, size, and statistics;
- understand the lifecycle boundaries of create, rename, truncate, move, and drop operations;
- recognize locking, dependency, privilege, replication, and recovery considerations;
- validate table state without modifying application data.

Detailed constraints belong to Part 3.4, sequences and identity columns to Part 3.5, defaults and generated columns to Part 3.6, and production schema evolution to Part 3.7.

## 1. What is a PostgreSQL table?

A table is a schema-contained relation that defines how a set of rows is represented. Its qualified identity combines schema and table name:

```text
clinical.patient
```

The table contract includes more than its name:

```text
schema and owner
column names and types
nullability and constraints
storage and access method
tablespace placement
privileges
dependencies
replication and backup expectations
lifecycle and retention requirements
```

This tutorial establishes the table foundation. Later sections add integrity, value generation, and controlled evolution. The introductory DDL is intentionally incomplete and must not be deployed as a production baseline without those controls.

## 2. Design before DDL

Before creating a table, answer:

- What real-world entity or event does one row represent?
- What uniquely identifies a row?
- Which attributes are required, optional, derived, or sensitive?
- What are the expected write, read, update, and delete patterns?
- What is the expected initial volume and growth rate?
- What retention, archival, privacy, and audit rules apply?
- Which application or team owns the table contract?
- Will the table participate in replication, CDC, ETL, or analytical workloads?
- Does it contain protected health information, personally identifiable information, financial information, credentials, audit evidence, or retention-regulated data?

DDL should implement an approved data contract rather than become the mechanism for discovering one in production. Sensitive-data design must also define minimization, approved purpose, retention, encryption, masking, auditing, legal holds, and deletion behavior.

## 3. Naming standards

Prefer lowercase, unquoted identifiers:

```text
patient_activity
event_timestamp
source_system
```

Avoid:

- quoted mixed-case names;
- unclear abbreviations;
- reserved or ambiguous words;
- names tied to temporary implementation details;
- environment names such as `prod_patient` inside a production database;
- names that expose sensitive information unnecessarily.

Use schema-qualified names in migrations and operational commands:

```sql
clinical.patient_activity
```

## 4. Column design fundamentals

Each column should represent one stable attribute of the row contract.

Consider:

- semantic meaning;
- correct PostgreSQL data type;
- nullability;
- expected range and precision;
- comparison and sorting behavior;
- indexing and query patterns;
- storage footprint;
- application-driver compatibility;
- migration and backward-compatibility requirements.

Avoid storing all values as `text` merely to postpone design decisions. Also avoid premature over-normalization or denormalization without workload evidence.

## 5. Initial data-type choices

Examples of deliberate choices include:

| Requirement | Candidate type |
|---|---|
| Integer identifier | `bigint` or another appropriately sized integer |
| Timestamp representing an instant | `timestamptz` |
| Calendar date | `date` |
| Exact decimal value | `numeric(precision, scale)` where justified |
| Arbitrary text | `text` |
| True/false state | `boolean` |
| PostgreSQL UUID value | `uuid` |
| Structured document with query needs | `jsonb` after governance review |

The correct choice depends on domain semantics. Part 1.9 provides the detailed PostgreSQL data-type foundation.

Changing a type later may require validation, locking, table rewrites, index work, application coordination, or explicit conversion logic. Choose deliberately before loading large volumes.

## 6. A minimal production-style table definition

The following example illustrates structure without attempting to teach every constraint or value-generation feature:

```sql
CREATE TABLE clinical.patient_activity (
    activity_id       bigint,
    patient_reference text,
    activity_type     text,
    occurred_at       timestamptz,
    source_system     text
);
```

This is intentionally incomplete as a production data contract. Do not deploy it unchanged. Subsequent sections will add keys, required-column rules, checks, defaults, generated values, indexes, privileges, retention controls, and operational validation.

## 7. Qualified creation and `search_path`

Prefer explicit placement:

```sql
CREATE TABLE clinical.patient_activity (...);
```

An unqualified command creates the table in the current schema—the first valid schema in the effective `search_path` in which the role can create objects. Creating a table requires `CREATE` on the target schema and `USAGE` on every referenced column type.

Do not let an unintended session path decide the production destination.

`CREATE TABLE IF NOT EXISTS` only suppresses a duplicate-name error. It does not prove that an existing relation has the expected type, columns, ownership, constraints, privileges, storage configuration, or business purpose. Idempotent deployment requires explicit contract validation.

## 8. Ownership

The creating role normally becomes the table owner unless ownership is assigned through an approved role workflow.

Inspect ownership:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    pg_get_userbyid(c.relowner) AS owner
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'p')
ORDER BY n.nspname, c.relname;
```

Prefer controlled non-login owner or deployment roles rather than individual human accounts. Ownership provides authority to alter and drop the table and should not be granted merely to solve a read/write access problem.

## 9. Table kinds

PostgreSQL environments can contain several relation types:

| `relkind` | Meaning |
|---|---|
| `r` | Ordinary table |
| `p` | Partitioned table |
| `f` | Foreign table |
| `v` | View |
| `m` | Materialized view |
| `S` | Sequence |

A partitioned table differs from an ordinary table, and its rows reside in its partitions. Foreign tables depend on a foreign-data wrapper and external system. Do not treat every `pg_class` row as a locally stored ordinary table. Tables also create a composite row type, and relation-like objects share a name namespace within the schema.

## 10. Persistence

`pg_class.relpersistence` helps distinguish:

| Value | Meaning |
|---|---|
| `p` | Permanent |
| `u` | Unlogged |
| `t` | Temporary |

Unlogged-table data is not written to WAL. PostgreSQL automatically truncates an unlogged table after a crash or unclean shutdown, and its contents are not replicated to standby servers. Indexes created on it are unlogged; associated identity or serial sequences created with it are also unlogged. Temporary tables are session- or transaction-scoped according to their definition and use session-specific schemas. Autovacuum cannot vacuum or analyze temporary tables, so the owning session may need to run `ANALYZE` after populating a temporary table used by complex queries.

Do not choose unlogged or temporary storage simply for perceived speed. Recovery, replication, durability, pooling, and operational behavior must be evaluated.

## 11. Access method and tablespace

Inspect the table access method and tablespace metadata:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    am.amname AS access_method,
    COALESCE(ts.spcname, 'database default') AS tablespace
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
LEFT JOIN pg_am AS am
  ON am.oid = c.relam
LEFT JOIN pg_tablespace AS ts
  ON ts.oid = c.reltablespace
WHERE c.relkind IN ('r', 'p')
ORDER BY n.nspname, c.relname;
```

The default table access method is normally `heap`. Tablespace selection affects physical placement but does not replace storage-capacity, IOPS, latency, backup, HA, and filesystem planning. For a partitioned parent, `relam` and `reltablespace` can act as defaults for subsequently created partitions; they do not show physical storage occupied by the parent itself.

Do not move a production table or change storage settings without reviewing lock behavior, available capacity, WAL generation, replication, and recovery consequences.

## 12. Table metadata with `information_schema`

A portable starting point is:

```sql
SELECT
    table_schema,
    table_name,
    table_type
FROM information_schema.tables
ORDER BY table_schema, table_name;
```

Information-schema views are privilege-filtered. They do not necessarily show every table in the database to every role.

PostgreSQL catalogs provide deeper implementation-specific metadata. Use each interface deliberately.

## 13. Column metadata

Inspect the current-role-visible column contract:

```sql
SELECT
    table_schema,
    table_name,
    ordinal_position,
    column_name,
    data_type,
    is_nullable
FROM information_schema.columns
ORDER BY table_schema, table_name, ordinal_position;
```

`data_type` is useful for orientation but does not always express every PostgreSQL-specific type detail. Later validation can use catalog functions such as `format_type()` when exact PostgreSQL type representation is required.

## 14. Size inspection

For an ordinary table:

```sql
SELECT
    pg_relation_size('clinical.patient_activity') AS main_fork_bytes,
    pg_table_size('clinical.patient_activity') AS table_bytes,
    pg_total_relation_size('clinical.patient_activity') AS total_bytes;
```

These functions measure different scopes. `pg_total_relation_size()` includes associated indexes, while `pg_table_size()` includes table storage such as TOAST and auxiliary data but excludes indexes.

For a partitioned parent, these functions do not recursively total all attached partitions. A zero or small parent value is not the size of the complete logical partition hierarchy. Recursive capacity reporting must discover descendants and aggregate them deliberately.

Size functions are observational, but broad size scans can consume resources. SAFE-READ does not mean zero operational cost.

## 15. Estimated and exact row counts

`pg_class.reltuples` is a planner estimate updated by maintenance activity:

```sql
SELECT
    n.nspname,
    c.relname,
    CASE
        WHEN c.reltuples < 0 THEN NULL
        ELSE c.reltuples::bigint
    END AS estimated_rows,
    c.reltuples < 0 AS row_estimate_unknown
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.relkind = 'r';
```

It is not guaranteed to be exact or current. A value of `-1` can mean the relation has not yet been vacuumed or analyzed and the estimate is unknown. Casting it to `bigint` does not make it exact.

```sql
SELECT count(*) FROM clinical.patient_activity;
```

can require scanning the table or an index and may be expensive. Do not run exact counts indiscriminately on large production tables.

## 16. Table statistics

`pg_stat_user_tables` provides operational observations such as estimated live/dead tuples, scan activity, modifications, and maintenance timestamps.

```sql
SELECT
    schemaname,
    relname,
    seq_scan,
    idx_scan,
    n_live_tup,
    n_dead_tup,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze
FROM pg_stat_user_tables
ORDER BY schemaname, relname;
```

These values are statistics, estimates, or cumulative counters. They are not automatically exact current facts or rates. Account for collection intervals and resets.

## 17. Dependencies

A table can be referenced by:

- views and materialized views;
- foreign keys;
- functions and procedures;
- triggers;
- sequences and identity relationships;
- publications and replication tooling;
- application SQL and ORM mappings;
- ETL, CDC, reporting, monitoring, and backup workflows.

PostgreSQL dependency tracking is important but cannot discover every external textual or application dependency. Lifecycle changes require both catalog inspection and application-owner confirmation.

## 18. Renaming a table

Conceptually:

```sql
ALTER TABLE clinical.patient_activity
RENAME TO patient_activity_history;
```

A rename changes the qualified name used by consumers. PostgreSQL can preserve internal dependencies, but external SQL, dynamic SQL, application configuration, dashboards, and scripts can still break.

`ALTER TABLE ... RENAME TO` acquires an `ACCESS EXCLUSIVE` lock. It can block or wait behind active work. Do not promise a zero-impact rename without workload-specific validation, an approved lock-wait boundary, or application coordination.

## 19. Truncating a table

```sql
TRUNCATE TABLE clinical.patient_activity;
```

`TRUNCATE` is destructive data removal. It requires the `TRUNCATE` privilege, acquires `ACCESS EXCLUSIVE` on every affected table, and does not scan rows individually. It is not equivalent to a harmless fast `DELETE`.

Important production considerations include:

- blocking and lock waits;
- foreign-key relationships;
- `ON TRUNCATE` trigger behavior and the fact that `ON DELETE` triggers do not fire;
- sequence restart options;
- replication and change-data-capture behavior;
- transactional rollback behavior and non-MVCC-safe visibility for older snapshots;
- recovery requirements.

`RESTRICT` is the default for foreign-key dependencies. `CASCADE` can expand the operation to referencing tables and their partitions. The decision between `DELETE` and `TRUNCATE` is semantic and operational—not simply slow versus fast.

This tutorial does not execute `TRUNCATE` in the hands-on lab.

## 20. Dropping a table

```sql
DROP TABLE clinical.patient_activity;
```

Dropping a table removes its definition and data when the change commits. The table owner, containing schema owner, or a superuser can drop it. `RESTRICT` is the default and refuses the operation when blocking dependencies exist.

```sql
DROP TABLE clinical.patient_activity CASCADE;
```

can remove dependent objects and must not be used as a generic cleanup shortcut. PostgreSQL automatically removes the target table's indexes, rules, triggers, and constraints. With `CASCADE`, a dependent view can be removed; for a foreign key from another table, the foreign-key constraint is removed rather than the referencing table itself.

Before production removal:

```text
Verify target → stop writes → inventory dependencies and consumers
→ validate backup/recovery → obtain approval → execute
→ validate applications, replication, monitoring, and storage
```

## 21. Table lifecycle states

A useful lifecycle model is:

```text
Proposed
  ↓
Reviewed contract
  ↓
Created
  ↓
Validated
  ↓
Active
  ↓
Changed through reviewed migrations
  ↓
Deprecated
  ↓
Writes stopped and consumers removed
  ↓
Archived or dropped
```

Do not move directly from “apparently unused” to “dropped.”

## 22. Production pre-change checklist

- [ ] Correct environment, endpoint, database, and schema verified
- [ ] Table contract and owner documented
- [ ] Column types reviewed against domain semantics
- [ ] Expected volume, growth, retention, and access patterns reviewed
- [ ] Required constraints and key strategy identified for later implementation
- [ ] Privileges and runtime/deployment roles understood
- [ ] Dependencies and external consumers inventoried
- [ ] Lock and workload impact assessed
- [ ] Replication, CDC, ETL, backup, and monitoring impact reviewed
- [ ] Rollback or tested recovery plan available
- [ ] Validation queries and success criteria defined
- [ ] Required change approval obtained

## 23. Hands-on lab — disposable database only

This exercise is intentionally state-changing:

```text
[LAB-ONLY — MUTATING]
```

Run it only in an authorized disposable, non-production database through a dedicated `psql` session. It uses one transaction and finishes with `ROLLBACK`.

### Step 1 — Verify the target and enable error handling

```sql
\set ON_ERROR_STOP on

SELECT
    current_database(),
    current_user,
    inet_server_addr(),
    inet_server_port(),
    pg_is_in_recovery();
```

Stop unless the target is approved for disposable lab work.

### Step 2 — Preflight collision check

```sql
SELECT
    to_regnamespace('tutorial_table_admin') AS existing_schema,
    to_regclass('tutorial_table_admin.activity_work') AS existing_table;
```

Both results must be `NULL`.

### Step 3 — Begin and create isolated objects

```sql
BEGIN;

CREATE SCHEMA tutorial_table_admin;

CREATE TABLE tutorial_table_admin.activity_work (
    activity_id        bigint,
    patient_reference  text,
    activity_type      text,
    occurred_at        timestamptz,
    source_system      text
);
```

### Step 4 — Inspect the table contract

```sql
SELECT
    table_schema,
    table_name,
    ordinal_position,
    column_name,
    data_type,
    is_nullable
FROM information_schema.columns
WHERE table_schema = 'tutorial_table_admin'
  AND table_name = 'activity_work'
ORDER BY ordinal_position;
```

### Step 5 — Insert controlled lab rows

```sql
INSERT INTO tutorial_table_admin.activity_work (
    activity_id,
    patient_reference,
    activity_type,
    occurred_at,
    source_system
)
VALUES
    (1, 'LAB-PATIENT-001', 'ENCOUNTER', clock_timestamp(), 'tutorial'),
    (2, 'LAB-PATIENT-002', 'CLAIM',     clock_timestamp(), 'tutorial');
```

These are synthetic tutorial values, not production or patient data.

### Step 6 — Inspect metadata and size

```sql
SELECT
    n.nspname,
    c.relname,
    c.relkind,
    c.relpersistence,
    pg_get_userbyid(c.relowner) AS owner,
    pg_table_size(c.oid) AS table_bytes,
    pg_total_relation_size(c.oid) AS total_bytes
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE n.nspname = 'tutorial_table_admin'
  AND c.relname = 'activity_work';
```

### Step 7 — Practice a controlled rename

```sql
ALTER TABLE tutorial_table_admin.activity_work
RENAME TO activity_archive_candidate;

SELECT
    to_regclass('tutorial_table_admin.activity_work') AS old_name,
    to_regclass('tutorial_table_admin.activity_archive_candidate') AS new_name;
```

The old name must be `NULL`; the new name must resolve.

### Step 8 — Inventory before cleanup

```sql
SELECT
    n.nspname,
    c.relname,
    c.relkind,
    pg_get_userbyid(c.relowner) AS owner
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE n.nspname = 'tutorial_table_admin'
ORDER BY c.relname;
```

### Step 9 — Explicit cleanup without `CASCADE`

```sql
DROP TABLE tutorial_table_admin.activity_archive_candidate;
DROP SCHEMA tutorial_table_admin;
```

### Step 10 — Validate and roll back

```sql
SELECT
    to_regnamespace('tutorial_table_admin') AS schema_after_cleanup,
    to_regclass('tutorial_table_admin.activity_archive_candidate') AS table_after_cleanup;

ROLLBACK;

SELECT
    to_regnamespace('tutorial_table_admin') AS schema_after_rollback,
    to_regclass('tutorial_table_admin.activity_archive_candidate') AS table_after_rollback;
```

All four results must be `NULL`. Ending the dedicated session is the final containment step. Transactional containment applies only while the transaction remains uncommitted; never add `COMMIT` to this lab workflow.

## 24. Companion SAFE-READ acceptance lab

`labs/table-lifecycle-check.sql` performs observational checks only. It inventories current-role-visible tables, owners, relation kinds, persistence, access methods, tablespaces, sizes, row estimates, and table statistics.

Run it with:

```bash
psql -X -v ON_ERROR_STOP=1 -d postgres -f labs/table-lifecycle-check.sql
```

Large environments may require an approved schema filter before running broad size or inventory queries.

## 25. Production takeaways

1. Define the row and table contract before writing DDL.
2. Use qualified names and deliberate owners.
3. Treat data types as domain and lifecycle decisions.
4. Distinguish table kinds and persistence modes.
5. Do not interpret estimates as exact counts.
6. SAFE-READ queries can still have operational cost.
7. Treat rename, move, truncate, and drop as reviewed changes.
8. Validate dependencies beyond PostgreSQL catalogs.
9. Avoid `CASCADE` as a cleanup shortcut.
10. Deprecate and drain consumers before removal.

## 26. Summary

Production table administration begins with a durable contract and continues through controlled ownership, inspection, change, deprecation, and retirement. The table is simultaneously a logical interface for applications and a physical database object with storage, locking, statistics, replication, backup, and recovery consequences.

```text
Design → Review → Create → Validate → Operate
→ Evolve → Deprecate → Drain → Archive or Drop
```
