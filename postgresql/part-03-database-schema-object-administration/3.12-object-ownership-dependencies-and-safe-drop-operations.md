# Part 3.12 — Object Ownership, Dependencies, and Safe DROP Operations

**Status:** Revised Final / Canonical Edition

**Target:** PostgreSQL 18

**Audience:** PostgreSQL administrators, DBREs, SREs, platform engineers, developers, and data engineers

**Companion lab:** `labs/ownership-dependency-check.sql`

## Learning objectives

By the end of this tutorial, you should be able to:

- distinguish object ownership from granted privileges;
- inventory owners for common database objects;
- explain how `pg_depend` and `pg_shdepend` protect object integrity;
- interpret normal, automatic, internal, partition, extension, owner, and ACL dependencies;
- trace common foreign-key, view, sequence, and extension relationships;
- understand the limits of catalog-based dependency discovery;
- plan ownership changes without creating security or operational drift;
- use `RESTRICT` as the default destructive-change boundary;
- explain why `CASCADE`, `DROP OWNED`, and `REASSIGN OWNED` require formal review;
- prepare a safe object-decommission plan before executing any `DROP`.

## 1. Ownership is administrative authority

Every PostgreSQL object has an owner. The owner is normally the role that created it, although deployment tooling, `SET ROLE`, restore behavior, or later `ALTER ... OWNER` commands can establish a different owner.

Ownership is not an ordinary grant. The right to alter or destroy an object is inherent in ownership and cannot be delegated as a standalone privilege. Membership in the owning role can also convey that authority, depending on role membership and inheritance behavior.

This is why production objects should normally be owned by controlled, non-personal roles such as:

```text
app_owner
reporting_owner
platform_owner
```

Application login roles should receive only the privileges required to use objects. They should not automatically own the objects they access.

## 2. Ownership is different from privileges

Ownership and privileges answer different questions:

| Question | Ownership | Privilege |
|---|---|---|
| Who controls the object's lifecycle? | Owner | Not implied |
| Who may use the object? | Owner implicitly controls grants | Determined by `GRANT`, defaults, and role membership |
| Who may drop or alter it? | Owner, owning-role member where applicable, or superuser | Cannot be granted as an ordinary object privilege |
| What changes when ownership changes? | Lifecycle authority moves to the new owner; the old owner's implicit owner authority ends | Explicit ACL entries, memberships, policies, and effective access require separate review |

Do not infer ownership from an ACL, and do not infer effective access from ownership columns alone. Effective authority can also come through role membership, ownership of a containing object, security-definer execution, or superuser status.

## 3. Inventory common object owners

Relations—including tables, partitioned tables, views, materialized views, sequences, foreign tables, and indexes—store their owner in `pg_class.relowner`:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS object_name,
    CASE c.relkind
        WHEN 'r' THEN 'TABLE'
        WHEN 'p' THEN 'PARTITIONED TABLE'
        WHEN 'v' THEN 'VIEW'
        WHEN 'm' THEN 'MATERIALIZED VIEW'
        WHEN 'S' THEN 'SEQUENCE'
        WHEN 'f' THEN 'FOREIGN TABLE'
        WHEN 'i' THEN 'INDEX'
        WHEN 'I' THEN 'PARTITIONED INDEX'
        ELSE c.relkind::text
    END AS object_type,
    pg_get_userbyid(c.relowner) AS owner
FROM pg_class AS c
JOIN pg_namespace AS n ON n.oid = c.relnamespace
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema')
  AND n.nspname !~ '^pg_toast'
ORDER BY n.nspname, c.relname;
```

Other catalogs carry ownership for other object classes:

| Object class | Catalog and owner column |
|---|---|
| Database | `pg_database.datdba` |
| Schema | `pg_namespace.nspowner` |
| Relation | `pg_class.relowner` |
| Routine | `pg_proc.proowner` |
| Type or domain | `pg_type.typowner` |
| Extension | `pg_extension.extowner` |
| Collation | `pg_collation.collowner` |
| Conversion | `pg_conversion.conowner` |

An inventory must define its scope. A query that lists only `pg_class` objects is not a complete database ownership inventory.

`pg_type` also contains automatically generated relation row types and array types. The companion artifact excludes relation row types and implicit array rows from its concise type-owner report; that is a reporting choice, not evidence that those catalog objects do not exist.

## 4. PostgreSQL dependency tracking

PostgreSQL records relationships between database objects so destructive commands can preserve structural integrity. A foreign key depends on referenced objects; a view depends on objects used by its stored query; a column depends on its data type; and extension members depend on their extension.

The primary catalogs are:

- `pg_depend` for dependencies between objects in one database;
- `pg_shdepend` for dependencies involving cluster-shared objects such as roles and tablespaces.

`DROP ... RESTRICT` refuses removal when a disallowed dependent object exists. `DROP ... CASCADE` recursively removes dependent objects according to PostgreSQL's dependency rules.

Catalog rows are implementation-level metadata. Use supported descriptive functions such as `pg_describe_object()` when presenting object addresses, and validate important impact through the exact `DROP ... RESTRICT` command in an approved rehearsal environment.

## 5. Understanding `pg_depend`

A `pg_depend` row identifies:

- the dependent object's catalog, OID, and optional column number;
- the referenced object's catalog, OID, and optional column number;
- the dependency type that controls drop behavior.

Important dependency codes include:

| Code | Meaning | Administrative interpretation |
|---|---|---|
| `n` | Normal | Referenced object needs `CASCADE` if the dependent remains. |
| `a` | Automatic | Dependent object is automatically removed with the referenced object. |
| `i` | Internal | Dependent object is an implementation part; target the owning object instead. |
| `P` / `S` | Partition primary/secondary | Internal-style relationship with multiple referenced partition objects. |
| `e` | Extension member | Member follows the owning extension's lifecycle. |
| `x` | Auto extension | Automatically removed with the referenced extension under extension dependency rules. |

Do not reduce dependency analysis to only `deptype = 'n'`. The other types explain why an object may disappear automatically, reject a direct drop, or belong to an extension or partition hierarchy.

## 6. Understanding `pg_shdepend`

`pg_shdepend` connects database objects to shared cluster objects. It has one cluster-wide copy, and its `dbid` identifies the database containing a database-local dependent object. Rows for shared dependent objects use `dbid = 0`.

Important codes include:

| Code | Meaning |
|---|---|
| `o` | A role owns the dependent object. |
| `a` | A role appears in the dependent object's ACL. |
| `i` | A role appears in an initial-privilege record. |
| `r` | A role is referenced by a policy. |
| `t` | A tablespace is referenced by a relation without storage. |

This catalog is central to role retirement. PostgreSQL will not drop a role that still owns objects or is referenced by protected dependencies.

The companion artifact intentionally reports database-local dependents for the current database and shared dependency rows for the current database object only. It does not expose all cluster-wide database, tablespace, or tenant metadata by default. Complete role retirement requires authorized inventory across every relevant database and shared object.

## 7. Trace foreign-key dependencies

Foreign keys are clearer when inspected through `pg_constraint` rather than by decoding raw dependency rows:

```sql
SELECT
    con.conname AS constraint_name,
    con.conrelid::regclass AS referencing_table,
    con.confrelid::regclass AS referenced_table,
    con.convalidated AS validated
FROM pg_constraint AS con
WHERE con.contype = 'f'
ORDER BY con.conrelid::regclass::text, con.conname;
```

For a production decommission, also identify application and ETL behavior that depends on the relationship. Catalogs cannot tell you whether external code expects a constraint, table, or column to exist.

## 8. Trace view and materialized-view dependencies

Views are represented through rewrite rules. A focused query can connect `pg_rewrite` dependency records back to the owning view:

```sql
SELECT DISTINCT
    view_ns.nspname AS view_schema,
    view_rel.relname AS view_name,
    source_ns.nspname AS source_schema,
    source_rel.relname AS source_object
FROM pg_rewrite AS rw
JOIN pg_class AS view_rel ON view_rel.oid = rw.ev_class
JOIN pg_namespace AS view_ns ON view_ns.oid = view_rel.relnamespace
JOIN pg_depend AS dep
  ON dep.classid = 'pg_rewrite'::regclass
 AND dep.objid = rw.oid
JOIN pg_class AS source_rel
  ON dep.refclassid = 'pg_class'::regclass
 AND dep.refobjid = source_rel.oid
JOIN pg_namespace AS source_ns ON source_ns.oid = source_rel.relnamespace
WHERE view_rel.relkind IN ('v', 'm')
  AND view_ns.nspname NOT IN ('pg_catalog', 'information_schema')
  AND source_ns.nspname NOT IN ('pg_catalog', 'information_schema')
  AND view_rel.oid <> source_rel.oid
ORDER BY view_schema, view_name, source_schema, source_object;
```

This is a focused relation-to-relation view inventory, not a universal dependency graph. Views can also depend on functions, operators, types, collations, and other objects.

## 9. Sequence ownership is a dependency relationship

An identity or serial-style sequence can be linked to a table column through dependency metadata. `pg_get_serial_sequence()` is often the simplest supported lookup for a known table and column.

Do not assume that a similarly named sequence is owned by a column. Likewise, do not assume dropping a column will leave its generated sequence untouched. Inspect the actual dependency and generation metadata first.

Changing a sequence owner is not the same as changing `OWNED BY`. One changes administrative ownership; the other changes the sequence-to-column lifecycle dependency.

## 10. Dependencies PostgreSQL might not know

PostgreSQL tracks dependencies that are represented in parsed object definitions and catalogs. It cannot provide a complete inventory of external or dynamically resolved consumers.

Examples that require separate discovery include:

- application SQL stored outside the database;
- ORM mappings, migrations, and generated queries;
- ETL, BI, reporting, and notebook workloads;
- operational scripts, monitoring queries, and backup tooling;
- SQL assembled dynamically inside routines;
- routine bodies stored as string literals where referenced relations are not captured;
- objects accessed through dynamic SQL, foreign systems, or runtime configuration.

SQL-standard routine bodies using `BEGIN ATOMIC` are parsed at definition time, allowing PostgreSQL to record dependencies recognized by the parser. String-literal routine bodies do not necessarily record relation dependencies referenced only inside the body.

Therefore, an empty dependency query never proves that an object is safe to remove.

## 11. Plan an ownership change

Conceptual example:

```sql
ALTER TABLE app.orders OWNER TO app_owner;
```

For a non-superuser, PostgreSQL requires authority over the current object and the ability to become the new owner role; object-specific commands can impose additional requirements such as `CREATE` on the containing schema.

Before changing ownership:

1. verify the exact database, schema, object identity, and current owner;
2. verify the target role and its login/inheritance purpose;
3. inventory ACLs, default privileges, policies, security-definer routines, and role memberships;
4. inspect related objects that may need a consistent ownership boundary;
5. test application, migration, backup, restore, and maintenance behavior;
6. define rollback and post-change validation;
7. execute through reviewed change control.

An owner change transfers lifecycle authority. It is a security-sensitive change even when no data rows are modified.

## 12. `REASSIGN OWNED` is database-scoped operational work

`REASSIGN OWNED` changes ownership of objects owned by selected roles. It affects objects in the current database and certain shared objects, but it does not traverse into other databases to change their local objects.

It also does not remove privileges granted to the old role on objects it does not own, and it does not change that role's default-privilege definitions.

A role-retirement workflow therefore commonly requires deliberate work in every database plus separate privilege and default-privilege review. Never run `REASSIGN OWNED` from an arbitrary maintenance database and assume the cluster is reconciled.

## 13. `DROP OWNED` is destructive

`DROP OWNED BY role_name` drops objects owned by the role in the current database and revokes privileges belonging to that role in relevant scopes. With `CASCADE`, it can recurse to objects owned by other roles.

This command is not a harmless privilege cleanup tool. Before using it:

- inventory the role's ownership and grants in every database;
- inspect shared-object implications;
- use `RESTRICT` during rehearsals;
- capture dependencies and application consumers;
- confirm backups and recovery objectives;
- define the exact role-retirement order;
- require peer approval and a maintenance plan.

Databases and tablespaces owned by the role are not removed by `DROP OWNED`; they require separate ownership handling.

## 14. Safe `DROP`: begin with `RESTRICT`

Use an explicitly qualified and typed command when applicable:

```sql
DROP VIEW app.order_summary RESTRICT;
DROP FUNCTION app.calculate_total(bigint) RESTRICT;
DROP TABLE app.retired_orders RESTRICT;
```

`RESTRICT` is the default for most PostgreSQL `DROP` commands, but writing it explicitly communicates intent and protects reviews from assumptions imported from other database systems.

If `RESTRICT` fails:

1. stop;
2. preserve the exact error and `DETAIL` output;
3. identify every reported dependent;
4. expand the analysis through catalogs and external-consumer discovery;
5. decide whether each dependent must be migrated, replaced, or retired;
6. rehearse the complete plan in a production-like environment;
7. execute individual, reviewed changes in an intentional order.

Do not respond to a dependency error by automatically appending `CASCADE`.

## 15. Why `CASCADE` is high risk

`CASCADE` recursively removes dependent objects. The first-level object named in the command is not the full blast radius.

Risks include:

- removal of constraints, views, routines, or other application objects;
- recursion into objects owned by other teams or roles;
- loss of access paths or integrity enforcement;
- lock waits and application errors during change execution;
- restore complexity and incompatible recovery dependencies;
- a wider effect than catalog summaries anticipated because the plan was incomplete.

If a reviewed migration truly requires `CASCADE`, record the expected dependent objects before execution, compare actual notices and post-change state with that manifest, and treat any difference as a failed validation.

## 16. Object decommission workflow

Use this minimum production workflow:

### Phase 1 — Identify

- exact cluster, endpoint, database, schema, object type, and signature;
- current owner and effective administrative role;
- business owner, technical owner, and consuming services.

### Phase 2 — Inventory

- catalog dependencies and reverse dependencies;
- extension and partition membership;
- constraints, views, routines, sequences, indexes, policies, and grants;
- dynamic SQL and external consumers;
- backup, restore, replication, publication, and monitoring use.

### Phase 3 — Prove disuse

- application-owner confirmation;
- query and workload evidence over an appropriate retention window;
- migration completion and rollback criteria;
- non-production rehearsal with the exact object definition and dependency graph.

### Phase 4 — Execute safely

- approved change window and communication;
- bounded lock and statement timeouts where appropriate;
- explicitly qualified `DROP ... RESTRICT`;
- no automatic retry with `CASCADE`;
- transaction use only when supported and operationally appropriate.

### Phase 5 — Validate

- expected object is absent;
- unexpected objects are not absent;
- applications, jobs, replicas, and monitoring remain healthy;
- grants, ownership, migrations, and documentation reflect the new baseline.

## 17. Troubleshooting

### `cannot drop ... because other objects depend on it`

Treat the failure as protective evidence. Read the complete detail, inspect the reported objects, and build a migration plan. Do not suppress the protection.

### Role cannot be dropped

Inspect ownership and shared dependencies across every database. The role may own objects, appear in ACLs or policies, or own shared objects. Role retirement is cluster-scoped even though many cleanup commands must run database by database.

### Owner change fails

Verify the current owner, role memberships, ability to become the target role, containing-schema requirements, object type, and managed-service restrictions. Do not grant superuser-equivalent authority solely to bypass the error.

### Dependency query shows nothing

Confirm query scope and object addressing. Then inspect stored definitions, dynamic SQL, application repositories, migrations, query telemetry, ETL/BI systems, and operational tooling. Catalog absence is not proof of disuse.

### Object belongs to an extension

Administer it through the extension lifecycle. Do not directly drop or reassign an extension member as though it were an independent application object.

## 18. Production checklist

- [ ] Exact environment, database, schema, object type, and identity verified
- [ ] Current and proposed owners verified
- [ ] Role membership and effective authority reviewed
- [ ] Object and shared dependencies inventoried
- [ ] Extension and partition membership checked
- [ ] Foreign keys, views, routines, sequences, policies, and ACLs reviewed
- [ ] Dynamic SQL and external consumers investigated
- [ ] Replication, backup, restore, and DR impact assessed
- [ ] Lock behavior and execution time rehearsed
- [ ] Rollback or recovery strategy tested
- [ ] `RESTRICT` used as the default boundary
- [ ] Any proposed `CASCADE` has an approved impact manifest
- [ ] Application and business owners approved decommission
- [ ] Post-change validation and monitoring defined

## 19. Hands-on lab

The companion artifact is:

```text
labs/ownership-dependency-check.sql
```

Classification:

```text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
```

It reads PostgreSQL 18 catalogs to report session context, schema/relation/routine/type/extension owners, current-database-local role dependencies, shared dependencies for the current database object, foreign keys, relation-to-relation view dependencies, sequence-to-column ownership dependencies, optionally filtered extension members, and dependency-type counts.

The artifact intentionally performs no `ALTER`, `DROP`, `REASSIGN OWNED`, `DROP OWNED`, privilege change, DML, or user-defined routine execution. Its output is an inventory for review, not a declaration that any object is safe to change or remove.

Run with:

```bash
psql -X --set=ON_ERROR_STOP=1 \
  --dbname=your_database \
  --file=labs/ownership-dependency-check.sql
```

Catalog visibility and output volume depend on the connected role and database. Capture the database, role, server version, artifact checksum, and execution timestamp when using the output as operational evidence.

The transcript contains internal platform metadata such as role, schema, object, extension, and dependency names. Store it only in an access-controlled location and review it before sharing. For large catalogs, first test output volume in a representative non-production or restored database, use a reviewed low-impact window, avoid repeated full polling, and stop if the reads cause measurable resource pressure.

Detailed extension-member output is skipped unless the operator supplies one exact extension name under the lab's restrictive input policy:

```bash
psql -X --set=ON_ERROR_STOP=1 \
  --set=extension_filter=hstore \
  --dbname=your_database \
  --file=labs/ownership-dependency-check.sql
```

The filter is used only as a quoted equality value. It does not enable dynamic SQL or mutation.

## 20. Summary

Ownership controls object lifecycle authority. Dependencies protect structural integrity. Neither one alone describes the complete production impact of changing or dropping an object.

Inventory owners deliberately, interpret both database-local and shared dependency catalogs, account for untracked external consumers, and use explicit `RESTRICT` behavior during planning. Treat owner changes, `REASSIGN OWNED`, `DROP OWNED`, and every destructive command as reviewed administrative changes. `CASCADE` is never a discovery shortcut.
