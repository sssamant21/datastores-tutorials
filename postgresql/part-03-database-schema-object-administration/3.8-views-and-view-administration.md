# Part 3.8 — Views and View Administration

**Status:** Revised Final / Canonical Edition  
**Target:** PostgreSQL 18  
**Audience:** PostgreSQL administrators, DBREs, SREs, developers, platform engineers, and data engineers

## Learning objectives

By the end of this tutorial, you should be able to:

- explain how ordinary PostgreSQL views differ from tables and materialized views;
- create stable, schema-qualified view interfaces;
- understand ownership, privileges, `security_invoker`, and row-level security behavior;
- identify automatically updatable and read-only views;
- use `LOCAL` and `CASCADED CHECK OPTION` correctly;
- inspect definitions, options, columns, and dependencies;
- replace, rename, alter, and drop views safely;
- plan application, reporting, replication, and managed-service impact;
- run an isolated view-administration lab without leaving persistent objects.

## 1. What is a view?

A view is a named query:

```sql
CREATE VIEW reporting.active_patient_event AS
SELECT
    event_id,
    patient_reference,
    event_type,
    occurred_at
FROM clinical.patient_event
WHERE status = 'active';
```

An ordinary view does not store the query's result rows. PostgreSQL runs the view query when the view is referenced.

```text
query against view
    → PostgreSQL rewrites and plans the query
    → base relations and functions execute
    → current result is returned
```

A view can provide abstraction, a stable interface, reusable filtering, privilege separation, and compatibility during schema evolution. It does not automatically improve performance.

## 2. View, table, and materialized view

| Object | Stores result rows | Automatically current | Normal DML target |
|---|---:|---:|---:|
| Table | Yes | Application maintained | Yes |
| Ordinary view | No | Reflects current base data | Sometimes |
| Materialized view | Yes | No; requires refresh | No ordinary automatic propagation |

Materialized-view administration is covered separately in Part 3.9.

## 3. Create explicit interfaces

Prefer explicit columns and stable aliases:

```sql
CREATE VIEW reporting.patient_event_api AS
SELECT
    e.event_id,
    e.patient_reference,
    e.event_type,
    e.occurred_at
FROM clinical.patient_event AS e;
```

Avoid using `SELECT *` as a long-term interface. PostgreSQL expands `*` when the view is created; columns later added to the base table do not automatically appear in the existing view. Explicit columns also make review, ownership, and compatibility clearer.

Schema-qualify both the view and referenced objects. The creator must have `USAGE` on referenced schemas so PostgreSQL can resolve those objects at creation or replacement time.

## 4. Column names and types are contracts

View output names, order, types, typmods, and collations can be application contracts.

Name expressions deliberately:

```sql
CREATE VIEW reporting.event_totals AS
SELECT
    patient_reference,
    count(*) AS event_count
FROM clinical.patient_event
GROUP BY patient_reference;
```

An unnamed literal or expression can produce an unsuitable output name. Explicit casts also prevent an unintended inferred type from becoming part of the interface.

## 5. `CREATE OR REPLACE VIEW`

`CREATE OR REPLACE VIEW` can change a view's defining query without dropping the view:

```sql
CREATE OR REPLACE VIEW reporting.patient_event_api AS
SELECT
    e.event_id,
    e.patient_reference,
    e.event_type,
    e.occurred_at,
    e.source_system
FROM clinical.patient_event AS e;
```

The replacement query must preserve existing output column names, order, and data types. New columns may be appended at the end.

Replacement cannot directly remove, reorder, rename, or change the type of an existing output column. Renaming through `ALTER VIEW ... RENAME COLUMN` is possible but remains an application contract change.

Replacement changes the defining `SELECT`, view options, and check option. Other properties such as ownership, grants, and non-`SELECT` rules remain. The executing role must own the view or be a member of its owning role. Re-evaluate preserved grants against the new columns and row set; retained privileges are not proof that the replacement is safe.

Replacement still requires locking and dependency-safe deployment. Existing clients can fail when they use positional mappings or assume a fixed number of columns, even when PostgreSQL permits an appended column.

Consumers should also select explicit columns. A consumer using `SELECT *` can break or receive newly exposed data after a compatible view extension.

## 6. Views and dependency tracking

PostgreSQL records dependencies between a view and parsed database objects referenced by its definition. `RESTRICT` prevents dropping a referenced object when the view depends on it; `CASCADE` authorizes dependent removal.

Do not use `CASCADE` as dependency discovery. Inspect dependencies and consumers before destructive DDL.

Database dependency tracking does not identify every external dependency, including application SQL, ETL, BI tools, dashboards, exports, or dynamically constructed queries.

## 7. Default privilege model

By default, access to base relations used by a view is checked using the permissions of the view owner.

The querying role normally needs:

- `USAGE` on the schema containing the view;
- the required privilege on the view itself.

The view owner must have the required privileges on underlying relations. Granting access to a view does not grant direct access to its base tables.

This can support controlled interfaces, but a normal view is not automatically a secure data-masking boundary.

Use a deliberately managed, preferably non-login owner role with only the required base-object privileges. Avoid personal accounts, superusers, or broadly privileged administrative roles as owners of application security views. Include view ownership in role lifecycle and offboarding procedures.

## 8. Security-invoker views

```sql
CREATE VIEW reporting.patient_event_invoker
WITH (security_invoker = true) AS
SELECT
    event_id,
    patient_reference,
    event_type
FROM clinical.patient_event;
```

For a security-invoker view, underlying relation privileges are checked using the invoking user. That user needs the relevant privileges on both the view and the underlying objects.

The user still needs `USAGE` only on the schema containing the view, not necessarily on every referenced schema; resolution of referenced names occurred when the view was created or replaced.

## 9. Views are not `SECURITY DEFINER` functions

A default view using owner permissions is not equivalent to a `SECURITY DEFINER` function.

Functions called by the view execute according to their own `SECURITY INVOKER` or `SECURITY DEFINER` declaration. The view user must have permission to execute functions invoked by the view. Expressions such as `CURRENT_USER` reflect the invoking user, not automatically the view owner.

Review function ownership, `EXECUTE`, volatility, leakproof status, and safe `search_path` separately.

## 10. Row-level security interaction

If an underlying relation uses row-level security, a normal view applies the policies and relevant permissions of the view owner by default.

With `security_invoker = true`, PostgreSQL instead uses the invoking user's policies and permissions as though the user referenced the base relation directly.

This choice can materially change which rows are visible. Test with the real application roles, including table owners and roles with `BYPASSRLS`. Do not validate RLS behavior using only a superuser.

Table owners normally bypass row-level security unless `FORCE ROW LEVEL SECURITY` applies. Superusers and roles with `BYPASSRLS` bypass policies. A default owner-rights view owned by one of these identities can therefore expose rows that the invoking role could not read directly.

## 11. Security-barrier views

```sql
CREATE VIEW reporting.restricted_patient_event
WITH (security_barrier = true) AS
SELECT
    event_id,
    patient_reference,
    event_type
FROM clinical.patient_event
WHERE sensitivity = 'standard';
```

Use `security_barrier` when a view is intended to provide row-level security filtering. It constrains optimization order so the view's qualifying conditions, and leakproof conditions where applicable, are evaluated with the required security semantics.

Security barriers can reduce optimizer freedom and affect performance. View predicates are protected from unsafe user-predicate pushdown, while leakproof functions can be evaluated earlier. During update operations, rows not ultimately returned can still be locked. Security barriers do not replace RLS, column privileges, secure functions, encryption, or formal access review.

Excluding a sensitive column is not sufficient masking if the same role can reach the data through the base table, another view, a function, replica, export, or reporting system. Verify effective access paths, not only the selected column list.

## 12. Automatically updatable views

A simple view can be automatically updatable. At the top level, it must generally:

- have exactly one `FROM` entry that is a table or updatable view;
- avoid `WITH`, `DISTINCT`, `GROUP BY`, `HAVING`, `LIMIT`, and `OFFSET`;
- avoid `UNION`, `INTERSECT`, and `EXCEPT`;
- avoid aggregates, window functions, and set-returning functions in the select list.

PostgreSQL can translate `INSERT`, `UPDATE`, `DELETE`, and `MERGE` against such a view into operations on the base relation.

Before granting write privileges, review writable columns, base constraints and triggers, defaults, identity behavior, RLS `USING` and `WITH CHECK` policies, audit behavior, conflict handling, `RETURNING`, and CDC consequences. Successful reads do not prove safe writes.

## 13. Updatable and read-only columns can coexist

A view can contain both simple base-column references and computed columns:

```sql
CREATE VIEW reporting.patient_event_display AS
SELECT
    event_id,
    patient_reference,
    upper(event_type) AS event_type_display
FROM clinical.patient_event;
```

The simple referenced columns can remain updatable while the computed output is read-only. An assignment to a non-updatable column is rejected.

## 14. Filtered views without a check option

Consider:

```sql
CREATE VIEW reporting.active_patient_event AS
SELECT
    event_id,
    patient_reference,
    status
FROM clinical.patient_event
WHERE status = 'active';
```

Without a check option, an allowed insert or update through the view can create a row that no longer satisfies `status = 'active'`. The operation can succeed while the affected row disappears from subsequent reads through that view.

## 15. `WITH CHECK OPTION`

```sql
CREATE VIEW reporting.active_patient_event AS
SELECT
    event_id,
    patient_reference,
    status
FROM clinical.patient_event
WHERE status = 'active'
WITH LOCAL CHECK OPTION;
```

PostgreSQL rejects `INSERT`, `UPDATE`, and `MERGE` results that do not remain visible according to the applicable view condition.

The check option is supported only for automatically updatable views and is not available for recursive views. Interactions with `INSTEAD OF` triggers and rules require special care because checks can stop cascading or be ignored in rewritten operations.

It constrains the results of `INSERT`, `UPDATE`, and `MERGE`; it does not constrain `DELETE`, replace base constraints, or establish authorization by itself. Test updates that move rows outside the predicate and any `ON CONFLICT DO UPDATE` path.

## 16. `LOCAL` versus `CASCADED`

For a view built on another view:

```text
LOCAL
    check this view's condition
    underlying views enforce only their own declared check options

CASCADED
    check this view and conditions in underlying base views
```

If `WITH CHECK OPTION` is written without `LOCAL` or `CASCADED`, PostgreSQL uses `CASCADED`.

Choose explicitly and test all layers. A local option does not mean that an underlying view's own check option is disabled.

## 17. Complex and trigger-updatable views

A complex view that fails the automatic-updatability rules is read-only by default.

`INSTEAD OF` triggers can implement controlled writes, but they introduce application logic, concurrency behavior, error handling, and audit requirements. PostgreSQL rules are another mechanism, but triggers are generally easier to reason about. `MERGE` has restrictions when rules are involved.

Do not add write behavior to a reporting view merely for convenience. Define ownership, validation, transaction behavior, and recovery first.

## 18. View performance

An ordinary view does not cache rows and does not make an expensive query inexpensive by itself. PostgreSQL normally rewrites and optimizes the combined query.

Performance depends on:

- predicates supplied by callers;
- base-table indexes and statistics;
- join cardinality;
- functions and expressions;
- RLS and security barriers;
- nested view depth;
- planning and execution settings;
- data volume and concurrency.

Use `EXPLAIN (ANALYZE, BUFFERS)` only in an authorized performance environment or under an approved production diagnostic procedure. `ANALYZE` executes the query.

Review representative caller predicates, nested-view expansion, RLS, security barriers, function cost, sorts and spills, parallelism, timeouts, and concurrency rather than benchmarking only the bare view query.

## 19. Nested views and interface depth

Views built on views can provide clean layering, but excessive nesting can make ownership, predicates, dependencies, and plans difficult to understand.

Document:

- the authoritative base objects;
- which layer provides security;
- which layer is an external contract;
- who owns each layer;
- how changes are tested end to end.

## 20. Temporary and recursive views

A temporary view is session-scoped and lives in a temporary schema. If a view references a temporary relation, PostgreSQL creates the view as temporary even if `TEMP` was not written.

Temporary views can shadow permanent relations of the same unqualified name. Use schema-qualified references in administrative and security-sensitive SQL. Connection pools should not create session-scoped objects without a cleanup and session-reuse policy.

A recursive view is shorthand around a recursive common table expression and requires an explicit view column list. Recursive views do not support `CHECK OPTION`.

Neither feature should be introduced into production workflows without clear lifecycle and concurrency expectations.

## 21. Inspecting views

Portable metadata:

```sql
SELECT
    table_schema,
    table_name,
    view_definition,
    check_option,
    is_updatable,
    is_insertable_into,
    is_trigger_updatable
FROM information_schema.views
ORDER BY table_schema, table_name;
```

PostgreSQL-specific metadata:

```sql
SELECT
    schemaname,
    viewname,
    viewowner,
    definition
FROM pg_views
ORDER BY schemaname, viewname;
```

Inspect options and relation metadata:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS view_name,
    pg_get_userbyid(c.relowner) AS owner,
    c.reloptions
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.relkind = 'v'
ORDER BY n.nspname, c.relname;
```

Information-schema views expose only objects visible to the current role. Do not interpret missing rows automatically as missing database objects.

`information_schema.views.view_definition` is null when the view is not owned by a currently enabled role, even when the view is otherwise visible.

## 22. Inspecting definitions and dependencies

Use `pg_get_viewdef` for a reconstructed definition:

```sql
SELECT pg_get_viewdef(
    'reporting.active_patient_event'::regclass,
    true
);
```

Catalog dependency queries can be useful, but they are easy to misinterpret because view dependencies are represented through rewrite rules. Prefer supported inspection functions and tested administration queries instead of manually modifying system catalogs.

## 23. Renaming and altering a view

Examples:

```sql
ALTER VIEW reporting.patient_event_api
RENAME TO patient_event_v1;

ALTER VIEW reporting.patient_event_v1
SET (security_invoker = true);
```

`ALTER VIEW` can change view options, ownership, schema, names, and certain column properties. Every change requires dependency, privilege, application, and rollback review.

For a bounded deployment:

```sql
BEGIN;
SET LOCAL lock_timeout = '5s';
SET LOCAL statement_timeout = '2min';
CREATE OR REPLACE VIEW ...;
-- run prepared metadata and smoke checks
COMMIT;
```

Timeouts are environment-specific. Do not leave a failed migration transaction idle while it retains locks.

## 24. Dropping views safely

```sql
DROP VIEW reporting.patient_event_v1 RESTRICT;
```

Use `RESTRICT` as the normal boundary. PostgreSQL refuses the drop when another database object depends on the view.

```sql
DROP VIEW reporting.patient_event_v1 CASCADE;
```

`CASCADE` can recursively remove dependent views and other objects. Never use it as a shortcut in production. Inventory database and external dependencies, preserve definitions and grants, obtain approval, and verify consumers before destructive DDL.

## 25. Safe deployment patterns

For a compatible extension:

```text
append compatible view columns
→ deploy consumers that tolerate both shapes
→ verify permissions and plans
→ observe
```

For a breaking change:

```text
create versioned view
→ grant and test
→ migrate consumers
→ observe old-view usage
→ revoke or retire old interface
→ drop later with RESTRICT
```

Versioned views are often safer than changing a shared interface in place.

Account for prepared statements, driver caches, connection pools, ORM mappings, BI metadata, exports, and schema registries. Define whether connections or consumers must be recycled and monitor for result-type, cached-plan, missing-column, and decoding failures.

Transactional DDL can restore an uncommitted definition. It cannot undo data already modified through an updatable view, results already exported, information already exposed, CDC messages, or application requests executed against the temporary definition. Define application rollback and incident response in addition to SQL rollback.

## 26. Replication, CDC, backups, and restores

Physical replication carries catalog changes through WAL. Logical replication does not generally replicate view DDL and does not publish ordinary view rows as base-table changes.

Coordinate:

- subscriber-side view definitions;
- function and type dependencies;
- grants and ownership;
- CDC queries that read through views;
- restore ordering;
- schema migration ordering;
- failover and disaster-recovery validation.

## 27. Production checklist

- [ ] Correct environment, endpoint, database, and schema verified
- [ ] View owner and migration role verified
- [ ] Owner is a deliberately managed least-privilege role
- [ ] Explicit output names, order, types, typmods, and collations reviewed
- [ ] Base tables, functions, nested views, and external consumers inventoried
- [ ] Direct and indirect access paths to sensitive columns verified
- [ ] Default versus security-invoker privilege behavior selected intentionally
- [ ] RLS tested using real application roles
- [ ] Security-barrier requirement and performance impact reviewed
- [ ] Automatic updatability and writable columns verified
- [ ] Write grants, triggers, RLS, audit, conflict, and CDC behavior reviewed
- [ ] `LOCAL` or `CASCADED CHECK OPTION` selected and tested
- [ ] Replacement compatibility and grants verified
- [ ] Prepared statements, pools, ORM, BI, export, and schema caches reviewed
- [ ] Query plans and base-table indexes reviewed
- [ ] Logical replication, CDC, backup, restore, and failover behavior reviewed
- [ ] Rollback, versioning, monitoring, and retirement procedures defined
- [ ] Destructive changes use `RESTRICT`

## 28. Hands-on lab — disposable database only

The companion lab is intentionally state-changing:

```text
[LAB-ONLY — MUTATING — TRANSACTIONALLY CONTAINED]
```

It creates an isolated base table and several views, proves read and automatic-write behavior, verifies `CHECK OPTION`, inspects security options and metadata, demonstrates replacement and dependency protection, rolls back, and programmatically verifies cleanup.

The lab validates definitions and stored catalog options only. It does not certify cross-role privileges, RLS behavior, masking, or security isolation; those require an authorized multi-role test environment using the real ownership and grant model.

Run only in an authorized disposable, non-production database with a dedicated session:

```bash
psql -X -v ON_ERROR_STOP=1 \
  -v lab_confirm=I_UNDERSTAND \
  -d disposable_database \
  -f labs/views-administration-lab.sql
```

## 29. Managed PostgreSQL services

The SQL semantics apply broadly to RDS for PostgreSQL, Aurora PostgreSQL-Compatible Edition, Azure Database for PostgreSQL, and Cloud SQL for PostgreSQL. Available roles, RLS administration, extension-provided functions, cross-database integrations, query monitoring, and deployment controls differ. Validate the provider, engine version, and organizational privilege model.

## 30. Summary

Views are database interfaces, not stored query results or automatic performance accelerators.

```text
define explicit contract
→ choose ownership and security semantics
→ test reads and permitted writes
→ inspect dependencies and plans
→ deploy compatibly
→ monitor consumers
→ retire with RESTRICT
```
