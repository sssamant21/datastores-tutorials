## 1.10.1 Why Constraints Matter

A PostgreSQL data type answers what kind of value a column can contain. A constraint answers what rules the stored data must satisfy.

For example:

```sql
visit_count integer NOT NULL CHECK (visit_count >= 0)
```

Application validation remains important for usability and business workflows, but critical integrity rules should not depend entirely on every application, script, ETL pipeline, or administrator behaving correctly.

## 1.10.2 Core PostgreSQL Constraints

This tutorial introduces `NOT NULL`, `CHECK`, `UNIQUE`, `PRIMARY KEY`, and `FOREIGN KEY`, plus constraint naming, composite keys, referential actions, constraint-backed indexes, child-side foreign-key indexing, and PostgreSQL 18 catalog inspection.

## 1.10.3 NOT NULL

Use `NOT NULL` when a value is mandatory:

```sql
patient_code varchar(30) NOT NULL
```

Use it because the domain requires a value, not merely because it appears stricter.

## 1.10.4 CHECK Constraints and NULL

A `CHECK` constraint requires its expression to evaluate to TRUE or UNKNOWN. Therefore:

```sql
CHECK (visit_count >= 0)
```

does not by itself reject `NULL`. If a value is required, combine the rules:

```sql
visit_count integer NOT NULL CHECK (visit_count >= 0)
```

Do not use `CHECK` as a substitute for arbitrary cross-row or cross-table integrity. Such rules generally belong in mechanisms designed for relationships or uniqueness, such as `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY`, or `EXCLUDE`, or in appropriately designed application/database logic.

## 1.10.5 UNIQUE

A `UNIQUE` constraint prevents duplicate key values according to PostgreSQL uniqueness semantics:

```sql
CONSTRAINT uq_constraint_patient_code UNIQUE (patient_code)
```

PostgreSQL automatically creates the unique B-tree index required to enforce an ordinary unique constraint. Do not create another identical unique index solely to enforce the same rule.

By default, null values in a unique constraint are considered distinct. PostgreSQL can instead use `UNIQUE NULLS NOT DISTINCT (...)` when the intended model treats nulls as equal for uniqueness.

## 1.10.6 PRIMARY KEY

A primary key identifies each row and provides uniqueness plus non-nullability while declaring the designated row identifier:

```sql
patient_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

A table has one primary key, although it can contain multiple columns. PostgreSQL automatically creates a unique B-tree index to enforce an ordinary primary key.

Composite example:

```sql
PRIMARY KEY (patient_id, sequence_no)
```

Use a composite key only when identity genuinely depends on multiple attributes.

## 1.10.7 FOREIGN KEY

A foreign key establishes referential integrity between tables:

```sql
patient_id bigint NOT NULL
    REFERENCES clinical.constraint_patient(patient_id)
```

In this lab, `constraint_patient` is the referenced/parent table and `constraint_visit` is the referencing/child table.

Common referential actions include `NO ACTION`, `RESTRICT`, `CASCADE`, `SET NULL`, and `SET DEFAULT`. `NO ACTION` is the default. When a foreign-key constraint is deferrable, `NO ACTION` checking can be deferred as permitted by its configuration. `RESTRICT` does not permit that referential action to be deferred.

This lab deliberately uses `ON DELETE RESTRICT`.

## 1.10.8 Foreign-Key Indexing

Creating a foreign key does not automatically create an index on the referencing child columns. For many production workloads, such an index is useful because PostgreSQL may need to locate referencing rows when a referenced key is updated or deleted.

```sql
CREATE INDEX idx_constraint_visit_patient_id
    ON clinical.constraint_visit(patient_id);
```

Index decisions should still consider workload, table size, cardinality, write overhead, and existing indexes.

## 1.10.9 Build the Parent Table

```sql
CREATE TABLE clinical.constraint_patient (
    patient_id bigint GENERATED ALWAYS AS IDENTITY,
    patient_code varchar(30) NOT NULL,
    age_years integer,
    status text NOT NULL DEFAULT 'ACTIVE',
    created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT pk_constraint_patient
        PRIMARY KEY (patient_id),

    CONSTRAINT uq_constraint_patient_code
        UNIQUE (patient_code),

    CONSTRAINT ck_constraint_patient_age
        CHECK (age_years IS NULL OR age_years BETWEEN 0 AND 130),

    CONSTRAINT ck_constraint_patient_status
        CHECK (status IN ('ACTIVE', 'INACTIVE'))
);
```

## 1.10.10 Build the Child Table

```sql
CREATE TABLE clinical.constraint_visit (
    visit_id bigint GENERATED ALWAYS AS IDENTITY,
    patient_id bigint NOT NULL,
    visit_sequence integer NOT NULL,
    visit_type text NOT NULL,
    visit_at timestamptz NOT NULL,

    CONSTRAINT pk_constraint_visit
        PRIMARY KEY (visit_id),

    CONSTRAINT uq_constraint_visit_sequence
        UNIQUE (patient_id, visit_sequence),

    CONSTRAINT ck_constraint_visit_sequence
        CHECK (visit_sequence > 0),

    CONSTRAINT ck_constraint_visit_type
        CHECK (visit_type IN ('ROUTINE', 'FOLLOW_UP', 'URGENT')),

    CONSTRAINT fk_constraint_visit_patient
        FOREIGN KEY (patient_id)
        REFERENCES clinical.constraint_patient(patient_id)
        ON DELETE RESTRICT
);
```

Create the child-side index separately:

```sql
CREATE INDEX idx_constraint_visit_patient_id
    ON clinical.constraint_visit(patient_id);
```

## 1.10.11 Insert Synthetic Data

```sql
INSERT INTO clinical.constraint_patient (
    patient_code,

    status

    ('LAB-P002', 52, 'ACTIVE'),
```


## 1.10.12 Query the Relationship

```sql
SELECT
    p.patient_code,
    p.status,
    v.visit_sequence,
    v.visit_type,
    v.visit_at
FROM clinical.constraint_patient AS p
JOIN clinical.constraint_visit AS v
    ON v.patient_id = p.patient_id
ORDER BY p.patient_code, v.visit_sequence;
```

## 1.10.13 Expected-Failure Lab Safety

Use a separate transaction for each intentional constraint violation:

```sql
BEGIN;
-- one intentionally invalid statement
ROLLBACK;
```

After PostgreSQL reports an error inside a transaction, issue `ROLLBACK` before beginning the next experiment.

### UNIQUE failure

```sql
BEGIN;
INSERT INTO clinical.constraint_patient (patient_code, age_years, status)
VALUES ('LAB-P001', 40, 'ACTIVE');
ROLLBACK;
```

### CHECK failure

```sql
BEGIN;
INSERT INTO clinical.constraint_patient (patient_code, age_years, status)
VALUES ('LAB-BAD-AGE', -10, 'ACTIVE');
ROLLBACK;
```

### FOREIGN KEY failure

```sql
BEGIN;
INSERT INTO clinical.constraint_visit (
    patient_id, visit_sequence, visit_type, visit_at
)
VALUES (999999999, 1, 'ROUTINE', CURRENT_TIMESTAMP);
ROLLBACK;
```

### ON DELETE RESTRICT

```sql
SELECT patient_id, patient_code
FROM clinical.constraint_patient
WHERE patient_code = 'LAB-P001';

BEGIN;
DELETE FROM clinical.constraint_patient
WHERE patient_code = 'LAB-P001';
ROLLBACK;
```

The delete should be rejected because dependent visits reference the parent.

## 1.10.14 Inspect Constraints with information_schema

```sql
SELECT
    table_schema,
    table_name,
    constraint_name,
    constraint_type,
    is_deferrable,
    initially_deferred,
    enforced
FROM information_schema.table_constraints
WHERE table_schema = 'clinical'
  AND table_name IN ('constraint_patient', 'constraint_visit')
ORDER BY table_name, constraint_type, constraint_name;
```

This view is privilege-aware and should not be treated as an unrestricted inventory of every database constraint. PostgreSQL's information-schema representation reports not-null constraints under the `CHECK` constraint category.

## 1.10.15 PostgreSQL 18 pg_constraint

PostgreSQL 18 represents `NOT NULL` constraints in `pg_constraint` with `contype = 'n'`.

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    con.conname AS constraint_name,
    con.contype AS constraint_type,
    con.condeferrable,
    con.condeferred,
    con.conenforced,
    pg_get_constraintdef(con.oid) AS definition
FROM pg_constraint AS con
JOIN pg_class AS c ON c.oid = con.conrelid
JOIN pg_namespace AS n ON n.oid = c.relnamespace
WHERE n.nspname = 'clinical'
  AND c.relname IN ('constraint_patient', 'constraint_visit')
ORDER BY c.relname, con.conname;
```

Useful PostgreSQL 18 `contype` values include `c` CHECK, `f` FOREIGN KEY, `n` NOT NULL, `p` PRIMARY KEY, `u` UNIQUE, and `x` EXCLUSION. PostgreSQL 18 also exposes enforcement metadata through `conenforced`. This introductory tutorial uses normal enforced constraints.

## 1.10.16 Inspect Indexes

```sql
SELECT
    schemaname,
    tablename,
    indexname,
    indexdef
FROM pg_indexes
WHERE schemaname = 'clinical'
  AND tablename IN ('constraint_patient', 'constraint_visit')
ORDER BY tablename, indexname;
```

Observe the indexes supporting `PRIMARY KEY` and `UNIQUE`, and compare them with the explicitly created `idx_constraint_visit_patient_id`.

A constraint expresses an integrity rule. An index is a physical access structure. Some constraints use indexes to enforce their rules.

## 1.10.17 Production Modeling Checklist

Before defining a constraint, ask whether the rule is always true for valid data, whether PostgreSQL should enforce it regardless of the writer, whether NULL has legitimate meaning, what identifies the row, whether relationships require referential integrity, what should happen when a parent is deleted, and whether foreign-key operations benefit from a child-side index.

## 1.10.18 Existing Production Tables Are Different

Creating constraints with new tutorial tables is not operationally equivalent to adding constraints to existing high-volume production tables. Production changes can involve existing invalid data, locks, table scans, index creation, CPU, disk I/O, WAL, replication impact, deployment sequencing, and application compatibility.

Do not convert this introductory lab directly into an unreviewed production `ALTER TABLE` runbook. PostgreSQL supports operational techniques such as adding certain supported constraints as `NOT VALID` and validating them separately with `VALIDATE CONSTRAINT`; those techniques belong in a later production schema-change tutorial.

## 1.10.19 PostgreSQL 18 Enforcement Features

PostgreSQL 18 includes additional constraint capabilities and enforcement metadata. Those advanced capabilities are intentionally outside this introductory lab. The foundation here is to declare an integrity rule, have PostgreSQL enforce it, and reject invalid data.
