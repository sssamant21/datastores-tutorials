## 1.7.1 Learning objectives

By the end of this section, you should be able to:

- distinguish a database, schema, table, column, and row;
- inspect schemas before creating one;
- understand schema ownership;
- create a schema with an explicit owner;
- inspect schema privileges;
- understand `search_path`;
- distinguish `SHOW search_path`, `current_schema()`, and `current_schemas(true)`;
- understand why schema qualification matters and why `search_path` has security implications;
- create a table and understand basic table ownership;
- introduce identity, primary-key, `NOT NULL`, and default concepts;
- inspect tables through `psql`, `information_schema`, and `pg_catalog`;
- use `to_regclass()` for safe existence checks;
- recognize schema/table drift;
- troubleshoot common schema and table creation failures;
- understand destructive schema/table operations without executing them; and
- validate the lab with a read-only artifact.

## 1.7.2 Safety classifications

```text
[SAFE-READ]
Read-only inspection.

[LAB-ONLY]
State-changing operation restricted to the tutorial lab.

[LAB-ONLY — INTENTIONAL ERROR]
Controlled failure used for learning.

[PRODUCTION-CAUTION]
Requires impact, dependency, security, change,
rollback, and operational assessment.

[DESTRUCTIVE]
Can permanently remove objects or data.
```

In this lab, `CREATE SCHEMA` and `CREATE TABLE` are `[LAB-ONLY]`. In production, both should be treated as `[PRODUCTION-CAUTION]`. DDL can interact with applications, migrations, privileges, dependencies, deployment ordering, locks, backups, monitoring, and automation.

## 1.7.5 Database, schema, and table

A schema provides a namespace inside a database:

```text
PostgreSQL Cluster
      ↓
Database
      ↓
Schema
      ↓
Table
      ↓
Columns + Rows
```

Schemas are database-local. A `clinical` schema in `healthcare_lab` is independent of a `clinical` schema in `tutorial_db`.

## 1.7.6 Inspect existing schemas

Using `psql`:

```text
\dn
```

Using SQL:

```sql
-- [SAFE-READ]
SELECT schema_name
FROM information_schema.schemata
ORDER BY schema_name;
```

`information_schema.schemata` reflects the current database and schemas visible/accessible to the current user. It is not an unrestricted cluster-wide inventory.

`information_schema` provides SQL-standard-oriented metadata useful for portability. `pg_catalog` provides PostgreSQL-specific metadata for deeper administration.

Inspect PostgreSQL schema metadata:

```sql
-- [SAFE-READ]
SELECT
    n.nspname AS schema_name,
    pg_catalog.pg_get_userbyid(n.nspowner) AS owner
FROM pg_catalog.pg_namespace AS n
ORDER BY n.nspname;
```

Do not directly modify system catalogs. Use supported PostgreSQL DDL.

## 1.7.7 Schema naming rule

PostgreSQL reserves schema names beginning with `pg_` for system purposes. Use application names such as `clinical`, `reporting`, `archive`, or `integration`; avoid names such as `pg_clinical` or `pg_application`.

## 1.7.8 Discover current state before creating the schema

```sql
-- [SAFE-READ]
SELECT
    n.nspname AS schema_name,
    pg_catalog.pg_get_userbyid(n.nspowner) AS owner
FROM pg_catalog.pg_namespace AS n
WHERE n.nspname = 'clinical';
```

If `clinical` already exists, stop, inspect its owner, understand why it exists, and compare current state with desired state. Do not delete it automatically.

Verify database `CREATE` privilege:

```sql
-- [SAFE-READ]
SELECT
    has_database_privilege(
        current_user,
        current_database(),
        'CREATE'
    ) AS can_create_schema;
```

If this returns `false`, do not automatically grant privileges or switch to superuser. Investigate the intended access model.

Creating a schema and assigning its owner are separate authorization questions. Database `CREATE` authority does not imply arbitrary owner assignment. In this lab, the executor and owner are both `tutorial_admin`.

## 1.7.9 Create and validate the schema

```sql
-- [LAB-ONLY]
CREATE SCHEMA clinical
    AUTHORIZATION tutorial_admin;
```

Expected command tag: `CREATE SCHEMA`.

Validate immediately:

```text
\dn clinical
```

```sql
-- [SAFE-READ]
SELECT
    n.nspname AS schema_name,
    pg_catalog.pg_get_userbyid(n.nspowner) AS owner
FROM pg_catalog.pg_namespace AS n
WHERE n.nspname = 'clinical';
```

The lab owner should be `tutorial_admin`.

A schema owner is not necessarily an application's runtime identity. Production designs may separate owner/migration, read-write, read-only, and administrative roles. That architecture is deferred to Part 4.

## 1.7.10 Understand `search_path`

Run all three:

```sql
SHOW search_path;
SELECT current_schema();
SELECT current_schemas(true);
```

Interpret them as:

```text
SHOW search_path
       ↓
configured search-path expression

current_schema()
       ↓
first effective schema used as the
current creation namespace

current_schemas(true)
       ↓
effective searchable schema sequence,
including implicit schemas
```

If `$user` appears in `search_path`, PostgreSQL can substitute a schema corresponding to `CURRENT_USER` when applicable. It does not mean PostgreSQL automatically creates a schema for every role.

`pg_catalog` receives special treatment during lookup and can participate in effective resolution even when it is not explicitly shown by `SHOW search_path`. A session's temporary schema can also receive special precedence for certain object types; detailed temporary-object resolution is deferred.

## 1.7.11 Schema qualification and security

If multiple schemas contain `patients`, an unqualified reference such as:

```sql
SELECT * FROM patients;
```

depends on name resolution. An explicit reference:

```sql
SELECT * FROM clinical.patients;
```

states the intended object. For administrative scripts and automation, prefer `schema.object` because it improves clarity, predictability, troubleshooting, automation safety, and security reasoning.

`search_path` is not only a convenience. Writable schemas in an effective search path can influence unqualified object resolution, so search-path design intersects with security, ownership, `CREATE` privileges, and automation behavior.

If an unqualified query fails while the qualified form succeeds, do not immediately change `search_path`. First verify the object, schema, configured path, `current_schema()`, effective schemas, and the application's expected resolution behavior.

Unqualified object creation is also path-dependent. Our lab avoids that ambiguity and uses `CREATE TABLE clinical.patients` explicitly.

## 1.7.12 Define and inspect the first table

The table is a synthetic healthcare model. No real patient information is used.

Before creation:

```text
\dt clinical.*
```

```sql
-- [SAFE-READ]
SELECT
    table_schema,
    table_name,
    table_type
FROM information_schema.tables
WHERE table_schema = 'clinical'
  AND table_name = 'patients';
```

Use `to_regclass()` for a safe existence check:

```sql
-- [SAFE-READ]
SELECT pg_catalog.to_regclass(
    'clinical.patients'
) AS patients_relation;
```

Before creation this should normally return `NULL`. When the relation exists, it resolves to the relation identity. This is useful in diagnostic scripts because it avoids deliberately triggering a relation-not-found error.

## 1.7.13 Create `clinical.patients`

```sql
-- [LAB-ONLY]
CREATE TABLE clinical.patients (
    patient_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    first_name VARCHAR(100) NOT NULL,
    last_name VARCHAR(100) NOT NULL,
    date_of_birth DATE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Expected command tag: `CREATE TABLE`.

Column overview:

| Column | Type | Purpose |
|---|---|---|
| `patient_id` | `BIGINT` | Generated row identifier |
| `first_name` | `VARCHAR(100)` | Synthetic first name |
| `last_name` | `VARCHAR(100)` | Synthetic last name |
| `date_of_birth` | `DATE` | Calendar date |
| `created_at` | `TIMESTAMPTZ` | Row creation timestamp |

`VARCHAR(100)` is a tutorial choice, not a universal PostgreSQL production recommendation. Part 1.9 compares `varchar(n)`, `varchar`, and `text`.

## 1.7.14 Identity, primary key, nullability, and defaults

`patient_id BIGINT GENERATED ALWAYS AS IDENTITY` tells PostgreSQL to generate identity values. Identity handles value generation; it does not itself guarantee uniqueness. The primary key supplies the uniqueness and non-null key semantics used here.

Because the column is `GENERATED ALWAYS`, normal inserts in Part 1.8 should omit `patient_id` and allow PostgreSQL to generate it. Advanced identity override behavior is deferred.

PostgreSQL uses supporting index infrastructure to enforce a primary key. Constraint design is deferred to Part 1.10 and index mechanics to Part 8.

`NOT NULL` means SQL `NULL` is not permitted for the specified columns. `DEFAULT CURRENT_TIMESTAMP` supplies a value when an insert omits `created_at`; it does not continuously update that column afterward.

`TIMESTAMPTZ` is PostgreSQL shorthand for `timestamp with time zone`. It is appropriate here for an event timestamp, but detailed timezone/storage/display semantics are deferred to Part 1.9.

## 1.7.15 Validate the table

Using `psql`:

```text
\dt clinical.*
\d clinical.patients
\d+ clinical.patients
```

Inspect table metadata:

```sql
-- [SAFE-READ]
SELECT
    schemaname AS schema_name,
    tablename AS table_name,
    tableowner AS table_owner
FROM pg_catalog.pg_tables
WHERE schemaname = 'clinical'
  AND tablename = 'patients';
```

Inspect columns:

```sql
-- [SAFE-READ]
SELECT
    ordinal_position,
    column_name,
    data_type,
    is_nullable,
    column_default,
    is_identity,
    identity_generation
FROM information_schema.columns
WHERE table_schema = 'clinical'
  AND table_name = 'patients'
ORDER BY ordinal_position;
```

For `patient_id`, verify `is_identity = YES` and `identity_generation = ALWAYS`.

For deeper PostgreSQL-specific inspection:

```sql
-- [SAFE-READ]
SELECT
    n.nspname AS schema_name,
    c.relname AS relation_name,
    c.relkind,
    pg_catalog.pg_get_userbyid(c.relowner) AS owner
FROM pg_catalog.pg_class AS c
JOIN pg_catalog.pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE n.nspname = 'clinical'
  AND c.relname = 'patients';
```

PostgreSQL uses the broader term `relation` for several object types. Tables are one kind of relation. No need to memorize `relkind` codes yet.

## 1.7.16 Schema privileges: `USAGE` vs `CREATE`

```sql
-- [SAFE-READ]
SELECT
    n.nspname AS schema_name,
    has_schema_privilege(
        current_user,
        n.oid,
        'USAGE'
    ) AS has_usage,
    has_schema_privilege(
        current_user,
        n.oid,
        'CREATE'
    ) AS has_create
FROM pg_catalog.pg_namespace AS n
WHERE n.nspname = 'clinical';
```

`USAGE` concerns access/name lookup for objects in the schema, subject to object privileges. `CREATE` permits creating new objects in the schema. `USAGE` alone should not be interpreted as permission to create a table.

Using the schema OID makes the diagnostic robust: if `clinical` is missing, the query returns zero rows instead of depending on a missing schema name.

If `has_create` is false, do not auto-GRANT. Verify the intended role, ownership, access model, and deployment/migration role before changing privileges.

## 1.7.17 Table definition vs table data

After successful creation:

```sql
-- [SAFE-READ]
SELECT COUNT(*) AS row_count
FROM clinical.patients;
```

Expected: `0`.

A table can exist with columns, types, constraints, identity, defaults, ownership, privileges, and metadata while containing zero application rows. Part 1.7 establishes structure; Part 1.8 introduces data.

## 1.7.18 Identifier casing

Unquoted PostgreSQL identifiers are folded to lowercase. A statement such as `CREATE TABLE PatientRecords (...)` creates an unquoted identifier that behaves as `patientrecords`. Quoted identifiers such as `"PatientRecords"` preserve case and generally require matching quoting later.

This tutorial uses `lowercase_snake_case`, for example `clinical`, `patients`, `patient_id`, `date_of_birth`, and `created_at`.

## 1.7.19 Controlled duplicate-schema failure

```sql
-- [LAB-ONLY — INTENTIONAL ERROR]
CREATE SCHEMA clinical
    AUTHORIZATION tutorial_admin;
```

Because `clinical` exists, PostgreSQL should reject the duplicate. Capture the exact error and inspect existing state rather than deleting the schema.

## 1.7.20 Controlled duplicate-table failure

```sql
-- [LAB-ONLY — INTENTIONAL ERROR]
CREATE TABLE clinical.patients (
    patient_id BIGINT
);
```

Again, capture the exact error and inspect `\d clinical.patients`.

The operational pattern is `ERROR → DISCOVER EXISTING STATE → COMPARE WITH DESIRED STATE`, not `ERROR → DROP OBJECT → TRY AGAIN`.

## 1.7.21 `IF NOT EXISTS` is not desired-state validation

PostgreSQL supports forms such as:

```sql
CREATE SCHEMA IF NOT EXISTS clinical;
CREATE TABLE IF NOT EXISTS clinical.patients (...);
```

But `IF NOT EXISTS` does not prove that an existing object has the intended owner, columns, data types, constraints, defaults, identity definition, or privileges.

Production automation eventually needs:

```text
DISCOVER
   ↓
COMPARE
   ↓
DETECT DRIFT
   ↓
PLAN
   ↓
CHANGE
   ↓
VALIDATE
```

## 1.7.22 Controlled schema-resolution experiment

Compare:

```text
\dt archive.*
\dt clinical.*
```

Do not create `archive` merely to make the first command succeed.

Then compare:

```sql
SELECT COUNT(*) FROM patients;
SELECT COUNT(*) FROM clinical.patients;
```

Depending on effective schema resolution, the unqualified form may fail even though `clinical.patients` exists. Object existence does not guarantee that an unqualified name resolves to it.

## 1.7.23 Troubleshoot `relation does not exist`

Use an evidence-first workflow:

```text
CAPTURE EXACT ERROR
       ↓
VERIFY SERVER
       ↓
VERIFY DATABASE
       ↓
VERIFY ROLE
       ↓
VERIFY SPELLING / CASE
       ↓
CHECK to_regclass()
       ↓
VERIFY EXPECTED SCHEMA
       ↓
SHOW search_path
       ↓
CHECK current_schema()
       ↓
CHECK effective schemas
       ↓
VERIFY DEPLOYMENT STATE
       ↓
DETERMINE ROOT CAUSE
```

Do not immediately conclude that the table is physically missing.

## 1.7.24 Troubleshoot schema creation

If `CREATE SCHEMA clinical` fails, capture the exact error, verify the database and current user, inspect database `CREATE` privilege, check whether the schema already exists, verify requested ownership/authorization, and determine root cause before remediation.

Useful query:

```sql
SELECT
    current_database(),
    current_user,
    has_database_privilege(
        current_user,
        current_database(),
        'CREATE'
    ) AS database_create_privilege;
```

## 1.7.25 Troubleshoot table creation

If `CREATE TABLE clinical.patients (...)` fails, verify the database, schema existence, current role, schema `CREATE` authority, existing table state, column definitions, data types, constraint syntax, and any other required privileges. Do not automatically elevate privileges.

## 1.7.26 Destructive boundaries

PostgreSQL supports:

```sql
-- [DESTRUCTIVE — EXAMPLE ONLY — DO NOT EXECUTE]
DROP TABLE clinical.patients;
```

and:

```sql
-- [DESTRUCTIVE — EXAMPLE ONLY — DO NOT EXECUTE]
DROP SCHEMA clinical;
```

Part 1.7 executes neither operation. It also does not provide executable `DROP ... CASCADE` cleanup. A dependency error should lead to dependency inspection and blast-radius analysis, not an automatic `CASCADE` response.

Leave `clinical` and `clinical.patients` intact for Part 1.8.

## 1.7.27 Physical-file boundary

Do not use filesystem commands such as `cp`, `mv`, or `rm` inside PostgreSQL's data directory to create, move, rename, copy, or delete tables. Use supported PostgreSQL interfaces. Physical storage architecture belongs in Part 5.

## 1.7.28 Metadata and data safety

Read-only metadata can still expose schema names, table names, columns, owners, application structure, and security design. `[SAFE-READ]` does not mean safe to publish. Review and redact production evidence before sharing.

The healthcare-shaped model is synthetic. Repository policy is:

```text
NO REAL PHI
NO REAL PII
NO CUSTOMER DATA
NO PRODUCTION EXPORTS
```

Do not commit captured production output from `\dn`, `\dt`, `\d`, `pg_namespace`, `pg_tables`, `information_schema`, or the validation artifact. Commit reusable logic, not environment inventories.
