# Part 1.6 — Create Your First Database

## Revised Final / Canonical Edition

**Tutorial target:** PostgreSQL 18  
**Prerequisites:** Parts 1.1–1.5  
**Primary lab role:** `tutorial_admin`  
**Existing database:** `tutorial_db`  
**New database:** `healthcare_lab`

Part 1.5 established the PostgreSQL logical hierarchy:

```text
PostgreSQL Database Cluster
        ↓
     Database
        ↓
      Schema
        ↓
       Table
      ↙     ↘
    Rows   Columns
```

Part 1.6 focuses on the database administration layer. The goal is not merely to run `CREATE DATABASE`, but to develop a production-minded workflow:

```text
DISCOVER
   ↓
VERIFY TARGET
   ↓
VERIFY AUTHORITY
   ↓
UNDERSTAND CURRENT STATE
   ↓
CHANGE
   ↓
VALIDATE
   ↓
TROUBLESHOOT FROM EVIDENCE
```

## 1.6.1 Learning objectives

By the end of this section, you should be able to:

- explain what a PostgreSQL database represents;
- distinguish a database from a schema;
- list databases with `psql` and SQL;
- understand why `pg_database` is cluster-wide;
- identify database ownership;
- inspect whether a role has `CREATEDB`;
- understand the distinction between creation authority and owner-assignment authority;
- safely create and validate a database;
- connect to it and demonstrate database isolation;
- explain why roles remain available across databases;
- understand `template0` and `template1`;
- inspect PostgreSQL 18 locale metadata;
- understand why `CREATE DATABASE` cannot run inside a transaction block;
- diagnose common database-creation failures;
- understand `DROP DATABASE` without performing it; and
- use the canonical read-only `database-check.sql` validator.

## 1.6.2 Safety classifications

```text
[SAFE-READ]
Read-only inspection.

[LAB-ONLY]
State-changing operation restricted to the dedicated tutorial environment.

[LAB-ONLY — INTENTIONAL ERROR]
Controlled failure used for learning.

[PRODUCTION-CAUTION]
Requires impact, security, dependency, capacity, backup, monitoring,
and change assessment.

[DESTRUCTIVE]
Can permanently remove objects/data.
```

For this tutorial, `CREATE DATABASE` is `[LAB-ONLY]`. In a real environment, database creation is `[PRODUCTION-CAUTION]`. Database deletion remains conceptual only.

## 1.6.3 Verify before database administration

Connect explicitly:

```bash
psql \
  -h localhost \
  -p 5432 \
  -U tutorial_admin \
  -d tutorial_db
```

Verify the target and identity:

```sql
-- [SAFE-READ]
SELECT
    current_database() AS database_name,
    session_user AS session_user,
    current_user AS effective_role,
    inet_server_addr() AS server_address,
    inet_server_port() AS server_port,
    pg_backend_pid() AS backend_pid;
```

Then run:

```text
\conninfo
```

Use this operational sequence before database-level DDL:

```text
VERIFY SERVER / ENDPOINT
          ↓
VERIFY CURRENT DATABASE
          ↓
VERIFY IDENTITY
          ↓
VERIFY AUTHORITY
          ↓
VERIFY TARGET DATABASE NAME
          ↓
CHANGE
          ↓
VALIDATE
```

A syntactically correct command executed against the wrong environment is still an operational failure.

## 1.6.4 PostgreSQL database hierarchy

Our cluster conceptually contains:

```text
PostgreSQL Database Cluster
│
├── postgres
├── template0
├── template1
├── tutorial_db
└── healthcare_lab        ← created in this lab
```

`healthcare_lab` is another database in the same PostgreSQL cluster. It is not a schema inside `tutorial_db`.

## 1.6.5 List databases with `psql`

```text
\l
```

or:

```text
\list
```

The inventory varies by environment. Never use sample tutorial output as evidence of the actual state of your server.

## 1.6.6 List databases using SQL

```sql
-- [SAFE-READ]
SELECT datname
FROM pg_catalog.pg_database
ORDER BY datname;
```

`\l` is a convenient `psql` view; `pg_catalog.pg_database` provides SQL/catalog inspection.

## 1.6.7 `pg_database` is a shared catalog

Most PostgreSQL catalogs describe objects associated with the current database. `pg_database` is different: it is a shared system catalog containing database-level information for the PostgreSQL cluster.

```text
tutorial_db connection
        │
        ▼
pg_database
        │
        ├── postgres
        ├── template0
        ├── template1
        ├── tutorial_db
        └── healthcare_lab
```

This is why you can inspect the cluster's database inventory while connected to one database.

## 1.6.8 Roles are cluster-wide

```text
Database objects
      ↓
mostly database-local

PostgreSQL roles
      ↓
cluster-wide
```

Creating `healthcare_lab` does not require recreating `tutorial_admin` inside the new database.

## 1.6.9 Verify the current database

```sql
-- [SAFE-READ]
SELECT current_database();

SELECT
    current_database(),
    current_user;
```

Before creating a database, determine who is actually executing the operation.

## 1.6.10 Who can create databases?

Inspect the role with `psql`:

```text
\du tutorial_admin
```

Then inspect the catalog:

```sql
-- [SAFE-READ]
SELECT
    rolname,
    rolsuper,
    rolcreatedb,
    rolcreaterole,
    rolcanlogin
FROM pg_catalog.pg_roles
WHERE rolname = current_user;
```

A role with PostgreSQL's `CREATEDB` attribute can create databases, subject to the relevant ownership and command requirements.

## 1.6.11 `CREATEDB` does not mean arbitrary owner assignment

These are separate questions:

```text
Can I create a database?
          ↓
CREATEDB / sufficient authority

Can I assign the requested OWNER?
          ↓
authority involving that target role
```

Do not assume that `CREATEDB` allows assignment of any PostgreSQL role as owner. For this beginner lab, the executing role `tutorial_admin` is also the intended owner.

## 1.6.12 Never solve privilege failures by immediately using superuser

If PostgreSQL reports `permission denied to create database`, use evidence:

```text
CAPTURE EXACT ERROR
        ↓
VERIFY CURRENT ROLE
        ↓
INSPECT CREATEDB
        ↓
VERIFY INTENDED OWNER
        ↓
VERIFY EXPECTED PRIVILEGE MODEL
        ↓
FOLLOW ENVIRONMENT ACCESS PROCESS
```

Do not casually grant `SUPERUSER` or `CREATEDB` merely to make a tutorial command succeed.

## 1.6.13 Database ownership

```sql
-- [SAFE-READ]
SELECT
    d.datname AS database_name,
    pg_catalog.pg_get_userbyid(d.datdba) AS owner
FROM pg_catalog.pg_database AS d
ORDER BY d.datname;
```

A database owner is a PostgreSQL role, not an operating-system filesystem owner.

## 1.6.14 Owner and connected user are different concepts

```text
Database owner
      ↓
Role owning the database

current_user
      ↓
Effective role executing commands
```

They can be the same, but they do not have to be. A production database owner should not automatically be the application's runtime login; ownership should be deliberately designed.

## 1.6.15 Define desired state before changing anything

Desired state:

```text
Database: healthcare_lab
Owner:    tutorial_admin
```

Check current state:

```sql
-- [SAFE-READ]
SELECT
    d.datname AS database_name,
    pg_catalog.pg_get_userbyid(d.datdba) AS owner
FROM pg_catalog.pg_database AS d
WHERE d.datname = 'healthcare_lab';
```

Use `DESIRED STATE → CURRENT STATE → COMPARE → ACTION`, not blind execution.

## 1.6.16 Create `healthcare_lab`

After verifying the environment, identity, privilege, target name, and owner:

```sql
-- [LAB-ONLY]
CREATE DATABASE healthcare_lab
    OWNER tutorial_admin;
```

Expected command tag:

```text
CREATE DATABASE
```

The explicit owner makes the intended state visible.

## 1.6.17 Validate immediately

```sql
-- [SAFE-READ]
SELECT
    d.datname AS database_name,
    pg_catalog.pg_get_userbyid(d.datdba) AS owner
FROM pg_catalog.pg_database AS d
WHERE d.datname = 'healthcare_lab';
```

Then:

```text
\l healthcare_lab
```

Use `CHANGE → VALIDATE`, never `CHANGE → ASSUME SUCCESS`.

## 1.6.18 Connect to the new database

```text
\c healthcare_lab
```

or:

```text
\connect healthcare_lab
```

Verify independently:

```sql
-- [SAFE-READ]
SELECT
    current_database() AS database_name,
    session_user AS session_user,
    current_user AS effective_role,
    pg_backend_pid() AS backend_pid;
```

Then run `\conninfo`. Do not rely only on the prompt.

## 1.6.19 `\c` is a `psql` command

`\c healthcare_lab` is a `psql` meta-command. It establishes a connection targeting another database; it is not an SQL statement that moves an existing backend session between databases.

## 1.6.20 One connection targets one database

```text
Connection A
    │
    └── tutorial_db

Connection B
    │
    └── healthcare_lab
```

This is a fundamental PostgreSQL database boundary.

## 1.6.21 Prove database isolation

While connected to `healthcare_lab`:

```sql
SELECT current_database();
```

Then:

```text
\dt clinical.*
```

The `clinical` objects from `tutorial_db` should not automatically appear. Return to `tutorial_db` and compare:

```text
\c tutorial_db
\dt clinical.*
```

The databases have independent logical namespaces.

## 1.6.22 Logical isolation does not mean independent infrastructure

Different databases provide separate logical database namespaces, but databases in the same PostgreSQL cluster share server infrastructure and cluster-level facilities such as roles. Later sections will introduce other shared operational mechanisms, including WAL architecture.

```text
new database
    ≠
new PostgreSQL server
```

## 1.6.23 Inspect database properties

```sql
-- [SAFE-READ]
SELECT
    d.datname AS database_name,
    pg_catalog.pg_get_userbyid(d.datdba) AS owner,
    pg_catalog.pg_encoding_to_char(d.encoding) AS encoding,
    d.datlocprovider AS locale_provider,
    d.datlocale AS locale_name,
    d.datcollate AS lc_collate,
    d.datctype AS lc_ctype,
    d.datallowconn AS allow_connections,
    d.datconnlimit AS connection_limit,
    d.datistemplate AS is_template
FROM pg_catalog.pg_database AS d
WHERE d.datname = 'healthcare_lab';
```

This provides a PostgreSQL 18-aware database metadata view.

## 1.6.24 Character encoding

```sql
SHOW server_encoding;

SELECT
    datname,
    pg_catalog.pg_encoding_to_char(encoding) AS encoding
FROM pg_catalog.pg_database
WHERE datname = current_database();
```

Many modern environments use UTF8, but inspect rather than assume.

## 1.6.25 PostgreSQL 18 locale providers

PostgreSQL 18 supports multiple locale-provider mechanisms, including providers such as `builtin`, `libc`, and ICU.

```sql
SELECT
    datname,
    datlocprovider,
    datlocale,
    datcollate,
    datctype
FROM pg_catalog.pg_database
WHERE datname = current_database();
```

Do not infer the complete localization configuration from only `datcollate` and `datctype`; the locale provider matters too.

## 1.6.26 Why locale matters

Localization settings can influence collation, character classification, and other locale-sensitive text behavior. The exact behavior depends partly on the selected provider. At this fundamentals stage, use the lab defaults unless a later controlled exercise requires alternatives.

## 1.6.27 Connection metadata

```sql
SELECT
    datname,
    datallowconn,
    datconnlimit
FROM pg_catalog.pg_database
WHERE datname = 'healthcare_lab';
```

`datallowconn` contributes to whether connections are permitted. `datconnlimit` records the database connection-limit setting. Values such as `-1` have PostgreSQL-defined special semantics.

## 1.6.28 Connection success is layered

```text
Client
  ↓
Network
  ↓
PostgreSQL listener
  ↓
Authentication policy
  ↓
Role LOGIN capability
  ↓
Database CONNECT privilege
  ↓
Credentials / TLS / service requirements
  ↓
Database session
```

No single metadata field explains the complete connection path.

## 1.6.29 Database templates

PostgreSQL creates databases by copying an existing template database. Normally `template1` is the default source.

```text
template1
    │
    │ clone
    ▼
new database
```

## 1.6.30 `template1`

`template1` is normally the default creation template. Objects intentionally added to it can propagate into databases subsequently created from it.

## 1.6.31 `template1` production warning

`[PRODUCTION-CAUTION]`

Do not customize `template1` casually. Changes should be intentional, documented, reviewed, validated, and understood as affecting future database creation. Do not use `template1` as an application database.

## 1.6.32 `template0`

`template0` provides a pristine alternative template and can be useful when database creation requires properties incompatible with the current `template1`, including certain encoding or locale requirements.

## 1.6.33 Strong `template0` boundary

Do not modify `template0`, and do not use it as an application database. Inspect it only:

```sql
-- [SAFE-READ]
SELECT
    datname,
    datistemplate,
    datallowconn
FROM pg_catalog.pg_database
WHERE datname IN ('template0', 'template1')
ORDER BY datname;
```

## 1.6.34 Template cloning is not a complete configuration clone

Template-based creation does not mean every database-level configuration and permission is simply duplicated. `CREATE DATABASE` succeeding does not prove production readiness. Production readiness may additionally require ownership validation, privileges, CONNECT policy, role design, database settings, backup coverage, monitoring, capacity, and application configuration.

## 1.6.35 `CREATE DATABASE` cannot run inside a transaction block

Controlled lab:

```sql
-- [LAB-ONLY — INTENTIONAL ERROR]
BEGIN;

CREATE DATABASE transaction_test_db;
```

PostgreSQL should reject the database creation. Then return the session to a clean transaction state:

```sql
ROLLBACK;
```

## 1.6.36 Automation implication

Later we may use Python, migration frameworks, CI/CD, Terraform, Ansible, and provisioning workflows. Some libraries or frameworks use transactions automatically. Automation must understand PostgreSQL command semantics rather than blindly place every SQL statement inside one transaction.

## 1.6.37 Controlled duplicate-database failure

After `healthcare_lab` exists:

```sql
-- [LAB-ONLY — INTENTIONAL ERROR]
CREATE DATABASE healthcare_lab
    OWNER tutorial_admin;
```

Capture the exact error, then inspect the existing state. Do not delete the database merely to make the command succeed on another run.

## 1.6.38 No `CREATE DATABASE IF NOT EXISTS`

Do not assume PostgreSQL supports:

```sql
CREATE DATABASE IF NOT EXISTS healthcare_lab;
```

Future automation should use:

```text
DISCOVER CURRENT STATE
          ↓
COMPARE WITH DESIRED STATE
          ↓
VALIDATE EXISTING PROPERTIES
          ↓
DETECT DRIFT
          ↓
CREATE / REMEDIATE WHEN APPROPRIATE
          ↓
VALIDATE
```

Existence alone is insufficient; an existing database might have an unexpected owner, encoding, locale, or connection policy.

## 1.6.39 Wrong-owner scenario

If the intended owner is `tutorial_admin` but metadata reports another role, do not immediately change ownership. Determine who provisioned the database, whether the owner was explicitly requested, whether automation is responsible, what the intended security model is, what dependencies exist, and whether remediation is approved.

## 1.6.40 Missing-owner scenario

If a future command requests `OWNER healthcare_app` and that role does not exist, inspect `pg_roles`. Do not automatically create an arbitrary login role. Role provisioning requires an intentional security model.

## 1.6.41 `createdb` utility

PostgreSQL also provides `createdb` as a convenience client utility:

```bash
# [REFERENCE — DO NOT RUN AS PART OF THIS LAB]
createdb \
  -h localhost \
  -p 5432 \
  -U tutorial_admin \
  --owner=tutorial_admin \
  healthcare_lab_cli
```

We do not create `healthcare_lab_cli`. `createdb` is a convenience interface that connects to PostgreSQL and requests database creation; it is not a fundamentally different server-side creation mechanism.

## 1.6.42 A client must connect somewhere first

To request creation of a new database, a client needs an existing database connection through which it can communicate with PostgreSQL. This explains the usefulness of maintenance databases such as `postgres` for administrative connections.

## 1.6.43 Two-database hands-on lab

Terminal A:

```bash
psql -h localhost -p 5432 -U tutorial_admin -d tutorial_db
```

Terminal B:

```bash
psql -h localhost -p 5432 -U tutorial_admin -d healthcare_lab
```

In each:

```sql
SELECT
    current_database(),
    current_user,
    pg_backend_pid();
```

This demonstrates `client → backend PID → database`.

## 1.6.44 Observe both database sessions

From a suitably privileged lab session:

```sql
-- [SAFE-READ]
SELECT
    pid,
    datname,
    usename,
    application_name,
    state
FROM pg_catalog.pg_stat_activity
WHERE datname IN ('tutorial_db', 'healthcare_lab')
ORDER BY datname, pid;
```

Visibility into other sessions depends on privileges. Do not grant broad privileges merely to complete this observation. Read-only metadata can still be sensitive.

## 1.6.45 Database-creation troubleshooting methodology

```text
CREATE DATABASE FAILED
          ↓
CAPTURE EXACT ERROR
          ↓
VERIFY SERVER / ENDPOINT
          ↓
VERIFY CURRENT DATABASE
          ↓
VERIFY CURRENT ROLE
          ↓
VERIFY CREATEDB AUTHORITY
          ↓
VERIFY REQUESTED OWNER AUTHORITY
          ↓
CHECK WHETHER DATABASE EXISTS
          ↓
CHECK WHETHER OWNER EXISTS
          ↓
CHECK TRANSACTION CONTEXT
          ↓
CHECK TEMPLATE / ENCODING / LOCALE REQUEST
          ↓
DETERMINE ROOT CAUSE
          ↓
APPLY CONTROLLED REMEDIATION
          ↓
RETRY WHEN JUSTIFIED
          ↓
VALIDATE
```

## 1.6.46 Scenario — database already exists

Check `pg_database`. If the database exists, do not drop it automatically. Determine whether it is expected, who owns it, whether its configuration matches, whether it contains objects, whether automation provisioned it, and whether it is the intended environment.

## 1.6.47 Scenario — permission denied

```sql
SELECT
    rolname,
    rolsuper,
    rolcreatedb
FROM pg_catalog.pg_roles
WHERE rolname = current_user;
```

Determine whether database creation is expected for the role. Do not broaden privileges before understanding the intended security model.

## 1.6.48 Scenario — transaction failure

If PostgreSQL reports that `CREATE DATABASE` cannot execute inside a transaction block, determine whether you executed `BEGIN`, a library opened a transaction automatically, or a migration/provisioning framework wrapped the command. Fix the execution model rather than repeatedly retrying.

## 1.6.49 `DROP DATABASE`

PostgreSQL supports database deletion, but Part 1.6 does not execute it:

```sql
-- [DESTRUCTIVE — EXAMPLE ONLY — DO NOT EXECUTE]
DROP DATABASE healthcare_lab;
```

`DROP DATABASE` removes the database and its contained objects/data. The operation itself does not provide an undo mechanism. Backup/restore is a separate recovery process and does not make database deletion harmless.

## 1.6.50 Current and active connections matter during deletion

A database cannot ordinarily be dropped by a session connected to that same database. Other active connections can also affect database removal. Additional removal behavior exists, but forced removal is deliberately deferred until later operational runbooks cover dependency analysis, active-session analysis, connection termination, backup verification, approval, recovery planning, and validation.

## 1.6.51 Keep `healthcare_lab`

Do not clean up the lab with `DROP DATABASE healthcare_lab;`. Keep it for later exercises. Persistent resources should be removed only for a reason.

## 1.6.52 Never manipulate database storage manually

Do not create, copy, move, or delete PostgreSQL database storage using filesystem commands such as `mkdir`, `cp`, `mv`, or `rm` inside the data directory as a substitute for logical database administration. Manage logical PostgreSQL objects through supported PostgreSQL interfaces.

## 1.6.53 Database metadata can be sensitive

Queries against `pg_database`, `pg_roles`, and `pg_stat_activity` may reveal database names, role names, owners, locale configuration, connection policy, session information, and architecture details.

```text
READ-ONLY
   ≠
SAFE TO PUBLISH
```

Review and redact production output before sharing it outside approved channels.

## 1.6.54 Do not commit environment inventories

The repository should contain reusable tutorial manuscripts, SQL validators, and synthetic examples. Do not commit output captured from real environments, including `\l`, `pg_database`, `pg_roles`, `pg_stat_activity`, or `database-check.sql` output, especially when it contains production identifiers.
