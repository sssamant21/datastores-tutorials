# Part 1.8 — INSERT, SELECT, UPDATE & DELETE

**Status:** Revised Final / Canonical Reconstruction  
**Target:** PostgreSQL 18  
**Lab model:** Synthetic data only  
**Safety model:** Explicit columns, targeted predicates, pre-change verification, `RETURNING`, and transaction-controlled destructive practice.

## 1.8.1 Objective

Part 1.7 created our first schema and table. We now work with rows using the four fundamental CRUD operations:

- Create → `INSERT`
- Read → `SELECT`
- Update → `UPDATE`
- Delete → `DELETE`

By the end of this tutorial you will be able to insert rows, query selected columns, filter and order results, update and delete specific rows, use `RETURNING`, practice changes inside transactions, and recognize dangerous unqualified `UPDATE` and `DELETE` statements.

## 1.8.3 INSERT — Creating Rows

Prefer an explicit target-column list:

```sql
INSERT INTO clinical.patient (
    first_name,
    last_name,
    date_of_birth
)
VALUES (
    'Avery',
    'Taylor',
    DATE '1990-04-15'
);
```

Explicit column lists make intent easier to review and avoid depending on physical column order.

### Insert multiple rows

```sql
INSERT INTO clinical.patient (
    first_name,
    last_name,
    date_of_birth
)
VALUES
    ('Jordan', 'Lee',    DATE '1985-08-20'),
    ('Morgan', 'Rivera', DATE '1994-11-03'),
    ('Casey',  'Patel',  DATE '2001-02-14');
```

All names and dates here are synthetic.

### INSERT ... RETURNING

PostgreSQL can return values from inserted rows:

```sql
INSERT INTO clinical.patient (
    first_name,
    last_name,
    date_of_birth
)
VALUES ('Riley', 'Morgan', DATE '1992-07-09')
RETURNING patient_id, first_name, last_name;
```

This is useful when PostgreSQL generates the identifier. Do not assume identity values.

## 1.8.4 SELECT — Reading Data

Prefer retrieving only the columns required:

```sql
SELECT
    patient_id,
    first_name,
    last_name,
    date_of_birth
FROM clinical.patient;
```

### Filtering with WHERE

```sql
SELECT patient_id, first_name, last_name
FROM clinical.patient
WHERE last_name = 'Taylor';
```

For an identified row:

```sql
SELECT patient_id, first_name, last_name
FROM clinical.patient
WHERE patient_id = 1;
```

The actual generated ID may differ. Inspect your data instead of assuming an ID.

### ORDER BY and LIMIT

```sql
SELECT patient_id, first_name, last_name
FROM clinical.patient
ORDER BY patient_id
LIMIT 10;
```

Use `ORDER BY` when result ordering matters. `LIMIT` controls returned rows; it is not a substitute for a precise predicate when modifying data.

## 1.8.5 UPDATE — Modifying Rows

Before an update, inspect the intended target:

```sql
SELECT patient_id, first_name, last_name
FROM clinical.patient
WHERE patient_id = 1;
```

Then use the same reviewed predicate:

```sql
UPDATE clinical.patient
SET last_name = 'Taylor-Smith'
WHERE patient_id = 1
RETURNING patient_id, first_name, last_name;
```

Operational pattern:

```text
SELECT target
→ verify expected row(s)
→ UPDATE with the reviewed predicate
→ inspect affected rows
→ verify result
```

PostgreSQL 18 also supports explicit old/new row references in DML `RETURNING`:

```sql
UPDATE clinical.patient
SET last_name = 'Taylor-Smith'
WHERE patient_id = 1
RETURNING
    patient_id,
    old.last_name AS old_last_name,
    new.last_name AS new_last_name;
```

### Critical UPDATE safety rule

This statement has no predicate:

```sql
UPDATE clinical.patient
SET last_name = 'Unknown';
```

It targets every eligible row. For interactive production administration, treat an unqualified `UPDATE` as high risk unless modifying all rows is explicitly intended, reviewed, and controlled.

## 1.8.6 DELETE — Removing Rows

Inspect the target first:

```sql
SELECT patient_id, first_name, last_name
FROM clinical.patient
WHERE patient_id = 5;
```

Then delete using the reviewed predicate:

```sql
DELETE FROM clinical.patient
WHERE patient_id = 5
RETURNING patient_id, first_name, last_name;
```

Use the actual lab identifier rather than assuming `5`.

### Critical DELETE safety rule

```sql
DELETE FROM clinical.patient;
```

With no `WHERE` clause, every row is targeted. PostgreSQL does not ask for an interactive confirmation before executing a valid unqualified `DELETE`.

Do not practice this against production data.

## 1.8.7 Transaction-Controlled Practice

Transactions provide a safe learning boundary for targeted DML.

```sql
BEGIN;

SELECT patient_id, first_name, last_name
FROM clinical.patient
WHERE patient_id = 1;

UPDATE clinical.patient
SET last_name = 'LAB-ROLLBACK-TEST'
WHERE patient_id = 1
RETURNING patient_id, first_name, last_name;

SELECT patient_id, first_name, last_name
FROM clinical.patient
WHERE patient_id = 1;

ROLLBACK;
```

Verify after rollback:

```sql
SELECT patient_id, first_name, last_name
FROM clinical.patient
WHERE patient_id = 1;
```

`COMMIT` preserves successful transaction changes; `ROLLBACK` cancels the transaction's changes. For destructive tutorial experiments, rollback is the default until you deliberately want to retain a change.

A transaction is an important safety mechanism, but it does not replace correct environment selection, predicate review, permissions, backups, concurrency awareness, or operational controls.

## Step 4 — Practice UPDATE safely

Find Avery's actual ID:

```sql
SELECT patient_id, first_name, last_name
FROM clinical.patient
WHERE first_name = 'Avery'
  AND last_name = 'Taylor';
```

Replace `<avery_patient_id>` below with that returned integer:

```sql
BEGIN;

UPDATE clinical.patient
SET last_name = 'Taylor-Lab'
WHERE patient_id = <avery_patient_id>
RETURNING patient_id, first_name, last_name;

SELECT patient_id, first_name, last_name
FROM clinical.patient
WHERE patient_id = <avery_patient_id>;

ROLLBACK;
```

Verify restoration:

```sql
SELECT patient_id, first_name, last_name
FROM clinical.patient
WHERE patient_id = <avery_patient_id>;
```

## Step 5 — Practice DELETE safely

Choose one synthetic tutorial row and record its actual ID. Then:

```sql
BEGIN;

SELECT patient_id, first_name, last_name
FROM clinical.patient
WHERE patient_id = <lab_patient_id>;

DELETE FROM clinical.patient
WHERE patient_id = <lab_patient_id>
RETURNING patient_id, first_name, last_name;

SELECT patient_id, first_name, last_name
FROM clinical.patient
WHERE patient_id = <lab_patient_id>;

ROLLBACK;
```

Verify the row is restored after rollback.

## 1.8.9 Production DML Checklist

Before an interactive production `UPDATE` or `DELETE`:

1. Confirm the database and environment.
2. Confirm the schema-qualified target table.
3. Inspect target rows with `SELECT`.
4. Review the exact `WHERE` predicate.
5. Determine the expected affected-row scope.
6. Consider transaction boundaries, locks, and application concurrency.
7. Use `RETURNING` when appropriate to inspect affected rows.
8. Verify the result before committing.
9. `COMMIT` only when the result is correct.
10. `ROLLBACK` when validation fails or the affected scope is unexpected.

## 1.8.10 Common Mistakes

### Missing WHERE on UPDATE

```sql
UPDATE clinical.patient
SET last_name = 'Smith';
```

Potential result: every eligible row is updated.

### Missing WHERE on DELETE

```sql
DELETE FROM clinical.patient;
```

Potential result: every row is deleted.

### Assuming generated IDs

Do not assume the first inserted row receives `patient_id = 1`. Identity/sequence-generated values can have gaps. Use `RETURNING` or query the intended row.

### Testing with sensitive data

Tutorial environments should contain synthetic data only. Do not copy PHI, credentials, secrets, production dumps, access tokens, or customer data into this lab.

## 1.8.11 Key Takeaways

The core row operations are `INSERT`, `SELECT`, `UPDATE`, and `DELETE`.

For modification work, develop this habit:

```text
identify → inspect → modify → observe → verify → commit or rollback
```

Use explicit column lists, schema-qualified administrative targets, precise predicates, and `RETURNING` when immediate evidence is useful. Never treat an unqualified `UPDATE` or `DELETE` casually.
