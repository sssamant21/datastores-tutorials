## 1.11.1 Why Users and Roles Matter

A PostgreSQL environment should not treat every application, developer, administrator, reporting process, and automation service as the same identity. Different identities require different capabilities. Grant an identity only the privileges required to perform its intended work: the principle of least privilege.

## 1.11.2 PostgreSQL Uses Roles

PostgreSQL uses a unified role model. A role can represent a person, application, service, administrator, automation identity, or permission group. A role can optionally be permitted to log in. Roles are PostgreSQL-cluster-level objects rather than objects belonging to only one database, which makes role administration security-sensitive.

## 1.11.3 LOGIN and NOLOGIN

A `NOLOGIN` role is useful as a permission-bearing role:

```sql
CREATE ROLE tutorial_reader NOLOGIN;
```

A `LOGIN` role can act as a login identity when authentication is configured appropriately:

```sql
CREATE ROLE tutorial_app LOGIN;
```

`LOGIN` does not itself determine what database objects the role may access. Authentication and authorization are separate concerns.

## 1.11.4 CREATE USER vs CREATE ROLE

PostgreSQL supports both `CREATE ROLE` and `CREATE USER`. `CREATE USER` is an alternative form of `CREATE ROLE` where `LOGIN` is assumed. This series primarily uses `CREATE ROLE` because it makes role attributes explicit.

## 1.11.5 Inspect the Current Identity

```sql
SELECT current_user, session_user;
```

`session_user` identifies the identity that established the session. `current_user` identifies the authorization identity currently used for permission checking.

## 1.11.6 Inspect Existing Roles

From `psql`, use `\du` or `\dg`. Catalog inspection:

```sql
SELECT
    rolname,
    rolcanlogin,
    rolsuper,
    rolcreatedb,
    rolcreaterole,
    rolinherit
FROM pg_roles
ORDER BY rolname;
```

## 1.11.7 Important Role Attributes

Important attributes include `LOGIN/NOLOGIN`, `SUPERUSER/NOSUPERUSER`, `CREATEDB/NOCREATEDB`, `CREATEROLE/NOCREATEROLE`, `INHERIT/NOINHERIT`, `REPLICATION/NOREPLICATION`, and `BYPASSRLS/NOBYPASSRLS`. Assign them deliberately.

## 1.11.8 SUPERUSER Is Not a Permission Fix

An application should not receive `SUPERUSER` merely because it encountered `permission denied`. Determine the missing capability and grant only what the workload requires.

## 1.11.9 Tutorial Authorization Model

The lab uses three synthetic roles:

- `tutorial_reader` — NOLOGIN read permission role
- `tutorial_writer` — NOLOGIN write permission role
- `tutorial_app` — LOGIN application-style identity

The login identity receives capabilities through membership in permission roles.

## 1.11.10 Create the Permission Roles

```sql
CREATE ROLE tutorial_reader
    NOLOGIN
    NOSUPERUSER
    NOCREATEDB
    NOCREATEROLE;

CREATE ROLE tutorial_writer
    NOLOGIN
    NOSUPERUSER
    NOCREATEDB
    NOCREATEROLE;
```

## 1.11.11 Create the Login Role

```sql
CREATE ROLE tutorial_app
    LOGIN
    NOSUPERUSER
    NOCREATEDB
    NOCREATEROLE;
```

The lab does not use production usernames, real service accounts, administrative attributes, or production credentials.

## 1.11.12 Password Safety

This tutorial intentionally does not embed passwords in SQL. Credentials committed to Git repositories, SQL files, shell history, CI logs, tickets, chat messages, or screenshots can become credential-exposure incidents. Authentication and secure credential provisioning are covered separately.

## 1.11.13 Grant Role Membership

```sql
GRANT tutorial_reader TO tutorial_app;
GRANT tutorial_writer TO tutorial_app;
```

## 1.11.14 PostgreSQL 18 Membership Options

A PostgreSQL role membership can carry membership-specific options including `ADMIN`, `INHERIT`, and `SET`. `ADMIN` concerns membership administration, `INHERIT` concerns automatic availability of privileges through membership, and `SET` concerns whether the member can use the granted role through `SET ROLE`. These membership options are distinct from object privileges such as `SELECT`, `INSERT`, `UPDATE`, and `DELETE`.

The tutorial application does not need permission delegation, so the lab does not intentionally grant `ADMIN OPTION`.

## 1.11.15 Inspect Membership Correctly

```sql
SELECT
    member_role.rolname  AS member_role,
    granted_role.rolname AS granted_role,
    m.admin_option,
    m.inherit_option,
    m.set_option
FROM pg_auth_members AS m
JOIN pg_roles AS granted_role ON granted_role.oid = m.roleid
JOIN pg_roles AS member_role ON member_role.oid = m.member
WHERE member_role.rolname = 'tutorial_app'
ORDER BY granted_role.rolname;
```

## 1.11.16 rolinherit Is Not the Entire Membership Story

In PostgreSQL 18, do not inspect only `pg_roles.rolinherit` and assume every membership relationship is understood. Membership-specific information is also represented by `pg_auth_members`, including `inherit_option`, `set_option`, and `admin_option`.

## 1.11.17 Role Attributes Are Not Ordinary Inherited Privileges

Object privileges such as `SELECT`, `INSERT`, and `UPDATE` can become available through appropriate role membership. Administrative role attributes do not simply behave like ordinary inherited object privileges. Do not assume that membership automatically makes every attribute of the granted role an attribute of the member.

## 1.11.18 Membership Does Not Create Object Privileges

Membership alone does not make a permission role capable of reading every table. Grant object privileges to the permission role:

```sql
GRANT USAGE ON SCHEMA clinical TO tutorial_reader;
GRANT SELECT ON TABLE clinical.constraint_patient TO tutorial_reader;
```

## 1.11.19 Grant Limited Writer Privileges

```sql
GRANT USAGE ON SCHEMA clinical TO tutorial_writer;

GRANT SELECT, INSERT, UPDATE
ON TABLE clinical.constraint_patient
TO tutorial_writer;
```

The lab deliberately does not grant `DELETE`, `TRUNCATE`, or `TRIGGER` unless required.

## 1.11.20 Schema and Table Privileges Are Different

Schema access and table privileges are separate authorization layers. For `clinical.constraint_patient`, a reader typically needs `USAGE` on schema `clinical` plus `SELECT` on the table.

## 1.11.21 Sequence Privileges Are Also Separate

The Part 1.10 table uses an identity column. PostgreSQL has a separate privilege model for sequences. When diagnosing generated-identifier or sequence-operation permission problems, inspect relevant sequence permissions rather than assuming table privileges represent every required capability.

## 1.11.22 Inspect Explicit Table Grants

```sql
SELECT
    grantee,
    privilege_type
FROM information_schema.role_table_grants
WHERE table_schema = 'clinical'
  AND table_name = 'constraint_patient'
  AND grantee IN ('tutorial_reader', 'tutorial_writer')
ORDER BY grantee, privilege_type;
```

## 1.11.23 Check Effective Privileges Safely

```sql
SELECT has_schema_privilege('tutorial_reader', 'clinical', 'USAGE');
SELECT has_table_privilege('tutorial_reader', 'clinical.constraint_patient', 'SELECT');
SELECT has_table_privilege('tutorial_reader', 'clinical.constraint_patient', 'DELETE');
```

Expected logical results are `true`, `true`, and `false` respectively.

## 1.11.24 Database Privileges

```sql
SELECT has_database_privilege(
    'tutorial_app',
    current_database(),
    'CONNECT'
);
```

Database, schema, table, and sequence privileges are separate authorization layers.

## 1.11.25 Ownership Is Different from Privileges

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS object_name,
    pg_get_userbyid(c.relowner) AS owner
FROM pg_class AS c
JOIN pg_namespace AS n ON n.oid = c.relnamespace
WHERE n.nspname = 'clinical'
  AND c.relname = 'constraint_patient';
```

Ownership is distinct from ordinary object privileges, role membership, and LOGIN. This foundation lab inspects ownership but does not transfer it.

## 1.11.26 PUBLIC

`PUBLIC` is a special pseudo-role representing all roles, including roles created later. A grant to `PUBLIC` therefore has much broader scope than a grant to a named permission role. Effective access can arise through direct grants, role membership, and applicable `PUBLIC` privileges. This tutorial does not broadly revoke `PUBLIC` privileges because changing them in an existing environment can break dependent workloads.

## 1.11.27 SET ROLE

A session can sometimes change authorization context with `SET ROLE role_name` and return with `RESET ROLE`. Whether the transition is permitted depends on the relevant role relationship, including membership semantics such as the `SET` option. Part 1.11 introduces the concept but does not require `SET ROLE` in final acceptance.

## 1.11.28 Default Privileges

A grant on an existing table does not automatically become a grant on every future table. `ALTER DEFAULT PRIVILEGES` configures privileges for subsequently created objects. Default privileges are associated with the role creating future objects and are not a universal retroactive database permission template. Hands-on default-privilege administration is deferred to a later tutorial.

## 1.11.29 Practical Least-Privilege Pattern

A scalable pattern is LOGIN ROLE → role membership → PERMISSION ROLE → object grants → DATABASE OBJECTS. This is generally easier to manage than repeatedly granting many object privileges directly to every application login.

## 1.11.30 Production Anti-Patterns

Avoid granting `SUPERUSER` to solve application permission errors, using `GRANT ALL` everywhere, sharing one database login among unrelated applications, committing database passwords to source control, or granting broad application privileges to `PUBLIC`. Investigate permission failures at the correct authorization layer.

## 1.11.31 Optional Controlled Cleanup

Do not perform cleanup until acceptance testing is complete.

```sql
REVOKE tutorial_reader FROM tutorial_app;
REVOKE tutorial_writer FROM tutorial_app;

REVOKE ALL ON TABLE clinical.constraint_patient FROM tutorial_reader;
REVOKE ALL ON TABLE clinical.constraint_patient FROM tutorial_writer;

REVOKE USAGE ON SCHEMA clinical FROM tutorial_reader;
REVOKE USAGE ON SCHEMA clinical FROM tutorial_writer;

DROP ROLE tutorial_app;
DROP ROLE tutorial_reader;
DROP ROLE tutorial_writer;
```

## 1.11.32 Why DROP ROLE Can Fail

A role may own objects, hold privileges, participate in dependencies, or have relationships across databases in the cluster. `DROP ROLE` may therefore correctly fail. `REASSIGN OWNED` and `DROP OWNED` are advanced role-retirement tools, not beginner cleanup shortcuts. Role retirement can require work in multiple databases, and destructive cascading dependency removal requires careful review. Part 1.11 does not execute those commands.

4. Grant role memberships.

## 1.11.34 Production Safety Boundary

Do not replace the synthetic tutorial roles with production usernames, existing administrators, customer identities, application service accounts, or deployment identities without a separate production change review. PostgreSQL roles are cluster-level identities, so `CREATE ROLE`, `ALTER ROLE`, role `GRANT`/`REVOKE`, and `DROP ROLE` can affect authorization beyond one tutorial database.

## 1.11.35 What You Should Know Now

You should be able to explain ROLE, LOGIN, NOLOGIN, role membership, ADMIN, INHERIT, SET, object privilege, ownership, PUBLIC, `current_user`, and `session_user`. You should also understand that role attributes differ from object privileges; membership differs from ownership; schema, table, and sequence privileges are separate; and existing grants differ from default privileges for future objects.
