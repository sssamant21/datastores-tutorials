# Part 1.14 — `postgresql.conf` and `pg_hba.conf`

**Status:** Revised Final / Canonical Edition  
**Target:** PostgreSQL 18  
**Audience:** PostgreSQL learners, DBAs, SREs, DBREs, platform engineers  
**Lab:** `labs/config-files-check.sql`

## 1.14.1 Why These Files Matter

Two PostgreSQL configuration files are especially important in day-to-day administration:

- `postgresql.conf` controls how the PostgreSQL server operates.
- `pg_hba.conf` controls which client connections match which authentication rules.

A useful mental model is:

```text
postgresql.conf
      |
      +---- How should PostgreSQL operate?
      |
      +---- Connections
      +---- Memory
      +---- WAL
      +---- Checkpoints
      +---- Logging
      +---- Autovacuum
      +---- Replication
      +---- Query behavior
      +---- Background processes
      +---- Network listeners

pg_hba.conf
      |
      +---- How should incoming clients authenticate?
             |
             +---- Connection type
             +---- Database
             +---- PostgreSQL role
             +---- Client network
             +---- Authentication method
```

`postgresql.conf` does not grant privileges on database objects. `pg_hba.conf` does not grant permission to read or modify tables. Authentication and authorization are separate layers.

## 1.14.2 Find the Active Configuration

Configuration files can reside in different locations depending on packaging, containers, Kubernetes, automation, and managed services. Never guess the active path. Ask PostgreSQL:

```sql
SHOW data_directory;
SHOW config_file;
SHOW hba_file;
SHOW ident_file;
```

## 1.14.3 `postgresql.conf`

`postgresql.conf` contains server configuration parameters covering connections, memory, WAL, checkpoints, replication, logging, autovacuum, query planning, SSL, background workers, client defaults, locks, and resource consumption.

Examples:

```conf
listen_addresses = 'localhost'
port = 5432
max_connections = 100
shared_buffers = '2GB'
work_mem = '16MB'
logging_collector = on
log_min_duration_statement = 1000
```

Inspect effective values with `SHOW` or `pg_settings`:

```sql
SELECT name, setting, unit, context, source
FROM pg_settings
WHERE name IN ('max_connections','shared_buffers','work_mem','listen_addresses')
ORDER BY name;
```

## 1.14.4 Configuration Sources and Precedence

A simplified operational model is:

```text
Built-in defaults
       ↓
postgresql.conf
       ↓
included configuration files
       ↓
postgresql.auto.conf
       ↓
server command-line configuration
```

Database-, role-, client-, and session-level settings can also affect parameters where their context permits them. Determine the effective source instead of relying on assumptions:

```sql
SELECT name, setting, source, sourcefile, sourceline
FROM pg_settings
WHERE name = 'work_mem';
```

## 1.14.5 Duplicate Configuration Entries

If the same applicable parameter appears more than once in configuration processing, a later applicable entry can override an earlier one. Finding a parameter in a file does not prove that line supplied the effective value. Use `pg_settings` to identify the active source.

## 1.14.6 `postgresql.auto.conf` and `ALTER SYSTEM`

`postgresql.auto.conf` stores cluster-wide settings written by `ALTER SYSTEM` and can override corresponding settings from `postgresql.conf`.

```sql
ALTER SYSTEM SET work_mem = '16MB';
```

This is an explanatory example only. Do not execute `ALTER SYSTEM` merely to complete this tutorial. It changes cluster-wide configuration state. Do not routinely edit `postgresql.auto.conf` manually; use the intended PostgreSQL or platform configuration mechanism.

## 1.14.7 Reload Versus Restart

Configuration parameters have different contexts. Inspect them before deciding whether a reload or restart is required:

```sql
SELECT name, setting, context, pending_restart
FROM pg_settings
WHERE name IN ('work_mem','shared_buffers','max_connections','log_min_duration_statement');
```

Two important contexts are:

```text
sighup     → configuration reload can apply the setting
postmaster → server restart is required
```

Never assume every configuration change requires a restart, and never assume reload is sufficient.

## 1.14.8 Detect Pending Restarts

```sql
SELECT name, setting, context, pending_restart
FROM pg_settings
WHERE pending_restart
ORDER BY name;
```

A `pending_restart` value of true indicates that a configuration change requires restart before becoming effective.

## 1.14.9 Reloading Configuration

For reloadable settings, PostgreSQL can reread configuration without a full restart:

```sql
SELECT pg_reload_conf();
```

On appropriate self-managed installations:

```bash
pg_ctl reload
```

A service manager may also provide a reload operation. A reload is not a restart; production restarts require additional operational planning.

## 1.14.10 Effective State vs File State

Use `pg_settings` for effective running settings. Use `pg_file_settings` to inspect current configuration-file contents and parsing/application issues.

```sql
SELECT sourcefile, sourceline, name, setting, applied, error
FROM pg_file_settings
WHERE error IS NOT NULL
ORDER BY sourcefile, sourceline;
```

Current file contents are not necessarily identical to configuration last successfully loaded by the running server.

## 1.14.11 `pg_hba.conf`

`pg_hba.conf` defines host-based authentication rules. A TCP/IP rule commonly follows:

```text
TYPE   DATABASE   USER   ADDRESS   METHOD
```

Example:

```conf
host    appdb    app_user    10.20.30.0/24    scram-sha-256
```

This identifies the connection type, requested database, PostgreSQL role, client network, and authentication method. It does not grant table or schema privileges.

## 1.14.12 Authentication Is Not Authorization

A successful HBA match and authentication establishes a PostgreSQL role. Authorization is separately controlled by ownership, role membership, and privileges such as `CONNECT`, `USAGE`, `SELECT`, `INSERT`, `UPDATE`, and `DELETE`.

## 1.14.13 Common HBA Connection Types

Important types include `local`, `host`, `hostssl`, `hostnossl`, `hostgssenc`, and `hostnogssenc`.

At an introductory level:

```text
local      Unix-domain socket
host       TCP/IP
hostssl    TCP/IP using SSL
hostnossl  TCP/IP without SSL
```

`hostssl` restricts a rule to SSL connections; it does not by itself configure certificates, enable a complete SSL deployment, establish certificate trust, or define the full TLS security policy.

## 1.14.14 Authentication Methods

PostgreSQL supports methods including `scram-sha-256`, `peer`, `cert`, `gss`, `sspi`, `ldap`, `radius`, `pam`, `oauth`, `trust`, and `reject`.

For password-based authentication in modern PostgreSQL deployments, prefer `scram-sha-256`. PostgreSQL 18 deprecates MD5-encrypted passwords. New deployments should use SCRAM-SHA-256 and existing MD5 deployments should plan migration rather than expanding MD5 usage.

```sql
SHOW password_encryption;
```

## 1.14.15 Why `trust` Requires Extreme Caution

A broad rule such as:

```conf
host    all    all    0.0.0.0/0    trust
```

can create severe security exposure because matching clients do not need normal authentication credentials. Do not use broad `trust` rules as a troubleshooting shortcut. Prefer the narrowest practical database, role, client-network, and authentication scope.

## 1.14.16 HBA Rule Ordering

PostgreSQL evaluates HBA rules in order and uses the first matching rule. A broad rule placed before a specific exception can make the exception unreachable.

```conf
host    appdb    app_user    10.20.30.0/24     reject
host    appdb    app_user    10.20.0.0/16      scram-sha-256
```

Evaluate the complete ordered HBA rule set, not only the rule being added.

## 1.14.17 Inspect HBA Configuration

Use `pg_hba_file_rules` to inspect current HBA file contents:

```sql
SELECT rule_number, file_name, line_number, type,
       database, user_name, address, auth_method, error
FROM pg_hba_file_rules
ORDER BY rule_number NULLS LAST, line_number;
```

Check parsing errors with:

```sql
SELECT file_name, line_number, error
FROM pg_hba_file_rules
WHERE error IS NOT NULL;
```

The view describes current file contents, which are not necessarily the HBA configuration last successfully loaded by the server.

## 1.14.18 Privilege Requirements

Some configuration inspection views expose sensitive operational information and may require elevated privileges. A permission error does not mean the PostgreSQL configuration is invalid. Do not grant superuser merely so a learner can complete this tutorial.

## 1.14.19 Reloading HBA Configuration

On typical Unix-like installations, HBA changes need to be reread before affecting new connections. A reload can be requested with `pg_reload_conf()` or an appropriate platform control mechanism. Microsoft Windows handles subsequent new connections differently.

Authentication changes must be tested with a new connection. An existing connection proves only that its previous authentication attempt succeeded.

## 1.14.20 Preventing Administrative Lockout

For production HBA changes:

```text
Keep existing administrative session
        ↓
Identify active hba_file
        ↓
Review complete ordered rule set
        ↓
Capture existing configuration
        ↓
Make smallest approved change
        ↓
Inspect pg_hba_file_rules
        ↓
Verify no parsing errors
        ↓
Reload where required
        ↓
Open NEW administrative connection
        ↓
Open NEW application/service connection
        ↓
Verify monitoring and dependencies
        ↓
Only then close fallback session
```

## 1.14.21 Rollback Strategy

Capture or version the existing configuration before changing it. If validation or new-connection tests fail, restore the previous configuration, reload as appropriate, and verify new administrative and application connections. Restart-required parameter rollback may itself require another restart and must be included in maintenance planning.

## 1.14.22 Managed PostgreSQL Services

Managed platforms such as Amazon RDS/Aurora PostgreSQL, Azure Database for PostgreSQL, and Google Cloud SQL for PostgreSQL may restrict direct operating-system or configuration-file access. Use provider-supported parameter, networking, identity, API, and service-management mechanisms rather than assuming a visible file should be edited directly.

## 1.14.23 Containers and Kubernetes

In containerized environments, configuration may be controlled by a ConfigMap, Secret, Helm values, PostgreSQL Operator, environment variables, persistent volumes, or another configuration-management system. Editing a running container directly can create drift or disappear after replacement. Identify and modify the authoritative source of truth.

## 1.14.24 Production Change Workflow

```text
Discover
   ↓
Identify active configuration
   ↓
Inspect effective value and source
   ↓
Determine reload/restart requirement
   ↓
Assess application + HA impact
   ↓
Capture rollback state
   ↓
Make smallest approved change
   ↓
Validate configuration
   ↓
Reload/restart only when required
   ↓
Verify effective state
   ↓
Test NEW connections when authentication changed
   ↓
Monitor
   ↓
Close change
```

The lab is read-only, but output may expose filesystem paths, database and role names, internal network ranges, authentication methods, and configuration topology.

```text
SAFE-READ ≠ SAFE-TO-PUBLISH
```

Sanitize captured output before posting it in public tickets, repositories, documentation, screenshots, or external support channels.

## 1.14.27 Key Operational Rules

1. Never guess configuration paths; use `SHOW config_file` and `SHOW hba_file`.
2. Use `pg_settings` to inspect effective settings.
3. Use `pg_file_settings` to inspect file configuration separately.
4. Use `pg_hba_file_rules` to inspect HBA structure.
5. Determine reload versus restart before acting.
6. Remember that HBA is first-match based.
7. Keep authentication separate from authorization.
8. Prefer SCRAM for password authentication and plan migration away from deprecated MD5 password storage.
9. Never grant superuser simply to complete a lab.
10. Test authentication changes with a new connection.
11. Identify the configuration source of truth, especially in managed and containerized environments.
12. Always plan rollback.

## 1.14.28 Final Mental Model

```text
                 PostgreSQL Configuration
                          |
             +------------+------------+
             |                         |
      Server behavior              Authentication
             |                         |
     postgresql.conf              pg_hba.conf
             |                         |
       pg_settings             pg_hba_file_rules
             |
     pg_file_settings
             |
             +-------------------------+
                          |
                    Validate state
                          |
                Reload / restart?
                          |
                       Verify
                          |
                       Monitor
```

The central operational questions are:

1. What configuration is PostgreSQL using?
2. Where did that configuration come from?
3. What operational action is required to change it?
4. How will the change be proven without creating an outage or authentication lockout?

These questions form the foundation for production PostgreSQL configuration management.
