# Part 1.5 — Database, Schema, Table, Row & Column

**Tutorial target:** PostgreSQL 18  
**Prerequisites:** Parts 1.1–1.4  
**Lab database:** `tutorial_db`  
**Lab role:** `tutorial_admin`

Parts 1.1–1.4 established PostgreSQL fundamentals, architecture, installation, and safe `psql` connectivity. This section establishes the logical hierarchy used throughout the tutorial:

```text
PostgreSQL Database Cluster
        │
        ├── Database
        │      ├── Schema
        │      │     ├── Table
        │      │     │     ├── Rows
        │      │     │     └── Columns
        │      │     └── Other objects
        │      └── Other schemas
        └── Other databases
```

The operational principle is equally important: when an object appears missing, do not immediately create it. Verify the database, schema, object name, search path, visibility, and deployment state first.

## 1.5.1 Safety classifications

```text
[SAFE-READ]
Observational/read-only operation.

[LAB-ONLY]
Changes state or intentionally generates an error inside the dedicated tutorial environment.

[PRODUCTION-CAUTION]
Requires production impact, dependency, security, and change assessment.

[DESTRUCTIVE]
Can permanently remove or replace data/objects.
```

All DDL and inserts in this section are `[LAB-ONLY]`. Do not execute them against production merely to follow the tutorial.

## 1.5.2 Verify the target first

Connect explicitly:

```bash
psql -h localhost -p 5432 -U tutorial_admin -d tutorial_db
```

Verify:

```sql
-- [SAFE-READ]
SELECT
    current_database() AS database_name,
    session_user AS session_user,
    current_user AS effective_role,
    inet_server_addr() AS server_address,
    inet_server_port() AS server_port,
    pg_backend_pid() AS backend_pid;
```

Then run `\conninfo`.

```text
VERIFY TARGET → VERIFY DATABASE → VERIFY IDENTITY → CHANGE STATE → VALIDATE
```

A valid DDL statement executed against the wrong database is still an operational mistake.

## 1.5.3 PostgreSQL logical hierarchy

A PostgreSQL database cluster is a collection of databases managed by a PostgreSQL server. The word cluster does not automatically mean multiple servers, HA, replication, a distributed database, or a Kubernetes cluster.

```text
PostgreSQL Database Cluster
├── postgres
├── template0
├── template1
└── tutorial_db
```

A database is a major logical container. Verify the current database with:

```sql
-- [SAFE-READ]
SELECT current_database();
```

List databases with `\l`.

A normal PostgreSQL connection targets one database. Switching with `\c postgres` causes `psql` to establish a connection to that database. Return with `\c tutorial_db`.

## 1.5.4 Database boundaries

A connection to `tutorial_db` does not directly address a table in another database using ordinary `database.schema.table` syntax. PostgreSQL supports explicit cross-database integration mechanisms such as `postgres_fdw`, but those are separate architectural features and are deferred.

## 1.5.5 Schemas

A schema is a namespace inside a database. Schemas can contain tables, views, sequences, functions, types, and other objects.

```text
tutorial_db
├── public
├── clinical
└── archive
```

Databases created from PostgreSQL's standard templates normally contain a `public` schema. It is a conventional default namespace, not a mandatory application schema.

Create the tutorial schema only after verifying the target:

```sql
-- [LAB-ONLY]
CREATE SCHEMA clinical;
```

Validate with `\dn`. Creating a schema requires appropriate privilege on the database. If creation fails with a permission error, do not automatically switch to superuser; verify database ownership, `CREATE` privilege, the intended role, and environment policy.

## 1.5.6 information_schema

PostgreSQL provides the `information_schema` schema with SQL-standard-oriented metadata views.

```sql
-- [SAFE-READ]
SELECT schema_name
FROM information_schema.schemata
ORDER BY schema_name;
```

`information_schema` results are scoped to the current database and can be affected by the current user's access and visibility. No returned metadata row is not proof that an object exists nowhere.

## 1.5.7 Tables, columns, and rows

A table is a logical relational object used to store structured data. Our first application table is `clinical.patients`, where `clinical` is the schema and `patients` is the table.

```sql
-- [LAB-ONLY]
CREATE TABLE clinical.patients (
    patient_id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    first_name    VARCHAR(100) NOT NULL,
    last_name     VARCHAR(100) NOT NULL,
    date_of_birth DATE,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Validate with:

```text
\dt clinical.*
\d clinical.patients
```

A column represents an attribute. Inspect columns with:

```sql
-- [SAFE-READ]
SELECT
    column_name,
    data_type,
    is_nullable,
    column_default
FROM information_schema.columns
WHERE table_schema = 'clinical'
  AND table_name = 'patients'
ORDER BY ordinal_position;
```

A row represents a record stored in the table. Insert only synthetic tutorial data:

```sql
-- [LAB-ONLY — SYNTHETIC DATA]
INSERT INTO clinical.patients (first_name, last_name, date_of_birth)
VALUES ('Ava', 'Carter', DATE '1988-04-12');

INSERT INTO clinical.patients (first_name, last_name, date_of_birth)
VALUES ('Noah', 'Wilson', DATE '1975-09-21');
```

Read the rows:

```sql
-- [SAFE-READ]
SELECT patient_id, first_name, last_name, date_of_birth, created_at
FROM clinical.patients
ORDER BY patient_id;
```

Columns are attributes; rows are records. `SELECT *` is convenient for exploration, but explicit column lists are often clearer and can reduce unnecessary retrieval and accidental exposure of fields.

## 1.5.8 Schema-qualified object names

Prefer explicit names such as `clinical.patients` for controlled administrative SQL. Schema qualification improves clarity, predictability, troubleshooting, automation safety, and security.

Different schemas can contain objects with the same unqualified name:

```sql
-- [LAB-ONLY]
CREATE SCHEMA archive;

CREATE TABLE archive.patients (
    patient_id  BIGINT,
    archived_at TIMESTAMPTZ
);
```

Validate with:

```text
\dt clinical.*
\dt archive.*
```

`clinical.patients` and `archive.patients` are different objects.

## 1.5.9 search_path

For an unqualified reference such as `SELECT * FROM patients;`, PostgreSQL resolves the object using namespace search rules. Inspect the configured expression:

```sql
-- [SAFE-READ]
SHOW search_path;
```

A common default is `"$user", public`, though environments can differ.

Inspect the effective resolved list:

```sql
-- [SAFE-READ]
SELECT current_schemas(true);
```

`SHOW search_path` shows the configured expression; `current_schemas(true)` shows the effective resolved schema list.

An entry such as `"$user"` can refer to a usable schema named for the effective user when such a schema exists. It does not create that schema automatically.

`pg_catalog` also participates in name resolution according to PostgreSQL's implicit rules, and a session temporary namespace can participate when temporary objects exist. Temporary-object behavior is deferred.

`search_path` is also a security concern. A writable schema in an effective search path can create object-resolution risk. Important administrative SQL should prefer explicit schema qualification. Detailed secure `search_path` design belongs in Part 4.

The search path also affects unqualified object creation. `CREATE TABLE patients (...)` can select a creation namespace from the applicable search path, while `CREATE TABLE clinical.patients (...)` explicitly determines the namespace.

## 1.5.10 Build the clinical model

Create the remaining tutorial tables:

```sql
-- [LAB-ONLY]
CREATE TABLE clinical.providers (
    provider_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    first_name  VARCHAR(100) NOT NULL,
    last_name   VARCHAR(100) NOT NULL,
    specialty   VARCHAR(150),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE clinical.appointments (
    appointment_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    patient_id     BIGINT NOT NULL,
    provider_id    BIGINT NOT NULL,
    appointment_at TIMESTAMPTZ NOT NULL,
    status         VARCHAR(50) NOT NULL,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Validate with `\dt clinical.*`.

### Lab design limitation

`appointments.patient_id` and `appointments.provider_id` are ordinary columns at this stage. Foreign-key constraints have not yet been created, so PostgreSQL does not currently enforce that these values correspond to rows in `clinical.patients` and `clinical.providers`. This is intentional; foreign keys and relational integrity are introduced in Part 1.10.

Insert a synthetic provider:

```sql
-- [LAB-ONLY — SYNTHETIC DATA]
INSERT INTO clinical.providers (first_name, last_name, specialty)
VALUES ('Maya', 'Patel', 'Cardiology');
```

Before inserting an appointment, query the IDs actually generated in your lab:

```sql
-- [SAFE-READ]
SELECT patient_id, first_name, last_name
FROM clinical.patients
ORDER BY patient_id;

SELECT provider_id, first_name, last_name
FROM clinical.providers
ORDER BY provider_id;
```

Never blindly assume generated IDs. Use query → evidence → action.

If your verified patient and provider IDs are both `1`, an example appointment is:

```sql
-- [LAB-ONLY — SYNTHETIC DATA]
INSERT INTO clinical.appointments (
    patient_id,
    provider_id,
    appointment_at,
    status
)
VALUES (
    1,
    1,
    CURRENT_TIMESTAMP + INTERVAL '1 day',
    'SCHEDULED'
);
```

## 1.5.11 Metadata inspection

Inspect tables:

```sql
-- [SAFE-READ]
SELECT table_schema, table_name, table_type
FROM information_schema.tables
WHERE table_schema IN ('clinical', 'archive')
ORDER BY table_schema, table_name;
```

Inspect columns:

```sql
-- [SAFE-READ]
SELECT
    table_schema,
    table_name,
    ordinal_position,
    column_name,
    data_type,
    is_nullable
FROM information_schema.columns
WHERE table_schema IN ('clinical', 'archive')
ORDER BY table_schema, table_name, ordinal_position;
```

PostgreSQL also provides PostgreSQL-specific system catalogs. For example:

```sql
-- [SAFE-READ]
SELECT nspname
FROM pg_catalog.pg_namespace
ORDER BY nspname;
```

At this level, think of `information_schema` as a SQL-standard-oriented metadata interface and `pg_catalog` as PostgreSQL-specific system metadata.

Do not directly `INSERT`, `UPDATE`, or `DELETE` PostgreSQL system catalogs as a normal administrative technique. Use supported PostgreSQL DDL and administrative interfaces.

Read-only metadata can still expose database names, schema names, table names, columns, data types, ownership, and application architecture. `[SAFE-READ]` does not mean safe to publish; redact production metadata before sharing it outside approved channels.

## 1.5.12 Object ownership

Newly created PostgreSQL objects normally have an owner. If `tutorial_admin` successfully executes the `CREATE SCHEMA` and `CREATE TABLE` statements, it will normally own the resulting objects unless ownership is subsequently changed.

Inspect with:

```text
\dn+
\dt clinical.*
```

Detailed `GRANT`, `REVOKE`, `USAGE`, `CREATE`, ownership, and role inheritance are deferred to Part 4.

## 1.5.13 Logical hierarchy is not physical storage

Database → schema → table → rows/columns is a logical model. Do not assume PostgreSQL physically stores a matching `tutorial_db/clinical/patients/` directory hierarchy or that one table always equals one simple OS file. Relation files, forks, TOAST, WAL, and physical storage are covered in Part 5.

## 1.5.14 Identifier casing

PostgreSQL folds unquoted identifiers to lowercase. An unquoted `PatientRecords` is treated as `patientrecords`, while a quoted `"PatientRecords"` preserves case-sensitive identity. Prefer predictable lowercase tutorial names such as `patient_records` unless quoted identifiers are deliberately required.

## 1.5.15 Controlled missing-object experiments

Run only in the lab:

```sql
-- [LAB-ONLY — INTENTIONAL ERROR]
SELECT *
FROM schema_that_does_not_exist.patients;

-- [LAB-ONLY — INTENTIONAL ERROR]
SELECT *
FROM clinical.table_that_does_not_exist;
```

Capture the exact errors, then inspect with `\dn` and `\dt clinical.*`. Use error → evidence → inspection → root cause → remediation.

## 1.5.16 Wrong-database experiment

Switch:

```text
\c postgres
```

Verify:

```sql
SELECT current_database();
```

Then run `\dt clinical.*`. The `clinical` schema created in `tutorial_db` does not automatically exist in `postgres`.

Return:

```text
\c tutorial_db
```

Verify the database and run `\dt clinical.*` again.

This establishes a critical production lesson: if an object appears missing, do not create it until you have verified the database.

## 1.5.17 Evidence-first object troubleshooting

If an application reports a missing relation, do not immediately run `CREATE TABLE`. Instead:

```text
Capture exact error
→ Verify connection
→ Verify database
→ Verify schema
→ Verify object spelling/case
→ Inspect search_path
→ Verify deployment/migration state
→ Evaluate visibility/privileges
→ Determine root cause
→ Remediate
```

Useful diagnostics include:

```sql
-- [SAFE-READ]
SELECT current_database(), session_user, current_user;
SHOW search_path;
SELECT current_schemas(true);

SELECT table_schema, table_name
FROM information_schema.tables
WHERE table_name = 'patients'
ORDER BY table_schema;
```

Also use `\dn` and `\dt clinical.*`.

Do not force every missing-object symptom into the same diagnosis; reason from the exact PostgreSQL error and supporting evidence.

## 1.5.18 Do not hide unexpected state yet

If rerunning `CREATE SCHEMA clinical;` reports that the schema already exists, that is useful evidence. We deliberately do not convert every command to `IF NOT EXISTS` merely to suppress state information.

Later automation will teach proper idempotency as discover state → compare desired state → determine drift → change only when appropriate → validate. Idempotency is more than ignoring existence errors.

## 1.5.19 No destructive cleanup yet

Do not run `DROP TABLE clinical.patients;` or `DROP SCHEMA clinical CASCADE;`. These objects are intentionally retained for later Part 1 labs. `DROP`, dependencies, `CASCADE`, rollback limitations, and production change controls are deferred.

## 1.5.20 Healthcare-data safety

The healthcare-style model provides realistic relationships, but the repository must contain only synthetic information. Never place real patient names, medical record numbers, diagnoses, addresses, clinical records, PHI, customer exports, or production screenshots containing PHI into the tutorial repository.
