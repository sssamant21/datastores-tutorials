A healthcare organization needs a small training application for scheduling appointments.


A patient can have many appointments.

## 1.15.15 Step 8 — Create Patients

```sql
CREATE TABLE clinical.patients (
    patient_id      bigint GENERATED ALWAYS AS IDENTITY,
    medical_record  varchar(30) NOT NULL,
    first_name      varchar(100) NOT NULL,
    last_name       varchar(100) NOT NULL,
    date_of_birth   date NOT NULL,
    email           text,
    active          boolean NOT NULL DEFAULT true,
    created_at      timestamptz NOT NULL DEFAULT current_timestamp,

    CONSTRAINT patients_pk
        PRIMARY KEY (patient_id),

    CONSTRAINT patients_medical_record_uk
        UNIQUE (medical_record)
);
```

This demonstrates:

```text
bigint
identity
varchar
text
date
boolean
timestamptz
DEFAULT
NOT NULL
PRIMARY KEY
UNIQUE
```

An identity column generates values.

It does **not** by itself provide the relational uniqueness guarantee expected from a primary key.

That is why:

```sql
PRIMARY KEY (patient_id)
```

remains important.

## 1.15.17 Step 10 — Create Appointments

```sql
CREATE TABLE scheduling.appointments (
    appointment_id      bigint GENERATED ALWAYS AS IDENTITY,
    patient_id          bigint NOT NULL,
    provider_id         bigint NOT NULL,
    appointment_time    timestamptz NOT NULL,
    appointment_type    varchar(50) NOT NULL,
    status              varchar(20) NOT NULL DEFAULT 'SCHEDULED',
    notes               text,
    created_at          timestamptz NOT NULL DEFAULT current_timestamp,

    CONSTRAINT appointments_pk
        PRIMARY KEY (appointment_id),

    CONSTRAINT appointments_patient_fk
        FOREIGN KEY (patient_id)
        REFERENCES clinical.patients(patient_id),

    CONSTRAINT appointments_provider_fk
        FOREIGN KEY (provider_id)
        REFERENCES clinical.providers(provider_id),

    CONSTRAINT appointments_status_ck
        CHECK (
            status IN (
                'SCHEDULED',
                'COMPLETED',
                'CANCELLED'
            )
        )
);
```

Relationship:

```text
clinical.patients
       |
       | patient_id
       ↓
scheduling.appointments
       ↑
       | provider_id
       |
clinical.providers
```

No `ON DELETE CASCADE` is intentionally configured.

The default foreign-key deletion behavior prevents referenced patient/provider deletion from silently deleting appointment history.

Foreign-key declarations also do not automatically create indexes on the referencing columns. Whether such indexes are appropriate depends on workload and will be covered with indexing later.

## 1.15.18 Understanding `timestamptz`

`appointment_time` uses:

```sql
timestamptz
```

Example input:

```sql
TIMESTAMPTZ '2026-10-05 09:00:00-04'
```

The correct mental model is:

```text
Input timestamp + offset
        ↓
An instant in time
        ↓
PostgreSQL stores the instant
        ↓
Session TimeZone controls display
```

Do not interpret `timestamptz` as permanently retaining the original textual `-04` zone information.

Applications that need to preserve a named scheduling zone such as:

```text
America/New_York
```

may need to store that domain information separately.

## 1.15.22 Step 14 — Create Appointments

Resolve surrogate IDs from stable tutorial business identifiers:

```sql
INSERT INTO scheduling.appointments (
    patient_id,
    provider_id,
    appointment_time,
    appointment_type
)

    p.patient_id,
    pr.provider_id,
    TIMESTAMPTZ '2026-10-05 09:00:00-04',
    'CONSULTATION'
FROM clinical.patients AS p
CROSS JOIN clinical.providers AS pr
WHERE p.medical_record = 'MRN-10001'
```

## 1.15.23 Step 15 — Query the Schedule

```sql

    a.appointment_id,
    p.medical_record,
    p.first_name || ' ' || p.last_name AS patient,
    pr.provider_code,
    pr.first_name || ' ' || pr.last_name AS provider,

    a.status
FROM scheduling.appointments AS a

  ON p.patient_id = a.patient_id

  ON pr.provider_id = a.provider_id
```

## 1.15.24 Step 16 — Practice UPDATE Safely

First identify the target:

```sql
SELECT
    a.appointment_id,
    p.medical_record,
    a.appointment_time,
    a.status
FROM scheduling.appointments AS a
JOIN clinical.patients AS p
  ON p.patient_id = a.patient_id
WHERE p.medical_record = 'MRN-10001'
  AND a.appointment_time =
      TIMESTAMPTZ '2026-10-05 09:00:00-04'
  AND a.status = 'SCHEDULED';
```

Only after verifying the target:

```sql
UPDATE scheduling.appointments AS a
SET status = 'COMPLETED'
FROM clinical.patients AS p
WHERE p.patient_id = a.patient_id
  AND p.medical_record = 'MRN-10001'
  AND a.appointment_time =
      TIMESTAMPTZ '2026-10-05 09:00:00-04'
  AND a.status = 'SCHEDULED'
RETURNING
    a.appointment_id,
    a.status;
```

Operational pattern:

```text
SELECT
   ↓
Verify
   ↓
UPDATE
   ↓
RETURNING
   ↓
Verify
```

## 1.15.28 Existing Objects vs Future Objects

Commands such as:

```sql
GRANT SELECT
ON ALL TABLES IN SCHEMA clinical
TO healthcare_readonly;
```

apply to matching objects that currently exist.

They do not automatically define privileges for every future table.

Future-object privilege management requires an appropriate default-privilege strategy, commonly involving:

```text
ALTER DEFAULT PRIVILEGES
```

That topic will be covered in later administration/security material.

## 1.15.29 Database `PUBLIC` Privileges

Explicitly granting:

```sql
GRANT CONNECT
ON DATABASE healthcare_lab
TO healthcare_app;
```

does not necessarily mean `healthcare_app` is the only identity capable of connecting.

PostgreSQL databases can have default privileges granted through `PUBLIC`.

The project intentionally does not revoke those defaults because Part 1 focuses on foundational role and privilege mechanics rather than complete database hardening.

Production environments should establish database access according to their security baseline.

## 1.15.30 Step 20 — Verify Privileges Without Destructive Testing

Instead of attempting a dangerous `DELETE` simply to prove that the read-only role cannot delete, inspect privileges:

```sql
SELECT
    has_schema_privilege(
        'healthcare_app',
        'clinical',
        'USAGE'
    ) AS app_clinical_usage,

    has_table_privilege(
        'healthcare_app',
        'clinical.patients',
        'SELECT'
    ) AS app_patient_select,

    has_table_privilege(
        'healthcare_app',
        'clinical.patients',
        'INSERT'
    ) AS app_patient_insert,

    has_table_privilege(
        'healthcare_readonly',
        'clinical.patients',
        'SELECT'
    ) AS readonly_patient_select,

    has_table_privilege(
        'healthcare_readonly',
        'clinical.patients',
        'DELETE'
    ) AS readonly_patient_delete;
```

Expected conceptual result:

```text
app_clinical_usage      true
app_patient_select      true
app_patient_insert      true
readonly_patient_select true
readonly_patient_delete false
```

This proves the intended privilege boundary without attempting destructive SQL.

## 1.15.39 Production Lessons

This beginner project already demonstrates several production principles.

### Separate ownership from runtime identities

Applications should not routinely operate as superusers or object owners.

### Use least privilege

Grant only what an identity needs.

### Use database constraints

Relational integrity should not depend entirely on application code.

### Validate before mutation

For important `UPDATE` and `DELETE` operations:

```text
SELECT
   ↓
verify target
   ↓
mutate
   ↓
RETURNING
   ↓
verify result
```

### Never test security with valuable data

Privilege inspection is safer than attempting destructive SQL against important records.

### Separate authentication from authorization

Authentication determines identity.

Privileges determine permitted operations.

### Understand configuration source of truth

Especially on managed and containerized platforms.

### Separate build, verification, and cleanup

```text
Build ≠ Acceptance ≠ Cleanup
```

### Never use production healthcare data for a tutorial

Use synthetic data only.
