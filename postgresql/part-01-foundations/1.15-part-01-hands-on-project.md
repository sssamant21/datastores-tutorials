## 1.15.3 Project Scenario

A synthetic healthcare training application tracks patients, providers, and appointments. A patient can have many appointments; a provider can have many appointments; each appointment references one patient and one provider.

## 1.15.4 Target Architecture

```text
PostgreSQL 18
├── Cluster roles
│   ├── healthcare_owner     (NOLOGIN ownership)
│   ├── healthcare_app       (runtime CRUD)
│   └── healthcare_readonly  (SELECT)
└── healthcare_lab
    ├── clinical
    │   ├── patients
    │   └── providers
    └── scheduling
        └── appointments
```

Applications should not normally operate as PostgreSQL superusers or object owners.

## 1.15.5 Safety and Data Boundary

The build is `[MUTATING LAB — ISOLATED ENVIRONMENT ONLY]`. It creates cluster-wide roles and database objects and performs INSERT, UPDATE, DELETE, and GRANT operations. Run it only on a dedicated training instance, disposable local environment, or explicitly approved development environment. Never automatically drop an unexpected existing database or role.

All people, identifiers, MRNs, appointments, providers, and contact information in this tutorial are synthetic. Do not substitute real patient information, PHI, production exports, or screenshots containing sensitive data. Synthetic email addresses use the reserved `.invalid` domain.

The lifecycle is deliberately separated:

```text
BUILD       → mutating, stateful, not automatically idempotent
ACCEPTANCE  → read-only, repeatable, does not repair
CLEANUP     → destructive, optional, explicitly invoked
```

## 1.15.7 Create Roles and Database

Create the ownership role:

```sql
CREATE ROLE healthcare_owner NOLOGIN;
```

The administrator must have appropriate authority to act as this role. A deliberately configured non-superuser lab administrator may use appropriate role membership, for example conceptually:

```sql
GRANT healthcare_owner TO lab_admin WITH INHERIT FALSE, SET TRUE;
```

Do not execute that placeholder unless the role and membership are appropriate for the lab.

Create the database:

```sql
CREATE DATABASE healthcare_lab OWNER healthcare_owner;
```

Connect:

```text
\c healthcare_lab
```

Create runtime identities without embedding passwords in committed SQL:

```sql
CREATE ROLE healthcare_app LOGIN;
CREATE ROLE healthcare_readonly LOGIN;
```

Set unique lab passwords interactively:

```text
\password healthcare_app
\password healthcare_readonly
```

Where authorized:

```sql
SET ROLE healthcare_owner;
SELECT session_user, current_user;
```

`session_user` is the original authenticated identity; `current_user` is the currently effective role.

## 1.15.9 Create Tables

```sql
CREATE TABLE clinical.patients (
    patient_id bigint GENERATED ALWAYS AS IDENTITY,
    medical_record varchar(30) NOT NULL,
    first_name varchar(100) NOT NULL,
    last_name varchar(100) NOT NULL,
    date_of_birth date NOT NULL,
    email text,
    active boolean NOT NULL DEFAULT true,
    created_at timestamptz NOT NULL DEFAULT current_timestamp,
    CONSTRAINT patients_pk PRIMARY KEY (patient_id),
    CONSTRAINT patients_medical_record_uk UNIQUE (medical_record)
);

CREATE TABLE clinical.providers (
    provider_id bigint GENERATED ALWAYS AS IDENTITY,
    provider_code varchar(30) NOT NULL,
    first_name varchar(100) NOT NULL,
    last_name varchar(100) NOT NULL,
    specialty varchar(100) NOT NULL,
    active boolean NOT NULL DEFAULT true,
    created_at timestamptz NOT NULL DEFAULT current_timestamp,
    CONSTRAINT providers_pk PRIMARY KEY (provider_id),
    CONSTRAINT providers_code_uk UNIQUE (provider_code)
);

CREATE TABLE scheduling.appointments (
    appointment_id bigint GENERATED ALWAYS AS IDENTITY,
    patient_id bigint NOT NULL,
    provider_id bigint NOT NULL,
    appointment_time timestamptz NOT NULL,
    appointment_type varchar(50) NOT NULL,
    status varchar(20) NOT NULL DEFAULT 'SCHEDULED',
    notes text,
    created_at timestamptz NOT NULL DEFAULT current_timestamp,
    CONSTRAINT appointments_pk PRIMARY KEY (appointment_id),
    CONSTRAINT appointments_patient_fk FOREIGN KEY (patient_id)
        REFERENCES clinical.patients(patient_id),
    CONSTRAINT appointments_provider_fk FOREIGN KEY (provider_id)
        REFERENCES clinical.providers(provider_id),
    CONSTRAINT appointments_status_ck CHECK
        (status IN ('SCHEDULED','COMPLETED','CANCELLED'))
);
```

Identity generates values but does not replace primary-key uniqueness. No `ON DELETE CASCADE` is intentionally configured, so deleting a referenced patient/provider does not silently delete appointment history. Foreign-key declarations do not automatically create indexes on the referencing columns; indexing is covered later.

`timestamptz` represents an instant in time; PostgreSQL displays it according to the session `TimeZone`. The original textual zone/offset is not a permanently retained property of the value. Applications needing a named scheduling zone may store that domain information separately.

Inspect with `\dn`, `\dt clinical.*`, `\dt scheduling.*`, and `\d` for each table.

```sql
INSERT INTO clinical.patients
    (medical_record, first_name, last_name, date_of_birth, email)
VALUES
 ('MRN-10001','Ava','Morgan',DATE '1988-04-12','ava.morgan@example.invalid'),
 ('MRN-10002','Noah','Patel',DATE '1979-11-03','noah.patel@example.invalid'),
 ('MRN-10003','Mia','Johnson',DATE '1995-06-24','mia.johnson@example.invalid');

INSERT INTO clinical.providers
    (provider_code, first_name, last_name, specialty)
VALUES
 ('PRV-101','Olivia','Chen','Cardiology'),
 ('PRV-102','Ethan','Williams','Primary Care');
```

Create appointments by resolving generated IDs from stable tutorial business identifiers:

```sql
INSERT INTO scheduling.appointments
    (patient_id, provider_id, appointment_time, appointment_type)
SELECT p.patient_id, pr.provider_id,
       TIMESTAMPTZ '2026-10-05 09:00:00-04', 'CONSULTATION'
FROM clinical.patients AS p
CROSS JOIN clinical.providers AS pr
WHERE p.medical_record = 'MRN-10001'
  AND pr.provider_code = 'PRV-101';

INSERT INTO scheduling.appointments
    (patient_id, provider_id, appointment_time, appointment_type)
SELECT p.patient_id, pr.provider_id,
       TIMESTAMPTZ '2026-10-05 10:30:00-04', 'FOLLOW_UP'
FROM clinical.patients AS p
CROSS JOIN clinical.providers AS pr
WHERE p.medical_record = 'MRN-10002'
  AND pr.provider_code = 'PRV-102';
```

Do not assume generated IDs such as `patient_id = 1` when stable identifiers can select the intended row.

## 1.15.11 Query and Update

```sql
SELECT a.appointment_id, p.medical_record,
       p.first_name || ' ' || p.last_name AS patient,
       pr.provider_code,
       pr.first_name || ' ' || pr.last_name AS provider,
       pr.specialty, a.appointment_time, a.appointment_type, a.status
FROM scheduling.appointments AS a
JOIN clinical.patients AS p ON p.patient_id = a.patient_id
JOIN clinical.providers AS pr ON pr.provider_id = a.provider_id
ORDER BY a.appointment_time;
```

Before UPDATE, verify the target with SELECT, then mutate with a constrained predicate and `RETURNING`:

```sql
SELECT a.appointment_id, p.medical_record, a.appointment_time, a.status
FROM scheduling.appointments AS a
JOIN clinical.patients AS p ON p.patient_id = a.patient_id
WHERE p.medical_record = 'MRN-10001'
  AND a.appointment_time = TIMESTAMPTZ '2026-10-05 09:00:00-04'
  AND a.status = 'SCHEDULED';

UPDATE scheduling.appointments AS a
SET status = 'COMPLETED'
FROM clinical.patients AS p
WHERE p.patient_id = a.patient_id
  AND p.medical_record = 'MRN-10001'
  AND a.appointment_time = TIMESTAMPTZ '2026-10-05 09:00:00-04'
  AND a.status = 'SCHEDULED'
RETURNING a.appointment_id, a.status;
```

Operational pattern: `SELECT → verify → UPDATE → RETURNING → verify`.

## 1.15.12 Practice DELETE with a Disposable Row

```sql
INSERT INTO clinical.patients
    (medical_record, first_name, last_name, date_of_birth)
VALUES ('MRN-DELETE-TEST','Delete','Test',DATE '2000-01-01');

BEGIN;

SELECT patient_id, medical_record
FROM clinical.patients
WHERE medical_record = 'MRN-DELETE-TEST';

DELETE FROM clinical.patients
WHERE medical_record = 'MRN-DELETE-TEST'
RETURNING patient_id, medical_record;
```

If the returned row is exactly the disposable test record, `COMMIT`; otherwise `ROLLBACK`. Never practice destructive SQL against valuable data.

## 1.15.13 Application and Read-Only Privileges

```sql
GRANT CONNECT ON DATABASE healthcare_lab TO healthcare_app;
GRANT USAGE ON SCHEMA clinical, scheduling TO healthcare_app;
GRANT SELECT, INSERT, UPDATE, DELETE
    ON ALL TABLES IN SCHEMA clinical TO healthcare_app;
GRANT SELECT, INSERT, UPDATE, DELETE
    ON ALL TABLES IN SCHEMA scheduling TO healthcare_app;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA clinical TO healthcare_app;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA scheduling TO healthcare_app;

GRANT CONNECT ON DATABASE healthcare_lab TO healthcare_readonly;
GRANT USAGE ON SCHEMA clinical, scheduling TO healthcare_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA clinical TO healthcare_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA scheduling TO healthcare_readonly;
```

Sequence `USAGE` is intentionally narrower than granting unnecessary sequence-state inspection. `GRANT ... ON ALL ... IN SCHEMA` covers matching existing objects, not every future object; future-object access requires a default-privilege strategy such as `ALTER DEFAULT PRIVILEGES`, covered later.

Explicit `CONNECT` grants do not necessarily mean these are the only roles capable of connecting because PostgreSQL can grant database privileges through `PUBLIC`. Full hardening is deferred to later security material.

Verify without destructive testing:

```sql
SELECT has_schema_privilege('healthcare_app','clinical','USAGE') AS app_clinical_usage,
       has_table_privilege('healthcare_app','clinical.patients','SELECT') AS app_patient_select,
       has_table_privilege('healthcare_app','clinical.patients','INSERT') AS app_patient_insert,
       has_table_privilege('healthcare_readonly','clinical.patients','SELECT') AS readonly_patient_select,
       has_table_privilege('healthcare_readonly','clinical.patients','DELETE') AS readonly_patient_delete;
```

The intended read-only DELETE result is `false`. `information_schema.role_table_grants` can inspect visible grants, but its visibility rules mean absence from that view is not universal proof of absence of all effective access.

## 1.15.14 Operational Inspection

Processes:

```sql
SELECT pid, usename, datname, application_name, client_addr, state
FROM pg_stat_activity
WHERE datname = 'healthcare_lab'
ORDER BY pid;
```

Files and configuration:

```sql
SHOW data_directory;
SHOW config_file;
SHOW hba_file;

SELECT name, setting, unit, context, source, pending_restart
FROM pg_settings
WHERE name IN
 ('listen_addresses','port','max_connections','shared_buffers','work_mem','password_encryption')
ORDER BY name;
```

Where authorized, HBA inspection is optional:

```sql
SELECT rule_number, type, database, user_name, address, auth_method, error
FROM pg_hba_file_rules
ORDER BY rule_number NULLS LAST;
```

If permission is denied, treat it as `SKIP — insufficient privilege`; do not grant superuser solely to make the optional check succeed.

Managed PostgreSQL and Kubernetes platforms may abstract OS access, PGDATA, HBA editing, service control, or true superuser capabilities. Use the provider/platform source of truth rather than weakening controls to reproduce a self-managed command.

## 1.15.15 SAFE-READ Acceptance

Run:

```bash
psql -d healthcare_lab -f labs/part-01-project-check.sql
```

The acceptance artifact is `[TUTORIAL-ACCEPTANCE — SAFE-READ]`. It verifies rather than repairs and performs no CREATE, ALTER, DROP, INSERT, UPDATE, DELETE, TRUNCATE, GRANT, REVOKE, ALTER SYSTEM, reload, restart, or session termination.

Interpretation:

```text
PASS → required state verified
FAIL → required state missing or incorrect
SKIP → optional inspection unavailable because of environment/privilege boundary
```

## 1.15.17 Production Lessons

This project establishes foundational operational habits:

- separate ownership from runtime identities;
- apply least privilege;
- use database constraints for relational integrity;
- validate targets before mutation;
- never test security with valuable data;
- separate authentication from authorization;
- understand the configuration source of truth;
- separate build, verification, and cleanup;
- never use production healthcare data for tutorials.

Troubleshooting should follow layered reasoning: server/network/database/role/authentication/CONNECT for connection failures; schema/table privileges for authorization failures; sequence and constraint checks for INSERT failures; and `pg_settings` source metadata for unexpected configuration.
