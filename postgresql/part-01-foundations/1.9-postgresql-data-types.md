## 1.9.1 Why Data Types Matter

Every PostgreSQL column has a data type. The type influences data integrity, storage representation, comparison semantics, available operators and functions, indexing choices, application behavior, query design, and maintainability.

The `clinical.data_type_lab` table used below is intentionally broad because it demonstrates many PostgreSQL types in one place. It is **not** a recommended production healthcare schema.

## 1.9.2 Integer Types

PostgreSQL provides `smallint`, `integer`, and `bigint` for whole numbers with different ranges. Choose a type whose range matches the domain and expected growth.

For newly designed generated identifiers, identity columns provide a clear SQL-level mechanism:

```sql
lab_id bigint GENERATED ALWAYS AS IDENTITY
```

## 1.9.3 Exact Numeric Values

For values requiring exact decimal arithmetic, use `numeric`/`decimal`.

```sql
charge_amount numeric(12,2)
```

Here 12 is precision and 2 is scale. Exact numeric types are appropriate when decimal precision must be preserved exactly, including many financial and billing values.

## 1.9.4 Approximate Numeric Values

`real` and `double precision` represent approximate floating-point values.

```sql
temperature_c double precision
```

Do not assume every decimal fraction is represented exactly, and do not automatically use floating point for financial values requiring exact decimal arithmetic.

## 1.9.5 VARCHAR vs TEXT

PostgreSQL supports `varchar(n)`, unconstrained `varchar`, and `text`.

```sql
patient_code varchar(30)
description  text
```

Use `varchar(n)` when the maximum length is a genuine domain rule. Use `text` when an arbitrary application-defined length restriction provides no useful integrity rule. Do not choose `varchar(n)` because of an assumption that it is inherently faster than `text` in PostgreSQL.

## 1.9.6 Boolean

Use PostgreSQL's native `boolean` type for genuinely binary values:

```sql
is_active boolean NOT NULL DEFAULT true
```

Avoid unnecessary text encodings such as Y/N or YES/NO unless an external interface or legacy model requires them.

## 1.9.7 Date and Time Types

Important temporal types include `date`, `time`, `timestamp`, and `timestamptz`.

```sql
birth_date      date,
appointment_at  timestamp,
recorded_at     timestamptz
```

`date` represents a calendar date without a time of day.

`timestamp` means `timestamp without time zone` and represents date-and-time fields without associating them with a particular UTC instant.

`timestamptz` is PostgreSQL's abbreviation for `timestamp with time zone`. It is generally appropriate when representing an actual instant that must be understood consistently across systems or regions. PostgreSQL stores the instant internally and displays it according to the session `TimeZone`; the original timezone name or textual offset is not preserved as part of the stored value.

```sql
SHOW TimeZone;
```

Distributed applications should explicitly distinguish actual instants from local wall-clock values.

## 1.9.8 NULL

`NULL` represents the absence of a known value. It is not zero, an empty string, false, or the string `NULL`.

Use:

```sql
WHERE description IS NULL;
```

or:

```sql
WHERE description IS NOT NULL;
```

SQL uses three-valued logic: TRUE, FALSE, and UNKNOWN. Comparisons involving `NULL` commonly produce UNKNOWN.

## 1.9.9 UUID

PostgreSQL provides a native `uuid` type:

```sql
patient_uuid uuid NOT NULL
```

UUIDs can be useful when identifiers must be generated independently across distributed systems. They are not automatically superior to integer identifiers; consider generation architecture, index behavior, storage, locality, interoperability, and operational requirements.

This lab uses the deterministic synthetic UUID `11111111-1111-4111-8111-111111111111`.

## 1.9.10 JSON and JSONB

PostgreSQL provides both `json` and `jsonb`. For data that will be queried, filtered, transformed, or indexed inside PostgreSQL, `jsonb` is commonly the practical choice. `json` can be useful when preserving the original textual representation matters.

```sql
metadata jsonb
```

Do not use JSON merely to avoid relational modeling. Strongly structured values requiring relational constraints, relationships, joins, and independent lifecycle management often belong in relational columns or tables.

## 1.9.11 Arrays

PostgreSQL supports arrays:

```sql
allergies text[]
```

Arrays can be appropriate when an attribute is genuinely multi-valued and naturally belongs to the row. If individual elements require identifiers, constraints, metadata, relationships, lifecycle, or auditing, a separate relational table may be a stronger model.

## 1.9.12 BYTEA

Use `bytea` for binary data:

```sql
binary_payload bytea
```

A small synthetic binary value can be created with:

```sql
decode('5047', 'hex')
```

Before storing large binary objects directly in PostgreSQL, consider database growth, WAL generation, replication traffic, backup size, restore time, storage cost, and recovery objectives.

## 1.9.13 Type Casting

Standard SQL:

```sql
CAST('125.37' AS numeric(12,2))
```

PostgreSQL shorthand:

```sql
'125.37'::numeric(12,2)
```

Do not assume PostgreSQL will implicitly perform every conversion an application expects. Explicit casts can make intent clearer and avoid ambiguity.

## 1.9.14 Hands-On Data Types Lab

Create the pedagogical tutorial table:

```sql
CREATE TABLE IF NOT EXISTS clinical.data_type_lab (
    lab_id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    patient_uuid    uuid NOT NULL,
    patient_code    varchar(30) NOT NULL,
    description     text,
    visit_count     integer NOT NULL DEFAULT 0,
    charge_amount   numeric(12,2),
    temperature_c   double precision,
    is_active       boolean NOT NULL DEFAULT true,
    birth_date      date,
    appointment_at  timestamp,
    recorded_at     timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    metadata        jsonb,
    allergies       text[],
    binary_payload  bytea
);
```

This table intentionally mixes unrelated type families for learning purposes. Do not copy this design directly into a production clinical model.

## 1.9.16 Inspect Values and Runtime Types

```sql
SELECT
    lab_id,
    patient_uuid,
    patient_code,
    description,
    visit_count,
    charge_amount,
    temperature_c,
    is_active,
    birth_date,
    appointment_at,
    recorded_at,
    metadata,
    allergies,
    binary_payload
FROM clinical.data_type_lab
WHERE patient_code = 'LAB-0001';
```

Use `pg_typeof()` to inspect expression types:

```sql
SELECT
    pg_typeof(patient_uuid)   AS patient_uuid_type,
    pg_typeof(patient_code)   AS patient_code_type,
    pg_typeof(visit_count)    AS visit_count_type,
    pg_typeof(charge_amount)  AS charge_amount_type,
    pg_typeof(temperature_c)  AS temperature_type,
    pg_typeof(is_active)      AS active_type,
    pg_typeof(birth_date)     AS birth_date_type,
    pg_typeof(appointment_at) AS appointment_type,
    pg_typeof(recorded_at)    AS recorded_at_type,
    pg_typeof(metadata)       AS metadata_type,
    pg_typeof(allergies)      AS allergies_type,
    pg_typeof(binary_payload) AS binary_payload_type
FROM clinical.data_type_lab
WHERE patient_code = 'LAB-0001';
```

## 1.9.17 Explore NULL Safely

```sql
SELECT lab_id, patient_code, description
FROM clinical.data_type_lab
WHERE description IS NOT NULL;
```

```sql
SELECT lab_id, patient_code, description
FROM clinical.data_type_lab
WHERE description IS NULL;
```

## 1.9.18 Production Modeling Guidance

Before choosing a type, ask what the value represents, what values are valid, whether exact precision matters, whether a temporal value is an instant or local wall-clock time, whether a length limit is a real domain rule, how the value will be queried/indexed, whether it represents a relationship, how large it can become, and how it affects backup, replication, and recovery.

Good type selection moves useful integrity rules into the database while keeping the model understandable.
