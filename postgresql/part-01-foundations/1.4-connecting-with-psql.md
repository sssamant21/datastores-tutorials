# Part 1.4 — Connecting with `psql`
## Revised Final / Canonical Edition

**Tutorial target:** PostgreSQL 18  
**Documentation baseline:** PostgreSQL 18.x  
**Prerequisites:** Parts 1.1–1.3  
**Lab database:** `tutorial_db`  
**Lab role:** `tutorial_admin`

Part 1.3 built and validated our PostgreSQL environment. We now focus on PostgreSQL's interactive terminal client, **`psql`**.

The objective is larger than learning a few backslash commands. Before performing database work, we want to be able to answer:

```text
Where am I connected?
Which database am I using?
Which identity am I using?
Which PostgreSQL server accepted the connection?
Which backend process represents my session?
```

Our operating principle begins here:

```text
VERIFY TARGET
     ↓
UNDERSTAND CONTEXT
     ↓
EXECUTE
     ↓
VALIDATE
```

## 1.4.1 Safety labels

The tutorial continues using these classifications:

```text
[SAFE-READ]
Observational/read-only operation.

[LAB-ONLY]
Changes state or intentionally creates workload
inside the dedicated tutorial environment.

[PRODUCTION-CAUTION]
Could affect production behavior, availability,
security, workload, configuration, or data.

[DESTRUCTIVE]
Could permanently remove or replace data/resources.
```

Remember: **Read-only does not mean safe to publish.** Database names, role names, addresses, queries, application names, configuration paths, and other diagnostic information can still be sensitive.

## 1.4.2 What is `psql`?

`psql` is PostgreSQL's interactive terminal client.

```text
┌──────────────────┐
│       psql       │
│      Client      │
└────────┬─────────┘
         │ PostgreSQL connection
         ▼
┌──────────────────┐
│ PostgreSQL       │
│ Server           │
│ tutorial_db      │
└──────────────────┘
```

Keep the distinction clear: `psql` is the client program; `postgres` is the server program. Closing `psql` does not stop PostgreSQL.

## 1.4.3 Verify the `psql` client

```bash
# [SAFE-READ]
psql --version
```

For this tutorial, we are using PostgreSQL 18. `psql --version` reports the client version and does not necessarily identify the version of the remote PostgreSQL server.

## 1.4.4 Client version vs server version

It is possible to have a PostgreSQL 18 `psql` client connecting to a PostgreSQL 17 server. After connecting, inspect the server:

```sql
-- [SAFE-READ]
SHOW server_version;
```

You can also use:

```sql
-- [SAFE-READ]
SELECT version();
```

Never assume client and server versions are identical.

## 1.4.5 PostgreSQL connection identity

A PostgreSQL connection normally needs four fundamental pieces of information: **host, port, database, and role**.

Our lab values are:

```text
Host:     localhost
Port:     5432
Database: tutorial_db
Role:     tutorial_admin
```

## 1.4.6 Explicit connection

```bash
psql \
  -h localhost \
  -p 5432 \
  -U tutorial_admin \
  -d tutorial_db
```

`-h` specifies the host, `-p` the port, `-U` the PostgreSQL role/user, and `-d` the database. For learning, troubleshooting, and controlled administration, explicit parameters reduce ambiguity.

## 1.4.7 Password handling

If password authentication applies, `psql` may prompt for the password for `tutorial_admin`. Enter the lab password created in Part 1.3.

Do not put real credentials into command lines, SQL files, shell scripts, Markdown, Git commits, screenshots, tickets, CI output, or chat messages. We deliberately do not use `PGPASSWORD` as our normal tutorial credential mechanism. `.pgpass` and production credential automation will be introduced later with their security requirements.

## 1.4.8 Successful connection

After connecting, you may see output conceptually similar to:

```text
psql (18.x)
Type "help" for help.

tutorial_db=>
```

You are now inside an interactive `psql` session.

## 1.4.9 Do not trust the prompt alone

The prompt provides useful context, but use this principle:

```text
Prompt
  ↓
Context hint

Explicit verification
  ↓
Operational evidence
```

Before important state-changing operations, verify explicitly.

## 1.4.10 Standard connection verification

```sql
-- [SAFE-READ]
SELECT
    current_database() AS database_name,
    session_user AS session_user,
    current_user AS effective_role,
    inet_server_addr() AS server_address,
    inet_server_port() AS server_port,
    pg_backend_pid() AS backend_pid;
```

For our normal TCP lab connection, this identifies the database, session identity, effective role, server address, server port, and backend PID. This becomes one of our standard operational checks.

## 1.4.11 `session_user` vs `current_user`

For our current simple lab they should normally match. `session_user` is the identity that initiated the session; `current_user` is the effective identity used for permission checks. Later, `SET ROLE` and role inheritance will make this distinction more important. We defer those details to Part 4 — Users, Roles & Security.

## 1.4.12 Unix-domain socket warning

For a TCP/IP connection, `inet_server_addr()` and `inet_server_port()` identify the PostgreSQL server endpoint. For a Unix-domain socket connection, however, these functions return `NULL`. A `NULL` server address/port therefore does not mean the connection failed.

## 1.4.13 `\conninfo`

Inside `psql`:

```text
\conninfo
```

This displays information about the current connection. PostgreSQL 18 enhanced the presentation and information provided by `\conninfo`, so we intentionally do not depend on a rigid output example from an older release.

## 1.4.14 SQL vs `psql` meta-commands

Compare SQL:

```sql
SELECT current_database();
```

with a `psql` meta-command:

```text
\conninfo
```

SQL is sent to PostgreSQL for server execution. `psql` meta-commands are interpreted by `psql`. Most begin with a backslash.

## 1.4.15 SQL termination

SQL statements normally end with a semicolon:

```sql
SELECT current_database();
```

`psql` meta-commands do not normally use a semicolon:

```text
\conninfo
```

## 1.4.16 Help

```text
\?
```

shows `psql` meta-command help. For SQL help:

```text
\h
```

For a particular SQL statement:

```text
\h CREATE TABLE
```

## 1.4.17 List databases

```text
\l
```

or:

```text
\list
```

You should see databases such as `postgres`, `template0`, `template1`, and `tutorial_db`. Classification: `[SAFE-READ]`. Database/object names can still be sensitive in real environments.

## 1.4.18 Database scope

A normal PostgreSQL connection targets one database. Database selection is part of the connection itself.

## 1.4.19 Change database with `\connect`

Inside `psql`:

```text
\connect postgres
```

or:

```text
\c postgres
```

Validate:

```sql
-- [SAFE-READ]
SELECT current_database();
```

Return:

```text
\c tutorial_db
```

and validate again. `\connect` establishes the new database connection context; it does not leave both ordinary connections simultaneously active in the same simple `psql` workflow.

## 1.4.20 List schemas

```text
\dn
```

Classification: `[SAFE-READ]`. You should normally see `public`.

## 1.4.21 List tables

```text
\dt
```

Part 1.3 created `lab_environment_check`. You can also specify:

```text
\dt public.*
```

Classification: `[SAFE-READ]`.

## 1.4.22 Describe a table

```text
\d lab_environment_check
```

This displays object metadata such as columns, data types, nullability, defaults, and indexes. For additional information:

```text
\d+ lab_environment_check
```

## 1.4.23 List roles

```text
\du
```

You should find `tutorial_admin` and possibly administrative roles such as `postgres`. Roles are cluster-wide, not owned by an individual database.

## 1.4.24 Inspect your backend

```sql
-- [SAFE-READ]
SELECT
    pid,
    usename,
    datname,
    application_name,
    client_addr,
    state
FROM pg_stat_activity
WHERE pid = pg_backend_pid();
```

Visibility into other sessions may depend on privileges. Do not respond to restricted visibility by casually granting yourself superuser or broad monitoring privileges.

## 1.4.25 Diagnostic-output sensitivity

`pg_stat_activity` and similar views may expose database names, role names, application names, client addresses, query text, and wait information. `[SAFE-READ]` does not mean safe to publish. Review and redact production diagnostic output before sharing it outside approved channels.

## 1.4.26 Set `application_name`

```sql
-- [LAB-ONLY — SESSION CHANGE]
SET application_name = 'postgresql-tutorial';
```

Verify:

```sql
-- [SAFE-READ]
SELECT
    pid,
    application_name,
    state
FROM pg_stat_activity
WHERE pid = pg_backend_pid();
```

Meaningful application names make workload identification easier.

## 1.4.27 Execute one SQL command from the shell

```bash
psql \
  -h localhost \
  -p 5432 \
  -U tutorial_admin \
  -d tutorial_db \
  -c "SELECT current_database(), current_user;"
```

This becomes useful for health checks, runbooks, shell scripts, automation, and CI/CD. Output appearing does not prove automation succeeded correctly. Later we will cover process exit status, SQL-error handling, `ON_ERROR_STOP`, and transaction-safe automation.

## 1.4.28 Execute multiple commands

```bash
psql \
  -h localhost \
  -p 5432 \
  -U tutorial_admin \
  -d tutorial_db \
  -c "SELECT current_database();" \
  -c "SELECT current_user;"
```

Useful for small operational checks. Larger validation logic belongs in SQL files.

## 1.4.29 Executing SQL files safely

```bash
psql \
  -h localhost \
  -p 5432 \
  -U tutorial_admin \
  -d tutorial_db \
  -f connection-check.sql
```

Before executing an SQL file: verify the target server, database, and role; review the file; understand whether it changes state; and verify its source. A `.sql` file is executable database logic. Never blindly execute an unknown SQL file merely because it exists in a repository.

## 1.4.30 Execute a file inside `psql`

```text
\i connection-check.sql
```

This executes the contents of the file. Its safety classification depends entirely on the contents of the referenced SQL file.

## 1.4.31 Query timing

Enable:

```text
\timing
```

Run:

```sql
-- [SAFE-READ]
SELECT count(*)
FROM lab_environment_check;
```

Toggle `\timing` again to disable it. `psql` elapsed time is not a complete PostgreSQL performance diagnosis.

## 1.4.32 Expanded output

```text
\x
```

Then run the standard connection identity query. Toggle again with `\x`, or use:

```text
\x auto
```

Expanded output is useful for wide administrative rows.

## 1.4.33 Pager

Inspect:

```text
\pset pager
```

Disable temporarily:

```text
\pset pager off
```

Re-enable:

```text
\pset pager on
```

## 1.4.34 Incomplete SQL

Enter:

```sql
SELECT
    current_database()
```

without the semicolon. The prompt changes because the query is incomplete. Finish with `;`. If `psql` appears to be waiting, check whether your SQL is incomplete.

## 1.4.35 Inspect and reset the query buffer

Start an incomplete statement and print the current query buffer:

```text
\p
```

Reset it:

```text
\r
```

## 1.4.36 Execute the query buffer

Build a query, inspect it with `\p`, then execute it with:

```text
\g
```

A useful safety pattern is: **Build → `\p` → Review → `\g` → Execute**.

## 1.4.37 Transaction-state exercise

`[LAB-ONLY]`

```sql
BEGIN;
SELECT current_database();
ROLLBACK;
```

Observe how the `psql` prompt reflects transaction state. This is only an introduction.

## 1.4.38 Failed transaction exercise

`[LAB-ONLY — INTENTIONAL SQL ERROR]`

```sql
BEGIN;

SELECT column_that_does_not_exist
FROM lab_environment_check;

SELECT current_database();

ROLLBACK;

SELECT current_database();
```

After an error inside an explicit transaction, subsequent SQL cannot proceed normally until the failed transaction is ended. Detailed transaction internals belong in Part 6.

## 1.4.39 Cancel a running query

`[LAB-ONLY — ARTIFICIAL WAIT]`

Never generate artificial long-running work on production or shared environments merely to practice cancellation.

```sql
SELECT pg_sleep(30);
```

While it runs, press `Ctrl+C`. This requests cancellation of the current operation. Validate the session with `SELECT current_database();`.

If an error/cancellation occurs while inside an explicit transaction, the transaction may require `ROLLBACK;` before normal SQL can continue. `Ctrl+C` cancels the operation; it does not stop the PostgreSQL server.

## 1.4.40 Quit `psql`

```text
\q
```

The `psql` connection closes and its associated backend ends; the PostgreSQL server continues running.

## 1.4.41 Understand connection defaults

Explicit connections are easiest to reason about, but `psql` can obtain defaults when parameters are omitted. A database name ultimately often defaults to the database user name, while the user ultimately often defaults to the operating-system user name. This explains errors such as `database "<operating-system-user>" does not exist` without PostgreSQL itself necessarily being unhealthy.

## 1.4.42 Host omitted on Unix-like systems

Compare an explicit `-h localhost` connection with one where the host is omitted. On Unix-like systems, omitting the host normally causes libpq to attempt a Unix-domain socket connection. On Windows, host omission behaves differently and normally results in a local TCP/IP connection.

## 1.4.43 Compare TCP and Unix socket information

Connect explicitly over TCP and run:

```sql
SELECT
    inet_server_addr(),
    inet_server_port();
```

Where supported, compare with a local socket connection. For a Unix-domain socket connection, both functions return `NULL`. That is expected. Use `\conninfo` as additional connection context.

## 1.4.44 Connection environment variables

libpq supports connection defaults such as `PGHOST`, `PGPORT`, `PGDATABASE`, and `PGUSER`.

```bash
# [LAB-ONLY — SHELL CONNECTION DEFAULTS]
export PGHOST=localhost
export PGPORT=5432
export PGDATABASE=tutorial_db
export PGUSER=tutorial_admin
```

Now `psql` can use those values. Inspect locally with:

```bash
env | grep '^PG'
```

Do not automatically paste environment output into tickets or public troubleshooting channels. Real environments may contain sensitive values.

## 1.4.45 Clear connection defaults

```bash
unset PGHOST
unset PGPORT
unset PGDATABASE
unset PGUSER
```

Forgotten environment variables can create an unexpected connection target. If `psql` appears to connect somewhere unexpected, inspect connection defaults before changing the database.

## 1.4.46 Explicit vs implicit connection

For routine personal work, `psql` can be convenient. For troubleshooting or controlled administration, explicit host, port, role, and database parameters reduce ambiguity.

## 1.4.47 Connection failure lab — nonexistent database

`[LAB-ONLY — INTENTIONAL CONNECTION FAILURE]`

```bash
psql \
  -h localhost \
  -p 5432 \
  -U tutorial_admin \
  -d database_that_does_not_exist
```

Capture the exact error. Do not immediately conclude PostgreSQL is down; the requested database may simply not exist.

## 1.4.48 Connection failure lab — unused port

First determine an unused port in the dedicated lab. Do not blindly assume a particular port is free. Then try:

```bash
psql \
  -h localhost \
  -p <unused-lab-port> \
  -U tutorial_admin \
  -d tutorial_db
```

Compare the error with the nonexistent-database error.

## 1.4.49 Connection failure lab — nonexistent role

`[LAB-ONLY — ONE INTENTIONAL FAILURE]`

```bash
psql \
  -h localhost \
  -p 5432 \
  -U role_that_does_not_exist \
  -d tutorial_db
```

Capture the exact response. Do not repeatedly generate authentication failures.

## 1.4.50 Connection failure lab — incorrect password

Using `tutorial_admin`, enter one incorrect **lab** password. Observe the exact error, stop, and reconnect using the correct lab credential. Do not turn this exercise into repeated password attempts.

## 1.4.51 Interpret connection failures from evidence

Do not assume an authentication message always means a wrong password. Use: **Connection failed → Capture exact error → Identify likely layer → Gather supporting evidence → Determine cause**.

## 1.4.52 Connection troubleshooting workflow

Start with:

```text
Host
 ↓
Port
 ↓
Reachability
 ↓
PostgreSQL response
 ↓
Database
 ↓
Role
 ↓
Authentication
 ↓
pg_hba.conf
```

Later environments add DNS, TLS, firewalls, security groups, proxies, load balancers, connection pools, Kubernetes networking, and cloud identity.

## 1.4.53 Two simultaneous `psql` sessions

Open Terminal A and connect to the lab. Run:

```sql
SELECT pg_backend_pid();
```

Record the PID. Open Terminal B, connect identically, and run the same query. The backend PIDs should normally differ.

## 1.4.54 Understand the two-session architecture

```text
Terminal A → psql A → Backend A
Terminal B → psql B → Backend B
```

This directly demonstrates the process-per-connection architecture introduced in Part 1.2.

## 1.4.55 Observe both sessions

From Terminal A:

```sql
-- [SAFE-READ]
SELECT
    pid,
    datname,
    usename,
    application_name,
    client_addr,
    state
FROM pg_stat_activity
WHERE datname = 'tutorial_db'
ORDER BY pid;
```

Locate both sessions.

## 1.4.56 Close one session

In Terminal B run `\q`. Return to Terminal A and rerun the activity query. The backend associated with Terminal B should disappear. The client closes, its connection closes, and the associated backend ends while PostgreSQL continues serving other sessions.

## 1.4.59 Final hands-on challenge

Without looking at the cheat sheet, connect to `localhost:5432`, database `tutorial_db`, role `tutorial_admin`. Determine the client version, server version, current database, session user, effective role, connection context, server address/port, backend PID, available databases/schemas/tables, the definition of `lab_environment_check`, and current connection information.

## 1.4.61 Production habits established

- Never assume the client version equals the server version.
- Never trust the prompt as the only environment check.
- Never assume a local connection is TCP.
- Never treat `NULL` `inet_server_addr()` as automatic failure.
- Never put passwords directly into tutorial commands.
- Never blindly execute an unknown SQL file.
- Never assume read-only diagnostic output is safe to publish.
- Never interpret every connection failure as a server outage.
- Never repeatedly generate authentication failures.
- Never leave forgotten `PG*` connection defaults in your shell.
- Never troubleshoot by randomly changing connection parameters.
- Always identify host, port, database, and role.
- Always verify the target before changing state.
- Always capture the exact error before attempting a fix.
- Always distinguish SQL from `psql` meta-commands.
- Always correlate client sessions with PostgreSQL backends when useful.

## 1.4.62 Completion checklist

You should now be able to explain what `psql` is; distinguish client/server versions; connect explicitly; understand connection defaults; identify database, role, and backend PID; distinguish `session_user` and `current_user`; understand TCP vs Unix-domain sockets; use core `psql` navigation and query-buffer commands; inspect `pg_stat_activity`; execute reviewed SQL commands/files; recognize and recover from failed transaction state; cancel a lab query; safely use and clear non-secret `PG*` connection defaults; diagnose controlled connection failures; correlate multiple `psql` sessions with backend processes; and run the reusable `connection-check.sql` validation artifact.
