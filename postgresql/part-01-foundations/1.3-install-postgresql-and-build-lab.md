# Part 1.3 — Install PostgreSQL and Build the Hands-On Lab Environment

## Revised Final / Canonical Edition

**Tutorial target:** PostgreSQL 18  
**Documentation baseline:** PostgreSQL 18.x  
**Lab model:** Native Linux primary + Docker alternative

This section builds the PostgreSQL environment used throughout the practical tutorial. The objective is not merely to install PostgreSQL. We will learn to **install → identify → connect → validate → create → write → restart → break → diagnose → recover** the environment.

## 1.3.1 Learning objectives

By the end of this section, you should be able to:

- distinguish PostgreSQL client tools from the PostgreSQL server;
- install PostgreSQL in a dedicated Linux lab;
- identify PostgreSQL processes, ports, configuration files, and data directories;
- validate PostgreSQL using multiple layers rather than relying only on service status;
- connect with `psql`;
- create a dedicated tutorial role and database;
- perform a basic read/write/transaction test;
- restart PostgreSQL and verify persistence;
- create an alternative PostgreSQL 18 Docker lab;
- deliberately stop the lab server, diagnose the failure, and recover it;
- apply basic production, credential, and repository-safety practices.

## 1.3.2 Safety convention

From this section onward, tutorial commands use four operational labels.

- `[SAFE-READ]` — observational or read-only operation.
- `[LAB-ONLY]` — changes state or intentionally creates workload in the dedicated tutorial environment.
- `[PRODUCTION-CAUTION]` — could affect availability, performance, configuration, security, workload, or data in production.
- `[DESTRUCTIVE]` — could permanently remove, replace, initialize, or destroy data/resources if used incorrectly.

A command may carry more than one classification. Do not use production, staging, shared development, customer, or company database environments for these labs.

## 1.3.5 PostgreSQL version policy

This tutorial targets PostgreSQL major version 18 with a PostgreSQL 18.x documentation baseline. Before building a real production environment, always verify the currently supported minor release and platform-specific installation guidance.

## 1.3.6 Inspect the operating system

```bash
# [SAFE-READ]
cat /etc/os-release
```

Record the distribution, version, and architecture. Installation procedures differ across Linux families. Never blindly execute package instructions written for another distribution.

## 1.3.7 Check whether PostgreSQL already exists

```bash
# [SAFE-READ]
psql --version
postgres --version
```

`psql` is the PostgreSQL client. `postgres` is the server executable. It is possible to have the client installed without the server.

## 1.3.8 Check for existing PostgreSQL processes

```bash
# [SAFE-READ]
ps -ef | grep '[p]ostgres'
```

Do not stop or modify an unfamiliar PostgreSQL process. Determine who owns it, which version and data directory it uses, which port it uses, and whether another application depends on it.

## 1.3.9 Check port 5432

```bash
# [SAFE-READ]
ss -ltn | grep ':5432'
```

A listener on port 5432 does not prove PostgreSQL is fully healthy. We validate several layers below.

## 1.3.10 Native Linux — Ubuntu/Debian

Distribution repositories can provide PostgreSQL directly:

```bash
# [LAB-ONLY]
sudo apt update
sudo apt install postgresql postgresql-client
```

The supplied major version may differ from this tutorial. For a PostgreSQL 18-specific lab, use the current official PostgreSQL PGDG repository procedure for your supported Ubuntu/Debian release and install PostgreSQL 18. Validate afterward with `psql --version`.

The tutorial intentionally avoids embedding a distribution codename that could become stale.

## 1.3.11 Native Linux — RHEL/Rocky/AlmaLinux

The workflow is:

```text
Configure PostgreSQL Yum repository
             ↓
Install PostgreSQL 18 packages
             ↓
Initialize database cluster
             ↓
Enable service
             ↓
Start service
             ↓
Validate PostgreSQL
```

Use PostgreSQL's current official Red Hat-family repository instructions for the exact OS release, architecture, and PostgreSQL major version. Do not copy an RPM repository URL from another Linux release.

## 1.3.12 Installation is not initialization

Installing PostgreSQL makes binaries and utilities such as `postgres`, `psql`, and `initdb` available. Initializing PostgreSQL creates a new database cluster, including its data directory, system catalogs, configuration, template databases, and initial `postgres` database.

At the PostgreSQL level, initialization uses `initdb`. PostgreSQL 18 enables data checksums by default when `initdb` creates a new cluster.

## 1.3.13 `initdb` safety

`[LAB-ONLY] [PRODUCTION-CAUTION] [DESTRUCTIVE IF MISUSED]`

Never casually execute `initdb`. Before initialization, verify that the target directory is intended for a new cluster, is not an existing PostgreSQL data directory, no existing instance depends on it, the correct OS account owns the cluster, and you understand which storage will be initialized.

Do not run `initdb` as root. Do not use `initdb` as a repair operation for an existing PostgreSQL cluster.

## 1.3.14 Discover the PostgreSQL service

```bash
# [SAFE-READ]
systemctl list-unit-files | grep -i postgres
systemctl list-units --type=service | grep -i postgres
```

Identify the actual unit for your installation. We represent it as `<postgresql-service>`.

## 1.3.15 Service operations

```bash
# [SAFE-READ]
sudo systemctl status <postgresql-service>
```

```bash
# [LAB-ONLY] [PRODUCTION-CAUTION]
sudo systemctl start <postgresql-service>
sudo systemctl stop <postgresql-service>
sudo systemctl restart <postgresql-service>
sudo systemctl enable <postgresql-service>
```

Never restart production PostgreSQL merely to determine whether an unexplained problem disappears. Collect evidence first.

## 1.3.16 Validation layer 1 — process

```bash
# [SAFE-READ]
ps -ef | grep '[p]ostgres'
```

This verifies that PostgreSQL processes exist. It does not prove the database is fully usable.

## 1.3.17 Validation layer 2 — listener

```bash
# [SAFE-READ]
ss -ltnp | grep ':5432'
```

A listener exists does not mean an application can successfully use PostgreSQL.

## 1.3.18 Validation layer 3 — `pg_isready`

```bash
# [SAFE-READ]
pg_isready -h localhost -p 5432
```

`pg_isready` checks PostgreSQL server connection status. It does not prove application queries, permissions, schema, replication, storage, or performance are healthy.

## 1.3.19 Validation layer 4 — execute SQL

For many native Linux package installations:

```bash
# [LAB-ONLY]
sudo -u postgres psql
```

Then:

```sql
-- [SAFE-READ]
SELECT version();
SELECT current_database();
SELECT current_user;
SELECT pg_backend_pid();
```

This validates the path from OS and PostgreSQL processes through listener, connection, authentication, backend, and SQL execution.

## 1.3.20 Verify the target before making changes

Before state-changing administration:

```sql
-- [SAFE-READ]
SELECT
    current_database(),
    current_user,
    inet_server_addr(),
    inet_server_port(),
    pg_backend_pid();

SHOW data_directory;
```

A correct command executed against the wrong server can cause an incident. The `psql` prompt is useful context, but explicit verification is stronger.

## 1.3.21 Discover the actual PostgreSQL paths

Do not guess:

```sql
-- [SAFE-READ]
SHOW data_directory;
SHOW config_file;
SHOW hba_file;
SHOW ident_file;
```

Record the data directory, `postgresql.conf`, `pg_hba.conf`, and `pg_ident.conf`. Ask the running PostgreSQL server rather than assuming package-specific paths.

## 1.3.22 What these files do

- `postgresql.conf` — server configuration.
- `pg_hba.conf` — client authentication rules.
- `pg_ident.conf` — user-name mapping.

We modify them safely in a later section.

## 1.3.23 Inspect runtime configuration

```sql
-- [SAFE-READ]
SHOW port;
SHOW listen_addresses;
SHOW max_connections;
SHOW shared_buffers;
```

The objective is inspection, not tuning. Do not interpret `SHOW max_connections` as an invitation to increase it.

## 1.3.24 Create the tutorial role

Use the privileged administrative account only for administrative work:

```sql
-- [LAB-ONLY]
CREATE ROLE tutorial_admin LOGIN;
```

Set the password interactively in `psql`:

```text
\password tutorial_admin
```

PostgreSQL roles are cluster-wide; `tutorial_admin` does not belong exclusively to one database.

## 1.3.25 Credential safety

Never commit real credentials into Git repositories, Markdown tutorials, SQL files, shell scripts, screenshots, tickets, CI logs, or chat messages.

Use placeholders:

```text
DB_HOST=localhost
DB_PORT=5432
DB_NAME=tutorial_db
DB_USER=tutorial_admin
DB_PASSWORD=<retrieve-securely>
```

Do not use production credentials for this tutorial.

## 1.3.26 Create the tutorial database

```sql
-- [LAB-ONLY]
CREATE DATABASE tutorial_db
OWNER tutorial_admin;
```

Validate:

```sql
-- [SAFE-READ]
SELECT
    datname,
    datdba::regrole AS owner
FROM pg_database
WHERE datname = 'tutorial_db';
```

## 1.3.27 Connect as the tutorial role

Exit the administrative session with `\q`, then:

```bash
psql \
  -h localhost \
  -p 5432 \
  -U tutorial_admin \
  -d tutorial_db
```

Allow `psql` to prompt for the password. Do not put it directly into the command.

```sql
-- [SAFE-READ]
SELECT
    current_database(),
    current_user,
    pg_backend_pid();
```

## 1.3.28 Create the first persistent lab table

```sql
-- [LAB-ONLY]
CREATE TABLE lab_environment_check (
    check_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    message text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT current_timestamp
);

INSERT INTO lab_environment_check (message)
VALUES ('PostgreSQL tutorial environment is working');
```

Read it:

```sql
-- [SAFE-READ]
SELECT *
FROM lab_environment_check;
```

## 1.3.29 Basic transaction validation

```sql
-- [LAB-ONLY]
BEGIN;

INSERT INTO lab_environment_check (message)
VALUES ('transaction rollback test');
```

Observe with `SELECT * FROM lab_environment_check;`, then:

```sql
-- [LAB-ONLY]
ROLLBACK;
```

Query again. The rollback-test row should no longer be visible. Transaction internals come later.

## 1.3.30 Restart and persistence test

Before restarting:

```sql
-- [SAFE-READ]
SELECT count(*)
FROM lab_environment_check;
```

Exit `psql`, then on the dedicated lab server only:

```bash
# [LAB-ONLY] [PRODUCTION-CAUTION]
sudo systemctl restart <postgresql-service>
```

Validate and reconnect:

```bash
# [SAFE-READ]
pg_isready -h localhost -p 5432

psql -h localhost -p 5432 -U tutorial_admin -d tutorial_db
```

```sql
-- [SAFE-READ]
SELECT *
FROM lab_environment_check;
```

The committed row should remain. Restart persistence is not equivalent to backup/recovery testing; backup, restore, and PITR receive dedicated labs later.

## 1.3.31 Docker alternative

Check Docker:

```bash
# [SAFE-READ]
docker version
```

Create a named volume:

```bash
# [LAB-ONLY]
docker volume create postgres_tutorial_data
```

The host exposes only `localhost:5432`, which maps to the PostgreSQL 18 container backed by the `postgres_tutorial_data` volume.

## 1.3.32 PostgreSQL 18 Docker storage layout

For the official PostgreSQL 18 container image, mount persistent storage at:

```text
/var/lib/postgresql
```

Do not teach the older PostgreSQL 17-and-earlier `/var/lib/postgresql/data` volume target as the PostgreSQL 18 default.

## 1.3.33 Start PostgreSQL 18 in Docker

```bash
# [LAB-ONLY — DEMONSTRATION CREDENTIAL]
docker run -d \
  --name postgres-tutorial \
  -e POSTGRES_USER=tutorial_admin \
  -e POSTGRES_PASSWORD='REPLACE_WITH_LAB_PASSWORD' \
  -e POSTGRES_DB=tutorial_db \
  -p 127.0.0.1:5432:5432 \
  -v postgres_tutorial_data:/var/lib/postgresql \
  postgres:18
```

Binding to `127.0.0.1:5432` keeps the default tutorial listener local to the workstation instead of deliberately publishing it on every host interface. The inline environment-variable password is acceptable only for this isolated disposable lab; it is not a production secret-management design.

## 1.3.34 Understand Docker initialization variables

`POSTGRES_USER`, `POSTGRES_PASSWORD`, and `POSTGRES_DB` are initialization settings. With an empty persistent volume, container startup initializes the cluster and creates the configured user/database. Once persistent storage contains an initialized cluster, restarting the container does not recreate the database from these settings.

## 1.3.35 Validate Docker PostgreSQL

```bash
# [SAFE-READ]
docker ps
docker logs postgres-tutorial

docker exec postgres-tutorial \
  pg_isready -U tutorial_admin -d tutorial_db

docker exec postgres-tutorial \
  psql -U tutorial_admin -d tutorial_db \
  -c "SELECT version();"
```

Treat database logs as potentially sensitive. Do not publish production logs without review/redaction.

## 1.3.36 Docker persistence test

```bash
# [LAB-ONLY]
docker stop postgres-tutorial
docker start postgres-tutorial
```

Validate:

```bash
# [SAFE-READ]
docker exec postgres-tutorial \
  pg_isready -U tutorial_admin -d tutorial_db
```

Container lifecycle and persistent database storage are different concepts. We deliberately do not delete the Docker volume in this section.

## 1.3.37 Avoid `latest`

Do not build the tutorial around `postgres:latest`. Use `postgres:18` to pin the tutorial to the major version being taught. Later CI/CD and production deployment sections discuss controlled minor versions and image digests.

## 1.3.38 Baseline PostgreSQL health check

```sql
-- [SAFE-READ]
SELECT version();
SELECT current_database();
SELECT current_user;
SELECT pg_backend_pid();
SHOW port;
SHOW data_directory;
SHOW config_file;
SHOW hba_file;
SHOW max_connections;
```

Then:

```sql
-- [SAFE-READ]
SELECT
    pid,
    backend_type,
    datname,
    usename,
    application_name,
    state
FROM pg_stat_activity
ORDER BY backend_type, pid;
```

Session metadata can contain operational information. Treat production diagnostic output appropriately.

## 1.3.40 Intentional failure exercise

`[LAB-ONLY — INTENTIONAL OUTAGE]`

Never perform this exercise against production, staging, shared development, CI infrastructure, or another person's PostgreSQL environment.

```bash
# [LAB-ONLY] [PRODUCTION-CAUTION]
sudo systemctl stop <postgresql-service>
```

Then observe:

```bash
# [SAFE-READ]
pg_isready -h localhost -p 5432
```

Attempt:

```bash
psql -h localhost -p 5432 -U tutorial_admin -d tutorial_db
```

Observe the failure.

## 1.3.41 Diagnose the outage

Do not immediately start PostgreSQL. First gather evidence:

```bash
# [SAFE-READ]
sudo systemctl status <postgresql-service>
ps -ef | grep '[p]ostgres'
ss -ltn | grep ':5432'
pg_isready -h localhost -p 5432
```

The first troubleshooting chain is: **Symptom → Service → Process → Listener → PostgreSQL readiness → Connection**.

## 1.3.42 Recover PostgreSQL

```bash
# [LAB-ONLY] [PRODUCTION-CAUTION]
sudo systemctl start <postgresql-service>
```

Validate:

```bash
# [SAFE-READ]
pg_isready -h localhost -p 5432
```

Reconnect and verify:

```bash
psql -h localhost -p 5432 -U tutorial_admin -d tutorial_db
```

```sql
-- [SAFE-READ]
SELECT current_timestamp;
SELECT * FROM lab_environment_check;
```

We have completed **Build → Validate → Break → Observe → Diagnose → Recover → Validate**.

## 1.3.43 Troubleshooting principle

Never assume an application connection failure means PostgreSQL is down. Investigate layer by layer: application → hostname/DNS → network → port/listener → PostgreSQL process → server readiness → authentication → database → role/privilege.

This develops into the tutorial's full production methodology:

**Symptom → Evidence → Diagnostic SQL → Root Cause → Immediate Mitigation → Permanent Fix → Validation → Prevention**

## 1.3.44 Tutorial data safety

All tutorial data must be synthetic. Never use real patient information, customer records, production exports, production credentials, cloud tokens, private keys, certificates, real access tokens, or sensitive internal endpoints.

Later healthcare examples may use tables such as `patients`, `providers`, and `appointments`, but every sample record must be fictional.

## 1.3.45 Production habits established in this lab

- Never guess which PostgreSQL server you are modifying.
- Never restart production as a troubleshooting experiment.
- Never run `initdb` casually.
- Never assume an open 5432 port means PostgreSQL is healthy.
- Never guess data/configuration paths.
- Never blindly increase `max_connections`.
- Never commit credentials.
- Never expose a database listener unnecessarily.
- Never use production data in tutorial labs.
- Always gather evidence before changing state.
- Always validate after a change.
- Always distinguish process availability from database health.
- Always know how to recover from the change you are making.

## 1.3.46 Final validation

Inside PostgreSQL:

```sql
-- [SAFE-READ]
SELECT
    version(),
    current_database(),
    current_user,
    pg_backend_pid();

SELECT *
FROM lab_environment_check;
```

Outside PostgreSQL:

```bash
# [SAFE-READ]
pg_isready -h localhost -p 5432
sudo systemctl status <postgresql-service>
ps -ef | grep '[p]ostgres'
```

The complete validation chain is: **Host/Container → PostgreSQL Process → Listener → pg_isready → Authentication → Database Connection → SQL Execution → DDL/Write/Read → Transaction → Restart → Persistence → Failure → Diagnosis → Recovery**.

## 1.3.47 Completion checklist

You should now be able to identify the PostgreSQL client/server and major version; understand installation versus initialization and `initdb` risk; discover PostgreSQL systemd services, processes, listeners, and configuration paths; use `pg_isready` and `psql`; verify the connection target; create a cluster-wide login role and database; perform DDL/DML and a basic transaction; restart the lab and verify persistence; build a PostgreSQL 18 Docker lab with the correct persistence layout and localhost binding; intentionally create and diagnose a lab outage; recover PostgreSQL; and apply credential and production-safety practices.
