## 1.12.1 Why PostgreSQL Processes Matter

When an application connects to PostgreSQL, executes SQL, performs maintenance, writes WAL, checkpoints data, or runs autovacuum, PostgreSQL server processes perform the work. Understanding these processes is fundamental to database administration, performance and connection troubleshooting, incident response, observability, capacity planning, transaction investigation, lock/wait analysis, and maintenance troubleshooting.

Part 1.12 focuses on observation. It does not terminate processes, cancel queries, restart PostgreSQL, or change server configuration.

## 1.12.2 PostgreSQL Is a Client/Server System

PostgreSQL follows a client/server architecture. Clients can include `psql`, applications, Python/Java services, ETL pipelines, BI tools, and administration tools. Clients connect over TCP/IP or Unix-domain sockets and PostgreSQL performs database work on their behalf.

## 1.12.3 The Primary Server Process

A PostgreSQL instance starts with a primary server process running the `postgres` executable. You may also encounter the historical term `postmaster`. This tutorial prefers **primary server process**. Do not confuse the primary server process with an individual client backend; interfering with the primary process can have dramatically broader impact.

## 1.12.4 One Client Connection, One Backend

A normal PostgreSQL client connection is handled by a server backend process. This process-per-connection model has implications for connection capacity, memory, CPU scheduling, operating-system resources, and connection pooling.

## 1.12.5 Find Your Backend PID

```sql
SELECT pg_backend_pid();
```

The returned PID identifies the PostgreSQL backend associated with the current session.

## 1.12.6 Inspect Your Current Backend

```sql
SELECT
    pid,
    usename,
    datname,
    application_name,
    client_addr,
    backend_start,
    state,
    wait_event_type,
    wait_event,
    backend_type
FROM pg_stat_activity
WHERE pid = pg_backend_pid();
```

## 1.12.7 pg_stat_activity

`pg_stat_activity` is one of PostgreSQL's most important operational views. Useful columns include `datname`, `pid`, `leader_pid`, `usename`, `application_name`, `client_addr`, `backend_start`, `xact_start`, `query_start`, `state_change`, `wait_event_type`, `wait_event`, `state`, `backend_xid`, `backend_xmin`, `query_id`, `query`, and `backend_type`.

Select only the columns needed to answer the operational question.

## 1.12.8 Monitoring Visibility and Privileges

Not every role necessarily sees the same level of activity information for every session. Limited activity detail does not mean PostgreSQL monitoring is broken. Check monitoring privileges before drawing that conclusion.

## 1.12.9 Query Text Can Be Sensitive

`pg_stat_activity.query` is valuable diagnostic evidence but can contain literal values, customer identifiers, application parameters, or other sensitive information. Do not casually copy complete production query text into Slack, Jira, email, screenshots, public documentation, or external support cases. Redact sensitive information before sharing evidence.

## 1.12.10 Inspect Backend Types

```sql
SELECT
    backend_type,
    COUNT(*) AS process_count
FROM pg_stat_activity
GROUP BY backend_type
ORDER BY backend_type;
```

The exact backend types depend on the environment and workload. Do not assume an unfamiliar PostgreSQL process is abnormal; identify it first.

## 1.12.11 Client Backend

A normal `psql` or application connection is typically represented as `client backend`.

```sql
SELECT
    pid,
    backend_type,
    usename,
    datname,
    state
FROM pg_stat_activity
WHERE pid = pg_backend_pid();
```

## 1.12.12 PostgreSQL Session States

Client backends can appear in states including `active`, `idle`, `idle in transaction`, `idle in transaction (aborted)`, and `disabled`. Session state is not a direct measurement of CPU utilization.

## 1.12.13 active

An `active` backend is executing a query, but `state = 'active'` does not necessarily mean it is currently consuming CPU.

```sql
SELECT
    pid,
    usename,
    datname,
    state,
    query_start,
    wait_event_type,
    wait_event
FROM pg_stat_activity
WHERE state = 'active'
ORDER BY query_start;
```

## 1.12.14 State and Wait Events Must Be Read Together

A valid situation is `state = 'active'` with `wait_event IS NOT NULL`. An active query can currently be waiting. Correlate `state`, `wait_event_type`, and `wait_event` instead of interpreting state alone.

## 1.12.15 idle

An idle backend still exists and is connected, but is waiting for another client command outside a transaction. Idle does not mean no backend or zero resource footprint.

## 1.12.16 idle in transaction

`idle in transaction` means a transaction remains open while the client is currently not executing a query. Long-lived open transactions can create operational problems. Part 1.12 does not intentionally create a persistent idle-in-transaction session.

## 1.12.17 Connection, Transaction, and Query Age

`backend_start`, `xact_start`, `query_start`, and `state_change` answer different questions. Connection age, transaction age, and query age are not equivalent.

## 1.12.18 Inspect Transaction Age

```sql
SELECT
    pid,
    usename,
    datname,
    state,
    xact_start,
    now() - xact_start AS transaction_age
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

A backend can have a short current query inside an old transaction. Do not use query duration alone to characterize transaction behavior.

## 1.12.19 Do Not Use an Arbitrary Old = Bad Rule

Do not automatically terminate a transaction because it exceeds an arbitrary duration. Correlate transaction age, session state, wait events, query context, blocking relationships, and application behavior before considering intervention.

## 1.12.20 Wait Events

```sql
SELECT
    pid,
    usename,
    state,
    wait_event_type,
    wait_event
FROM pg_stat_activity
WHERE wait_event IS NOT NULL
ORDER BY pid;
```

Wait information helps determine whether a backend is waiting and what category of event it is waiting on. Detailed wait-event diagnosis belongs in later performance tutorials.

## 1.12.21 Inspect Long-Running Active Queries Safely

```sql
SELECT
    pid,
    usename,
    datname,
    application_name,
    now() - query_start AS query_age,
    state,
    wait_event_type,
    wait_event
FROM pg_stat_activity
WHERE state = 'active'
  AND pid <> pg_backend_pid()
ORDER BY query_start;
```

This introductory query intentionally omits full query text. Retrieve it only when needed and handle it appropriately.

## 1.12.22 Background PostgreSQL Processes

PostgreSQL performs internal work including checkpoints, background buffer writing, WAL writing, autovacuum, replication, and background-worker activity. These are normal parts of PostgreSQL operation.

## 1.12.23 Checkpointer

The checkpointer coordinates checkpoint-related activity. Detailed checkpoint behavior, WAL recovery, storage impact, and tuning are deferred to later tutorials.

## 1.12.24 Background Writer

The background writer periodically writes selected dirty shared buffers so reusable clean buffers are more likely to be available when server processes need them. The background writer and checkpointer have related but distinct responsibilities.

## 1.12.25 WAL Writer

The WAL writer participates in writing WAL buffers. It should not be interpreted as the only mechanism involved in every WAL flush. Detailed WAL durability mechanics belong later.

## 1.12.26 Autovacuum Launcher and Workers

The autovacuum launcher coordinates autovacuum work and workers perform maintenance. Autovacuum is enabled by default and operationally important because it automates `VACUUM` and `ANALYZE` work needed for healthy operation. Seeing an autovacuum worker does not mean it should automatically be terminated. Interfering with autovacuum without understanding the workload can contribute to dead tuples, bloat, stale statistics, transaction-ID aging, and maintenance backlog.

## 1.12.27 Background Workers

PostgreSQL and extensions can use background workers for specialized tasks. An unfamiliar PostgreSQL process is not automatically a process that should be killed. Identify its `backend_type`, purpose, subsystem, and current activity first.

## 1.12.28 Operating-System Inspection

On self-managed PostgreSQL hosts, OS process inspection may be available:

```bash
ps -ef | grep '[p]ostgres'
```

or:

```bash
ps aux | grep '[p]ostgres'
```

Output varies by operating system, packaging, containerization, service manager, and PostgreSQL version.

## 1.12.29 Managed PostgreSQL Services

Managed PostgreSQL services generally do not provide the same host-level process administration as self-managed servers. SQL-level observability such as `pg_stat_activity`, combined with provider-specific monitoring, remains important.

## 1.12.30 Never Treat kill -9 as Routine Backend Management

Discovering a PostgreSQL PID does not make `kill -9 <pid>` a routine database-management procedure. Use PostgreSQL-aware procedures with authorization and impact understood when intervention is actually required. This tutorial performs no OS-level termination.

## 1.12.31 Query Cancellation vs Session Termination

`pg_cancel_backend(pid)` requests cancellation of the current query and the session normally remains. `pg_terminate_backend(pid)` requests termination of the backend/session and ends the connection. Part 1.12 executes neither function.

## 1.12.32 PostgreSQL 18 Termination Timeout

PostgreSQL 18 supports `pg_terminate_backend(pid, timeout)`, where timeout is expressed in milliseconds. This is an advanced operational capability and is mentioned only for awareness; it is not used in this lab.

## 1.12.33 Backend Signaling Requires Authorization

Cancellation and termination are privilege-controlled. The ability to observe a PID does not mean the current role should or can signal that backend.

## 1.12.34 Revalidate a PID Before Future Intervention

PIDs are not permanent database-session identities. Do not take an old PID from a ticket, Slack message, screenshot, old query result, or incident note and assume it still represents the same backend. Revalidate `pid`, `backend_start`, `usename`, `datname`, `application_name`, state, and query context before any future intervention.

## 1.12.35 Count Client Connections

```sql
SELECT COUNT(*) AS client_backend_count
FROM pg_stat_activity
WHERE backend_type = 'client backend';
```

Connection count is not active-query count.

## 1.12.36 Group Connections by Database

```sql
SELECT
    datname,
    COUNT(*) AS connection_count
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY datname
ORDER BY connection_count DESC, datname;
```

## 1.12.37 Group Client Backends by State

```sql
SELECT
    state,
    COUNT(*) AS session_count
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY state
ORDER BY state;
```

## 1.12.38 Group Connections by Application

```sql
SELECT
    application_name,
    COUNT(*) AS connection_count
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY application_name
ORDER BY connection_count DESC, application_name;
```

Meaningful `application_name` values make production troubleshooting easier.

## 1.12.39 PostgreSQL 18 Per-Backend I/O — Forward Reference

PostgreSQL 18 provides additional per-backend I/O observability. Detailed correlation of backend, query, waits, CPU, I/O, locks, and WAL belongs in later performance material.

## 1.12.40 Hands-On Process Inspection Lab

Identify your backend:

```sql

```

Inspect it:

```sql
SELECT
    pid,
    usename,
    datname,
    application_name,

```

Inspect backend types, client states, open transaction ages, and wait events using the read-only queries introduced above.

## 1.12.41 Production Monitoring Discipline

Even read-only diagnostics should be proportional to the question. Retrieve only needed columns, avoid unnecessary full query text, and avoid unnecessarily high-frequency polling.

## 1.12.42 Production Safety Boundary

Part 1.12 performs observation only. It does not execute `pg_cancel_backend()`, `pg_terminate_backend()`, `kill`, `kill -9`, service restarts, `ALTER SYSTEM`, or configuration changes. It does not intentionally manufacture blocking locks, connection storms, long transactions, idle-in-transaction incidents, or autovacuum interruption.

## 1.12.43 What You Should Know Now

You should understand the primary server process, client backend, PID, `pg_backend_pid()`, `pg_stat_activity`, `backend_type`, session states, activity timestamps, wait events, checkpointer, background writer, WAL writer, and autovacuum launcher/workers.

Key distinctions are: process existence does not mean CPU-bound; active does not necessarily mean running on CPU; waiting does not mean idle; idle does not mean zero resource footprint; query age differs from transaction age; connection count differs from active-query count; and an observable PID is not automatically a safe termination target.

## 1.12.44 Operational Decision Model

Use: **Observe → Identify → Correlate → Understand → Assess impact → Only then consider intervention.** Do not use “see old/active PID → terminate” as an incident-response model.
