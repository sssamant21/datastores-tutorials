# Part 1.2 — PostgreSQL Architecture Fundamentals
## Client, Server, Connections, and Processes

Part 1.1 established what PostgreSQL is and introduced databases, schemas, tables, clients, and basic server inspection. We will now move one level deeper and understand **what happens when a client connects to PostgreSQL and executes SQL**.

This is still a fundamentals section. We intentionally defer shared-buffer internals, WAL internals, MVCC, VACUUM, detailed locking, checkpoints, replication, and query-planner internals until their dedicated sections.

## 1.2.1 Lab safety convention

From this section forward, commands may carry one of three operational labels:

- `[SAFE-READ]` — observational/read-only command that normally does not change database state.
- `[LAB-ONLY]` — exercise that intentionally creates activity or changes state; use the tutorial environment rather than production.
- `[PRODUCTION-CAUTION]` — operation that can affect workload, availability, configuration, data, or other sessions and requires production assessment.

These labels are guidance rather than a substitute for understanding your own environment, permissions, workload, and organizational controls.

> **Lab safety:** Perform workload-generation exercises in the dedicated tutorial environment. Do not intentionally create sleeping sessions, long-running transactions, connection storms, blocking, deadlocks, or other artificial workloads on production systems.

## 1.2.2 Fundamental PostgreSQL architecture

```text
Client (psql / Python / application)
        |
        | Connection
        v
PostgreSQL Server
        |
        v
Database
```

The client sends requests. PostgreSQL processes those requests and returns results.

```sql
SELECT * FROM patients;
```

The client/server relationship is the foundation of PostgreSQL architecture.

## 1.2.3 PostgreSQL clients

Clients can include `psql`, Python, Java, Go, Node.js applications, ETL pipelines, BI platforms, monitoring systems, migration tools, administration tools, and connection poolers. They may use different drivers and libraries, but ultimately communicate with PostgreSQL through its frontend/backend protocol.

## 1.2.4 PostgreSQL server vs database

A PostgreSQL server/database cluster can manage multiple databases:

```text
PostgreSQL Server
├── postgres
├── healthcare_db
├── billing_db
└── analytics_db
```

These are multiple databases managed by the same PostgreSQL server, not four PostgreSQL servers.

## 1.2.5 PostgreSQL "cluster" terminology

In core PostgreSQL terminology, a database cluster is a collection of databases managed by a PostgreSQL server and associated with a data directory. This does not inherently mean multiple PostgreSQL machines. Replicated primary/standby systems are a separate architectural concept introduced later.

## 1.2.6 PostgreSQL operating-system processes

On a self-managed server, a simplified process model is:

```text
Operating System
└── PostgreSQL
    ├── Supervisor postgres process
    ├── Client backend processes
    ├── Auxiliary/background processes
    └── Other workers as required
```

The main server process supervises PostgreSQL and accepts incoming connection requests. You may also encounter the historical/common term `postmaster` for this supervising process. This tutorial primarily uses **supervisor `postgres` process**.

## 1.2.7 PostgreSQL listens for connections

A client can connect over TCP/IP:

```bash
psql -h 10.10.20.15 -p 5432 -U app_user -d healthcare_db
```

PostgreSQL normally defaults to TCP port `5432`, but never assume the port in an unfamiliar environment.

```sql
-- [SAFE-READ]
SHOW port;
```

## 1.2.8 TCP/IP vs Unix-domain sockets

Remote connections commonly use TCP/IP. On Unix-like systems, a local client can use a Unix-domain socket. For example, `psql -d postgres` may use a Unix-domain socket when no host is specified, depending on platform and client configuration.

This distinction becomes important when troubleshooting connectivity and `pg_hba.conf`.

## 1.2.9 Inspect the current connection endpoint

```sql
-- [SAFE-READ]
SELECT inet_server_addr(), inet_server_port();
```

For a TCP/IP connection, PostgreSQL can return the server address and port. For a Unix-domain socket connection, these functions can return `NULL`; that does not automatically indicate a broken connection.

## 1.2.10 What happens when a client connects?

At a simplified level:

```text
Client starts
  -> Connection request
  -> PostgreSQL receives request
  -> Authentication
  -> Session/backend established
  -> Client sends SQL
  -> PostgreSQL returns results
```

The backend process is central to PostgreSQL architecture.

## 1.2.11 Process-per-connection architecture

Traditional PostgreSQL uses a process-per-connection architecture:

```text
Client 1 -> Backend Process 1
Client 2 -> Backend Process 2
Client 3 -> Backend Process 3
```

Two `psql` sessions can access the same server while having different server-side backend processes.

## 1.2.12 Find your backend PID

```sql
-- [SAFE-READ]
SELECT pg_backend_pid();
```

`pg_backend_pid()` returns the process ID of the PostgreSQL server process attached to the current session.

## 1.2.13 Why backend PIDs matter

If OS monitoring identifies a busy PostgreSQL PID, correlate it with PostgreSQL activity:

```sql
-- [SAFE-READ]
SELECT pid, usename, datname, application_name, state, query
FROM pg_stat_activity
WHERE pid = 18425;
```

This provides the operational chain:

```text
Operating System PID
  -> PostgreSQL Backend
  -> Application
  -> Database
  -> SQL Query
```

## 1.2.14 Background and auxiliary processes

At an introductory level:

```text
PostgreSQL
├── Supervisor postgres process
├── Client backend processes
├── Auxiliary/background processes
│   ├── Checkpointer
│   ├── Background writer
│   ├── WAL writer
│   └── Autovacuum launcher
└── Additional workers/processes when required
```

Depending on configuration and workload, PostgreSQL may also use autovacuum workers, WAL senders/receivers, parallel workers, logical replication workers, and other background workers. Their internals are covered later.

## 1.2.15 Inspect PostgreSQL activity

`pg_stat_activity` is one of PostgreSQL's most important operational views.

```sql
-- [SAFE-READ]
SELECT
    pid,
    backend_type,
    datname,
    usename,
    application_name,
    client_addr,
    state
FROM pg_stat_activity
ORDER BY backend_type, pid;
```

Important columns include PID, backend type, database, user, application name, client address, and state. Exact visibility depends on PostgreSQL version, configuration, permissions, and workload.

## 1.2.16 Active vs idle sessions

An `active` backend is executing a query. An `idle` backend is waiting for another client command while the connection remains open. An idle session is therefore still connected.

## 1.2.17 Idle in transaction

`idle in transaction` is different from ordinary `idle`.

```sql
BEGIN;
SELECT * FROM patients;
```

If the client waits without `COMMIT` or `ROLLBACK`, the backend can remain idle in transaction. Long-lived transactions can have important operational consequences, covered later under transactions, MVCC, VACUUM, and troubleshooting.

## 1.2.18 Connection lifecycle

```text
Client starts
  -> Connection request
  -> Authentication
  -> Backend/session established
  -> SQL commands
  -> Queries execute
  -> Client disconnects
  -> Backend ends
```

Database connections have a cost.

## 1.2.19 `max_connections`

```sql
-- [SAFE-READ]
SHOW max_connections;
```

This parameter controls the maximum number of concurrent database connections PostgreSQL allows, subject to reserved connection slots and related configuration. Do not treat `max_connections` as a simple capacity knob. Increasing it can increase PostgreSQL and operating-system resource requirements.

A production investigation should consider application concurrency, instance count, pool size per instance, total potential connections, and PostgreSQL capacity rather than blindly increasing the limit.

## 1.2.20 Connection multiplication

If 50 application pods can each open 20 PostgreSQL connections, the application can potentially request 1,000 connections. Reasonable-looking per-instance pool sizes can therefore become large database-wide connection counts.

## 1.2.21 Why connection pooling exists

A common architecture is:

```text
Applications
    |
    v
PgBouncer
    |
    v
PostgreSQL
```

PgBouncer is a connection pooler. Depending on pooling mode and application behavior, it can help decouple application-side connection demand from server-side PostgreSQL connection count. Configuration is covered later.

## 1.2.22 Basic SQL processing path

For learning purposes, use this conceptual pipeline:

```text
Client
  -> Backend
  -> Parser
  -> Analysis / Rewrite
  -> Planner / Optimizer
  -> Executor
  -> Result
```

The parser interprets syntax; analysis/rewrite resolves objects and transformations; the planner/optimizer determines an execution strategy; and the executor executes the selected plan. This is deliberately simplified and is expanded in the query-performance section.

## 1.2.23 Simple query through the architecture

```sql
-- [SAFE-READ]
SELECT 10 + 20;
```

Even a small SQL statement goes through PostgreSQL's query-processing machinery.

## 1.2.24 Where storage enters the picture

For stored data, the model eventually expands toward:

```text
Application
  -> Backend
  -> Query Processing
  -> PostgreSQL Memory
  -> Operating System
  -> Storage
```

Shared buffers, WAL, pages, checkpoints, OS cache, and storage latency are intentionally deferred.

## 1.2.25 Self-managed PostgreSQL

In self-managed environments, teams may control Linux, PostgreSQL installation/configuration, storage, backups, replication, monitoring, and upgrades. Examples include bare metal, VMware, EC2, Azure VM, and Google Compute Engine.

## 1.2.26 Managed PostgreSQL

Managed services shift the operational boundary. Examples include Amazon RDS for PostgreSQL, Aurora PostgreSQL-Compatible, Azure Database for PostgreSQL, Cloud SQL for PostgreSQL, and AlloyDB for PostgreSQL. Direct OS visibility may not be available, so investigations often combine PostgreSQL statistics, cloud monitoring, and provider diagnostics.

## 1.2.27 Hands-On Lab — Observe PostgreSQL connections and backends

Use two terminal sessions connected to the dedicated tutorial PostgreSQL environment.

### Step 1 — Terminal A

```bash
psql -h localhost -p 5432 -U postgres -d postgres
```

Do not place real passwords directly into commands committed to the repository.

```sql
-- [SAFE-READ]
SELECT pg_backend_pid();
```

Record the PID and keep the connection open.

### Step 2 — Terminal B

Open another terminal, connect in the same way, and run:

```sql
-- [SAFE-READ]
SELECT pg_backend_pid();
```

The PIDs should normally differ, demonstrating `Connection A -> Backend A` and `Connection B -> Backend B`.

### Step 3 — Observe both sessions

```sql
-- [SAFE-READ]
SELECT pid, usename, datname, application_name, client_addr, state
FROM pg_stat_activity
WHERE backend_type = 'client backend'
ORDER BY pid;
```

### Step 4 — Label the sessions

Terminal A:

```sql
-- [LAB-ONLY]
SET application_name = 'postgres_tutorial_session_a';
```

Terminal B:

```sql
-- [LAB-ONLY]
SET application_name = 'postgres_tutorial_session_b';
```

Then inspect:

```sql
-- [SAFE-READ]
SELECT pid, application_name, state
FROM pg_stat_activity
WHERE application_name LIKE 'postgres_tutorial%';
```

### Step 5 — Create observable activity

Terminal A:

```sql
-- [LAB-ONLY]
SELECT pg_sleep(30);
```

Do this only in the tutorial environment. Immediately from Terminal B:

```sql
-- [SAFE-READ]
SELECT pid, application_name, state, wait_event_type, wait_event
FROM pg_stat_activity
WHERE application_name = 'postgres_tutorial_session_a';
```

### Step 6 — Observe SQL text

While Terminal A is sleeping, from Terminal B:

```sql
-- [SAFE-READ]
SELECT pid, application_name, state, query
FROM pg_stat_activity
WHERE application_name = 'postgres_tutorial_session_a';
```

This establishes `Session -> PID -> Application -> Current SQL`.

### Step 7 — Disconnect

After the sleep completes, exit Terminal A with `\q`. From Terminal B, query for `postgres_tutorial_session_a` again. The disconnected session should no longer appear.

## 1.2.28 Optional self-managed Linux exercise

On a Linux host you administer:

```bash
# [SAFE-READ]
ps -ef | grep '[p]ostgres'
```

Compare with:

```sql
-- [SAFE-READ]
SELECT pid, backend_type, datname, usename, application_name
FROM pg_stat_activity
ORDER BY pid;
```

This establishes the correlation `Linux process <-> PostgreSQL PID <-> pg_stat_activity <-> database session <-> application`. Managed services may not provide this OS-level visibility.

## 1.2.29 Production troubleshooting preview

A future high-CPU investigation might follow:

```text
High CPU
  -> OS PID (self-managed)
  -> PostgreSQL Backend
  -> Application
  -> Database
  -> SQL
  -> Query Plan
  -> Root Cause
```

The architecture learned here makes later troubleshooting possible.

## 1.2.32 Production takeaways

- PostgreSQL uses client/server architecture.
- A PostgreSQL server is not the same as an individual database.
- "Database cluster" has a specific meaning in core PostgreSQL terminology.
- PostgreSQL traditionally uses a process-per-connection architecture.
- Each connected client is associated with a PostgreSQL backend.
- `pg_backend_pid()` identifies the current session's server process.
- `pg_stat_activity` provides visibility into PostgreSQL activity.
- `idle` and `idle in transaction` are different states.
- Connections consume server resources.
- `max_connections` should not be increased blindly.
- Application connection multiplication matters during capacity planning.
- Self-managed PostgreSQL can provide OS-level visibility that managed services may hide.

Operational chain to remember:

```text
Application
  -> Connection
  -> Backend PID
  -> SQL
  -> Database workload
  -> CPU / Memory / I/O
```
