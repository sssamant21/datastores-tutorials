## 1.13.1 Why PostgreSQL Files and Directories Matter

PostgreSQL presents data logically as clusters, databases, schemas, tables, and indexes, but ultimately persists information using storage managed by the database server. Understanding this layout helps with storage troubleshooting, disk-capacity incidents, WAL growth, backup/recovery, tablespaces, startup failures, corruption investigations, filesystem monitoring, migrations, and incident response.

The central rule is: understanding PostgreSQL physical storage does not grant permission to manipulate PostgreSQL physical storage manually. PostgreSQL-managed files must not be treated like ordinary disposable application files.

## 1.13.2 PGDATA and data_directory

`PGDATA` is a conventional name for the PostgreSQL cluster data directory and an environment variable commonly used to identify it. PostgreSQL exposes the configured location through:

```sql
SHOW data_directory;
```

or:

```sql
SELECT current_setting('data_directory');
```

Operationally, distinguish the conventional/environment-variable concept `PGDATA` from the server's configured `data_directory`. Do not assume a shell variable is authoritative for the instance to which you are connected.

## 1.13.3 Do Not Hard-Code the Data Directory

Installations can use distribution-specific, custom, mounted, or container paths. Use `SHOW data_directory` instead of assuming a universal filesystem location.

## 1.13.4 Multiple PostgreSQL Clusters

A self-managed host can run more than one PostgreSQL cluster. A directory, PostgreSQL process, and `$PGDATA` value do not by themselves prove that a path belongs to the session under investigation. Connect to the intended instance, obtain `SHOW data_directory`, correlate it with the intended service/process, and only then perform authorized OS-level inspection.

## 1.13.5 PostgreSQL Data-Directory Structure

A PostgreSQL 18 data directory can contain entries such as `base/`, `global/`, `pg_commit_ts/`, `pg_dynshmem/`, `pg_logical/`, `pg_multixact/`, `pg_notify/`, `pg_replslot/`, `pg_serial/`, `pg_snapshots/`, `pg_stat/`, `pg_stat_tmp/`, `pg_subtrans/`, `pg_tblspc/`, `pg_twophase/`, `pg_wal/`, `pg_xact/`, `PG_VERSION`, `postgresql.auto.conf`, `postmaster.opts`, `postmaster.pid`, and other PostgreSQL-managed entries.

An unfamiliar PostgreSQL file or directory is not automatically safe to delete.

## 1.13.6 PG_VERSION

`PG_VERSION` identifies the PostgreSQL major version associated with the cluster data directory. On an authorized self-managed lab host, it can be read after verifying the correct data directory. Do not modify it. Editing `PG_VERSION` does not upgrade PostgreSQL.

## 1.13.7 base/

`PGDATA/base/` contains per-database storage for databases using the default tablespace. Its subdirectories use internal database identifiers rather than database names. Do not rename them.

## 1.13.8 Database OIDs

```sql
SELECT oid, datname
FROM pg_database
ORDER BY oid;
```

For the current database:

```sql
SELECT oid, datname
FROM pg_database
WHERE datname = current_database();
```

For a database using the default tablespace, its OID participates in its physical storage path under `base/`.

## 1.13.9 Database OID Does Not Always Mean base/<OID>

User-defined tablespaces can place database storage elsewhere. Physical placement depends on tablespace configuration.

## 1.13.10 global/

`PGDATA/global/` contains cluster-wide relations, including shared PostgreSQL catalogs. The built-in `pg_global` tablespace corresponds to this cluster-wide storage area. Do not manipulate these files manually.

## 1.13.11 Logical Relation vs Physical Storage

A table or index is a logical database object. Do not assume a table name equals a filesystem filename or that a relation OID is a permanent physical filename.

## 1.13.12 Relation Filenodes

PostgreSQL associates relation storage with a filenode:

```sql
SELECT pg_relation_filenode('clinical.constraint_patient');
```

A relation OID is not necessarily the current filenode. Operations such as `TRUNCATE`, `REINDEX`, `CLUSTER`, and some rewrites can result in different physical storage while the logical object continues to exist. Revalidate physical identity during each investigation rather than relying on old incident evidence.

## 1.13.13 pg_relation_filepath()

```sql
SELECT pg_relation_filepath('clinical.constraint_patient');
```

`pg_relation_filepath()` reports the path for the first segment of the relation's main fork. It does not report every physical file belonging to the logical relation.

## 1.13.14 Relation Forks

A relation can have multiple physical forks: a main fork, free-space-map (`_fsm`) fork, visibility-map (`_vm`) fork, and an initialization (`_init`) fork where applicable for unlogged relations. Do not delete a fork because its suffix appears optional; PostgreSQL manages these structures.

## 1.13.15 Relation Segments

A sufficiently large relation fork can span multiple filesystem segments such as `12345`, `12345.1`, `12345.2`, and so on. The commonly encountered default segment size is 1 GB, but this is a build-time characteristic and must not be treated as an immutable universal constant. One relation can therefore have multiple forks and each fork can have multiple segments.

## 1.13.16 TOAST Storage

A logical table can also have associated TOAST storage for values requiring TOAST handling. This is another reason one table does not equal one filesystem file. Detailed TOAST internals are deferred to later storage tutorials.

## 1.13.17 Inspect Relation Size Through PostgreSQL

Use PostgreSQL size functions rather than trying to infer logical object size from one OS file:

```sql
SELECT pg_size_pretty(pg_relation_size('clinical.constraint_patient')) AS relation_size;
```

```sql
SELECT pg_size_pretty(pg_total_relation_size('clinical.constraint_patient')) AS total_relation_size;
```

## 1.13.18 Tablespaces

Inspect tablespaces with:

```sql
SELECT
    oid,
    spcname,
    pg_tablespace_location(oid) AS location
FROM pg_tablespace
ORDER BY oid;
```

Conceptually, `pg_default` corresponds to default database storage under `PGDATA/base`, while `pg_global` corresponds to `PGDATA/global`. User-defined tablespaces use PostgreSQL's tablespace-management mechanism.

## 1.13.19 pg_tblspc/

`PGDATA/pg_tblspc/` participates in user-defined tablespace storage. Entries are associated with tablespace OIDs and can reference storage outside the main data directory. Do not manually delete, rename, replace, or repoint tablespace links during normal administration.

## 1.13.20 pg_wal/

`PGDATA/pg_wal/` contains PostgreSQL Write-Ahead Log files. WAL is fundamental to durability, crash recovery, backup/recovery, replication, and point-in-time recovery.

If `pg_wal` grows unexpectedly, investigate why. Do not manually delete WAL files to reclaim space.

## 1.13.21 Disk Full Does Not Mean Delete WAL

Possible contributors to WAL retention or growth include WAL generation rate, archiving problems, replication, replication slots, backup/recovery activity, and checkpoint/WAL behavior. Diagnose the retention or growth mechanism before remediation.

## 1.13.22 pg_xact/

`PGDATA/pg_xact/` contains transaction commit-status information. Never manually delete, truncate, edit, move, or rename its files as an ordinary cleanup operation.

## 1.13.23 pg_multixact/

`PGDATA/pg_multixact/` contains PostgreSQL-managed multitransaction status information used when multiple transactions participate in certain row-locking situations. It is not an operator-managed cleanup directory.

## 1.13.24 Statistics Directories

PostgreSQL 18's data-directory layout includes `pg_stat/` and `pg_stat_tmp/` for statistics-related subsystem storage. These are PostgreSQL-managed directories and are not manual cleanup targets.

## 1.13.25 Temporary PostgreSQL Files

PostgreSQL can create temporary files during operations requiring temporary disk storage, including `pgsql_tmp` areas associated with database or tablespace storage. A PostgreSQL temporary file is not automatically an operator-managed disposable file.

## 1.13.26 postmaster.pid

A running PostgreSQL cluster normally maintains `postmaster.pid` containing server/runtime information. Do not assume a PID file is safe to delete merely because it appears stale. Verify server state, correct data directory, and intended cluster, then follow a controlled recovery procedure. Part 1.13 does not delete or modify `postmaster.pid`.

## 1.13.27 Configuration Files

Common PostgreSQL configuration files include `postgresql.conf`, `pg_hba.conf`, `pg_ident.conf`, and `postgresql.auto.conf`. Do not assume every configuration file physically resides inside `PGDATA`.

## 1.13.28 Discover Configuration Locations Through PostgreSQL

```sql
SHOW config_file;
SHOW hba_file;
SHOW ident_file;
```

Part 1.13 discovers these locations. Part 1.14 explains the configuration files themselves.

## 1.13.29 postgresql.auto.conf

`postgresql.auto.conf` is used for settings written through PostgreSQL's `ALTER SYSTEM` mechanism and participates in configuration precedence. Part 1.13 only identifies it conceptually and does not edit it or execute `ALTER SYSTEM`.

## 1.13.30 Filesystem Permissions Are Not a Shortcut

A PostgreSQL permission problem should not automatically lead to `chmod -R 777` or broad recursive ownership changes. A production installation can involve data directories, tablespaces, symlinks, service accounts, backup tooling, and security controls. Understand ownership and deployment architecture before changing permissions. Part 1.13 changes no permissions.

## 1.13.31 Self-Managed Filesystem Inspection

For an authorized self-managed lab, first run:

```sql
SHOW data_directory;
```

Verify that the returned path corresponds to the intended running cluster. Only then use read-only OS inspection such as `ls -ld`, `ls -la`, or reading `PG_VERSION` against that verified path.

## 1.13.32 Read-Only Does Not Mean Zero Cost

Broad recursive commands such as `du -ah` or `find` can generate substantial filesystem metadata activity on large PostgreSQL storage. Prefer targeted inspection based on the incident.

## 1.13.33 Managed PostgreSQL Services

Managed services may not expose the PostgreSQL host filesystem. SQL-level investigation can still use interfaces such as `pg_database`, `pg_tablespace`, `pg_tablespace_location()`, `pg_relation_filenode()`, `pg_relation_filepath()`, `pg_relation_size()`, and `pg_total_relation_size()`, subject to platform behavior and privileges. The acceptance artifact requires no OS access.

## 1.13.34 Never Modify PostgreSQL Storage Behind PostgreSQL

Do not manually delete, rename, move, or truncate relation files; delete WAL; modify `pg_xact` or `pg_multixact`; remove tablespace links; alter relation segments/forks; modify `PG_VERSION`; blindly delete `postmaster.pid`; or recursively change PGDATA permissions. Understand PostgreSQL-managed storage through supported interfaces and remediate through supported procedures.

## 1.13.35 Disk-Full Incident Model

Do not use `disk full -> find biggest file -> delete it`. Instead identify the affected filesystem, identify the PostgreSQL storage consumer, determine why it is growing, understand its retention/lifecycle, choose PostgreSQL-aware remediation, and verify recovery.

Questions can include whether WAL is accumulating, a relation is growing, temporary storage is growing, a replication slot is retaining WAL, archiving is failing, a tablespace is filling, or backup/recovery activity is involved.

## 1.13.36 Hands-On SQL Storage Inspection Lab

```sql
SHOW data_directory;
```

```sql
SELECT oid, datname
FROM pg_database
WHERE datname = current_database();
```

```sql
SELECT
    oid,
    spcname,
    pg_tablespace_location(oid) AS location
FROM pg_tablespace
ORDER BY oid;
```

```sql
SELECT to_regclass('clinical.constraint_patient') AS expected_relation;
```

```sql
SELECT pg_relation_filenode('clinical.constraint_patient') AS filenode;
```

```sql
SELECT pg_relation_filepath('clinical.constraint_patient') AS main_fork_first_segment;
```

```sql
SELECT
    pg_size_pretty(pg_relation_size('clinical.constraint_patient')) AS relation_size,
    pg_size_pretty(pg_total_relation_size('clinical.constraint_patient')) AS total_relation_size;
```

```sql
SHOW config_file;
SHOW hba_file;
SHOW ident_file;
```

Every SQL operation above is observational.

## 1.13.37 Optional Self-Managed Lab

This section is optional and not part of canonical acceptance. First use `SHOW data_directory`, record and verify the returned path, and correlate it with the intended PostgreSQL instance. Read-only filesystem inspection may then use `ls` or `cat PG_VERSION` as authorized. Do not use an unverified `$PGDATA` value as the sole source of truth.

## 1.13.38 Production Safety Boundary

Part 1.13 permits appropriately targeted `SHOW`, `SELECT`, `current_setting()`, `current_database()`, `to_regclass()`, `pg_relation_filenode()`, `pg_relation_filepath()`, `pg_relation_size()`, `pg_total_relation_size()`, and `pg_tablespace_location()` calls. Optional authorized self-managed inspection may use read-only OS tools.

It performs no DDL, DML, `VACUUM`, `REINDEX`, `CLUSTER`, `ALTER SYSTEM`, generic server-file reads, filesystem mutation, WAL deletion, relation-file manipulation, tablespace-link manipulation, or transaction-state manipulation.

## 1.13.39 What You Should Know Now

You should understand `PGDATA`, `data_directory`, `base/`, `global/`, `pg_wal/`, `pg_xact/`, `pg_multixact/`, `pg_tblspc/`, `pg_stat/`, `pg_stat_tmp/`, `PG_VERSION`, `postmaster.pid`, and `postgresql.auto.conf` at an introductory level.

Key distinctions are: database name is not a filesystem directory name; table name is not a filesystem filename; relation OID is not a permanent filenode; one relation is not one physical file; `pg_relation_filepath()` is not every file belonging to a table; a shell `$PGDATA` value is not automatically authoritative; disk full does not mean delete WAL; temporary does not mean safe manual deletion; a permission problem does not mean `chmod 777`; and a PID file is not automatically safe to delete.

## 1.13.40 Operational Decision Model

Use: **Observe -> Identify -> Map logical object to physical storage -> Determine why storage exists/grows -> Assess operational impact -> Choose PostgreSQL-supported remediation -> Verify.**

Never use “see large PostgreSQL file -> delete it” as a storage-management model.
