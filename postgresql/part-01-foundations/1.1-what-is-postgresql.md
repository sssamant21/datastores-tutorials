# 1.1 — What Is PostgreSQL?

## From Database Fundamentals to Your First PostgreSQL Server

## Learning objectives

By the end of this section, you should be able to explain:

- what a database management system is;
- what PostgreSQL is and how it differs from SQL;
- the PostgreSQL object hierarchy: cluster → database → schema → object;
- the client/server model;
- what `psql` is;
- how to inspect basic server and session information;
- how to perform a small, safe CRUD exercise using a temporary table.

## 1.1.1 What is a database?

Applications need a reliable way to store and retrieve information. A healthcare application, for example, might manage patients, providers, appointments, medications, claims, and addresses.

Flat files can work for small experiments, but production applications usually need concurrency, transactions, relationships, constraints, access control, indexing, crash recovery, backup, replication, and efficient querying. A database management system (DBMS) provides these capabilities.

## 1.1.2 What is PostgreSQL?

PostgreSQL is an open-source object-relational database management system. Applications and users connect to a PostgreSQL server to store, retrieve, modify, and protect data.

At a high level:

```text
Application
    |
    | SQL
    v
PostgreSQL
    |
    v
Database
    |
    +-- Tables
    +-- Indexes
    +-- Views
    +-- Functions
    +-- Other objects
```

For example:

```sql
SELECT *
FROM patients;
```

## 1.1.3 PostgreSQL vs SQL

SQL is a language. PostgreSQL is a database management system that understands SQL.

```text
SQL
 |
 | instructions
 v
PostgreSQL
 |
 v
Data
```

Other relational database systems also implement SQL, but their dialects and capabilities are not identical.

## 1.1.4 Cluster, database, schema, and table

In core PostgreSQL terminology, a database cluster is a collection of databases managed by a PostgreSQL server/data directory. Within each database are schemas, and schemas contain objects such as tables and functions.

```text
PostgreSQL Cluster
|
+-- Database: postgres
|
+-- Database: healthcare_db
|   |
|   +-- Schema: public
|   |
|   +-- Schema: clinical
|       |
|       +-- Table: patients
|       +-- Table: providers
|       +-- Table: appointments
|
+-- Database: analytics_db
```

A useful fundamental hierarchy is:

```text
Cluster
  -> Database
      -> Schema
          -> Table or other object
```

A PostgreSQL connection connects to one database at a time.

## 1.1.5 Rows and columns

A relational table stores related information in rows and columns.

| patient_id | first_name | last_name | city |
| ---: | --- | --- | --- |
| 1001 | John | Smith | Charlotte |
| 1002 | Maria | Garcia | Raleigh |
| 1003 | David | Wilson | Durham |

Columns describe attributes. Each row represents a record.

This model becomes important later when we study primary keys, foreign keys, constraints, indexes, MVCC, query optimization, and storage.

## 1.1.6 PostgreSQL is a client/server system

PostgreSQL normally operates as a server. Clients connect to it and send requests.

```text
psql -------------+
Python app -------+---> PostgreSQL Server
Java app ---------+
BI / ETL tools ---+
```

Clients do not normally manipulate PostgreSQL database files directly.

## 1.1.7 Connection information

A PostgreSQL network connection commonly needs:

```text
Host
Port
Database
Username
Authentication credentials
```

The customary/default PostgreSQL TCP port is `5432`, although it can be changed.

Example connection information:

```text
Host:       db.example.internal
Port:       5432
Database:   healthcare_db
User:       healthcare_app
```

Do not place real production passwords in tutorial commands, screenshots, shell history, or source control.

## 1.1.8 What is psql?

`psql` is PostgreSQL's interactive terminal/client.

A typical connection command is:

```bash
psql -h localhost -p 5432 -U postgres -d postgres
```

The main options here are:

```text
-h  host
-p  port
-U  user
-d  database
```

## 1.1.9 First server and session inspection

After connecting, run:

```sql
SELECT version();
SELECT current_database();
SELECT current_user;
SHOW port;
```

On a self-managed PostgreSQL system, these are also useful:

```sql
SHOW data_directory;
SHOW config_file;
SHOW hba_file;
```

The last three settings expose server-side filesystem paths. Managed cloud services may restrict filesystem-level access even when PostgreSQL exposes related settings.

## 1.1.10 Inspect connection details

Run:

```sql
SELECT
    current_database() AS database,
    current_user AS username,
    inet_server_addr() AS server_address,
    inet_server_port() AS server_port;
```

For a Unix-domain socket connection, the address and port functions can return `NULL`. That is expected and does not mean the session is disconnected.

Inside `psql`, also try:

```text
\conninfo
```

## 1.1.11 Introduction to pg_stat_activity

PostgreSQL exposes current server activity through system views. One of the most important is `pg_stat_activity`.

```sql
SELECT
    pid,
    usename,
    datname,
    application_name,
    client_addr,
    state,
    backend_type
FROM pg_stat_activity
ORDER BY pid;
```

At this stage, remember only that this view helps map PostgreSQL server processes and sessions to users, databases, applications, addresses, and activity states.

We will use it repeatedly in later performance and incident-response labs.

## 1.1.12 Find your backend PID

Run:

```sql
SELECT pg_backend_pid();
```

`pg_backend_pid()` returns the process ID of the PostgreSQL server process attached to the current session.

Then find the current session:

```sql
SELECT
    pid,
    usename,
    datname,
    application_name,
    state
FROM pg_stat_activity
WHERE pid = pg_backend_pid();
```

This introduces an important relationship:

```text
Client session
    -> PostgreSQL connection
        -> Server backend PID
```

We will examine this process model in Section 1.2.

## 1.1.13 Why use PostgreSQL instead of ordinary files?

A database server coordinates concurrent access and provides mechanisms for transactions, locking, consistency, recovery, security, and durability.

For example, multiple users may attempt to modify related data concurrently:

```text
User A ---+
          +---> PostgreSQL ---> Data
User B ---+
```

PostgreSQL coordinates that work rather than requiring each application to implement database concurrency and recovery itself.

## 1.1.14 Introduction to transactions

Suppose an application transfers money between two accounts. The logical operation contains multiple changes:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE account_id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE account_id = 2;

COMMIT;
```

This introduces the idea of a transaction: related operations can be treated as a logical unit of work.

Transactions, isolation, locking, MVCC, WAL, and crash recovery are covered later. Do not use this simplified transfer example as a production financial implementation.

## 1.1.16 Hands-on exercise — explore databases

Inside `psql`:

```text
\l
```

or:

```text
\list
```

Then compare that with SQL:

```sql
SELECT datname
FROM pg_database
ORDER BY datname;
```

Commands beginning with a backslash are `psql` meta-commands. They are not ordinary SQL statements.

## 1.1.17 Hands-on exercise — temporary table and CRUD

Use a temporary table so this introductory exercise does not create a permanent application object:

```sql
CREATE TEMP TABLE tutorial_test (
    id integer,
    message text
);
```

Insert two rows:

```sql
INSERT INTO tutorial_test
VALUES
    (1, 'Hello PostgreSQL'),
    (2, 'My first PostgreSQL lab');
```

Read them:

```sql
SELECT *
FROM tutorial_test
ORDER BY id;
```

Update one row:

```sql
UPDATE tutorial_test
SET message = 'PostgreSQL is running'
WHERE id = 1;
```

Delete one row:

```sql
DELETE FROM tutorial_test
WHERE id = 2;
```

Validate:

```sql
SELECT *
FROM tutorial_test
ORDER BY id;
```

The temporary table belongs to the session and is automatically removed when the session ends.

## 1.1.18 Fundamental mental model

```text
                       CLIENTS
                          |
             +------------+------------+
             |            |            |
            psql        Python        App
             |            |            |
             +------------+------------+
                          |
                          v
                  PostgreSQL Server
                          |
                    +-----+-----+
                    |           |
                Database A   Database B
                    |
                  Schema
                    |
              +-----+-----+
              |           |
            Table       Table
              |
          Rows / Columns
```

Later sections will add processes, memory, storage, WAL, MVCC, locks, indexes, replication, backup, and monitoring to this model.

## 1.1.19 Production takeaways

1. PostgreSQL is a database server, not simply a collection of files.
2. Core PostgreSQL hierarchy is cluster → database → schema → object.
3. A client connects to one database per connection.
4. PostgreSQL exposes significant operational information through SQL and system views.
5. `pg_stat_activity` and backend PIDs will become central to DBRE/SRE troubleshooting.
6. Do not experiment against production systems while following beginner labs; use an isolated lab environment.
