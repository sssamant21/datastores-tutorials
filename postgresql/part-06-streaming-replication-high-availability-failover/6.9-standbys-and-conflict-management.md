# 6.9 — Standbys and Conflict Management

## Purpose

A PostgreSQL physical standby can serve read-only workloads while continuously replaying WAL from the primary. These responsibilities can conflict when recovery needs to apply a change while a standby query still depends on affected database state.

The production tradeoff is simple:

```text
standby query completion
          vs
WAL replay / recovery freshness
```

This tutorial develops an operational model for hot-standby conflicts, query cancellation, WAL replay, VACUUM interactions, monitoring, and safe remediation.

## Learning Objectives

You should be able to:

- explain hot-standby read behavior;
- identify recovery-conflict categories;
- understand VACUUM/snapshot interactions;
- interpret `max_standby_streaming_delay` and `max_standby_archive_delay`;
- evaluate `hot_standby_feedback`;
- use `pg_stat_database_conflicts`;
- monitor WAL receive/replay progress;
- distinguish query cancellation from replication failure;
- recognize that some conflicts can terminate a session;
- use `log_recovery_conflict_waits` as supporting evidence;
- safely reproduce conflict behavior in an isolated lab.

## 1. Hot Standby

A physical standby can serve read-only queries while recovery continues. It is still a recovery system, so query execution must coexist with WAL replay.

Normal reads can run, but the standby is not another writable primary. Restrictions during recovery are broader than ordinary transaction-level read-only behavior.

## 2. Recovery Conflicts

A recovery conflict occurs when WAL replay requires database state that conflicts with activity executing on the standby. PostgreSQL may wait for the conflict to resolve. If the applicable recovery-delay budget is exhausted, conflicting activity can be canceled so recovery can proceed.

If recovery waits too long:

```text
long query
    |
    v
WAL replay delayed
    |
    v
replay lag grows
    |
    v
standby becomes stale
```

For HA standbys, this can undermine failover readiness.

## 3. Conflict Categories

Inspect cumulative conflict counters on the standby:

```sql
SELECT
    datname,
    confl_tablespace,
    confl_lock,
    confl_snapshot,
    confl_bufferpin,
    confl_deadlock
FROM pg_stat_database_conflicts
ORDER BY datname;
```

Monitor counter deltas/rates rather than treating totals as current incident rates.

## 4. Snapshot and VACUUM Conflicts

A long-running standby query may require older row versions while the primary performs updates/deletes and VACUUM cleanup. Replaying that cleanup can conflict with the standby snapshot.

VACUUM-related conflicts are not limited to obvious large DELETE workloads. Visibility-map changes can also matter, including for index-only scans.

Correlate conflict evidence with primary VACUUM and workload evidence before drawing conclusions.

## 5. Lock and DDL Conflicts

Primary operations involving strong locks can conflict with standby activity when WAL is replayed. Examples can include `ALTER TABLE`, `DROP TABLE`, `DROP DATABASE`, and tablespace operations.

Most recovery conflicts are discussed as query cancellation, but some documented cases can terminate a session. Applications must account for both outcomes.

A canceled query or terminated session does not by itself prove replication failure.

## 6. `max_standby_streaming_delay`

```sql
SHOW max_standby_streaming_delay;
```

This controls how long recovery is prepared to wait while applying streamed WAL when conflicts occur.

It is a recovery-delay budget, not a guaranteed runtime allowance for each query. If earlier conflicts have already consumed delay, a later query may receive less time.

Larger values generally favor query completion; smaller values generally favor recovery freshness.

## 7. `max_standby_archive_delay`

```sql
SHOW max_standby_archive_delay;
```

This serves the corresponding purpose while applying archived WAL.

```text
max_standby_streaming_delay -> streamed WAL
max_standby_archive_delay   -> archived WAL
```

A value of `-1` permits indefinite waiting and needs careful justification for an HA-focused standby.

## 8. `hot_standby_feedback`

```sql
SHOW hot_standby_feedback;
```

Hot standby feedback can prevent the primary from removing row versions still required by standby queries, reducing some cleanup-related conflicts.

The tradeoff is potentially longer dead-tuple retention and primary table/index bloat. It is not a universal fix.

## 9. Standby Purpose

### HA-focused standby

Prioritize replay freshness, failover readiness, controlled query duration, and application tolerance for conflict cancellation.

### Reporting-focused standby

Longer queries and greater replay delay may be acceptable when data-staleness objectives are explicitly defined.

### Mixed workload

Rapid failover readiness and unrestricted long-running analytics can conflict. When one policy cannot satisfy both safely, consider separate HA and reporting standbys.

## 10. Monitoring Recovery

Confirm role:

```sql
SELECT pg_is_in_recovery();
```

On a standby:

```sql
SELECT
    pg_last_wal_receive_lsn(),
    pg_last_wal_replay_lsn(),
    pg_last_xact_replay_timestamp();
```

Interpret replay timestamps carefully when the primary is idle; they are not a continuously ticking wall-clock lag metric.

Inspect long-running activity:

```sql
SELECT
    pid,
    usename,
    application_name,
    state,
    query_start,
    now() - query_start AS query_runtime,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start;
```

## 11. `log_recovery_conflict_waits`

`log_recovery_conflict_waits` provides additional observability for recovery-conflict waits. Correlate logs with conflict counters, affected queries, and replay evidence.

Treat logging as evidence, not remediation.

## 12. Production Monitoring Model

Correlate:

```text
pg_stat_database_conflicts
        +
long-running standby queries
        +
WAL receive/replay positions
        +
replay timestamp evidence
        +
recovery-conflict logs
        +
primary VACUUM / DDL evidence
```

No single signal normally explains the full incident.

## 13. Troubleshooting Flow

```text
Query/session affected
        |
        v
Confirm standby state
        |
        v
Inspect conflict-counter changes
        |
        v
Identify conflict category
        |
        v
Inspect affected query/session
        |
        v
Inspect WAL receive/replay progress
        |
        v
Inspect standby delay settings
        |
        v
Inspect hot_standby_feedback
        |
        v
Correlate primary VACUUM / DDL / workload
        |
        v
Compare with standby purpose/SLO
        |
        v
Choose remediation
```

Diagnose first; tune second.

## 14. Unsafe Reactions

Do not automatically increase standby-delay settings because replay lag may increase.

Do not automatically enable `hot_standby_feedback` because primary-side bloat risk may increase.

Do not terminate reporting sessions without understanding workload ownership.

Do not treat recovery-conflict cancellation as proof that replication must be rebuilt.

## 15. Application Considerations

Applications reading from hot standbys should define behavior for:

- canceled reads;
- terminated connections;
- safe retry;
- bounded backoff;
- alternative read targets.

Repeatedly retrying an incompatible long-running query can recreate the same conflict.

## 16. LAB-WRITE — Controlled Hot-Standby Conflict

Locked lab:

`labs/hot-standby-conflict-lab.sql`

The lab requires a dedicated lab primary and physical standby. It explicitly separates PRIMARY and STANDBY execution contexts.

It may create and mutate dedicated lab objects, run a controlled standby read, inspect conflict counters and replay, and clean up the lab schema.

It must not modify application tables, terminate unrelated sessions, disable autovacuum globally, manipulate replication slots, reset WAL, fill `pg_wal`, or alter production replication policy.

Conflict reproduction is timing-dependent. No cancellation observed is a valid informational result and must not trigger increasingly destructive attempts.

## 17. Lab Classification

```text
PASS     -> expected conflict/recovery evidence observed
INFO     -> experiment completed but no conflict occurred
WARNING  -> topology/configuration/context unsuitable
UNKNOWN  -> evidence insufficient
```

## 18. Production Acceptance Checklist

- [ ] standby purpose is documented;
- [ ] HA versus reporting priority is documented;
- [ ] maximum acceptable replay lag is defined;
- [ ] query-duration policy is defined;
- [ ] both standby delay settings are reviewed;
- [ ] `hot_standby_feedback` policy is documented;
- [ ] primary bloat is monitored when feedback is used;
- [ ] `pg_stat_database_conflicts` is monitored;
- [ ] conflict deltas/rates are observable;
- [ ] long-running standby queries are monitored;
- [ ] WAL receive/replay progress is monitored;
- [ ] recovery-conflict logging policy is defined;
- [ ] applications handle cancellation and possible session termination;
- [ ] retries are bounded;
- [ ] configuration changes follow change control;
- [ ] HA/reporting workloads are separated when objectives cannot be reconciled.

## 19. Key Takeaways

1. Hot standbys serve reads while performing recovery.
2. Read-only queries can conflict with WAL replay.
3. Recovery conflicts are not automatically replication failures.
4. PostgreSQL can cancel conflicting activity; some cases can terminate sessions.
5. `pg_stat_database_conflicts` provides important cumulative evidence.
6. Standby delay settings are recovery-delay controls, not per-query runtime guarantees.
7. `hot_standby_feedback` can reduce cleanup conflicts while increasing primary bloat risk.
8. Monitor conflicts, queries, replay, logs, and primary workload together.
9. HA and reporting can impose competing requirements.
10. Diagnose first; tune second.
