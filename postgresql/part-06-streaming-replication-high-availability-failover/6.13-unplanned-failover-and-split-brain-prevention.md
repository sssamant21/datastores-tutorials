# 6.13 --- Unplanned Failover and Split-Brain Prevention

## Purpose

An unplanned PostgreSQL failover transfers database service to a
surviving standby after the current primary becomes unavailable,
unhealthy, isolated, or unsafe to continue serving production traffic.

Unlike a planned switchover, operators may not have the opportunity to
quiesce writers, capture a final primary WAL boundary, verify that the
standby replayed that boundary, coordinate application shutdown, or
gracefully stop the old primary.

The central challenge is:

> Restore database service without creating two independent writable
> primaries.

The most important operational rule is:

> **Primary unreachable does not automatically mean primary fenced.**

## 1. Learning Objectives

By the end of this tutorial, you should be able to:

-   distinguish unplanned failover from planned switchover;
-   classify primary-failure evidence;
-   distinguish unreachability from fencing;
-   explain split-brain risk;
-   identify viable promotion candidates;
-   assess candidate receive/replay state;
-   understand asynchronous and synchronous RPO implications;
-   establish and verify fencing;
-   perform an emergency GO / NO-GO decision;
-   promote and validate a standby;
-   redirect clients safely;
-   understand ambiguous transaction outcomes;
-   quarantine a returning former primary;
-   understand timeline divergence;
-   evaluate `pg_rewind` eligibility;
-   choose rewind or rebuild;
-   restore HA protection;
-   preserve incident evidence.

## 2. Planned Switchover vs Unplanned Failover

Planned switchover begins with healthy systems, controllable writes, and
an opportunity to establish a final WAL boundary.

Unplanned failover may begin with only this fact:

``` text
A is not responding normally.
```

A might be stopped, crashed, network-isolated, storage-stalled,
partitioned, still running, or still accepting writes through another
path.

That uncertainty drives the failover procedure.

## 3. DISRUPTIVE-LAB Classification

Companion runbook:

`labs/unplanned-failover-runbook.md`

Classification: **DISRUPTIVE-LAB**

The procedure may intentionally isolate a primary, stop database
services, perform infrastructure fencing, promote a standby, change
routing, interrupt connections, change replication topology, and rewind
or rebuild a former primary.

Execute it first in a controlled lab or staging HA topology.

## 4. Reference Topology

Normal:

``` text
Application
    |
    v
Primary A
    |
    | physical streaming replication
    v
Standby B
```

Service recovery:

``` text
Application
    |
    v
Primary B
```

Preferred final state:

``` text
Application
    |
    v
Primary B
    |
    v
Standby A
```

or another healthy replacement standby.

## 5. Failure Detection Is Not Promotion Authorization

Signals such as a failed health check, `psql` timeout, SSH timeout, or
monitoring alert prove that something is wrong from particular
observation points.

They do not prove that A cannot serve another client.

``` text
FAILURE DETECTED != PROMOTION AUTHORIZED
```

## 6. Unreachable Is Not Fenced

An operator being unable to reach A does not prove application clients
cannot reach A.

``` text
UNREACHABLE != FENCED
```

This is the central split-brain prevention rule.

## 7. Split Brain

Split brain exists when independent servers can act as writable
authorities for the same workload.

If both A and promoted B accept writes, their histories can diverge.
PostgreSQL does not provide a safe automatic merge of two independently
writable histories.

Preventing this state is critical.

## 8. PostgreSQL vs External HA Control

PostgreSQL provides replication, recovery, and promotion mechanisms.

External HA architecture commonly provides failure detection, fencing,
routing, orchestration, and infrastructure control.

Do not assume PostgreSQL promotion itself arbitrates a network
partition.

## 9. Incident Authority

Production failover should have explicit authority.

A safe sequence is:

``` text
failure detected
    ↓
incident declared
    ↓
evidence collected
    ↓
fencing verified
    ↓
emergency GO authorized
    ↓
promotion
```

Freeze unrelated changes while stabilizing the HA incident.

## 10. Use Multiple Evidence Sources

Correlate PostgreSQL, infrastructure, network, storage, application,
monitoring, orchestrator, and cloud/platform evidence.

One timed-out monitoring probe is materially different from a database
failure combined with authoritative infrastructure evidence that the old
host is stopped.

## 11. Classify Fencing State

Use explicit states:

``` text
FENCED
Positive evidence A cannot serve writes.

NOT FENCED
Positive evidence A can still serve writes.

UNKNOWN
Insufficient evidence.
```

For failover purposes:

``` text
UNKNOWN → split-brain risk remains
```

Never silently reinterpret `UNKNOWN` as `FENCED`.

## 12. Authoritative Fencing

Environment-specific fencing may include power fencing, cloud instance
stop, VM shutdown, storage fencing, network isolation, or orchestrator
fencing.

A fencing request is not enough.

``` text
FENCING ACTION
    ↓
VERIFY RESULT
    ↓
PROMOTION MAY PROCEED
```

## 13. Network Partition Risk

A network partition can make A unreachable to operators while A remains
writable to clients in another network segment.

Promoting B in that condition without fencing can create two writable
primaries.

## 14. Confirm Candidate Recovery State

On B:

``` sql
SELECT
    pg_is_in_recovery(),
    pg_last_wal_receive_lsn(),
    pg_last_wal_replay_lsn(),
    pg_last_xact_replay_timestamp(),
    pg_is_wal_replay_paused();
```

Before promotion, B should normally still be in recovery.

Unexpected paused replay requires investigation.

## 15. WAL Receiver Evidence

Inspect safe operational fields from `pg_stat_wal_receiver`, including
status, slot name, sender host/port, written/flushed LSNs, latest end
LSN, and last message receipt time.

Avoid collecting credential-bearing connection strings.

## 16. Preserve Pre-Promotion Evidence

When practical without materially worsening the outage, capture:

-   timestamp;
-   recovery state;
-   receive LSN;
-   replay LSN;
-   last replay timestamp;
-   receiver state;
-   slot state;
-   PostgreSQL logs;
-   storage/compute health.

Promotion changes B's state, so this evidence can be valuable during RPO
analysis and RCA.

## 17. No Final Primary Boundary May Exist

In a planned switchover, operators can capture a final durable primary
WAL boundary after quiescing writes.

In an unplanned failure:

``` text
FINAL PRIMARY STATE = UNKNOWN
```

may be unavoidable.

Do not invent a final WAL boundary.

## 18. Asynchronous Replication and RPO

With asynchronous replication, a commit can be acknowledged on A before
the corresponding WAL is durably available on B.

Recent acknowledged transactions can therefore be exposed to loss after
promotion.

Do not claim zero data loss without supporting evidence.

## 19. Synchronous Replication Requires Context

Assess:

``` text
synchronous_standby_names
+
actual participating standby
+
synchronous_commit behavior
+
failure timing
```

The word `synchronous` alone is insufficient for an RPO conclusion.

## 20. RPO Evidence Classification

Use:

``` text
CONFIRMED
Evidence establishes the outcome.

POSSIBLE
A credible loss window exists.

UNKNOWN
Evidence is insufficient.
```

Do not turn "lag looked small" into "no transactions were lost."

## 21. Candidate Capacity

Assess CPU, memory, storage, IOPS, throughput, connections, WAL
capacity, WAL sender capacity, and replication-slot capacity.

If B is undersized but promotion is required to restore degraded
service, document the limitation.

## 22. Multiple Standby Selection

For multiple candidates, collect evidence about recovery state,
receive/replay position, replay timestamp, receiver state,
infrastructure health, capacity, failure-domain independence, topology,
and logical replication implications.

Do not automatically promote the candidate with the numerically largest
replay LSN.

Candidate selection is an HA decision involving both freshness and
operational safety.

## 23. LSN Comparison Has Context

Before promotion, candidates following the same primary history can use
WAL positions as useful freshness evidence.

After timeline divergence, a larger LSN is not a universal cross-history
statement that one server is automatically better.

## 24. Read-Only Availability Is Not Promotion Readiness

A hot standby can successfully serve queries while still being behind
the former primary.

Successful `SELECT` queries do not prove that B contains every
transaction from A or that all promotion prerequisites are satisfied.

## 25. Logical Replication Gate

If logical replication or failover-enabled logical slots are involved,
inspect their readiness.

Track database service and logical consumer health separately.

Do not experimentally drop or recreate synchronized logical slots during
emergency promotion.

## 26. Emergency GO / NO-GO

Final gate:

``` text
[ ] candidate identified and healthy enough
[ ] candidate pre-promotion state captured where practical
[ ] RPO exposure acknowledged
[ ] old primary fenced
[ ] fencing positively verified
[ ] routing procedure ready
[ ] monitoring active
[ ] incident authority approves
```

The fencing gate is mandatory.

## 27. Promotion

Immediately before promotion:

``` text
POINT OF NO SIMPLE RETURN
```

Canonical lab mechanism:

``` sql
SELECT pg_promote(wait => true);
```

This is **STATE-CHANGING / DISRUPTIVE**.

## 28. Verify Promotion

On B:

``` sql
SELECT pg_is_in_recovery();
```

Expected: `false`.

Also validate PostgreSQL logs, database availability, storage health,
and monitoring.

Do not route applications merely because the promotion request returned.

## 29. Database Smoke Test

Before routing, validate expected database access, authentication,
required objects/roles, read path, approved write test, storage, and
monitoring.

Use a dedicated lab validation object or approved production smoke-test
procedure. Do not modify arbitrary business data.

## 30. Redirect Application Traffic

After B is confirmed healthy as primary, change the approved routing
mechanism.

Routing must continue to exclude A.

Check connection pools, persistent sessions, DNS caching, proxy state,
driver retries, and application retries.

## 31. Ambiguous Transaction Outcomes

A client may receive a connection failure without knowing whether its
transaction committed on A before the failure.

``` text
client saw error != transaction definitely did not commit
```

Blindly replaying business operations can create duplicates.

Applications should use workload-appropriate idempotency, transaction
reconciliation, or duplicate protection.

## 32. Validate Application Recovery

Confirm new connections reach B, authentication succeeds, the correct
database is reached, read/write paths work, transactions complete, and
no application path reaches A.

Record the `SERVICE RESTORED` timestamp.

## 33. Service Restored Does Not Mean HA Restored

Immediately after promotion, B may be serving applications without a
standby.

Therefore:

``` text
SERVICE RESTORED
+
DEGRADED HA
```

can both be true.

## 34. Document RPO Outcome

After stabilization, classify the RPO outcome as `CONFIRMED`,
`POSSIBLE`, or `UNKNOWN`, supported by available evidence.

Record candidate pre-promotion evidence, relevant synchronous policy,
application reconciliation results, and any identified missing or
duplicate transactions.

## 35. Returning Former Primary

When A returns, keep it fenced and excluded from writable routing.

Do not assume it automatically becomes a standby.

## 36. Preserve Incident Evidence

Before destructive recovery where practical, preserve PostgreSQL logs,
system logs, timeline/history evidence, configuration, failure
timestamps, and storage/platform events.

## 37. Timeline Divergence

After B is promoted, A and B can have divergent histories.

A is not merely "behind." It must be reconciled before becoming a
standby.

## 38. Never Rejoin A Directly

Safe model:

``` text
A returns
   ↓
quarantine
   ↓
preserve evidence
   ↓
inspect
   ↓
rewind/rebuild decision
   ↓
configure as standby
   ↓
validate
   ↓
restore HA
```

## 39. `pg_rewind` Decision

``` text
Is pg_rewind positively eligible?
         |
     +---+---+
     |       |
    YES    NO / UNKNOWN
     |       |
  rewind    rebuild
```

Do not guess.

## 40. Rewind Prerequisites

The target requires either data checksums enabled or `wal_log_hints=on`,
with `full_page_writes=on`.

Required WAL/history and connectivity conditions must also be satisfied.

## 41. Rewind Source and Target

For the normal post-failover scenario:

``` text
SOURCE = B
current authoritative primary

TARGET = A
former primary being repaired
```

Confirm this explicitly before execution.

## 42. Rewind Safety Gate

Before rewind:

``` text
[ ] A quarantined
[ ] A excluded from application routing
[ ] required incident evidence preserved
[ ] rewind eligibility established
[ ] SOURCE confirmed as B
[ ] TARGET confirmed as A
[ ] required WAL/history available
[ ] authentication/connectivity validated
[ ] rebuild fallback available
[ ] operator approval recorded
```

If `pg_rewind` fails, stop, preserve evidence, assess the target, and
rebuild when required. Do not blindly retry.

## 43. Post-Rewind Configuration

Do not expose A immediately after rewind.

Modern PostgreSQL standby operation uses normal configuration parameters
plus `standby.signal`, not legacy `recovery.conf`.

If `pg_rewind -R` is used, validate generated standby configuration and
connection settings before starting A.

## 44. Fresh Rebuild Is a First-Class Path

If rewind eligibility, WAL history, or A's integrity is uncertain,
rebuild is a legitimate production recovery choice.

Create a new standby from B using the approved base-backup or
provisioning process.

## 45. Restore Replication

Once A is safely prepared, validate:

-   `pg_is_in_recovery()`;
-   WAL receiver;
-   WAL sender;
-   receive/replay progress;
-   slot topology;
-   storage;
-   monitoring.

## 46. Slots, Synchronous Replication, and Cascades

Review physical/logical slots and WAL retention deliberately. Do not
automatically drop slots during emergency recovery.

If synchronous replication was part of the design, revalidate
`synchronous_standby_names`, `application_name`, `sync_state`, and
applicable `synchronous_commit` policy.

For cascading replication, validate downstream recovery state, upstream
relationships, slots, sender capacity, monitoring, and synchronous
policy.

## 47. Monitoring and Backups

Monitoring should reflect B as primary and A as failed, fenced,
recovering, or standby.

Validate backup target, role discovery, credentials, schedule,
retention, and monitoring after the role change.

## 48. Restore HA Protection

Preferred final topology:

``` text
Application
    |
    v
Primary B
    |
    v
Standby A
```

or another healthy standby.

Only after replication protection, monitoring, backups, slot topology,
and applicable synchronous/logical policies are validated should
`HA RESTORED` be recorded.

If standby protection cannot immediately be restored, record:

``` text
STATUS: DEGRADED HA
Owner:
Risk:
Remediation:
Target completion:
```

## 49. Failback Is Separate

Once A is a healthy standby, emergency recovery is complete.

If A should become primary again later, use **6.12 --- Planned
Switchover**.

``` text
6.13 = emergency service + HA recovery
6.12 = controlled future role transition
```

## 50. Canonical Emergency Failover Flow

``` text
PRIMARY FAILURE DETECTED
          ↓
DECLARE INCIDENT
          ↓
FREEZE UNRELATED CHANGES
          ↓
COLLECT MULTI-SOURCE EVIDENCE
          ↓
IDENTIFY FAILURE DOMAIN
          ↓
ASSESS CANDIDATE(S)
          ↓
CAPTURE PRE-PROMOTION STATE
          ↓
ASSESS / ACKNOWLEDGE RPO EXPOSURE
          ↓
FENCE A
          ↓
VERIFY FENCING
          ↓
EMERGENCY GO / NO-GO
          ↓
PROMOTE B
          ↓
VERIFY B PRIMARY
          ↓
DATABASE SMOKE TEST
          ↓
REDIRECT APPLICATION
          ↓
HANDLE CONNECTION / TRANSACTION RECOVERY
          ↓
VALIDATE APPLICATION
          ↓
SERVICE RESTORED
          ↓
DOCUMENT RPO OUTCOME
          ↓
KEEP A QUARANTINED
          ↓
PRESERVE INCIDENT EVIDENCE
          ↓
REWIND / REBUILD DECISION
          ↓
RESTORE STANDBY
          ↓
VALIDATE REPLICATION / SLOTS / SYNC POLICY
          ↓
VALIDATE BACKUPS + MONITORING
          ↓
HA RESTORED
          ↓
CLOSE RECOVERY
```

## 51. Production Acceptance Checklist

Before declaring emergency recovery complete:

-   [ ] incident declared;
-   [ ] failure evidence recorded;
-   [ ] failure domain assessed;
-   [ ] candidate selected using documented evidence;
-   [ ] pre-promotion state captured where practical;
-   [ ] RPO exposure acknowledged;
-   [ ] A fenced and fencing positively verified;
-   [ ] emergency GO authorized;
-   [ ] B promoted and confirmed out of recovery;
-   [ ] database smoke test passed;
-   [ ] application routing targets B;
-   [ ] application validation passed;
-   [ ] ambiguous transaction outcomes addressed where applicable;
-   [ ] RPO outcome classified without unsupported claims;
-   [ ] A remains quarantined;
-   [ ] incident evidence preserved where appropriate;
-   [ ] A rewound/rebuilt or replacement standby created;
-   [ ] replication protection restored;
-   [ ] slot topology reviewed;
-   [ ] synchronous/logical policies reviewed if applicable;
-   [ ] monitoring reflects new roles;
-   [ ] backup behavior validated;
-   [ ] final topology documented;
-   [ ] degraded-HA risk has explicit ownership if HA is not yet
    restored.

1.  Unplanned failover begins with uncertainty.
2.  Failure detection is not promotion authorization.
3.  Primary unreachable does not mean primary fenced.
4.  Network partitions can leave the old primary writable.
5.  Fencing must be positively verified.
6.  `UNKNOWN` fencing state remains a split-brain risk.
7.  Preserve candidate evidence before promotion when practical.
8.  Unplanned failover may not provide a final primary WAL boundary.
9.  Asynchronous replication can expose acknowledged transactions to
    loss.
10. Synchronous durability depends on actual policy and transaction
    behavior.
11. Do not claim zero data loss without evidence.
12. Candidate freshness and infrastructure health both matter.
13. Promotion is the point of no simple return.
14. Validate B before routing applications.
15. Failed client requests can have ambiguous commit outcomes.
16. Service restoration and HA restoration are separate milestones.
17. Keep the former primary quarantined.
18. A former primary can have a divergent history, not merely be behind.
19. `pg_rewind` requires positive eligibility.
20. Confirm rewind source and target explicitly.
21. Rebuild is a legitimate first-class recovery path.
22. Review slots, synchronous policy, monitoring, and backups.
23. Explicitly track degraded HA.
24. Failback is a separate planned switchover.
25. Preserve evidence for RCA.
