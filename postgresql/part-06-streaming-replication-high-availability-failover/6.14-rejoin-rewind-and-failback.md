# 6.14 --- Rejoin, Rewind, and Failback

## Purpose

After an unplanned PostgreSQL failover, restoring application service on
the new primary is only part of recovery.

B is now the authoritative primary. A, the former primary, must remain
quarantined until its divergent history has been reconciled through an
evidence-based `pg_rewind` or fresh rebuild.

> **Rejoin does not automatically mean failback.**

## 1. Starting State

``` text
Application
     |
     v
Primary B

Former Primary A
       |
       v
Quarantined / Fenced
```

Explicitly establish:

``` text
AUTHORITATIVE PRIMARY = B
FORMER PRIMARY        = A
```

## 2. DISRUPTIVE-LAB Classification

Companion checklist: `labs/rejoin-failback-checklist.md`

Classification: **DISRUPTIVE-LAB**

The workflow may modify PostgreSQL data files, run `pg_rewind`, rebuild
a cluster, change recovery configuration, restart PostgreSQL, change
replication topology, and perform a later planned role transition.

## 3. Rejoin and Failback Are Separate

Rejoin:

``` text
B Primary
   |
   v
A Standby
```

Failback:

``` text
A Primary
   |
   v
B Standby
```

`B Primary → A Standby` is already a valid final production topology.

## 4. Why A Cannot Simply Restart

After B is promoted and accepts writes, A and B may have divergent
timelines. A is potentially divergent, not merely behind.

`pg_rewind` reconciles A to B's authoritative history; it does not merge
independently committed transactions.

## 5. Quarantine A and Protect B

A must remain excluded from all writable application paths through
rewind/rebuild and initial standby validation.

Before repairing A, verify B is healthy enough to remain authoritative:
PostgreSQL, application, storage, capacity, monitoring, and backup state
should be understood.

## 6. Preserve Evidence

Before destructive recovery, preserve useful PostgreSQL/system logs,
timeline/history evidence, configuration, failure timestamps, and
platform/storage events where required.

## 7. Rejoin Decision

``` text
Can A safely use pg_rewind?
          |
      +---+---+
      |       |
     YES    NO / UNKNOWN
      |       |
   REWIND    REBUILD
```

`UNKNOWN` is not permission to experimentally rewind.

## 8. Rewind Eligibility

Positive eligibility should establish shared ancestry, a valid timeline
relationship, target integrity, data checksums or `wal_log_hints`,
`full_page_writes`, required WAL/history, source connectivity, and
target accessibility.

The rewind target requires data checksums enabled or
`wal_log_hints = on`, with `full_page_writes = on`.

## 9. WAL and Timeline History

`pg_rewind` uses timeline history to determine divergence and requires
necessary target WAL.

If required WAL is absent from target `pg_wal` but available from
archive, the target-WAL restore path can be used:

``` bash
pg_rewind --restore-target-wal ...
```

If required WAL cannot be recovered, rebuild.

## 10. Target Shutdown State

A must remain fenced and unavailable to applications. `pg_rewind`
requires the target to reach the required clean state. By default it can
complete crash recovery in single-user mode when possible.

Do not casually disable this protection with `--no-ensure-shutdown`.

## 11. Source and Target

``` text
SOURCE = B
AUTHORITATIVE PRIMARY

TARGET = A
QUARANTINED FORMER PRIMARY
```

Before rewind verify that `--target-pgdata` identifies A,
`--source-server` identifies B, and B remains the application primary.

## 12. Credential Safety

Do not place passwords, credential-bearing `conninfo`, or secret
environment variables in operational evidence. Use approved
authentication and, where appropriate, a dedicated least-privilege
rewind role.

## 13. Dry Run

Where practical:

``` bash
pg_rewind   --dry-run   --target-pgdata="$PGDATA"   --source-server="<approved connection to B>"
```

A successful dry run supports the GO decision but does not replace it.

## 14. Rewind GO / NO-GO

``` text
[ ] B confirmed authoritative and stable
[ ] A quarantined and excluded from writable routing
[ ] required evidence preserved
[ ] rewind prerequisites positively established
[ ] WAL/history available or recoverable
[ ] SOURCE confirmed as B
[ ] TARGET confirmed as A
[ ] authentication/connectivity validated
[ ] dry run successful where practical
[ ] rebuild fallback available
[ ] operator approval recorded
```

## 15. Execute Rewind

**STATE-CHANGING / DESTRUCTIVE RECOVERY OPERATION**

``` bash
pg_rewind   --target-pgdata="$PGDATA"   --source-server="<approved connection to B>"
```

Do not use `--no-sync` for the production rejoin procedure.

If rewind fails: **STOP**, preserve output, do not start A, assess the
target, and rebuild when required. Do not blindly retry.

## 16. Rebuild Is a First-Class Path

Rebuild when rewind requirements are not satisfied, eligibility is
uncertain, required history cannot be obtained, target integrity is
uncertain, rewind fails, or operational risk favors a clean copy.

## 17. Rewind Success Is Not Startup Approval

After rewind, inspect standby configuration before A starts. Validate
`standby.signal`, `primary_conninfo`, `primary_slot_name`,
`application_name`, TLS/network settings, host-specific settings, and
archive/recovery settings.

Modern PostgreSQL uses `standby.signal`, not legacy `recovery.conf`.

If `pg_rewind -R` is used, inspect the generated `standby.signal` and
`postgresql.auto.conf` changes. Generated configuration is not
automatically validated configuration.

## 18. Start and Validate A

After configuration validation, start A and immediately run:

``` sql
SELECT pg_is_in_recovery();
```

Expected: `true`.

If false, keep A isolated and investigate.

A may still need WAL recovery after rewind. Validate the WAL receiver
and both receive and replay progress.

Safe receiver evidence includes status, slot name, sender host/port,
written/flushed LSN, latest end LSN, and message receipt time. Avoid
credential-bearing `conninfo`.

## 19. Receive, Replay, and Pause State

On A:

``` sql
SELECT
    pg_last_wal_receive_lsn(),
    pg_last_wal_replay_lsn(),
    pg_last_xact_replay_timestamp(),
    pg_get_wal_replay_pause_state();
```

Remember:

``` text
RECEIVED != REPLAYED
```

Normal recovery should not be unexpectedly paused. Avoid universal lag
thresholds; evaluate progress in workload and RPO context.

## 20. Primary-Side Replication

On B, validate A through `pg_stat_replication`, including application
name, client address, state, sent/write/flush/replay LSN, sync state,
and reply time.

## 21. Restore HA Policies

Review physical replication slots deliberately and do not automatically
drop stale-looking slots.

If synchronous replication is required, validate
`synchronous_standby_names`, `application_name`, `sync_state`, and
applicable `synchronous_commit` policy.

If logical failover slots are used, validate their readiness separately.
Physical HA health does not prove logical failover protection.

## 22. Monitoring and Backups

Monitoring should identify B as primary and A as standby. Validate role
discovery, replication/WAL/storage alerts, connections, and dashboards.

Validate backup target, role discovery, credentials, schedule,
retention, monitoring, and restore visibility.

## 23. HA Restoration Gate

``` text
[ ] B healthy primary
[ ] A in recovery
[ ] WAL receiver healthy
[ ] receive progressing
[ ] replay progressing
[ ] replay not unexpectedly paused
[ ] physical slot policy validated
[ ] synchronous policy validated if applicable
[ ] logical replication validated if applicable
[ ] monitoring correct
[ ] backups correct
```

Then record:

``` text
REJOIN COMPLETE
HA RESTORED
```

## 24. Decide Whether Failback Is Necessary

A healthy topology:

``` text
Application
     |
     v
Primary B
     |
     v
Standby A
```

can remain final.

Record:

``` text
Failback required: YES / NO
Reason:
Owner:
```

Do not fail back merely because A used to be primary.

## 25. Failback Is a New Planned Change

If failback is required, treat it as a separately approved planned
change. Stabilize and prove the rejoined topology before performing
another role transition.

Failback reuses the 6.12 Planned Switchover controls.

## 26. Failback Pre-Flight

``` text
[ ] B healthy primary
[ ] A healthy standby
[ ] replication stable
[ ] replay not paused
[ ] A capacity validated
[ ] maintenance coordinated
[ ] writer-quiesce procedure ready
[ ] routing procedure ready
[ ] monitoring active
[ ] rollback boundary understood
[ ] change approved
```

## 27. Quiesce Writers and Establish Final Boundary

Control all application, scheduled, batch, queue, and maintenance write
paths.

After writers are controlled, on B:

``` sql
SELECT pg_current_wal_flush_lsn()
       AS final_required_lsn;
```

On A, verify the replay LSN has reached the required boundary in the
appropriate history context.

Do not substitute "lag looks zero" for boundary evidence.

## 28. Fence B

Routing is not fencing.

Before promoting A, B must be prevented from accepting unintended writes
using the approved planned-switchover fencing mechanism. Positively
verify fencing.

## 29. Failback GO / NO-GO

``` text
[ ] application writes quiesced
[ ] final B boundary recorded
[ ] A replayed required boundary
[ ] B fenced
[ ] B fencing verified
[ ] routing ready
[ ] monitoring active
[ ] change authority approves
```

## 30. Promote and Verify A

**POINT OF NO SIMPLE RETURN**

``` sql
SELECT pg_promote(wait => true);
```

Then verify:

``` sql
SELECT pg_is_in_recovery();
```

Expected: `false`.

Perform the approved database smoke test before routing applications.

## 31. Redirect Clients and Restore B

After A passes validation, route applications to A and verify
connections, pools, DNS/proxy state, and read/write health.

Do not assume B automatically becomes a standby. Assess B and reconcile
it using the appropriate standby procedure. If histories diverged, apply
the same evidence-based rewind/rebuild decision.

## 32. Final HA Validation

``` text
[ ] A primary
[ ] B standby
[ ] receive/replay healthy
[ ] slots correct
[ ] synchronous policy correct
[ ] logical replication healthy if applicable
[ ] monitoring correct
[ ] backups correct
[ ] application routing correct
```

Then record:

``` text
FAILBACK COMPLETE
HA RESTORED
```

## 33. Rollback Boundaries

Before rewind, B can continue serving while A remains quarantined.

After a failed rewind, do not assume A's old state remains usable.

After successful rejoin, failback can simply be cancelled.

Before failback promotion, the planned change can be aborted through the
approved restoration procedure.

After A promotion, there is no simple rollback. Once A accepts writes, B
must be reconciled before reuse.

## 34. Canonical Rejoin Flow

``` text
B AUTHORITATIVE PRIMARY
A QUARANTINED
        ↓
PRESERVE EVIDENCE
        ↓
VERIFY B STABILITY
        ↓
ASSESS A
        ↓
VERIFY REWIND PREREQUISITES
        ↓
VERIFY WAL / TIMELINE HISTORY
        ↓
      REWIND ELIGIBLE?
       ┌─────┴─────┐
       ↓           ↓
      YES      NO / UNKNOWN
       ↓           ↓
   DRY RUN       REBUILD
       ↓           |
CONFIRM SOURCE=B   |
CONFIRM TARGET=A   |
       ↓           |
DESTRUCTIVE GO     |
       ↓           |
    REWIND         |
       └─────┬─────┘
             ↓
VALIDATE CONFIGURATION
             ↓
START A IN RECOVERY
             ↓
COMPLETE WAL RECOVERY
             ↓
VERIFY RECEIVE + REPLAY
             ↓
VERIFY SLOT / SYNC / LOGICAL HA
             ↓
VERIFY MONITORING + BACKUPS
             ↓
HA RESTORED
             ↓
REJOIN COMPLETE
```

## 35. Canonical Failback Decision

``` text
B PRIMARY
A HEALTHY STANDBY
HA RESTORED
      ↓
FAILBACK REQUIRED?
   ┌──┴──┐
   ↓     ↓
  NO    YES
   ↓     ↓
 STOP   NEW PLANNED CHANGE
         ↓
     QUIESCE WRITERS
         ↓
CAPTURE B FLUSH LSN
         ↓
VERIFY A REPLAY
         ↓
FENCE + VERIFY B
         ↓
PROMOTE A
         ↓
VERIFY + SMOKE TEST
         ↓
ROUTE APPLICATION
         ↓
RESTORE B AS STANDBY
         ↓
VALIDATE HA
         ↓
FAILBACK COMPLETE
```

## 36. Key Takeaways

-   Rejoin and failback are separate operations.
-   B is authoritative after failover.
-   A remains quarantined until reconciled.
-   `pg_rewind` reconciles histories; it does not merge transactions.
-   Rewind eligibility must be positively established.
-   Missing target WAL may be recoverable from archive.
-   Confirm source B and target A explicitly.
-   Use a dry run where practical.
-   Failed rewind is a hard stop; rebuild is a first-class path.
-   Rewind success does not authorize immediate startup.
-   Validate generated recovery configuration.
-   A must start in recovery.
-   Validate both WAL receive and replay.
-   Restore slot, synchronous, logical, monitoring, and backup policies
    deliberately.
-   `B Primary → A Standby` can be the final topology.
-   Failback is a separately approved planned change.
-   Quiesce writers and capture B's durable flush boundary before
    failback.
-   Routing is not fencing.
-   Verify promotion before routing.
-   Restore B safely as a standby after failback.
-   Declare HA restored only after protection is proven.
