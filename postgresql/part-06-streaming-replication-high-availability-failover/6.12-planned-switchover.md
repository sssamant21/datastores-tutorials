# 6.12 --- Planned Switchover

## Purpose

A planned PostgreSQL switchover intentionally transfers the primary role
from the current primary to a selected standby during a controlled
maintenance event.

Unlike emergency failover, a planned switchover begins with both systems
expected to be healthy. The objective is not simply to promote a
standby.

A production switchover should:

``` text
prepare
  ↓
validate
  ↓
quiesce all writers
  ↓
establish final WAL boundary
  ↓
confirm candidate replay
  ↓
fence old primary
  ↓
final GO / NO-GO
  ↓
promote candidate
  ↓
validate new primary
  ↓
redirect clients
  ↓
validate application
  ↓
recover former primary
  ↓
restore HA protection
```

The central safety requirement is:

> At no point should operators knowingly allow two writable PostgreSQL
> primaries to serve the same workload.

## 1. Learning Objectives

By the end of this tutorial, you should be able to:

-   distinguish planned switchover from emergency failover;
-   identify switchover prerequisites;
-   validate a promotion candidate;
-   establish GO / NO-GO gates;
-   inventory and quiesce database writers;
-   establish a durable final WAL boundary;
-   verify candidate replay against that boundary;
-   prevent split brain;
-   promote and validate a standby safely;
-   redirect database clients;
-   account for existing connections;
-   evaluate `pg_rewind` eligibility;
-   rebuild the former primary when rewind is inappropriate;
-   restore replication and HA protection;
-   understand phase-dependent rollback;
-   capture evidence throughout the change.

## 2. Planned Switchover vs Emergency Failover

Before:

``` text
Application
    |
    v
Primary A
    |
    v
Standby B
```

Target:

``` text
Application
    |
    v
Primary B
    |
    v
Standby A
```

During planned switchover both nodes should initially be reachable,
replication should be healthy, writes can be deliberately controlled,
synchronization can be verified, and routing can be coordinated.

## 3. Switchover Is More Than Promotion

Promotion alone does not perform a complete production switchover.

A complete procedure includes application coordination, writer control,
replication validation, WAL-boundary validation, fencing, promotion,
routing, service validation, former-primary recovery, and HA
restoration.

``` text
promotion != complete switchover
```

Classification: **DISRUPTIVE-LAB**

The procedure intentionally performs state-changing operations. Execute

## 5. Pre-Flight Gate

Validate:

-   current primary and candidate standby;
-   replication path;
-   WAL receive/replay progress;
-   replay pause state;
-   replication slots;
-   logical replication requirements if applicable;
-   configuration compatibility;
-   CPU, memory, storage, and network health;
-   candidate capacity;
-   application routing;
-   monitoring;
-   backup/recovery readiness.

If critical evidence is missing, the result is **NO-GO**.

## 6. Confirm Node Roles

On both servers:

``` sql
SELECT pg_is_in_recovery();
```

Expected before switchover:

``` text
Primary A → false
Standby B → true
```

If role ownership is uncertain, stop and investigate.

## 7. Validate Replication

On A:

``` sql
SELECT
    pid,
    application_name,
    client_addr,
    state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    sync_state,
    reply_time
FROM pg_stat_replication;
```

On B:

``` sql
SELECT
    pg_is_in_recovery(),
    pg_last_wal_receive_lsn(),
    pg_last_wal_replay_lsn(),
    pg_last_xact_replay_timestamp();
```

Also inspect `pg_stat_wal_receiver`.

`state = streaming` alone is not a sufficient readiness criterion.

## 8. Replay Pause Gate

On B:

``` sql
SELECT pg_is_wal_replay_paused();
```

Unexpected paused replay is **NO-GO** until understood and resolved.

## 9. Slot and Logical Replication Gates

Where slots are used, inspect `pg_replication_slots`, including
`active`, `restart_lsn`, `wal_status`, `safe_wal_size`, and
`invalidation_reason`.

If logical replication consumers or logical failover slots are involved,
validate their readiness separately before promotion. Physical standby
health does not automatically prove logical continuity.

## 10. Configuration and Capacity

Validate candidate configuration and production capacity, including
relevant connection, worker, WAL sender, slot, CPU, memory, storage,
IOPS, throughput, and network requirements.

A synchronized standby can still be operationally unsuitable for primary
workload.

## 11. Routing Is Not Fencing

``` text
ROUTING
Where new connections go

FENCING
Whether the old primary can still serve competing writes
```

A DNS or load-balancer change alone does not necessarily terminate
existing sessions.

A safe switchover requires both routing control and fencing.

## 12. Inventory Writers

Identify every process capable of writing:

-   application services;
-   background workers;
-   scheduled jobs;
-   ETL;
-   Kafka consumers;
-   CDC processes;
-   integration workers;
-   administrative scripts;
-   manual database users.

Application maintenance mode does not automatically stop every writer.

## 13. Quiesce Writes

Enter the approved write-freeze state and verify it using database and
application evidence.

If an active writer remains:

``` text
STOP
  ↓
identify owner and transaction
  ↓
wait / application-controlled completion /
explicitly approved termination
```

The procedure must not automatically terminate sessions.

## 14. Establish the Final WAL Boundary

After application writes are quiesced, capture a durable WAL boundary on
A:

``` sql
SELECT pg_current_wal_flush_lsn();
```

Record this as `FINAL_REQUIRED_LSN`.

## 15. Verify Candidate Replay

On B:

``` sql
SELECT pg_last_wal_replay_lsn();
```

The promotion gate requires:

``` text
candidate replay LSN >= FINAL_REQUIRED_LSN
```

Do not substitute "lag looks small", `state = streaming`, or only the
receive LSN.

The candidate must have replayed the required captured boundary.

## 16. Checkpoint Is Not Catch-Up Proof

A checkpoint does not prove B has replayed the required WAL. Use
explicit LSN evidence.

## 17. Fence A

Before B becomes writable, A must no longer be able to serve competing
application writes.

For the lab, stopping PostgreSQL on A provides a clear fencing
mechanism. Production implementations may use appropriate infrastructure
or orchestration fencing.

The important requirement is positive evidence that A cannot serve
competing writes.

## 18. Final GO / NO-GO

Immediately before promotion:

``` text
[ ] All intended writers quiesced
[ ] Long-running writer condition resolved
[ ] Final WAL boundary captured
[ ] B replayed required boundary
[ ] B healthy
[ ] A fenced
[ ] Routing change ready
[ ] Monitoring active
[ ] Operator approval recorded
```

Any mandatory failure means **STOP**.

## 19. Promotion: Point of No Simple Return

Before promotion, a controlled abort may still be possible.

After promotion, returning to A is another HA operation rather than
simply undoing one command.

Canonical lab promotion:

``` sql
SELECT pg_promote(wait => true);
```

This is **STATE-CHANGING / DISRUPTIVE**.

## 20. Validate B Before Routing

Verify:

``` sql
SELECT pg_is_in_recovery();
```

Expected: `false`.

Then validate database availability, expected objects/roles, storage
health, monitoring, and approved read/write smoke testing before
redirecting application traffic.

## 21. Redirect and Validate Clients

Move the approved routing mechanism to B and record the timestamp.

Check persistent sessions, connection pools, DNS caching, health checks,
driver retry behavior, and application transaction success.

A routing change does not prove all existing sessions moved.

## 22. Monitoring and Backup Validation

Monitoring must reflect the new roles:

``` text
Before: A = Primary, B = Standby
After:  B = Primary, A = fenced/recovering/Standby
```

Validate backup automation as well. Do not assume role- or host-specific
backup jobs automatically follow the new primary.

## 23. Keep A Fenced

After B becomes primary, A remains fenced until deliberately recovered.

Never restart A into the writable application path merely to see whether
it works.

## 24. Former-Primary Recovery

Choose deliberately between `pg_rewind` and a fresh standby rebuild.

``` text
Is A safely eligible for pg_rewind?
          |
      +---+---+
      |       |
     YES    NO / UNKNOWN
      |       |
   rewind    rebuild
```

If eligibility is uncertain, rebuilding is the conservative path.

## 25. `pg_rewind` Safety

`pg_rewind` is state-changing recovery work, not a diagnostic command.

Eligibility includes the required PostgreSQL configuration
prerequisites, including data checksums or `wal_log_hints=on`, with
`full_page_writes=on`.

The target cluster must be appropriately stopped before rewind.

If rewind fails, stop, preserve evidence, assess the target, and rebuild
when necessary. Do not blindly retry.

After rewind, inspect recovery configuration before starting A. Confirm
that A will follow B using the intended upstream endpoint, credentials,
slot, and application identity.

## 26. Fresh Rebuild Path

When rewind is unavailable, inappropriate, unsuccessful, or uncertain,
create a fresh standby from B using the approved base-backup or
provisioning process.

## 27. Restore Replication

After A is safely configured as a standby:

``` text
Primary B
    |
    v
Standby A
```

Validate:

-   `pg_is_in_recovery()` on A;
-   WAL receiver state on A;
-   sender state on B;
-   receive/replay progress;
-   slot topology;
-   storage capacity;
-   monitoring.

## 28. Synchronous and Cascading Topologies

If synchronous replication is used, revalidate the intended synchronous
relationship.

For cascading topologies, create explicit before/after dependency maps
because promotion can affect upstream relationships, slot placement,
sender requirements, monitoring, and recovery configuration.

## 29. Rollback Is Phase-Dependent

**Before fencing/promotion:** a clean abort may be possible with A
remaining primary.

**A fenced, B not promoted:** A may potentially be restored through a
controlled abort after state and routing validation.

**B promoted:** there is no simple command reversal. If B has accepted
writes, do not restart A as the original primary. Returning service to A
requires another controlled HA transition.

## 30. Evidence Package

Capture:

**Pre-change** - roles; - replication relationship; - candidate
health; - slot state; - capacity/configuration checks; - writer
inventory; - monitoring status.

**Transition** - write-freeze evidence; - final primary flush LSN; -
candidate replay LSN; - fencing evidence; - final GO approval; -
promotion timestamp.

**Post-promotion** - new-primary role evidence; - smoke-test result; -
routing timestamp; - application validation; - monitoring/backup
validation; - former-primary recovery method; - restored replication
evidence; - final topology.

## 31. Canonical Switchover Flow

``` text
PRE-FLIGHT
    ↓
ROLE / TOPOLOGY VALIDATION
    ↓
CAPACITY + CONFIGURATION VALIDATION
    ↓
LOGICAL SLOT CHECK, IF APPLICABLE
    ↓
INVENTORY WRITERS
    ↓
QUIESCE ALL WRITERS
    ↓
RESOLVE ACTIVE WRITERS
    ↓
CAPTURE FINAL PRIMARY FLUSH LSN
    ↓
WAIT FOR B REPLAY >= REQUIRED LSN
    ↓
FENCE A
    ↓
FINAL GO / NO-GO
    ↓
PROMOTE B
    ↓
VERIFY B IS PRIMARY
    ↓
DATABASE SMOKE TEST
    ↓
REDIRECT CLIENTS
    ↓
VALIDATE APPLICATION
    ↓
VALIDATE MONITORING + BACKUPS
    ↓
KEEP A FENCED
    ↓
REWIND ELIGIBILITY DECISION
       ├── eligible → pg_rewind
       └── otherwise → fresh rebuild
    ↓
CONFIGURE A TO FOLLOW B
    ↓
START A AS STANDBY
    ↓
VALIDATE REPLICATION
    ↓
VALIDATE SYNC POLICY, IF APPLICABLE
    ↓
VALIDATE FINAL HA TOPOLOGY
    ↓
CLOSE MAINTENANCE
```

## 32. Preferred Completion State

Application success on B is not the preferred final acceptance state.

Preferred:

``` text
Application
    |
    v
Primary B
    |
    v
Standby A
```

with replication progressing, monitoring healthy, backup behavior
validated, and intended HA policy restored.

If standby protection cannot be restored before maintenance closure,
explicitly record **DEGRADED HA** with an owner and remediation plan.

## 33. Key Takeaways

1.  Planned switchover is a controlled HA transition, not merely
    promotion.
2.  Both nodes should begin healthy.
3.  Inventory and quiesce all writers.
4.  Capture a durable final WAL boundary.
5.  Validate candidate replay against that boundary.
6.  Received WAL is not equivalent to replayed WAL.
7.  A checkpoint is not proof of catch-up.
8.  Routing and fencing solve different problems.
9.  Fence the old primary before promotion.
10. Promotion is the point of no simple return.
11. Validate the new primary before routing clients.
12. Existing connections require explicit consideration.
13. Keep the former primary fenced until deliberately recovered.
14. `pg_rewind` is conditional and state-changing.
15. Rebuild when rewind eligibility is uncertain.
16. Revalidate slots, synchronous policy, monitoring, and backups.
17. Capture evidence throughout the change.
18. Restore standby protection before considering HA fully restored.
