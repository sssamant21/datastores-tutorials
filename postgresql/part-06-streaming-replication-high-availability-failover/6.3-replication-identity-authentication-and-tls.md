# Part 6.3 — Replication Identity, Authentication, and TLS

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition — Pending Repository Validation  
**Audience:** DBAs, DBREs, SREs, Platform Engineers  
**Lab:** `labs/replication-access-check.sql`  
**Classification:** Production-focused; lab is SAFE-READ

## Purpose
Physical streaming replication creates a privileged trust path. Production readiness requires a dedicated least-privilege identity, restricted `pg_hba.conf` access, strong authentication, TLS server verification, protected secret handling, and controlled credential/certificate rotation.

> **Production rule:** grant only the identity, network path, privilege, and trust required by the approved replication topology.

Part 6.3 does not build the standby; construction begins in Part 6.4.

## Replication Trust Path
```text
Standby
  │ approved network + verified TLS + dedicated credential
  ▼
pg_hba.conf
  │ matching replication rule
  ▼
Replication role
  │ LOGIN + REPLICATION
  ▼
Primary WAL sender
```

Each layer is independent: network controls origin, TLS protects transport/server identity, HBA authorizes the connection class, the role identifies the principal, and `REPLICATION` authorizes replication.

## Dedicated Replication Identity
Conceptual example only:
```sql
CREATE ROLE replicator
WITH LOGIN REPLICATION NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS;
```
A dedicated connection identity normally needs `LOGIN` and `REPLICATION`; unrelated administrative privileges should not be granted merely to make replication work. `REPLICATION` is itself highly privileged and must be tightly controlled.

## Replication HBA Rules
Physical replication connections use the special `replication` value in the database field.

Conceptual pattern:
```text
hostssl  replication  replicator  <approved-standby-CIDR>  scram-sha-256
```
Avoid broad patterns such as:
```text
host  replication  all  0.0.0.0/0  trust
```

HBA order matters: PostgreSQL uses the first matching record. Review connection type, replication selector, user, CIDR, authentication method, options, ordering, and overlapping rules.

## Safe HBA Inspection
PostgreSQL 18 exposes `pg_hba_file_rules`, including rule/file/line metadata, type, database, user, address, authentication method, options, and parse errors. The view represents current file contents, which can differ from rules currently loaded by the server. Access is restricted by default. If evidence is inaccessible, record **UNKNOWN** rather than elevating privileges solely for the lab.

## SCRAM and TLS
For password authentication, use the approved strong-authentication policy such as `scram-sha-256`. Password strength does not prove server identity; verified TLS is a separate control.

libpq supports:
```text
disable | allow | prefer | require | verify-ca | verify-full
```

`verify-ca` validates the certificate chain. `verify-full` additionally validates the requested server identity. For security-sensitive production replication, prefer `verify-full` when the certificate/DNS architecture supports it. Do not treat `sslmode=require` as equivalent to hostname verification.

## Certificate Trust
Document the issuing CA, trust-chain deployment, server certificate identity, hostname/IP used by the standby, validity period, renewal owner, expiry monitoring, and rotation procedure. Client certificates are optional architecture controls, not universal streaming-replication requirements.

## primary_conninfo and Secrets
A standby commonly uses `primary_conninfo`, conceptually:
```text
primary_conninfo='host=<primary> port=5432 user=<replication-role> sslmode=verify-full ...'
```
Never collect complete `primary_conninfo` as routine acceptance evidence. It can expose credentials or sensitive connection metadata.

Do not expose replication credentials through Git, shell history, screenshots, tickets, chat, CI logs, acceptance output, broadly readable files, or unnecessary environment variables. Password/passfiles or an approved secret manager must be protected according to the host and organizational policy.

## Rotation
Credential rotation must be staged: prepare replacement → deploy securely → controlled reconnect → verify replication → observe → revoke obsolete credential.

Certificate rotation must similarly prepare trust before retiring old material: deploy CA/intermediate trust → install new certificate → validate hostname/IP → test TLS/reconnect → verify replication → observe → retire obsolete trust.

## Failure Model
| Condition | Result |
|---|---|
| Wrong role / missing LOGIN or REPLICATION | FAIL |
| Unapproved source / no matching HBA rule | FAIL |
| Broad unsafe HBA rule | FAIL/REVIEW |
| Authentication failure | FAIL |
| TLS unavailable when required | FAIL |
| Untrusted CA / hostname mismatch / expired certificate | FAIL |
| Secret unavailable | FAIL |
| HBA evidence inaccessible | UNKNOWN |
| Standby trust evidence absent | UNKNOWN |
| Rotation procedure untested | UNKNOWN |

Never convert UNKNOWN to PASS by assumption.

## Monitoring and Evidence
Acceptance evidence may inspect `pg_roles`, `pg_settings`, `pg_stat_ssl`, and `pg_hba_file_rules`. `pg_stat_ssl` describes current connections; it does not prove how a future standby will connect. Likewise, `ssl=on` does not prove the standby will use `verify-full`.

## Managed Services
Managed PostgreSQL can abstract HBA, certificates, replication identities, networking, and endpoints. Preserve the same objectives—least privilege, network restriction, authentication, transport verification, rotation, and evidence—using provider-supported mechanisms.

## Key Takeaways
- Replication access is a privileged trust path.
- Prefer a dedicated `LOGIN + REPLICATION` identity over a general superuser.
- Restrict HBA rules by identity and approved source network.
- HBA ordering is part of the security model.
- Encryption and server identity verification are different controls.
- `verify-full` adds server-name verification.
- Client certificates are optional.
- Never collect credential-bearing `primary_conninfo` as routine evidence.
- Rotation must be staged and validated.
- Missing, stale, inaccessible, or contradictory evidence remains UNKNOWN.
