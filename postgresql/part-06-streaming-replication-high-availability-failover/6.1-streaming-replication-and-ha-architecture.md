## Mission

Build the architectural foundation required to operate PostgreSQL
physical streaming replication safely in production. This section
explains primary/standby roles, WAL flow, asynchronous and synchronous
replication at an architectural level, failure domains, service
endpoints, writable authority, failover boundaries, and the relationship
between replication, high availability, backup, and disaster recovery.

This tutorial does **not** build a standby, change replication
configuration, promote a server, or perform failover. Those operations
belong to later Part 6 sections.

## 1. The Production Problem

A single PostgreSQL server can be healthy and well backed up yet still
represent a service-availability risk.

A basic HA topology introduces another PostgreSQL server capable of
maintaining a physical copy of the primary:

``` text
Application
    |
    v
Service / Database Endpoint
    |
    v
+----------------------+
| Primary              |
| writable authority   |
+----------+-----------+
           |
           | WAL
           v
+----------------------+
| Standby              |
| recovery / read-only |
+----------------------+
```

The presence of a standby does not by itself create a complete HA
service. Production HA also requires decisions about failure detection,
promotion authority, fencing, client routing, validation, recovery
objectives, and reintegration.

## 2. Primary and Standby Roles

The **primary** is the PostgreSQL server currently authorized to accept
the application's writes.

A **physical standby** follows the primary by applying WAL generated by
the primary. While the standby remains in recovery it is not a second
independent writable primary.

A hot standby can serve read-only queries while recovery continues,
subject to recovery behavior and conflicts discussed later in Part 6.

The most important operational invariant is:

``` text
exactly one writable authority
```

A topology with two servers capable of independently accepting writes
after a role transition is not a healthy HA topology.

## 3. WAL Is the Replication Transport

PostgreSQL physical streaming replication is based on WAL.

At a conceptual level:

``` text
Application transaction
        |
        v
      Primary
        |
        v
   WAL generated
        |
        v
    WAL sender
        |
        | network stream
        v
   WAL receiver
        |
        v
 receive / write / flush
        |
        v
      replay
        |
        v
     Standby
```

Physical replication follows cluster-level WAL changes rather than
replaying application SQL statements as a logical change stream.

Receive, write, flush, and replay positions are distinct operational
concepts. They must not be treated as interchangeable evidence of
replication health or durability. Detailed measurement belongs to Parts
6.5 and 6.6.

## 4. Streaming Replication

With streaming replication, the standby can receive WAL records from the
primary as they are generated rather than depending only on completed
WAL segment archival.

A healthy stream is one component of HA readiness, but:

``` text
streaming = healthy transport state
streaming != complete HA
streaming != zero data loss
streaming != application availability
```

The production question is not merely whether WAL is flowing. It is
whether the entire service can preserve a single writable authority and
meet its declared recovery objectives during failure.

## 5. Asynchronous Replication

Streaming replication is commonly operated asynchronously.

Architecturally:

``` text
Client
  |
  v
Primary
  |
  +---- transaction acknowledgement ----> Client
  |
  +---- WAL propagation ----------------> Standby
```

The primary can acknowledge a transaction without waiting for the
standby to confirm the corresponding replication stage.

This reduces coupling between primary transaction latency and
standby/network health, but creates a potential data-loss window if the
primary fails before required WAL reaches the standby.

Therefore:

``` text
asynchronous replication does not imply RPO = 0
```

The actual exposure depends on workload, WAL progress, failure timing,
topology, and operating policy.

## 6. Synchronous Replication

PostgreSQL can be configured so transaction completion waits for
specified standby acknowledgement according to the configured
synchronous-replication policy.

Conceptually:

``` text
Client
  |
  v
Primary
  |
  +---- WAL ----------------------------> Standby
  |                                        |
  |<---------- configured acknowledgement--+
  |
  +---- transaction acknowledgement ----> Client
```

Do not reduce this to:

``` text
synchronous = zero data loss
```

PostgreSQL provides different acknowledgement semantics through
configuration such as `synchronous_standby_names` and
`synchronous_commit`. The exact durability, latency, and availability
behavior must be evaluated from the actual configuration.

Part 6.7 covers that policy in depth.

## 7. Hot Standby

A standby operating with hot-standby capability can accept read-only
sessions while WAL recovery continues.

This can support:

-   reporting
-   read scaling
-   operational queries
-   workload isolation

However, a hot standby is still replaying changes from the primary. Read
workloads can interact with recovery and create conflicts. Staleness and
replay progress also matter.

Part 6.9 covers those operational trade-offs.

## 8. Failure Domains

Replication only improves availability when the topology survives the
failures it is designed to tolerate.

Weak topology:

``` text
Physical Host A
├── Primary
└── Standby
```

Loss of Host A removes both instances.

Another correlated design may be:

``` text
Failure Domain A
├── Primary
└── Standby
```

A single infrastructure event can still remove both copies.

Production assessment should identify at least:

-   primary failure domain
-   standby failure domain
-   shared compute dependencies
-   shared storage dependencies
-   shared network dependencies
-   shared power/infrastructure dependencies
-   routing dependencies
-   control-plane dependencies
-   backup dependencies

A standby existing in the inventory is not sufficient evidence that
failure-domain isolation exists.

## 9. Service Endpoints and Client Routing

Applications normally need a stable mechanism for locating the current
writable database service.

``` text
Clients
   |
   v
Service Endpoint
   |
   v
Current Writable Primary
```

After a role transition, database promotion alone does not guarantee
that applications are using the correct server.

HA design must account for:

-   writer endpoint ownership
-   reader endpoints where applicable
-   connection pools
-   DNS/proxy/load-balancer behavior
-   stale connections
-   health checks
-   routing changes
-   application validation

Implementation-specific routing belongs to later operational sections.

## 10. Promotion Is Not Complete Failover

Promotion changes a standby's PostgreSQL role. Production failover is
broader.

A safe conceptual sequence is:

``` text
detect / declare failure
        |
        v
establish promotion authority
        |
        v
fence former primary
        |
        v
promote selected standby
        |
        v
route clients
        |
        v
validate database service
        |
        v
validate application
        |
        v
observe and preserve evidence
```

The exact sequence depends on the HA implementation, but the safety
objective is constant: do not allow an old primary and a promoted
standby to become competing writable authorities.

## 11. Fencing and Split-Brain Prevention

Consider:

``` text
Primary A
   |
   X  failure / isolation

Standby B
   |
   v
Promoted to Primary B
```

If Primary A later returns and can still accept writes:

``` text
Primary A  <--- writes
Primary B  <--- writes
```

the service has lost its single-writer invariant.

This is the class of failure commonly described as split brain.

A production design must define how the former primary is prevented from
serving writes before the promoted standby becomes the accepted writable
service. The mechanism is implementation-specific and is treated
operationally in Part 6.13.

## 12. Replication, HA, Backup, and DR

These concepts solve different problems.

  Capability          Primary purpose
  ------------------- ---------------------------------------------------
  Replication         Maintain another PostgreSQL copy through WAL
  High availability   Maintain service through component failure
  Failover            Transfer service/writable authority after failure
  Backup              Maintain an independent recoverable copy
  Disaster recovery   Restore service after a larger disruptive event

Replication must not replace the independent recovery path established
in Part 5.

For example, unwanted or corrupting changes can propagate through
replication. A healthy standby is therefore not proof that historical
recovery requirements are satisfied.

## 13. RPO and RTO

**Recovery Point Objective (RPO)** describes the acceptable data-loss
objective.

**Recovery Time Objective (RTO)** describes the acceptable
service-restoration objective.

Neither should be inferred from statements such as:

``` text
replication is streaming
standby is healthy
promotion worked
SQL connection succeeded
```

A production design declares objectives and later measures actual
outcomes under controlled tests.

Part 6.15 will require measured acceptance evidence.

## 14. HA Evidence

Architecture decisions should be based on evidence.

Useful categories include:

``` text
Topology
Roles
Failure domains
Replication mode
Routing
Promotion authority
Fencing mechanism
Declared RPO
Declared RTO
Independent recovery path
Operational ownership
```

Evidence may be:

``` text
PASS
FAIL
UNKNOWN
```

`UNKNOWN` is mandatory when evidence is missing, stale, inaccessible, or
contradictory. Guessing converts an architecture review into an unsafe
assumption.

## 15. Core Production Invariants

Part 6 uses these invariants throughout the remaining tutorials.

### Invariant 1 --- One writer

Exactly one server owns writable authority.

### Invariant 2 --- Fence before competing writes

A promoted standby must not coexist with an unfenced former primary
capable of serving writes.

### Invariant 3 --- Replication health is not application health

A green replication state does not prove routing, authentication,
connection pools, queries, or application behavior are healthy.

### Invariant 4 --- Replication is not backup

Maintain the independent Part 5 backup and recovery path.

### Invariant 5 --- Promotion is not complete failover

Promotion is one database operation within a larger service transition.

### Invariant 6 --- RPO/RTO are declared and tested

Do not infer them from topology or process state.

### Invariant 7 --- Failure domains are explicit

A standby must be evaluated against correlated infrastructure failures.

### Invariant 8 --- Missing evidence is UNKNOWN

Do not convert absence of evidence into PASS.

## 16. Architecture Review Example

Given:

``` text
                    Application
                         |
                         v
                   Writer Endpoint
                         |
                         v
                +----------------+
                | Primary A      |
                | Zone A         |
                +-------+--------+
                        |
                    async WAL
                        |
                        v
                +----------------+
                | Standby B      |
                | Zone B         |
                +----------------+
```

Do not immediately call the design HA-ready.

Ask:

1.  Who decides that A has failed?
2.  Who is authorized to promote B?
3.  How is A fenced?
4.  How does the writer endpoint move?
5.  What happens to existing application connections?
6.  What transaction-loss exposure exists with asynchronous replication?
7.  What RPO has the business accepted?
8.  What RTO has been declared?
9.  Are Zone A and Zone B truly independent for the intended failure?
10. Does an independent backup/recovery path exist?
11. Who owns the failover decision?
12. What evidence proves each answer?

Any unanswered safety-critical item remains `UNKNOWN`.

## 17. Production Checklist

Before accepting an HA architecture:

``` text
[ ] Writable authority is explicitly identified
[ ] Standby role is explicitly identified
[ ] Replication mode is known
[ ] Failure domains are documented
[ ] Correlated dependencies are documented
[ ] Writer endpoint/routing mechanism is known
[ ] Promotion authority is defined
[ ] Fencing mechanism is defined
[ ] Split-brain prevention is documented
[ ] Declared RPO exists
[ ] Declared RTO exists
[ ] Independent backup/recovery path exists
[ ] Operational ownership exists
[ ] Missing evidence is classified UNKNOWN
```
