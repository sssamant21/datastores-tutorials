# Part 6.5 — Verify Streaming and WAL Replay

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition — Pending Repository Validation  
**Lab:** `labs/streaming-replay-check.sql`  
**Classification:** SAFE-READ

## Purpose
Part 6.4 built a physical standby. Part 6.5 proves that the expected primary/standby topology is actually transporting and replaying WAL.

```text
WAL generated -> sent -> written -> flushed -> replayed -> application-visible change
```

Each stage is distinct.

## Scope
This tutorial covers role evidence, WAL sender/receiver evidence, sent/write/flush/replay LSN semantics, standby receive/replay positions, timeline context, evidence freshness/permissions, optional controlled-write verification, and PASS/FAIL/UNKNOWN interpretation.

Lag thresholds belong to 6.6, synchronous policy to 6.7, slot lifecycle to 6.8, cascading topology to 6.10, and failover to 6.12+.

## Observed Role
```sql
SELECT pg_is_in_recovery();
```

| Expected | Observed | Result |
|---|---:|---|
| Primary | false | matches |
| Standby | true | matches |
| Primary | true | FAIL |
| Standby | false | FAIL / STOP |
| unavailable | unknown | UNKNOWN |

The lab reports observed role; operator intent must come from the approved topology. Suspected multiple writers is a fencing/incident condition, not a reason to promote another node.

## Primary WAL Sender Evidence
`pg_stat_replication` provides one row per WAL sender. Relevant evidence includes `application_name`, `client_addr`, `state`, `sent_lsn`, `write_lsn`, `flush_lsn`, `replay_lsn`, `sync_state`, and `reply_time`.

```text
sent_lsn -> write_lsn -> flush_lsn -> replay_lsn
```

These stages are not interchangeable. `streaming` is expected steady-state evidence; `catchup` can represent active replication still catching up. Only directly connected replication clients appear; cascading topology is covered in 6.10.

## Standby WAL Receiver Evidence
`pg_stat_wal_receiver` supplies receiver/upstream evidence. The lab selects operational fields such as status, receive/timeline positions, written/flushed positions, message times, slot name, sender host, and sender port.

It deliberately excludes `conninfo`.

`written_lsn` is not durable-flush evidence; `flushed_lsn` represents a later durability stage.

## Receive and Replay
```sql
SELECT
    pg_last_wal_receive_lsn(),
    pg_last_wal_replay_lsn(),
    pg_last_xact_replay_timestamp();
```

Receiving WAL and replaying WAL are different. A standby may receive WAL while replay remains behind.

## Idle-System Trap
An unchanged replay LSN does not prove failure when the primary generated no new WAL. Likewise, an old replay transaction timestamp is not a universal lag metric. Quantitative lag analysis belongs to 6.6.

## Statistics Freshness
Do not repeatedly sample statistics inside one long-running transaction and assume every query is a fresh observation. Use fresh observations when comparing state over time. Stale evidence is UNKNOWN, not PASS.

## Permissions
The lab does not grant privileges or escalate itself. Use an approved monitoring/DBRE identity. If required evidence is inaccessible, classify it as UNKNOWN.

## Timeline and Topology
Receiver timeline and upstream identity are context for validation. Unexpected topology/timeline evidence must be investigated, not normalized into PASS. Rewind/rejoin procedures are covered later.

## Optional Controlled-Write Verification
For an explicitly approved validation relation only:

```text
primary write -> commit -> WAL transport -> replay -> exact marker visible on standby
```

Do not create tables or insert markers into an arbitrary production application schema. The canonical SQL lab performs no writes.

## Decision Model
**PASS:** required evidence is available, fresh enough, and consistent with the approved topology.

**FAIL:** evidence directly contradicts a required condition.

**UNKNOWN:** required evidence is missing, inaccessible, stale, or lacks topology context.

**CONTRADICTORY:** evidence sources disagree. Investigate; never convert this to PASS.

## Failure Scenarios
Investigate an unexpected writable standby, primary in recovery, missing sender/receiver, unexpected sender/receiver state, missing receive/replay evidence, replay not progressing during known WAL generation, unexpected upstream/timeline, permission-limited evidence, stale observations, failed controlled marker, or suspected multiple writers.

No automatic remediation belongs here.

## Key Takeaways
- Process health is not replication proof.
- Sent, written, flushed, and replayed WAL are distinct.
- WAL receipt is not WAL replay.
- `written_lsn` is not durable-flush evidence.
- Old replay timestamps do not necessarily mean lag.
- Missing, stale, inaccessible, or contradictory evidence is not PASS.
- Quantitative lag analysis follows in 6.6.
