# Part 6.2 — Replication Prerequisites and Change Planning

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition — Pending Repository Validation  
**Audience:** DBAs, DBREs, SREs, Platform Engineers  
**Lab:** `labs/replication-prerequisites-check.sql`  
**Classification:** Production-focused; lab is SAFE-READ

## 1. Purpose

Physical streaming replication should not begin with `pg_basebackup` or a configuration edit. It should begin with a readiness decision.

This tutorial establishes the prerequisite and change-control gate that must be satisfied before building a PostgreSQL physical standby. It focuses on compatibility, capacity, network and platform dependencies, WAL sender readiness, optional slot capacity, recovery protection, change ownership, stop conditions, and evidence.

> **Production rule:** ready to configure does not automatically mean ready to change production.

Part 6.2 does not create replication identities, edit `pg_hba.conf`, configure TLS, build a standby, measure lag, or perform failover. Those activities belong to later Part 6 sections.

## 2. Relationship to Earlier Parts

Part 6 assumes the operating practices established in Parts 1–5.

- Part 2 supplies installation, service-management, capacity, and production-configuration fundamentals.
- Part 4 supplies roles, `pg_hba.conf`, least privilege, and TLS fundamentals.
- Part 5 supplies physical backup, WAL, recovery readiness, RPO/RTO, and the rule that replication is not backup.
- Part 6.1 supplies the HA architecture and single-writer model.

Part 6.2 applies those controls to a replication change rather than reteaching them.

## 3. Define the Intended Topology First

Record the proposed topology before inspecting parameters.

At minimum capture:

| Item | Required evidence |
|---|---|
| Current primary | Host/service identity and PostgreSQL cluster identity |
| Proposed standby | Host/service identity and intended role |
| Environment | Production, staging, lab, or other controlled scope |
| Replication mode | Physical streaming replication |
| Expected topology | Direct primary-to-standby for this stage |
| Failure domains | Placement evidence from infrastructure |
| Application endpoint | How clients currently reach the writer |
| Change owner | Person/team authorized to execute |
| Validation owner | Person/team responsible for acceptance |
| Rollback authority | Person/team allowed to stop/reverse the change |

Do not infer topology from hostnames alone.

## 4. PostgreSQL Version and Platform Compatibility

Physical log shipping operates on PostgreSQL's binary/WAL representation. Primary and standby planning must therefore treat major-version compatibility as a hard prerequisite.

For the Part 6 lab, the target is PostgreSQL 18. Record both:

```sql
SHOW server_version;
SHOW server_version_num;
```

Do not approve a mixed-major physical replication design without a separately supported migration mechanism.

Primary and standby systems should also be sufficiently similar for reliable operation. Tablespaces require special attention because tablespace path names are propagated unchanged. If tablespaces are used, compatible mount paths must exist on the standby.

The SQL lab can inventory tablespaces, but operating-system mount validation requires external evidence.

## 5. Capacity Is a Budget, Not a Boolean

A server can satisfy a PostgreSQL minimum and still be unsafe for production replication.

Evaluate:

- current database size and growth;
- WAL generation characteristics;
- primary and standby disk capacity;
- disk free-space/headroom;
- storage latency and throughput expectations;
- CPU and memory headroom;
- expected replication clients and base-backup activity;
- current and expected WAL sender consumption;
- replication-slot capacity when slots are part of the design;
- monitoring capacity and retention.

Use this model:

```text
current utilization
+ expected replication overhead
+ failure/recovery overhead
+ operational safety margin
= required capacity
```

Core PostgreSQL SQL cannot prove filesystem free space, storage latency, cloud volume limits, or network throughput. Missing infrastructure evidence must remain **UNKNOWN**.

## 6. WAL-Level Readiness

Physical streaming replication requires WAL sufficient for replication.

Inspect:

```sql
SHOW wal_level;
```

For PostgreSQL 18, `wal_level = replica` is sufficient for physical streaming replication. `logical` is also technically sufficient because it includes the information provided by `replica`, but it may generate additional WAL for workloads that use logical-decoding-related features.

`wal_level = minimal` is not acceptable for streaming physical replication.

`wal_level` is a server-start parameter. If a change is required, the change plan must account for a PostgreSQL restart rather than treating it as a reload-only operation.

## 7. WAL Sender Capacity

Inspect:

```sql
SHOW max_wal_senders;
```

`max_wal_senders` controls the maximum number of concurrent WAL sender processes used by standby connections and streaming base-backup clients.

A value greater than zero is not by itself a production PASS.

Capacity must account for:

- planned standbys;
- simultaneous streaming base backups;
- existing replication clients;
- temporary disconnected/orphaned sender occupancy;
- operational reserve.

The assessment therefore compares configured capacity with known demand. If demand is not known, the result is **UNKNOWN**, not PASS.

`max_wal_senders` is a server-start parameter.

A standby that may later become primary must also be configured with an appropriate sender capacity for the intended post-promotion topology.

## 8. Replication Slots Are Conditional

Physical replication slots can protect required WAL from being removed before a standby consumes it, but slots are not mandatory for every streaming-replication design.

If the architecture plans to use slots, inspect:

```sql
SHOW max_replication_slots;
```

and inventory:

```sql
SELECT *
FROM pg_replication_slots;
```

For 6.2, the objective is only to determine whether slot capacity exists for the proposed design.

Detailed slot lifecycle, retained-WAL risk, invalidation, `max_slot_wal_keep_size`, and remediation belong to **Part 6.8**.

`max_replication_slots` is a server-start parameter.

## 9. WAL Retention and Archive Dependencies

Inspect the current retention-related configuration, including:

```text
wal_keep_size
max_slot_wal_keep_size
archive_mode
archive_command
archive_library
```

Do not interpret these as universally required for streaming replication.

- `wal_keep_size` can retain additional past WAL for standby use.
- a replication slot can retain WAL required by its consumer;
- WAL archiving can provide another source of WAL in an architecture designed to use archives;
- these mechanisms have different failure and capacity characteristics.

Part 6.2 records the current state and whether the proposed design has a defined retention strategy. Detailed retention operations remain in Part 6.8, while backup/archive recovery remains governed by Part 5.

## 10. Connection Budget

Do not confuse ordinary client capacity with WAL sender capacity.

Record:

```sql
SHOW max_connections;
SHOW superuser_reserved_connections;
```

and inspect current database sessions.

The goal is to understand whether the replication change occurs on an already resource-constrained server. WAL senders have their own `max_wal_senders` limit, so `max_connections` must not be used as a substitute for sender-capacity analysis.

Connection-budget evidence is contextual: a current session count alone cannot prove future capacity.

## 11. Network, DNS, and Time Dependencies

The future standby must be able to reach the source through the approved network path.

Before implementation, externally validate:

- source and destination addresses/names;
- DNS resolution;
- routing;
- firewall/security rules;
- required port reachability;
- expected latency and stability;
- time synchronization;
- proxy/load-balancer behavior, if applicable.

A SQL session on the primary cannot prove end-to-end connectivity from the future standby. Therefore the SAFE-READ lab records these controls as **UNKNOWN — external evidence required** unless independent evidence is attached.

Authentication rules and TLS configuration are intentionally deferred to Part 6.3.

## 12. Tablespace Compatibility

Inventory non-default tablespaces:

```sql
SELECT spcname, pg_tablespace_location(oid)
FROM pg_tablespace
ORDER BY spcname;
```

If user-defined tablespaces exist, validate corresponding standby storage and paths before standby creation.

SQL evidence from the primary proves the configured path, not that the destination mount exists or has adequate capacity. Destination readiness remains an external gate.

## 13. Configuration Change Inventory

For every proposed parameter change record:

| Field | Required |
|---|---|
| Parameter | Exact PostgreSQL setting |
| Current value | Evidence from target |
| Proposed value | Approved intended value |
| Reason | Why the change is needed |
| Context | Restart/reload/session behavior from `pg_settings` |
| Source | Active configuration source |
| Risk | Expected production effect |
| Rollback | How to restore prior state |
| Owner | Responsible operator |

`pg_settings` exposes useful metadata including `setting`, `unit`, `context`, `source`, `sourcefile`, `sourceline`, and `pending_restart`.

Do not assume all configuration changes are reloadable.

## 14. Recovery Protection Before HA Work

Before changing replication architecture, confirm that the Part 5 recovery design remains valid.

Required evidence includes:

- an approved physical backup/recovery method;
- WAL/recovery dependencies understood;
- recovery ownership;
- recovery evidence current enough for the organization's policy;
- no plan to replace independent backup with the new standby.

A healthy replica is not an independent backup strategy.

If recovery readiness is not proven, mark the prerequisite **UNKNOWN** or **FAIL** according to local policy and stop the production change.

## 15. Failure-Domain Assessment

A standby only improves availability when its dependencies match the intended failure model.

Assess whether primary and standby share:

- physical host;
- rack;
- availability zone;
- power/network path;
- storage backend;
- hypervisor or cluster dependency;
- control-plane dependency;
- secrets/DNS/load-balancer dependency.

PostgreSQL cannot prove most of these relationships. Require infrastructure evidence.

## 16. Change Window and Operational Ownership

The change plan must name:

- execution owner;
- database owner;
- infrastructure/network owner;
- application-validation owner;
- incident/escalation contact;
- rollback authority;
- approved maintenance window;
- observation period.

The plan must also state whether any prerequisite parameter change requires restart and what service impact that restart creates.

## 17. Blast Radius

Describe what can fail if the change goes wrong.

Examples:

- primary restart extends beyond the window;
- incorrect parameter prevents startup;
- WAL capacity grows unexpectedly;
- network path is blocked;
- standby initialization increases primary I/O;
- tablespace destination is missing;
- replication consumes capacity needed by the application;
- backup/recovery protection is accidentally weakened.

Do not hide these behind a generic "low risk" label.

## 18. Stop Conditions

Do **not** proceed with the production implementation when a safety-critical prerequisite is FAIL or UNKNOWN.

Typical stop conditions include:

```text
[ ] target identity cannot be proven
[ ] PostgreSQL compatibility is unresolved
[ ] required network path is unverified
[ ] standby storage readiness is unverified
[ ] tablespace compatibility is unresolved
[ ] WAL sender capacity is insufficient or unknown
[ ] slot capacity is insufficient/unknown when slots are required
[ ] required restart impact is not approved
[ ] backup/recovery readiness is unproven
[ ] failure-domain assumptions are unverified
[ ] rollback/fallback is undefined
[ ] change or rollback authority is unclear
[ ] required monitoring/evidence is unavailable
```

## 19. Rollback and Fallback

Because 6.2 is a planning stage, distinguish rollback from fallback.

**Rollback** restores changed configuration to its approved previous state.

**Fallback** describes what happens when standby construction or later validation cannot continue—for example, leave the existing primary service unchanged, abandon the incomplete standby build, preserve evidence, and reschedule after prerequisites are corrected.

Never improvise rollback during an incident.

## 20. Evidence Model

Use four outcomes:

| Result | Meaning |
|---|---|
| PASS | Requirement is explicitly supported by current evidence |
| FAIL | Evidence proves the requirement is not satisfied |
| UNKNOWN | Evidence is missing, stale, inaccessible, or contradictory |
| NOT APPLICABLE | Requirement does not apply to the approved design |

Do not convert UNKNOWN to PASS based on assumption.

## 21. Pre-Change Decision Gate

A production implementation may proceed only when:

1. target identity is verified;
2. topology is approved;
3. PostgreSQL/platform compatibility is established;
4. database and infrastructure capacity are acceptable;
5. WAL sender capacity is sufficient;
6. slot capacity is sufficient when slots are planned;
7. network/DNS/time prerequisites are externally proven;
8. tablespace dependencies are resolved;
9. required restart/reload impacts are approved;
10. Part 5 recovery protection remains intact;
11. monitoring/evidence collection is ready;
12. owners, stop conditions, rollback, and fallback are explicit;
13. no safety-critical item remains UNKNOWN.

## 22. Hands-On Acceptance

Run:

```text
labs/replication-prerequisites-check.sql
```

The lab is **SAFE-READ**. It inventories PostgreSQL-side evidence and deliberately leaves infrastructure-only prerequisites UNKNOWN.

The lab must not:

- run `ALTER SYSTEM`;
- create/drop replication slots;
- create replication users;
- edit `pg_hba.conf`;
- alter TLS;
- call `pg_promote()`;
- restart/reload PostgreSQL;
- run `pg_basebackup`;
- build or promote a standby.

No database cleanup is required because the lab performs no writes.

## 24. Key Takeaways

- Replication deployment starts with evidence, not with standby creation.
- `wal_level` must support physical replication.
- `max_wal_senders` is a capacity budget, not a checkbox.
- replication slots are conditional architecture components, not universal requirements.
- SQL cannot prove infrastructure capacity, networking, DNS, time synchronization, or failure-domain independence.
- tablespaces introduce destination-path prerequisites.
- server-start parameters require restart-aware change planning.
- replication does not replace Part 5 backup/recovery.
- missing or contradictory evidence is UNKNOWN.
- safety-critical FAIL or UNKNOWN results stop the production change.
