# 6.10 — Cascading Replication and Topology

## Purpose

PostgreSQL physical standbys do not always need to receive WAL directly from the primary.

A standby can receive WAL from another standby:

```text
Primary
   |
   | WAL
   v
Standby A
   |
   | WAL
   v
Standby B
```

This is **cascading replication**.

It can reduce direct replication fan-out from the primary and support regional or hierarchical standby architectures. It also introduces additional dependencies, replication hops, monitoring requirements, and failure domains.

This tutorial develops a production operating model for designing, validating, monitoring, and troubleshooting cascading physical-replication topologies.

## 1. Learning Objectives

By the end of this tutorial, you should be able to:

- explain cascading physical replication;
- distinguish direct and cascading replication;
- identify upstream and downstream servers;
- understand WAL flow through a cascade;
- identify intermediate cascading standbys;
- use `pg_stat_replication`;
- use `pg_stat_wal_receiver`;
- understand the direct-connection scope of PostgreSQL replication statistics;
- evaluate per-hop and end-to-end replication health;
- map replication slots to the correct hop;
- understand failure dependencies;
- evaluate maintenance blast radius;
- understand promotion implications;
- understand asynchronous cascading behavior;
- validate a cascade without modifying replication state;
- troubleshoot a cascade one hop at a time.

## 2. Direct Physical Replication

A common topology is:

```text
              +--> Standby A
              |
Primary ------+
              |
              +--> Standby B
```

Each standby receives WAL directly from the primary. This is easy to reason about and avoids intermediate replication dependencies.

## 3. Cascading Physical Replication

A cascading topology introduces an intermediate standby:

```text
Primary
   |
   | WAL
   v
Standby A
   |
   | WAL
   v
Standby B
```

Standby A is downstream of Primary and upstream for Standby B. It participates in both receiving and sending WAL.

## 4. Upstream and Downstream

Every streaming relationship can be represented as:

```text
UPSTREAM
   |
   | WAL
   v
DOWNSTREAM
```

For `Primary → A → B`:

| Node | Immediate upstream | Direct downstream |
|---|---|---|
| Primary | none | A |
| A | Primary | B |
| B | A | none |

During incidents, identify the immediate replication hop rather than saying only that a downstream node's replication is broken.

## 5. Intermediate Cascading Standby

An intermediate standby can simultaneously perform:

```text
WAL receive
+
WAL replay
+
read workload
+
WAL send
```

This matters for monitoring and capacity planning.

## 6. Cascading Replication Is Still Physical Replication

Cascading replication does not transform WAL into logical application events. The downstream remains a physical standby and replays physical WAL.

## 7. Cascading Replication Is Asynchronous

A critical PostgreSQL topology rule is that cascading replication is asynchronous.

For:

```text
Primary → Standby A → Standby B
```

the `A → B` cascading relationship must not be treated as a mechanism for extending synchronous commit acknowledgment through the cascade.

Synchronous replication policy remains a separate design concern.

## 8. Why Use Cascading Replication?

Potential reasons include:

- reducing direct streaming connections to the primary;
- reducing primary-side replication fan-out;
- reducing inter-site replication traffic;
- supporting regional replication hierarchies;
- providing additional downstream read replicas;
- isolating replication traffic across network boundaries.

The tradeoff is increased dependency on relay standbys.

## 9. Multi-Hop Cascades

A cascade can contain several levels:

```text
Primary
   |
   v
Standby A
   |
   v
Standby B
   |
   v
Standby C
```

Each additional hop introduces another replication dependency, possible lag location, network path, maintenance dependency, and monitoring requirement.

Every additional hop should have a documented operational reason.

## 10. Runtime Topology Evidence

For each server determine its role, immediate upstream, and direct downstream.

Role:

```sql
SELECT pg_is_in_recovery();
```

Immediate upstream on a standby:

```sql
SELECT *
FROM pg_stat_wal_receiver;
```

Direct downstream:

```sql
SELECT *
FROM pg_stat_replication;
```

These observations allow topology reconstruction from PostgreSQL runtime evidence.

## 11. `pg_stat_wal_receiver`

`pg_stat_wal_receiver` provides evidence about the immediate upstream streaming relationship.

For Standby B in:

```text
Primary → A → B
```

B's WAL receiver should correspond to A while B is actively streaming from A.

The view describes the immediate connection, not the entire upstream chain.

## 12. `pg_stat_replication`

A server with directly connected streaming replicas exposes WAL sender information through `pg_stat_replication`.

An important limitation is that this view represents directly connected downstream standbys.

For:

```text
Primary → A → B
```

the Primary can observe A as its direct downstream connection. It should not be expected to reconstruct B from the Primary's `pg_stat_replication` view.

## 13. One Node Cannot Reveal the Entire Cascade

For:

```text
Primary → A → B → C
```

query each relevant node and correlate the observations.

```text
local runtime evidence
        +
evidence from other nodes
        |
        v
validated topology
```

## 14. Intended vs Observed Topology

Production environments should maintain both an intended topology and an observed topology.

A static architecture diagram is not sufficient proof of current replication state.

## 15. Replication Lag Is Per Hop

For `Primary → A → B`, B can be current with A while A is delayed relative to Primary.

Therefore:

```text
hop health
    !=
end-to-end freshness
```

Production monitoring needs both.

## 16. WAL Receive and Replay Evidence

On a standby:

```sql
SELECT
    pg_last_wal_receive_lsn(),
    pg_last_wal_replay_lsn(),
    pg_last_xact_replay_timestamp();
```

These help determine whether WAL is being received, replayed, and advancing standby state.

Interpret timestamp-based lag carefully during idle upstream periods.

## 17. Intermediate Standby Failure

If A becomes unavailable in:

```text
Primary → A → B
```

B loses its streaming server even if the original primary remains healthy.

An intermediate cascading standby is therefore part of the downstream availability path.

## 18. Upstream Streaming Failure Is Different

Do not confuse an unavailable intermediate standby with an intermediate standby that remains running but loses its upstream streaming connection.

A cascading standby can forward WAL received through streaming and WAL made available through archive recovery. Loss of the intermediate node's upstream streaming connection does not automatically mean its downstream must stop immediately.

Investigate how the intermediate standby is obtaining WAL before determining downstream impact.

## 19. Dependency Mapping and Maintenance Blast Radius

For:

```text
Primary → A → B → C
```

C depends on B, B depends on A, and A depends on Primary.

Before restarting, patching, or reconfiguring an intermediate standby, inspect its directly connected downstream replicas:

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    sync_state
FROM pg_stat_replication
ORDER BY application_name, client_addr;
```

Maintenance scope may include the entire downstream branch.

## 20. Replication Slots and Cascades

When replication slots are used, placement should correspond to the actual streaming hop.

```text
Primary
   |
   | slot supporting A
   v
A
   |
   | slot supporting B
   v
B
```

A primary-side slot for A does not automatically manage WAL retention for the A→B relationship.

Where slots are used:

```sql
SELECT
    slot_name,
    slot_type,
    active,
    active_pid,
    restart_lsn,
    wal_status,
    safe_wal_size,
    inactive_since,
    invalidation_reason
FROM pg_replication_slots
ORDER BY slot_name;
```

Interpret each slot relative to the server where it exists.

## 21. Hot Standby Feedback Through a Cascade

Hot standby feedback can propagate upstream through a cascading topology:

```text
Standby B
    |
    v
Standby A
    |
    v
Primary
```

The production tradeoff remains fewer cleanup-related conflicts versus potential primary tuple-retention/bloat pressure.

## 22. Promotion and Cascading Topology

If A is promoted in:

```text
Primary → A → B
```

B can continue following the promoted upstream under appropriate timeline/recovery configuration.

Promotion should not be described as inherently breaking downstream streaming.

After failover, validate node roles, upstream relationship, WAL receiver, downstream WAL senders, timeline following, replication slots, receive/replay progress, and application routing.

## 23. Cascading Replication Configuration Dependencies

An intermediate standby serving downstream replicas needs sufficient replication capability.

Review:

- `max_wal_senders`;
- replication authentication;
- network access;
- recovery/hot-standby configuration;
- downstream `primary_conninfo`;
- slot configuration when used.

Configuration must support both recovery and downstream sender responsibilities.

## 24. Network Failure Domains

Cascading replication creates independent network links. A failure on `A → B` can affect only that downstream branch while Primary and A remain healthy.

Find the first unhealthy hop rather than assuming a primary-side problem.

## 25. Capacity Planning

Review intermediate standby:

- CPU;
- memory;
- storage latency and throughput;
- WAL replay performance;
- network bandwidth;
- WAL sender capacity;
- connection/process limits.

A cascading standby should not be sized only as a passive database copy.

## 26. Delayed Standby Considerations

If `recovery_min_apply_delay` is used, network and cascading delay can interact with configured apply-delay behavior.

Validate delayed-replica architecture end to end using observed replay behavior.

## 27. Production Topology Inventory

Maintain an inventory containing:

- node;
- role;
- immediate upstream;
- direct downstream replicas;
- region/AZ;
- `application_name`;
- replication slot;
- synchronous/asynchronous policy;
- expected upstream;
- network path;
- monitoring owner;
- failover role.

Compare intended inventory with runtime evidence periodically.

## 28. Troubleshooting Flow

```text
Downstream stale
      |
      v
Confirm server role
      |
      v
Inspect pg_stat_wal_receiver
      |
      v
Identify immediate upstream
      |
      v
Check immediate upstream health
      |
      v
Check upstream receive/replay state
      |
      v
Inspect upstream pg_stat_replication
      |
      v
Check network/authentication
      |
      v
Check WAL availability
      |
      v
Check slot state if used
      |
      v
Move one hop upstream
      |
      v
Repeat until first unhealthy hop found
```

Troubleshoot the chain one hop at a time.

## 29. Safe Topology Changes

Before changing replication topology:

1. document current intended relationships;
2. capture runtime evidence;
3. identify replication slots;
4. identify synchronous-replication dependencies;
5. identify all direct downstream replicas;
6. assess downstream branch impact;
7. verify WAL availability;
8. document rollback;
9. make the required controlled change;
10. validate streaming;
11. validate replay;
12. validate downstream impact;
13. update the topology inventory.

## 30. Hands-On Lab

Locked lab:

`labs/cascade-topology-check.sql`

The lab is observation-only. It determines:

- whether the node is primary or standby;
- whether it has an active WAL receiver;
- immediate streaming upstream;
- direct downstream replicas;
- sender application/client information;
- receive/replay positions;
- relevant replication slots;
- whether the node appears to be an intermediate cascading standby.

## 31. Lab Safety Contract

The lab will not:

- create/drop replication slots;
- change `primary_conninfo`;
- change `primary_slot_name`;
- change synchronous-replication policy;
- pause WAL replay;
- promote a standby;
- terminate WAL senders;
- restart PostgreSQL;
- modify application data.

Its workflow is:

```text
observe → identify → map → correlate → validate
```

## 32. Multi-Node Lab Requirement

Running the lab on one node cannot prove an entire multi-hop topology.

Run the check on each relevant node and correlate the evidence.

Possible local classifications:

```text
PRIMARY
LEAF STANDBY
CASCADING STANDBY
UNKNOWN
```

## 33. Lab Interpretation

**PASS** — observed runtime evidence is consistent with expected local role/topology.

**INFO** — node is healthy but does not have both upstream and downstream relationships.

**WARNING** — observed topology differs from expected architecture or an expected relationship is missing.

**UNKNOWN** — available evidence is insufficient.

The lab must not modify replication state merely to obtain a stronger classification.

## 35. Key Takeaways

1. Cascading replication allows a physical standby to receive WAL from another standby.
2. An intermediate standby can simultaneously receive, replay, and send WAL.
3. Cascading replication is asynchronous.
4. `pg_stat_wal_receiver` provides evidence about the immediate streaming upstream.
5. `pg_stat_replication` exposes directly connected downstream relationships.
6. One server cannot reveal an entire multi-hop topology.
7. Reconstruct cascades by correlating evidence from each node.
8. Every additional hop introduces another dependency and potential lag location.
9. Hop health is not the same as end-to-end freshness.
10. Intermediate-node failure can interrupt an entire downstream branch.
11. Loss of upstream streaming does not necessarily mean downstream streaming stops immediately if the intermediate continues obtaining WAL.
12. Replication slots must be reasoned about per hop.
13. Hot standby feedback can propagate through a cascade.
14. Promotion does not inherently require downstream streaming to break, but topology must be validated afterward.
15. Troubleshoot a cascade one hop at a time.
16. Observe first; modify topology only through an explicit runbook.
