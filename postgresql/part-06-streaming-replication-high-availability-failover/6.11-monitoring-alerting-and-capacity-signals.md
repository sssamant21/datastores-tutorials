# 6.11 --- Monitoring, Alerting, and Capacity Signals

## Purpose

PostgreSQL high availability is not complete when replication is merely
configured.

A production HA platform must continuously determine whether the
expected replication path is available, WAL is moving and being
replayed, standbys are sufficiently current, replication slots are safe,
recovery conflicts are increasing, replication capacity is constrained,
and infrastructure is approaching a condition that could compromise HA.

Effective HA observability combines:

``` text
Availability + Progress + Safety + Capacity → HA readiness evidence
```

The objective is not simply to collect PostgreSQL metrics. It is to
identify degradation early enough that operators can investigate before
a standby loses usefulness for failover, recovery, or disaster recovery.

## 1. Learning Objectives

By the end of this tutorial, you should be able to:

-   build a production HA observability model;
-   monitor primary and standby roles;
-   inspect WAL sender and receiver state;
-   monitor receive and replay progress;
-   distinguish connectivity from freshness;
-   interpret byte-based and time-based lag correctly;
-   monitor replication slots and WAL-retention risk;
-   monitor recovery conflicts;
-   measure WAL sender and slot headroom;
-   monitor cascading topologies hop by hop;
-   distinguish collection from alerting;
-   design warning and critical conditions;
-   establish production baselines;
-   relate monitoring to RPO and RTO;
-   collect evidence safely during incidents.

## 2. HA Observability Model

Production HA monitoring should answer four questions:

-   **Availability:** Is the expected replication path operational?
-   **Progress:** Is WAL moving and being replayed?
-   **Safety:** Is anything threatening recoverability, durability, or
    failover readiness?
-   **Capacity:** Is the system approaching a database, storage,
    network, or configuration limit?

No single metric proves complete HA health.

## 3. Connectivity Is Not Freshness

A standby can remain connected while falling behind.

``` text
CONNECTED != CURRENT
STREAMING != FAILOVER READY
```

Replication connectivity is one signal within a broader readiness model.

## 4. Start With Node Role

Before interpreting HA statistics:

``` sql
SELECT pg_is_in_recovery();
```

Role awareness is essential because sender, receiver, replay, and
recovery statistics have different meanings depending on where they are
collected.

## 5. Upstream Sender Monitoring

Use intentional columns from `pg_stat_replication`:

``` sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    write_lag,
    flush_lag,
    replay_lag,
    sync_state,
    reply_time
FROM pg_stat_replication
ORDER BY application_name, client_addr;
```

This provides evidence about directly connected replication clients. In
cascading topologies it does not reconstruct the complete replication
tree.

## 6. WAL Progress Pipeline

Conceptually:

``` text
Primary WAL → sent → written → flushed → replayed
```

A standby can receive quickly while replaying slowly, or transport
itself can be delayed. Monitoring should identify where progress begins
to diverge.

## 7. Replication Statistics Are Observations

Standby progress is reported to upstream servers periodically.

``` text
one sample != perfect instantaneous state
```

Interpret state, WAL positions, time, trend, and expected topology
together.

## 8. Byte-Based WAL Distance

Use `pg_wal_lsn_diff()` to compare WAL locations. This produces a
WAL-distance signal.

It is not automatically equivalent to elapsed seconds, transaction
count, recovery duration, business RPO, or physical filesystem
consumption.

## 9. Standby WAL Receiver Monitoring

`pg_stat_wal_receiver` provides evidence about the immediate upstream
streaming relationship.

Ask whether a receiver exists, what state it is in, who the upstream is,
whether WAL position advances, and when upstream communication was last
observed.

A missing receiver on a standby expected to stream deserves
investigation, but recovery design matters.

## 10. Receive and Replay Progress

``` sql
SELECT
    pg_last_wal_receive_lsn(),
    pg_last_wal_replay_lsn(),
    pg_last_xact_replay_timestamp();
```

A standby can continue receiving WAL while replay falls behind.

## 11. Receive-to-Replay Distance

Where both LSNs are available:

``` sql
SELECT pg_wal_lsn_diff(
    pg_last_wal_receive_lsn(),
    pg_last_wal_replay_lsn()
);
```

A continuously growing distance can indicate replay is not keeping pace.
It does not identify the root cause by itself.

## 12. Replay Timestamp Requires Context

An old `pg_last_xact_replay_timestamp()` does not automatically mean the
standby is lagging. If the upstream has generated no relevant new
transaction activity, the timestamp can become old while the standby
remains current.

Correlate timestamp evidence with WAL positions and workload activity.

## 13. Lag Requires a Defined Measurement

Avoid generic "replication lag high" alerts. Define whether the signal
is write lag, flush lag, replay lag, WAL byte distance,
receive-to-replay distance, or time since replayed transaction.

## 14. Trend and Persistence Matter

A large but shrinking backlog differs from a smaller but continuously
growing backlog. Likewise, a short reconnect differs from prolonged
replication loss.

Where supported, monitoring should consider magnitude, direction,
duration, and impact.

## 15. Replication State

Replication states such as `startup`, `catchup`, and `streaming` are
useful, but state alone does not prove freshness. Combine state with WAL
progress and expected topology.

## 16. WAL Receiver Timing Configuration

Relevant context includes:

-   `wal_receiver_timeout`
-   `wal_receiver_status_interval`

These settings help explain monitoring behavior. Their configured values
are not universal alert thresholds.

## 17. Synchronous Replication Observability

Where synchronous replication is configured, monitor `sync_state`
together with the expected policy. The question is not merely whether a
replication connection exists, but whether the expected synchronous
relationship is present.

## 18. Replication Slot Monitoring

Useful PostgreSQL 18 evidence includes:

``` sql
SELECT
    slot_name,
    slot_type,
    active,
    active_pid,
    restart_lsn,
    wal_status,
    safe_wal_size,
    inactive_since,
    invalidation_reason
FROM pg_replication_slots
ORDER BY slot_name;
```

A slot existing does not prove that it is operationally safe.

## 19. `wal_status` Interpretation

  -----------------------------------------------------------------------
  `wal_status`                        Operational interpretation
  ----------------------------------- -----------------------------------
  `reserved`                          Required WAL retained within normal
                                      reservation behavior

  `extended`                          Inspect retention trend and context

  `unreserved`                        Warning: required WAL is no longer
                                      guaranteed to remain retained

  `lost`                              Critical: required WAL is lost and
                                      the slot is unusable
  -----------------------------------------------------------------------

Do not classify `extended` as automatically critical.

## 20. `safe_wal_size`

`safe_wal_size` provides evidence about how much additional WAL can be
written before a slot is at risk under applicable retention limits.

``` text
safe_wal_size IS NULL != automatically failure
```

Always correlate it with `wal_status` and retention configuration.

## 21. WAL Retention Is Not Filesystem Usage

``` text
WAL retention evidence != actual filesystem utilization
```

SQL views cannot replace external monitoring for `pg_wal` filesystem
utilization, free bytes, growth rate, time-to-capacity, storage latency,
throughput, and errors.

## 22. Recovery Conflict Monitoring

Use `pg_stat_database_conflicts`. Evaluate affected database, conflict
category, change over time, rate of increase, user impact, and
relationship to replay progress.

Historical cumulative counts greater than zero do not automatically
represent a current incident.

## 23. WAL Sender Capacity

`max_wal_senders` covers replication connections and streaming
base-backup clients.

Operational headroom should account for normal standbys, maintenance,
streaming base backup, standby rebuilds, and reconnect behavior.

No universal spare-sender threshold applies to every environment.

## 24. Replication Slot Capacity

``` text
max_replication_slots - existing slots = slot headroom
```

Operating permanently at the configured maximum can constrain emergency
or planned operations.

## 25. Connection and Infrastructure Capacity

HA readiness also depends on connection capacity and post-failover
workload capability.

External monitoring should cover CPU saturation, memory pressure,
storage capacity/latency/throughput/errors, and network
latency/loss/resets.

Do not infer infrastructure health solely from PostgreSQL SQL views.

## 26. Cascading Topology Monitoring

For:

``` text
Primary → A → B
```

monitor `Primary → A` and `A → B` independently, while also evaluating
B's end-to-end freshness relative to the original primary.

``` text
healthy A → B != B current with Primary
```

## 27. Collection vs Alerting

Collect rich diagnostic evidence. Alert only on actionable abnormal
conditions.

Not every metric change should page an operator.

## 28. Alert Design

A useful alert identifies:

-   what happened;
-   where it happened;
-   which replication hop is affected;
-   severity;
-   persistence;
-   supporting evidence;
-   the next diagnostic action.

Avoid generic alerts without operational context.

## 29. Warning vs Critical

Exact thresholds belong to environment-specific policy.

**WARNING** represents degradation requiring investigation while HA
capability may remain available.

**CRITICAL** represents conditions directly threatening availability,
recoverability, durability, or failover readiness.

Thresholds and persistence windows must align with service objectives.

## 30. Baselines, RPO, and RTO

Establish baselines for replay distance, WAL generation rate, network
latency, conflict rate, slot activity, WAL growth, sender usage, slot
usage, and failover headroom.

One PostgreSQL lag metric does not equal business RPO.

RTO is also broader than replication lag and can depend on promotion
readiness, capacity, routing/load-balancer behavior, application
reconnect behavior, automation, and operator procedures.

## 31. Evidence-First Incident Diagnosis

``` text
Alert
  ↓
Confirm node role
  ↓
Confirm expected topology
  ↓
Inspect sender/receiver state
  ↓
Check WAL positions
  ↓
Check replay progress
  ↓
Check slot state
  ↓
Check conflict deltas
  ↓
Check WAL/storage capacity
  ↓
Check CPU/network/storage
  ↓
Identify first unhealthy layer
```

Begin with evidence, not configuration changes.

## 32. Unsafe Reactions

Avoid immediately:

-   dropping replication slots;
-   restarting PostgreSQL;
-   rebuilding a standby;
-   increasing WAL retention blindly;
-   changing sender/slot limits without capacity review;
-   terminating sessions indiscriminately;
-   promoting solely because lag is elevated;
-   changing synchronous policy without understanding durability impact.

## 33. Monitoring During Incidents

Where possible combine PostgreSQL telemetry with host, storage/cloud,
network, and external availability telemetry.

A monitoring architecture dependent entirely on healthy SQL access can
lose visibility during the incident where it is most needed.

## 34. Production Signal Matrix

  ------------------------------------------------------------------------------
  Signal                  Source                         Purpose
  ----------------------- ------------------------------ -----------------------
  Node recovery role      `pg_is_in_recovery()`          Role awareness

  Sender state            `pg_stat_replication`          Direct downstream
                                                         health

  Receiver state          `pg_stat_wal_receiver`         Immediate upstream
                                                         health

  Receive/replay LSN      standby functions/views        Transport/apply
                                                         progress

  Slot state              `pg_replication_slots`         WAL-retention safety

  Conflict counters       `pg_stat_database_conflicts`   Recovery/query pressure

  Sender capacity         `pg_settings`                  Sender headroom

  Slot capacity           `pg_settings`                  Slot headroom

  WAL disk utilization    OS/cloud monitoring            Storage safety

  CPU/storage/network     OS/cloud monitoring            Infrastructure capacity
  ------------------------------------------------------------------------------

## 35. Hands-On Lab

Locked lab:

`labs/ha-observability-check.sql`

Classification: **SAFE-READ**

The lab collects PostgreSQL-side HA evidence without changing database
state.

## 36. Lab Safety Contract

The lab will not:

-   create or drop replication slots;
-   modify PostgreSQL settings;
-   expose full `primary_conninfo`;
-   change synchronous replication policy;
-   pause/resume WAL replay;
-   promote a standby;
-   terminate sessions;
-   restart PostgreSQL;
-   modify application data.

## 37. Lab Classification

Use conservative classifications:

-   `PASS`
-   `INFO`
-   `WARNING`
-   `CRITICAL`
-   `UNKNOWN`

Prefer `UNKNOWN` over an unsupported health conclusion.

Slot examples:

``` text
reserved   → PASS / INFO according to context
extended   → INFO / WARNING according to trend
unreserved → WARNING
lost       → CRITICAL
```

`safe_wal_size IS NULL` requires context.

A missing receiver is normal on a primary but can be `WARNING` or
`UNKNOWN` on a standby expected to stream.

Historical conflict counters are informational in a one-time SQL
execution; rate/delta alerting belongs in the monitoring platform.

## 38. External Monitoring Requirements

SQL cannot safely establish all HA conditions.

External monitoring remains required for:

-   `pg_wal` filesystem utilization;
-   filesystem free capacity;
-   storage latency and throughput;
-   storage errors;
-   host CPU saturation;
-   memory pressure;
-   network latency and packet loss;
-   cloud-volume limits;
-   load-balancer readiness;
-   application reconnect success.

## 39. Production Acceptance Checklist

-   [ ] Primary/standby roles monitored
-   [ ] Expected topology documented
-   [ ] WAL sender and receiver state monitored
-   [ ] WAL positions and replay progress collected
-   [ ] Per-hop lag monitored
-   [ ] End-to-end freshness monitored for cascades
-   [ ] Replication slots and `wal_status` monitored
-   [ ] WAL-retention risk monitored
-   [ ] `pg_wal` capacity monitored externally
-   [ ] Recovery conflicts monitored as deltas/rates
-   [ ] Synchronous policy observable
-   [ ] WAL sender and slot headroom monitored
-   [ ] Sender capacity accounts for base backup/rebuild activity
-   [ ] CPU, storage, and network monitored
-   [ ] Warning/critical policies documented
-   [ ] Persistence windows documented
-   [ ] Thresholds align with service objectives
-   [ ] Alert runbooks identify next evidence to collect
-   [ ] Monitoring remains available during degraded conditions
-   [ ] Monitoring and alerts tested during planned failover exercises

## 40. Key Takeaways

1.  Replication connectivity does not prove freshness.
2.  Streaming state does not prove failover readiness.
3.  HA observability combines availability, progress, safety, and
    capacity.
4.  Monitor WAL transport and replay separately.
5.  WAL byte distance and elapsed-time lag are different signals.
6.  Replay timestamps require workload context.
7.  Trends and persistence are often more useful than isolated samples.
8.  Monitor slots together with WAL-storage capacity.
9.  `wal_status = 'lost'` is critical.
10. `safe_wal_size IS NULL` is not automatically failure.
11. Recovery conflicts should be evaluated as changes over time.
12. Sender capacity must include operational work such as base backups
    and rebuilds.
13. Cascades require per-hop and end-to-end monitoring.
14. SQL observability cannot replace host, storage, network, and cloud
    monitoring.
15. Prefer `UNKNOWN` over unsupported health conclusions.
16. Test monitoring during planned failover exercises.
