# Part 2.12 — Memory Configuration and Resource Management

**Status:** Revised Final / Canonical Edition  
**Target:** PostgreSQL 18  
**Audience:** PostgreSQL administrators, SREs, DBREs, platform engineers, and application engineers.

## Objectives

After completing this tutorial, you should be able to:

- explain PostgreSQL's major memory consumers;
- distinguish shared memory, operation limits, session limits, and planner estimates;
- understand `shared_buffers`, `work_mem`, and `hash_mem_multiplier`;
- distinguish `maintenance_work_mem`, `autovacuum_work_mem`, and `vacuum_buffer_usage_limit`;
- understand `temp_buffers` and `effective_cache_size`;
- understand explicit huge pages and `huge_pages_status`;
- recognize parallel-query memory multiplication;
- distinguish parallel-query from parallel-maintenance memory behavior;
- inspect PostgreSQL 18 memory contexts where privileges permit;
- interpret `EXPLAIN (MEMORY)` correctly as planning memory;
- correlate temporary-file evidence with query execution;
- build NORMAL, PEAK, and FAILURE capacity-risk scenarios;
- recognize host, cgroup/container, OOM, and restart-loop risks;
- make production memory changes through a controlled change/rollback gate.

## Safety Classes

```text
[SAFE-READ]
    Read-only PostgreSQL inspection.

[SAFE-READ — PRIVILEGE REQUIRED]
    Read-only inspection that may require elevated monitoring privileges.

[SESSION-LOCAL]
    Changes only the current session and is restored afterward.

[LAB-ONLY]
    Changes only disposable lab objects.

[PRODUCTION-CHANGE — MEMORY / OOM RISK]
    Persistent resource change requiring capacity review.

[PRODUCTION-CHANGE — STARTUP AVAILABILITY RISK]
    Change that can prevent successful PostgreSQL startup.
```

The companion acceptance artifact is strictly read-only.

## 1. Memory Is Not One Pool

```text
PostgreSQL / host memory
        |
        +--> shared PostgreSQL memory
        +--> backend/session memory
        +--> sort/hash executor operations
        +--> parallel query workers
        +--> maintenance
        +--> autovacuum
        +--> temporary-table buffers
        +--> extensions/background workers
        +--> OS/kernel
        +--> filesystem cache
        +--> agents and other processes
```

The central production rule is:

```text
configured memory limits
        !=
actual resident memory

and

individually safe-looking settings
        !=
safe combined configuration
```

Memory tuning is capacity engineering, not isolated parameter tuning.

## 3. `shared_buffers`

```sql
SHOW shared_buffers;
```

`shared_buffers` controls PostgreSQL's shared buffer cache.

```text
backend processes
       |
       v
shared_buffers
       |
       v
OS filesystem cache
       |
       v
storage
```

PostgreSQL relies on both its own shared buffers and operating-system caching.

PostgreSQL documentation describes roughly 25% of system memory as a reasonable starting point on many dedicated database systems with sufficient RAM, while also warning that substantially larger allocations do not necessarily improve performance.

Treat that as:

```text
vendor starting point
        !=
production sizing formula
```

Do not assign nearly all system memory to `shared_buffers`.

A substantial `shared_buffers` change should also trigger review of:

```text
max_wal_size
checkpoint behavior
dirty-buffer behavior
storage throughput
recovery requirements
```

Memory, WAL, checkpoints, and storage are connected.

---

## 4. `work_mem`

```sql
SHOW work_mem;
```

`work_mem` is a base memory limit for applicable executor operations before temporary files may be used.

Examples include:

```text
ORDER BY / DISTINCT sorts
merge joins
hash joins
hash aggregation
Memoize
applicable IN-subquery hash processing
```

The critical rules are:

```text
work_mem != server memory limit
work_mem != connection memory limit
```

One query can have multiple simultaneously active operations with their own applicable memory limits.

---

## 5. Capacity-Risk Model for `work_mem`

A useful exposure model is:

```text
work_mem
    ×
simultaneously active work_mem-class operations
    ×
concurrent queries
    ×
participating parallel processes
```

This intentionally estimates risk. It does **not** predict exact RSS or guarantee that every operation consumes its full limit.

For example:

```text
work_mem = 64 MB
50 active memory-intensive queries
2 simultaneously active operations/query
```

A simple base exposure scenario is:

```text
64 MB × 50 × 2
= 6,400 MB
≈ 6.25 GB
```

Hash operations and parallel execution can increase the scenario further.

A global `work_mem` increase therefore has a potentially large blast radius.

---

## 6. `hash_mem_multiplier`

```sql
SHOW hash_mem_multiplier;
```

PostgreSQL derives the applicable hash-operation memory limit from:

```text
work_mem × hash_mem_multiplier
```

PostgreSQL 18 defaults `hash_mem_multiplier` to `2.0`.

Example:

```text
work_mem = 64 MB
hash_mem_multiplier = 2.0

hash-operation memory limit basis
≈ 128 MB
```

This is a limit/budget, not guaranteed permanent allocation.

---

## 7. Parallel Query Memory

Parallel query can multiply resource exposure because applicable limits such as `work_mem` generally apply independently to participating parallel workers.

Conceptually:

```text
query
 |
 +--> leader
 +--> worker 1
 +--> worker 2
 +--> worker 3
 +--> worker 4
```

A single client query can therefore involve several PostgreSQL processes consuming executor resources.

Inspect:

```sql
SHOW max_worker_processes;
SHOW max_parallel_workers;
SHOW max_parallel_workers_per_gather;
```

PostgreSQL 18 also provides cumulative database statistics:

```sql
SELECT
    datname,
    parallel_workers_to_launch,
    parallel_workers_launched
FROM pg_stat_database
WHERE datname = current_database();
```

These counters are cumulative evidence, not an instantaneous worker count.

---

## 8. `maintenance_work_mem`

```sql
SHOW maintenance_work_mem;
```

This applies to maintenance operations such as:

```text
VACUUM
CREATE INDEX
ALTER TABLE ADD FOREIGN KEY
```

PostgreSQL 18 defaults it to `64MB`.

It can often be larger than `work_mem` because an individual session generally performs only one applicable maintenance operation at a time.

But concurrent maintenance commands still matter.

---

## 9. Parallel Maintenance Is Different

Do not use this generic formula:

```text
maintenance_work_mem × parallel maintenance workers
```

as if parallel maintenance behaved like parallel query.

For supported parallel utility commands, PostgreSQL treats `maintenance_work_mem` as applying to the overall utility command rather than independently granting the full amount to every parallel worker.

Still consider:

```text
concurrent maintenance commands
+
autovacuum
+
normal workload
```

when building the capacity model.

---

## 10. `autovacuum_work_mem`

```sql
SHOW autovacuum_work_mem;
SHOW autovacuum_max_workers;
```

PostgreSQL 18 defaults:

```text
autovacuum_work_mem = -1
```

which causes autovacuum to use `maintenance_work_mem`.

Therefore increasing `maintenance_work_mem` can indirectly increase potential autovacuum memory exposure.

A planning scenario may consider:

```text
autovacuum_max_workers
    ×
per-worker applicable memory limit
```

as potential configured exposure.

It is not a claim that every worker permanently allocates the entire amount.

---

## 11. `vacuum_buffer_usage_limit`

```sql
SHOW vacuum_buffer_usage_limit;
```

PostgreSQL 18 defaults this to `2MB`.

It controls the Buffer Access Strategy used by `VACUUM` and `ANALYZE`.

Do not confuse:

```text
maintenance_work_mem
    -> maintenance-operation memory

vacuum_buffer_usage_limit
    -> VACUUM/ANALYZE buffer-cache strategy
```

They address different resource concerns.

---

## 12. `temp_buffers`

```sql
SHOW temp_buffers;
```

`temp_buffers` controls the maximum session-local buffers available for temporary tables.

PostgreSQL 18 defaults it to `8MB`.

It is not the same as executor temporary files:

```text
temp_buffers
    -> temporary tables

sort/hash spill files
    -> executor operations
```

PostgreSQL allocates temporary buffers as needed, so the configured maximum is not necessarily immediate resident allocation.

A session can effectively change `temp_buffers` only before it first accesses a temporary table.

---

## 13. `effective_cache_size`

```sql
SHOW effective_cache_size;
```

This is a planner estimate of cache that may be available to a query.

It does **not** allocate memory.

Never calculate:

```text
shared_buffers
+
effective_cache_size
+
work_mem
=
RAM usage
```

That is incorrect.

---

## 14. Explicit Huge Pages

```sql
SHOW huge_pages;
SHOW huge_pages_status;
SHOW huge_page_size;
```

PostgreSQL 18 `huge_pages` values are:

```text
try
on
off
```

with `try` as the default.

```text
try
    -> attempt huge pages and fall back if unavailable

on
    -> require huge pages

off
    -> do not request huge pages
```

Distinguish:

```text
huge_pages
    -> requested policy

huge_pages_status
    -> actual runtime status
```

A production change to:

```text
huge_pages = on
```

is:

```text
[PRODUCTION-CHANGE — STARTUP AVAILABILITY RISK]
```

because PostgreSQL startup can fail if required huge pages cannot be obtained.

---

## 15. Transparent Huge Pages Are Different

```text
PostgreSQL explicit huge pages
        !=
Linux Transparent Huge Pages
```

PostgreSQL documentation notes that Linux Transparent Huge Pages have caused performance degradation for some PostgreSQL workloads on some Linux versions and currently discourages their use.

Do not treat THP and PostgreSQL's explicit huge-page mechanism as the same feature.

---

## 16. Connections and Memory

```sql
SHOW max_connections;
```

Each backend has memory overhead even before expensive sorts or hashes occur.

But:

```text
max_connections × work_mem
```

is not exact PostgreSQL memory consumption.

A better model distinguishes:

```text
configured connection ceiling
connected sessions
active query concurrency
memory-intensive operation concurrency
parallel execution
failure/retry storms
```

Current client-backend state can be inspected safely:

```sql
SELECT
    state,
    COUNT(*) AS sessions
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY state
ORDER BY state;
```

Historical peaks are more useful for capacity planning than a single snapshot.

---

## 17. NORMAL / PEAK / FAILURE Models

Memory capacity should be tested against more than steady state.

```text
NORMAL
    typical connections and active concurrency

PEAK
    expected business/load-test maximum

FAILURE
    retry/connection storm
    long-running queries
    downstream slowdown
    maintenance overlap
    increased parallel execution
```

A configuration that works only under NORMAL conditions has weak production safety margin.

---

## 18. PostgreSQL 18 Memory Context Observability

Where privileges permit:

```text
[SAFE-READ — PRIVILEGE REQUIRED]
```

PostgreSQL 18 provides `pg_backend_memory_contexts`.

Example:

```sql
SELECT
    name,
    type,
    total_bytes,
    used_bytes,
    free_bytes
FROM pg_backend_memory_contexts
ORDER BY total_bytes DESC
LIMIT 20;
```

PostgreSQL 18's view includes fields such as `type` and `path`, and its schema differs from older PostgreSQL examples.

This view demonstrates that backend memory consists of multiple memory contexts rather than one monolithic allocation.

It is optional because access normally requires suitable monitoring privileges.

Do not make it a mandatory acceptance query.

---

## 19. Advanced Memory Logging

PostgreSQL also provides:

```text
pg_log_backend_memory_contexts(pid)
```

which can request memory-context information from another backend and write substantial diagnostic information to the server log.

Classify this as:

```text
[ADVANCED INCIDENT DIAGNOSTIC]
```

It is not part of the standard lab or acceptance artifact.

Repeated use can create significant logging overhead.

---

## 20. PostgreSQL 18 `EXPLAIN (MEMORY)`

PostgreSQL 18 supports:

```sql
EXPLAIN (MEMORY)
SELECT ...
```

Important:

```text
EXPLAIN (MEMORY)
        ->
planning-phase memory

EXPLAIN (MEMORY)
        !=
total executor peak memory
```

Do not use planning-memory output as a substitute for executor-memory analysis.

---

## 21. Executor Sort Evidence

In a disposable lab:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...
ORDER BY ...;
```

can show executor-specific evidence such as:

```text
Sort Method
Memory
Disk
```

depending on the plan and runtime behavior.

`EXPLAIN ANALYZE` executes the statement.

Never run it against an unknown production statement without first understanding cost and side effects.

```sql
CREATE SCHEMA memory_lab;
```

Load synthetic data:

```sql
INSERT INTO memory_lab.orders (

    category,
    created_at

SELECT
    (random() * 10000)::bigint,
    round((random() * 1000)::numeric, 2),
    'category-' || (g % 25),
    now() - ((g % 365) * interval '1 day')

```


## 25. Optional Session-Local `work_mem` Experiment

```sql
-- [OPTIONAL LAB — SESSION-LOCAL]
SHOW work_mem;

SET work_mem = '1MB';

EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM memory_lab.orders
ORDER BY amount DESC;

RESET work_mem;
```

Lowering the session-local limit may make a spill more likely, but the actual result depends on the execution plan, row width, and runtime behavior.

The experiment does not justify a global `work_mem` change.

## 26. Temporary-File Statistics

```sql
SELECT
    datname,
    temp_files,
    temp_bytes
FROM pg_stat_database
WHERE datname = current_database();
```

These are cumulative database statistics.

```text
temp_bytes
    != current temporary disk usage

cumulative counters
    != this query alone
```

Use a before/after snapshot if you need a controlled delta.

Do not reset shared statistics for tutorial convenience.

---

## 27. Safe Delta Method

```text
snapshot temp_files/temp_bytes
        |
        v
controlled lab query
        |
        v
snapshot again
        |
        v
after - before
```

Avoid:

```sql
SELECT pg_stat_reset();
```

Shared operational history should be preserved.

---

## 28. Temporary Files Are Evidence, Not a Prescription

Never use:

```text
temp files observed
       |
       v
increase global work_mem
```

as an automatic response.

Instead:

```text
identify query
      |
inspect plan
      |
identify sort/hash/spill
      |
measure frequency and size
      |
measure concurrency/parallelism
      |
choose remediation
```

Possible remediations include:

```text
query/index optimization
workload-specific memory setting
concurrency control
global setting change
capacity increase
```

## 29. Host / OS Capacity Boundary

Production memory planning needs headroom for:

```text
PostgreSQL
OS/kernel
filesystem cache
monitoring agents
security agents
backup agents
other processes
safety margin
```

Do not allocate nearly all physical RAM through PostgreSQL configuration.

Swap should also be interpreted carefully.

```text
some pages historically in swap
        !=
active memory-pressure swapping
```

Investigate swap-in/swap-out activity, latency, and actual memory pressure rather than using simplistic rules.

---

## 30. Containers and Kubernetes

This is a platform/SRE consideration.

Example:

```text
node RAM = 64 GiB
PostgreSQL pod memory limit = 16 GiB
```

The database does not have a 64-GiB budget merely because the node does.

```text
node RAM
    !=
container memory budget
```

Kubernetes requests and limits are also different concepts:

```text
request
    -> scheduling/reservation concept

limit
    -> configured enforcement boundary
```

Memory configuration must respect the effective cgroup/container boundary.

---

## 31. OOM and Restart-Loop Risk

Avoid claiming exactly which process will always be terminated.

The safe model is:

```text
memory demand exceeds effective boundary
        |
        v
kernel/cgroup OOM handling
        |
        v
one or more processes may terminate
        |
        v
database availability impact
```

In an orchestrated environment:

```text
PostgreSQL starts
      |
workload returns
      |
memory rises
      |
OOM/container termination
      |
restart
      |
workload returns
      |
repeat
```

A memory change must have explicit OOM/restart-loop rollback criteria.

## 32. Production Memory Incident Workflow

```text
memory pressure / OOM / latency
        |
        v
confirm physical/cgroup boundary
        |
        v
inspect OS/cgroup memory + swap activity
        |
        v
inspect PostgreSQL memory configuration
        |
        v
inspect connections + active concurrency
        |
        v
inspect parallel execution
        |
        v
inspect expensive sorts/hashes/plans
        |
        v
inspect temporary-file evidence
        |
        v
inspect maintenance/autovacuum overlap
        |
        v
inspect extensions/background workers
        |
        v
build NORMAL / PEAK / FAILURE scenarios
        |
        v
identify root cause
        |
        v
apply smallest safe remediation
        |
        v
monitor
```

Do not blindly add RAM or globally raise `work_mem` without identifying the workload and multiplication factors.

## 33. Managed PostgreSQL

Managed services can restrict memory parameters, derive values from instance size, control restart behavior, hide host-level details, and expose provider-specific metrics.

Examples include Amazon RDS/Aurora PostgreSQL, Azure Database for PostgreSQL, and Google Cloud SQL for PostgreSQL.

Distinguish:

```text
PostgreSQL parameter semantics
             from
provider resource implementation
```

Do not assume self-managed OS or huge-page procedures apply to a managed service.

## 34. Production Memory Change Gate

Before changing production memory configuration:

```text
[ ] PostgreSQL version confirmed
[ ] Physical/cgroup memory boundary confirmed
[ ] Current values/source/context recorded
[ ] pending_restart checked
[ ] OS/kernel memory reserved
[ ] Filesystem-cache requirement considered
[ ] Monitoring/security/backup agents considered
[ ] Current and peak connections measured
[ ] Active query concurrency measured
[ ] Failure/retry-storm scenario modeled
[ ] work_mem operations/query considered
[ ] hash_mem_multiplier considered
[ ] Parallel query workers considered
[ ] Concurrent maintenance reviewed
[ ] autovacuum_work_mem inheritance reviewed
[ ] autovacuum_max_workers reviewed
[ ] vacuum_buffer_usage_limit reviewed
[ ] Temporary-file evidence reviewed
[ ] Relevant query plans reviewed
[ ] Huge-page policy/status reviewed
[ ] Container/Kubernetes boundary reviewed
[ ] Swap activity reviewed where applicable
[ ] Managed-service restrictions reviewed
[ ] NORMAL scenario modeled
[ ] PEAK scenario modeled
[ ] FAILURE scenario modeled
[ ] Safety headroom retained
[ ] Previous values documented
[ ] Restart/reload requirement identified
[ ] Success criteria defined
[ ] Rollback criteria defined
[ ] OOM/restart-loop rollback trigger defined
[ ] Monitoring window defined
```

## 37. Key Takeaways

```text
shared_buffers
    -> PostgreSQL shared buffer cache

work_mem
    -> applicable executor-operation memory limit/basis

hash_mem_multiplier
    -> hash-operation multiplier

maintenance_work_mem
    -> maintenance-operation memory

autovacuum_work_mem
    -> autovacuum memory, or inherits maintenance_work_mem

vacuum_buffer_usage_limit
    -> VACUUM/ANALYZE buffer access strategy

temp_buffers
    -> session temporary-table buffers

effective_cache_size
    -> planner estimate, not allocation

huge_pages
    -> configured explicit huge-page policy

huge_pages_status
    -> actual huge-page runtime state
```

Most importantly:

```text
memory settings
      +
active concurrency
      +
operations/query
      +
parallelism
      +
maintenance/autovacuum
      +
OS/container boundary
      +
failure conditions
      =
production memory risk
```

Capacity formulas in this tutorial are exposure models, not exact RSS predictions.
