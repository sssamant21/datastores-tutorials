# Part 2.15 --- Integrated Project: Build a Production-Style PostgreSQL Server from Scratch

**Status:** Revised Final / Canonical Edition\
**Target:** PostgreSQL 18\
**Audience:** PostgreSQL administrators, DBREs, SREs, platform
engineers, and production support engineers.

## Project Goal

Build a production-style PostgreSQL 18 server by applying the
architecture, installation, storage, service-management, configuration,
security, WAL, logging, operating-system, and validation practices
developed throughout Part 2.

This is an integration project. It does not replace the detailed
tutorials in 2.1--2.14.

The project separates two classes of work:

``` text
BUILD / CHANGE WORK
    Explicit operator actions that create or modify the environment.

ACCEPTANCE WORK
    Read-only checks that prove what was built and expose conditions
    requiring review.
```

The companion `labs/production-server-acceptance.sh` is an acceptance
artifact. It does not build or modify the server.

------------------------------------------------------------------------

## 1. Learning Outcomes

After completing this project, you should be able to:

-   plan a PostgreSQL deployment before installation;
-   prepare a Linux host using documented prerequisites;
-   install PostgreSQL 18 using an approved method;
-   initialize a cluster intentionally with `initdb`;
-   design and validate data, WAL, and tablespace storage;
-   manage PostgreSQL through the selected service-management model;
-   configure memory and worker resources from a capacity model;
-   establish a connection and session budget;
-   configure authentication and network access deliberately;
-   review WAL, checkpoint, and durability settings;
-   establish logging and diagnostic controls;
-   validate operating-system and resource-limit dependencies;
-   capture a production configuration baseline;
-   execute an inspection-only final acceptance workflow;
-   distinguish successful installation from production readiness.

## 2. Safety Classification

This project uses these classifications:

``` text
[SAFE-READ]
    Reads state without intentionally changing it.

[HOST-READ]
    Reads operating-system/service state without changing it.

[LAB-ONLY]
    Mutates only a disposable lab environment.

[PRODUCTION-CHANGE]
    Changes persistent PostgreSQL or host state.

[PRODUCTION-CHANGE — RELOAD]
    Requires controlled PostgreSQL configuration reload.

[PRODUCTION-CHANGE — RESTART]
    Requires controlled PostgreSQL restart.

[SECURITY-CHANGE]
    Changes authentication, TLS, network exposure, roles,
    credentials, firewall policy, or another security boundary.
```

Never copy a `[LAB-ONLY]` build command into production without adapting
it to the actual platform, change process, backup/recovery architecture,
and security requirements.

## 7. Phase 3 --- Prepare Storage

Define storage before initializing the cluster.

Example design:

``` text
/pgdata/18/main      -> PGDATA
/pgwal/18/main       -> optional dedicated WAL storage
/pgts/...            -> optional tablespaces
```

This is an example, not a universal required layout.

Review:

``` text
capacity
latency
IOPS
throughput
filesystem
mount persistence
ownership
permissions
backup/snapshot interaction
monitoring
growth
failure domain
```

### WAL separation

A dedicated WAL device can be appropriate when justified by the storage
architecture and workload. It is not automatically required.

If WAL is placed separately, its durability and availability
requirements are at least as important as the main data directory.

### Gate 3

``` text
[ ] PGDATA storage defined
[ ] WAL placement decision documented
[ ] tablespace strategy documented
[ ] capacity/growth reviewed
[ ] persistence verified
```

## 8. Phase 4 --- Initialize the Cluster

Cluster initialization is a mutation.

``` text
[LAB-ONLY / PRODUCTION-CHANGE]
```

Use the PostgreSQL 18 `initdb` appropriate to the selected installation.

Conceptual example:

``` bash
initdb -D /pgdata/18/main
```

Do not blindly use defaults.

Before initialization, decide:

``` text
locale
encoding
data checksums
authentication bootstrap
WAL directory if separately designed
superuser/bootstrap ownership
```

Never run `initdb` against a directory containing an existing cluster.

### Verify initialization

After initialization and before application onboarding, verify:

``` text
PG_VERSION
base/
global/
pg_wal/
postgresql.conf or configured config location
pg_hba.conf or configured HBA location
```

Do not manually edit internal relation files.

### Gate 4

``` text
[ ] correct target directory initialized
[ ] PostgreSQL major version confirmed
[ ] locale/encoding decision recorded
[ ] checksum decision recorded
[ ] WAL layout verified
[ ] ownership/permissions verified
```

## 11. Phase 7 --- Configure Memory and Resources

Do not begin with generic percentages.

Build a memory model from:

``` text
host/container memory
shared_buffers
connection budget
work_mem exposure
hash_mem_multiplier
maintenance_work_mem
autovacuum exposure
temp_buffers
parallel workers
background workers
OS/filesystem cache
agents/monitoring
safety headroom
```

Inspect the effective configuration:

``` sql
-- [SAFE-READ]
SELECT name, setting, unit, context, source, pending_restart
FROM pg_settings
WHERE name IN (
    'shared_buffers',
    'work_mem',
    'hash_mem_multiplier',
    'maintenance_work_mem',
    'autovacuum_work_mem',
    'temp_buffers',
    'effective_cache_size',
    'huge_pages',
    'max_worker_processes',
    'max_parallel_workers',
    'max_parallel_workers_per_gather'
)
ORDER BY name;
```

### PostgreSQL 18 I/O configuration

Where applicable, include PostgreSQL 18 I/O settings in the resource
review:

``` sql
-- [SAFE-READ]
SELECT name, setting, unit, context, source, pending_restart
FROM pg_settings
WHERE name IN (
    'io_method',
    'io_workers',
    'io_max_concurrency'
)
ORDER BY name;
```

Do not copy I/O settings between servers without validating platform and
workload behavior.

## 12. Phase 8 --- Configure Connection and Session Capacity

Build the connection budget from the complete application topology:

``` text
application instances
× pool maximum
+ deployment surge
+ background jobs
+ ETL/reporting
+ monitoring
+ administration
+ failure/reconnect headroom
```

Review:

``` sql
-- [SAFE-READ]
SELECT name, setting, unit, context, source, pending_restart
FROM pg_settings
WHERE name IN (
    'max_connections',
    'reserved_connections',
    'superuser_reserved_connections',
    'authentication_timeout',
    'statement_timeout',
    'lock_timeout',
    'transaction_timeout',
    'idle_in_transaction_session_timeout',
    'idle_session_timeout',
    'client_connection_check_interval'
)
ORDER BY name;
```

Reserved capacity is not a substitute for capacity planning.

Do not grant reserved-connection privileges broadly to application
roles.

External connection pooling can be part of the architecture, but pooler
behavior must be validated for the application's transaction/session
semantics.

------------------------------------------------------------------------

## 13. Phase 9 --- Configure Network and Authentication

Network and authentication changes are security-sensitive.

Review:

``` sql
-- [SAFE-READ]
SELECT name, setting, context, source, pending_restart
FROM pg_settings
WHERE name IN ('listen_addresses', 'port', 'ssl')
ORDER BY name;
```

Design the complete access boundary:

``` text
listen_addresses
port
host firewall
cloud security group / NSG
Kubernetes/network policy
load balancer/proxy
TLS
pg_hba.conf
database roles
credential/secret management
```

### HBA review

Where permitted:

``` sql
-- [SAFE-READ]
SELECT
    rule_number,
    type,
    database,
    user_name,
    address,
    netmask,
    auth_method,
    error
FROM pg_hba_file_rules
ORDER BY rule_number;
```

Review rule order carefully. PostgreSQL uses the first matching HBA
record; there is no fallback to later records after authentication
fails.

Do not introduce broad `trust` access as a shortcut for production
connectivity.

### Gate 9

``` text
[ ] required clients can reach intended interface
[ ] unnecessary exposure avoided
[ ] HBA rules reviewed in order
[ ] authentication standard satisfied
[ ] TLS policy satisfied where required
[ ] administrative recovery path tested
```

``` sql
    'min_wal_size',
```


## 21. Running the Final Acceptance Script

Use standard libpq connection mechanisms:

``` bash
export PGHOST="db.example.internal"
export PGPORT="5432"
export PGDATABASE="postgres"
export PGUSER="acceptance_reader"
```

Use an approved credential mechanism such as `.pgpass`, `PGPASSFILE`, or
a secrets-management wrapper.

Do not commit plaintext passwords.

Run:

``` bash
chmod +x labs/production-server-acceptance.sh
./labs/production-server-acceptance.sh
```

Optional host checks can be enabled:

``` bash
CHECK_HOST=1 ./labs/production-server-acceptance.sh
```

Optional systemd inspection can be enabled by supplying the actual unit:

``` bash
CHECK_HOST=1 \
PG_SYSTEMD_UNIT="postgresql-example.service" \
./labs/production-server-acceptance.sh
```

The script never starts, stops, reloads, enables, or restarts the
service.

## 22. Acceptance Results

Classify findings rather than automatically remediating them.

``` text
PASS
    Evidence matches the approved baseline.

REVIEW
    Evidence requires human review or comparison to environment policy.

FAIL
    A defined acceptance requirement is not satisfied.

NOT CHECKED
    The artifact cannot safely validate the requirement.

NOT APPLICABLE
    The requirement does not apply to the architecture.
```

The generic script primarily gathers evidence and detects objective
conditions such as parsing errors or restart-pending settings.

Environment-specific acceptance thresholds belong in a separately
reviewed policy or manifest.

## 31. Production Principles

### Build from an architecture

Installation is an implementation step, not the architecture.

### Separate mutation from acceptance

A validator should not silently change the system it is validating.

### Validate effective state

Do not assume configuration text equals runtime state.

### Model capacity across boundaries

Connections, memory, workers, WAL, storage, and OS resources interact.

### Preserve administrative access

Security hardening must not destroy the tested recovery path.

### Treat backups as incomplete until restore is proven

Recoverability is the objective.

### Capture evidence

A reproducible build plus verifiable evidence improves operations,
incident response, and change safety.
