## 2.6.1 Introduction

PostgreSQL storage design is part of the database architecture, not merely a filesystem decision.

After PostgreSQL software installation and cluster initialization, the production design must establish where the cluster resides, what storage backs it, where WAL resides, whether external tablespaces exist, how much capacity headroom is available, and how the storage will be monitored and expanded.

```text
PostgreSQL cluster
        │
        ├── PGDATA
        │     ├── base/
        │     ├── global/
        │     ├── pg_wal/
        │     ├── pg_tblspc/
        │     └── cluster metadata
        │
        ├── optional external tablespaces
        │
        └── physical storage
              ├── capacity
              ├── IOPS
              ├── throughput
              ├── latency
              ├── durability
              └── failure characteristics
```

Production storage must therefore be designed around both **capacity and I/O behavior**.

## 2.6.3 `PGDATA`

`PGDATA` identifies the PostgreSQL cluster data directory.

A production deployment might use:

```text
/pgdata/18/main
```

The path itself is an organizational choice. What matters is that it is explicit, documented, correctly owned, appropriately protected, adequately sized, monitored, recoverable, and backed by suitable storage.

The acceptance workflow must not automatically discover and select a PostgreSQL cluster.

```text
PGDATA unset
        ↓
REQUIRES VALIDATION

PGDATA nonexistent
        ↓
BLOCKER

PGDATA explicitly supplied
        ↓
SAFE-READ validation
```

---

## 2.6.4 PostgreSQL Storage Layout

A PostgreSQL cluster normally contains structures such as:

```text
PGDATA/
├── PG_VERSION
├── base/
├── global/
├── pg_commit_ts/
├── pg_dynshmem/
├── pg_logical/
├── pg_multixact/
├── pg_notify/
├── pg_replslot/
├── pg_serial/
├── pg_snapshots/
├── pg_stat/
├── pg_stat_tmp/
├── pg_subtrans/
├── pg_tblspc/
├── pg_twophase/
├── pg_wal/
└── pg_xact/
```

Configuration files are traditionally stored with the data directory, but PostgreSQL permits configuration files to be located elsewhere. Therefore the physical presence of `postgresql.conf`, `pg_hba.conf`, or `pg_ident.conf` directly beneath `PGDATA` must not be treated as an unconditional storage-layout requirement.

---

## 2.6.5 PostgreSQL Owns Its Internal Files

Directories such as `base/`, `global/`, `pg_xact/`, `pg_multixact/`, `pg_wal/`, and `pg_tblspc/` are PostgreSQL-managed structures.

Operators should never manually remove relation files simply because they appear large. Filesystem deletion is not a substitute for supported PostgreSQL DDL or maintenance operations.

---

## 2.6.6 `base/`

`base/` contains per-database storage for databases using the default tablespace. Physical filenames are implementation details managed by PostgreSQL.

---

## 2.6.7 `global/`

`global/` contains cluster-wide relations associated with PostgreSQL's global storage. A cluster cannot safely be managed as a set of unrelated database directories.

---

## 2.6.8 WAL

PostgreSQL Write-Ahead Log normally appears as:

```text
PGDATA/pg_wal
```

WAL supports crash recovery, durability, replication, backup/recovery workflows, and point-in-time recovery architectures. WAL must never be treated as ordinary disposable logging.

---

## 2.6.9 WAL Physical Location

Although `pg_wal` normally appears beneath `PGDATA`, PostgreSQL supports initializing WAL on another storage location.

Inspect both the logical path and resolved path:

```bash
ls -ld "$PGDATA/pg_wal"
readlink -f "$PGDATA/pg_wal" 2>/dev/null || true
```

For a resolved WAL path:

```bash
df -hT "$resolved_wal_path"
df -i "$resolved_wal_path"
findmnt -T "$resolved_wal_path"
```

---

## 2.6.10 Never Delete WAL for Capacity Recovery

Deleting files from `pg_wal` merely to recover capacity is prohibited. A full or rapidly growing WAL filesystem requires diagnosis of the generation or retention cause, such as workload volume, archiving problems, replication behavior, replication slots, backup activity, or checkpoint behavior.

---

## 2.6.11 Dedicated Storage

A production architecture may separate operating-system and database storage:

```text
OS: /
PostgreSQL: /pgdata
Optional WAL: /pgwal
Optional tablespaces: /pgts/*
```

Potential advantages include clearer capacity ownership, storage monitoring, expansion planning, workload visibility, and reduced coupling with OS filesystem growth. A dedicated mount does not by itself guarantee performance.

---

## 2.6.12 Filesystem Identification

Do not assume `/pgdata` is a dedicated filesystem simply because the directory exists.

```bash
findmnt -T "$PGDATA"
df -hT "$PGDATA"
```

A directory path is not necessarily a filesystem boundary.

---

## 2.6.13 Filesystem Type

Inspect:

```bash
findmnt -T "$PGDATA" -no FSTYPE
```

The canonical tutorial does not declare one filesystem universally optimal. Selection depends on supported operating systems, platform architecture, operational practices, workload, backup/recovery requirements, and organizational standards.

---

## 2.6.14 Mount Options

Inspect:

```bash
findmnt -T "$PGDATA" -no OPTIONS
```

Changing mount options is outside SAFE-READ validation. The acceptance script must not modify `/etc/fstab`, remount filesystems, or change mount behavior.

---

## 2.6.15 Capacity

Inspect:

```bash
df -hT "$PGDATA"
```

Capacity analysis must consider current utilization, daily growth, WAL growth, maintenance headroom, workload growth, and expansion lead time. A universal utilization percentage is not used as a PostgreSQL safety rule.

---

## 2.6.16 Inodes

Inspect:

```bash
df -i "$PGDATA"
```

`df -h` reports byte capacity while `df -i` reports inode availability.

---

## 2.6.17 Growth-Based Capacity Planning

For example, growth from 1.05 TB to 1.20 TB over 30 days is approximately 150 GB / 30, or 5 GB/day. A simple 90-day projection is about 450 GB.

Production forecasting should additionally account for new workloads, retention changes, indexes, WAL generation, maintenance, seasonal growth, migration activity, and safety headroom.

---

## 2.6.18 Maintenance Headroom

Operations such as `CREATE INDEX`, `REINDEX`, `VACUUM FULL`, `CLUSTER`, table rewrites, large ingestion, migrations, and WAL bursts may require substantial additional storage. Normal workload fitting on a filesystem does not prove that planned maintenance will fit.

---

## 2.6.19 Storage Performance

Capacity alone does not define suitable database storage. Production storage should also be evaluated for latency, IOPS, throughput, queueing, durability, and failure behavior.

---

## 2.6.20 Production Benchmark Safety

The acceptance lab must not generate synthetic writes against production storage. It must not automatically run `fio` write workloads, `dd` write tests, large temporary-file generation, or stress workloads. Missing diagnostic packages must not be installed automatically.

---

## 2.6.21 Built-In Tablespaces

PostgreSQL provides built-in tablespaces including `pg_default` and `pg_global`. `pg_default` provides normal default placement for user objects; `pg_global` contains shared cluster-wide objects.

---

## 2.6.22 External Tablespaces

Tablespaces allow PostgreSQL objects to be placed in filesystem locations outside normal default storage. They are storage-placement mechanisms, not independent PostgreSQL clusters.

---

## 2.6.23 Appropriate Tablespace Use

Tablespaces can be useful for different storage devices, capacity expansion, storage-tier placement, workload placement, or controlled migration.

They should not be created merely because applications use different schemas. Logical organization is not the same as physical storage placement. Multiple tablespaces on the same underlying logical filesystem often provide little physical-storage isolation.

---

## 2.6.24 Creating a Tablespace

Conceptual example:

```sql
CREATE TABLESPACE fast_ts
OWNER postgres
LOCATION '/pgts/fast';
```

This is `[TUTORIAL-DBA-ACTION — MUTATING]`.

Filesystem preparation is a separate `[TUTORIAL-OPERATOR-ACTION — MUTATING]` activity. The target must be intentionally prepared according to PostgreSQL requirements. The acceptance artifact does not create it.

---

## 2.6.25 `pg_tblspc`

External tablespaces are represented through PostgreSQL-managed symbolic links beneath:

```text
PGDATA/pg_tblspc
```

SAFE-READ inspection:

```bash
ls -la "$PGDATA/pg_tblspc"

find "$PGDATA/pg_tblspc" \
  -maxdepth 1 \
  -mindepth 1 \
  -type l \
  -printf '%f -> %l\n'
```

Do not manually modify these links.

---

## 2.6.26 Empty `pg_tblspc`

An empty `PGDATA/pg_tblspc` does not mean PostgreSQL has no tablespaces. It normally means there are no external/user-defined tablespace links. Built-in tablespaces still exist.

---

## 2.6.27 Tablespace Target Validation

Every external tablespace link should be resolved and its target checked for availability, filesystem accessibility, capacity, and ownership expectations.

A dangling or unavailable tablespace target is a `BLOCKER`. The acceptance script must not recreate the link, mount a filesystem, or attempt automatic recovery.

---

## 2.6.28 Tablespace Failure Domain

An external tablespace remains part of the PostgreSQL cluster. Backup, recovery, monitoring, and disaster-recovery architecture must account for external tablespaces.

---

## 2.6.29 Optional Online Tablespace Inventory

If PostgreSQL is already running and database access is intentionally available:

```sql
SELECT
    spcname,
    spcowner::regrole,
    pg_tablespace_location(oid)
FROM pg_tablespace
ORDER BY spcname;
```

This is `[TUTORIAL-ACCEPTANCE — SAFE-READ]`.

If the server is offline, this validation is `NOT APPLICABLE`. The acceptance workflow must never start PostgreSQL merely to execute this query.

---

## 2.6.30 Ownership

Inspect:

```bash
stat -c '%U %G %a %n' "$PGDATA"
```

Unexpected ownership should be reported rather than corrected automatically.

---

## 2.6.31 Permissions

The lab must account for both an expected owner-only model and an intentionally approved PostgreSQL group-read model. Unexpected broad access is a `WARNING` or `BLOCKER`; an ambiguous access model is `REQUIRES VALIDATION`.

No automatic `chmod`, `chown`, or ACL modification is permitted.

---

## 2.6.32 Cloud Block Storage

Cloud-backed PostgreSQL storage should consider both capacity and performance envelope, including IOPS, throughput, latency, burst behavior, queue depth, volume size, instance-level storage limits, expansion behavior, and durability.

These are infrastructure/platform characteristics rather than universal PostgreSQL guarantees.

---

## 2.6.33 Storage Monitoring

Production monitoring should provide visibility into capacity, growth, inode utilization where relevant, latency, IOPS, throughput, queueing, WAL growth, tablespace capacity, and storage errors.

---

## 2.6.34 Prohibited Filesystem Operations

Do not casually delete relation files or WAL, manually alter `pg_tblspc`, move live `PGDATA`, replace live storage mounts, recursively change permissions/ownership, or copy live `PGDATA` as though it were an ordinary filesystem backup.

---

## 2.6.35 Acceptance Stop Conditions

### BLOCKER

- `PGDATA` missing or inaccessible
- `PG_VERSION` missing from the expected initialized cluster
- `pg_wal` missing
- resolved WAL target unavailable
- critical filesystem unavailable
- dangling tablespace target
- required tablespace filesystem unavailable
- unexpected severe permission exposure

### REQUIRES VALIDATION

- unexpected `PGDATA` owner
- nonstandard permission model
- unknown mount architecture
- unexpected WAL placement
- unknown tablespace ownership
- unusual filesystem architecture
- ambiguous shared-storage configuration

The acceptance script reports these conditions. It does not repair them.

```bash

df -i "$PGDATA"
findmnt -T "$PGDATA"
```

Record device, filesystem, mount, capacity, utilization, inode utilization, and mount options.

## 2.6.40 Inspect Mount Options

```bash
findmnt -T "$PGDATA" -no OPTIONS
```

Do not remount or modify `/etc/fstab`.

---

## 2.6.41 Inspect WAL

```bash
ls -ld "$PGDATA/pg_wal"
readlink -f "$PGDATA/pg_wal" 2>/dev/null || true
```

Inspect the resolved target using SAFE-READ filesystem commands.

---

## 2.6.42 Inspect Tablespaces

```bash
ls -la "$PGDATA/pg_tblspc"

find "$PGDATA/pg_tblspc" \
  -maxdepth 1 \
  -mindepth 1 \
  -type l \
  -printf '%f -> %l\n'
```

Resolve each external target individually. Do not recursively follow arbitrary symlinks throughout `PGDATA`.

## 2.6.45 Acceptance Script Prohibitions

The canonical artifact must never invoke mutating operations including:

- privilege switching (`sudo`, `su`, `runuser`);
- file/directory creation, deletion, copying, moving, or permission changes;
- symlink creation/removal;
- mount/unmount, filesystem creation/repair/resize, or LVM resize;
- `initdb`;
- tablespace DDL;
- PostgreSQL start/stop/restart;
- systemd mutations;
- package installation;
- PostgreSQL configuration mutation;
- synthetic storage write benchmarks;
- automatic remediation.

---

## 2.6.46 Operational Decision Model

```text
Storage observation
        ↓
Is the target unambiguously healthy?
        │
        ├── Yes → PASS
        │
        └── No
             ↓
Can safety be determined without mutation?
        │
        ├── Yes → WARNING / BLOCKER
        │
        └── No → REQUIRES VALIDATION
```

**Detection must not silently become remediation.**
