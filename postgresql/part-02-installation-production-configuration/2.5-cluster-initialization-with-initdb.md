# 2.5 — Cluster Initialization with `initdb`

**Part:** 2 — Installation & Production Configuration
**Edition:** Revised Final / Canonical
**Target:** PostgreSQL 18 on Linux
**Initialization classification:** `[TUTORIAL-OPERATOR-ACTION — MUTATING]`
**Acceptance classification:** `[TUTORIAL-ACCEPTANCE — SAFE-READ]`

---

# 2.5.1 Introduction

Installing PostgreSQL software and creating a PostgreSQL database cluster are separate lifecycle operations.

Parts 2.3 and 2.4 established the PostgreSQL software layer.

Part 2.5 establishes the initial database-cluster layer.

```text
PostgreSQL software installed
        ↓
Initialization design approved
        ↓
Exact initdb binary verified
        ↓
PGDATA validated
        ↓
Cluster owner validated
        ↓
Locale/provider selected
        ↓
Encoding selected
        ↓
Checksum policy confirmed
        ↓
Authentication bootstrap selected
        ↓
WAL layout confirmed
        ↓
Controlled initdb
        ↓
PostgreSQL cluster created
        ↓
SAFE-READ offline validation
        ↓
Initialization evidence
```

Before `initdb`:

```text
PostgreSQL software exists
Database cluster does not yet exist
```

After successful `initdb`:

```text
PGDATA contains persistent PostgreSQL cluster state
```

`initdb` is therefore not an exploratory command.

It is a deliberate, persistent, **mutating lifecycle operation**.

# 2.5.3 Installation Is Not Initialization

PostgreSQL installation produces software:

```text
PostgreSQL binaries
libraries
extensions
supporting files
documentation
```

Cluster initialization produces persistent database state:

```text
PGDATA
system catalogs
template databases
configuration files
WAL structure
control metadata
transaction state
```

Therefore:

```text
postgres --version succeeds
```

does not prove:

```text
A PostgreSQL database cluster exists.
```

Likewise, a PostgreSQL installation may support more than one independently initialized cluster.

---

# 2.5.4 What `initdb` Creates

`initdb` creates a new PostgreSQL database cluster.

Conceptually:

```text
Approved empty target
        ↓
       initdb
        ↓
Initialized PostgreSQL cluster
```

The resulting cluster contains PostgreSQL-managed structures such as:

```text
PG_VERSION
base/
global/
pg_wal/
postgresql.conf
pg_hba.conf
pg_ident.conf
```

and other internal directories and files required by PostgreSQL.

These are PostgreSQL-managed cluster state.

They must not be treated as disposable build artifacts.

---

# 2.5.5 Default Databases

Initialization creates the standard databases:

```text
template0
template1
postgres
```

Conceptually:

```text
template0
   ↓
pristine template baseline

template1
   ↓
default template for CREATE DATABASE

postgres
   ↓
general administrative/default connection database
```

These databases are part of PostgreSQL's bootstrap architecture.

# 2.5.6 Safety Classification

Running:

```bash

```

is classified:

```text
[TUTORIAL-OPERATOR-ACTION — MUTATING]
```

because it creates persistent cluster state.

Inspection is separate:

```text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
```

SAFE-READ examples include:

```text
inspect host
inspect architecture
inspect identity
inspect PostgreSQL binaries
inspect filesystem
inspect directory contents
inspect ownership
inspect permissions
inspect locale
inspect PG_VERSION
inspect cluster structure
inspect control metadata
inspect PostgreSQL processes
```

The canonical acceptance artifact must never invoke `initdb`.

# 2.5.9 Verify the Exact PostgreSQL 18 Binary

Where multiple installations may coexist, do not rely only on shell resolution.

Inspect:

```bash
command -v initdb
initdb --version
```

but prefer the approved absolute path for execution.

For example, for the tutorial source installation:

```bash
/opt/postgresql/18/bin/initdb --version
```

Expected major version:

```text
PostgreSQL 18
```

Wrong major version:

```text
BLOCKER
```

Do not initialize first and discover the version afterward.

# 2.5.10 Define `PGDATA`

The tutorial uses:

```text
/pgdata/18/main
```

as its example `PGDATA`.

This is an organizational convention.

It is **not a PostgreSQL requirement**.

A valid production path must instead satisfy the deployment's requirements for:

```text
persistence
capacity
performance
ownership
permissions
backup
monitoring
failure recovery
operational clarity
```

Record the exact path before initialization.

# 2.5.11 Validate the Filesystem

Inspect the intended filesystem before initialization.

For example:

```bash
df -h /pgdata
df -i /pgdata
```

Understand:

```text
device
filesystem
mount point
capacity
inode capacity
persistence
failure domain
backup implications
monitoring
```

Do not initialize PostgreSQL onto storage whose operational purpose is unknown.

---

# 2.5.12 Validate Target-Directory State

Inspect:

```bash
ls -ld /pgdata/18/main
```

and, where permitted:

```bash
find /pgdata/18/main -mindepth 1 -maxdepth 1 -print
```

For a new cluster, the initialization target must be intentionally suitable for initialization.

Unknown existing contents require investigation.

Classification:

```text
REQUIRES VALIDATION
```

or, when they conflict with the intended initialization:

```text
BLOCKER
```

Never automatically execute:

```bash
rm -rf /pgdata/18/main/*
```

to make `initdb` succeed.

Unknown files are evidence.

# 2.5.13 Detect Existing Cluster State

Indicators of an existing PostgreSQL cluster include:

```text
PG_VERSION
global/pg_control
base/
pg_wal/
postgresql.conf
pg_hba.conf
```

If these appear unexpectedly:

```text
STOP
        ↓
Identify the cluster
        ↓
Determine ownership
        ↓
Determine version
        ↓
Determine operational purpose
```

Do not delete existing PostgreSQL state to repeat a tutorial.

---

# 2.5.14 Cluster Owner

`initdb` must be executed by the operating-system account that will own the PostgreSQL server process.

A common convention is:

```text
postgres
```

but PostgreSQL does not require that literal username.

The important relationship is:

```text
initdb execution owner
        =
cluster file owner
        =
PostgreSQL server operating-system owner
```

unless an explicitly supported architecture says otherwise.

---

# 2.5.15 Never Run `initdb` as Root

`initdb` must not be executed as root.

Use the operational model:

```text
Privileged storage preparation
        ↓
Correct ownership established
        ↓
Privilege boundary crossed
        ↓
Approved PostgreSQL service account
        ↓
Identity verified
        ↓
initdb
```

Immediately before initialization:

```bash
id
```

Verify the intended account.

Do not put automatic `sudo`, `su`, or `runuser` behavior into the acceptance artifact.

---

# 2.5.16 Ownership Validation

Inspect:

```bash
id
ls -ld "$PGDATA"
```

The cluster owner must have the access required to initialize and operate the cluster.

If ownership is wrong, document the problem.

Do not let SAFE-READ acceptance automatically run:

```text
chown
chmod
setfacl
```

Filesystem remediation is a separately authorized mutation.

---

# 2.5.17 Directory Permissions

PostgreSQL protects cluster data from unintended access.

The appropriate permission design depends on the approved operating model.

Do not blindly prescribe one permission mode without understanding requirements involving:

```text
server owner
approved group access
backup software
monitoring
security policy
host controls
```

Likewise, do not weaken permissions simply to make initialization succeed.

# 2.5.19 PostgreSQL 18 Locale Providers

PostgreSQL 18 supports locale-provider choices including:

```text
libc
icu
builtin
```

`libc` is the default provider.

The provider should be deliberately understood and recorded rather than inferred after initialization.

---

# 2.5.20 `libc` Provider

With:

```text
--locale-provider=libc
```

PostgreSQL uses operating-system locale facilities.

The host's locale environment is therefore part of the initialization context.

Record the selected locale and operating-system environment.

---

# 2.5.21 ICU Provider

An ICU-backed initialization requires PostgreSQL built with the corresponding ICU capability.

Conceptually:

```bash
initdb \
  --locale-provider=icu \
  --icu-locale=<approved-locale> \
  ...
```

Before using ICU, validate:

```text
PostgreSQL ICU capability
approved ICU locale
application requirements
collation expectations
upgrade/migration implications
```

Also inspect and preserve the locale summary reported during initialization.

---

# 2.5.22 Builtin Provider

PostgreSQL 18's builtin locale provider supports defined builtin locale behavior.

Relevant supported initialization locales include:

```text
C
C.UTF-8
PG_UNICODE_FAST
```

Do not treat builtin, libc, and ICU as interchangeable implementations.

Record the selected provider and locale.

---

# 2.5.23 Encoding

Cluster initialization establishes the default encoding used by the template databases.

Production evidence should record:

```text
Encoding:
Locale provider:
Locale:
```

`UTF8` is common, but the tutorial does not treat it as an unexplained universal requirement.

The application and localization design should determine the value.

---

# 2.5.24 Locale and Encoding Compatibility

Do not independently select arbitrary locale and encoding values.

Use:

```text
Application requirement
        ↓
Locale/provider design
        ↓
Compatible encoding
        ↓
Initialization
```

If compatibility is unresolved:

```text
BLOCKER / REQUIRES VALIDATION
```

depending on whether initialization is imminent.

---

# 2.5.25 PostgreSQL 18 Data Checksums

PostgreSQL 18 introduces an important initialization-default change:

```text
Data checksums are enabled by default.
```

Therefore a normal PostgreSQL 18 `initdb` creates a checksum-enabled cluster unless that default is explicitly overridden.

Older operational material that assumes:

```text
Checksums default OFF
```

must not be carried forward into this tutorial.

---

# 2.5.26 `--no-data-checksums`

PostgreSQL 18 provides:

```text
--no-data-checksums
```

to disable the new default.

This is an explicit architecture exception.

It must not be inserted into the normal production tutorial command simply to reproduce older behavior.

Record:

```text
Data checksums:
ENABLED / DISABLED

Reason:
```

before initialization.

---

# 2.5.27 Authentication Bootstrap

`initdb` generates the initial `pg_hba.conf`.

Authentication bootstrap therefore requires deliberate design.

Relevant initialization controls include:

```text
--auth
--auth-local
--auth-host
```

Record:

```text
Local authentication:
Host authentication:
```

before execution.

These settings establish the initial HBA baseline.

They do not replace the complete production authentication design covered later in Part 2.10.

---

# 2.5.28 Avoid Blind `trust`

Do not teach:

```bash
initdb --auth=trust ...
```

as the generic production baseline.

`trust` allows matching connections without password verification.

It may be appropriate only where the associated trust boundary is explicitly understood and approved.

Initialization convenience is not sufficient justification for a broad production trust policy.

---

# 2.5.29 Local and Host Authentication

PostgreSQL permits separate bootstrap policies for:

```text
local Unix-domain socket connections
```

and:

```text
TCP/IP host connections
```

using:

```text
--auth-local
--auth-host
```

This can be useful because these connection paths may have different trust boundaries.

---

# 2.5.30 SCRAM

Where password authentication is required, PostgreSQL's modern password-authentication mechanism is:

```text
scram-sha-256
```

For example, an approved design could specify:

```text
Local authentication:
<approved local policy>

Host authentication:
scram-sha-256
```

Authentication is not equivalent to transport security.

Remote production access still requires the appropriate network and TLS/security design.

---

# 2.5.31 Bootstrap Database Superuser

`initdb` creates the bootstrap database superuser.

By default, its name corresponds to the operating-system account running `initdb`.

A different database username can be selected using:

```text
--username
```

Record both identities:

```text
OS cluster owner:
Bootstrap DB superuser:
```

Do not assume they must always have the same literal name.

---

# 2.5.32 Bootstrap Credential Handling

If bootstrap password provisioning is required, use an approved credential-handling mechanism.

PostgreSQL supports controlled mechanisms such as password prompting and password-file input.

Never place the actual password into:

```text
Git
tutorial manuscripts
learner evidence
shell command history
tickets
terminal transcripts
general-purpose logs
```

The learner artifact may record:

```text
Password provisioning method:
<approved mechanism>
```

It must not record the secret itself.

---

# 2.5.33 Default WAL Location

By default PostgreSQL places WAL beneath:

```text
PGDATA/pg_wal
```

This is the normal baseline.

Do not teach:

```text
Production PostgreSQL must always place WAL on another disk.
```

That is not a universal PostgreSQL requirement.

---

# 2.5.34 Separate WAL Directory

`initdb` can use another WAL location when an explicit architecture requires it.

Evaluate:

```text
storage performance
latency
durability
failure domains
cloud-volume characteristics
backup/recovery
monitoring
operational complexity
```

A separate WAL location should solve an identified architectural problem.

It should not exist because of folklore.

---

# 2.5.35 WAL Segment Size

PostgreSQL's standard WAL segment-size default is:

```text
16 MB
```

A different segment size can be selected during initialization.

Changing it is an initialization-time architectural choice.

Record any nondefault value and its rationale.

Do not change it as generic tuning.

---

# 2.5.36 Synchronization Safety

Normal production initialization should allow PostgreSQL to synchronize the files it creates safely.

Do not make these part of the normal production tutorial command:

```text
--no-sync
--no-sync-data-files
```

These controls may be useful in specialized or testing scenarios, but they weaken the normal initialization durability workflow.

They require explicit context and justification.

---

# 2.5.37 `--sync-only` Is Not Initialization

Do not confuse:

```text
initdb --sync-only
```

with creating a PostgreSQL cluster.

`--sync-only` performs synchronization-related work against existing database files and exits.

It does not replace normal cluster initialization.

# 2.5.48 `pg_controldata`

Where the matching PostgreSQL 18 utility is available, use its approved absolute path.

For example:

```bash
/opt/postgresql/18/bin/pg_controldata "$PGDATA"
```

It can help inspect initialization properties without starting PostgreSQL.

If permissions prevent inspection:

```text
REQUIRES VALIDATION
```

The SAFE-READ artifact must not invoke `sudo` to bypass that boundary.

# 2.5.49 Offline Checksum-State Validation

For this initialization stage, prefer cluster-control metadata to establish the configured checksum state.

The expected PostgreSQL 18 baseline is:

```text
Checksums enabled
```

unless the approved initialization plan explicitly selected otherwise.

Do not start PostgreSQL merely to run:

```sql
SHOW data_checksums;
```

Part 2.5 remains offline.

---

# 2.5.50 `pg_checksums` Safety Boundary

`pg_checksums` has both inspection and mutation capabilities.

A checksum verification operation may be read-oriented but can also be I/O intensive.

Do not require a full relation-file checksum scan as the default Part 2.5 acceptance check.

Most importantly, the SAFE-READ artifact must never execute:

```text
pg_checksums --enable
pg_checksums --disable
```

Those operations modify cluster state.
