# Part 2.9 — Connection and Session Configuration

**Status:** Revised Final / Canonical Edition  
**Target:** PostgreSQL 18  
**Audience:** PostgreSQL administrators, SREs, DBREs, platform engineers, and application engineers.

---

## 2.9.1 Objectives

This tutorial explains PostgreSQL connection capacity, listener behavior, authentication boundaries, session configuration, timeouts, connection pooling, and safe troubleshooting.

After completing it, you should be able to:

- explain the PostgreSQL connection path;
- inspect listener, port, socket, connection-limit, authentication, and session settings;
- distinguish ordinary, reserved-role, and superuser-reserved connection capacity;
- understand `pg_use_reserved_connections`;
- inspect active sessions and connection ownership;
- distinguish TCP connections from Unix-domain socket connections;
- understand HBA first-match behavior;
- inspect HBA rules without modifying them;
- understand PostgreSQL 18 SCRAM guidance and legacy MD5 considerations;
- distinguish authentication from authorization;
- use session-scoped and transaction-local settings safely;
- explain `search_path` correctness and security implications;
- distinguish statement, lock, idle-session, and idle-in-transaction timeouts;
- build a system-level connection budget;
- troubleshoot connection storms without blindly raising `max_connections`.

```text
Application
    |

    v

    |
    v

    |
```


## 2.9.5 Listener and Port

```sql
-- [SAFE-READ]
SHOW listen_addresses;
SHOW port;
```

PostgreSQL normally uses TCP port `5432` by default, but production systems can use another port.

`listen_addresses` determines which IP interfaces PostgreSQL attempts to listen on. A value of `*` does not itself authorize remote access.

Successful remote access depends on multiple controls:

```text
network route/firewall
        +
listen_addresses
        +
pg_hba.conf
        +
authentication
        +
database authorization
```

`listen_addresses` and `port` are server-start settings. Do not change them in this lab.

> **Production safety:** Never use `listen_addresses='*'` merely as a troubleshooting shortcut. Review network exposure, firewall/security-group policy, TLS, HBA rules, and authentication first.

## 2.9.6 Unix-Domain Sockets

PostgreSQL can also accept local connections through Unix-domain sockets.

```sql
-- [SAFE-READ]
SHOW unix_socket_directories;
```

Conceptually:

```text
TCP:
client -> IP address -> TCP port -> PostgreSQL

Unix socket:
local client -> socket file -> PostgreSQL
```

This distinction explains why client/server IP functions can return `NULL` for a local socket connection.

```sql
-- [SAFE-READ]
SELECT
    inet_client_addr(),
    inet_client_port(),
    inet_server_addr(),
    inet_server_port();
```

Do not interpret a `NULL` client IP as automatically indicating a broken session.

## 2.9.7 Connection Capacity

```sql
-- [SAFE-READ]
SHOW max_connections;
SHOW reserved_connections;
SHOW superuser_reserved_connections;
```

PostgreSQL 18 provides layered connection capacity:

```text
max_connections
|
+-- ordinary capacity
|
+-- reserved_connections
|     -> superusers and roles with privileges of
|        pg_use_reserved_connections
|
`-- superuser_reserved_connections
      -> final superuser reserve
```

When ordinary slots are exhausted, eligible roles can use `reserved_connections`. When only the superuser-reserved slots remain, only superusers can connect.

Do not grant `pg_use_reserved_connections` broadly to normal application roles. Reserved capacity is intended to preserve operational access.

---

## 2.9.8 Do Not Treat `max_connections` as a Target

A server configured with:

```text
max_connections = 500
```

does not imply that 500 application sessions should normally remain connected.

A connection budget must consider:

```text
application pools
+ application replicas
+ ETL/batch
+ monitoring
+ administrative access
+ operational tools
+ reserved capacity
+ memory/CPU/workload constraints
```

Increasing `max_connections` increases PostgreSQL resource requirements and requires restart.

Do not use:

```text
too many connections -> increase max_connections
```

as an incident response procedure.

Investigate the source first.

## 2.9.9 Current Session Utilization

```sql
-- [SAFE-READ]
SELECT count(*) AS current_connections
FROM pg_stat_activity;
```

Break down by state:

```sql
-- [SAFE-READ]
SELECT
    state,
    count(*) AS connections
FROM pg_stat_activity
GROUP BY state
ORDER BY connections DESC, state NULLS LAST;
```

By user/application:

```sql
-- [SAFE-READ]
SELECT
    usename,
    COALESCE(NULLIF(application_name, ''), '<unset>') AS application_name,
    state,
    count(*) AS sessions
FROM pg_stat_activity
GROUP BY
    usename,
    COALESCE(NULLIF(application_name, ''), '<unset>'),
    state
ORDER BY sessions DESC;
```

Do not terminate sessions merely because they are idle.

## 2.9.12 TCP Keepalive and Client Checking

```sql
-- [SAFE-READ]
SHOW tcp_keepalives_idle;
SHOW tcp_keepalives_interval;
SHOW tcp_keepalives_count;
SHOW tcp_user_timeout;
SHOW client_connection_check_interval;
```

TCP keepalives and `client_connection_check_interval` are different mechanisms.

`client_connection_check_interval` controls periodic checks for client disconnection while a query is running. A zero value disables periodic checks.

TCP behavior is platform-dependent. `tcp_user_timeout` requires operating-system support and is irrelevant to Unix-domain socket sessions.

Do not tune these parameters blindly; consider the operating system, load balancers, proxies, firewalls, poolers, and application retry behavior.

## 2.9.14 Authentication Is Not Authorization

```text
Authentication:
    Who are you?

Authorization:
    What may you access or execute?
```

A successful login does not grant unrestricted access to databases, schemas, tables, sequences, functions, or other objects.

## 2.9.15 HBA Inspection

PostgreSQL exposes parsed HBA information through `pg_hba_file_rules`.

```sql
-- [SAFE-READ — SECURITY-SENSITIVE OUTPUT]
SELECT
    rule_number,
    type,
    database,
    user_name,
    address,
    auth_method,
    options,
    error
FROM pg_hba_file_rules
ORDER BY rule_number;
```

A non-null `error` indicates a problem with the corresponding record.

HBA output can reveal database names, roles, source networks, and authentication methods. Do not paste full output into public tickets, screenshots, or repositories without review.

Visibility may depend on privileges.

---

## 2.9.16 HBA First-Match Behavior

HBA records are evaluated in order.

```text
connection
   |
Rule 1 -> no match
   |
Rule 2 -> no match
   |
Rule 3 -> MATCH
   |
use Rule 3 authentication method
   |
success OR failure
```

PostgreSQL does not fall through to a later rule when authentication under the first matching record fails.

Therefore rule order is operationally significant.

Never add a broad HBA record without reviewing relevant earlier and later records.

---

## 2.9.17 Safe HBA Change Workflow

HBA modification is a production change, not part of this lab.

```text
understand requested access
        |
identify exact source/network
        |
identify database and role
        |
select authentication method
        |
review existing rule order
        |
add the narrowest appropriate rule
        |
validate configuration
        |
reload/apply using platform procedure
        |
test a NEW connection
        |
keep known-good admin access until validated
```

On Unix-like systems HBA changes normally require PostgreSQL to reread configuration. PostgreSQL has platform-specific behavior, including different handling on Windows.

Never switch an HBA rule to `trust` simply to make an authentication problem disappear.

## 2.9.18 PostgreSQL 18 Password Authentication

```sql
-- [SAFE-READ]
SHOW password_encryption;
```

For new PostgreSQL 18 deployments, prefer SCRAM-SHA-256 password authentication where password authentication is required and clients support it.

Legacy MD5-encrypted password support is deprecated.

A controlled migration should follow:

```text
inventory client libraries
        |
verify SCRAM compatibility
        |
configure password encryption
        |
rotate selected credentials
        |
validate applications
        |
migrate HBA policy
        |
monitor
```

A PostgreSQL HBA rule that says `md5` can negotiate SCRAM when the role's stored password is SCRAM-based. Understand this behavior when migrating.

Never expose password verifiers or credential material in tutorial output.

## 2.9.22 `search_path`

```sql
-- [SAFE-READ]
SHOW search_path;
```

`search_path` determines how unqualified object names are resolved.

```sql
SELECT * FROM orders;
```

depends on the effective path.

Explicit qualification:

```sql
SELECT * FROM sales.orders;
```

makes object resolution clearer.

`search_path` is both a correctness and security concern. Privileged functions and operational scripts require particular care when resolving unqualified objects through schemas writable by untrusted roles.

## 2.9.24 Timeout Family

These settings solve different problems:

```text
statement_timeout
    -> statement execution duration

lock_timeout
    -> time waiting to acquire a lock

idle_in_transaction_session_timeout
    -> idle time while an open transaction exists

idle_session_timeout
    -> ordinary idle session duration
```

Timeout policy should be workload-specific. A value appropriate for an API may be unsuitable for ETL, reporting, analytics, or maintenance.

```sql
-- [SESSION-LOCAL]
```


## 2.9.27 Idle vs Idle in Transaction

```text
idle
    -> connected
    -> no current statement
    -> no active transaction

idle in transaction
    -> connected
    -> transaction remains open
    -> can retain locks/snapshots and increase operational risk
```

Inspect:

```sql
-- [SAFE-READ]
SELECT
    pid,
    usename,
    application_name,
    state,
    xact_start,
    state_change
FROM pg_stat_activity
WHERE state LIKE 'idle in transaction%';
```

Do not automatically terminate these sessions. First identify the application, transaction age, locks, workload, and retry behavior.

## 2.9.28 `idle_session_timeout` and Poolers

Before applying `idle_session_timeout`, understand:

```text
[ ] connection pooler/middleware
[ ] pooling mode
[ ] expected idle lifecycle
[ ] reconnect behavior
[ ] retry behavior
[ ] representative production traffic
```

Unexpected server-side closure of idle connections can interact poorly with middleware that expects them to persist.

## 2.9.29 `SET` vs `SET LOCAL`

Session-scoped:

```sql
SET statement_timeout = '5s';
```

It remains until reset, changed, or the session ends.

Transaction-local:

```sql
BEGIN;

SET LOCAL statement_timeout = '2s';

SHOW statement_timeout;

COMMIT;
```

After the transaction, the transaction-local value no longer applies.

For controlled administrative work, `SET LOCAL` can provide a useful narrow scope.

## 2.9.30 Database and Role Defaults

Persistent defaults can be configured at database or role scope, for example:

```sql
-- [PRODUCTION-CHANGE — EXAMPLE ONLY]
ALTER DATABASE appdb
SET statement_timeout = '30s';

ALTER ROLE app_user
SET statement_timeout = '30s';
```

PostgreSQL can also apply role-specific settings within a particular database.

Do not execute these examples in this lab. They affect future sessions and require change review.

## 2.9.31 Connection Pooling and Budgeting

A connection pool controls physical PostgreSQL connection concurrency but does not eliminate capacity planning.

```text
pool size
× application replicas
× services
× independently scaled workloads
```

Example:

```text
20 connections / instance
× 10 instances
× 4 services
= 800 possible PostgreSQL connections
```

A production budget should reserve capacity for:

```text
application workloads
ETL/batch
monitoring
DBA/SRE access
operational tooling
reserved-role access
superuser emergency access
```

The hard connection ceiling is a protection boundary, not a utilization target.

## 2.9.32 Connection Storm Troubleshooting

Start with read-only inspection:

```sql
SELECT count(*) AS connections
FROM pg_stat_activity;

SELECT
    usename,
    COALESCE(NULLIF(application_name, ''), '<unset>') AS application_name,
    state,
    count(*) AS sessions
FROM pg_stat_activity
GROUP BY
    usename,
    COALESCE(NULLIF(application_name, ''), '<unset>'),
    state
ORDER BY sessions DESC;
```

Investigate:

```text
connection leaks
pool configuration
application replica growth
retry storms
deployment events
batch jobs
monitoring
idle sessions
idle-in-transaction sessions
proxy/pooler behavior
recent configuration changes
```

Do not automatically increase `max_connections`.

## 2.9.37 Key Takeaways

```text
listen_addresses
    -> network interfaces PostgreSQL listens on

max_connections
    -> hard connection-capacity boundary

reserved_connections
    -> operational reserve for eligible roles

superuser_reserved_connections
    -> final superuser reserve

pg_use_reserved_connections
    -> privilege enabling eligible use of reserved slots

pg_hba.conf
    -> ordered client-authentication rules

authentication
    != authorization

idle
    != idle in transaction

SET
    != persistent server configuration

SET LOCAL
    -> transaction-local configuration

search_path
    -> correctness and security consideration

connection pool size
    != total architecture connection budget
```

The operational method is:

```text
identify failing layer
        ->
inspect effective configuration
        ->
measure actual connection demand
        ->
make the narrowest safe change
        ->
validate with a new connection
        ->
monitor
        ->
rollback when required
```
