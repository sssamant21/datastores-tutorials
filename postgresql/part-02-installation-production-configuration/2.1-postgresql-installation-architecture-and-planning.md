## 2.1.1 Introduction

A reliable PostgreSQL deployment begins before PostgreSQL is installed.

Installing packages is usually one of the simplest parts of building a database server. The harder questions are architectural:

- Which PostgreSQL major version will be deployed?
- Which Linux platform will host it?
- How will PostgreSQL be installed and patched?
- Where will persistent database data live?
- What CPU, memory, storage, and connection capacity is required?
- Which networks may reach PostgreSQL?
- How will authentication and transport security be handled?
- How will the server be started and stopped?
- How will logs and metrics be collected?
- How will the database be backed up and restored?
- What are the required RPO and RTO?
- Who owns configuration, patching, monitoring, backup, and capacity?

A disposable development system can sometimes tolerate decisions being made after installation.

A production system should not.

The objective of this section is therefore not to install PostgreSQL.

The objective is to create an intentional **PostgreSQL Server Build Specification** that will guide the remainder of Part 2.

In this tutorial, **build** means designing and deploying the complete PostgreSQL server. It does not imply that PostgreSQL must be compiled from source.

# 2.1.3 Think in Layers

A PostgreSQL deployment is more than a database process.

A simplified production stack is:

```text
Applications / Users
        │
        ▼
DNS / Service Discovery
        │
        ▼
Network / Firewall
        │
        ▼
PostgreSQL Network Listener
        │
        ▼
Client Authentication
        │
        ▼
Database Authorization
        │
        ▼
PostgreSQL Server Processes
        │
        ▼
PostgreSQL Configuration
        │
        ▼
Database Cluster / PGDATA
        │
        ▼
Filesystem / Storage
        │
        ▼
Linux Operating System
        │
        ▼
Compute Infrastructure
```

Operational services surround this stack:

```text
                  PostgreSQL
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
     Backup       Monitoring      Logging
        │             │             │
        └─────────────┼─────────────┘
                      ▼
              Operational Response
```

A database incident may therefore originate outside PostgreSQL itself.

Examples include storage latency, filesystem exhaustion, DNS failure, firewall changes, connection exhaustion, incorrect authentication rules, expired certificates, OS resource limits, and application connection storms.

Production planning must consider the complete stack.

# 2.1.4 PostgreSQL Software Is Not a Database Cluster

This distinction is fundamental.

Installing PostgreSQL provides programs such as `postgres`, `psql`, `initdb`, `pg_ctl`, `pg_dump`, `pg_restore`, `pg_basebackup`, and `pg_config`.

Installing these programs does not automatically mean that the desired PostgreSQL database cluster exists.

Conceptually:

```text
PostgreSQL software
        │
        │ initdb
        ▼
PostgreSQL database cluster
        │
        ▼
PGDATA
```

`initdb` creates a new PostgreSQL database cluster. The cluster contains the persistent state required by a PostgreSQL server instance.

This distinction matters during installation, initialization, patching, backup, recovery, migration, troubleshooting, and major-version upgrades.

Part 2.3 will install PostgreSQL software. Part 2.5 will deliberately initialize the database cluster. We will not blur those operations together.

# 2.1.5 PostgreSQL Version Strategy

The target for this tutorial is **PostgreSQL 18**.

A production build should record the major version, minor-release maintenance policy, application compatibility, driver compatibility, extension compatibility, backup-tool compatibility, monitoring compatibility, and upgrade strategy.

Version selection is an application and operational compatibility decision, not simply a decision to install whichever package the OS provides.

# 2.1.6 Package Installation vs Source Installation

Two important installation models are package-managed installation and source-code installation.

Package-based deployments commonly integrate with dependency management, software inventory, security patching, operating-system conventions, automation, and service management. Linux ecosystems commonly use package managers such as `dnf` and `apt`.

The exact repository, package names, binary locations, configuration paths, initialization behavior, and systemd units depend on the Linux distribution and packaging source. We will inspect rather than assume those details. For the integrated Part 2 production-style build, package installation is the preferred baseline.

PostgreSQL can also be compiled from source. PostgreSQL 18 supports documented source-build workflows using both **Autoconf / Make** and **Meson**.

Source builds are useful for PostgreSQL development, specialized build options, debugging, controlled test environments, custom installation prefixes, and environments requiring deliberate compile-time choices. But source installation also transfers more lifecycle responsibility to the operator, including tracking security releases, rebuilding PostgreSQL, managing build dependencies, controlling compiler/build options, validating patches, maintaining the build pipeline, and performing upgrades.

Part 2.4 will examine source installation in an isolated lab.

# 2.1.7 Define the Linux Platform

Document the target platform before installation: operating system, distribution, release, architecture, and environment type.

Installation procedures should not be assumed to be identical across RHEL-family systems, Ubuntu, Debian, Amazon Linux, and other supported Linux platforms. Differences may include package repositories, package names, binary locations, cluster initialization, service-unit names, SELinux/AppArmor behavior, firewall tooling, and filesystem conventions.

# 2.1.8 PostgreSQL Operating-System Account

PostgreSQL server processes must run under an appropriate unprivileged operating-system account. A conventional account name is `postgres`; the literal name is a convention, not an architectural requirement.

`initdb` must not be run as `root`. The database-cluster files must be owned by the operating-system account that owns the PostgreSQL server process.

For this tutorial, the PostgreSQL OS account is `postgres`.

# 2.1.9 Network Port

The conventional PostgreSQL TCP port is `5432`, which is our lab baseline.

Changing the port is not a substitute for security. Network protection must instead come from layered controls: routing → firewall/security controls → `listen_addresses` → `pg_hba.conf` → TLS where required → authentication → database authorization.

# 2.1.10 Design PGDATA Before initdb

`PGDATA` identifies the PostgreSQL database-cluster data directory. The location should be intentional before cluster initialization.

For this tutorial, we will use `/pgdata/18/main`. This is a **tutorial and organizational convention**; PostgreSQL does not require production installations to use this path.

Whatever path an organization selects should be intentional, documented, correctly owned, correctly permissioned, backed by suitable storage, monitored for capacity, and included in backup and recovery planning.

# 2.1.11 Separate Software and Persistent State Conceptually

PostgreSQL software and the PostgreSQL database cluster are different lifecycle objects. Software may be patched, upgraded, replaced, or reinstalled. Persistent database state must be protected, backed up, monitored, recoverable, and migrated deliberately.

# 2.1.12 Storage Architecture

Before deployment, identify capacity, IOPS, throughput, latency, durability, filesystem, growth rate, backup behavior, snapshot behavior, and failure characteristics.

Storage requirements should be derived from workload characteristics rather than database size alone. Capacity and performance are separate dimensions.

# 2.1.13 WAL Storage Strategy

PostgreSQL Write-Ahead Logging is fundamental to durability and recovery. Within the cluster, WAL normally appears under `PGDATA/pg_wal`.

Do not move WAL to separate storage merely because an old tuning guide recommends it. Separate WAL storage creates another infrastructure and failure dependency that must itself be durable, monitored, sized, backed by appropriate performance, and included in recovery planning.

Our initial Part 2 decision is to use the standard cluster layout initially and separate WAL storage only when workload, storage architecture, or operational requirements provide a justified reason.

# 2.1.14 Storage Capacity Planning

Required storage is not simply the current database size. Potential consumers include table data, indexes, WAL, temporary files, database growth, maintenance operations, reindexing, operational headroom, backup staging where applicable, and logs where applicable.

Production storage must preserve enough operational headroom for expected growth and database activity.

# 2.1.15 CPU Planning

CPU requirements depend on query concurrency, query complexity, parallel execution, background workers, autovacuum, maintenance activity, encryption, and application connection behavior. Record an initial assumption and validate capacity later with representative workload testing.

# 2.1.16 Memory Planning

Avoid universal percentage rules. Memory consumption includes Linux, filesystem cache, PostgreSQL shared memory, backend/session memory, query-operation memory, maintenance memory, autovacuum workers, and other processes.

Important settings later include `shared_buffers`, `work_mem`, `maintenance_work_mem`, `autovacuum_work_mem`, `temp_buffers`, and `max_connections`. Memory planning therefore requires parameter sizing, concurrency analysis, OS requirements, and workload behavior.

# 2.1.17 Connection Planning

Estimate application instances, workers per instance, connections per worker, administrative sessions, monitoring sessions, maintenance sessions, and reconnect/failover behavior. Do not solve uncertain capacity simply by configuring an extremely large `max_connections`. Connection pooling may need to become part of the architecture.

# 2.1.18 Network Exposure

PostgreSQL 18 defaults `listen_addresses` to local loopback behavior rather than exposing the server broadly. Remote connectivity should therefore be enabled intentionally.

The connection path should be: authorized client/network → network ACL/firewall → selected PostgreSQL interface → `listen_addresses` → `pg_hba.conf` → TLS where required → authentication → database privileges.

Do not begin a production design with `listen_addresses = '*'` and broad network access merely because it makes initial connectivity easier.

# 2.1.19 Authentication Baseline

For new password-based PostgreSQL 18 configurations, our baseline is `SCRAM-SHA-256`. MD5-encrypted password support is deprecated.

Authentication is only one layer. Remote production connectivity should consider network restriction, TLS where required, server identity verification, authentication, and database authorization. SCRAM authentication should not be mistaken for complete transport-security architecture.

# 2.1.20 Logging Requirements

Logging is part of the architecture rather than a post-deployment convenience. Operators may need evidence for startup failures, authentication failures, connection activity, slow statements, lock waits, checkpoint behavior, temporary-file activity, autovacuum, errors, and fatal events.

The architecture should define where logs are written, who can read them, how they are rotated, how long they are retained, whether they are shipped centrally, whether SQL text could contain sensitive information, and who owns log monitoring.

# 2.1.21 Backup Requirements

A database should not become important before its recovery requirements are defined. Record backup method, destination, retention, encryption requirements, RPO, RTO, restore procedure, restore-testing frequency, ownership, and monitoring.

**RPO — Recovery Point Objective:** acceptable amount of data loss measured in time or recoverable state.

**RTO — Recovery Time Objective:** acceptable duration required to restore service.

# 2.1.22 Monitoring Requirements

Plan visibility for CPU, memory, filesystem utilization, storage latency, IOPS, throughput, connections, database growth, WAL generation, locks, long transactions, query latency, autovacuum, temporary files, availability, and backup status.

The server must be designed so that its health can be observed from the beginning.

# 2.1.23 Time Synchronization

Correct host time matters for logging, incident timelines, monitoring, authentication systems, distributed applications, backup operations, and cross-system event correlation. Time synchronization is required and the timezone standard must be documented.

# 2.1.24 DNS and Host Identity

Record the server's intended hostname, FQDN, and role. Applications should use an intentional connectivity architecture rather than undocumented IP addresses.

# 2.1.25 Environment Separation

Define development, test, staging, and production explicitly. Consider separation for credentials, networking, storage, backup, monitoring, configuration, access, and data. Production credentials and datasets should not be casually reused in tutorial or test environments.

# 2.1.26 Operational Ownership

Document ownership for PostgreSQL configuration, OS configuration, patching, backup, restore testing, monitoring, security, capacity, and upgrades. Configuration changes should occur through intentional and traceable operational processes.

# 2.1.28 Hands-On Lab — Design the PostgreSQL Server

## Lab classification

`[TUTORIAL-ACCEPTANCE — SAFE-READ]`

### Objective

Inspect the Linux host and produce the architecture specification for the PostgreSQL server that will be built throughout Part 2.

### Safety boundary

This lab does **not** install PostgreSQL, initialize a PostgreSQL cluster, modify PostgreSQL configuration, modify authentication, modify networking, modify firewall rules, create filesystems, mount storage, change ownership or permissions, or start/stop/reload/restart PostgreSQL.

Commands such as `sudo`, `dnf install`, `apt install`, `initdb`, `mkfs`, `mount`, `chown`, `chmod`, `systemctl restart`, `systemctl enable`, `firewall-cmd`, and `ufw` intentionally do **not** belong in this lab.

The only expected write is creation of the learner's local planning document.

# 2.1.29 Inspect Host Identity

```bash
hostname
hostnamectl
cat /etc/os-release
uname -m
uname -r
```

Record hostname, Linux distribution/release, CPU architecture, and kernel.

# 2.1.30 Inspect CPU

```bash
nproc
lscpu
```

Record logical CPUs, architecture, and virtualization. This is inventory; do not tune the host.

# 2.1.31 Inspect Memory

```bash
free -h
grep -E 'MemTotal|MemAvailable|SwapTotal|SwapFree' /proc/meminfo
```

Record total RAM, available RAM, and swap. Do not derive final PostgreSQL memory settings from RAM alone.

# 2.1.32 Inspect Storage

```bash
lsblk
df -hT
findmnt
```

Record OS filesystem, candidate PostgreSQL filesystem, filesystem type, available capacity, and storage technology if known. Do not create, format, resize, or mount storage.

# 2.1.33 Inspect Network Identity

```bash
hostname -f
ip addr
ip route
```

Record hostname, FQDN, primary address, network/subnet, and default route. Do not change networking or firewall configuration.

# 2.1.34 Inspect Time Configuration

```bash
timedatectl
```

Record timezone, clock synchronization, and time synchronization service.

# 2.1.36 Identify Unresolved Decisions

```bash
grep -n 'TBD' postgresql-server-build-spec.txt
```

Unresolved values expose requirements that still need owners or evidence. Do not invent values merely to make the document look complete.

# 2.1.37 Classify Unresolved Requirements

Use classifications such as `KNOWN`, `REQUIRES VALIDATION`, `REQUIRES APPLICATION INPUT`, `REQUIRES SECURITY INPUT`, `REQUIRES INFRASTRUCTURE INPUT`, `REQUIRES BUSINESS INPUT`, and `REQUIRES CAPACITY TESTING`.

Not every database architecture decision belongs exclusively to the database administrator.

# 2.1.38 Architecture Record

The resulting design should be explainable as application → authorized network → firewall/ACL → PostgreSQL host → Linux/PostgreSQL 18/systemd/package service integration/OS account/TCP 5432/PGDATA, surrounded by backup, monitoring, logging, time synchronization, capacity management, and restore testing.

# 2.1.39 Acceptance Checklist

The planning lab passes when the learner can answer or explicitly classify platform, installation, storage, resource, network, security, and operational requirements. Unknown values may remain. Undocumented unknowns may not.

# 2.1.40 Production Anti-Patterns

Avoid installing whatever PostgreSQL version the OS happens to provide, putting PGDATA on the root filesystem simply because space is available, setting `max_connections` extremely high just in case, listening on every interface and securing it later, broad `pg_hba.conf` rules, treating SCRAM as complete network security, separating WAL based on old folklore, universal memory percentage rules, postponing monitoring or backup, determining RPO/RTO during an outage, or assuming every Linux distribution uses the same PostgreSQL systemd service name.

# 2.1.41 Production Readiness Gate

Before proceeding to Linux host preparation, the PostgreSQL major version, Linux platform, installation method, repository/package strategy, service account, port, PGDATA design, storage architecture, WAL strategy, CPU/memory capacity, connection assumptions, network boundaries, authentication baseline, TLS requirement, logging/monitoring/backup requirements, RPO/RTO ownership, time synchronization, configuration ownership, and patch ownership must be selected, recorded, or explicitly classified.

# 2.1.42 What We Built

We deliberately did **not install PostgreSQL**. Instead, we produced a PostgreSQL Server Build Specification that captures the Linux platform, installation method, service account, network baseline, PGDATA design, storage/WAL strategy, capacity and connection assumptions, authentication/TLS baseline, logging, monitoring, backup requirements, and operational ownership.

# 2.1.43 Operational Takeaway

Production PostgreSQL installation begins with architecture and requirements, not with a package-manager command.

Answering where data lives, who can connect, how much capacity is required, how access is protected, how failures are recovered, how the server is observed and patched, and who owns each operational responsibility creates a PostgreSQL environment that is easier to operate, secure, monitor, troubleshoot, recover, scale, patch, and upgrade.
