## 2.1.1 Introduction

A reliable PostgreSQL deployment begins before PostgreSQL is installed.

Installing packages is usually one of the simplest parts of building a database server. The harder questions are architectural:

- Which PostgreSQL major version will be deployed?
- Which Linux platform will host it?
- How will PostgreSQL be installed and patched?
- Where will persistent database data live?
- What CPU, memory, storage, and connection capacity is required?
- Which networks may reach PostgreSQL?
- How will authentication and transport security be handled?
- How will the server be started and stopped?
- How will logs and metrics be collected?
- How will the database be backed up and restored?
- What are the required RPO and RTO?
- Who owns configuration, patching, monitoring, backup, and capacity?

A disposable development system can sometimes tolerate decisions being made after installation.

A production system should not.

The objective of this section is therefore not to install PostgreSQL.

The objective is to create an intentional **PostgreSQL Server Build Specification** that will guide the remainder of Part 2.

In this tutorial, **build** means designing and deploying the complete PostgreSQL server. It does not imply that PostgreSQL must be compiled from source.

## 2.1.2 Learning Objectives

By the end of this section, you should be able to:

1. distinguish PostgreSQL software installation from database-cluster initialization;
2. define a PostgreSQL version strategy;
3. distinguish package-based installation from source compilation;
4. identify Linux-platform dependencies;
5. define the PostgreSQL operating-system service account;
6. define the initial network and port architecture;
7. design the PostgreSQL data-directory strategy;
8. establish an initial WAL-storage strategy;
9. identify CPU, memory, storage, and connection requirements;
10. define security boundaries before enabling remote access;
11. identify logging, monitoring, backup, RPO, and RTO requirements;
12. identify operational ownership;
13. document unresolved architecture decisions rather than hiding them behind arbitrary defaults;
14. produce a reusable PostgreSQL Server Build Specification.

## 2.1.3 Think in Layers

A PostgreSQL deployment is more than a database process.

A simplified production stack is:

```text
Applications / Users
        │
        ▼
DNS / Service Discovery
        │
        ▼
Network / Firewall
        │
        ▼
PostgreSQL Network Listener
        │
        ▼
Client Authentication
        │
        ▼
Database Authorization
        │
        ▼
PostgreSQL Server Processes
        │
        ▼
PostgreSQL Configuration
        │
        ▼
Database Cluster / PGDATA
        │
        ▼
Filesystem / Storage
        │
        ▼
Linux Operating System
        │
        ▼
Compute Infrastructure
```

Operational services surround this stack:

```text
                  PostgreSQL
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
     Backup       Monitoring      Logging
        │             │             │
        └─────────────┼─────────────┘
                      ▼
              Operational Response
```

A database incident may therefore originate outside PostgreSQL itself.

Examples include:

- storage latency;
- filesystem exhaustion;
- DNS failure;
- firewall changes;
- connection exhaustion;
- incorrect authentication rules;
- expired certificates;
- OS resource limits;
- application connection storms.

Production planning must consider the complete stack.

## 2.1.4 PostgreSQL Software Is Not a Database Cluster

This distinction is fundamental.

Installing PostgreSQL provides programs such as:

```text
postgres
psql
initdb
pg_ctl
pg_dump
pg_restore
pg_basebackup
pg_config
```

Installing these programs does not automatically mean that the desired PostgreSQL database cluster exists.

Conceptually:

```text
PostgreSQL software
        │
        │ initdb
        ▼
PostgreSQL database cluster
        │
        ▼
PGDATA
```

`initdb` creates a new PostgreSQL database cluster.

The cluster contains the persistent state required by a PostgreSQL server instance.

This distinction matters during:

- installation;
- initialization;
- patching;
- backup;
- recovery;
- migration;
- troubleshooting;
- major-version upgrades.

Part 2.3 will install PostgreSQL software.

Part 2.5 will deliberately initialize the database cluster.

We will not blur those operations together.

## 2.1.6 Package Installation vs Source Installation

Two important installation models are:

```text
Package-managed installation

Source-code installation
```

### Package-managed installation

Package-based deployments commonly integrate with:

- dependency management;
- software inventory;
- security patching;
- operating-system conventions;
- automation;
- service management.

Linux ecosystems commonly use package managers such as:

```text
dnf
apt
```

The exact repository, package names, binary locations, configuration paths, initialization behavior, and systemd units depend on the Linux distribution and packaging source.

We will inspect rather than assume those details.

For the integrated Part 2 production-style build, package installation is the preferred baseline.

### Source installation

PostgreSQL can also be compiled from source.

PostgreSQL 18 supports documented source-build workflows using both:

```text
Autoconf / Make

Meson
```

Source builds are useful for scenarios such as PostgreSQL development, specialized build options, debugging, controlled test environments, custom installation prefixes, and environments requiring deliberate compile-time choices.

But source installation also transfers more lifecycle responsibility to the operator.

Before choosing it for production, answer:

```text
Who tracks PostgreSQL security releases?
Who rebuilds PostgreSQL?
Who manages build dependencies?
Who controls compiler/build options?
Who validates patches?
Who maintains the build pipeline?
Who performs upgrades?
```

Part 2.4 will examine source installation in an isolated lab.

## 2.1.7 Define the Linux Platform

Document the target platform before installation.

Example:

```text
Operating system: Linux
Distribution: <distribution>
Release: <release>
Architecture: x86_64 / arm64
Environment: VM / physical / cloud
```

Installation procedures should not be assumed to be identical across RHEL-family systems, Ubuntu, Debian, Amazon Linux, and other supported Linux platforms.

Differences may include package repositories, package names, binary locations, cluster initialization, service-unit names, SELinux/AppArmor behavior, firewall tooling, and filesystem conventions.

The tutorial will explicitly discover these differences where they matter.

## 2.1.8 PostgreSQL Operating-System Account

PostgreSQL server processes must run under an appropriate unprivileged operating-system account.

A conventional account name is:

```text
postgres
```

The literal name `postgres` is a convention, not an architectural requirement.

The important relationship is:

```text
Privileged OS administrator
        │
        │ host/package administration
        ▼
Dedicated PostgreSQL OS account
        │
        │ owns/runs PostgreSQL
        ▼
PostgreSQL server
```

`initdb` must not be run as `root`.

The database-cluster files must be owned by the operating-system account that owns the PostgreSQL server process.

For this tutorial:

```text
PostgreSQL OS account:
postgres
```

## 2.1.9 Network Port

The conventional PostgreSQL TCP port is:

```text
5432
```

Our lab baseline will use:

```text
Port:
5432
```

Changing the port is not a substitute for security.

Network protection must instead come from layered controls such as:

```text
routing
    ↓
firewall / security controls
    ↓
listen_addresses
    ↓
pg_hba.conf
    ↓
TLS where required
    ↓
authentication
    ↓
database authorization
```

## 2.1.10 Design PGDATA Before `initdb`

`PGDATA` identifies the PostgreSQL database-cluster data directory.

The location should be intentional before cluster initialization.

For this tutorial, we will use:

```text
/pgdata/18/main
```

Conceptually:

```text
/pgdata
└── 18
    └── main
```

This is a **tutorial and organizational convention**.

PostgreSQL does not require production installations to use `/pgdata/18/main`.

The convention makes the purpose, major version, and cluster identity obvious:

```text
/pgdata → purpose
18      → PostgreSQL major version
main    → cluster identity
```

Whatever path an organization selects should be intentional, documented, correctly owned, correctly permissioned, backed by suitable storage, monitored for capacity, and included in backup and recovery planning.

## 2.1.11 Separate Software and Persistent State Conceptually

Think of PostgreSQL as two lifecycle objects:

```text
PostgreSQL software
        │
        └── executables / libraries

PostgreSQL database cluster
        │
        └── persistent database state
```

Their exact paths depend on the installation method and Linux packaging.

The important architectural principle is that software and persistent database state have different lifecycles.

Software may be patched, upgraded, replaced, or reinstalled.

Persistent database state must be protected, backed up, monitored, recoverable, and migrated deliberately.

This separation becomes particularly important during major-version upgrades.

## 2.1.12 Storage Architecture

PostgreSQL depends heavily on storage behavior.

Before deployment, identify:

```text
capacity
IOPS
throughput
latency
durability
filesystem
growth rate
backup behavior
snapshot behavior
failure characteristics
```

A simple architecture might be:

```text
Linux host
│
├── OS / software storage
│
└── PostgreSQL storage
    │
    └── /pgdata
        └── 18
            └── main
```

The underlying implementation may use local SSD, cloud block storage, SAN, or other durable storage suitable for the platform and workload.

Storage requirements should be derived from workload characteristics rather than database size alone.

Capacity and performance are separate dimensions.

## 2.1.13 WAL Storage Strategy

PostgreSQL Write-Ahead Logging is fundamental to durability and recovery.

Within the cluster, WAL normally appears under:

```text
PGDATA/pg_wal
```

The architecture should explicitly decide whether the normal placement is appropriate.

Do not move WAL to separate storage merely because an old tuning guide recommends it.

Separate WAL storage creates another infrastructure and failure dependency that must itself be durable, monitored, sized, backed by appropriate performance, and included in recovery planning.

The decision should consider write workload, storage latency, IOPS, throughput, failure characteristics, recovery requirements, and operational complexity.

Our initial Part 2 decision is:

```text
WAL strategy:
Use the standard cluster layout initially.

Separate WAL storage:
Not required unless workload, storage architecture,
or operational requirements provide a justified reason.
```

## 2.1.14 Storage Capacity Planning

Required storage is not simply the current database size.

Potential consumers include table data, indexes, WAL, temporary files, database growth, maintenance operations, reindexing, operational headroom, backup staging where applicable, and logs where applicable.

Therefore:

```text
Required filesystem capacity
        ≠
Current database size
```

Production storage must preserve enough operational headroom for expected growth and database activity.

Running the PostgreSQL filesystem close to exhaustion is dangerous because normal operation can continue creating WAL, table pages, index pages, temporary files, and maintenance-related files.

Part 2.6 will develop this into a detailed storage methodology.

## 2.1.15 CPU Planning

CPU requirements depend on workload behavior.

Consider query concurrency, query complexity, parallel execution, background workers, autovacuum, maintenance activity, encryption, and application connection behavior.

At this stage, record an initial assumption rather than pretending the first server size is permanent.

Example:

```text
Initial CPU:
4 vCPU

Workload assumption:
Moderate transactional lab workload

Capacity validation:
Required after representative workload testing
```

## 2.1.16 Memory Planning

Avoid starting with a universal rule such as allocating a fixed percentage of RAM to PostgreSQL.

Memory consumption comes from multiple areas:

```text
Physical RAM
│
├── Linux operating system
├── Filesystem cache
├── PostgreSQL shared memory
├── Backend/session memory
├── Query-operation memory
├── Maintenance memory
├── Autovacuum workers
└── Other processes
```

Important PostgreSQL settings later include `shared_buffers`, `work_mem`, `maintenance_work_mem`, `autovacuum_work_mem`, `temp_buffers`, and `max_connections`.

Some memory is shared. Other memory may be consumed concurrently by multiple sessions or operations.

Therefore memory planning combines parameter sizing, concurrency analysis, OS requirements, and workload behavior.

Part 2.8 will build the actual baseline.

## 2.1.17 Connection Planning

Connections consume resources.

Estimate application instances, workers per instance, connections per worker, administrative sessions, monitoring sessions, maintenance sessions, and reconnect/failover behavior.

For example:

```text
4 application instances
×
10 connections
=
40 application connections
```

Then account separately for administration, monitoring, maintenance, and operational reserve.

Do not solve uncertain capacity simply by configuring an extremely large `max_connections`.

Connection pooling may need to become part of the architecture.

## 2.1.18 Network Exposure

PostgreSQL 18 defaults `listen_addresses` to local loopback behavior rather than exposing the server broadly.

Remote connectivity should therefore be enabled intentionally.

A production connection path should conceptually be:

```text
Authorized client/network
        │
        ▼
Network ACL / Firewall
        │
        ▼
Selected PostgreSQL interface
        │
        ▼
listen_addresses
        │
        ▼
pg_hba.conf
        │
        ▼
TLS where required
        │
        ▼
Authentication
        │
        ▼
Database privileges
```

Do not begin a production design with `listen_addresses = '*'` and broad network access merely because it makes initial connectivity easier.

The allowed network path should be designed first.

## 2.1.19 Authentication Baseline

For new password-based PostgreSQL 18 configurations, our baseline is:

```text
SCRAM-SHA-256
```

PostgreSQL 18 uses SCRAM-SHA-256 as the normal modern password-encryption baseline, while MD5-encrypted password support is deprecated.

Authentication is only one layer.

For remote production connectivity, consider network restriction + TLS where required + server identity verification + authentication + database authorization.

SCRAM authentication should not be mistaken for complete transport-security architecture.

Part 2.10 will implement these controls carefully.

## 2.1.20 Logging Requirements

Logging is part of the architecture rather than a post-deployment convenience.

Operators may need evidence for startup failures, authentication failures, connection activity, slow statements, lock waits, checkpoint behavior, temporary-file activity, autovacuum, errors, and fatal events.

The architecture should answer where logs are written, who can read them, how they are rotated, how long they are retained, whether they are shipped centrally, whether SQL text could contain sensitive information, and who owns log monitoring.

Part 2.12 will implement the production logging baseline.

## 2.1.21 Backup Requirements

A database should not become important before its recovery requirements are defined.

Record backup method, backup destination, retention, encryption requirements, RPO, RTO, restore procedure, restore-testing frequency, ownership, and monitoring.

### RPO

**Recovery Point Objective** — the acceptable amount of data loss measured in time or recoverable state.

### RTO

**Recovery Time Objective** — the acceptable duration required to restore service.

The detailed backup implementation appears later in this tutorial series. The requirement belongs in the architecture from day one.

## 2.1.22 Monitoring Requirements

A production database should not become observable only after its first incident.

Plan visibility for CPU, memory, filesystem utilization, storage latency, IOPS, throughput, connections, database growth, WAL generation, locks, long transactions, query latency, autovacuum, temporary files, availability, and backup status.

Potential monitoring systems include Prometheus, Grafana, cloud-native monitoring, and enterprise observability platforms.

Part 13 explores PostgreSQL monitoring in depth.

The Part 2 requirement is simpler: the server must be designed so that its health can be observed from the beginning.

## 2.1.23 Time Synchronization

Correct host time matters for logging, incident timelines, monitoring, authentication systems, distributed applications, backup operations, and cross-system event correlation.

The build specification must therefore include:

```text
Time synchronization:
Required

Timezone standard:
Documented
```

Part 2.2 will validate this on the Linux host.

## 2.1.24 DNS and Host Identity

Record the server's intended identity.

Example:

```text
Hostname:
pg-prod-01

FQDN:
pg-prod-01.example.internal

Role:
PostgreSQL primary
```

Applications should use an intentional connectivity architecture rather than undocumented IP addresses.

Future high-availability architectures may introduce a DNS endpoint, VIP, load balancer, proxy, or cluster service.

## 2.1.25 Environment Separation

Define environments explicitly, for example development, test, staging, and production.

Consider separation for credentials, networking, storage, backup, monitoring, configuration, access, and data.

Production credentials and production datasets should not be casually reused in tutorial or test environments.

## 2.1.26 Operational Ownership

Production configuration requires ownership.

Possible owners include DBA, DBRE, SRE, Platform Engineering, and Database Platform Team.

Document ownership for PostgreSQL configuration, OS configuration, patching, backup, restore testing, monitoring, security, capacity, and upgrades.

Settings such as `shared_buffers`, `max_connections`, `wal_level`, `listen_addresses`, logging, and authentication should change through intentional and traceable operational processes.

## 2.1.40 Production Anti-Patterns

Avoid:

```text
Install whatever PostgreSQL version the OS happens to provide.
```

```text
Put PGDATA on the root filesystem because space is available today.
```

```text
Set max_connections extremely high just in case.
```

```text
Listen on every interface and secure it later.
```

```text
Create broad pg_hba.conf rules temporarily.
```

```text
Treat SCRAM authentication as complete network security.
```

```text
Move WAL to separate storage because an old tuning guide recommends it.
```

```text
Configure PostgreSQL memory using one universal percentage.
```

```text
Configure monitoring after production go-live.
```

```text
Design backup after the database contains important data.
```

```text
Determine RPO and RTO during an outage.
```

```text
Assume every Linux distribution uses the same PostgreSQL systemd service name.
```

These approaches defer important architecture decisions until the environment becomes harder to change.

## 2.1.43 Operational Takeaway

Production PostgreSQL installation begins with architecture and requirements, not with a package-manager command.

The important questions are:

```text
Where will the data live?
Who can connect?
How much capacity is required?
How will access be protected?
How will failures be recovered?
How will the server be observed?
How will it be patched?
Who owns each operational responsibility?
```

Answering those questions before deployment creates a PostgreSQL environment that is easier to operate, secure, monitor, troubleshoot, recover, scale, patch, and upgrade.
