# Part 2.8 --- Memory and Resource Configuration

**Status:** Revised Final / Canonical Edition\
**Target:** PostgreSQL 18\
**Audience:** PostgreSQL administrators, SREs, DBREs, platform
engineers, and developers operating PostgreSQL.

------------------------------------------------------------------------

## 2.8.1 Objectives

PostgreSQL memory tuning is a capacity-planning problem, not a
collection of magic parameter values. By the end of this tutorial, you
should be able to:

-   explain PostgreSQL shared, session, query, and maintenance memory;
-   inspect the major memory and worker settings safely;
-   distinguish allocated memory from planner estimates;
-   explain why `work_mem × max_connections` is not a valid upper memory
    bound;
-   account for hash operations, parallelism, autovacuum, and
    temporary-table buffers;
-   identify settings that require restart versus settings suitable for
    session-scoped testing;
-   inspect huge-page configuration without changing the operating
    system;
-   recognize host, container, Kubernetes, and managed-service resource
    boundaries;
-   compare an intentionally constrained sort with a larger
    session-scoped `work_mem`;
-   build a production memory-change proposal with evidence and rollback
    criteria.

> **Production safety principle:** observe first, test at the narrowest
> practical scope, measure the result, and use an approved change
> process before modifying global production memory settings.

------------------------------------------------------------------------

## 2.8.2 Memory Architecture

PostgreSQL does not use one monolithic memory pool.

``` text
Physical / Effective Memory Limit
|
+-- Operating system and filesystem cache
|
+-- PostgreSQL shared memory
|   +-- shared_buffers
|   +-- WAL-related shared memory
|   `-- other shared structures
|
+-- PostgreSQL backend processes
|   +-- session/process overhead
|   +-- query operations
|   |   +-- sorts
|   |   +-- hashes
|   |   `-- aggregates
|   `-- temporary-table buffers
|
+-- maintenance and autovacuum workers
|
+-- parallel/background workers
|
+-- extensions, agents, sidecars, and other processes
|
`-- operational safety margin
```

For containers and Kubernetes, the effective memory limit may be lower
than the physical RAM of the underlying host. Capacity planning must use
the memory actually available to PostgreSQL.

------------------------------------------------------------------------

## 2.8.3 Establish the Resource Boundary

### Self-managed Linux

Safe inspection:

``` bash
free -h
cat /proc/meminfo
```

Useful fields include `MemTotal`, `MemAvailable`, `Cached`, `SwapTotal`,
`SwapFree`, and huge-page fields.

Do not interpret Linux's `free` column as the only usable memory. The
kernel intentionally uses memory for filesystem caching.

### Containers

On cgroup v2 systems, inspect the effective limit where available:

``` bash
cat /sys/fs/cgroup/memory.max
cat /sys/fs/cgroup/memory.current
```

Older cgroup-v1 systems use different paths. Do not assume the host's
physical RAM is available to the PostgreSQL process.

### Kubernetes

Inspect the pod specification:

``` bash
kubectl get pod <postgres-pod> -o yaml
```

Review container memory requests and limits. Do not change them as part
of this tutorial.

### Managed PostgreSQL

Amazon RDS/Aurora PostgreSQL, Azure Database for PostgreSQL, Cloud SQL
for PostgreSQL, and other managed services expose different
configuration and operating-system controls. Commands involving `/proc`,
`sysctl`, `journalctl`, or direct PostgreSQL server startup are
primarily for self-managed systems. Follow the provider's
parameter/configuration mechanisms and restart semantics.

## 2.8.4 Safe Configuration Inventory

The following query is read-only.

``` sql
-- [TUTORIAL-ACCEPTANCE — SAFE-READ]
SELECT
    name,
    setting,
    unit,
    context,
    source
FROM pg_settings
WHERE name IN (
    'shared_buffers',
    'work_mem',
    'maintenance_work_mem',
    'autovacuum_work_mem',
    'temp_buffers',
    'effective_cache_size',
    'wal_buffers',
    'hash_mem_multiplier',
    'vacuum_buffer_usage_limit',
    'huge_pages',
    'huge_page_size',
    'huge_pages_status',
    'max_connections',
    'max_worker_processes',
    'max_parallel_workers',
    'max_parallel_workers_per_gather'
)
ORDER BY name;
```

`pg_settings.context` is valuable operationally because it indicates how
a parameter can take effect. Always verify the actual server rather than
relying on memory.

## 2.8.5 `shared_buffers`

`shared_buffers` controls PostgreSQL's primary shared buffer cache.

``` sql
SHOW shared_buffers;
```

For a dedicated database server, PostgreSQL documentation describes
approximately 25% of system memory as a reasonable starting point, while
also noting that substantially larger allocations are not automatically
better because PostgreSQL relies on the operating-system cache.

For a hypothetical dedicated 32 GiB host:

``` text
32 GiB × 25% ≈ 8 GiB
```

This is a starting point for testing, not a universal production
prescription.

### Production considerations

-   `shared_buffers` is a server-start setting; changing it requires
    restart.
-   Preserve memory for the operating system, backend processes, query
    memory, maintenance, workers, extensions, and other services.
-   Larger `shared_buffers` can increase checkpoint-related WAL
    pressure; evaluate related WAL/checkpoint capacity, including
    `max_wal_size`.
-   Never change it in production solely because a generic tuning
    formula recommends a value.

------------------------------------------------------------------------

## 2.8.6 `work_mem`

`work_mem` is the base memory limit used by eligible query operations
before they may spill to temporary disk files.

``` sql
SHOW work_mem;
```

Examples include sorts and hash-based operations. The important
production rule is:

``` text
work_mem is not allocated once per connection.
```

A single execution plan can contain multiple memory-consuming nodes,
many sessions can execute concurrently, and parallel execution can add
workers.

A useful risk model is:

``` text
aggregate query-memory risk
≈ active sessions
× concurrent memory-consuming plan nodes
× applicable per-operation memory
× parallel execution effects
```

This is a capacity-planning model, not an exact PostgreSQL upper-bound
equation.

### Session-scoped testing

Prefer narrow experiments:

``` sql
SET work_mem = '64MB';
SHOW work_mem;
RESET work_mem;
```

Do not use `ALTER SYSTEM` in this lab.

------------------------------------------------------------------------

## 2.8.7 `hash_mem_multiplier`

Hash-based operations can use a memory limit derived from:

``` text
work_mem × hash_mem_multiplier
```

Inspect:

``` sql
SHOW hash_mem_multiplier;
```

PostgreSQL 18 documents a default of `2.0`. For example, with:

``` text
work_mem = 32 MB
hash_mem_multiplier = 2.0
```

a qualifying hash operation has a limit derived from approximately 64
MB.

This parameter must be included when evaluating memory pressure from
hash joins and hash aggregates.

------------------------------------------------------------------------

## 2.8.8 `maintenance_work_mem`

Inspect:

``` sql
SHOW maintenance_work_mem;
```

This setting applies to maintenance operations such as `VACUUM`,
`CREATE INDEX`, and some `ALTER TABLE` operations.

It can often be configured higher than ordinary `work_mem`, but it is
still concurrency-sensitive. Multiple sessions can perform maintenance
simultaneously.

------------------------------------------------------------------------

## 2.8.9 `autovacuum_work_mem`

Inspect:

``` sql
SHOW autovacuum_work_mem;
```

When the value is `-1`, autovacuum uses `maintenance_work_mem`.

Do not interpret that as a single maintenance-memory allocation.
Multiple autovacuum workers can run concurrently, so memory planning
must account for worker concurrency.

------------------------------------------------------------------------

## 2.8.10 `vacuum_buffer_usage_limit`

PostgreSQL 18 exposes:

``` sql
SHOW vacuum_buffer_usage_limit;
```

This controls the Buffer Access Strategy size used by `VACUUM` and
`ANALYZE`. It is separate from `maintenance_work_mem`. Treat it as part
of maintenance-resource planning; detailed vacuum tuning belongs in the
maintenance tutorials.

------------------------------------------------------------------------

## 2.8.11 `temp_buffers`

`temp_buffers` controls the maximum amount of memory used for
temporary-table buffers within each session.

``` sql
SHOW temp_buffers;
```

It is not general sort memory and is not a substitute for `work_mem`.

A session can change `temp_buffers` only before its first access to
temporary tables. For an experiment:

``` sql
SET temp_buffers = '32MB';

CREATE TEMP TABLE temp_memory_demo AS
SELECT generate_series(1, 10000) AS id;
```

Do this only in a lab session.

------------------------------------------------------------------------

## 2.8.12 `effective_cache_size`

Inspect:

``` sql
SHOW effective_cache_size;
```

This parameter is frequently misunderstood.

``` text
effective_cache_size:
  DOES NOT allocate RAM
  DOES NOT reserve RAM
  DOES influence planner cost estimates
```

It represents the planner's estimate of cache likely to be available to
a query, considering PostgreSQL shared buffers and relevant
operating-system filesystem cache while also accounting for competing
workload.

------------------------------------------------------------------------

## 2.8.13 Connections and Memory

Inspect:

``` sql
SHOW max_connections;
```

More connections can mean more backend processes and more potential
concurrent query operations.

``` text
more connections
   |
   +-- more backend/process overhead
   +-- more concurrent queries
   +-- more possible work_mem consumers
   `-- greater aggregate memory risk
```

Do not automatically raise `max_connections` to solve application
connection pressure. Evaluate pooling and workload behavior.

Safe connection inventory:

``` sql
SELECT
    state,
    count(*) AS connections
FROM pg_stat_activity
GROUP BY state
ORDER BY connections DESC;
```

------------------------------------------------------------------------

## 2.8.14 Parallelism

Inspect:

``` sql
SHOW max_worker_processes;
SHOW max_parallel_workers;
SHOW max_parallel_workers_per_gather;
```

Parallel execution introduces another memory-concurrency dimension:

``` text
Leader
 |
 +-- worker
 +-- worker
 `-- worker
```

Do not estimate production memory using only
`max_connections × work_mem`.

------------------------------------------------------------------------

## 2.8.15 Huge Pages

Safe PostgreSQL inspection:

``` sql
SHOW huge_pages;
SHOW huge_page_size;
SHOW huge_pages_status;
```

`huge_pages_status` is particularly useful because it shows whether
explicit huge pages are actually in use.

For self-managed Linux:

``` bash
grep -i huge /proc/meminfo
```

Where the PostgreSQL binary and data directory are directly available,
PostgreSQL can calculate its main shared-memory huge-page requirement:

``` bash
postgres -D "$PGDATA" -C shared_memory_size_in_huge_pages
```

This tutorial does **not** change huge-page configuration.

### Explicit huge pages versus THP

``` text
PostgreSQL explicit huge pages != Linux Transparent Huge Pages
```

PostgreSQL documentation notes that Transparent Huge Pages have caused
performance degradation for some PostgreSQL workloads on some Linux
versions. Treat THP configuration as an OS-level change requiring
platform review and testing.

------------------------------------------------------------------------

## 2.8.16 Linux Overcommit and OOM Investigation

Self-managed Linux inspection:

``` bash
sysctl vm.overcommit_memory
free -h
journalctl -k | grep -i -E 'oom|killed process'
```

On systems where `journalctl` is unavailable, use the appropriate
platform logging mechanism.

These commands are observational in this tutorial. Do not change kernel
overcommit behavior as part of the lab.

An OOM event should trigger review of:

-   effective host/container memory;
-   `shared_buffers`;
-   `work_mem`;
-   `hash_mem_multiplier`;
-   active connection and query concurrency;
-   parallel workers;
-   maintenance and autovacuum concurrency;
-   extensions/background workers;
-   sidecars/monitoring agents;
-   swap and kernel policy;
-   container/Kubernetes limits.

## 2.8.17 Lab Safety Boundary

> **LAB-ONLY --- CREATES OBJECTS AND RUNS LARGE SORTS**

The lab creates:

``` text
Database: memory_lab
Schema:   memory_lab
Table:    memory_lab.orders
Rows:     approximately 1,000,000
```

Run it only in a disposable lab or approved non-production environment.
Storage use, temporary I/O, execution time, and memory consumption vary
by system.

`EXPLAIN (ANALYZE, BUFFERS)` **executes the statement**. For unfamiliar
or potentially expensive production SQL, begin with `EXPLAIN` without
`ANALYZE`.

## 2.8.18 Create the Lab

``` sql
CREATE DATABASE memory_lab;
```

Reconnect to `memory_lab`, then:

``` sql
CREATE SCHEMA memory_lab;

CREATE TABLE memory_lab.orders (
    order_id    BIGINT GENERATED ALWAYS AS IDENTITY,
    customer_id BIGINT NOT NULL,
    order_date  TIMESTAMPTZ NOT NULL DEFAULT now(),
    amount      NUMERIC(12,2) NOT NULL,
    status      TEXT NOT NULL
);

INSERT INTO memory_lab.orders
    (customer_id, order_date, amount, status)
SELECT
    (random() * 100000)::BIGINT,
    now() - (random() * interval '365 days'),
    round((random() * 5000)::numeric, 2),
    CASE (random() * 3)::INT
        WHEN 0 THEN 'NEW'
        WHEN 1 THEN 'PROCESSING'
        WHEN 2 THEN 'COMPLETED'
        ELSE 'CANCELLED'
    END
FROM generate_series(1, 1000000);

ANALYZE memory_lab.orders;
```

## 2.8.19 Establish a Temporary-I/O Baseline

Before the sort experiment:

``` sql
SELECT
    datname,
    temp_files,
    temp_bytes,
    pg_size_pretty(temp_bytes) AS temp_written
FROM pg_stat_database
WHERE datname = current_database();
```

These statistics are cumulative. Record a baseline and compare the delta
after the workload; do not attribute the entire cumulative value to one
query.

## 2.8.20 Constrained Sort

Change only the current session:

``` sql
SET work_mem = '1MB';
SHOW work_mem;
```

Execute in the lab:

``` sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM memory_lab.orders
ORDER BY amount;
```

Inspect:

-   sort method;
-   memory;
-   disk usage;
-   temporary reads/writes;
-   execution time.

A sufficiently large sort may use an external sort and temporary disk
storage. Exact results depend on the environment.

------------------------------------------------------------------------

## 2.8.21 Larger Session-Scoped `work_mem`

Now:

``` sql
SET work_mem = '64MB';

EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM memory_lab.orders
ORDER BY amount;
```

Compare the plan and temporary I/O with the constrained run.

The objective is not to prove that 64 MB is optimal. The objective is to
observe how a session-scoped memory change can alter execution behavior.

Restore the session:

``` sql
RESET work_mem;
SHOW work_mem;
```

## 2.8.22 Compare Temporary-I/O Delta

## 2.8.23 Production Memory Budget

For a hypothetical 32 GiB dedicated server, think in resource pools
rather than one formula:

``` text
32 GiB effective memory
 |
 +-- PostgreSQL shared memory
 +-- OS/filesystem cache
 +-- active query memory
 +-- maintenance/autovacuum
 +-- backend/session overhead
 +-- parallel/background workers
 +-- extensions/agents
 `-- safety reserve
```

A configuration such as:

``` text
shared_buffers       = 8 GiB
work_mem             = 16 MiB
maintenance_work_mem = 1 GiB
max_connections      = 200
```

must **not** be evaluated as merely:

``` text
8 GiB + (200 × 16 MiB)
```

That ignores plan-node multiplicity, hashes, parallelism, maintenance,
backend overhead, temporary buffers, extensions, and the operating
system.

## 2.8.24 Production Change Gate

Before a global memory increase, document:

``` text
[ ] Effective RAM/container limit
[ ] Current MemAvailable / memory pressure
[ ] Peak active sessions
[ ] Peak active queries
[ ] Representative execution plans
[ ] Memory-consuming plan nodes
[ ] hash_mem_multiplier
[ ] Parallel-worker configuration
[ ] Autovacuum concurrency
[ ] Maintenance concurrency
[ ] Temporary-file rate/delta
[ ] Other host/container consumers
[ ] OOM history
[ ] Current parameter value
[ ] Proposed parameter value
[ ] Restart/reload/session semantics
[ ] Expected benefit
[ ] Monitoring plan
[ ] Rollback trigger
[ ] Rollback value
[ ] Change owner
[ ] Approved maintenance window when required
```

## 2.8.26 Lab Cleanup

First restore any session-scoped settings:

``` sql
RESET work_mem;
```

Close your sessions connected to `memory_lab`.

From another database, inspect remaining sessions:

``` sql
SELECT
    pid,
    usename,
    application_name,
    state
FROM pg_stat_activity
WHERE datname = 'memory_lab';
```

Do not automatically terminate other users' sessions just to complete
cleanup.

When the lab database is no longer in use:

``` sql
DROP DATABASE memory_lab;
```

## 2.8.29 Key Takeaways

``` text
shared_buffers
  -> PostgreSQL shared buffer cache

work_mem
  -> base memory limit for eligible query operations

hash_mem_multiplier
  -> modifies the memory limit for hash operations

maintenance_work_mem
  -> memory for eligible maintenance operations

autovacuum_work_mem
  -> autovacuum worker memory; may inherit maintenance_work_mem

vacuum_buffer_usage_limit
  -> VACUUM/ANALYZE buffer access strategy limit

temp_buffers
  -> temporary-table buffers per session

effective_cache_size
  -> planner estimate; does not allocate RAM

max_connections
  -> affects backend resources and potential concurrency

parallel workers
  -> add another dimension to aggregate memory consumption
```

The production method is:

``` text
measure -> understand concurrency -> test narrowly
        -> validate -> review -> deploy -> monitor
```
