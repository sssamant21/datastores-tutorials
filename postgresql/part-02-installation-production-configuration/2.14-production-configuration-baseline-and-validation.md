# Part 2.14 --- Production Configuration Baseline and Validation

**Status:** Revised Final / Canonical Edition\
**Target:** PostgreSQL 18\
**Audience:** PostgreSQL administrators, DBREs, SREs, platform
engineers, and production support engineers.

## Objectives

After completing this tutorial, you should be able to:

-   treat PostgreSQL configuration as a production baseline rather than
    a collection of isolated parameters;
-   identify the active PostgreSQL configuration files and parameter
    sources;
-   distinguish current runtime values from values present in
    configuration files;
-   detect configuration-file parsing or application problems;
-   identify settings that require a server restart;
-   review connection, memory, WAL/checkpoint, logging, timeout, worker,
    and I/O settings as one capacity system;
-   inspect authentication configuration without changing access;
-   validate important production settings using read-only PostgreSQL
    interfaces;
-   separate database-level validation from host-, filesystem-,
    service-, and network-level validation;
-   recognize where managed PostgreSQL services restrict host or
    configuration access;
-   use a repeatable pre-change and post-change validation methodology;
-   preserve rollback evidence for production configuration changes.

------------------------------------------------------------------------

## 1. Safety Model

This tutorial uses the following safety classifications.

``` text
[SAFE-READ]
    Reads PostgreSQL state without intentionally changing it.

[HOST-READ]
    Reads operating-system or service metadata without changing it.

[LAB-ONLY]
    Changes only a disposable lab environment.

[PRODUCTION-CHANGE]
    Changes persistent PostgreSQL or host configuration.

[PRODUCTION-CHANGE — RELOAD]
    Requires a controlled configuration reload.

[PRODUCTION-CHANGE — RESTART]
    Requires a controlled PostgreSQL restart.

[SECURITY-CHANGE]
    Changes authentication, TLS, listening interfaces, firewall policy,
    roles, credentials, or another access-control boundary.
```

The companion `production-baseline-check.sh` artifact is designed as an
inspection-only acceptance check. It does **not** edit configuration,
execute `ALTER SYSTEM`, reload PostgreSQL, restart PostgreSQL, modify
authentication rules, change firewall policy, or perform DDL/DML.

------------------------------------------------------------------------

## 2. What Is a Production Configuration Baseline?

A production baseline is the reviewed and approved state from which a
PostgreSQL server is operated.

It includes more than `postgresql.conf`.

``` text
Production PostgreSQL baseline
        |
        +-- PostgreSQL version/build
        +-- active configuration locations
        +-- parameter values and sources
        +-- connection/authentication boundary
        +-- memory/resource configuration
        +-- worker/process capacity
        +-- WAL/checkpoint configuration
        +-- logging/diagnostics
        +-- timeout policy
        +-- data/WAL/tablespace storage layout
        +-- service-management model
        +-- operating-system resource limits
        +-- monitoring/alerting expectations
        +-- change/rollback procedure
```

A parameter can be individually valid while the complete system is
unsafe. Production review therefore evaluates interactions between
settings.

------------------------------------------------------------------------

## 3. Baseline Validation Is Not Tuning

These are different activities.

``` text
BASELINE VALIDATION
    What is configured?
    Where did the value come from?
    Is the configuration internally valid?
    Does it match the approved architecture?
    Does a restart remain pending?

TUNING
    Should the value be changed?
    What workload evidence supports the change?
    What capacity impact will the change have?
```

Do not turn an acceptance script into an automatic tuning tool.

A production validator should report evidence. Humans and controlled
automation should decide whether a persistent change is appropriate.

------------------------------------------------------------------------

## 4. Establish Server Identity First

Before comparing settings, establish which server you are inspecting.

``` sql
-- [SAFE-READ]
SELECT
    current_database() AS database_name,
    current_user AS current_user,
    version() AS server_version;
```

Also inspect server start time:

``` sql
-- [SAFE-READ]
SELECT pg_postmaster_start_time();
```

This matters because a baseline captured from the wrong cluster,
database, environment, or newly restarted server can lead to an invalid
conclusion.

Record environment metadata outside PostgreSQL as appropriate:

``` text
environment
cluster/service name
region
host or managed-service identifier
PostgreSQL major/minor version
change/ticket identifier
validation timestamp
operator
```

Do not place passwords or secrets in the evidence package.

------------------------------------------------------------------------

## 5. Discover Configuration Locations

Do not assume all installations keep configuration files directly under
`PGDATA`.

``` sql
-- [SAFE-READ]
SHOW data_directory;
SHOW config_file;
SHOW hba_file;
SHOW ident_file;
```

A distribution package, container image, managed service, or custom
startup configuration can place configuration differently.

The baseline should record the locations reported by the running server
rather than relying on a hard-coded filesystem assumption.

------------------------------------------------------------------------

## 6. Understand Configuration Sources

PostgreSQL settings can originate from multiple layers, including:

``` text
compiled/default value
environment/startup command
postgresql.conf
included configuration files
postgresql.auto.conf
database defaults
role defaults
session/client settings
```

For server-wide runtime inspection, `pg_settings` is the primary source.

``` sql
-- [SAFE-READ]
SELECT
    name,
    setting,
    unit,
    context,
    source,
    sourcefile,
    sourceline,
    pending_restart
FROM pg_settings
ORDER BY name;
```

Important fields include:

-   `setting` --- current runtime value;
-   `context` --- the context required to change the parameter;
-   `source` --- source of the current value;
-   `sourcefile` / `sourceline` --- configuration-file provenance when
    visible;
-   `pending_restart` --- whether the configuration-file value differs
    from the active runtime value for a parameter that requires restart.

Permissions can limit visibility of some source-file information.

------------------------------------------------------------------------

## 7. Configuration Precedence Matters

A value written in one configuration file is not necessarily the
effective value.

For example:

``` text
postgresql.conf
       |
       +--> include / include_dir
       |
       +--> later configuration entry
       |
postgresql.auto.conf
       |
       v
effective server configuration
```

PostgreSQL processes configuration entries in order, and later
applicable entries can override earlier ones.

`postgresql.auto.conf` is used for settings written by `ALTER SYSTEM`
and is read with the server configuration.

Therefore, never validate a production baseline by grepping only one
`postgresql.conf` file.

------------------------------------------------------------------------

## 8. Inspect Configuration-File Parsing

`pg_file_settings` summarizes settings found in PostgreSQL configuration
files and reports whether entries can be applied.

``` sql
-- [SAFE-READ; privilege dependent]
SELECT
    sourcefile,
    sourceline,
    seqno,
    name,
    setting,
    applied,
    error
FROM pg_file_settings
WHERE error IS NOT NULL
   OR applied IS FALSE
ORDER BY seqno;
```

Interpret results carefully.

`applied = false` does not always mean syntax failure. An earlier entry
can also be superseded by a later value.

The strongest failure signal is a non-null `error`.

A production validation should distinguish:

``` text
configuration parse/application error
        !=
valid entry overridden by later configuration
```

Access to `pg_file_settings` is privilege restricted by default.

------------------------------------------------------------------------

## 9. Detect Pending Restarts

A configuration file can contain the intended value while the running
server still uses the previous value.

Check:

``` sql
-- [SAFE-READ]
SELECT
    name,
    setting,
    unit,
    source,
    sourcefile,
    sourceline
FROM pg_settings
WHERE pending_restart
ORDER BY name;
```

A non-empty result is operationally important.

It means:

``` text
desired file configuration
        !=
currently active runtime state
```

Do **not** automatically restart PostgreSQL because this query returns
rows.

A production restart requires an approved change window, dependency
review, HA/failover considerations, application coordination where
required, and a rollback/recovery plan.

------------------------------------------------------------------------

## 10. Reloadable vs Restart-Required Settings

PostgreSQL settings have different change contexts.

Inspect them instead of memorizing every parameter:

``` sql
-- [SAFE-READ]
SELECT
    name,
    setting,
    unit,
    context,
    pending_restart
FROM pg_settings
WHERE name IN (
    'listen_addresses',
    'port',
    'max_connections',
    'shared_buffers',
    'work_mem',
    'maintenance_work_mem',
    'max_wal_size',
    'checkpoint_timeout',
    'logging_collector',
    'log_destination'
)
ORDER BY name;
```

The `context` column helps determine how a setting can be changed.

Never assume that:

``` text
configuration file edited successfully
        =
running server now uses the value
```

Likewise, do not call `pg_reload_conf()` from a SAFE-READ acceptance
artifact. Reload is an operational action.

## 11. Memory Baseline

Review memory settings as a group.

``` sql
-- [SAFE-READ]
SELECT
    name,
    setting,
    unit,
    context,
    source,
    pending_restart
FROM pg_settings
WHERE name IN (
    'shared_buffers',
    'work_mem',
    'hash_mem_multiplier',
    'maintenance_work_mem',
    'autovacuum_work_mem',
    'temp_buffers',
    'effective_cache_size',
    'huge_pages',
    'max_connections',
    'max_worker_processes',
    'max_parallel_workers',
    'max_parallel_workers_per_gather'
)
ORDER BY name;
```

A useful capacity model is:

``` text
shared/global allocations
+
concurrent backend/session exposure
+
per-operation work memory exposure
+
maintenance/autovacuum exposure
+
worker/parallel exposure
+
OS + filesystem cache
+
monitoring/agents
+
safety headroom
<=
available host/container memory
```

Do not use a simple formula such as:

``` text
RAM - shared_buffers = safe work_mem pool
```

`work_mem` is an operation-level limit and a query can use it multiple
times. Concurrent queries multiply the exposure.

------------------------------------------------------------------------

## 12. Connection and Session Baseline

Review connection capacity together with memory and application
topology.

``` sql
-- [SAFE-READ]
SELECT
    name,
    setting,
    unit,
    context,
    source,
    pending_restart
FROM pg_settings
WHERE name IN (
    'max_connections',
    'reserved_connections',
    'superuser_reserved_connections',
    'authentication_timeout',
    'statement_timeout',
    'lock_timeout',
    'transaction_timeout',
    'idle_in_transaction_session_timeout',
    'idle_session_timeout',
    'client_connection_check_interval'
)
ORDER BY name;
```

Then inspect current client-session counts:

``` sql
-- [SAFE-READ]
SELECT
    state,
    COUNT(*) AS sessions
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY state
ORDER BY state;
```

A point-in-time session count is not sufficient for capacity planning.

The production baseline should also consider:

``` text
application replicas
pool maximum per replica
HPA/autoscaling maximum
deployment surge
background jobs
ETL/reporting
monitoring
administrative reserve
failover/reconnect behavior
historical peak
```

------------------------------------------------------------------------

## 13. Network Listening Baseline

Inspect:

``` sql
-- [SAFE-READ]
SELECT
    name,
    setting,
    context,
    source,
    pending_restart
FROM pg_settings
WHERE name IN (
    'listen_addresses',
    'port',
    'ssl'
)
ORDER BY name;
```

`listen_addresses` controls which interfaces accept TCP/IP connection
attempts. It is a server-start parameter.

A value such as:

``` text
*
```

is not automatically wrong, but it substantially changes the network
exposure model and must be evaluated with:

``` text
host/network firewall
security groups / NSGs
Kubernetes network policy
load balancer/proxy exposure
pg_hba.conf
TLS requirements
service ownership
```

Do not change listening addresses or firewall policy as part of a
read-only baseline check.

------------------------------------------------------------------------

## 14. Authentication Baseline

PostgreSQL provides `pg_hba_file_rules` for inspecting parsed host-based
authentication rules.

A safe summary can avoid printing authentication option values that
might contain sensitive operational information:

``` sql
-- [SAFE-READ; privilege dependent]
SELECT
    rule_number,
    type,
    database,
    user_name,
    address,
    netmask,
    auth_method,
    error
FROM pg_hba_file_rules
ORDER BY rule_number;
```

Focus especially on:

``` text
parsing errors
unexpected broad networks
unexpected databases/users
weak or legacy authentication policy
rule ordering
missing expected restrictions
```

Do not automatically rewrite `pg_hba.conf`.

Authentication changes can lock out applications and administrators and
must be treated as security changes.

------------------------------------------------------------------------

## 15. WAL and Checkpoint Baseline

Inspect the major WAL/checkpoint controls together:

``` sql
-- [SAFE-READ]
SELECT
    name,
    setting,
    unit,
    context,
    source,
    pending_restart
FROM pg_settings
WHERE name IN (
    'wal_level',
    'wal_buffers',
    'wal_compression',
    'checkpoint_timeout',
    'checkpoint_completion_target',
    'max_wal_size',
    'min_wal_size',
    'archive_mode',
    'archive_command',
    'archive_library',
    'max_wal_senders'
)
ORDER BY name;
```

### Sensitive-command caution

`archive_command` can contain paths or operational command text.

A generic acceptance artifact should therefore avoid printing its
complete value unless the environment explicitly permits it.

For shared evidence, prefer checking state without exposing command
text:

``` sql
-- [SAFE-READ]
SELECT
    name,
    CASE
        WHEN name IN ('archive_command', 'archive_library')
            THEN CASE WHEN setting = '' THEN '<empty>' ELSE '<configured>' END
        ELSE setting
    END AS setting,
    unit,
    context,
    source,
    pending_restart
FROM pg_settings
WHERE name IN (
    'wal_level',
    'wal_buffers',
    'checkpoint_timeout',
    'checkpoint_completion_target',
    'max_wal_size',
    'min_wal_size',
    'archive_mode',
    'archive_command',
    'archive_library'
)
ORDER BY name;
```

## 16. Background Writer and I/O Baseline

PostgreSQL resource configuration includes background-writer and I/O
behavior. Relevant settings should be inspected according to the
deployment architecture and PostgreSQL version.

For PostgreSQL 18, also recognize that asynchronous I/O configuration is
part of the resource baseline.

Example:

``` sql
-- [SAFE-READ]
SELECT
    name,
    setting,
    unit,
    context,
    source,
    pending_restart
FROM pg_settings
WHERE name IN (
    'bgwriter_delay',
    'bgwriter_lru_maxpages',
    'bgwriter_lru_multiplier',
    'io_method',
    'io_workers',
    'io_max_concurrency'
)
ORDER BY name;
```

Do not copy a baseline from another server merely because it has the
same vCPU count. Storage latency, workload shape, memory, connection
concurrency, and deployment model can differ.

------------------------------------------------------------------------

## 17. Logging and Diagnostic Baseline

Inspect logging controls without changing them:

``` sql
-- [SAFE-READ]
SELECT
    name,
    setting,
    unit,
    context,
    source,
    pending_restart
FROM pg_settings
WHERE name IN (
    'logging_collector',
    'log_destination',
    'log_min_messages',
    'log_min_error_statement',
    'log_connections',
    'log_disconnections',
    'log_checkpoints',
    'log_lock_waits',
    'log_lock_failures',
    'log_temp_files',
    'log_autovacuum_min_duration',
    'log_error_verbosity'
)
ORDER BY name;
```

Logging has both observability and risk implications.

Too little logging can hide failures.

Too much logging can create:

``` text
storage growth
I/O pressure
central logging cost
high ingestion volume
sensitive-data exposure
```

Avoid automatically enabling broad statement or parameter logging in
production.

------------------------------------------------------------------------

## 18. Configuration Validation Must Include Storage

Database configuration cannot compensate for an unsafe storage design.

Review externally:

``` text
PGDATA filesystem
pg_wal location
tablespace locations
filesystem free space
inode availability
mount persistence
ownership and permissions
storage latency/IOPS/throughput
backup/snapshot integration
volume growth
WAL growth
log growth
```

PostgreSQL's data directory contains critical database state.
Configuration files may traditionally live there but can also be located
elsewhere.

A SQL-only validator cannot prove that the underlying filesystem has
sufficient capacity or durability.

------------------------------------------------------------------------

## 19. Operating-System and Resource-Limit Validation

The production baseline should include host-level evidence where the
platform permits access.

Examples:

``` text
physical/container memory
CPU allocation
swap policy
process limits
open-file limits
shared-memory/kernel constraints where relevant
filesystem/mount options
disk capacity
time synchronization
service manager configuration
OOM behavior
```

These checks are platform-specific.

Do not encode one Linux distribution's service name or kernel policy as
a universal PostgreSQL requirement.

------------------------------------------------------------------------

## 20. Managed PostgreSQL Services

Managed services change the validation boundary.

You may not have access to:

``` text
postgresql.conf filesystem
PGDATA
systemd
kernel parameters
mount configuration
postgres OS account
host logs
```

Configuration may instead be controlled through:

``` text
AWS RDS/Aurora parameter groups
Azure Database for PostgreSQL server parameters
Google Cloud SQL database flags
provider APIs/control planes
```

Therefore:

``` text
self-managed baseline
        !=
managed-service baseline
```

The PostgreSQL-side SAFE-READ queries remain useful where supported, but
host-level evidence must come from the provider control plane and
monitoring system.

------------------------------------------------------------------------

## 21. Build an Approved Baseline Manifest

Do not hard-code undocumented universal values.

Instead maintain an environment-specific baseline manifest.

Example structure:

``` yaml
postgresql:
  major_version: 18

identity:
  environment: production
  service: patient-db

configuration:
  max_connections:
    expected: 300
    rationale: approved connection-capacity model
  shared_buffers:
    expected: 8GB
    rationale: approved memory-capacity model
  checkpoint_timeout:
    expected: 15min
    rationale: workload-tested baseline

security:
  tls_required: true

operations:
  restart_window_required: true
  configuration_owner: DBRE
```

The values above are examples only.

A production baseline should be derived from the actual host/container
capacity, workload, availability architecture, and organizational
standards.

## 22. Drift Detection

Baseline validation becomes especially useful when repeated.

Conceptually:

``` text
approved baseline
       |
       v
capture current state
       |
       v
normalize evidence
       |
       v
compare
       |
       +--> no drift
       |
       +--> expected approved drift
       |
       +--> unexplained drift
```

Not every difference is an incident.

Classify differences:

``` text
EXPECTED
    approved deployment/change

BENIGN
    known environment-specific difference

REVIEW REQUIRED
    undocumented change

CRITICAL
    security, availability, durability, or capacity risk
```

The acceptance artifact in this tutorial collects evidence; it does not
automatically remediate drift.

## 23. Pre-Change Validation

Before a production configuration change, capture:

``` text
server/version identity
current parameter values
parameter sources
pending_restart state
configuration parsing errors
session/connection state
resource/capacity evidence
relevant storage state
relevant monitoring baseline
HA/replication state when applicable
```

Also record:

``` text
change reason
expected outcome
affected settings
reload vs restart requirement
rollback values
maintenance window
validation queries
owner
```

This provides a before-state for comparison.

------------------------------------------------------------------------

## 24. Change Gate

A production configuration change should pass a gate such as:

``` text
1. Problem/evidence documented
2. Parameter interaction reviewed
3. Capacity impact reviewed
4. Security impact reviewed
5. HA/failover impact reviewed
6. Reload/restart requirement identified
7. Rollback values captured
8. Maintenance window approved where required
9. Monitoring prepared
10. Post-change acceptance plan prepared
```

Only after that should the operator perform the change.

The canonical acceptance script intentionally does not implement the
change.

------------------------------------------------------------------------

## 25. Post-Change Validation

After an approved change:

``` text
1. Confirm server identity/version
2. Confirm expected runtime value
3. Confirm source/provenance
4. Check pending_restart
5. Check configuration parsing
6. Validate connectivity
7. Validate application health
8. Validate database health
9. Validate resource behavior
10. Compare key metrics to pre-change baseline
11. Record evidence
```

A successful command is not the same as a successful production change.

------------------------------------------------------------------------

## 26. Rollback Decision

Rollback criteria should be defined before implementation.

Examples include:

``` text
database fails to start
application cannot authenticate/connect
unexpected memory pressure
connection saturation
checkpoint/WAL regression
storage pressure
logging flood
replication/HA degradation
latency or error-rate regression
unexpected restart requirement
```

The exact thresholds are environment-specific.

Do not improvise rollback criteria only after impact begins.

## 27. Hands-On Lab --- Production Baseline Inspection

### Goal

Capture a read-only PostgreSQL configuration evidence package.

### Prerequisites

``` text
PostgreSQL 18
psql
a role with enough visibility for the desired system views
the companion production-baseline-check.sh
```

Some views expose additional information only to privileged roles. Lack
of permission should be reported rather than bypassed.

### Environment variables

Use standard libpq environment/configuration mechanisms.

Example:

``` bash
export PGHOST="db.example.internal"
export PGPORT="5432"
export PGDATABASE="postgres"
export PGUSER="baseline_reader"
```

Do not put a plaintext password into the script or commit credentials to
the repository.

### Run

``` bash
chmod +x labs/production-baseline-check.sh
./labs/production-baseline-check.sh
```

The script uses `psql` read-only queries and stops on SQL errors.

## 31. Production Principles

### Principle 1 --- Validate effective state

Do not validate only the text in one configuration file.

### Principle 2 --- Configuration is a system

Memory, connections, workers, WAL, storage, logging, and OS resources
interact.

### Principle 3 --- Separate observation from mutation

Acceptance checks should not silently modify production.

### Principle 4 --- Preserve operational access

Connection and authentication changes must retain a tested
administrative recovery path.

### Principle 5 --- Treat restart as a production event

`pending_restart` is evidence, not authorization to restart.

### Principle 6 --- Baselines are environment-specific

A setting appropriate for one workload can be unsafe for another.

### Principle 7 --- Capture before and after evidence

Configuration management without evidence makes incident analysis and
rollback harder.
