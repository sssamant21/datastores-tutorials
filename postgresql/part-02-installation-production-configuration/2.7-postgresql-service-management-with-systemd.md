# 2.7 — PostgreSQL Service Management with systemd

**Part:** 2 — Installation & Production Configuration  
**Edition:** Revised Final / Canonical  
**Target:** PostgreSQL 18 on Linux with systemd  
**Service-operation classification:** `[TUTORIAL-OPERATOR-ACTION — MUTATING]`  
**Acceptance classification:** `[TUTORIAL-ACCEPTANCE — SAFE-READ]`

## 2.7.1 Introduction

Installing PostgreSQL and initializing a cluster does not by itself establish a production service-management architecture. On Linux systems using systemd, operators must know exactly which unit, operating-system identity, executable or approved wrapper, and PostgreSQL cluster they are managing before performing lifecycle operations.

The production model is:

```text
discover → inspect → select explicitly → correlate → operate only when authorized
```

The canonical acceptance workflow is observational. It never starts, stops, restarts, reloads, enables, disables, masks, unmasks, or repairs PostgreSQL or systemd.

## 2.7.2 Learning Objectives

After this section you should be able to discover PostgreSQL-related units, inspect the effective systemd definition, distinguish runtime state from enablement, validate service identity and `ExecStart`, correlate `MainPID` with an explicitly supplied `PGDATA`, inspect bounded journal evidence, understand PostgreSQL shutdown semantics, distinguish systemd state from PostgreSQL readiness, and run a SAFE-READ acceptance check.

## 2.7.3 Service Naming Is Not Universal

A PostgreSQL unit might be named `postgresql.service`, `postgresql-18.service`, `postgresql@18-main.service`, or something distribution- or organization-specific. These are examples only.

Package installations should normally use and understand the package/distribution service infrastructure. Source installations may use organization-managed units. Never guess the production unit from its name.

## 2.7.4 Explicit Service Selection

The canonical lab requires `PG_SERVICE`:

```bash
export PG_SERVICE=postgresql-18.service
printf 'PG_SERVICE=%s\n' "$PG_SERVICE"
```

The value above is only an example.

```text
PG_SERVICE unset → BLOCKER
PG_SERVICE supplied → validate exact unit
```

Discovery may report candidates, but the acceptance script never selects one automatically.

## 2.7.5 Discover Candidate Units

```bash
systemctl list-unit-files --type=service | grep -i postgres
systemctl list-units --type=service --all | grep -i postgres
```

Discovery output is informational and does not establish cluster identity.

## 2.7.6 Multi-Cluster Protection

A host can contain multiple PostgreSQL versions or clusters. Before a lifecycle operation, correlate as much of the following as the architecture exposes:

```text
host
+ systemd unit
+ service account
+ binary / approved wrapper
+ PGDATA
+ MainPID
+ optional postmaster.pid
+ port/readiness target
```

## 2.7.7 Validate Unit Existence

```bash
systemctl show "$PG_SERVICE" -p LoadState --value
```

Classification:

```text
loaded → continue
not-found → BLOCKER
ambiguous/error → REQUIRES VALIDATION
```

The acceptance script does not create or repair units.

## 2.7.8 Runtime State and Enablement

Inspect separately:

```bash
systemctl is-active "$PG_SERVICE"
systemctl is-enabled "$PG_SERVICE"
systemctl is-failed "$PG_SERVICE"
```

`is-active` describes current runtime state. `is-enabled` describes unit enablement configuration. They are not equivalent.

Suggested interpretation:

```text
active → PASS for runtime observation
inactive → REQUIRES VALIDATION against intended state
failed → BLOCKER
activating/deactivating → REQUIRES VALIDATION
```

An intentionally offline service is not automatically defective.

## 2.7.9 Effective Unit

```bash
systemctl cat "$PG_SERVICE"
```

Review the effective vendor unit and drop-ins. Relevant directives can include `User=`, `Group=`, `Environment=`, `EnvironmentFile=`, `ExecStart=`, `ExecStop=`, `ExecReload=`, `KillSignal=`, `Restart=`, and timeout directives.

Structured inspection:

```bash
systemctl show "$PG_SERVICE"   -p Id -p LoadState -p ActiveState -p SubState -p UnitFileState   -p MainPID -p User -p Group -p ExecStart -p ExecReload   -p Restart -p FragmentPath
```

Values extracted from systemd metadata are evidence only. The acceptance script must never execute them using `eval`, `bash -c`, or `sh -c`.

## 2.7.10 Service Account

```bash
systemctl show "$PG_SERVICE" -p User -p Group
```

PostgreSQL must run under an appropriate non-root identity.

```text
explicit PostgreSQL server identity = root → BLOCKER
expected non-root identity → PASS
unexpected non-root identity → REQUIRES VALIDATION
ambiguous identity → REQUIRES VALIDATION
```

An empty `User=` property alone is not enough to prove that the PostgreSQL server process runs as root; correlate it with the deployed architecture and running process.

## 2.7.11 ExecStart and Wrapper Validation

```bash
systemctl show "$PG_SERVICE" -p ExecStart
systemctl cat "$PG_SERVICE"
```

A package-managed service may use a wrapper rather than directly invoking `postgres -D ...`.

```text
expected PostgreSQL 18 executable → PASS
approved package wrapper → valid after architectural confirmation
unknown wrapper → REQUIRES VALIDATION
clearly wrong PostgreSQL major version → BLOCKER
```

Do not dynamically execute paths or strings extracted from `ExecStart`.

## 2.7.12 Type=notify

`Type=notify` is valid when PostgreSQL has the required systemd notification support. It is not a universal requirement for every PostgreSQL service. Follow the deployed package/vendor unit architecture.

## 2.7.13 PGDATA Correlation

The service may identify its cluster using `-D`, `PGDATA`, an environment file, a package wrapper, cluster-management tooling, or another approved launcher.

If the operator explicitly supplies:

```bash
export PGDATA=/pgdata/18/main
```

the acceptance script may compare available evidence. If `PGDATA` is unset, correlation is `NOT APPLICABLE`.

The script must not recursively scan the host for clusters. Production hosts may contain backups, old clusters, snapshots, and test data directories.

## 2.7.14 Environment Files

A unit may reference `EnvironmentFile=`. The acceptance workflow may report that reference but must not automatically dump the file because it may contain sensitive operational information.

## 2.7.15 MainPID and Process Inspection

```bash
MAIN_PID="$(systemctl show "$PG_SERVICE" -p MainPID --value)"
printf 'MainPID=%s\n' "$MAIN_PID"
```

For a positive numeric PID:

```bash
ps -fp "$MAIN_PID"
```

`MainPID=0` must be interpreted with service state. A supporting process inventory is:

```bash
ps -ef | grep '[p]ostgres'
```

Multiple PostgreSQL processes are normal and do not by themselves prove multiple clusters.

## 2.7.16 postmaster.pid Correlation

When explicit `PGDATA` is supplied and `$PGDATA/postmaster.pid` exists:

```bash
head -n 1 "$PGDATA/postmaster.pid"
```

may be compared with systemd `MainPID`.

A clear mismatch requires validation and may be a blocker when the architecture unambiguously requires both to represent the same server.

Never delete, rename, truncate, or edit `postmaster.pid` during acceptance.

## 2.7.17 Starting PostgreSQL

```bash
systemctl start "$PG_SERVICE"
```

Classification: `[TUTORIAL-OPERATOR-ACTION — MUTATING]`.

Before a production start, confirm the host, environment, exact unit, PostgreSQL installation, PGDATA, required storage, configuration, application impact, and authorization. The acceptance lab never starts PostgreSQL.

## 2.7.18 Startup and Recovery

Crash recovery can make PostgreSQL startup take longer than an ordinary start. systemd startup timeout behavior must therefore be understood in the context of PostgreSQL recovery. This tutorial does not prescribe one universal timeout.

## 2.7.19 Stopping PostgreSQL

```bash
systemctl stop "$PG_SERVICE"
```

Classification: `[TUTORIAL-OPERATOR-ACTION — MUTATING / AVAILABILITY IMPACT]`.

The acceptance lab never stops PostgreSQL.

## 2.7.20 PostgreSQL Shutdown Modes

PostgreSQL shutdown behavior includes:

```text
Smart / SIGTERM
→ reject new connections and wait for existing sessions.

Fast / SIGINT
→ terminate active sessions, roll back active transactions, orderly shutdown.

Immediate / SIGQUIT
→ emergency termination; recovery is required on next startup.
```

Do not assume every systemd unit implements stop behavior identically. Inspect the effective unit.

`SIGKILL` (`kill -9`) is not a routine PostgreSQL shutdown mechanism.

## 2.7.21 Restart and Reload

```bash
systemctl restart "$PG_SERVICE"
systemctl reload "$PG_SERVICE"
```

Both are mutating. Restart can affect availability. Reload works only when the deployed unit implements suitable reload behavior.

Do not use restart as the default troubleshooting response. Preserve evidence and diagnose first.

## 2.7.22 Avoid Mixing Lifecycle Managers

On a systemd-managed production cluster, do not casually mix systemd lifecycle commands with independent `pg_ctl` lifecycle commands. Doing so can create disagreement between actual PostgreSQL process state and systemd's expected service state.

The acceptance lab invokes neither lifecycle mechanism.

## 2.7.23 systemd State Is Not PostgreSQL Health

`systemctl is-active` reports service-manager state. It does not prove that PostgreSQL accepts expected connections, application authentication succeeds, queries perform normally, replication is healthy, or storage is healthy.

## 2.7.24 pg_isready

If PostgreSQL is already running, the target is explicitly known, and `pg_isready` is installed:

```bash
pg_isready -h <approved-host-or-socket> -p <approved-port>
```

Common exit statuses:

```text
0 → accepting connections
1 → rejecting connections
2 → no response
3 → no attempt made
```

Correct database credentials are not required merely for basic readiness detection. The acceptance workflow does not request or embed passwords for this check.

Readiness is still not complete database or application health.

## 2.7.25 Journal Inspection

Use bounded evidence:

```bash
journalctl -u "$PG_SERVICE" -b -n 100 --no-pager
```

If journal access is denied, classify it as `REQUIRES VALIDATION`. Do not automatically escalate with `sudo`.

Journal output can contain operationally sensitive information. Review evidence before sharing it externally.

## 2.7.26 Masking, Enablement, and Manager Operations

The following are mutating and excluded from acceptance:

```text
systemctl enable / disable / reenable / preset
systemctl mask / unmask
systemctl daemon-reload / daemon-reexec
systemctl reset-failed
```

The acceptance workflow may inspect state but never changes it.

## 2.7.27 Restart Policy, Timeouts, and Resource Limits

Inspect without changing:

```bash
systemctl show "$PG_SERVICE" -p Restart
systemctl show "$PG_SERVICE" -p TimeoutStartUSec -p TimeoutStopUSec
systemctl show "$PG_SERVICE"   -p LimitNOFILE -p LimitNPROC -p LimitMEMLOCK -p TasksMax
```

Unexpected values require architectural validation rather than automatic tuning. Resource tuning is covered later in Part 2.13.

## 2.7.28 Dependencies and Storage

```bash
systemctl list-dependencies "$PG_SERVICE"
```

Dependencies can include mounts, network targets, and other services.

Part 2.6 established that PostgreSQL may depend on PGDATA, WAL, and external tablespace storage. Required storage must be available before an authorized production start. The acceptance lab never mounts or repairs storage.

## 2.7.30 Evidence Artifact

Suggested learner evidence:

```text
postgresql-systemd-service.txt
```

Record timestamp, hostname, environment, PG_SERVICE, load/active/sub/unit-file state, fragment path, service identity, ExecStart/ExecReload, expected/observed PostgreSQL version, optional PGDATA evidence, MainPID, optional postmaster.pid PID, restart policy, timeouts, resource limits, journal accessibility, readiness result, observed risks, and follow-up.

Do not include passwords, tokens, private keys, or credential-bearing connection strings.

## 2.7.31 Acceptance Classifications

```text
PASS
WARNING
BLOCKER
NOT APPLICABLE
REQUIRES VALIDATION
```

`PASS` means the expected condition was positively observed. `WARNING` is non-blocking attention. `BLOCKER` prevents safe acceptance. `NOT APPLICABLE` means a check legitimately does not apply. `REQUIRES VALIDATION` means available evidence or architecture is insufficient.

## 2.7.32 Acceptance Stop Conditions

BLOCKER examples:

- systemctl unavailable;
- PG_SERVICE unset;
- specified unit not found;
- service clearly failed;
- explicit PostgreSQL service identity is root;
- clearly incorrect PostgreSQL major-version executable.

REQUIRES VALIDATION examples:

- multiple candidate units;
- unexpected non-root service account;
- unknown ExecStart wrapper;
- ambiguous PGDATA;
- MainPID/postmaster.pid mismatch;
- unexpected unit customization;
- unexpected masked state;
- journal inaccessible;
- unexpected restart policy;
- activating/deactivating service.

The artifact reports these conditions and never repairs them.

## 2.7.34 Canonical Acceptance Prohibitions

The canonical acceptance artifact must never execute:

```text
sudo / su / runuser
systemctl start / stop / restart / reload / try-restart / reload-or-restart
systemctl enable / disable / reenable / preset / mask / unmask
systemctl daemon-reload / daemon-reexec / reset-failed
service lifecycle commands
pg_ctl lifecycle commands
direct postgres startup
kill / pkill / killall
unit/drop-in/environment-file mutation
postmaster.pid mutation
PostgreSQL configuration mutation
mount / umount / filesystem repair
package installation
credential collection
automatic remediation
```

## 2.7.35 Production Service Preflight

Before any later production service operation confirm:

```text
[ ] correct host and environment
[ ] explicit PG_SERVICE
[ ] unit loaded
[ ] correct PostgreSQL installation
[ ] service account validated
[ ] ExecStart/wrapper understood
[ ] PGDATA correlated where applicable
[ ] MainPID understood
[ ] PGDATA/WAL/tablespace storage available
[ ] port/readiness target known
[ ] application/replication/backup impact understood
[ ] shutdown behavior understood
[ ] startup/recovery behavior understood
[ ] maintenance authorization obtained where required
[ ] rollback/recovery path understood
```

## 2.7.36 Troubleshooting Decision Flow

```text
PostgreSQL service issue
→ confirm host/environment
→ confirm exact PG_SERVICE
→ inspect LoadState
→ inspect ActiveState/SubState
→ inspect effective unit
→ inspect MainPID/process
→ correlate PGDATA if explicitly known
→ preserve bounded journal evidence
→ optional pg_isready
→ diagnose
→ decide whether mutation is actually required
```

Immediate restart is deliberately excluded as the default response.
