# 2.2 — Linux Host Preparation and Prerequisites

**Part:** 2 — Installation & Production Configuration  
**Edition:** Revised Final / Canonical  
**Target:** PostgreSQL 18 on Linux  
**Lab classification:** `[TUTORIAL-ACCEPTANCE — SAFE-READ]`

## Introduction

Before installing PostgreSQL, validate the Linux host that will run it. Reliability depends on the operating system, CPU architecture, memory, swap behavior, storage, filesystem state, resource limits, networking, DNS, time synchronization, security controls, package management, and service management.

The production workflow is:

```text
Inspect → Understand → Classify → Document → Remediate separately when justified → Revalidate
```

The acceptance lab performs inspection only. Remediation is a separate operator-controlled activity.

## Learning Objectives

By the end of this section, you should be able to identify the Linux platform, inspect CPU and NUMA topology, memory and swap, storage and filesystems, network and DNS, time synchronization, OS identity, shell resource limits, service management, SELinux/AppArmor, firewall tooling, and package management; distinguish host readiness from PostgreSQL installation; and classify findings as `PASS`, `WARNING`, `BLOCKER`, `NOT APPLICABLE`, or `REQUIRES VALIDATION`.

## Readiness Classification

- **PASS** — inspected requirement satisfies the planned architecture.
- **WARNING** — does not prevent installation but needs review.
- **BLOCKER** — a requirement necessary for safe deployment is not satisfied.
- **NOT APPLICABLE** — the check does not apply to this host.
- **REQUIRES VALIDATION** — available evidence is insufficient for a conclusion.

Use `BLOCKER` carefully. Ordinary platform differences are not blockers.

## Operating System and Host Identity

Inspect:

```bash
cat /etc/os-release
uname -r
uname -m
hostname
hostnamectl
```

Record the distribution, release, kernel, architecture, hostname, and intended production identity. Package names, repositories, service names, security controls, and firewall tooling vary by distribution.

## CPU and NUMA

Inspect:

```bash
nproc
lscpu
```

Where available:

```bash
numactl --hardware
```

Record logical CPUs, sockets, cores, threads, architecture, and NUMA topology. This is inventory, not tuning. Do not automatically apply NUMA tuning merely because NUMA exists.

## Memory and Swap

Inspect:

```bash
free -h
grep -E 'MemTotal|MemAvailable|SwapTotal|SwapFree' /proc/meminfo
swapon --show
```

Record total and available RAM plus swap configuration and usage. Do not immediately convert total RAM into PostgreSQL settings; detailed memory configuration belongs in Part 2.8.

The presence of swap is not automatically a PostgreSQL failure, and this tutorial does not recommend blindly disabling swap.

## Storage and Filesystems

Inspect:

```bash
lsblk
lsblk -f
df -hT
df -i
findmnt
```

Where appropriate, inspect `/etc/fstab` read-only. Evaluate percentage used, absolute free capacity, expected growth, WAL activity, temporary files, maintenance operations, and operational headroom. Do not declare one filesystem universally correct for PostgreSQL.

The tutorial convention is `/pgdata/18/main`. At this stage, inspect the planned parent location only. If `/pgdata` does not exist, classify it as requiring preparation/validation rather than automatically failing the host.

## Network, DNS, and Time

Inspect:

```bash
hostname -f
ip addr
ip route
timedatectl
```

Where appropriate use `getent hosts` for name-resolution validation. If an FQDN cannot yet be resolved, use `REQUIRES VALIDATION` rather than automatically failing the server.

Time synchronization is part of the production host baseline because accurate timestamps matter for logging, monitoring, incident correlation, backup operations, authentication systems, and distributed applications. It is not presented as a PostgreSQL-enforced installation prerequisite.

## Operator and PostgreSQL OS Account

Inspect:

```bash
whoami
id
getent passwd postgres
```

`postgres` is the conventional service-account name in this tutorial, not a mandatory literal name. If it does not exist before package installation, do not automatically create it; the selected packaging/deployment workflow may create it. PostgreSQL must run under an appropriate unprivileged server owner, and `initdb` must not be run as root.

## Resource Limits

Inspect:

```bash
ulimit -a
ulimit -n
ulimit -u
```

These values describe the current shell execution context. They are useful evidence but are not proof of limits that will apply to PostgreSQL when launched by systemd.

```text
Administrator shell ulimit ≠ necessarily PostgreSQL systemd service limits
```

Actual service limits are validated after the service exists, primarily in Part 2.7.

Do not apply historical kernel tuning recipes automatically. Observe the environment, identify an actual PostgreSQL/platform requirement, compare it with current state, change only when justified, and revalidate. Detailed OS/kernel analysis belongs in Part 2.13.

## Service Management

Inspect:

```bash
ps -p 1 -o comm=
systemctl --version
```

Do not assume a PostgreSQL systemd unit name before installation. Package and distribution conventions vary.

## SELinux and AppArmor

Where available:

```bash
getenforce
sestatus
aa-status
```

SELinux `Enforcing` is not a PostgreSQL failure. AppArmor may be `NOT APPLICABLE` on platforms that do not use it. Security controls should be understood and integrated with PostgreSQL rather than disabled for convenience.

## Firewall Tooling

Detect applicable tooling:

```bash
command -v firewall-cmd
command -v nft
command -v ufw
```

Read-only firewall inspection may still require elevated privileges. If complete evidence is unavailable, report `REQUIRES VALIDATION`. The SAFE-READ lab does not invoke `sudo` automatically and does not modify firewall rules.

Do not expose TCP 5432 during this readiness stage. Network exposure is implemented later after authorized networks, `listen_addresses`, `pg_hba.conf`, TLS requirements, and authentication have been deliberately defined.

## Package Management and Software Supply

Detect:

```bash
command -v dnf
command -v yum
command -v apt
```

Do not install anything yet. Production installation may use an approved public repository, internal package mirror, artifact repository, offline repository, golden image, or controlled image pipeline. Public Internet access is not inherently required.

## Filesystem Ownership Planning

The PostgreSQL cluster directory must ultimately be controlled by the server owner, but this acceptance section does not perform `chown`, `chmod`, or recursive ownership changes. Storage creation, ownership, and permissions are handled deliberately in later sections.

## Host Preparation vs PostgreSQL Installation

Maintain the boundary:

```text
Part 2.2 — Linux host readiness
        ↓
Part 2.3 — Package-based PostgreSQL installation
        ↓
Part 2.5 — Database-cluster initialization
```

Host-readiness automation must not silently cross these boundaries.

## Hands-On Lab — Linux Host Readiness Assessment

**Classification:** `[TUTORIAL-ACCEPTANCE — SAFE-READ]`

Collect evidence for host identity, OS, kernel, architecture, CPU/NUMA, memory, swap, storage, filesystem capacity/inodes, planned PostgreSQL storage, network, DNS, time, security controls, shell resource limits, service management, package management, and PostgreSQL OS-account state.

Create the learner artifact:

```text
postgresql-host-readiness.txt
```

For each area record `Status`, `Evidence`, and `Notes`, then summarize:

```text
PASS:
WARNING:
BLOCKER:
NOT APPLICABLE:
REQUIRES VALIDATION:

Decision:
READY / NOT READY / READY WITH FOLLOW-UP
```

A missing optional diagnostic utility is not equivalent to a genuine deployment blocker. Potential real blockers include incompatible target architecture, inability to provision required storage, insufficient required production capacity, an unusable target filesystem, unresolved mandatory security requirements, an unapproved/unverifiable software source, or an unsatisfied organizational production prerequisite.

## Safety Boundary

The acceptance lab must not invoke `sudo`, install/remove packages, create users/groups, partition/format filesystems, change mounts, ownership, permissions, kernel parameters, swap, SELinux/AppArmor, firewall/network policy, services, install PostgreSQL, run `initdb`, or modify PostgreSQL configuration.

The canonical artifact `labs/host-readiness-check.sh` must remain SAFE-READ, detect available utilities, tolerate missing optional commands and permission-limited inspection, collect useful evidence, distinguish shell limits from service limits, and avoid remediation.

## Production Readiness Gate

Before advancing to package installation, confirm that the Linux distribution/release/kernel/architecture are identified; CPU, memory, swap, storage, filesystem and inode evidence is collected; PostgreSQL storage planning is documented; hostname/network/routes/DNS/time requirements are understood; operator and service-account strategy is understood; shell resource limits are inspected; service management and applicable security/firewall tooling are identified; the package/software-supply strategy is known; no unresolved `BLOCKER` remains; and warnings/validation items are tracked.

## Operational Takeaway

A production PostgreSQL server should begin with evidence rather than immediately running a package installation command. Understand the OS, CPU, memory, swap, storage, filesystem, network, DNS, time, security, resource limits, service management, package management, and operational ownership first. Then classify what is known, what needs follow-up, and what genuinely blocks deployment.
