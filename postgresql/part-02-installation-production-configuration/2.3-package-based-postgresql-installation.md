## Introduction

Part 2.1 designed the PostgreSQL server and Part 2.2 validated the Linux host. We can now install PostgreSQL 18 software.

A critical distinction must remain clear:

```text
PostgreSQL software installation != PostgreSQL database-cluster initialization
```

The deployment sequence is: validate the Linux host, select an approved PostgreSQL source, install PostgreSQL 18 packages, verify packages and binaries, inspect packaging side effects, perform controlled `initdb`, configure PostgreSQL, and only then start the validated production cluster.

This section covers package installation and post-installation verification. The intentionally managed production database cluster is initialized in Part 2.5.

## Learning Objectives

By the end of this section, you should be able to distinguish PostgreSQL software from a database cluster; identify approved software sources; distinguish distribution repositories from PGDG repositories; verify the intended PostgreSQL major version before installation; inspect package metadata and provenance; perform an approved PostgreSQL 18 package installation; locate and verify binaries; distinguish client and server packages; identify multiple PostgreSQL versions; discover systemd integration; detect packaging-created clusters and unexpected running processes; separate mutating installation from SAFE-READ acceptance; and produce a production installation record.

## Package Installation vs Cluster Initialization

Package installation places PostgreSQL software on the host. Depending on the package set this can include `postgres`, `psql`, `initdb`, `pg_ctl`, `pg_dump`, `pg_restore`, `pg_isready`, supporting libraries, systemd integration, documentation, and development components.

A package being installed does not mean the production database cluster has been intentionally initialized. `initdb` creates a PostgreSQL database cluster. Part 2.3 may inspect `initdb --version`, but it must not initialize the cluster.

Package administration may require elevated operating-system privileges. `initdb`, by contrast, must be executed as the PostgreSQL server owner rather than root. Do not confuse package-management privilege with PostgreSQL server ownership.

## Why Package-Based Installation?

Package-based deployment commonly provides repeatable installation, dependency management, software provenance, operating-system inventory, security-update integration, version tracking, standardized placement, service-management integration, controlled upgrade paths, and compatibility with infrastructure automation. Source installation remains valid for appropriate use cases and is covered in Part 2.4.

## Production Software-Supply Model

Before installing anything, establish the required PostgreSQL major version, repository, repository owner, exact packages, architecture, package version, and approval path. Only then should package installation occur.

A production environment may use Linux distribution repositories, PostgreSQL community repositories, internal enterprise mirrors, artifact repositories, offline repositories, golden images, or controlled machine-image pipelines. Direct Internet access from a database server is not inherently required.

## Distribution Repository vs PGDG

Linux distribution repositories and PostgreSQL Global Development Group (PGDG) repositories are not necessarily equivalent. They can differ in available PostgreSQL versions, package names, binary locations, service integration, cluster-management tooling, initialization behavior, upgrade tooling, and patch availability.

Therefore generic commands such as `dnf install postgresql` or `apt install postgresql` must never automatically be interpreted as "install PostgreSQL 18." Repository resolution must be understood first.

Our target is PostgreSQL 18. The required workflow is: confirm PostgreSQL 18 is required, select the approved repository, inspect package metadata, confirm version and architecture, approve installation, install, and independently verify the resulting binaries.

## Detect the Linux Packaging Model

Inspect `/etc/os-release`, then detect available package tools with `command -v dnf`, `yum`, `apt`, `rpm`, and `dpkg`. RHEL/Rocky/AlmaLinux commonly use DNF/RPM, while Debian/Ubuntu commonly use APT/DPKG. Exact repository and package behavior remains distribution-specific.

## Capture Pre-Installation State

Before modifying the host, record OS and architecture and inspect whether `postgres`, `psql`, `initdb`, and `pg_config` already exist. If found, inspect their versions. Also inspect package inventory, services, processes, and packaging-specific cluster state.

This prevents blind installation over an existing PostgreSQL deployment. Multiple major versions are not automatically wrong; they require validation because side-by-side installations can be legitimate during controlled upgrade workflows.

## Inspect Package Metadata First

Applicable read-only metadata inspection can include `dnf info <package>`, `dnf list --available <package>`, `apt-cache policy <package>`, or `apt-cache show <package>`. Verify package name, version, architecture, repository/source, and dependencies before approving installation.

## Repository Configuration and Installation Are Mutations

Repository configuration changes the software-supply and potentially trust configuration of the host. Adding PGDG repository definitions, repository configuration packages, signing/trust material, enabled repositories, or package modules is therefore `[TUTORIAL-OPERATOR-ACTION — MUTATING]`.

The actual package installation is also mutating. Conceptually it may use `sudo dnf install <approved-postgresql-18-packages>` or `sudo apt install <approved-postgresql-18-packages>`, but the exact command depends on the approved platform and repository. The SAFE-READ acceptance artifact never performs these operations.

## Production Change Gate

Before installation confirm the correct host and environment, Linux distribution and architecture, PostgreSQL 18 approval, repository provenance, exact package/version, existing PostgreSQL installations, side-by-side version impact, existing services/processes/clusters, change authorization, and a deployment-specific recovery plan.

Avoid broad host upgrades such as `dnf update -y` or `apt upgrade -y` as hidden PostgreSQL installation steps. These can modify unrelated software. For operator-driven changes, inspect the transaction and dependencies before approving execution. Controlled automation may use noninteractive operations when deliberately designed to do so.

## RHEL-Family Packaging

RHEL-family systems may obtain PostgreSQL from distribution repositories, the PGDG Yum repository, or an internal enterprise mirror. These sources must not be treated as interchangeable. Verify that the selected source explicitly provides PostgreSQL 18.

Conceptually install only the approved PostgreSQL 18 package set. After installation inspect RPM/DNF inventory and independently verify binaries. On documented Red Hat-family PostgreSQL package paths, package installation and database initialization can be separate operations, but this behavior must not be generalized to every Linux distribution or repository.

## Debian/Ubuntu Packaging

Debian/Ubuntu systems may use distribution repositories, the PGDG APT repository, or internal mirrors. With the approved PGDG APT repository, version-specific package naming includes `postgresql-18` and corresponding version-specific client/development packages where required. `sudo apt install postgresql-18` is therefore a valid conceptual PGDG example, not a universal command for every Debian/Ubuntu repository configuration.

Debian-family packaging can include additional PostgreSQL cluster-management conventions and tooling. Post-installation validation should therefore inspect packaging-specific cluster tooling when available rather than relying only on `ps` and `systemctl`.

## Automatic Cluster Initialization

Never infer cluster state from package installation alone. After installation inspect packages, binaries, services, processes, and clusters.

If installation created or started an unexpected cluster, classify the condition as `REQUIRES VALIDATION`. Do not automatically stop, disable, delete, reuse, or reconfigure it. First determine PostgreSQL version, cluster identity, PGDATA, owner, port, service, configuration, package origin, application usage, and organizational policy. Any remediation is a separate approved mutation.

## Verify PostgreSQL Binaries

Locate `postgres` with `command -v postgres` and inspect `postgres --version` when available. The required major version is PostgreSQL 18. If it is not in PATH, do not automatically modify PATH or create symlinks; use package inventory and packaging-specific locations.

Locate and inspect `psql`. Remember that `psql` is a client; its presence does not prove the server package is installed.

Locate `initdb` and inspect `initdb --version` when available, but do not run `initdb <directory>` in Part 2.3.

Where installed, inspect `pg_config --version`, `--bindir`, `--libdir`, and `--pkglibdir`. `pg_config` is useful supplementary evidence but is not complete inventory of every PostgreSQL installation. Missing `pg_config` is not automatically a blocker unless the deployment specifically requires the relevant package components.

Where available, supporting utilities such as `pg_ctl`, `pg_dump`, `pg_restore`, and `pg_isready` can provide additional version evidence.

## PATH Is Not Complete Inventory

`command -v postgres` answers which executable the current shell would resolve. It does not answer which PostgreSQL versions are installed. Complete inventory correlates package inventory, binary paths, binary versions, service discovery, and cluster discovery.

If multiple major versions are discovered, use `REQUIRES VALIDATION` until their purpose is understood. Do not automatically remove, relink, stop, or reconfigure any version.

## Discover systemd Integration and Processes

Where systemd exists, read-only discovery can use `systemctl list-unit-files | grep -i postgres` and `systemctl list-units --type=service --all | grep -i postgres`. Do not assume universal PostgreSQL unit names.

Inspect processes with `ps -ef | grep '[p]ostgres'`. If a PostgreSQL process exists unexpectedly, classify it as `REQUIRES VALIDATION` and determine version, cluster, PGDATA, port, owner, service, and packaging origin before continuing. Never terminate it automatically.

Do not start PostgreSQL merely to prove installation. Package validation can use inventory, binary/version inspection, service discovery, process discovery, and cluster discovery.

## Configuration and Network Boundary

Part 2.3 does not modify `postgresql.conf`, `pg_hba.conf`, PGDATA, `listen_addresses`, port, logging, WAL, or memory settings. It does not open TCP 5432. Remote access and security configuration belong to later controlled stages.

## Package Provenance and Recovery Planning

The installation record should identify what was installed, version, architecture, repository/mirror, host, environment, time, operator, and change authorization.

Do not define rollback universally as uninstalling PostgreSQL. Package removal can affect dependencies, configuration files, service definitions, package-created clusters, and future package resolution. Define recovery according to the deployment context before mutation.

## Hands-On Lab Architecture

The lab has three deliberately separated phases:

1. **Phase A — `[TUTORIAL-ACCEPTANCE — SAFE-READ]` precheck:** inspect OS, architecture, existing PostgreSQL commands, package inventory, services, processes, clusters, repository/source plan, and change authorization.
2. **Phase B — `[TUTORIAL-OPERATOR-ACTION — MUTATING]`:** perform only the approved PostgreSQL 18 repository/package installation. Record the exact repository configuration, package manager, requested packages, command, execution time, operator, change reference, and result. Do not mix `initdb`, configuration, service startup, or firewall changes into this step.
3. **Phase C — `[TUTORIAL-ACCEPTANCE — SAFE-READ]`:** inspect OS, architecture, package manager, installed PostgreSQL packages, `postgres`, `psql`, `initdb`, optional `pg_config`/supporting utilities, systemd units, PostgreSQL processes, packaging-specific cluster state, and multiple-version state.

## Installation Evidence Artifact

Create `postgresql-package-installation.txt` containing host/environment/change metadata; OS/distribution/architecture; repository owner, mirror and approval; pre-installation PostgreSQL packages/services/processes/clusters; exact installation command and result; post-installation package inventory; `postgres`, `psql`, `initdb`, and optional `pg_config` paths/versions; service/process/cluster discovery; multiple-version state; automatic-initialization state; overall classification; and notes.

## Acceptance Criteria

Before advancing, confirm the correct host/environment, OS and architecture, approved software source, PostgreSQL 18 package/version, successful package transaction, installed-package inventory, PostgreSQL 18 server binary or understood packaging-specific location, client/initdb versions, optional `pg_config` where applicable, multiple-version state, service/process/cluster discovery, automatic-initialization state, and installation evidence. No unreviewed cluster may be modified, no manual `initdb` executed, no service manipulated by the acceptance lab, no PostgreSQL configuration modified, and no firewall/network exposure introduced.

## Stop Conditions

Stop before Part 2.5 if the wrong PostgreSQL major version is installed; package provenance cannot be verified; an existing PostgreSQL installation is not understood; multiple versions exist for unknown reasons; an unexpected PostgreSQL process, service, or cluster exists; package installation has unresolved errors; or architecture does not match the approved deployment.

## Production Anti-Patterns

Avoid installing whichever version the default repository provides; assuming a package named `postgresql` means PostgreSQL 18; assuming distro and PGDG packages behave identically; treating `psql` as proof of the server version; treating PATH as complete inventory; automatically removing an older PostgreSQL version; automatically stopping a discovered process; automatically deleting a packaging-created cluster; installing packages and immediately running `initdb`; starting PostgreSQL merely to test package installation; opening TCP 5432; modifying `pg_hba.conf`; applying broad OS package upgrades as hidden prerequisites; or combining repository configuration, installation, `initdb`, PostgreSQL configuration, firewall changes, and startup into one uncontrolled script.

## Canonical SAFE-READ Artifact

The canonical acceptance artifact is `labs/postgres-install-check.sh`. It remains SAFE-READ: no sudo, repository/package/account/filesystem changes, `initdb`, cluster creation/deletion, service mutation, PostgreSQL configuration, firewall/network mutation, or PATH/symlink mutation. It detects OS/architecture/package tooling, inventories PostgreSQL packages, locates and versions binaries where possible, discovers services/processes/packaging-specific clusters, highlights possible multiple-version state, and tolerates unavailable optional utilities.
