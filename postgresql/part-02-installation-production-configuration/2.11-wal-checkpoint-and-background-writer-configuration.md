# Part 2.11 --- WAL, Checkpoint, and Background Writer Configuration

**Status:** Revised Final / Canonical Edition\
**Target:** PostgreSQL 18

## Objective

Build a production baseline for WAL generation, checkpoint behavior,
background writing, archiving, and recovery-related capacity without
weakening PostgreSQL durability.

## Safety Model

-   `[SAFE-READ]` --- inspect configuration/statistics.
-   `[PRODUCTION-CHANGE]` --- persistent parameter change.
-   `[PRODUCTION-CHANGE — RELOAD]` / `[PRODUCTION-CHANGE — RESTART]` ---
    use the setting's actual context.
-   Never disable durability controls merely to improve benchmark
    results.

## 1. WAL Is a Durability Boundary

PostgreSQL uses write-ahead logging so required WAL records reach
durable storage before corresponding data-file changes are considered
safely persisted.

Do not casually disable or weaken settings such as `fsync`,
`full_page_writes`, or synchronous commit policy. Any durability
trade-off must be explicit, workload-specific, and approved.

## 2. Inspect the Baseline

``` sql
-- [SAFE-READ]
SELECT name, setting, unit, context, source, pending_restart
FROM pg_settings
WHERE name IN (
  'wal_level',
  'wal_buffers',
  'wal_compression',
  'wal_sync_method',
  'synchronous_commit',
  'fsync',
  'full_page_writes',
  'checkpoint_timeout',
  'checkpoint_completion_target',
  'max_wal_size',
  'min_wal_size',
  'archive_mode',
  'max_wal_senders',
  'bgwriter_delay',
  'bgwriter_lru_maxpages',
  'bgwriter_lru_multiplier',
  'bgwriter_flush_after'
)
ORDER BY name;
```

## 3. Checkpoints

Checkpoint behavior affects recovery time and I/O distribution.
Important controls include:

``` text
checkpoint_timeout
checkpoint_completion_target
max_wal_size
min_wal_size
```

`max_wal_size` is a soft WAL growth target, not a filesystem capacity
limit. Plan enough disk headroom for workload spikes, archiving delays,
replication requirements, recovery, and maintenance.

## 4. Background Writer

The background writer attempts to make clean reusable buffers available
so backend processes are less likely to perform their own writes.

Relevant settings include:

``` text
bgwriter_delay
bgwriter_lru_maxpages
bgwriter_lru_multiplier
bgwriter_flush_after
```

Aggressive background writing can increase total I/O; insufficient
background writing can shift writes to backend processes. Tune only from
measured workload and storage evidence.

## 5. Observe Runtime Behavior

``` sql
-- [SAFE-READ]
SELECT * FROM pg_stat_checkpointer;

SELECT * FROM pg_stat_bgwriter;

SELECT * FROM pg_stat_wal;
```

Capture rates over time rather than interpreting a single cumulative
snapshot as a workload rate.

## 6. Archiving and Recovery

If point-in-time recovery or an archive-based design is required,
validate the complete pipeline:

``` text
WAL generated
 -> archive mechanism
 -> durable archive destination
 -> monitoring
 -> retention
 -> recovery procedure
 -> restore/PITR test
```

A configured archive command/library is not proof of recoverability.

Do not print archive commands into generic shared evidence because they
can contain sensitive implementation details.

## 7. Replication Capacity

Where streaming replication is used, review:

``` text
wal_level
max_wal_senders
replication slots
WAL retention
standby lag
network capacity
storage capacity
failure/rebuild procedure
```

Replication slots can retain WAL. Monitor slot state and storage
consequences.

## 8. Production Investigation Pattern

When checkpoint/WAL I/O is suspected:

1.  capture storage latency/IOPS/throughput;
2.  inspect checkpoint statistics;
3.  inspect WAL generation rate;
4.  review checkpoint frequency and causes;
5.  inspect archiving/replication retention;
6.  correlate with workload and maintenance;
7.  change one justified variable at a time;
8.  compare before/after evidence.

## 9. Production Checklist

``` text
[ ] durability settings reviewed
[ ] checkpoint behavior measured
[ ] WAL generation measured
[ ] filesystem headroom reviewed
[ ] background-writer behavior reviewed
[ ] archive health monitored if used
[ ] replication retention reviewed if used
[ ] recovery procedure documented
[ ] restore/PITR tested where required
[ ] rollback values captured before tuning
```
