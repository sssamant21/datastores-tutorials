# Part 2.13 — Connection Management, Limits, and Timeouts

**Status:** Revised Final / Canonical Edition  
**Target:** PostgreSQL 18  
**Audience:** PostgreSQL administrators, SREs, DBREs, platform engineers, developers, and application engineers.

## Objectives

After completing this tutorial, you should be able to:

- explain PostgreSQL's client-connection/backend model;
- understand `max_connections` as a capacity ceiling rather than a throughput target;
- understand PostgreSQL 18 ordinary, reserved, and superuser-reserved connection capacity;
- understand the purpose of `pg_use_reserved_connections`;
- build an application connection budget;
- model replica, pool, autoscaling, deployment, and reconnect multiplication;
- distinguish connected sessions from active database concurrency;
- recognize connection leaks, connection storms, and retry amplification;
- understand application and external connection pooling;
- understand session-pooling and transaction-pooling boundaries;
- inspect client sessions safely with `pg_stat_activity`;
- identify `idle` and `idle in transaction` sessions;
- understand authentication, statement, lock, transaction, and idle-session timeouts;
- understand `client_connection_check_interval` and TCP keepalive controls;
- diagnose connection saturation without immediately raising `max_connections`;
- build NORMAL, PEAK, DEPLOYMENT, and FAILURE capacity scenarios;
- apply production connection and timeout changes through controlled change gates.

## 2. Connection Capacity Is Not `max_connections` Alone

The central production rule is:

```text
connection capacity
      !=
max_connections alone
```

A useful production model is:

```text
PostgreSQL connection ceiling
-
reserved operational capacity
-
administrative/monitoring allowance
-
background/ETL allowance
-
safety headroom
=
application connection budget
```

Application teams should consume deliberately allocated connection budgets rather than independently selecting arbitrary pool sizes.

---

## 3. PostgreSQL Client Connection Model

Conceptually:

```text
application/client
       |
       v
TCP/Unix socket
       |
       v
authentication
       |
       v
PostgreSQL client backend/session
       |
       v
SQL execution
```

A connection consumes server resources even when it is not actively executing SQL.

Therefore:

```text
connected sessions
        !=
active query concurrency
```

## 4. Inspect Current Client Sessions

```sql
-- [SAFE-READ]
SELECT
    state,
    COUNT(*) AS sessions
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY state
ORDER BY state;
```

PostgreSQL 18 activity states include:

```text
active
idle
idle in transaction
idle in transaction (aborted)
fastpath function call
disabled
```

A current snapshot is useful for diagnosis, but historical peaks are required for capacity planning.

---

## 5. Inspect Connections by Database and Application

By database:

```sql
-- [SAFE-READ]
SELECT
    datname,
    COUNT(*) AS sessions
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY datname
ORDER BY sessions DESC, datname;
```

By application and state:

```sql
-- [SAFE-READ]
SELECT
    application_name,
    state,
    COUNT(*) AS sessions
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY application_name, state
ORDER BY application_name, state;
```

Use meaningful service identifiers such as:

```text
claims-api
member-search
etl-loader
reporting-service
```

Do not place passwords, tokens, PII, PHI, customer identifiers, or request payloads in `application_name`.

## 6. `max_connections`

```sql
SHOW max_connections;
```

`max_connections` defines the configured client-connection ceiling subject to PostgreSQL's reserved-slot rules.

It is not a performance target.

Do not assume:

```text
more connections
      =
more throughput
```

More connections can create:

```text
more backend overhead
more memory exposure
more runnable processes
more simultaneous SQL
more lock contention
more CPU pressure
more storage pressure
```

A persistent increase should be classified as:

```text
[PRODUCTION-CHANGE — CAPACITY / RESTART RISK]
```

Review Part 2.12 memory capacity before raising it.

## 7. PostgreSQL 18 Reserved Connection Architecture

Inspect:

```sql
SELECT
    name,
    setting,
    unit,
    context,
    source,
    pending_restart
FROM pg_settings
WHERE name IN (
    'max_connections',
    'reserved_connections',
    'superuser_reserved_connections'
)
ORDER BY name;
```

Conceptually PostgreSQL protects connection capacity in tiers:

```text
+------------------------------------------------------+
|                 max_connections                      |
|                                                      |
|  ordinary connection capacity                       |
|                                                      |
|  +-----------------------------------------------+   |
|  | reserved_connections                          |   |
|  | operational privileged reserve                |   |
|  |                                               |   |
|  | +-----------------------------------------+   |   |
|  | | superuser_reserved_connections          |   |   |
|  | | final superuser emergency reserve       |   |   |
|  | +-----------------------------------------+   |   |
|  +-----------------------------------------------+   |
+------------------------------------------------------+
```

Normal application roles should use ordinary capacity.

Roles granted the predefined role:

```text
pg_use_reserved_connections
```

can use the `reserved_connections` reserve when ordinary slots are exhausted.

The final `superuser_reserved_connections` capacity remains for superuser access.

Operational model:

```text
application role
    -> ordinary slots

DBRE/SRE operational role
+ pg_use_reserved_connections
    -> ordinary + reserved operational slots

superuser
    -> final emergency reserve as well
```

Do not grant reserved-slot access to ordinary applications merely to avoid connection-limit errors.

---

## 8. Reserved Capacity Is Incident Capacity

Reserved connections should provide an administrative recovery path during saturation.

They are not:

```text
extra application pool capacity
```

If normal applications routinely need reserved slots, the underlying connection-capacity problem has not been solved.

## 9. Application Pool Multiplication

Suppose:

```text
10 replicas
×
20 connections/replica
=
200 potential application connections
```

Now add:

```text
background workers
scheduled jobs
ETL
reporting
monitoring
administrative sessions
```

The database demand is larger than the pool size of any one application instance.

---

## 10. Multiple Services

Example:

```text
orders-api
10 replicas × 20 = 200

claims-api
8 replicas × 20 = 160

reporting
5 replicas × 10 = 50
```

Potential application-side pool capacity:

```text
200 + 160 + 50
= 410
```

This is a capacity-exposure scenario, not a claim that all 410 connections are simultaneously active.

---

## 11. Kubernetes Autoscaling

Suppose:

```text
minimum replicas = 5
maximum replicas = 30
pool maximum = 20
```

The topology permits:

```text
30 × 20
= 600 potential pooled connections
```

Do not size PostgreSQL only for the five replicas currently running.

For capacity review, use the maximum permitted topology.

---

## 12. Rolling Deployment Multiplication

A rolling deployment can temporarily create:

```text
old replicas
+
new/surge replicas
```

Therefore:

```text
steady-state replicas
      !=
deployment-time connection producers
```

Review the deployment strategy, including replica count and surge behavior, together with the pool maximum.

---

## 13. Reconnect and Failover Storms

Connections can surge during:

```text
database failover
database restart
network recovery
application restart
node replacement
pool recreation
```

Conceptually:

```text
database becomes reachable
          |
          v
many application processes reconnect
          |
          v
authentication + backend creation surge
          |
          v
queries resume simultaneously
```

Connection **establishment rate** can therefore matter in addition to steady-state connection count.

Applications should use bounded retry behavior, backoff, and jitter appropriate to their architecture.

---

## 14. NORMAL / PEAK / DEPLOYMENT / FAILURE

Production connection planning should model:

```text
NORMAL
    ordinary business workload

PEAK
    expected maximum workload

DEPLOYMENT
    old/new replicas overlap
    autoscaling/surge behavior

FAILURE
    failover
    restart
    network recovery
    reconnect storm
    retry amplification
```

A configuration that survives only NORMAL conditions has weak operational headroom.

---

## 15. Formal Application Connection Budget

Example:

```text
safe application budget = 400

orders-api        120
claims-api        100
member-api         80
reporting          40
batch/ETL          30
unallocated         30
---------------------
total              400
```

The numbers are environment-specific.

The important model is:

```text
database capacity
       |
       v
service connection budgets
       |
       v
pool configuration
       |
       v
replica/HPA limits
```

Do not allocate every ordinary PostgreSQL slot to application pool maxima. Preserve headroom.

## 16. Pool Ownership

For each production pool, record:

```text
service
owner
database
minimum replicas
maximum replicas
pool minimum
pool maximum
pool acquisition/connection timeout
idle timeout
connection lifetime
retry policy
backoff policy
```

This turns a database connection problem into an attributable capacity model.

---

## 17. Pool Size Is Not Active Concurrency

Example:

```text
pool maximum = 50
```

does not mean:

```text
50 SQL statements are always executing
```

Monitor separately:

```text
application pool size
pool utilization
PostgreSQL connected sessions
PostgreSQL active sessions
database CPU
database memory
storage pressure
```

A bounded pool can provide useful backpressure. An oversized pool can simply move the application queue into PostgreSQL.

---

## 18. External Pooling

Conceptually:

```text
applications
      |
      v
application pools
      |
      v
optional external pooler
      |
      v
PostgreSQL backends
```

An external pooler such as PgBouncer can reduce the number of server backends required for a larger client population.

Pooling mode changes semantics, so application compatibility must be reviewed.

---

## 19. Session Pooling

Conceptually:

```text
client session
      |
      v
server connection retained
for the client session
```

This preserves more session-level behavior but provides less aggressive multiplexing.

---

## 20. Transaction Pooling

Conceptually:

```text
client
   |
transaction
   |
borrow PostgreSQL connection
   |
COMMIT / ROLLBACK
   |
return connection
```

The next transaction may execute on a different PostgreSQL backend.

Review application dependencies on session state, including applicable use of:

```text
session-level SET
temporary objects
prepared-statement behavior
LISTEN/NOTIFY
session-level advisory locks
other backend-local/session-local state
```

Exact PgBouncer compatibility depends on its current version and configuration; validate pooler-specific behavior against PgBouncer documentation rather than applying blanket rules.

---

## 21. Connection Storm Feedback Loop

A production failure can become self-amplifying:

```text
database slows
      |
queries remain busy longer
      |
pool saturates
      |
requests wait/fail
      |
clients retry
      |
connection/query demand increases
      |
database slows further
```

The database cannot solve retry amplification by itself.

Application-side failure containment can include:

```text
bounded retries
backoff
jitter
request timeout
connection timeout
load shedding/circuit control where appropriate
```

---

## 22. Timeout Lifecycle

Timeouts solve different lifecycle problems:

```text
network connection
       |
       v
authentication
       |
       | authentication_timeout
       v
session established
       |
       +--> active statement
       |       |
       |       +--> statement_timeout
       |       +--> lock_timeout
       |
       +--> transaction lifetime
       |       |
       |       +--> transaction_timeout
       |
       +--> idle in transaction
       |       |
       |       +--> idle_in_transaction_session_timeout
       |
       +--> idle outside transaction
               |
               +--> idle_session_timeout
```

Do not configure these independently.

---

## 23. `authentication_timeout`

```sql
SHOW authentication_timeout;
```

This limits how long authentication may take to complete.

It protects the connection-establishment/authentication phase and should not be confused with SQL execution timeouts.

---

## 24. `statement_timeout`

```sql
SHOW statement_timeout;
```

This limits statement duration.

Conceptually:

```text
statement begins
      |
execution exceeds configured threshold
      |
statement canceled
```

A timeout is a workload-control mechanism, not a substitute for query optimization.

A broad global timeout can unexpectedly affect:

```text
ETL
reporting
schema migrations
maintenance
batch processing
administrative operations
```

Prefer the smallest appropriate configuration scope.

---

## 25. `lock_timeout`

```sql
SHOW lock_timeout;
```

`lock_timeout` applies while a statement is waiting to acquire an applicable lock.

```text
statement_timeout
    -> overall statement duration

lock_timeout
    -> applicable lock acquisition wait
```

Design the two values together.

A shorter nonzero `statement_timeout` can fire before a longer `lock_timeout` becomes useful.

---

## 26. `transaction_timeout`

```sql
SHOW transaction_timeout;
```

`transaction_timeout` limits transaction lifetime.

Conceptually:

```text
transaction begins
      |
statements + waits + idle periods
      |
transaction lifetime reaches threshold
      |
timeout action
```

Design it together with:

```text
statement_timeout
idle_in_transaction_session_timeout
```

Do not impose a broad transaction lifetime without measuring legitimate transaction behavior.

---

## 27. `idle_in_transaction_session_timeout`

```sql
SHOW idle_in_transaction_session_timeout;
```

An idle session outside a transaction and an idle session inside a transaction have very different operational consequences.

Example:

```sql
BEGIN;

SELECT ...;

-- client stops sending SQL
-- transaction remains open
```

Potential consequences include:

```text
locks retained
old transaction snapshot retained
vacuum cleanup affected
table bloat pressure
connection remains occupied
```

This state deserves high operational attention.

---

## 28. Detect Idle Transactions Safely

```sql
SELECT
    pid,
    usename,
    datname,
    application_name,
    state,
    xact_start,
    state_change,
    wait_event_type,
    wait_event
FROM pg_stat_activity
WHERE backend_type = 'client backend'
  AND state LIKE 'idle in transaction%'
ORDER BY xact_start NULLS LAST;
```

Do not automatically terminate a session merely because it is idle in transaction.

First determine:

```text
application owner
transaction age
locks held
business operation
production impact
termination consequence
```

Backend cancellation/termination belongs in an incident-response runbook.

---

## 29. `idle_session_timeout`

```sql
SHOW idle_session_timeout;
```

This targets sessions idle outside a transaction.

It solves a different problem from idle-in-transaction protection.

Connection poolers and middleware may not react well when server-side idle sessions are unexpectedly closed.

Before enabling an aggressive value, test:

```text
pool health checks
connection validation
reconnect behavior
application error handling
```

---

## 30. End-to-End Timeout Budget

Production systems often include:

```text
business request budget
application request timeout
pool acquisition timeout
database statement timeout
lock timeout
transaction timeout
proxy/load-balancer timeout
service-mesh timeout
retry policy
```

Avoid situations such as:

```text
caller gives up after 5 seconds
        |
database continues expensive work
for much longer
```

unless that behavior is explicitly required.

There is no universal timeout number; design the hierarchy around workload semantics.

---

## 31. `client_connection_check_interval`

```sql
SHOW client_connection_check_interval;
```

This can help PostgreSQL detect a disappeared client while executing a long-running query on platforms where the required kernel socket events are supported.

It does not replace TCP keepalive.

```text
client_connection_check_interval
    -> applicable socket checking during execution

TCP keepalive
    -> kernel TCP peer-failure detection
```

Platform support must be verified.

---

## 32. TCP Keepalive Controls

Inspect:

```sql
SELECT
    name,
    setting,
    unit,
    context,
    source
FROM pg_settings
WHERE name IN (
    'tcp_keepalives_idle',
    'tcp_keepalives_interval',
    'tcp_keepalives_count',
    'tcp_user_timeout'
)
ORDER BY name;
```

These settings participate in network-failure detection.

For applicable PostgreSQL TCP parameters, zero commonly means use the operating-system default rather than simply "disabled".

OS support and effective values must be verified.

These settings are irrelevant to Unix-domain socket connections.

---

## 33. Safe Active-Session Inspection

```sql
SELECT
    pid,
    usename,
    datname,
    application_name,
    state,
    query_start,
    now() - query_start AS runtime,
    wait_event_type,
    wait_event
FROM pg_stat_activity
WHERE backend_type = 'client backend'
  AND state = 'active'
  AND pid <> pg_backend_pid()
ORDER BY query_start;
```

The basic tutorial intentionally excludes `query`.

SQL text can contain sensitive application data or literals.

Use metadata-first diagnosis and inspect query text only when necessary and appropriately authorized.

## 34. Wait Events

A non-null wait event does not automatically mean lock contention.

Use:

```text
wait_event_type
wait_event
```

to determine the actual wait category.

Connection saturation can be a symptom of:

```text
slow SQL
lock contention
CPU saturation
storage latency
memory pressure
network problems
downstream application behavior
```

## 36. Do Not Immediately Raise `max_connections`

Connection exhaustion can result from:

```text
connection leak
oversized pools
autoscaling
deployment overlap
reconnect storm
retry amplification
excess idle connections
idle-in-transaction sessions
slow queries
blocking
resource saturation
missing/incorrect pooling
```

Increasing `max_connections` can transform a controlled connection rejection into:

```text
OOM
CPU saturation
lock contention
storage saturation
```

Find the source of demand first.

## 38. Controlled Statement-Timeout Lab

Inspect the starting value:

```sql
SHOW statement_timeout;
```

Then:

```sql
-- [LAB-ONLY — EXPECTED CANCELLATION]
SET statement_timeout = '2s';

SELECT pg_sleep(3);
```

The `SELECT` should be canceled when the configured statement timeout is reached.

Immediately restore:

```sql
RESET statement_timeout;
```

If the client enters an unexpected state, restore or reconnect before continuing.

This intentional cancellation is never part of the acceptance artifact.

## 39. Two-Session Lock Lab

Create a disposable table:

```sql
CREATE SCHEMA connection_lab;

CREATE TABLE connection_lab.lock_test (
    id integer PRIMARY KEY,
    value text NOT NULL
);

INSERT INTO connection_lab.lock_test
VALUES (1, 'original');
```

### Session A

```sql
SET application_name = 'part-2.13-lock-lab-a';

BEGIN;

UPDATE connection_lab.lock_test
SET value = 'session-a'
WHERE id = 1;
```

Keep Session A open temporarily.

### Session B

```sql
SET application_name = 'part-2.13-lock-lab-b';

SET lock_timeout = '2s';

UPDATE connection_lab.lock_test
SET value = 'session-b'
WHERE id = 1;
```

Session B should encounter the configured lock-wait timeout while Session A retains the conflicting row lock.

Restore Session B:

```sql
RESET lock_timeout;
RESET application_name;
```

Return to Session A:

```sql
ROLLBACK;
RESET application_name;
```

This is:

```text
[LAB-ONLY — TWO-SESSION LOCKING EXERCISE]
```

Never perform this exercise against an arbitrary production table.

## 41. Lab Cleanup

In every lab session, ensure there is no open transaction and restore session-local settings:

```sql
RESET statement_timeout;
RESET lock_timeout;
RESET application_name;
```

Close extra lab sessions normally.

Reconnect:

```text
\c postgres
```

Then:

```sql
DROP DATABASE connection_lab;
```

If active connections remain, identify your own lab sessions and close them normally.

Do not terminate unrelated sessions.
