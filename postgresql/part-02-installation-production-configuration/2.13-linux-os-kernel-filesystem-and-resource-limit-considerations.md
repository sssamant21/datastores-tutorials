# Part 2.13 --- Linux OS, Kernel, Filesystem, and Resource-Limit Considerations

**Status:** Revised Final / Canonical Edition\
**Target:** PostgreSQL 18

## Objective

Validate the Linux and filesystem dependencies that PostgreSQL SQL
configuration alone cannot prove.

## Safety Model

The companion lab is `[TUTORIAL-ACCEPTANCE — SAFE-READ]` /
`[HOST-READ]`.

Kernel, mount, filesystem, systemd, user-limit, swap, huge-page,
ownership, or permission changes are production changes and are
intentionally excluded from the lab.

## 1. PostgreSQL Depends on the Host

A healthy PostgreSQL configuration can still fail because of:

``` text
memory pressure
CPU starvation
open-file limits
process limits
filesystem exhaustion
inode exhaustion
storage latency
mount failure
OOM behavior
time problems
IPC/systemd behavior
container/cgroup limits
```

Treat the host as part of the database architecture.

## 2. CPU and Memory

Inspect actual resources available to the PostgreSQL runtime, not only
physical host totals.

``` bash
# [HOST-READ]
nproc
free -h
```

For containers or systemd-managed services, also review cgroup/service
constraints because they can differ from host capacity.

Avoid universal prescriptions for swap or kernel values. The correct
policy depends on workload, memory model, operating system,
virtualization/container design, and organizational standards.

## 3. Resource Limits

PostgreSQL can be affected by limits on:

``` text
processes/tasks
open files
memory
locked memory
service-specific limits
system-wide file handles
socket backlog
```

Read-only shell checks:

``` bash
ulimit -n
ulimit -u
```

For a systemd service, inspect the effective service unit rather than
assuming an interactive shell's limits are identical to PostgreSQL's
limits.

## 4. Linux IPC and systemd

PostgreSQL uses operating-system IPC facilities. On systemd systems,
PostgreSQL's documentation specifically calls out `RemoveIPC`
considerations for the PostgreSQL operating-system account.

Do not blindly change `logind.conf`. First validate how the service
account was created and the platform's packaging guidance.

## 5. Huge Pages and Memory Overcommit

Huge pages and Linux memory-overcommit behavior can affect PostgreSQL
startup and memory behavior.

These settings are host-level controls. Evaluate them together with:

``` text
shared_buffers
connection count
parallelism
other services
container limits
HA/failover capacity
```

Do not copy sysctl values from an unrelated server.

## 6. Filesystem Capacity

Check both blocks and inodes:

``` bash
# [HOST-READ]
df -h
df -i
```

Monitor separately:

``` text
PGDATA
pg_wal
tablespaces
log filesystem
backup staging areas
temporary/spill locations
```

Do not treat `df` utilization alone as storage health; latency,
throughput, IOPS, queueing, burst limits, and growth rate also matter.

## 7. Mount Persistence and Identity

For self-managed servers, verify that database storage is the intended
persistent filesystem before PostgreSQL starts.

A missing mount can be dangerous if the mount point still exists as an
ordinary directory on the root filesystem.

Record:

``` text
device/volume identity
mount point
filesystem type
mount options
persistent mount configuration
capacity
monitoring
ownership
```

## 8. Ownership and Permissions

The PostgreSQL operating-system account must have appropriate access to
its storage and configuration.

Do not recursively `chown` or `chmod` PostgreSQL directories as a
generic remediation. First understand tablespaces, symlinks, packaging,
backup agents, TLS keys, and the intended security model.

## 9. Time and DNS

Reliable time and name resolution are operational dependencies for:

``` text
logs/correlation
TLS validation
monitoring
distributed systems
backup/automation
incident investigation
```

Use the platform's approved time synchronization and DNS architecture.

## 10. OOM and Capacity Failure

When PostgreSQL is killed by the operating system or container runtime,
investigate the complete memory envelope:

``` text
shared memory
backend/session memory
parallel workers
maintenance/autovacuum
extensions
OS cache
other agents/processes
cgroup/service limits
```

Do not respond only by increasing a memory limit without identifying the
workload/capacity cause.

## 11. Managed Services

RDS/Aurora, Azure Database for PostgreSQL, Cloud SQL, and similar
services hide or manage much of the underlying OS.

In those environments, translate this chapter into provider-visible
controls:

``` text
instance/vCPU/memory class
storage capacity/performance
parameter groups/configuration
maintenance
monitoring
network
backup
HA
provider limits
```

Do not claim host-level validation when the provider does not expose the
host.

## 12. Production Checklist

``` text
[ ] effective CPU/memory limits known
[ ] open-file/process limits reviewed
[ ] systemd/service limits reviewed
[ ] IPC/systemd behavior reviewed
[ ] huge-page/overcommit policy reviewed
[ ] PGDATA/WAL/tablespace mounts verified
[ ] capacity and inode headroom monitored
[ ] storage performance monitored
[ ] ownership/permissions reviewed
[ ] time/DNS dependencies validated
[ ] OOM/cgroup behavior understood
[ ] managed-service boundaries documented where applicable
```

## Lab

Run:

``` bash
labs/os-baseline-check.sh
```

The script is inspection-only. It does not execute `sysctl -w`, change
limits, edit systemd units, mount filesystems, alter swap, or change
permissions.
