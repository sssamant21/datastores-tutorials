# Part 2.11 — Logging and Error Reporting Configuration

**Status:** Revised Final / Canonical Edition  
**Target:** PostgreSQL 18  
**Audience:** PostgreSQL administrators, SREs, DBREs, platform engineers, and application engineers.

## Objectives

After completing this tutorial, you should be able to:

- explain PostgreSQL server logging architecture;
- inspect effective logging configuration safely;
- understand `log_destination` and `logging_collector`;
- use structured logging concepts such as `csvlog` and `jsonlog`;
- design useful `log_line_prefix` metadata;
- understand PostgreSQL 18 granular `log_connections`;
- distinguish statement, duration, sampled, and transaction logging;
- understand error and bind-parameter logging risks;
- use lock, checkpoint, autovacuum, temporary-file, and recovery-conflict logging appropriately;
- understand rotation versus retention;
- recognize logging collector, disk, privacy, and centralized-ingestion risks;
- use a bounded production logging change/rollback process;
- distinguish self-managed from managed-service logging.

## Safety Classes

```text
[SAFE-READ]
    Read-only PostgreSQL inspection.

[SAFE-READ — OPERATIONALLY SENSITIVE OUTPUT]
    Read-only output that can reveal infrastructure or security details.

[SESSION-LOCAL]
    Changes only the current session and is restored afterward.

[LAB-ONLY]
    Changes disposable lab objects only.

[PRODUCTION-CHANGE]
    Persistent logging/configuration change requiring review.

[PRODUCTION-CHANGE — HIGH VOLUME / DATA EXPOSURE RISK]
    Can materially increase logging, storage, cost, or sensitive-data exposure.
```

The companion acceptance artifact is strictly read-only.

## Why Logging Matters

PostgreSQL logs help answer:

```text
Why did PostgreSQL restart?
Why did authentication fail?
Why was a statement canceled?
Which statements are slow?
Are clients repeatedly reconnecting?
Are sessions blocked?
Is autovacuum struggling?
Are queries spilling to temporary files?
What happened around a checkpoint?
Are recovery conflicts occurring?
```

Production logging requires balance:

```text
too little
   -> insufficient incident evidence

too much
   -> I/O + disk + collector pressure + cost
      + sensitive-data exposure + excessive noise
```

Logs must be treated as potentially sensitive production data.

---

## Logging Architecture

```text
PostgreSQL process
       |
       v
server message / error
       |
       v
logging subsystem
       |
       +--> stderr
       +--> csvlog
       +--> jsonlog
       +--> syslog
       +--> eventlog (platform dependent)
```

With the collector:

```text
server processes
      |
      v
logging collector
      |
      v
PostgreSQL-managed log files
      |
      v
optional agent / centralized logging platform
```

Extremely high logging rates can create collector/output pressure. Logging itself can therefore affect database performance.

```sql
SELECT
    name,
    setting,
    unit,
    context,
    source,
    pending_restart
FROM pg_settings
WHERE name IN (
    'log_destination',
    'logging_collector',
    'log_directory',
    'log_filename',
    'log_file_mode',
    'log_rotation_age',
    'log_rotation_size',
    'log_truncate_on_rotation',
    'log_min_messages',
    'log_min_error_statement',
    'log_min_duration_statement',
    'log_min_duration_sample',
    'log_statement',
    'log_duration',
    'log_connections',
    'log_disconnections',
    'log_error_verbosity',
    'log_line_prefix',
    'log_lock_waits',
    'log_lock_failures',
    'deadlock_timeout',
    'log_temp_files',
    'log_autovacuum_min_duration',
    'log_checkpoints',

    'log_parameter_max_length',
    'log_parameter_max_length_on_error',

    'log_transaction_sample_rate'

```

Use `context` rather than memorizing which parameters require session change, reload, or restart. `pending_restart` shows whether a changed value is waiting for restart.

`sourcefile` and `sourceline` can be useful for privileged troubleshooting but can expose filesystem/configuration layout, so they are excluded from the standard acceptance artifact.

## Log Destinations

```sql
SHOW log_destination;
```

PostgreSQL 18 supports destinations including:

```text
stderr
csvlog
jsonlog
syslog
eventlog (Windows)
```

Multiple destinations can be configured where appropriate.

Structured formats such as CSV and JSON can simplify downstream parsing, but format choice should match the logging pipeline rather than being treated as universally superior.

---

## `logging_collector`

```sql
SHOW logging_collector;
```

The logging collector captures supported server output and writes PostgreSQL-managed log files. It is required for PostgreSQL-managed `csvlog` and `jsonlog` output.

It is a server-start setting. Check:

```sql
SELECT name, setting, context, source, pending_restart
FROM pg_settings
WHERE name = 'logging_collector';
```

Do not enable or disable it casually in production.

Very high logging volume can create collector/output pressure and potentially affect server processes.

## Log Directory, Filename, and Permissions

```sql
SHOW log_directory;
SHOW log_filename;
SHOW log_file_mode;
```

These values can expose infrastructure details.

Logs can contain:

```text
database/user names
application names
client information
SQL text
bind parameters
object names
errors
filesystem details
```

Restrict access appropriately.

Managed services may not provide direct filesystem access.

## Rotation Is Not Retention

Inspect:

```sql
SHOW log_rotation_age;
SHOW log_rotation_size;
SHOW log_truncate_on_rotation;
```

Remember:

```text
rotation
    -> when PostgreSQL begins another log file

retention
    -> how long historical logs remain
```

A production design needs both rotation and a retention/capacity policy.

Never use indiscriminate filesystem deletion as a normal logging-management strategy.

---

## `log_line_prefix`

```sql
SHOW log_line_prefix;
```

A useful text prefix can include metadata for correlation, for example:

```text
timestamp
PID/session
user
database
application_name
client
```

PostgreSQL uses `%` escapes. `%q` can terminate the prefix for non-session processes when later fields are meaningful only for session backends.

PostgreSQL 18 adds `%L` for client IP address.

Do not add every available field merely because it exists. Use the minimum metadata needed for operational correlation.

---

## `application_name`

Meaningful values such as:

```text
orders-api
claims-etl
reporting-service
```

are more useful than generic identifiers such as `app` or `python`.

Never place credentials, tokens, PII, PHI, or other secrets into `application_name`.

Hands-on lab:

```sql
-- [SESSION-LOCAL]
SET application_name = 'part-2.11-logging-lab';

SELECT pid, application_name, state
FROM pg_stat_activity
WHERE pid = pg_backend_pid();

RESET application_name;
```

## PostgreSQL 18 `log_connections`

PostgreSQL 18 provides granular connection-stage logging rather than only the older boolean-style behavior.

Connection aspects include:

```text
receipt
authentication
authorization
setup_durations
```

and `all` can select all supported connection aspects.

`setup_durations` is particularly useful for separating connection-establishment costs such as backend creation, authentication, and overall setup.

Use connection logging for a bounded diagnostic question:

```text
connection problem
      |
      v
enable/choose only useful stages
      |
      v
bounded diagnostic window
      |
      v
collect evidence
      |
      v
restore baseline
```

High connection rates can create high log volume.

Also, duplicate connection messages do not automatically prove an application reconnect storm; some clients can make multiple attempts during authentication discovery.

---

## `log_disconnections`

```sql
SHOW log_disconnections;
```

This can record session termination and duration information.

Do not assume it can be freely toggled after a session is already established; follow `pg_settings.context` and PostgreSQL 18 semantics when planning a change.

## Error Severity

```sql
SHOW log_min_messages;
```

PostgreSQL logging uses PostgreSQL's defined severity ordering, including levels such as:

```text
DEBUG5 ... DEBUG1
INFO
NOTICE
WARNING
ERROR
LOG
FATAL
PANIC
```

Do not map this mechanically to another logging framework's severity ordering.

Lower thresholds can substantially increase log volume.

---

## Error Statement Logging

```sql
SHOW log_min_error_statement;
```

This controls when the SQL statement associated with an error is included in server logging.

Statements may contain sensitive literals.

```text
error logging
      |
      v
SQL text may be retained
      |
      v
security/privacy/retention implications
```

---

## `log_statement`

```sql
SHOW log_statement;
```

Supported policies include:

```text
none
ddl
mod
all
```

`log_statement=all` is not a generic production troubleshooting default.

Classify broad production statement logging as:

```text
[PRODUCTION-CHANGE — HIGH VOLUME / DATA EXPOSURE RISK]
```

Statement logging can expose SQL and, in applicable protocol/logging cases, bind parameter values.

Parameterized SQL does not guarantee that parameter values can never appear in PostgreSQL logs.

Errors that occur before statement classification/logging can instead be captured according to `log_min_error_statement`.

---

## Duration Logging

```sql
SHOW log_duration;
SHOW log_min_duration_statement;
```

Distinguish:

```text
log_duration
    -> duration for every completed statement when enabled

log_min_duration_statement
    -> statement and duration when threshold is met
```

For `log_min_duration_statement`:

```text
-1       disabled
0        all completed statements
positive threshold
         statements at/above threshold
```

Avoid combining several high-volume logging mechanisms without estimating the result.

---

## Sampled Statement Logging

```sql
SHOW log_min_duration_sample;
SHOW log_statement_sample_rate;
SHOW log_transaction_sample_rate;
```

Conceptually:

```text
log_min_duration_statement
    -> deterministic threshold logging

log_min_duration_sample
    +
log_statement_sample_rate
    -> sampled threshold logging

log_transaction_sample_rate
    -> sampled transaction statement logging
```

Sampling reduces volume but also means the logs are not a complete population.

---

## Bind-Parameter Logging

```sql
SHOW log_parameter_max_length;
SHOW log_parameter_max_length_on_error;
```

For applicable normal statement logging, `log_parameter_max_length` controls parameter-value logging/truncation.

Conceptually:

```text
-1       full value
0        disable applicable parameter logging
positive truncate to configured byte limit
```

`log_parameter_max_length_on_error` separately controls parameter values associated with errors; PostgreSQL 18 defaults this setting to `0`.

Parameter logging can expose:

```text
PII / PHI
tokens
account identifiers
business-sensitive values
```

It can also add conversion/processing overhead.

Never assume prepared statements make logs safe automatically.

---

## Lock Logging

```sql
SHOW log_lock_waits;
SHOW log_lock_failures;
SHOW deadlock_timeout;
```

`log_lock_waits` can record sessions waiting longer than `deadlock_timeout`.

PostgreSQL 18 also provides `log_lock_failures` for applicable failed lock acquisitions.

Use logs together with live state:

```text
logs
    -> historical evidence

pg_stat_activity + pg_locks
    -> current state
```

Do not globally lower `deadlock_timeout` merely to generate faster diagnostic logging.

---

## Checkpoint Logging

```sql
SHOW log_checkpoints;
```

PostgreSQL 18 enables checkpoint logging by default.

Use:

```text
checkpoint logs
       +
pg_stat_checkpointer
       +
WAL generation
       +
storage metrics
       =
better diagnosis
```

A checkpoint log entry is not automatically an error.

---

## Autovacuum Logging

```sql
SHOW log_autovacuum_min_duration;
```

PostgreSQL 18 defaults this to `10min`.

Conceptually:

```text
-1       disable
0        log all qualifying autovacuum actions
positive log actions at/above threshold
```

When enabled appropriately, PostgreSQL can also provide evidence about certain skipped autovacuum operations.

Do not casually set the threshold to zero on a busy production cluster.

---

## Temporary-File Logging

```sql
SHOW log_temp_files;
```

Conceptually:

```text
-1       disabled
0        log every temporary file
positive log files at/above threshold
```

Temporary-file log entries are emitted when the file is removed and include size information.

A temporary file does not automatically mean `work_mem` should be increased. Investigate query plans, workload shape, concurrency, and memory implications.

---

## Recovery-Conflict Logging

```sql
SHOW log_recovery_conflict_waits;
```

This is primarily relevant to standby/recovery systems where query execution can conflict with WAL replay.

Treat it as replication observability rather than a primary-server default recommendation.

---

## Error Verbosity

```sql
SHOW log_error_verbosity;
```

More verbose output can improve debugging but also increase log size and reveal additional internal information.

Use the narrowest level needed for the diagnostic objective.

## Hands-On Lab

The required lab does **not** modify global PostgreSQL logging.

Create an isolated database:

```sql
-- [LAB-ONLY]
CREATE DATABASE logging_lab;
```

Reconnect:

```text
\c logging_lab
```

Create:

```sql
CREATE SCHEMA logging_lab;

CREATE TABLE logging_lab.orders (
    order_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL,
    amount numeric(12,2) NOT NULL,
    status text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

Identify the session:

```sql
SET application_name = 'part-2.11-logging-lab';

SELECT
    pid,
    usename,
    datname,
    application_name,
    client_addr,
    state,
    backend_start,
    state_change
FROM pg_stat_activity
WHERE pid = pg_backend_pid();
```

Use synthetic data only:

```sql
INSERT INTO logging_lab.orders(customer_id, amount, status)
VALUES (1001, 50.00, 'NEW');
```

Generate one deterministic disposable error:

```sql
SELECT *
FROM logging_lab.table_that_does_not_exist;
```

A client-side `ERROR` does not guarantee that identical statement/error information will appear in the server log. The result depends on active server logging policy.

The required lab does not change `log_min_duration_statement`, `log_statement`, or any other server logging policy.

## Self-Managed Log Inspection

Authorized operators can inspect:

```sql
SHOW log_directory;
SHOW log_filename;
```

If direct filesystem access exists, use targeted inspection rather than dumping an entire production log.

For example, in an isolated training environment:

```bash
tail -n 100 <postgresql-log-file>
grep 'part-2.11-logging-lab' <postgresql-log-file>
```

Never put real secrets or sensitive customer/patient data into a test statement merely to make it easy to find in a log.

## Production Logging Strategy

Useful evidence may include:

```text
startup/shutdown
fatal errors
authentication problems
slow statements
lock waits/failures
deadlocks
checkpoint activity
autovacuum activity
temporary-file spills
recovery conflicts
```

Control:

```text
events/sec
GB/hour or GB/day
local disk
collector throughput
network forwarding
central ingestion
retention
search/index cost
sensitive-data exposure
```

Logging itself must have a capacity model.

---

## Centralized Logging Boundary

```text
PostgreSQL
    |
agent / collector
    |
network
    |
central platform
    |
index / storage / retention
    |
cost
```

Before increasing logging, consider downstream limits and cost.

Production ownership should also define what happens when the forwarding agent, network, or central destination fails.

---

## Temporary Diagnostic Logging Pattern

```text
define the diagnostic question
        |
        v
choose the smallest logging change
that can answer it
        |
        v
define a bounded time window
        |
        v
collect evidence
        |
        v
restore previous configuration
        |
        v
verify configuration
        |
        v
verify log volume normalizes
```

Do not leave incident-only logging enabled indefinitely.

## Production Logging Change Gate

Before changing production logging:

```text
[ ] Diagnostic/business requirement identified
[ ] PostgreSQL version confirmed
[ ] Current value/source recorded
[ ] pg_settings.context checked
[ ] pending_restart checked
[ ] Expected events/sec estimated
[ ] GB/hour or GB/day estimated
[ ] Local disk headroom reviewed
[ ] Rotation reviewed
[ ] Retention reviewed
[ ] SQL-text exposure reviewed
[ ] Bind-parameter exposure reviewed
[ ] Privacy/security requirements reviewed
[ ] Collector/agent capacity reviewed
[ ] Network impact reviewed
[ ] Central ingestion cost reviewed
[ ] Managed-service restrictions reviewed
[ ] Diagnostic duration defined
[ ] Previous value documented
[ ] Success criteria defined
[ ] Rollback criteria defined
[ ] Post-change monitoring defined
```

## Managed PostgreSQL

On managed platforms such as Amazon RDS/Aurora PostgreSQL, Azure Database for PostgreSQL, and Google Cloud SQL for PostgreSQL, operators may not have direct access to:

```text
$PGDATA
log_directory
host filesystem
postgresql.conf
service manager
```

Providers can expose logs through cloud-specific log services, diagnostics, parameter controls, and export mechanisms.

Distinguish PostgreSQL parameter semantics from provider-specific implementation.

## Key Takeaways

```text
log_destination
    -> destination/format

logging_collector
    -> PostgreSQL-managed collection

log_line_prefix
    -> correlation metadata

log_connections
    -> PostgreSQL 18 granular connection-stage evidence

log_statement
    -> statement-category logging

log_min_duration_statement
    -> threshold slow-statement logging

log_lock_waits / log_lock_failures
    -> lock evidence

log_checkpoints
    -> checkpoint event evidence

log_autovacuum_min_duration
    -> autovacuum evidence

log_temp_files
    -> temporary-file evidence
```

The production objective is:

```text
enough evidence
      +
controlled volume
      +
safe data handling
      +
bounded diagnostic changes
```

not:

```text
log everything
```
