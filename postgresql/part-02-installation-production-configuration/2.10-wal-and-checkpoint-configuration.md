# Part 2.10 — WAL and Checkpoint Configuration

**Status:** Revised Final / Canonical Edition  
**Target:** PostgreSQL 18  
**Audience:** PostgreSQL administrators, SREs, DBREs, platform engineers, and application engineers.

## Objectives
Understand WAL durability, checkpoints, WAL sizing/retention, PostgreSQL 18 monitoring, replication-slot retention, archiving risk, safe capacity planning, and production troubleshooting.

## Safety Classes
- `[SAFE-READ]` — read-only inspection.
- `[SAFE-READ — OPERATIONALLY SENSITIVE OUTPUT]` — read-only output that can reveal infrastructure details.
- `[LAB-ONLY — GENERATES WAL]` — disposable workload that creates WAL.
- `[PRODUCTION-CHANGE]` — persistent operational/configuration change.
- `[DURABILITY-CRITICAL]` — can affect crash safety, recovery, or acknowledged-transaction durability.

## WAL Fundamentals
PostgreSQL follows the write-ahead rule: required WAL describing a change must reach durable storage before the corresponding changed data page can safely reach persistent storage. WAL supports crash recovery and underpins physical replication, PITR, backup/recovery workflows, and logical decoding when appropriately configured.

WAL resides under `$PGDATA/pg_wal`. Never manually delete, truncate, or randomly move files from this directory to recover disk space.

## Safe Configuration Inventory
```sql
SELECT name, setting, unit, context, source
FROM pg_settings
WHERE name IN (
 'fsync','synchronous_commit','wal_level','wal_buffers','wal_compression',
 'wal_writer_delay','wal_writer_flush_after','wal_segment_size',
 'full_page_writes','checkpoint_timeout','checkpoint_completion_target',
 'checkpoint_flush_after','checkpoint_warning','max_wal_size','min_wal_size',
 'wal_keep_size','max_slot_wal_keep_size','archive_mode'
)
ORDER BY name;
```

## WAL Configuration
`wal_level` controls WAL information available for recovery/replication. PostgreSQL 18 defaults to `replica`; `logical` adds logical-decoding information. Do not lower it as a WAL-volume shortcut without reviewing PITR, archiving, replication, logical decoding, and base-backup implications.

With `wal_buffers=-1`, PostgreSQL automatically sizes WAL buffers from `shared_buffers` (1/32, subject to documented bounds). Measure before overriding automatic sizing.

`wal_compression` compresses full-page images and can trade CPU for reduced WAL volume. PostgreSQL 18 supports `off`, `pglz`, and build-dependent `lz4`/`zstd`; historical `on` means `pglz`.

`full_page_writes` protects against partially written pages. Do not disable it merely to reduce WAL.

## Durability Controls
These settings are not equivalent:

```text
fsync=off
 -> corruption/recovery danger after failure

full_page_writes=off
 -> torn-page protection reduced; corruption possible

synchronous_commit=off
 -> recently acknowledged transactions can be lost after crash,
    without by itself making the database inconsistent
```

Treat durability changes as production changes requiring explicit RPO/recovery review.

## Checkpoints
Checkpoints advance PostgreSQL's recovery starting point. Central automatic triggers are `checkpoint_timeout` and WAL volume approaching `max_wal_size`. A scheduled checkpoint may be skipped when no WAL has been written since the previous checkpoint.

`checkpoint_timeout` controls the timed interval. `checkpoint_completion_target` (default 0.9 in PostgreSQL 18) spreads checkpoint work across much of the interval. `checkpoint_warning` helps identify closely spaced WAL-driven checkpoints.

`max_wal_size` is a **soft limit**, not a maximum `pg_wal` filesystem size. Actual retention can exceed it because of heavy WAL generation, archiving, slots, replica lag, `wal_keep_size`, and recovery requirements.

`min_wal_size` provides recyclable WAL capacity; it is not an exact minimum directory size.

## PostgreSQL 18 WAL Statistics
```sql
SELECT
    wal_records,
    wal_fpi,
    wal_bytes,
    wal_buffers_full,
    stats_reset
FROM pg_stat_wal;
```

PostgreSQL 18 does **not** expose the older `wal_write`, `wal_sync`, `wal_write_time`, or `wal_sync_time` fields in `pg_stat_wal`. WAL I/O belongs to the PostgreSQL 18 `pg_stat_io` monitoring model.

## PostgreSQL 18 Checkpointer Statistics
```sql
SELECT
    num_timed,
    num_requested,
    num_done,
    restartpoints_timed,
    restartpoints_req,
    restartpoints_done,
    write_time,
    sync_time,
    buffers_written,
    slru_written,
    stats_reset
FROM pg_stat_checkpointer;
```

`num_timed` and `num_requested` count checkpoint attempts, including skipped attempts; `num_done` counts checkpoints actually performed. Restartpoint counters apply to recovery/standby behavior.

## Safe WAL Measurement
Capture an LSN before and after a controlled workload:
```sql
SELECT pg_current_wal_lsn();
SELECT pg_wal_lsn_diff('<ending-lsn>','<starting-lsn>');
```
LSN movement is cluster-wide and includes concurrent workloads.

PostgreSQL 18 can also expose per-backend WAL statistics:
```sql
SELECT * FROM pg_stat_get_backend_wal(pg_backend_pid());
```
Use this as an optional controlled-lab attribution method where privileges permit.

## Hands-On Lab
`[LAB-ONLY — CREATES OBJECTS AND GENERATES WAL]`

Before running, confirm a disposable/training environment, sufficient storage headroom, no current WAL/storage incident, and no unintended replication/backup impact.

```sql
CREATE DATABASE wal_lab;
```
Reconnect with `\c wal_lab`, then:
```sql
CREATE SCHEMA wal_lab;
CREATE TABLE wal_lab.orders (
 order_id bigint GENERATED ALWAYS AS IDENTITY,
 customer_id bigint NOT NULL,
 order_date timestamptz NOT NULL DEFAULT now(),
 amount numeric(12,2) NOT NULL,
 status text NOT NULL
);
```

Capture WAL/checkpointer baselines, then generate controlled WAL:
```sql
INSERT INTO wal_lab.orders(customer_id,order_date,amount,status)
SELECT (random()*100000)::bigint,
       now()-(random()*interval '365 days'),
       round((random()*5000)::numeric,2),
       CASE (g%4) WHEN 0 THEN 'NEW' WHEN 1 THEN 'PAID'
                  WHEN 2 THEN 'SHIPPED' ELSE 'CLOSED' END
FROM generate_series(1,100000) AS g;

UPDATE wal_lab.orders
SET status='ARCHIVED'
WHERE order_id <= 25000;
```
Capture the second snapshots and compare deltas. Do not reset shared statistics.

Do not force `CHECKPOINT` as part of the standard lab; it is an administrative action and can generate significant I/O.

## Replication-Slot Retention
```sql
SELECT slot_name,slot_type,active,restart_lsn,confirmed_flush_lsn,
       wal_status,safe_wal_size
FROM pg_replication_slots;

SHOW max_slot_wal_keep_size;
```
PostgreSQL 18 defaults `max_slot_wal_keep_size` to `-1`, so this setting does not limit WAL retained by slots. An inactive slot is not automatically unused or safe to drop. Never automate slot deletion from this tutorial.

## Archive Health
Prefer:
```sql
SELECT archived_count,last_archived_wal,last_archived_time,
       failed_count,last_failed_wal,last_failed_time,stats_reset
FROM pg_stat_archiver;
```
Treat archive and slot output as operationally sensitive. PostgreSQL 18 can use an archive command or archive library. Repeated archive failure can cause WAL accumulation and eventually filesystem exhaustion. Do not blindly disable archiving; it may underpin PITR/DR.

## WAL Disk-Pressure Workflow
```text
measure filesystem capacity
 -> measure WAL generation rate
 -> check archive health
 -> inspect slots and consumer lag
 -> check workload changes
 -> inspect checkpoint behavior
 -> identify retention owner
 -> remediate cause
 -> verify normal WAL lifecycle resumes
 -> monitor restored headroom
```
Never begin by deleting WAL.

## Key Takeaways
- WAL is a durability/recovery stream, not disposable application logging.
- `max_wal_size` is not a filesystem ceiling.
- PostgreSQL 18 `pg_stat_wal` contains generation counters; WAL I/O is monitored through `pg_stat_io`.
- `pg_stat_checkpointer.num_done` represents completed checkpoints.
- Slots and failed archiving can retain substantial WAL.
- Never drop a slot or delete WAL merely to free space.
- Tune checkpoints from evidence: WAL rate, checkpoint behavior, storage performance, recovery objectives, and retention dependencies.
