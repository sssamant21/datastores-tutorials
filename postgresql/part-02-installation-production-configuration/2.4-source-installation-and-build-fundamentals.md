**Build classification:** `[TUTORIAL-OPERATOR-ACTION — MUTATING]`

## 2.4.1 Introduction

Part 2.3 covered installation from prebuilt operating-system packages. PostgreSQL can also be built directly from source.

A source installation gives the organization more control over source, compiler, build system, build features, dependencies, installation prefix, testing, and artifact production, but also transfers more lifecycle responsibility to the organization.

A production source-build lifecycle is: approved source → integrity verification → controlled build environment → toolchain validation → build configuration → compilation → regression testing → controlled installation → binary/capability verification → build manifest → patch/rebuild lifecycle.

Source installation should therefore be treated as software supply-chain engineering, not merely as running a few compiler commands.

## 2.4.2 Learning Objectives

By the end of this section, you should be able to explain when source installation is appropriate; distinguish package and source installations; identify trusted PostgreSQL source; distinguish release source from development source; verify source integrity; identify PostgreSQL build prerequisites; understand PostgreSQL's Autoconf/GNU Make and Meson/Ninja workflows; choose a build method deliberately; configure an isolated installation prefix; select build capabilities deliberately; avoid accidental build-feature differences; compile PostgreSQL using an unprivileged build account; understand PostgreSQL regression-test behavior; distinguish build testing from production runtime; install compiled PostgreSQL software safely; verify installed binaries by absolute path; detect package/source coexistence; create a reproducible build manifest; and preserve the boundary between source installation and `initdb`.

## 2.4.3 Package Installation vs Source Installation

Package installation follows repository → prebuilt package → package manager → installed PostgreSQL. Source installation follows trusted PostgreSQL source → verify integrity → validate toolchain → configure build → compile → test → install → verify.

Source installation provides greater build control but requires greater operational ownership.

## 2.4.4 Source Builds Are Not Automatically Better

Do not assume source build means faster PostgreSQL or more production-grade PostgreSQL. A standardized PGDG, distribution, or enterprise package can be an excellent production choice. Source compilation should have a documented engineering requirement.

## 2.4.5 Appropriate Source-Build Use Cases

Examples include PostgreSQL development, extension development, controlled research, testing PostgreSQL patches, nonstandard installation prefixes, specific build-time capabilities, debug/instrumentation builds, platforms not adequately served by available packages, and organization-maintained PostgreSQL build pipelines.

For production, source compilation should preferably be reproducible through a controlled build process.

## 2.4.6 Prefer Packages When They Meet the Requirement

Packages commonly simplify dependency management, software inventory, security updates, patch management, service integration, configuration management, and upgrade planning. If an approved package satisfies the deployment requirements, source compilation should not be introduced merely for novelty.

## 2.4.7 Safety Classification

`[TUTORIAL-ACCEPTANCE — SAFE-READ]` covers host/toolchain, disk, package, binary, version, and process inspection.

`[TUTORIAL-OPERATOR-ACTION — MUTATING]` covers dependency installation, source extraction, configure/Meson setup, compilation, and installation.

`[TUTORIAL-OPERATOR-ACTION — MUTATING / TEMPORARY TEST RUNTIME]` covers regression tests such as `make check`, `make check-world`, and `meson test`. Regression testing can create temporary PostgreSQL runtime state and is not SAFE-READ.

## 2.4.8 PostgreSQL 18 Build Systems

For Linux source builds, PostgreSQL 18 documentation covers Autoconf + GNU Make and Meson + Ninja. For this tutorial, Autoconf + GNU Make is the primary/reference Linux workflow, while Meson + Ninja is an additional documented workflow. Do not mix the two build systems accidentally within one build tree.

## 2.4.9 Build Method Must Be Recorded

Every build should record `AUTOCONF_MAKE` or `MESON_NINJA`, plus source, compiler, toolchain versions, configuration options, resolved capabilities, installation prefix, tests, and results.

## 2.4.10 Trusted Source

Production source should come from an approved origin such as the official PostgreSQL release source, an approved enterprise mirror, controlled artifact repository, approved source-control checkout, or controlled internal build pipeline. Do not compile arbitrary PostgreSQL archives obtained from unknown mirrors.

## 2.4.11 Release Source vs Development Source

For production release builds, use a clearly identified PostgreSQL release corresponding to the intended version. Record PostgreSQL version, release, source origin, archive, acquisition date, and approval. Development Git source is appropriate for development, patch testing, and other explicitly controlled workflows. Do not silently substitute a development source tree for an approved production release.

## 2.4.12 Verify Source Integrity

Calculate the source digest, for example:

```bash
sha256sum <postgresql-source-archive>
```

Compare it with the expected value obtained through the approved trust process. The model is trusted source + trusted expected integrity information + calculated local digest → exact match. A successful download alone does not establish integrity. If verification fails, classify it as `BLOCKER` and do not extract or compile the source.

## 2.4.13 Source Extraction

Source extraction is `[TUTORIAL-OPERATOR-ACTION — MUTATING]`. Use a dedicated build workspace. Never extract PostgreSQL source inside PGDATA, WAL directories, tablespace directories, or production database storage.

## 2.4.14 Controlled Build Environment

Prefer a dedicated build environment → compile → test → record manifest → produce controlled artifact → verify → deploy, rather than compiling directly on a busy production database host. Compilation and regression testing consume CPU, memory, disk, inodes, I/O, and temporary storage and may require development packages otherwise unnecessary on the database server.

## 2.4.15 Disk and Filesystem Precheck

Before extracting/building, inspect `df -h` and `df -i`. Confirm capacity for the source archive, extracted source, build tree, test artifacts, and installation prefix.

## 2.4.16 C Compiler

PostgreSQL 18 requires an appropriate standards-compliant C compiler including C99 capability. Inspect `cc --version` and, where applicable, `gcc --version`. Do not teach that GCC is mandatory; teach that a C99-capable compiler is required and GCC is a common choice. Record the actual compiler and version.

## 2.4.17 GNU Make

For the Autoconf workflow, verify GNU Make with `make --version` and, where applicable, `gmake --version`. Record which executable and version were used. A generic non-GNU `make` should not be assumed equivalent.

## 2.4.18 Meson and Ninja

For the Meson workflow inspect `meson --version` and `ninja --version`. Missing Meson/Ninja is not automatically a blocker when the approved build method is Autoconf/GNU Make. Evaluate prerequisites relative to the selected build method.

## 2.4.19 Flex and Bison

PostgreSQL source builds require appropriate Flex and GNU Bison tooling. Inspect `flex --version` and `bison --version`. Do not assume arbitrary `lex` and `yacc` implementations are interchangeable with PostgreSQL's documented requirements.

## 2.4.20 Perl

PostgreSQL's source build process and test infrastructure use Perl. Inspect `perl --version` and record the detected version.

## 2.4.21 Archive Tooling

Inspect `tar --version` and verify the decompression capability required by the selected source archive.

## 2.4.22 Build Features and Dependencies

Selected builds may require Readline/libedit, zlib, ICU, OpenSSL, LZ4, Zstandard, LDAP, GSSAPI, XML, XSLT, systemd integration, and other capabilities. Use deployment requirement → required capability → build option → dependency → compilation → test → capability verification. Do not install every optional dependency or enable every feature automatically.

## 2.4.23 Readline / libedit

Interactive `psql` environments commonly benefit from line editing and command history. Deliberately determine whether GNU Readline, libedit, or neither is appropriate. Missing Readline is not automatically a universal build blocker.

## 2.4.24 zlib

zlib support affects functionality that uses compressed data/archive capabilities. If required, record whether zlib is enabled. Do not assume every successfully compiled PostgreSQL binary has identical compression capabilities.

## 2.4.25 ICU

ICU affects internationalization and collation capabilities. Production build specifications should explicitly record whether ICU support is expected and whether the final build provides it.

## 2.4.26 OpenSSL / TLS

If production requires PostgreSQL TLS support, the build specification must explicitly include and verify the appropriate OpenSSL-backed capability. Compilation success alone does not prove required TLS capability exists.

## 2.4.27 LZ4 and Zstandard

Where required, record LZ4 and Zstandard separately as enabled, disabled, or not required. Avoid generic evidence such as “compression enabled.”

## 2.4.28 Build Reproducibility

Different build hosts can contain different libraries. Automatically detected capabilities can therefore produce different binaries from nominally similar commands. Production evidence should capture requested configuration plus resolved capabilities.

## 2.4.29 Unprivileged Build Account

Do not build PostgreSQL as root. Use an unprivileged build account for source extraction, configure, compile, and regression tests. Use controlled privilege only where required for prerequisite package management or the final installation destination. Avoid `sudo ./configure`, `sudo make`, and `sudo make check`.

## 2.4.30 Build Account vs Runtime Account

The build account compiles/tests PostgreSQL; installation authority writes the approved software prefix; the PostgreSQL service account owns and runs the database cluster. Do not grant broad privileges to the runtime account merely to simplify compilation.

## 2.4.31 Installation Prefix

This tutorial uses `/opt/postgresql/18` as an organizational convention, not a PostgreSQL requirement. The isolated prefix makes package/source coexistence easier to understand.

## 2.4.32 Validate the Prefix Before Installation

Determine whether the prefix exists, who owns it, what it contains, whether another PostgreSQL installation uses it, whether package management owns it, which filesystem contains it, and whether capacity is sufficient. An unexpected existing installation is `REQUIRES VALIDATION`. Never automatically remove it.

## 2.4.33 Avoid Package-Managed Paths

Do not casually install source-built PostgreSQL over package-managed paths such as `/usr/bin` or `/usr/lib`. Doing so can make package inventory differ from actual binaries and future package updates can conflict with the custom installation.

## 2.4.34 Autoconf Configuration

Example:

```bash
./configure --prefix=/opt/postgresql/18
```

Classification: `[TUTORIAL-OPERATOR-ACTION — MUTATING]`. Investigate configuration failures such as missing compiler/build tools/headers/libraries, unsupported options, or dependency mismatches. Do not bypass failed checks without understanding the cause.

## 2.4.35 Autoconf Build Options

Use PostgreSQL's documented configuration options. Do not copy arbitrary flags from unrelated environments. Preserve the exact configuration command in the build manifest.

## 2.4.36 Compile with GNU Make

Run `make` after successful configuration. This is mutating. Parallel compilation may use `make -j <jobs>`, but concurrency must be chosen deliberately. Do not teach `make -j$(nproc)` as a universal production default.

## 2.4.37 Regression Testing with `make check`

`make check` is `[TUTORIAL-OPERATOR-ACTION — MUTATING / TEMPORARY TEST RUNTIME]`, not SAFE-READ. Regression tests can start a temporary PostgreSQL server and create temporary state. This does not mean the intended production cluster has been initialized. Run testing under the unprivileged build account in an appropriate environment.

## 2.4.38 Broader Testing with `make check-world`

`make check-world` can provide broader applicable test coverage and can consume more resources. It has the same mutating/temporary-runtime classification and should be used deliberately in an appropriate build or CI environment.

## 2.4.39 `installcheck` Production Warning

**PRODUCTION SAFETY WARNING:** Do not point PostgreSQL regression/installcheck testing at a production database cluster. `installcheck` operates against an existing installation and can create/drop regression-test objects. Prefer isolated build-time regression testing for this tutorial.

## 2.4.40 Failed Regression Tests

Treat unexplained test failures as `BLOCKER` or `REQUIRES VALIDATION`. Investigate the failed test, environment, locale, compiler, dependencies, build options, resource limits, platform behavior, and test output. Do not automatically install after unexplained failures.

## 2.4.41 Install with GNU Make

After successful build/testing, `make install` is `[TUTORIAL-OPERATOR-ACTION — MUTATING]`. Confirm the destination immediately before execution and use elevated privilege only if required by the approved destination and organizational procedure.

## 2.4.42 Meson Setup

Use a dedicated build directory, for example:

```bash
meson setup build --prefix=/opt/postgresql/18
```

This is mutating. Preserve the Meson configuration in the build manifest.

## 2.4.43 Meson Feature Selection

Meson features may use `enabled`, `disabled`, or `auto`. Do not assume Autoconf option names translate directly to Meson. Use required capability → build-system-specific option → resolved capability. Pay special attention to automatically detected features for reproducible production builds.

## 2.4.44 Meson/Ninja Compilation

The PostgreSQL Meson workflow commonly uses:

```bash
ninja -C build
```

This is mutating. Choose build concurrency according to build-environment resources and policy.

## 2.4.45 Meson Regression Tests

Run:

```bash
meson test -C build
```

Classification: `[TUTORIAL-OPERATOR-ACTION — MUTATING / TEMPORARY TEST RUNTIME]`. Treat failures as engineering evidence and do not automatically proceed after unexplained failures.

## 2.4.46 Meson Installation

After successful build/testing:

```bash
meson install -C build
```

This is mutating. Validate the configured prefix before installation.

## 2.4.47 Verify the Installation Prefix

SAFE-READ verification can inspect `/opt/postgresql/18` and `/opt/postgresql/18/bin`. Verify binaries by absolute path:

```bash
/opt/postgresql/18/bin/postgres --version
/opt/postgresql/18/bin/psql --version
/opt/postgresql/18/bin/initdb --version
/opt/postgresql/18/bin/pg_config --version
```

Expected major version is PostgreSQL 18. Another major version is a `BLOCKER`.

## 2.4.48 Verify `pg_config`

Inspect `pg_config --version`, `--bindir`, `--libdir`, `--pkglibdir`, and `--sharedir` using the absolute source-install path. This provides useful layout evidence.

## 2.4.49 Do Not Modify PATH Automatically

The acceptance workflow may report shell-resolved and source-prefix binaries but must never modify PATH, `/etc/profile`, `/etc/environment`, shell profiles, or symlinks. Environment integration should be separately designed and approved.

## 2.4.50 Package and Source Coexistence

A host may legitimately contain package-managed and source-built PostgreSQL binaries. Compare versions by absolute path and document package-managed PostgreSQL, source-built PostgreSQL, operational purpose, and runtime selection. Do not automatically remove or relink either installation.

## 2.4.51 Do Not Run Production `initdb`

PostgreSQL 18 software installed does not mean a production cluster has been created. SAFE-READ acceptance may run `initdb --version`, but must never execute `initdb -D <PGDATA>`. Production cluster initialization belongs to Part 2.5.

## 2.4.52 Do Not Start PostgreSQL

Part 2.4 must not run `pg_ctl start` or `systemctl start ...` to validate source installation. End state: PostgreSQL software installed → PostgreSQL 18 verified → build provenance recorded → production cluster not initialized → production server not started.

## 2.4.53 Do Not Create systemd Integration Yet

Do not create an ad hoc production service during source installation. Part 2.7 owns PostgreSQL service-management design and validation.

## 2.4.54 Do Not Configure Network Access

Part 2.4 does not modify `listen_addresses`, port, `pg_hba.conf`, firewall, or security groups. Network exposure is unnecessary for source-build verification.

## 2.4.55 Source Installation Lifecycle Ownership

An organization operating source-built PostgreSQL must own source provenance, build reproduction, security updates, minor-version rebuilds, dependency updates, compiler/toolchain changes, build options, test evidence, artifact retention, deployment, rollback/recovery, upgrade testing, and software inventory. A directory under `/opt` is not a lifecycle strategy.

## 2.4.56 Production Build Manifest

Create `postgresql-source-build.txt` containing source version/release/origin/archive/digests, build host/environment/OS/architecture, compiler and tool versions, build method, feature capabilities, exact configuration command, prefix, resolved capabilities, build command/concurrency/result, testing result and disposition, install command/prefix/result, absolute binary versions and `pg_config` layout, package/source coexistence, runtime state, change-control evidence, and overall PASS/WARNING/BLOCKER/REQUIRES VALIDATION result.

## 2.4.57 Hands-On Lab Workflow

Phase A SAFE-READ precheck → Phase B source acquisition/integrity/extraction `[MUTATING]` → Phase C configure/compile `[MUTATING]` → Phase D regression testing `[MUTATING / TEMPORARY TEST RUNTIME]` → Phase E install `[MUTATING]` → Phase F SAFE-READ acceptance.

## 2.4.58 Phase A — SAFE-READ Precheck

Inspect OS, architecture, disk/inodes, compiler, GNU Make/gmake, Meson, Ninja, Flex, Bison, Perl, tar, existing PostgreSQL binaries, package inventory, and intended installation prefix.

## 2.4.59 Phase B — Source Preparation

Acquire approved PostgreSQL 18 source, verify integrity, use an approved build workspace, and extract source. Stop immediately on failed integrity verification.

## 2.4.60 Phase C — Build

Choose exactly one build method: `AUTOCONF_MAKE` or `MESON_NINJA`. Record all build commands and resolved capabilities. Run under an unprivileged build account.

## 2.4.61 Phase D — Regression Testing

Regression testing is mutating/temporary-runtime. Use appropriate isolated testing such as `make check` or `meson test -C build`. Do not point regression testing at production.

## 2.4.62 Phase E — Installation

Install only after the build succeeds, tests are reviewed, the prefix is verified, and existing installations are understood. Use narrowly scoped privilege if required.

## 2.4.63 Phase F — SAFE-READ Acceptance

Verify installation prefix, `postgres`, `psql`, `initdb`, `pg_config`, PostgreSQL major version, layout, package/source coexistence, PATH resolution, and running PostgreSQL processes. Confirm that the production cluster was not intentionally initialized and the production PostgreSQL service was not intentionally started.

## 2.4.64 Acceptance Criteria

Before advancing, confirm PostgreSQL 18 source and provenance; integrity; build host/architecture; unprivileged build account; compiler/toolchain; build method/options/resolved capabilities; approved prefix; understood existing installations; successful build; reviewed regression tests; successful installation; PostgreSQL 18 binary verification; `psql`, `initdb`, and `pg_config` inspection; understood coexistence; no acceptance-script PATH modification; no production `initdb`; no production service startup; no PostgreSQL configuration mutation; no network exposure; and a completed build manifest.

## 2.4.65 Stop Conditions

Stop if source provenance cannot be established; integrity verification fails; the wrong PostgreSQL version is obtained; required prerequisites are missing; configuration or compilation fails; regression tests fail without understood disposition; the installation prefix conflicts with unknown software; package/source ownership is unclear; unexpected PostgreSQL processes/clusters exist; or required build capabilities are absent.

## 2.4.66 Production Anti-Patterns

Avoid compiling from source merely because it sounds faster; unknown source mirrors; skipped integrity verification; installing every optional dependency; enabling every feature; unnoticed auto-detected feature drift; building as root; unplanned compilation on busy production hosts; uncontrolled build concurrency; ignored regression failures; `installcheck` against production; overwriting package-managed binaries; deleting unknown prefixes; automatic ownership/permission/PATH/symlink changes; production `initdb`; starting PostgreSQL merely to validate compilation; ad hoc systemd services; opening TCP 5432 during source installation; and operating source-built PostgreSQL without a patch/rebuild strategy.

## 2.4.67 Canonical SAFE-READ Artifact

Canonical artifact: `labs/source-install-check.sh` classified `[TUTORIAL-ACCEPTANCE — SAFE-READ]`.

It may inspect OS, architecture, disk/inodes, compiler, GNU Make/gmake, Meson, Ninja, Flex, Bison, Perl, tar, package-managed PostgreSQL, installation prefix, source-installed binaries, versions, `pg_config` layout, PATH resolution, package/source coexistence, and running PostgreSQL processes.

It must never invoke sudo; install dependencies; modify repositories; download/extract source; configure; run Meson setup; compile; run regression tests; install binaries; remove build trees; modify ownership/permissions/PATH; create symlinks; run `initdb`; create/delete clusters; start/stop PostgreSQL; modify systemd/PostgreSQL/`pg_hba.conf`/firewall/network configuration.

## 2.4.68 Operational Takeaway

Package deployment asks which approved PostgreSQL package should be deployed. Source deployment adds: can we reproduce exactly how this PostgreSQL binary was produced and what capabilities it contains?

A production-quality source build requires trusted source + verified integrity + known toolchain + explicit build method + controlled capabilities + successful tests + isolated installation + reproducible evidence + lifecycle ownership.
