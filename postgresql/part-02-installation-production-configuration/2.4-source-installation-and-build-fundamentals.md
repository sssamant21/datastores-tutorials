**Part:** 2 — Installation & Production Configuration
**Edition:** Revised Final / Canonical
**Target:** PostgreSQL 18 on Linux
**Build classification:** `[TUTORIAL-OPERATOR-ACTION — MUTATING]`

**Acceptance classification:** `[TUTORIAL-ACCEPTANCE — SAFE-READ]`

---

# 2.4.1 Introduction

Part 2.3 covered installation from prebuilt operating-system packages.

PostgreSQL can also be built directly from source.

A source installation gives the organization more control over:

```text
Source
Compiler
Build system
Build features
Dependencies
Installation prefix
Testing
Artifact production
```

but also transfers more lifecycle responsibility to the organization.

A production source-build lifecycle looks like:

```text
Approved source
      ↓
Integrity verification
      ↓
Controlled build environment
      ↓
Toolchain validation
      ↓
Build configuration
      ↓
Compilation
      ↓
Regression testing
      ↓
Controlled installation
      ↓
Binary/capability verification
      ↓
Build manifest
      ↓
Patch/rebuild lifecycle
```

Source installation should therefore be treated as **software supply-chain engineering**, not merely as running a few compiler commands.

By the end of this section, you should be able to:

1. explain when source installation is appropriate;
2. distinguish package and source installations;
3. identify trusted PostgreSQL source;
4. distinguish release source from development source;
5. verify source integrity;
6. identify PostgreSQL build prerequisites;
7. understand PostgreSQL's Autoconf/GNU Make workflow;
8. understand PostgreSQL's Meson/Ninja workflow;
9. choose a build method deliberately;
10. configure an isolated installation prefix;
11. select build capabilities deliberately;
12. avoid accidental build-feature differences;
13. compile PostgreSQL using an unprivileged build account;
14. understand PostgreSQL regression-test behavior;
15. distinguish build testing from production runtime;
16. install compiled PostgreSQL software safely;
17. verify installed binaries by absolute path;
18. detect package/source coexistence;
19. create a reproducible build manifest;
20. preserve the boundary between source installation and `initdb`.

# 2.4.3 Package Installation vs Source Installation

Package installation typically follows:

```text
Repository
    ↓
Prebuilt package
    ↓
Package manager
    ↓
Installed PostgreSQL
```

Source installation follows:

```text
Trusted PostgreSQL source
        ↓
Verify integrity
        ↓
Validate toolchain
        ↓
Configure build
        ↓
Compile
        ↓
Test
        ↓
Install
        ↓
Verify
```

Source installation provides greater build control but requires greater operational ownership.

---

# 2.4.4 Source Builds Are Not Automatically Better

Do not assume:

```text
Source build = faster PostgreSQL
```

or:

```text
Source build = more production-grade PostgreSQL
```

A standardized PGDG, distribution, or enterprise package can be an excellent production choice.

Source compilation should have a documented engineering requirement.

---

# 2.4.5 Appropriate Source-Build Use Cases

Examples include:

```text
PostgreSQL development

Extension development

Controlled research

Testing PostgreSQL patches

Nonstandard installation prefixes

Specific build-time capabilities

Debug/instrumentation builds

Platforms not adequately served by available packages

Organization-maintained PostgreSQL build pipelines
```

For production, source compilation should preferably be reproducible through a controlled build process.

---

# 2.4.6 Prefer Packages When They Meet the Requirement

Packages commonly simplify:

```text
dependency management
software inventory
security updates
patch management
service integration
configuration management
upgrade planning
```

If an approved package satisfies the deployment requirements, source compilation should not be introduced merely for novelty.

# 2.4.10 Trusted Source

Production source should come from an approved origin such as:

```text
Official PostgreSQL release source

Approved enterprise mirror

Controlled artifact repository

Approved source-control checkout

Controlled internal build pipeline
```

Do not compile arbitrary PostgreSQL archives obtained from unknown mirrors.

---

# 2.4.11 Release Source vs Development Source

For production release builds, use a clearly identified PostgreSQL release corresponding to the intended version.

Record:

```text
PostgreSQL version:
Release:
Source origin:
Archive:
Acquisition date:
Approval:
```

Development Git source is appropriate for development, patch testing, and other explicitly controlled workflows.

Do not silently substitute a development source tree for an approved production release.

---

# 2.4.12 Verify Source Integrity

Calculate the source digest.

For example:

```bash
sha256sum <postgresql-source-archive>
```

Then compare it with the expected value obtained through the approved trust process.

The security model is:

```text
Trusted source
      +
Trusted expected integrity information
      +
Calculated local digest
      ↓
Exact match
```

A successful download alone does not establish integrity.

If verification fails:

```text
BLOCKER
```

Do not extract or compile the source.

---

# 2.4.13 Source Extraction

Extracting source modifies the build workspace.

Classification:

```text
[TUTORIAL-OPERATOR-ACTION — MUTATING]
```

Conceptually:

```bash
tar -xf <postgresql-source-archive>
```

Use a dedicated build workspace.

Never extract PostgreSQL source inside:

```text
PGDATA
WAL directories
tablespace directories
production database storage
```

---

# 2.4.14 Controlled Build Environment

Prefer:

```text
Dedicated build environment
        ↓
Compile
        ↓
Test
        ↓
Record manifest
        ↓
Produce controlled artifact
        ↓
Verify
        ↓
Deploy
```

over compiling directly on a busy production database host.

Compilation and regression testing consume:

```text
CPU
memory
disk
inodes
I/O
temporary storage
```

and may require development packages that are otherwise unnecessary on the database server.

# 2.4.15 Disk and Filesystem Precheck

Before extracting/building:

```bash
df -h
df -i
```

Confirm capacity for:

```text
source archive
extracted source
build tree
test artifacts
installation prefix
```

Insufficient build-space capacity should be resolved before compilation begins.

# 2.4.16 C Compiler

PostgreSQL requires an appropriate standards-compliant C compiler; for PostgreSQL 18 the documented requirement includes C99 capability.

Inspect:

```bash
cc --version
```

and where applicable:

```bash
gcc --version
```

Do not teach:

```text
GCC is mandatory
```

Instead:

```text
C99-capable C compiler required
GCC is a common choice
```

Record the actual compiler and version.

---

# 2.4.17 GNU Make

For the Autoconf workflow, verify GNU Make.

Inspect:

```bash
make --version
```

and, on systems where GNU Make is named differently:

```bash
gmake --version
```

The canonical build record should capture which executable and version were used.

A generic non-GNU `make` should not be assumed equivalent.

---

# 2.4.18 Meson and Ninja

For the Meson workflow inspect:

```bash
meson --version
ninja --version
```

Missing Meson/Ninja is not automatically a blocker when the approved build method is Autoconf/GNU Make.

Build prerequisites must be evaluated relative to the selected build method.

---

# 2.4.19 Flex and Bison

PostgreSQL source builds require appropriate Flex and GNU Bison tooling.

Inspect:

```bash
flex --version
bison --version
```

Do not assume arbitrary `lex` and `yacc` implementations are interchangeable with PostgreSQL's documented build requirements.

---

# 2.4.20 Perl

PostgreSQL's source build process and test infrastructure use Perl.

Inspect:

```bash
perl --version
```

The toolchain record should capture the detected version.

---

# 2.4.21 Archive Tooling

For release archives inspect:

```bash
tar --version
```

and verify the decompression capability required by the selected source archive.

Do not begin source acquisition without knowing the build environment can safely process the approved artifact.

# 2.4.22 Build Features and Dependencies

The selected build may require capabilities such as:

```text
Readline / libedit
zlib
ICU
OpenSSL
LZ4
Zstandard
LDAP
GSSAPI
XML
XSLT
systemd integration
other optional capabilities
```

The correct model is:

```text
Deployment requirement
        ↓
Required PostgreSQL capability
        ↓
Build option
        ↓
Library/dependency
        ↓
Compilation
        ↓
Test
        ↓
Capability verification
```

Do not install every optional dependency or enable every feature automatically.

---

# 2.4.23 Readline / libedit

Interactive `psql` environments commonly benefit from line editing and command history.

The build specification should deliberately determine whether:

```text
GNU Readline
libedit
or neither
```

is appropriate.

Missing Readline is not automatically a universal build blocker.

---

# 2.4.24 zlib

zlib support affects PostgreSQL functionality that uses compressed data/archive capabilities.

If the approved build requires it, record:

```text
zlib:
ENABLED
```

Do not assume every successfully compiled PostgreSQL binary has identical compression capabilities.

---

# 2.4.25 ICU

ICU affects important internationalization and collation capabilities.

Production build specifications should explicitly record whether ICU support is expected and whether the final build provides it.

This becomes especially important when reproducing builds across different hosts.

---

# 2.4.26 OpenSSL / TLS

If the production deployment requires PostgreSQL TLS support, the build specification must explicitly include and verify the appropriate OpenSSL-backed capability.

Do not assume:

```text
PostgreSQL compiled successfully
```

means:

```text
Required TLS capability exists
```

Build capability verification is part of acceptance.

---

# 2.4.27 LZ4 and Zstandard

Where required, record LZ4 and Zstandard capabilities separately:

```text
LZ4:
ENABLED / DISABLED / NOT REQUIRED

Zstandard:
ENABLED / DISABLED / NOT REQUIRED
```

Avoid generic evidence such as:

```text
compression enabled
```

because it does not identify the actual capability.

---

# 2.4.28 Build Reproducibility

Two build hosts can contain different libraries.

Therefore a build system that automatically detects capabilities can potentially produce different binaries from nominally similar commands.

Production build evidence should capture:

```text
Requested configuration
        +
Resolved capabilities
```

not merely the command that initiated the build.

---

# 2.4.29 Unprivileged Build Account

Do not build PostgreSQL as root.

Preferred model:

```text
Unprivileged build account
        ↓
Source extraction
        ↓
Configure
        ↓
Compile
        ↓
Regression tests
```

Use controlled privilege only where required for the final installation destination or prerequisite package management.

Avoid:

```bash
sudo ./configure
sudo make
sudo make check
```

and equivalent root-run Meson compilation/testing.

---

# 2.4.30 Build Account vs Runtime Account

The accounts may have separate responsibilities:

```text
Build account
    ↓
compiles/tests PostgreSQL

Installation authority
    ↓
writes approved software prefix

PostgreSQL service account
    ↓
owns and runs database cluster
```

Do not grant broad privileges to the PostgreSQL runtime account simply to make compilation easier.

---

# 2.4.31 Installation Prefix

Use a deliberate installation prefix.

For this tutorial:

```text
/opt/postgresql/18
```

This is:

```text
Tutorial / organizational convention
```

and **not** a PostgreSQL requirement.

The isolated prefix makes package/source coexistence easier to understand.

---

# 2.4.32 Validate the Prefix Before Installation

Before writing to the prefix determine:

```text
Does it already exist?

Who owns it?

What is inside it?

Is another PostgreSQL installation using it?

Does the package manager own it?

Which filesystem contains it?

Is capacity sufficient?
```

An unexpected existing installation should produce:

```text
REQUIRES VALIDATION
```

Never automatically:

```bash
rm -rf /opt/postgresql/18
```

---

# 2.4.33 Avoid Package-Managed Paths

Do not casually install source-built PostgreSQL over package-managed paths such as:

```text
/usr/bin
/usr/lib
```

Doing so can create:

```text
Package inventory
      ≠
Actual binaries
```

and future package updates may overwrite the custom installation.

---

# 2.4.34 Autoconf Configuration

For the traditional build workflow:

```bash
./configure --prefix=/opt/postgresql/18
```

Classification:

```text
[TUTORIAL-OPERATOR-ACTION — MUTATING]
```

The configuration phase examines the build environment and prepares the build.

Configuration failure should be investigated.

Common causes include:

```text
missing compiler
missing build tool
missing headers
missing library
unsupported option
dependency mismatch
```

Do not bypass failed checks without understanding the cause.

---

# 2.4.35 Autoconf Build Options

Autoconf build capabilities are expressed through PostgreSQL's documented configuration options.

Do not copy arbitrary build flags from unrelated environments.

Record the exact configuration command:

```text
CONFIGURATION COMMAND:
./configure ...
```

and preserve it in the build manifest.

---

# 2.4.36 Compile with GNU Make

After successful configuration:

```bash
make
```

Classification:

```text
[TUTORIAL-OPERATOR-ACTION — MUTATING]
```

Parallel compilation may use:

```bash
make -j <jobs>
```

but concurrency must be chosen deliberately.

Avoid teaching:

```bash
make -j$(nproc)
```

as a universal production default.

On shared infrastructure, uncontrolled compilation can consume significant CPU, memory, and I/O.

---

# 2.4.37 Regression Testing with `make check`

Baseline regression testing may use:

```bash
make check
```

Classification:

```text
[TUTORIAL-OPERATOR-ACTION — MUTATING / TEMPORARY TEST RUNTIME]
```

This is not SAFE-READ.

The regression tests can start a temporary PostgreSQL server and create temporary test state.

It does **not** mean the intended production cluster has been initialized.

Run regression testing under the unprivileged build account in an appropriate build/test environment.

---

# 2.4.38 Broader Testing with `make check-world`

For stronger build/release validation:

```bash
make check-world
```

may be appropriate.

Classification:

```text
[TUTORIAL-OPERATOR-ACTION — MUTATING / TEMPORARY TEST RUNTIME]
```

This can execute broader applicable PostgreSQL test suites and consume substantially more resources.

Use it deliberately in an appropriate build or CI environment.

---

# 2.4.39 `installcheck` Production Warning

```text
!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!
PRODUCTION SAFETY WARNING
!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!

Do not point PostgreSQL regression/installcheck testing
at a production database cluster.
```

`installcheck` operates against an existing PostgreSQL installation and can create/drop regression-test objects.

For this tutorial's source-build workflow, prefer isolated build-time regression testing rather than testing against an operational production database.

---

# 2.4.40 Failed Regression Tests

A failed test is evidence.

Initial classification:

```text
BLOCKER
or
REQUIRES VALIDATION
```

Investigate:

```text
failed test
environment
locale
compiler
dependencies
build options
resource limits
platform behavior
test output
```

Do not automatically continue with installation after unexplained test failures.

Any accepted known failure requires an explicit engineering disposition.

# 2.4.41 Install with GNU Make

After successful build/testing:

```bash
make install
```

Classification:

```text
[TUTORIAL-OPERATOR-ACTION — MUTATING]
```

This writes PostgreSQL software into the configured installation prefix.

Confirm the destination immediately before execution.


Classification:

```text
[TUTORIAL-OPERATOR-ACTION — MUTATING]
```

# 2.4.43 Meson Feature Selection

Meson features may use values such as:

```text
enabled
disabled
auto
```

Do not assume Autoconf option names translate directly to Meson.

The engineering model remains:

```text
Required capability
      ↓
Build-system-specific option
      ↓
Resolved capability
```

For reproducible production builds, pay particular attention to automatically detected features.

# 2.4.47 Verify the Installation Prefix

After installation, SAFE-READ verification may inspect:

```bash
ls -ld /opt/postgresql/18
ls -l /opt/postgresql/18/bin
```

Then verify binaries using absolute paths:

```bash
/opt/postgresql/18/bin/postgres --version
/opt/postgresql/18/bin/psql --version
/opt/postgresql/18/bin/initdb --version
/opt/postgresql/18/bin/pg_config --version
```

Expected major version:

```text
PostgreSQL 18
```

If another major version appears:

```text
BLOCKER
```

---

# 2.4.48 Verify `pg_config`

Inspect:

```bash
/opt/postgresql/18/bin/pg_config --version
/opt/postgresql/18/bin/pg_config --bindir
/opt/postgresql/18/bin/pg_config --libdir
/opt/postgresql/18/bin/pg_config --pkglibdir
/opt/postgresql/18/bin/pg_config --sharedir
```

This provides useful evidence about the source installation layout.

---

# 2.4.49 Do Not Modify PATH Automatically

The acceptance workflow may report:

```text
Shell postgres:
<path>

Source postgres:
/opt/postgresql/18/bin/postgres
```

but must never modify:

```text
PATH
/etc/profile
/etc/environment
~/.bashrc
symlinks
```

Environment integration should be separately designed and approved.

---

# 2.4.50 Package and Source Coexistence

A host may contain:

```text
/usr/bin/psql
```

and:

```text
/opt/postgresql/18/bin/psql
```

This can be legitimate.

Compare versions using absolute paths and document:

```text
Package-managed PostgreSQL:
Source-built PostgreSQL:
Operational purpose:
Runtime selection:
```

Do not automatically remove or relink either installation.

---

# 2.4.51 Do Not Run Production `initdb`

After successful source installation:

```text
PostgreSQL 18 software installed
        ≠
Production cluster created
```

The SAFE-READ acceptance workflow may execute:

```bash
/opt/postgresql/18/bin/initdb --version
```

but must never execute:

```bash
/opt/postgresql/18/bin/initdb -D <PGDATA>
```

Production cluster initialization belongs to Part 2.5.

---

# 2.4.52 Do Not Start PostgreSQL

Part 2.4 must not run:

```bash
pg_ctl start
```

or:

```bash
systemctl start ...
```

to validate source installation.

The desired end state is:

```text
PostgreSQL software installed
        ↓
PostgreSQL 18 verified
        ↓
Build provenance recorded
        ↓
Production cluster NOT initialized
        ↓
Production server NOT started
```

---

# 2.4.53 Do Not Create systemd Integration Yet

Do not create an ad hoc production service under:

```text
/etc/systemd/system/
```

during source installation.

Part 2.7 owns PostgreSQL service-management design and validation.

---

# 2.4.54 Do Not Configure Network Access

Part 2.4 does not modify:

```text
listen_addresses
port
pg_hba.conf
firewall
security groups
```

Network exposure is unnecessary for source-build verification.

---

# 2.4.55 Source Installation Lifecycle Ownership

An organization operating source-built PostgreSQL must own:

```text
source provenance
build reproduction
security updates
minor-version rebuilds
dependency updates
compiler/toolchain changes
build options
test evidence
artifact retention
deployment
rollback/recovery
upgrade testing
software inventory
```

A directory under `/opt` is not a lifecycle strategy.

# 2.4.65 Stop Conditions

Stop if:

```text
Source provenance cannot be established
Source integrity verification fails
Wrong PostgreSQL version is obtained
Required build prerequisite is missing
Build configuration fails
Compilation fails
Regression tests fail without understood disposition
Installation prefix conflicts with unknown existing software
Package/source ownership is unclear
Unexpected PostgreSQL process exists
Unexpected cluster exists
Build capabilities do not meet deployment requirements
```

Do not advance to Part 2.5 until these conditions are resolved.

# 2.4.66 Production Anti-Patterns

Avoid:

```text
Compile from source because it sounds faster.
```

```text
Download source from an unknown mirror.
```

```text
Trust an archive without integrity verification.
```

```text
Install every optional development dependency.
```

```text
Enable every PostgreSQL build feature.
```

```text
Allow auto-detected build capabilities to vary unnoticed.
```

```text
Build PostgreSQL as root.
```

```text
Compile on a busy production DB host without planning.
```

```text
Use uncontrolled make -j concurrency.
```

```text
Ignore failed regression tests.
```

```text
Run installcheck against production.
```

```text
Overwrite package-managed PostgreSQL binaries.
```

```text
Delete an unknown existing source prefix.
```

```text
Automatically change ownership or permissions.
```

```text
Automatically modify PATH.
```

```text
Automatically create PostgreSQL symlinks.
```

```text
Run production initdb after installation.
```

```text
Start PostgreSQL merely to validate compilation.
```

```text
Create an ad hoc systemd service.
```

```text
Open TCP 5432 during source installation.
```

```text
Operate source-built PostgreSQL without a patch/rebuild strategy.
```

# 2.4.68 Operational Takeaway

Package deployment asks:

```text
Which approved PostgreSQL package should we deploy?
```

Source deployment adds a deeper requirement:

```text
Can we reproduce exactly how this PostgreSQL binary
was produced and what capabilities it contains?
```

A production-quality source build therefore requires:

```text
Trusted source
      +
Verified integrity
      +
Known toolchain
      +
Explicit build method
      +
Controlled capabilities
      +
Successful tests
      +
Isolated installation
      +
Reproducible evidence
      +
Lifecycle ownership
```
