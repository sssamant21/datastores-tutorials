# Part 2.10 --- Authentication and Network Access Baseline

**Status:** Revised Final / Canonical Edition\
**Target:** PostgreSQL 18

## Objective

Establish a production-safe baseline for PostgreSQL network exposure and
client authentication without treating `pg_hba.conf` as the only
security boundary.

## Safety Model

-   `[SAFE-READ]` --- inspection only.
-   `[SECURITY-CHANGE]` --- changes to `listen_addresses`, TLS, HBA,
    roles, credentials, firewall/security-group/network-policy rules.
-   `[PRODUCTION-CHANGE — RELOAD]` --- HBA changes normally require
    PostgreSQL to re-read configuration.
-   `[PRODUCTION-CHANGE — RESTART]` --- settings with postmaster context
    require restart.

Never apply example CIDRs, role names, or authentication rules unchanged
in production.

## 1. Access Is a Chain

A client connection depends on all relevant layers:

``` text
DNS / address
    -> network route
    -> firewall / SG / NSG / network policy
    -> PostgreSQL listen address + port
    -> TLS policy
    -> pg_hba.conf rule selection
    -> authentication
    -> database CONNECT privilege
    -> object privileges
```

A successful TCP connection does not prove authorization is correct, and
a correct HBA rule cannot overcome a blocked network path.

## 2. Discover the Effective Server Boundary

``` sql
-- [SAFE-READ]
SELECT name, setting, context, source, pending_restart
FROM pg_settings
WHERE name IN (
  'listen_addresses',
  'port',
  'ssl',
  'hba_file',
  'ident_file',
  'password_encryption',
  'authentication_timeout'
)
ORDER BY name;
```

Do not assume configuration files live inside `PGDATA`; PostgreSQL
permits alternate configuration-file locations.

## 3. `listen_addresses`

`listen_addresses` controls which TCP/IP interfaces accept PostgreSQL
connections. Do not use `'*'` as a generic production recommendation.
Bind only to interfaces required by the approved architecture.

A network listener is not an authorization policy. Restrict exposure at
both the network layer and PostgreSQL authentication layer.

## 4. `pg_hba.conf`

HBA records are evaluated in order. The first record matching the
connection type, client address, database, and user determines the
authentication rule. Authentication failure does not cause PostgreSQL to
fall through to later HBA records.

This makes rule order a production-critical design property.

Inspect parsed rules where permitted:

``` sql
-- [SAFE-READ]
SELECT
  rule_number,
  type,
  database,
  user_name,
  address,
  netmask,
  auth_method,
  options,
  error
FROM pg_hba_file_rules
ORDER BY rule_number;
```

Any non-null `error` requires investigation.

## 5. Authentication Baseline

For password authentication, prefer SCRAM-SHA-256 for new PostgreSQL 18
deployments unless an approved integration requires another supported
method.

Do not use remote `trust` as a convenience mechanism. `trust` allows a
connecting client to claim a PostgreSQL user identity without password
authentication.

Other supported authentication designs can include certificates, GSSAPI,
LDAP, PAM, OAuth, peer authentication, and platform-specific mechanisms.
Select them from organizational requirements rather than tutorial
defaults.

## 6. TLS

Where policy requires encrypted client/server traffic:

-   enable and configure TLS using approved certificates;
-   protect private keys;
-   define certificate renewal ownership;
-   validate client behavior;
-   decide whether HBA must require `hostssl`;
-   validate hostname/certificate requirements where applicable.

`ssl=on` alone does not prove that every client connection is encrypted.

## 7. Database-Level Access

Passing HBA authentication is only one gate. Review `CONNECT` privilege
and role/object authorization separately.

``` sql
-- [SAFE-READ]
SELECT
  datname,
  datallowconn,
  has_database_privilege(current_user, datname, 'CONNECT') AS current_user_can_connect
FROM pg_database
ORDER BY datname;
```

## 8. Change Procedure

For a production authentication change:

1.  identify the exact client source, database, and role;
2.  record current HBA/network state;
3.  design the narrowest required rule;
4.  validate syntax;
5.  preserve an administrative recovery path;
6.  apply through the approved change process;
7.  reload only when required;
8.  test both intended access and intended denial;
9.  monitor authentication failures;
10. roll back if behavior differs from the plan.

Do not terminate existing sessions merely to test a new HBA rule.

## 9. Common Failure Modes

``` text
connection refused
    -> listener/service/network path

timeout
    -> routing/firewall/security boundary

no pg_hba.conf entry
    -> no matching HBA rule

password authentication failed
    -> credential/authentication mismatch

certificate failure
    -> TLS trust/identity/configuration

permission denied after login
    -> SQL privilege problem, not HBA
```

## 10. Production Checklist

``` text
[ ] required interfaces only
[ ] port documented
[ ] network controls reviewed
[ ] HBA rules reviewed in order
[ ] no unexplained HBA parse errors
[ ] authentication method approved
[ ] remote trust not used as a shortcut
[ ] TLS requirements validated
[ ] secrets stored outside repository
[ ] administrative recovery access tested
[ ] CONNECT/object privileges reviewed separately
[ ] rollback documented
```
