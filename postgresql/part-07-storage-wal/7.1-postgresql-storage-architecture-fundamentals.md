# 7.1 --- PostgreSQL Storage Architecture Fundamentals

**Target:** PostgreSQL 18\
**Classification:** Production Fundamentals\
**Lab:** `labs/storage-architecture-check.sql`\
**Lab Classification:** SAFE-READ\
**Status:** Canonical

## Purpose

PostgreSQL exposes logical objects such as databases, schemas, tables,
indexes, and rows. Beneath them is a physical storage system composed of
relations, forks, pages, buffers, WAL, tablespaces, temporary storage,
and PostgreSQL-managed files.

For administrators, DBREs, SREs, and platform engineers, the goal is to
connect SQL-visible objects to physical storage evidence safely.

## Logical to Physical Storage

``` text
PostgreSQL Cluster
  -> Database
     -> Schema
        -> Relation
           -> Relation forks
              -> Pages / blocks
                 -> PostgreSQL-managed files
                    -> Filesystem / storage
```

Logical names and filesystem representation are different layers.
Filesystem evidence should be correlated with PostgreSQL catalogs and
supported functions.

## Cluster Storage

Inspect the PostgreSQL data directory with:

``` sql
SHOW data_directory;
SELECT current_setting('data_directory');
```

Important PostgreSQL-managed locations include:

``` text
PGDATA/
+-- base/
+-- global/
+-- pg_tblspc/
+-- pg_wal/
+-- pg_xact/
+-- ...
```

Do not manually delete or modify PostgreSQL-managed files merely because
they appear large or unfamiliar.

## Relations and Storage Composition

Tables, indexes, materialized views, sequences, and TOAST relations are
examples of PostgreSQL relations.

A table's complete footprint can include:

``` text
Table
+-- heap
+-- indexes
+-- TOAST
+-- auxiliary forks
```

Therefore:

``` text
heap size != complete table storage footprint
```

## Relation Forks

Important relation forks include `main`, `fsm`, `vm`, and, where
applicable, `init`.

-   `main` contains primary relation data.
-   FSM tracks available free space.
-   VM tracks page visibility information.
-   The initialization fork is used for unlogged relations.

Later Part 7 modules inspect these structures in detail.

## Pages and Blocks

PostgreSQL organizes tables and indexes into fixed-size pages, also
called blocks. The common build uses 8 KiB pages, but operational
tooling must derive the actual value:

``` sql
SELECT current_setting('block_size');
```

Do not hard-code 8192 in production diagnostics.

## Shared Buffers

A simplified path is:

``` text
Query
  -> Executor
     -> Buffer Manager
        -> Shared Buffers
           -> Relation Storage
```

A buffered page can be clean or dirty. A dirty page contains changes not
yet persisted to the corresponding relation storage.

PostgreSQL also works with operating-system caching and specialized I/O
paths:

``` text
shared_buffers != all PostgreSQL memory
shared_buffers != all operating-system caching
```

## Write-Ahead Logging

A simplified modification path is:

``` text
Transaction change
   +-> modified page -> dirty buffer -> later relation write
   |
   +-> WAL record -> WAL buffer -> WAL flush -> durable commit
```

The write-ahead rule ensures required WAL reaches durable storage before
corresponding dirty data pages can be persisted in a way that would
violate recovery guarantees.

The central distinction is:

``` text
COMMIT durable != modified heap/index page already persisted
WAL flush      != dirty data-page flush
```

## Checkpoints

Checkpoint processing participates in persisting dirty pages and
establishing recovery boundaries.

``` text
transactions
  -> dirty buffers
  -> WAL continues
  -> checkpoint processing
  -> dirty-page writes
```

Checkpoint behavior affects recovery, WAL recycling, storage I/O, and
latency.

``` text
checkpoint != backup
```

The 7.1 lab observes checkpoint statistics but never issues
`CHECKPOINT`.

## WAL and LSNs

WAL normally resides under `PGDATA/pg_wal/`. PostgreSQL identifies
positions in the WAL stream with Log Sequence Numbers (LSNs).

On a primary:

``` sql
SELECT pg_current_wal_lsn();
```

The lab checks recovery state before treating this as applicable. Parts
7.9 and 7.10 cover WAL internals and WAL-volume measurement.

## Physical Relation Paths

Supported functions can correlate logical relations with
PostgreSQL-managed paths:

``` sql
SELECT pg_relation_filepath('some_table');
```

The returned path is relative to the cluster data directory. It is
diagnostic evidence, not permission to modify the file.

Never manually delete relation or WAL files to recover space.

## Size Functions

Different functions answer different storage questions:

``` sql
SELECT pg_relation_size('some_table');
SELECT pg_table_size('some_table');
SELECT pg_indexes_size('some_table');
SELECT pg_total_relation_size('some_table');
```

Therefore:

``` text
relation size != table size != index size != total relation size
```

`pg_class.relpages` is an estimate maintained by operations such as
VACUUM, ANALYZE, and some DDL. It is not an exact real-time filesystem
block count.

## Database Size

``` sql
SELECT
    current_database(),
    pg_size_pretty(pg_database_size(current_database()));
```

Database size still does not represent complete cluster or filesystem
capacity requirements. WAL, temporary files, other databases,
tablespaces, logs, and operational headroom can consume additional
space.

``` text
database size != required filesystem capacity
```

## Tablespaces

Tablespaces allow PostgreSQL-managed objects to reside in alternate
filesystem locations. They are not independent PostgreSQL databases.

Part 7.12 covers tablespace architecture and operational placement
decisions.

## Temporary Storage

Sorts, hashes, aggregations, index creation, and other executor work can
generate temporary storage activity when required memory exceeds the
operation's available memory.

``` text
filesystem growth != automatically permanent relation growth
```

Part 7.13 covers temporary-file spill behavior.

## Evidence-First Production Diagnosis

Use this sequence:

``` text
1. Identify instance and database.
2. Record observation time and PostgreSQL version.
3. Determine block size.
4. Identify data-directory context.
5. Identify tablespaces.
6. Measure database storage.
7. Identify large relations.
8. Separate table/index/total storage.
9. Correlate relations with PostgreSQL-managed paths.
10. Observe WAL state.
11. Observe WAL/checkpointer statistics.
12. Correlate with filesystem/storage metrics.
13. State what the evidence proves.
14. Preserve unknowns.
```

For an alert such as "PostgreSQL volume increased by 300 GB", possible
contributors include heap growth, indexes, TOAST, dead-row/bloat
effects, WAL growth or retention, temporary files, new relations,
tablespaces, logs, or non-PostgreSQL filesystem usage.

Do not infer the cause merely from the largest relation.

## Production Safety Rules

1.  Do not manually modify PostgreSQL relation files.
2.  Do not manually modify WAL files.
3.  Do not delete unknown files from the data directory.
4.  Do not force checkpoints merely for demonstration.
5.  Do not reset statistics during evidence collection without an
    approved test.
6.  Do not assume the default page size.
7.  Do not expose credentials or sensitive application data.
8.  Do not interpret inaccessible evidence as healthy.
9.  Correlate PostgreSQL evidence with infrastructure evidence.
10. Preserve timestamps.

If evidence cannot be obtained:

``` text
UNKNOWN / INSUFFICIENT PRIVILEGE
```

is more accurate than declaring the condition healthy.

## Core Invariants

``` text
logical row      != physical tuple
tuple            != page
page             != relation

heap size        != total table footprint
database size    != cluster storage requirement

WAL              != heap storage
WAL flush        != dirty-page flush
COMMIT           != checkpoint
checkpoint       != backup

FSM              != visibility map
tablespace       != independent database
temporary file   != permanent relation storage
shared_buffers   != total PostgreSQL memory
```
