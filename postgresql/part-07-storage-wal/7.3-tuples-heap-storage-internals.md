# 7.3 --- Tuples and Heap Storage Internals

**Target:** PostgreSQL 18\
**Classification:** Production Fundamentals\
**Lab:** `labs/heap-tuple-inspection.sql`\
**Lab Classification:** SAFE-READ\
**Status:** Canonical

## Purpose

Part 7.2 established pages and blocks. Part 7.3 moves one level deeper:

``` text
Relation -> Heap Page -> Item Identifier / Line Pointer -> Heap Tuple -> Tuple Header -> Tuple Data
```

The goal is to understand how a logical SQL row is represented
physically inside a PostgreSQL heap relation. Detailed MVCC visibility
analysis belongs to Part 7.4.

## Logical Rows and Physical Tuple Versions

Applications work with logical rows; PostgreSQL stores physical tuple
versions.

``` text
logical row != physical tuple version
```

A logical row can be represented by different physical tuple versions
during its lifetime.

## Heap Storage

An ordinary PostgreSQL table uses heap storage. A heap relation consists
of pages, and each page can contain multiple tuple versions. Heap
storage is not application-level primary-key, creation-time, or
business-time ordering.

## Line Pointers and Tuples

A heap page contains line pointers and tuple data as separate
structures.

``` text
line pointer != tuple
```

A line pointer identifies the location and state of an item on the page.

## CTID

PostgreSQL exposes a row version's physical location through `ctid`:

``` text
ctid = (block number, item number)
CTID = physical tuple-version location
CTID != durable logical row identifier
```

Applications should not use CTID as persistent business identity.

## Heap Tuple Structure

Conceptually:

``` text
+--------------------------------+
| Fixed tuple header             |
+--------------------------------+
| Optional NULL bitmap           |
+--------------------------------+
| Optional / historical fields   |
+--------------------------------+
| Alignment / padding            |
+--------------------------------+ <- t_hoff
| User attribute data            |
+--------------------------------+
```

On most systems the fixed heap tuple header occupies 23 bytes before
optional portions and alignment.

``` text
physical tuple size != sum(logical column sizes)
```

## Heap Tuple Header

Important physical fields include:

``` text
t_xmin
t_xmax
t_cid / t_xvac
t_ctid
t_infomask2
t_infomask
t_hoff
```

These contain physical and transaction-related metadata; they are not a
complete MVCC visibility decision by themselves.

### `t_xmin`

`t_xmin` records the transaction ID associated with insertion of this
particular tuple version.

### `t_xmax`

`t_xmax` contains transaction-related information associated with
deletion, update, or locking state.

``` text
xmax != 0 != tuple definitely dead
```

Visibility depends on additional MVCC state and is covered in Part 7.4.

### `t_cid` and `t_xvac`

`t_cid` and `t_xvac` share an overlaid physical field rather than being
two independent simultaneously stored fields.

### `t_ctid`

`t_ctid` is physical tuple metadata and can participate in linking
toward another tuple version. It is not durable application identity.

### `t_infomask` and `t_infomask2`

These contain tuple-state and representation flags.

``` text
decoded tuple flags != complete MVCC visibility determination
```

The canonical 7.3 lab records raw values and defers deeper
interpretation to Part 7.4.

### `t_hoff`

`t_hoff` identifies the offset from the beginning of the tuple to the
start of user attribute data.

## NULL Bitmap

When applicable, PostgreSQL maintains null-state information in a tuple
NULL bitmap. The 7.3 lab does not decode application attributes from it.

## Multiple Physical Tuple Versions

One logical row can be associated with multiple physical tuple versions
over time.

``` text
physical tuple versions != currently visible logical rows
physical tuple observations != SELECT count(*) result
```

Low-level physical evidence must not automatically be interpreted as
corruption or inconsistency.

## Inspecting Heap Tuples with `pageinspect`

PostgreSQL provides:

``` sql
heap_page_items(get_raw_page(...))
```

The canonical lab uses this only after an explicit target, ordinary
heap-table validation, block validation, `pageinspect` availability, and
sufficient privilege.

The target is restricted to:

``` text
relkind = 'r'
```

## Production Safety

The lab never automatically executes:

``` sql
CREATE EXTENSION pageinspect;
```

It never prints raw `get_raw_page()` output and never uses:

``` sql
SELECT * FROM heap_page_items(...);
```

Normal evidence excludes:

``` text
t_data
decoded application attributes
application column values
raw page bytea
```

The lab also does not classify tuples as LIVE, DEAD, COMMITTED, ABORTED,
VISIBLE, or INVISIBLE from tuple metadata alone.

# Hands-On Lab --- Heap Tuple Inspection

**File:** `labs/heap-tuple-inspection.sql`\
**Classification:** SAFE-READ

## Level 1 --- Baseline

Collect timestamp, PostgreSQL version, database, session user, recovery
state, block size, `pageinspect` availability, and target status. No raw
page access occurs without an explicit target.

## Level 2 --- Explicit Tuple Inspection

The operator supplies:

``` text
inspect_schema
inspect_relation
inspect_block
```

The lab validates:

``` text
target exists
 -> ordinary heap table
 -> main fork contains blocks
 -> requested block valid
 -> pageinspect installed
 -> required privilege available
 -> heap_page_items()
 -> structural metadata only
```

Approved structural output includes:

``` text
observed_at
database
schema
relation
block_number
lp
lp_off
lp_flags
lp_len
t_xmin
t_xmax
t_field3
t_ctid
t_infomask2
t_infomask
t_hoff
```

## Evidence Classification

``` text
OBSERVED
NOT APPLICABLE
PREREQUISITE NOT MET
INSUFFICIENT PRIVILEGE
UNKNOWN
REVIEW
```

Missing evidence is never interpreted as healthy evidence.

## Safety Boundary

The lab performs no DDL, DML, VACUUM, CHECKPOINT, statistics reset,
configuration change, filesystem or WAL modification, session
termination, raw-page output, `t_data` output, attribute reconstruction,
application-value decoding, or automatic visibility classification.

## Core Invariants

``` text
logical row != physical tuple version
line pointer != heap tuple
CTID = physical tuple-version location
CTID != durable logical identifier
tuple header != application payload
physical tuple size != sum of logical column sizes
xmin/xmax = physical transaction metadata
xmin/xmax alone != complete visibility determination
xmax != 0 != automatically dead tuple
physical tuple observations != visible row count
heap_page_items() != permission to expose t_data
page inspection != permission to modify storage
```
