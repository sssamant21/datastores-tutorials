# 7.2 --- Pages, Blocks, and Physical Layout

**Target:** PostgreSQL 18\
**Classification:** Production Fundamentals\
**Lab:** `labs/page-block-inspection.sql`\
**Lab Classification:** SAFE-READ\
**Status:** Canonical

## Purpose

PostgreSQL stores table and index relations as sequences of fixed-size
pages, also called blocks.

This module moves one level below the relation architecture introduced
in Part 7.1:

``` text
Relation
  -> Fork
     -> Blocks / Pages
        -> Page Header
        -> Item Identifiers
        -> Free Space
        -> Items / Tuples
        -> Special Space
```

The goal is structural understanding. Detailed heap tuple internals
belong to Part 7.3, MVCC storage behavior to Part 7.4, FSM/VM internals
to Part 7.5, and relation-file segmentation to Part 7.7.

## Page and Block Terminology

Within PostgreSQL relation-storage discussions, page and block commonly
describe the same fixed-size unit.

``` text
Relation main fork
 +-- Block 0
 +-- Block 1
 +-- Block 2
 +-- ...
```

Each block contains one PostgreSQL page.

``` text
page == block
```

in this PostgreSQL storage context. A PostgreSQL block is not the same
concept as an operating-system filesystem block or storage-device
sector.

## PostgreSQL Page Size

The common PostgreSQL build uses an 8 KiB page size, but production
tooling should derive the actual server value:

``` sql
SELECT current_setting('block_size');
```

Do not hard-code 8192 in production diagnostics.

## Relation Size and Block Count

For the main fork:

``` text
main_fork_blocks = main_fork_bytes / block_size
```

Use supported PostgreSQL evidence:

``` sql
SELECT pg_relation_size('some_table', 'main');
```

together with the dynamically observed block size.

## Block Numbers

Blocks are numbered from zero.

For a ten-block relation, valid block numbers are 0 through 9. Before
low-level inspection:

``` text
requested block >= 0
AND
requested block < relation block count
```

must hold.

## Block Number and Byte Offset

Conceptually:

``` text
byte offset = block number * block size
```

This is useful for understanding physical layout. It is not an
instruction to open or modify PostgreSQL relation files manually.

## Standard Page Structure

A PostgreSQL page contains several logical regions:

``` text
+---------------------------------------+
| PageHeaderData                        |
+---------------------------------------+
| ItemIdData / line pointers            |
|             ↓                         |
|                                       |
|           Free Space                  |
|                                       |
|                              ↑        |
| Items / tuples                        |
+---------------------------------------+
| Special Space                         |
+---------------------------------------+
```

The standard page header is 24 bytes. Each item identifier occupies four
bytes. Exact item interpretation depends on the relation type.

## Page Header

Common page-header fields include:

``` text
pd_lsn
pd_checksum
pd_flags
pd_lower
pd_upper
pd_special
pd_pagesize_version
pd_prune_xid
```

The 7.2 lab focuses on structural metadata and deliberately avoids
printing tuple payloads.

## `pd_lsn`

`pd_lsn` records the WAL location associated with the page's most recent
relevant change. Detailed WAL analysis remains in Parts 7.9 and 7.10.

## `pd_checksum`

`pd_checksum` contains checksum information when data checksums are
enabled.

Inspect cluster configuration first:

``` sql
SHOW data_checksums;
```

If checksums are disabled, checksum interpretation is `NOT APPLICABLE`.
A checksum observation by itself is not sufficient to declare
corruption.

## `pd_lower`, `pd_upper`, and `pd_special`

`pd_lower` marks the end of the item-identifier array. `pd_upper` marks
the beginning of stored item data from the upper side of the page.
`pd_special` marks the beginning of special space.

``` text
Page start
  |
  | Header
  | Item identifiers
  |
pd_lower
  |
  | contiguous unallocated space
  |
pd_upper
  |
  | tuple/item data
  |
pd_special
  |
  | special space
  |
Page end
```

A useful structural calculation is:

``` text
contiguous_page_free_bytes = pd_upper - pd_lower
```

when page boundaries are valid.

This is page-local free space, not filesystem free space.

## Page Boundary Relationships

Useful structural checks include:

``` text
pd_lower <= pd_upper
pd_upper <= pd_special
pd_special <= block_size
reported page size == configured block size
```

These are observations, not an automatic corruption verdict.

The lab therefore uses evidence states such as:

``` text
OBSERVED
REVIEW
UNKNOWN
```

## Item Identifiers and CTID

PostgreSQL pages maintain an array of item identifiers, also called line
pointers.

A tuple's `ctid` connects SQL-visible physical identity to page storage:

``` text
CTID
 +-- block number
 +-- item position
```

For example, `(42,7)` refers to an item position on block 42.

``` text
CTID != permanent logical row identifier
```

Applications should not use CTID as a durable business key.

Detailed tuple interpretation belongs to Part 7.3.

## Page Free Space Versus Filesystem Space

A critical production distinction is:

``` text
free space inside PostgreSQL page
              !=
filesystem reclaimable space
```

PostgreSQL can reuse free space within existing pages without shrinking
the underlying relation file.

``` text
reusable page space != filesystem-released capacity
```

This distinction becomes important for VACUUM, dead tuples, bloat, and
capacity analysis.

## Relation Files and Segmentation

A relation is not necessarily represented by one operating-system file.
Large relations can be divided into multiple physical file segments.

The normal PostgreSQL build commonly uses 1 GiB relation segments, but
segment size is a build-time characteristic and should not be treated as
an immutable constant.

Detailed file segmentation belongs to Part 7.7.

## `pageinspect`

PostgreSQL provides the `pageinspect` extension for low-level page
inspection.

Useful interfaces include:

``` sql
get_raw_page(...)
page_header(...)
page_checksum(...)
```

`get_raw_page()` obtains a page image. `page_header()` interprets common
structural metadata.

Low-level page inspection requires appropriate privileges.

## Production Rule --- Do Not Automatically Install `pageinspect`

The lab does not run:

``` sql
CREATE EXTENSION pageinspect;
```

Instead:

``` text
pageinspect installed?
  NO  -> PREREQUISITE NOT MET
  YES -> check inspection privilege
```

Installing an extension is outside this SAFE-READ lab.

## Production Rule --- Never Dump Raw Pages

The normal lab output never prints the raw `bytea` returned by
`get_raw_page()`.

``` text
get_raw_page()
      |
      v
page_header()
      |
      v
structural metadata only
```

This reduces the risk of application tuple contents appearing in
terminal output, screenshots, tickets, CI logs, or incident evidence.

## Explicit Inspection Target

The lab never automatically chooses the largest application relation for
raw-page inspection.

The operator must explicitly provide:

``` text
schema
relation
block number
```

If no target is supplied, the lab performs baseline inventory only.

## Target Validation

Before inspection:

``` text
relation exists?
  -> supported relation type?
     -> main fork contains blocks?
        -> block number valid?
           -> pageinspect installed?
              -> sufficient privilege?
                 -> inspect structural metadata
```

Failure at a gate becomes evidence rather than unsafe behavior.

## Evidence Classification

The canonical lab uses:

``` text
OBSERVED
NOT APPLICABLE
PREREQUISITE NOT MET
INSUFFICIENT PRIVILEGE
UNKNOWN
REVIEW
```

Missing evidence is never automatically interpreted as healthy.

## Core Invariants

``` text
page == block
    within PostgreSQL relation-storage terminology

PostgreSQL block != operating-system filesystem block
relation         != one page
relation         != necessarily one OS file
page size        != tuple size
page free space  != filesystem free space
block number     != byte offset
byte offset      = block number * block size
CTID             != permanent logical row identifier
page inspection  != permission to modify a page
structural anomaly != automatic corruption verdict
```
