# Part 4.12 — Authentication Architecture and `pg_hba.conf` Policy

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Track:** Part 4 — Users, Roles & Security

## 1. Why Authentication Architecture Matters

PostgreSQL authorization begins only after a client establishes an authenticated database session.

```text
client
  ↓
network path
  ↓
ordered pg_hba.conf rule selection
  ↓
authentication
  ↓
PostgreSQL role
  ↓
CONNECT authorization
  ↓
object privileges
  ↓
RLS / routines / application controls
```

Authentication determines who may attempt to establish a session, from where, to which database, as which PostgreSQL role, and using which authentication mechanism.

It does not determine which application objects or rows the authenticated role may access.

## 2. Authentication vs Authorization

Keep these boundaries explicit:

```text
Authentication → establish identity/session
Authorization  → determine permitted database operations
```

`pg_hba.conf` participates primarily in connection authentication policy. It does not replace `CONNECT`, `GRANT`/`REVOKE`, role membership, ownership, RLS, or `SECURITY DEFINER` controls.

Therefore, authentication success does not imply application authorization.

## 3. Layered Connection Model

A useful production model is:

```text
network reachability
+ ordered HBA rule selection
+ authentication mechanism
+ identity mapping
+ CONNECT privilege
= potential database session
```

After that, schema/object privileges, ownership, RLS, routines, and application controls govern usable access.

## 4. HBA Record Structure

A typical HBA record contains:

```text
TYPE DATABASE USER ADDRESS METHOD OPTIONS
```

Example:

```text
hostssl appdb app_runtime 10.20.0.0/16 scram-sha-256
```

No individual field should be interpreted independently of the complete rule.

## 5. Connection Types

Important types include `local`, `host`, `hostssl`, `hostnossl`, `hostgssenc`, and `hostnogssenc`.

`hostssl` is a transport requirement; `scram-sha-256` is an authentication mechanism. SCRAM is not TLS, and TLS is not database authorization.

## 6. Database and User Matching

The DATABASE field can include special selectors such as `all`, `sameuser`, `samerole`, and `replication`; it is not always one literal database.

The USER field can involve explicit roles and role/group-oriented selectors, so role membership can matter. Authentication architecture and PostgreSQL role architecture must be reviewed together.

## 7. Address Matching

Host rules can restrict source addresses or networks, including broad or special selectors such as `0.0.0.0/0`, `::/0`, `samehost`, and `samenet`.

Broad selectors are review signals, not automatic proof of Internet exposure. Routing, firewalls, security groups, private networking, and service networking also affect reachability.

## 8. Ordered First-Match Policy

HBA rules are ordered. PostgreSQL uses the first matching rule. If authentication under that selected rule fails, later HBA rules are not fallback authentication choices.

Therefore, rule order is security behavior. Never reorder HBA evidence merely to simplify audit output.

## 9. Included HBA Files and External Lists

HBA configuration can use `include`, `include_if_exists`, and `include_dir`. Included records participate in the ordered policy at their inclusion point. `@filename` constructs can expand database/user lists.

Preserve `rule_number`, `file_name`, and `line_number` together during review.

## 10. `pg_hba_file_rules`

PostgreSQL exposes `pg_hba_file_rules` for parsed HBA inspection. Important evidence includes rule number, file and line provenance, type, database, user, address, netmask, authentication method, options, and parser error.

In PostgreSQL 18, `address` and `netmask` are text; `database`, `user_name`, and `options` are arrays of text.

## 11. File State vs Loaded State

`pg_hba_file_rules` represents current HBA file contents PostgreSQL can inspect. It must not be treated by itself as proof of the last successfully loaded runtime authentication policy.

```text
current file state != last successfully loaded runtime state
```

## 12. Inspection Privileges and Parser Errors

Security-sensitive configuration views can require elevated privileges. Do not weaken production privileges merely so an acceptance script can run.

Surface `error IS NOT NULL` as configuration evidence requiring review, without automatically declaring an outage or vulnerability.

## 13. Authentication Methods

PostgreSQL supports authentication architectures including SCRAM-SHA-256, password, trust, reject, peer, certificate, GSSAPI, SSPI, LDAP, PAM, and PostgreSQL 18 OAuth.

Methods should be selected intentionally rather than inherited indefinitely from legacy configurations.

## 14. SCRAM and Password Encryption

For modern password-based deployments, SCRAM should normally be the design target where supported.

`password_encryption` can be inspected safely. A generic acceptance artifact should never expose `pg_authid.rolpassword` or other credential-verifier contents.

## 15. PostgreSQL 18 MD5 Deprecation

PostgreSQL 18 deprecates MD5 password authentication. An HBA `md5` rule should trigger migration/modernization review, not an automatic vulnerability declaration.

If the HBA method is `md5` but a role has a SCRAM verifier, PostgreSQL can perform SCRAM authentication. Therefore an `md5` HBA entry does not prove MD5 was used on the wire.

## 16. `password`, `trust`, and `reject`

A `password` rule requires review of transport protection. Its presence alone does not prove a password crossed the network unencrypted.

A `trust` rule is highly security-sensitive and should be reviewed for database, role, network, order, and surrounding controls.

A `reject` rule is also order-sensitive; a prior matching rule can make a later reject irrelevant for that connection.

## 17. Peer, OAuth, and Username Mapping

`peer` authentication depends on local operating-system identity and socket access.

PostgreSQL 18 OAuth belongs in the authentication architecture but the generic lab must never expose or test bearer tokens, refresh tokens, or client secrets.

Where external identities are mapped to PostgreSQL roles, `pg_ident.conf` and `pg_ident_file_mappings` become security-sensitive evidence.

## 18. TLS vs Authentication

Transport encryption, server verification, client identity, authentication, and database authorization are distinct security questions. Part 4.13 covers TLS and client certificates in depth.

## 19. HBA Does Not Grant `CONNECT` or Object Access

A potential session requires network reachability, a matching HBA rule, successful authentication, and `CONNECT` authorization.

Even then, schema/table/routine privileges, ownership, RLS, and application controls still govern access.

## 20. Reload Behavior and Existing Sessions

On typical self-managed Unix-like systems, HBA changes require configuration reload before new connections use the changed policy. Windows behavior differs, and managed services may use provider-specific mechanisms.

The SAFE-READ acceptance artifact must never call `pg_reload_conf()`.

Changing HBA policy does not automatically terminate existing sessions. Connection pools can therefore mask new-connection authentication failures.

## 21. Replication and Service Identities

HBA changes can affect replication, HA, DR, applications, monitoring, backup, ETL, migration tooling, health checks, automation, and administrative tooling.

Inventory these dependencies before tightening authentication.

## 22. DNS Dependencies

Hostname-dependent HBA rules make DNS part of the authentication architecture. Review forward/reverse resolution, availability, correctness, and latency where relevant.

## 23. Managed PostgreSQL Services

Managed services may implement authentication/network policy through service parameters, firewalls, security groups, private networking, cloud IAM, TLS requirements, and provider controls rather than direct HBA file editing.

Separate PostgreSQL authentication concepts from provider-specific implementation.

## 24. Production Investigation Workflow

1. Record `current_database()`, `session_user`, `current_user`, and `current_role`.
2. Identify HBA configuration location where permitted.
3. Inspect `pg_hba_file_rules` while preserving rule order and file provenance.
4. Review parser errors.
5. Review authentication methods, especially `trust`, `password`, `md5`, `reject`, SCRAM, and OAuth.
6. Review type, database, user, address, and options together.
7. Review username mappings where applicable.
8. Inventory applications, pools, administrators, replication, monitoring, backup, and automation.
9. Perform controlled expected-allow and expected-deny tests separately.
10. Preserve an independently tested administrative recovery path.

## 25. Production Change Safety and Rollback

Before modifying authentication policy, capture the current configuration and included files, identify dependencies, validate syntax, obtain appropriate review, verify recovery, activate through the approved mechanism, test new allowed and denied connections, validate replication/background services, and monitor.

Rollback should restore a known-good authentication state. Do not reconstruct authentication policy from memory during a lockout.

## 26. SAFE-READ Acceptance Strategy

The canonical artifact inspects execution context, HBA/ident locations, password-encryption and authentication-timeout settings, parsed HBA rules, order and provenance, matching selectors, methods/options, parser errors, sensitive-method review signals, and username-map evidence where permitted.

It does not edit HBA/ident configuration, reload PostgreSQL, change credentials/roles/privileges, inspect password verifiers, modify networking, test credentials/OAuth, or terminate sessions.

```text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
```

## 27. Evidence Sensitivity

Authentication evidence can expose internal networks, database/role names, methods, identity mappings, replication paths, filesystem paths, and administrative architecture.

```text
SAFE-READ != safe to publish
```

Protect production evidence appropriately.

## 28. Key Takeaways

```text
HBA rule exists            != rule selected
later specific rule        != effective if an earlier rule matches
authentication failure     != fallback to later HBA rule
current HBA file           != proof of last loaded runtime policy
HBA match                  != authentication success
authentication success     != CONNECT privilege
CONNECT                    != table access
SCRAM                      != TLS
HBA says md5               != proof MD5 authentication occurred
HBA changed                != existing sessions terminated
SAFE-READ                  != safe to publish
```

For DBRE/SRE teams, `pg_hba.conf` should be managed as ordered production authentication policy with explicit validation, recovery, evidence protection, and rollback.
