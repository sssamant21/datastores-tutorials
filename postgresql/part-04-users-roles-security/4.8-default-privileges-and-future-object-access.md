# Part 4.8 — Default Privileges and Future-Object Access

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Track:** Part 4 — Users, Roles & Security

---

## 1. Why Default Privileges Matter

A common PostgreSQL production problem looks like this:

```text
Existing tables work.
New tables fail.
```

For example, an application can successfully access:

```text
clinical.patient
clinical.provider
clinical.encounter
```

but a newly deployed table:

```text
clinical.claim
```

returns:

```text
permission denied for table claim
```

Privileges granted to existing objects are not automatically copied to objects created later.

PostgreSQL provides:

```sql
ALTER DEFAULT PRIVILEGES
```

to control privileges assigned when future objects are created.

The fundamental rule is:

```text
ALTER DEFAULT PRIVILEGES
        |
        +-- future objects
        |
        X-- existing objects
```

Default privileges should therefore be part of the application's ownership and deployment design rather than a workaround added after repeated permission failures.

---

## 2. Learning Objectives

By the end of this tutorial, you should be able to:

- distinguish current-object grants from future-object defaults,
- identify the role whose defaults govern object creation,
- understand `FOR ROLE`,
- understand schema-scoped defaults,
- distinguish global and per-schema defaults,
- configure defaults for tables, sequences, routines, types, and supported PostgreSQL 18 object classes,
- account for `PUBLIC`,
- understand `MAINTAIN` in future-table access,
- inspect `pg_default_acl`,
- expand configured ACL entries,
- troubleshoot wrong-creator deployment drift,
- design rollback for incorrect default privileges,
- and validate default privilege configuration safely.

## 3. Existing Objects vs Future Objects

A command such as:

```sql
GRANT SELECT
ON TABLE clinical.patient
TO app_readonly;
```

changes an existing table.

Likewise:

```sql
GRANT SELECT
ON ALL TABLES IN SCHEMA clinical
TO app_readonly;
```

operates on applicable tables that already exist when the command runs.

Neither establishes a permanent rule for tables created later.

Conceptually:

```text
GRANT
   |
   +-- current/existing objects

ALTER DEFAULT PRIVILEGES
   |
   +-- future objects
```

A mature access model commonly needs both.

---

## 4. The Creating Role Is the Critical Boundary

Default privileges are tied to the role under which future objects are created.

Suppose the application uses:

```text
app_owner
migration_login
app_runtime
app_readonly
```

and the desired object owner is:

```text
app_owner
```

The critical question is:

> Which role is current when CREATE executes?

Default privileges are not automatically collected from every role that the current role belongs to.

Therefore:

```text
role membership
      !=
use of that role's default privileges
```

This distinction is essential in automated deployment systems.

---

## 5. FOR ROLE

PostgreSQL supports:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
...
```

Conceptually:

```text
FOR ROLE app_owner
        |
        v
default policy associated with
objects subsequently created
under that role's creation context
```

For example:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA clinical
GRANT SELECT
ON TABLES
TO app_readonly;
```

This is a security-mutating administrative example. It is not part of the SAFE-READ acceptance artifact.

---

## 6. Deployment Roles and SET ROLE

A deployment login can intentionally switch to an owner role:

```sql
SET ROLE app_owner;
```

and then create application objects.

A controlled design may therefore look like:

```text
migration_login
       |
       | controlled SET ROLE
       v
app_owner
       |
       +-- CREATE objects
       +-- own objects
       +-- supply applicable default privileges
```

Before object creation, a deployment can validate:

```sql
SELECT
    session_user,
    current_user,
    current_role;
```

This is an important protection against wrong-creator deployment drift.

Role membership and `SET ROLE` capability should still follow least privilege. Do not grant broad membership merely to simplify deployments.

---

## 7. Wrong-Creator Drift

Suppose defaults are configured for:

```text
app_owner
```

but a deployment creates objects directly while:

```text
current_user = migration_login
```

The expected default privilege configuration can be missed.

Conceptually:

```text
Expected

migration_login
      |
      | SET ROLE
      v
app_owner
      |
      +-- CREATE TABLE


Drift

migration_login
      |
      +-- CREATE TABLE directly
```

This is a major cause of:

```text
old objects work
new objects fail
```

or inconsistent ACLs across deployments.

---

## 8. Schema-Scoped Defaults

Default privileges can be scoped to supported objects created in a particular schema.

Example:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA clinical
GRANT SELECT
ON TABLES
TO app_readonly;
```

This allows different policies for:

```text
clinical
billing
reporting
internal_admin
```

Schema scope is therefore a useful least-privilege boundary.

Not every default-privilege object category supports `IN SCHEMA`. For example, large objects are not schema-contained objects.

---

## 9. Future Table Privileges

A read-only role might receive:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA clinical
GRANT SELECT
ON TABLES
TO app_readonly;
```

A runtime role might instead require:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA clinical
GRANT SELECT, INSERT, UPDATE, DELETE
ON TABLES
TO app_runtime;
```

The privilege list should come from the application's access contract.

Avoid using `ALL PRIVILEGES` as a substitute for defining the actual requirement.

---

## 10. Future Sequence Privileges

Table defaults do not automatically provide sequence access.

Applications that use sequences may require separate defaults:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA clinical
GRANT USAGE
ON SEQUENCES
TO app_runtime;
```

Additional sequence privileges should be granted only when the application's operations require them.

Remember:

```text
table defaults
    !=
sequence defaults
```

---

## 11. Future Routine Privileges

PostgreSQL supports default privileges for routines.

Prefer the collective terminology:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA clinical
GRANT EXECUTE
ON ROUTINES
TO app_runtime;
```

`FUNCTIONS` is also accepted in this context, but `ROUTINES` expresses the collective function/procedure intent more clearly.

Functions and procedures do not receive independently configurable default privilege policies through separate default ACL classes.

In `pg_default_acl`, routine defaults use:

```text
defaclobjtype = 'f'
```

---

## 12. PUBLIC and Routine Defaults

Routine access deserves additional attention because PostgreSQL's built-in defaults normally include routine execution for `PUBLIC`.

A security review should therefore ask:

```text
What does PUBLIC receive?

What custom global defaults exist?

What schema-specific additions exist?

Which named roles receive EXECUTE?
```

Do not conclude that a routine is restricted merely because an application role has an explicit `EXECUTE` grant.

---

## 13. Future Type Privileges

Default privileges can apply to types.

For example:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA clinical
GRANT USAGE
ON TYPES
TO app_runtime;
```

This can matter for application-defined domains, enums, composite types, ranges, and other user-defined types.

---

## 14. Future MAINTAIN Privileges

PostgreSQL 18 permits `MAINTAIN` as part of table default privileges.

For example:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA clinical
GRANT MAINTAIN
ON TABLES
TO dbre_role;
```

This can be useful when a DBRE role genuinely requires maintenance authority over every future table in the specified creation scope.

However:

```text
can receive MAINTAIN
        !=
should automatically receive MAINTAIN
```

The blast radius must be evaluated.

Also remember:

```text
authorized to maintain
        !=
operationally safe to maintain now
```

Maintenance operations can still affect locks, I/O, WAL, replicas, latency, CPU, and storage.

---

## 15. PostgreSQL 18 Large-Object Defaults

PostgreSQL 18 supports default privileges for large objects.

In `pg_default_acl`, the object-type code is:

```text
L = LARGE OBJECT
```

This is PostgreSQL 18-specific functionality and should not be silently generalized to older PostgreSQL releases.

Large objects are not schema-contained objects, so schema-scoped assumptions used for tables or routines do not apply to them.

---

## 16. Existing Objects Are Not Retroactively Changed

Suppose `clinical.patient` already exists.

Then you configure:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA clinical
GRANT SELECT
ON TABLES
TO app_readonly;
```

The existing table does not suddenly acquire that grant.

A migration may therefore require two distinct phases:

```text
Phase 1
Existing-object remediation

        +

Phase 2
Future-object defaults
```

These must be validated separately.

---

## 17. pg_default_acl

Customized default privilege information is represented in `pg_default_acl`.

Important columns include:

```text
defaclrole
defaclnamespace
defaclobjtype
defaclacl
```

Conceptually:

```text
pg_default_acl
      |
      +-- creator/default owner
      +-- global or schema scope
      +-- object class
      +-- ACL
```

---

## 18. PostgreSQL 18 Object-Type Codes

| Code | Object class |
|---|---|
| `r` | relation/table |
| `S` | sequence |
| `f` | function/routine |
| `T` | type |
| `n` | schema |
| `L` | large object |

---

## 19. Global Default Privileges

A `pg_default_acl` entry with `defaclnamespace = 0` represents a global default privilege entry.

Global customized defaults participate in determining the initial privileges for future objects of that class created by the targeted role.

They must be reviewed carefully because they can affect objects beyond one application schema.

---

## 20. Per-Schema Default Privileges

A nonzero `defaclnamespace` references a schema-specific default privilege configuration.

Conceptually:

```text
global/built-in defaults
        +
per-schema additions
        =
future object's initial privilege configuration
```

---

## 21. Per-Schema REVOKE Is Not a Global Override

Do not assume:

```text
global default GRANT
        +
schema default REVOKE
        =
global privilege removed
```

Per-schema default privileges are additive relative to the global/default behavior.

A schema-level default `REVOKE` therefore cannot simply cancel a privilege supplied by a global default.

Always inspect both global defaults and schema-specific defaults before predicting future ACLs.

---

## 22. Quick Inspection with psql

For interactive administration, `psql` provides:

```text
\ddp
```

This displays default access privilege settings that differ from PostgreSQL's built-in defaults.

For automated acceptance checks, `pg_default_acl` remains preferable because SQL output is easier to inspect, filter, compare, and retain as evidence.

---

## 23. Expanding Default ACLs

PostgreSQL's `aclexplode()` can expand an ACL into fields such as:

```text
grantor
grantee
privilege_type
is_grantable
```

This is valuable audit evidence.

However:

```text
aclexplode()
        !=
complete effective access calculation
```

It expands configured ACL entries. Effective authorization can additionally involve ownership, role membership, `PUBLIC`, superuser authority, predefined roles, and object-specific security mechanisms.

Part 4.9 examines effective access more deeply.

---

## 24. Troubleshooting — Existing Tables Work, New Tables Fail

Investigate:

```text
actual object creator
current_user during CREATE
object owner
schema
global default ACL
schema-specific default ACL
PUBLIC
actual resulting object ACL
```

Do not simply repeat the grant manually on every new table without identifying why the future-object policy failed.

---

## 25. Troubleshooting — Defaults Configured for Wrong Role

Check who owns the default ACL, who actually created the object, whether `SET ROLE` was executed, and what `current_user` was during `CREATE`.

---

## 26. Troubleshooting — Tables Work but Inserts Fail

A deployment may correctly configure `TABLES` but omit `SEQUENCES`.

A sequence-backed insert can therefore fail even when the table's ACL is correct.

Audit the two object classes independently.

---

## 27. Troubleshooting — Unexpected Routine Exposure

If a new routine appears executable by more roles than expected, review built-in defaults, custom global defaults, schema-specific defaults, `PUBLIC`, and the explicit routine ACL.

For `SECURITY DEFINER` routines, unexpected execution exposure deserves additional security review.

---

## 28. Rollback Strategy

Reversing a default privilege configuration changes what happens afterward. It does not automatically repair objects created while the incorrect default was active.

A proper rollback includes:

1. Restore intended default configuration.
2. Identify objects created during the affected interval.
3. Inspect their actual ACLs.
4. Remediate affected existing objects separately.
5. Validate future-object behavior.

---

## 29. Production Investigation Workflow

1. Confirm `session_user`, `current_user`, and `current_role`.
2. Identify creator and owner.
3. Inspect global defaults.
4. Inspect schema defaults.
5. Inspect object type.
6. Inspect `PUBLIC`.
7. Inspect resulting object ACL.
8. Compare deployment behavior.

---

## 30. Managed PostgreSQL Services

The PostgreSQL default privilege model remains foundational on managed PostgreSQL platforms.

However, managed services may introduce restrictions or provider-specific administrative roles affecting role administration, ownership, deployment identities, privileged operations, and managed superuser substitutes.

Validate the platform's behavior before applying a production access design.

---

## 31. SAFE-READ Acceptance Strategy

The canonical acceptance artifact inspects session identity, `pg_default_acl`, creator roles, schema scope, object classes, ACL entries, grantors, grantees, and grant options.

It does not execute security-mutating operations such as `ALTER DEFAULT PRIVILEGES`, `GRANT`, `REVOKE`, object creation, role switching, ownership changes, or application-data modification.

Therefore it remains:

```text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
```

- [ ] Identify the target object class.
- [ ] Identify schema scope where applicable.

## 33. Key Takeaways

```text
object-creating current role
          +
object class
          +
global default privileges
          +
schema-specific additions where applicable
          =
future object's initial privilege configuration
```

Remember:

```text
existing-object GRANT != future-object default
role membership != automatic use of member role's defaults
same schema != same defaults for every creator
table defaults != sequence defaults
schema REVOKE != override of global default GRANT
aclexplode() != complete effective authorization
```

Treat default privileges as part of the application's ownership and deployment architecture from the beginning.
