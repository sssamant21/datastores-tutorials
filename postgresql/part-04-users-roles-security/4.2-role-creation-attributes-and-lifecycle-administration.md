# Part 4.2 — Role Creation, Attributes, and Lifecycle Administration

**Status:** Revised Final / Canonical Edition
**Target:** PostgreSQL 18
**Audience:** PostgreSQL administrators, DBREs, SREs, platform engineers
**Companion Lab:** `labs/role-lifecycle-check.sql`

---

## 1. Learning Objectives

By the end of this tutorial, you should be able to:

- design login, group, owner, deployment, service, and administrative roles;
- create roles with explicit least-privilege attributes;
- distinguish `CREATE ROLE` from `CREATE USER`;
- manage password and non-password authentication boundaries safely;
- interpret PostgreSQL 18 role attributes correctly;
- understand delegated `CREATEROLE` administration;
- manage role-specific configuration defaults;
- plan role disablement, ownership transfer, privilege cleanup, and removal;
- inspect one role's lifecycle state without exposing password hashes;
- avoid production lockout and orphaned ownership.

---

## 2. Roles Need an Explicit Purpose

PostgreSQL uses one role object for identities commonly described as users, groups, owners, and service accounts. The difference is design and attributes, not a separate catalog type.

| Role category | Typical design |
| --- | --- |
| Human login | `LOGIN`; receives access through controlled memberships |
| Workload/service login | `LOGIN`; narrowly scoped, independently rotated credential |
| Group/access role | `NOLOGIN`; owns privilege bundles rather than objects |
| Owner role | Usually `NOLOGIN`; owns application objects |
| Deployment role | Login or federated identity with an explicit path to the owner role |
| Monitoring/support role | Limited memberships or predefined roles after risk review |
| Break-glass administrator | Strongly controlled, monitored, temporary use |

A name alone does not enforce a category. Document the owner, purpose, environment, authentication method, privilege source, expiry/rotation policy, and removal procedure for every production role.

Roles are cluster-wide. Creating, renaming, or dropping one can affect every database in the cluster.

## 3. `CREATE ROLE` and `CREATE USER`

`CREATE ROLE` defaults to `NOLOGIN`:

```sql
CREATE ROLE app_readonly
    NOLOGIN
    NOSUPERUSER
    NOCREATEDB
    NOCREATEROLE
    NOREPLICATION
    NOBYPASSRLS;
```

`CREATE USER` is an alternative spelling that implies `LOGIN`. For operational clarity, many teams use `CREATE ROLE ... LOGIN` so the login decision remains visible:

```sql
CREATE ROLE app_runtime
    LOGIN
    NOSUPERUSER
    NOCREATEDB
    NOCREATEROLE
    NOREPLICATION
    NOBYPASSRLS
    CONNECTION LIMIT 20;
```

These examples are security-mutating. Run them only in an approved isolated lab or reviewed change window.

PostgreSQL role names follow SQL identifier rules. PostgreSQL uses the `pg_` prefix for predefined roles, whose capabilities can change between releases. Reserve that prefix in your organizational naming standard to avoid ambiguity and future collisions.

## 4. Attribute Defaults and Risk

When omitted, PostgreSQL creates a role with conservative powerful-attribute defaults:

| Attribute | Default | Meaning |
| --- | --- | --- |
| `SUPERUSER` | `NOSUPERUSER` | Bypasses nearly all database permission checks |
| `CREATEDB` | `NOCREATEDB` | Can create databases |
| `CREATEROLE` | `NOCREATEROLE` | Can create roles and administer permitted roles |
| `LOGIN` | `NOLOGIN` for `CREATE ROLE` | Can be the initial connection identity |
| `REPLICATION` | `NOREPLICATION` | Can initiate replication and manage replication slots |
| `BYPASSRLS` | `NOBYPASSRLS` | Bypasses every RLS policy |
| `INHERIT` | `INHERIT` | Supplies the default inheritance option for new memberships |
| `CONNECTION LIMIT` | `-1` | No role-specific limit |

Explicit negative attributes make reviews easier, but they do not replace policy-as-code, drift detection, or effective-access testing.

`CONNECTION LIMIT` is approximate, excludes prepared transactions and background-worker connections, and is not enforced for superusers. It is not a workload governor or denial-of-service control.

## 5. PostgreSQL 18 `INHERIT` Semantics

In PostgreSQL 18, the role-level `INHERIT` attribute determines the default `INHERIT` option when new membership grants are created. The actual membership edge stores `inherit_option`.

Do not use `rolinherit` alone to decide whether a role currently receives another role's privileges. Inspect the membership graph and each edge's `INHERIT`, `SET`, and `ADMIN` options.

Part 4.3 handles membership behavior in depth.

## 6. Credentials Without Secret Leakage

A role can have `LOGIN` without a PostgreSQL password. Whether a connection succeeds depends on the matched authentication method and external controls.

Never place a plaintext password in:

- repository SQL;
- shell history;
- ticket comments;
- screenshots;
- CI logs;
- chat transcripts.

Interactive `psql` administration can use:

```text
\password app_runtime
```

This prompts for the password without embedding it in an SQL command. Automated workflows should use an approved secret manager and a mechanism that does not print the secret.

`PASSWORD NULL` makes password authentication fail for the role, but it does not disable certificate, GSSAPI, peer, trust, cloud IAM, or other non-password authentication paths.

`VALID UNTIL` expires only the password. It does not expire the role and is not enforced for non-password authentication.

PostgreSQL 18 deprecates MD5-encrypted passwords. Use the organization's reviewed SCRAM migration and authentication policy. Renaming a role clears an MD5-encrypted password because the role name participates in the MD5 verifier; plan credential rotation as part of such a rename.

Use the public `pg_roles` view for inventory. It masks password contents. Do not query `pg_authid` or export verifier values into evidence.

## 7. Delegated Role Administration

`CREATEROLE` is powerful but is not identical to superuser. In PostgreSQL 18, a non-superuser with `CREATEROLE` generally needs `ADMIN OPTION` on an existing target role to alter or drop it.

Important boundaries include:

- only a superuser can create or alter superuser status;
- replication and `BYPASSRLS` changes have additional attribute requirements;
- a role administrator can use membership administration to create consequential access paths;
- `ADMIN OPTION`, `SET`, and `INHERIT` must be reviewed separately;
- automatic grants associated with role creation are safeguards against accidental immediate use, not complete security boundaries.

Treat `CREATEROLE` as privileged administrative access. Monitor its use and separate role administration from routine application ownership.

## 8. Altering Roles Safely

`ALTER ROLE` changes attributes not omitted from the command:

```sql
ALTER ROLE app_runtime
    CONNECTION LIMIT 30
    NOCREATEDB
    NOCREATEROLE;
```

Membership is not changed with `ALTER ROLE`; use reviewed `GRANT role TO member` and `REVOKE role FROM member` operations.

Before changing `LOGIN`, powerful attributes, connection limits, or names:

1. identify applications, poolers, jobs, replication clients, and people using the role;
2. identify direct and indirect memberships;
3. inventory owned objects and granted privileges in every database;
4. identify active sessions and transaction impact;
5. define rollback and independent administrator access;
6. test the replacement path before revoking the old one;
7. monitor authentication failures and authorization denials.

`NOLOGIN` prevents new initial logins as that role, but it does not terminate existing sessions and does not remove membership, ownership, ACLs, or non-login use through `SET ROLE`.

## 9. Role-Specific Configuration Defaults

PostgreSQL can attach session defaults to a role globally or for one database:

```sql
ALTER ROLE reporting_user SET statement_timeout = '2min';

ALTER ROLE reporting_user IN DATABASE analytics
    SET statement_timeout = '30s';
```

These settings take effect at login. `SET ROLE` and `SET SESSION AUTHORIZATION` do not reapply them. Database-and-role-specific settings override role-only and database-only settings.

Review security-sensitive defaults such as `search_path`, logging behavior, timeouts, and session settings. A role default is not an immutable control: users may be able to change settings during a session, depending on the parameter and their privileges.

## 10. A Safe Role Lifecycle

### Provision

1. Approve the access contract and accountable owner.
2. Choose a non-conflicting, policy-compliant name.
3. Create the role with explicit least-privilege attributes.
4. Configure authentication outside repository history.
5. Grant only reviewed memberships and object privileges.
6. Validate both allow and deny cases.
7. Record rotation, review, and retirement dates.

### Operate

- review powerful attributes and membership edges;
- rotate credentials through approved mechanisms;
- detect unused or unexpected roles;
- prevent personal roles from owning application objects;
- review role-specific configuration drift;
- monitor authentication and administrative changes.

### Disable

Disabling is a coordinated incident or lifecycle action, not a single universal command. Depending on the access path, it can require:

- `NOLOGIN`;
- password invalidation or rotation;
- external identity or certificate revocation;
- membership and privilege revocation;
- session termination through a separately approved procedure;
- application/pooler credential replacement.

### Retire

A role cannot be dropped while referenced anywhere in the cluster. Inventory every database before removal.

For objects that must survive, a reviewed pattern is:

```sql
REASSIGN OWNED BY departing_role TO successor_owner;
DROP OWNED BY departing_role;
```

These commands are destructive/security-mutating and require careful review:

- `REASSIGN OWNED` transfers ownership; it does not remove privileges granted to the old role;
- `DROP OWNED` drops objects owned by the role in the current database and revokes privileges granted to it;
- both generally must be considered in every database containing relevant dependencies;
- shared objects and cross-database effects require explicit inspection;
- `CASCADE` can remove dependent objects and must never be used casually.

Do not paste this sequence into production as a generic cleanup script. Build an approved per-database manifest of objects, grants, default privileges, policies, and shared objects first. Record the intended successor for each valuable object class; verify the current database before every command; prefer the default `RESTRICT` behavior; and stop on any unexpected dependency. A transaction can help group changes inside one database, but it is not a substitute for a cross-database rollback plan, application coordination, backups, and an independently tested administrator path.

Only after ownership and privilege dependencies are resolved should `DROP ROLE` be attempted. Role memberships involving the dropped role are automatically revoked, but other roles remain.

## 11. Hands-On Lab — SAFE-READ Lifecycle Inspection

The companion lab inspects one declared target role without creating, altering, disabling, or dropping it.

Run from the repository root:

```bash
umask 077
psql --no-psqlrc \
  --dbname=appdb \
  --set=expected_database=appdb \
  --set=expected_session_user=security_auditor \
  --set=target_role=app_runtime \
  --file=labs/role-lifecycle-check.sql \
  --output=role-lifecycle-check.out
```

The input policy accepts simple unquoted lowercase identifiers. The lab:

- verifies PostgreSQL 18, database, session role, and target-role existence;
- reports the target's attributes and role-level configuration;
- reports incoming and outgoing direct memberships;
- inventories current-database ownership and explicit ACL/default-ACL entries;
- summarizes shared dependency records relevant to removal planning;
- runs in a repeatable-read, read-only transaction;
- rolls back and exits nonzero when a hard gate fails.

The output contains sensitive security metadata. Restrict, redact, retain, and dispose of it under approved policy. It is point-in-time evidence, not authorization to alter or drop the role.

The inventory has deliberate limits. Role/database settings that target all roles rather than the declared role are outside the target-specific setting section. To avoid disclosing arbitrary custom configuration data, the lab displays values only for a narrow allowlist of operational settings and redacts all other values. Explicit ACL output does not include access received through `PUBLIC`, ownership, membership, or built-in defaults. Type ownership counts can include automatically generated array or relation-associated types. Shared-dependency counts help locate databases and dependency categories, but they are not a substitute for reviewed `DROP ROLE` diagnostics and per-database inspection.

Run the lab using an approved auditor identity with only the catalog visibility required by local policy. Do not switch to superuser merely to obtain a cleaner report. When a connection pooler is involved, confirm which PostgreSQL role the backend actually uses; pooler authentication can differ from the database's `session_user`. On clusters with large catalogs or many dependency rows, schedule the inventory conservatively, observe latency and replica lag, and stop if the catalog workload or output becomes excessive.

A disablement change needs a separate validation plan. `NOLOGIN` does not terminate existing sessions, invalidate externally managed credentials, remove memberships, revoke ACLs, or prevent an authorized member from reaching a non-login role through `SET ROLE`. Coordinate the database change with pooler drains, secret rotation, external identity revocation, session handling, and application-owner confirmation.

## 12. Production Review Checklist

- [ ] The role has an accountable owner and documented purpose.
- [ ] Login and non-login status matches the role category.
- [ ] Powerful attributes are explicitly justified.
- [ ] Credentials are absent from SQL, repositories, logs, and tickets.
- [ ] Password expiry is not mistaken for role expiry.
- [ ] Non-password authentication paths are included in disablement plans.
- [ ] Membership options are reviewed edge by edge.
- [ ] Role-specific configuration defaults are inventoried.
- [ ] Ownership and grants are inspected in every relevant database.
- [ ] Active sessions and pooler behavior are considered.
- [ ] External identity, certificate, and secret-manager access is revoked where applicable.
- [ ] Existing sessions are handled through a separately approved procedure.
- [ ] Successor ownership and rollback paths are tested.
- [ ] A per-database dependency and successor-owner manifest is approved.
- [ ] `DROP OWNED` uses `RESTRICT` unless an exceptional `CASCADE` impact is fully proven.
- [ ] `REASSIGN OWNED`, `DROP OWNED`, and `DROP ROLE` receive change review.
- [ ] Independent administrative recovery access remains available.
- [ ] Evidence output is protected and redacted before sharing.

---

## 13. Key Takeaways

1. PostgreSQL roles are cluster-wide and can represent logins, groups, owners, or administrators.
2. Least privilege begins with explicit attributes and deliberate role categories.
3. `VALID UNTIL` expires a password, not a role.
4. `NOLOGIN` blocks new initial logins but does not erase existing access relationships.
5. Role removal is a cross-database ownership-and-privilege workflow.
6. Password verifiers and plaintext credentials do not belong in audit evidence.
7. A safe lifecycle includes provisioning, validation, operation, disablement, dependency cleanup, and retirement.
