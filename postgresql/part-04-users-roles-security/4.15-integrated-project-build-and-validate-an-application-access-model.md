# Part 4.15 — Integrated Project — Build and Validate an Application Access Model

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Track:** Part 4 — Users, Roles & Security

## 1. Project Goal

This final Part 4 project integrates PostgreSQL identity, membership, ownership, privileges, default privileges, privileged routines, RLS, authentication, TLS, and drift validation into one application-access model.

The reference design is:

```text
owner / migration identity
        ↓
reusable NOLOGIN access roles
        ↓
runtime LOGIN identity
        ↓
database + schema + object privileges
        ↓
optional privileged routines / RLS
        ↓
authentication + TLS
        ↓
expected allow / expected deny
        ↓
approved baseline + drift monitoring
```

The goal is not to create the largest possible privilege model. It is to create one that is explicit, testable, maintainable, and recoverable.

## 2. Reference Scenario

The project uses synthetic identifiers:

```text
database: appdb
schema:   app

app_owner      — intended application-object owner; normally NOLOGIN
app_read       — reusable read-access role; normally NOLOGIN
app_write      — reusable write-access role; normally NOLOGIN
app_runtime    — application LOGIN identity
app_migration  — deployment/migration LOGIN identity
```

These names are educational defaults, not mandatory production naming standards.

## 3. Ownership and Runtime Separation

The runtime login should not normally own the objects it consumes.

```text
owner / controlled migration path
            ↓
        owns objects
            ↓
access roles receive privileges
            ↓
runtime receives memberships
```

Ownership conveys authority beyond ordinary ACL grants. For this project, database/schema/relation/sequence/routine ownership by `app_runtime` is a review signal.

This is an architectural pattern, not a PostgreSQL requirement.

## 4. LOGIN and NOLOGIN Roles

PostgreSQL roles represent identity and authorization. `LOGIN` determines whether a role can authenticate.

Reusable privilege bundles are commonly represented by NOLOGIN roles, while authenticating application identities use LOGIN.

```text
authentication identity
        !=
privilege bundle
```

## 5. Membership

Membership connects login identities to reusable privilege roles.

PostgreSQL 18 membership evidence includes:

```text
ADMIN
INHERIT
SET
```

These options have distinct effects and must not be reduced to a single member/not-member flag.

Also review membership in PostgreSQL predefined roles and provider-specific roles. Such membership is review-required evidence, not automatically a vulnerability.

## 6. Database Boundary

The model must explicitly define database access such as `CONNECT` and `TEMPORARY`, plus ownership.

`CONNECT` permits connection to a database but does not grant schema/table access.

For this project, `app_runtime` unexpectedly owning `appdb` should trigger review.

## 7. Database-Local Catalog Boundary

Schemas, relations, routines, policies, and many other catalogs are database-local.

Therefore:

```text
connect to appdb
before validating appdb application objects
```

Seeing `appdb` in `pg_database` while connected elsewhere does not mean the session can inspect `appdb`'s application catalogs.

The canonical acceptance artifact reports whether the current database is `appdb`; it does not automatically reconnect.

## 8. Schema Boundary

The `app` schema should explicitly define:

- owner,
- `USAGE`,
- `CREATE`,
- PUBLIC exposure.

`USAGE` and `CREATE` are different capabilities. Runtime access commonly requires `USAGE` without requiring object-creation authority.

## 9. Relations and Columns

Define table/view access explicitly.

Typical conceptual bundles:

```text
app_read
  SELECT approved objects

app_write
  INSERT / UPDATE / DELETE approved objects
```

Explicit column ACLs must also be considered because they can create narrower access exceptions.

Views, materialized views, partitioned tables, and foreign tables can have behavior beyond a simple ordinary-table model. Foreign tables can additionally depend on remote-system authorization.

## 10. Sequences

Sequence privileges are distinct from table privileges.

Applications that generate identifiers can depend on sequence behavior, so sequence `USAGE`, `SELECT`, and `UPDATE` evidence should be evaluated separately.

Do not assume table `INSERT` alone proves all generated-value operations will succeed.

## 11. Routines

Routine `EXECUTE` is an independent privilege boundary.

Identify overloaded routines using schema + routine name + identity arguments.

For `SECURITY DEFINER`, review:

- routine kind,
- owner,
- execution exposure,
- routine-local configuration,
- secure `search_path`,
- qualified object references,
- caller-controlled input,
- intended privilege boundary.

A non-null `proconfig` does not itself prove that a privileged routine is hardened.

## 12. Default Privileges and Object Creator

Default privileges apply in the creator-role context.

```text
object creator
      ↓
determines applicable default privileges
```

If `app_migration` creates objects while `app_owner` is intended to own them, the deployment process must explicitly define how ownership and default privileges are established.

Do not assume objects automatically become owned by `app_owner`.

## 13. PUBLIC

Least privilege cannot be evaluated only from application-role ACLs.

`PUBLIC` represents all PostgreSQL roles and may independently have database, schema, routine, or other access.

Keep these rules in mind:

```text
NULL ACL != no access
PUBLIC   != automatically insecure
owner    != ordinary grantee
```

Review PUBLIC against the intended application policy.

## 14. Row-Level Security

RLS is an additional row-access layer; it does not replace object privileges or authentication.

Validate:

- table RLS state,
- FORCE RLS state,
- applicable policies,
- policy roles,
- commands,
- permissive/restrictive behavior,
- `USING`,
- `WITH CHECK`,
- owner/BYPASSRLS context.

`has_table_privilege()` does not prove which rows are visible.

## 15. Authentication

Authentication policy is separate from authorization.

Use the Part 4.12 canonical artifact to validate HBA/authentication policy. HBA matching does not grant application object privileges.

## 16. TLS

Transport security is separate from application authorization.

Use the Part 4.13 canonical artifact for TLS/client-certificate validation.

Document TLS requirements, server verification, trust roots, optional client certificates, and proxy/load-balancer boundaries separately from object privileges.

## 17. Additional Privilege Surfaces

Depending on the application, also consider:

- custom type/domain `USAGE`,
- maintenance authority,
- parameter privileges,
- extension/provider capabilities.

These should not silently enter a runtime privilege bundle merely because the application requires ordinary DML.

## 18. Expected Access Matrix

Define expected behavior before implementation.

| Identity | CONNECT | Schema USAGE | Schema CREATE | Read | Write | Role Admin | Own App Objects |
|---|---|---|---|---|---|---|---|
| `app_runtime` | expected | expected | denied | as required | as required | denied | denied |
| `app_read` | model-dependent | expected | denied | expected | denied | denied | denied |
| `app_write` | model-dependent | expected | denied | model-dependent | expected | denied | denied |
| `app_owner` | model-dependent | expected | owner/model | owner authority | owner authority | model-dependent | expected |
| `app_migration` | deployment-specific | deployment-specific | deployment-specific | deployment-specific | deployment-specific | denied unless justified | creator/ownership strategy required |

This is the reference policy for the tutorial, not a universal PostgreSQL standard.

## 19. Positive and Negative Validation

A strong access model validates:

```text
expected allow
+
expected deny
```

Privilege-check functions provide catalog/effective-privilege evidence but do not replace end-to-end application tests.

```text
has_*_privilege() evidence
        !=
behavioral authorization test
```

Use synthetic/test identities and controlled sessions for behavioral testing. The canonical SAFE-READ collector does not impersonate roles.

## 20. Implementation Workflow

A production rollout should:

1. define identities and privilege bundles,
2. define owner and creator roles,
3. define membership,
4. define database/schema boundaries,
5. define relation/column/sequence/routine access,
6. define default privileges,
7. define RLS where required,
8. define authentication/TLS requirements,
9. implement through reviewed migration/IaC,
10. validate expected allow and deny behavior,
11. approve the configuration,
12. capture a known-good security baseline,
13. monitor drift.

## 21. Recovery and Rollback

Before changing production access:

- capture current grants/memberships/ownership/policies,
- identify dependent workloads,
- preserve an independently tested recovery identity,
- define rollback,
- apply the smallest intended change,
- validate new connections and application behavior,
- monitor permission/authentication failures.

Do not compensate for one missing privilege by granting broad administrative authority.

## 22. Managed Services

Managed PostgreSQL can introduce provider-owned roles, authentication integrations, TLS controls, extensions, and restricted administrative semantics.

Keep the logical model portable and document provider-specific implementation separately.

Do not attempt to “clean up” provider-owned state merely because it differs from a self-managed cluster.

## 23. Acceptance Layers

The final project validates:

```text
1. target database context
2. role attributes
3. membership
4. ownership
5. explicit privileges
6. column exceptions
7. sequences
8. routines
9. default privileges / creator context
10. PUBLIC
11. SECURITY DEFINER
12. RLS
13. references to authentication/TLS controls
14. expected allow / expected deny
15. baseline/drift monitoring
```

## 24. SAFE-READ Acceptance Artifact

The canonical `labs/application-access-acceptance.sql` validates an already implemented model.

It performs no:

- role creation/modification,
- `GRANT` / `REVOKE`,
- ownership changes,
- DDL/DML,
- RLS changes,
- `ALTER SYSTEM`,
- HBA/TLS changes or reload,
- password-verifier inspection,
- `SET ROLE`,
- session-authorization changes,
- external authentication testing,
- automatic remediation,
- session termination.

```text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
```

## 25. Completion Criteria

The design should be able to answer:

```text
Who authenticates?
Which roles bundle access?
Who creates objects?
Who owns objects?
Who can connect?
Who can use/create in the schema?
Who can read/write?
Are there column exceptions?
Who can use sequences?
Who can execute routines?
What happens to future objects?
Does PUBLIC broaden access?
Does RLS apply?
Are privileged routines intentionally exposed?
How are authentication and transport validated?
What should succeed?
What should fail?
How is known-good state baselined?
How is drift detected?
How is access recovered or rolled back?
```

## 26. Key Takeaways

```text
runtime login       != object owner
LOGIN identity      != privilege bundle
CONNECT             != object access
schema USAGE        != schema CREATE
table privilege     != sequence privilege
table privilege     != RLS row visibility
existing grants     != future-object grants
NULL ACL            != no access
authentication      != authorization
TLS                 != authorization
catalog evidence    != behavioral proof
current state       != approved baseline
SAFE-READ           != safe to publish
```

A production application-access model should be deliberately designed, independently validated, baselined only after approval, and continuously reviewed for drift.
