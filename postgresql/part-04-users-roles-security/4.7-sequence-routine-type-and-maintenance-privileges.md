# Part 4.7 — Sequence, Routine, Type, and Maintenance Privileges

**Target:** PostgreSQL 18  
**Audience:** PostgreSQL administrators, DBREs, SREs, platform engineers, developers  
**Status:** Revised Final / Canonical Edition

---

## 1. Why These Privileges Matter

PostgreSQL authorization extends beyond databases, schemas, tables, and columns.

Production workloads also interact with:

- sequences,
- functions,
- procedures,
- custom data types,
- domains,
- materialized views,
- and relations requiring maintenance.

These objects have their own privilege rules.

For example, an application can have `INSERT` on a table and still fail when PostgreSQL attempts to generate an identifier from a sequence.

A role may be able to discover a function but not execute it.

A DBRE may need to maintain a table without needing ownership of that table.

The production troubleshooting model is therefore:

```text
operation
   |
   +-- Which objects participate?
   |
   +-- Who owns those objects?
   |
   +-- Which privileges are required?
   |
   +-- Where do effective privileges come from?
          |
          +-- direct grant
          +-- role membership
          +-- PUBLIC
          +-- ownership
          +-- predefined role
          +-- superuser
```

Never assume the privilege on the most visible object is the only authorization involved.

## 2. Learning Objectives

By the end of this tutorial, you should be able to:

- distinguish `SECURITY INVOKER` from `SECURITY DEFINER`,
- audit `PUBLIC EXECUTE`,
- recognize unsafe routine object resolution,
- understand type and domain `USAGE`,
- explain `MAINTAIN`,
- distinguish targeted `MAINTAIN` from `pg_maintain`,
- inspect effective privileges,
- understand future-object default privileges,
- and investigate production authorization failures without modifying database state.

## 3. Sequences Are Independent Objects

A sequence is a PostgreSQL object that generates numeric values.

Sequences frequently support generated identifiers.

For example:

```sql
CREATE TABLE clinical.patient (
    patient_id bigint GENERATED BY DEFAULT AS IDENTITY,
    patient_name text
);
```

The table and its backing sequence are different database objects.

Therefore:

```text
table privilege != sequence privilege
```

A role with:

```sql
GRANT INSERT
ON clinical.patient
TO app_writer;
```

does not automatically receive every privilege required on an associated sequence.

This is one of the first things to investigate when an apparently valid insert receives a sequence permission error.

---

## 4. Sequence Privileges

PostgreSQL sequences support:

```text
USAGE
SELECT
UPDATE
```

The exact privilege required depends on the sequence operation.

| Sequence operation | Accepted privilege |
|---|---|
| `nextval()` | `USAGE` or `UPDATE` |
| `currval()` | `USAGE` or `SELECT` |
| `lastval()` | `USAGE` or `SELECT` on the applicable sequence |
| `setval()` | `UPDATE` |

Do not reduce the sequence privilege model to `sequence access = USAGE`; PostgreSQL's rules are more specific.

---

## 5. Why INSERT Can Fail

Suppose an application executes:

```sql
INSERT INTO clinical.patient (patient_name)
VALUES ('Example Patient');
```

The application may have `INSERT` on the table. However, generating `patient_id` may require access to the backing sequence.

The investigation should therefore check both objects:

```text
INSERT
  |
  +-- clinical.patient
  |       +-- INSERT?
  |
  +-- backing sequence
          +-- required sequence privilege?
```

The correct fix is the narrow privilege required by the application—not broad ownership or superuser access.

---

## 6. Inspecting Sequences

A safe sequence inventory can be obtained from PostgreSQL catalogs:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS sequence_name,
    pg_get_userbyid(c.relowner) AS owner,
    c.relacl
FROM pg_class AS c
JOIN pg_namespace AS n
    ON n.oid = c.relnamespace
WHERE c.relkind = 'S'
ORDER BY n.nspname, c.relname;
```

This does not advance the sequence.

---

## 7. Checking Effective Sequence Privileges

PostgreSQL provides `has_sequence_privilege()`.

```sql
SELECT
    current_user,
    has_sequence_privilege(
        current_user,
        'clinical.patient_patient_id_seq',
        'USAGE'
    ) AS has_usage,
    has_sequence_privilege(
        current_user,
        'clinical.patient_patient_id_seq',
        'SELECT'
    ) AS has_select,
    has_sequence_privilege(
        current_user,
        'clinical.patient_patient_id_seq',
        'UPDATE'
    ) AS has_update;
```

These functions evaluate effective privilege rather than requiring authorization to be reconstructed solely from ACL text.

---

## 8. Do Not Test Sequence Privileges by Advancing Production Sequences

This is not an acceptable SAFE-READ privilege test:

```sql
SELECT nextval('clinical.patient_patient_id_seq');
```

Neither is:

```sql
SELECT setval(...);
```

Sequence operations can change sequence state. Do not assume that wrapping sequence advancement in `BEGIN` / `ROLLBACK` makes it a harmless read-only test.

For production acceptance checks, use privilege inquiry functions instead.

---

## 9. Functions, Procedures, and Routines

PostgreSQL executable database objects include `FUNCTION` and `PROCEDURE`.

PostgreSQL also uses `ROUTINE` as a collective concept where functions and procedures are handled together.

The primary access privilege is `EXECUTE`.

```sql
GRANT EXECUTE
ON FUNCTION clinical.calculate_risk(bigint)
TO app_runtime;
```

---

## 10. Routine Signatures Matter

PostgreSQL supports overloaded functions.

```text
calculate_risk(integer)
calculate_risk(bigint)
calculate_risk(text)
```

These are different routine identities.

Use the correct argument signature during privilege administration. A useful catalog helper is `pg_get_function_identity_arguments()`.

```sql
SELECT
    n.nspname,
    p.proname,
    pg_get_function_identity_arguments(p.oid)
FROM pg_proc AS p
JOIN pg_namespace AS n
    ON n.oid = p.pronamespace;
```

---

## 11. SECURITY INVOKER

The normal/default model is `SECURITY INVOKER`.

The routine executes using the privileges of the caller.

```text
caller
   |
   v
routine
   |
   | caller's authority
   v
referenced objects
```

---

## 12. SECURITY DEFINER

A function can instead use `SECURITY DEFINER`.

A security-definer function executes with the privileges of its owner.

```text
caller
   |
   | EXECUTE
   v
SECURITY DEFINER function
   |
   | owner's authority
   v
protected objects
```

This can intentionally provide a controlled privilege boundary. It can also create privilege-escalation opportunities if designed incorrectly.

---

## 13. SECURITY DEFINER Review Model

For every privileged routine, review:

```text
SECURITY DEFINER?
      |
      +-- owner
      +-- who has EXECUTE?
      +-- does PUBLIC have EXECUTE?
      +-- function-local search_path?
      +-- writable schemas in object-resolution path?
      +-- dynamic SQL?
      +-- user-controlled input?
      +-- referenced privileged objects?
```

A privileged routine should not depend on attacker-controlled object resolution.

---

## 14. Secure search_path

A typical controlled pattern is:

```sql
CREATE FUNCTION admin.some_operation(...)
RETURNS ...
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = admin, pg_temp
AS $$
...
$$;
```

Trusted schemas should precede `pg_temp`, and untrusted writable schemas should not participate in privileged object resolution.

---

## 15. Missing Local search_path Does Not Automatically Prove Vulnerability

An audit finding of:

```text
SECURITY DEFINER
+
no function-local search_path
```

should be classified as **REVIEW REQUIRED**, not automatically **VULNERABLE**.

A function may have other protections, including fully schema-qualified references and tightly controlled schemas.

---

## 16. PUBLIC EXECUTE

New functions normally receive `EXECUTE` for `PUBLIC`.

An explicit grant to an application role does not prove that only that role can execute the function.

A controlled creation pattern can use one transaction:

```sql
BEGIN;

CREATE FUNCTION ...;

REVOKE ALL
ON FUNCTION admin.secure_operation(bigint)
FROM PUBLIC;

GRANT EXECUTE
ON FUNCTION admin.secure_operation(bigint)
TO app_runtime;

COMMIT;
```

---

## 17. Routine Ownership Is Security-Relevant

Changing ownership can materially alter the security behavior of a `SECURITY DEFINER` function because it executes using its owner's privileges.

Do not use ownership changes as a generic permission troubleshooting shortcut.

---

## 18. Checking Effective EXECUTE

PostgreSQL provides `has_function_privilege()`:

```sql
SELECT
    has_function_privilege(
        current_user,
        'clinical.calculate_risk(bigint)',
        'EXECUTE'
    );
```

---

## 19. Types and Domains

PostgreSQL supports `USAGE` privileges on types.

```sql
GRANT USAGE
ON TYPE clinical.patient_status
TO app_runtime;
```

This is relevant to enums, domains, composite types, and other user-defined types.

---

## 20. Checking Type Privileges

PostgreSQL provides `has_type_privilege()`:

```sql
SELECT
    has_type_privilege(
        current_user,
        'clinical.patient_status',
        'USAGE'
    );
```

---

## 21. MAINTAIN

PostgreSQL provides the relation-level `MAINTAIN` privilege.

It supports maintenance authority for operations including:

```text
VACUUM
ANALYZE
CLUSTER
REFRESH MATERIALIZED VIEW
REINDEX
LOCK TABLE
```

subject to the rules of the individual commands.

This separates application data privileges from maintenance authority.

---

## 22. Checking MAINTAIN

PostgreSQL exposes `MAINTAIN` through `has_table_privilege()`:

```sql
SELECT
    has_table_privilege(
        current_user,
        'clinical.patient',
        'MAINTAIN'
    );
```

This reinforces:

```text
data access != maintenance authority
```

---

## 23. pg_maintain

PostgreSQL provides the predefined role `pg_maintain`.

Membership supplies broad maintenance authority across relations, supporting operations such as `VACUUM`, `ANALYZE`, `CLUSTER`, `REFRESH MATERIALIZED VIEW`, `REINDEX`, and `LOCK TABLE` as though the role had `MAINTAIN` on those relations.

`pg_maintain` is useful—but broad.

---

## 24. Targeted MAINTAIN vs pg_maintain

For narrowly scoped requirements, targeted `MAINTAIN` can preserve a smaller privilege boundary than membership in `pg_maintain`.

Do not grant `pg_maintain` merely because one maintenance command received a permission error.

---

## 25. Authorization Does Not Mean Operational Safety

A critical DBRE principle is:

```text
Can I execute it?
        !=
Should I execute it now?
```

Maintenance can still affect locks, application latency, I/O, CPU, WAL generation, replication, disk utilization, and maintenance windows.

Privilege authorization is only one production gate.

---

## 26. Ownership Is Not an Ordinary Grant

Owners possess inherent authority over their objects.

Therefore, no explicit ACL does not necessarily mean no effective privilege.

Effective authorization may come from:

```text
direct GRANT
role membership
PUBLIC
ownership
predefined roles
superuser
```

---

## 27. Default Privileges

PostgreSQL provides `ALTER DEFAULT PRIVILEGES` to control privileges assigned to objects created in the future.

Relevant object classes include:

```text
TABLES
SEQUENCES
FUNCTIONS / ROUTINES
TYPES
```

The crucial rule is that default privileges affect future objects; they are not retroactive remediation for existing objects.

---

## 28. Global and Per-Schema Defaults

Default privileges can involve both general and per-schema rules.

Do not assume a schema-specific `REVOKE` simply cancels a privilege supplied by a global default privilege configuration.

When unexpected privileges appear on newly created objects, inspect the complete default-privilege configuration.

---

## 29. Effective Privilege Investigation

Use a layered workflow:

1. Confirm `session_user`, `current_user`, and `current_role`.
2. Identify the exact object.
3. Identify the owner.
4. Inspect direct ACLs.
5. Inspect role membership.
6. Check `PUBLIC`.
7. Check predefined roles such as `pg_maintain`.
8. Consider ownership and superuser authority.
9. Ask PostgreSQL using effective privilege functions.

Useful functions include:

```text
has_sequence_privilege()
has_function_privilege()
has_type_privilege()
has_table_privilege()
pg_has_role()
```

---

## 30. Production Scenario — INSERT Works in One Environment but Fails in Another

If staging succeeds while production reports `permission denied for sequence`, compare:

```text
table privilege
sequence privilege
role membership
object ownership
default privileges
```

A deployment may have created objects under different creators or default privilege configurations.

---

## 31. Production Scenario — Routine Works for One Role but Not Another

Investigate:

```text
exact routine signature
EXECUTE privilege
role membership
PUBLIC
routine owner
SECURITY INVOKER / DEFINER
```

For `SECURITY INVOKER`, underlying object privileges may also matter.

For `SECURITY DEFINER`, the owner's authority and routine security design become critical.

---

## 32. Production Scenario — Maintenance Permission Failure

Before granting anything, determine:

```text
Which operation?
Which relation?
Which role?
Does it already inherit MAINTAIN?
Does it belong to pg_maintain?
Is ownership actually required?
```

Avoid solving a targeted maintenance requirement by unnecessarily transferring ownership.

---

## 33. Managed PostgreSQL Services

Managed PostgreSQL platforms can impose additional administrative boundaries around superuser capabilities, predefined roles, ownership, extensions, maintenance operations, replication, and system catalogs.

The native PostgreSQL privilege model remains the foundation, but production procedures must also be validated against the specific managed service.

---

## 34. SAFE-READ Production Audit Pattern

Prefer catalog inspection and effective privilege functions rather than executing the privileged operation merely to see whether it succeeds.

```text
SAFE
has_sequence_privilege(...)

NOT SAFE-READ
nextval(...)
```

```text
SAFE
has_table_privilege(..., 'MAINTAIN')

NOT SAFE-READ
VACUUM ...
```

---

## 35. Production Checklist

Before changing sequence, routine, type, or maintenance privileges:

- [ ] Confirm the effective session identity.
- [ ] Identify the exact object.
- [ ] Identify the exact routine signature.
- [ ] Check ownership.
- [ ] Check direct ACLs.
- [ ] Check inherited role membership.
- [ ] Check `PUBLIC`.
- [ ] Check predefined roles.
- [ ] Use effective privilege functions.
- [ ] Review `SECURITY DEFINER`.
- [ ] Review function-local `search_path`.
- [ ] Review writable schemas.
- [ ] Review dynamic SQL.
- [ ] Review sequence requirements.
- [ ] Prefer targeted `MAINTAIN` where appropriate.
- [ ] Evaluate operational impact separately from authorization.
- [ ] Review default privileges for future objects.
- [ ] Validate managed-service restrictions.
- [ ] Define rollback before production privilege changes.

---

## 36. Key Takeaways

Remember:

```text
table privilege != sequence privilege
routine EXECUTE != underlying object privilege
data access != maintenance authority
direct ACL != complete effective authorization
authorized != operationally safe
```

For production troubleshooting, combine:

```text
identity
+ exact object
+ ownership
+ ACL
+ role membership
+ PUBLIC
+ predefined roles
+ effective privilege checks
```

Use the narrowest privilege that satisfies the requirement.

Avoid using `SUPERUSER`, ownership transfer, broad role membership, or `PUBLIC` grants as shortcuts for problems that can be solved with targeted PostgreSQL privileges.
