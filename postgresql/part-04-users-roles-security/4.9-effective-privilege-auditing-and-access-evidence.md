# Part 4.9 — Effective Privilege Auditing and Access Evidence

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Track:** Part 4 — Users, Roles & Security

---

## 1. Why Effective Privilege Auditing Matters

PostgreSQL access is not determined by a single ACL entry.

A role might be able to read a table even when its name does not appear directly in the table ACL.

For example:

```text
analyst_login
      |
      +-- member of reporting_reader
                    |
                    +-- SELECT on clinical.patient
```

An audit that searches only for a direct `analyst_login` ACL entry can therefore reach the wrong conclusion.

Effective authorization can involve:

```text
direct grants
     +
role membership
     +
PUBLIC
     +
ownership
     +
superuser authority
     +
predefined roles
     +
database/schema prerequisites
     +
object-specific security controls
```

The objective of an access audit is not simply:

> What ACL entries exist?

The stronger question is:

> Does PostgreSQL consider this role authorized for the requested operation, and what evidence helps explain that result?

---

## 2. Learning Objectives

By the end of this tutorial, you should be able to:

- distinguish configured ACLs from effective privileges,
- use PostgreSQL privilege-inquiry functions,
- use `pg_has_role()` to investigate role relationships,
- distinguish direct membership from effective membership,
- interpret membership-specific `ADMIN`, `INHERIT`, and `SET` options,
- identify `PUBLIC` as an access path,
- distinguish ownership from explicit grants,
- identify superuser and `BYPASSRLS` implications,
- account for predefined roles,
- audit database and schema prerequisites,
- audit tables, columns, sequences, routines, and types,
- test grant-option capability separately,
- identify RLS as an additional authorization layer,
- and collect repeatable SAFE-READ authorization evidence.

---

## 3. Configured ACL vs Effective Access

Consider:

```text
clinical.patient ACL
        |
        +-- reporting_reader = SELECT
```

and:

```text
analyst_login
        |
        +-- reporting_reader
```

Searching the table ACL only for `analyst_login` misses the membership path.

Therefore:

```text
ACL entry != complete authorization decision
```

ACL inspection answers which access-control entries are explicitly configured. Effective privilege inquiry answers whether PostgreSQL considers the role to possess the privilege.

---

## 4. PostgreSQL Privilege-Inquiry Functions

PostgreSQL provides privilege-checking functions including:

```text
has_database_privilege()
has_schema_privilege()
has_table_privilege()
has_any_column_privilege()
has_column_privilege()
has_sequence_privilege()
has_function_privilege()
has_type_privilege()
```

Example:

```sql
SELECT has_table_privilege(
    'app_runtime',
    'clinical.patient',
    'SELECT'
);
```

A `true` result means PostgreSQL considers the tested role to possess that table privilege according to the function's privilege semantics.

However, a successful table privilege check does not by itself prove that the complete application access path succeeds. Database, schema, RLS, and other controls can still matter.

---

## 5. Execution Identity

Start every investigation by recording:

```sql
SELECT
    current_database(),
    session_user,
    current_user,
    current_role;
```

Conceptually:

```text
session_user  = identity that established the session
current_user  = effective identity used for permission checking
current_role  = PostgreSQL synonym for current_user
```

`current_user` can differ from `session_user`, including after `SET ROLE` or while executing a `SECURITY DEFINER` function.

---

## 6. Audit the Complete Access Chain

A normal table-access path can involve:

```text
LOGIN
  |
  v
DATABASE -- CONNECT
  |
  v
SCHEMA -- USAGE
  |
  v
TABLE -- SELECT / INSERT / UPDATE / DELETE
  |
  v
COLUMN
```

Additional operations can depend on sequences, routines, types, and RLS. Check the relevant layers independently.

---

## 7. Database Privilege Evidence

```sql
SELECT has_database_privilege(
    'app_runtime',
    current_database(),
    'CONNECT'
);
```

Database access should be recorded independently from object-level access.

---

## 8. Schema Privilege Evidence

```sql
SELECT has_schema_privilege(
    'app_runtime',
    'clinical',
    'USAGE'
);
```

An investigation can legitimately find database `CONNECT = true`, schema `USAGE = false`, and table `SELECT = true`. Keep these as separate facts.

---

## 9. Table Privilege Evidence

```sql
SELECT
    has_table_privilege('app_runtime', 'clinical.patient', 'SELECT') AS can_select,
    has_table_privilege('app_runtime', 'clinical.patient', 'INSERT') AS can_insert,
    has_table_privilege('app_runtime', 'clinical.patient', 'UPDATE') AS can_update,
    has_table_privilege('app_runtime', 'clinical.patient', 'DELETE') AS can_delete;
```

This provides privilege evidence without performing the underlying operations.

---

## 10. Privilege vs Grant Option

These are separate questions: can the role use the privilege, and can the role delegate it?

```sql
SELECT has_table_privilege(
    'app_runtime',
    'clinical.patient',
    'SELECT WITH GRANT OPTION'
);
```

A privilege being available does not imply its grant option is available.

---

## 11. Column Privileges

```sql
SELECT has_column_privilege(
    'app_runtime',
    'clinical.patient',
    'ssn',
    'SELECT'
);
```

PostgreSQL can also answer whether a role has the requested privilege on at least one column:

```sql
SELECT has_any_column_privilege(
    'app_runtime',
    'clinical.patient',
    'SELECT'
);
```

Effective column privilege can result from broader table privilege, so a `true` result does not necessarily mean an explicit column-level ACL exists.

---

## 12. Sequence Privileges

```sql
SELECT has_sequence_privilege(
    'app_runtime',
    'clinical.patient_id_seq',
    'USAGE'
);
```

Table privilege does not imply sequence privilege. Do not call `nextval()` merely to prove authorization exists.

---

## 13. Routine Privilege Evidence

```sql
SELECT has_function_privilege(
    'app_runtime',
    'clinical.calculate_risk(integer)',
    'EXECUTE'
);
```

Preserve routine identity arguments because overloaded routines can share a name. Do not execute an unknown application routine merely to test authorization.

---

## 14. Type Privilege Evidence

```sql
SELECT has_type_privilege(
    'app_runtime',
    'clinical.patient_status',
    'USAGE'
);
```

This can matter for enums, domains, composite types, range types, and other user-defined types.

---

## 15. Direct Role Membership

Direct memberships are represented in `pg_auth_members`.

PostgreSQL 18 membership records include `admin_option`, `inherit_option`, and `set_option`.

```text
ADMIN   -> can administer/grant membership
INHERIT -> privileges can be inherited through the membership
SET     -> member can SET ROLE to the granted role
```

A direct membership row is useful evidence, but direct membership is not the complete transitive membership graph.

---

## 16. Effective Role Relationships with pg_has_role()

Memberships can form chains. PostgreSQL provides `pg_has_role()` for role relationship inquiries.

Important checks include:

```text
MEMBER
USAGE
SET
```

Use `pg_auth_members` for direct membership configuration and `pg_has_role()` for effective role relationship inquiry. Do not treat them as interchangeable.

---

## 17. Role-Level INHERIT vs Membership INHERIT

Authorization evidence can include both `pg_roles.rolinherit` and `pg_auth_members.inherit_option`.

Do not reduce inheritance analysis to `rolinherit = true`. Inspect role attributes, membership-specific options, and the membership path together.

---

## 18. PUBLIC Is an Access Path

`PUBLIC` represents all roles. An audit should consider direct grants, membership, PUBLIC, and ownership rather than searching only for the subject role's name.

---

## 19. Ownership Requires Separate Evidence

Ownership is not merely another ACL row.

An object's owner normally starts with the object's ordinary privileges and implicitly possesses grant-option authority. Owners also have inherent ownership authority over the object. Ordinary privileges can nevertheless be revoked from the owner.

Record ownership independently.

---

## 20. Superuser Authority

A PostgreSQL superuser bypasses ordinary permission checks. Therefore `rolsuper = true` is critical authorization evidence.

Never conclude that a role lacks access solely because there is no explicit ACL without considering superuser status.

---

## 21. BYPASSRLS

`pg_roles.rolbypassrls` is separate from ordinary table privileges and must be captured as security-sensitive authorization evidence.

---

## 22. Predefined Roles

PostgreSQL provides predefined roles that can confer broad capabilities, including `pg_read_all_data` and `pg_write_all_data`.

A role can therefore have broad access without appearing directly in an object's ACL.

Predefined-role semantics should be verified against the PostgreSQL version in use because their capabilities can evolve between releases.

---

## 23. Explicit Configured ACL Evidence

ACL expansion can expose grantor, grantee, privilege type, and grantability.

However:

```text
explicit ACL expansion != complete effective authorization
```

A relation without an explicit ACL entry might not appear in an ACL-expansion result. That absence does not prove that the role lacks access.

---

## 24. Row-Level Security Is Another Layer

Useful evidence includes:

```text
relrowsecurity
relforcerowsecurity
rolbypassrls
row_security_active()
```

`row_security_active() = true` does not tell you exactly which rows are visible, and table `SELECT = true` does not prove unrestricted row visibility.

Part 4.11 examines RLS policy design and validation in detail.

---

## 25. Views and Other Relation Types

Applications may access tables, partitioned tables, views, materialized views, and foreign tables. Record the relation type as part of the evidence and do not assume every relation follows the same authorization path.

---

## 26. Cluster-Wide vs Database-Local Evidence

PostgreSQL roles and membership information are cluster-wide. Most application objects are database-local.

Retained evidence should ideally identify:

```text
environment / cluster
database
role
schema
object
privilege
collection time
```

---

## 27. Managed PostgreSQL Services

Managed PostgreSQL services can introduce provider-specific administrative roles and restrictions.

Report PostgreSQL-visible facts such as `rolsuper`, `rolbypassrls`, memberships, ownership, and effective privileges. Do not automatically translate a provider-defined administrative role into PostgreSQL superuser.

---

## 28. Production Investigation Workflow

1. Record database, `session_user`, `current_user`, and `current_role`.
2. Inspect role attributes.
3. Inspect direct memberships and membership options.
4. Use `pg_has_role()` when effective membership needs verification.
5. Check database prerequisites.
6. Check schema prerequisites.
7. Check the target object with the appropriate `has_*_privilege()` function.
8. Check grant option when relevant.
9. Record ownership.
10. Inspect explicit ACL evidence.
11. Check PUBLIC.
12. Check predefined-role membership.
13. Check RLS indicators.
14. Record verified facts separately from interpretation.

Do not claim a causal access path merely because two facts coexist.

---

## 29. Evidence Quality

Weak evidence:

```text
I looked at the ACL and did not see the role.
```

Better evidence records the role, database `CONNECT`, schema `USAGE`, object privilege, owner, superuser status, BYPASSRLS status, and RLS state.

Stronger evidence additionally captures membership, predefined roles, PUBLIC, explicit ACLs, grant options, object identity, database context, and collection time.

---

## 30. Production Query Scope

SAFE-READ does not mean zero operational cost.

Avoid unnecessarily generating every role × every object × every privilege during production incidents.

Prefer scoped investigation by role, schema, object, and privilege. Broad inventory queries are more appropriate for controlled labs or deliberately scheduled audit collection.

---

## 31. Audit Output Is Security-Sensitive

A read-only authorization report can reveal administrative roles, superuser identities, BYPASSRLS roles, memberships, object names, SECURITY DEFINER routines, RLS configuration, and grant relationships.

```text
SAFE-READ != safe to publish
```

Store and share production authorization evidence according to organizational security controls.

---

## 32. Avoid Dangerous Verification

Do not prove authorization by unnecessarily exercising it.

Avoid `INSERT`, `UPDATE`, `DELETE`, `nextval()`, `setval()`, application routine execution, `GRANT`, `REVOKE`, or `SET ROLE` merely to discover whether permission exists.

Prefer privilege inquiry functions, `pg_has_role()`, and catalog inspection.

---

## 33. Allow and Deny Acceptance

Application-specific security testing should eventually validate both expected allow and expected deny behavior.

The reusable Part 4.9 artifact remains an evidence collector. Environment-specific assertions belong in application-specific tests and the integrated Part 4.15 project.

---

## 34. SAFE-READ Acceptance Strategy

The canonical artifact inspects session identity, role attributes, direct memberships, database privileges, schema privileges, relation privileges, column privileges, sequence privileges, routine privileges, type privileges, ownership, explicit ACL metadata, and RLS indicators.

It does not switch roles, change grants, modify roles or ownership, mutate application data, advance sequences, execute application routines, or perform maintenance.

Therefore it remains:

```text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
```

- [ ] Use `pg_has_role()` when effective membership needs verification.
- [ ] Check predefined-role memberships.
- [ ] Check database and schema prerequisites.
- [ ] Use the appropriate `has_*_privilege()` function.
- [ ] Check grant-option capability when relevant.
- [ ] Check ownership separately.
- [ ] Inspect PUBLIC.
- [ ] Treat explicit ACLs as supporting evidence.
- [ ] Check RLS indicators.

## 36. Key Takeaways

Effective PostgreSQL authorization is broader than an ACL string.

```text
effective privilege inquiry
          +
direct/effective membership
          +
PUBLIC
          +
ownership
          +
role attributes
          +
predefined roles
          +
database/schema prerequisites
          +
object-specific controls
          =
authorization evidence
```

Remember:

```text
no direct ACL != no access
direct membership != complete membership graph
table privilege != complete application access path
column privilege = true != explicit column grant exists
SELECT privilege = true != all rows visible
privilege exists != grant option exists
SAFE-READ != safe to publish
```

A reliable DBRE/SRE privilege audit combines PostgreSQL privilege-inquiry functions with membership, ownership, ACL, role-attribute, prerequisite, and security-layer evidence while clearly separating verified facts from interpretation.
