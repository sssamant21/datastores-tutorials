# Part 4.11 — Row-Level Security Design and Validation

**Target:** PostgreSQL 18
**Status:** Revised Final / Canonical Edition
**Track:** Part 4 — Users, Roles & Security

## 1. Why Row-Level Security Matters

Traditional PostgreSQL privileges answer whether a role can SELECT, INSERT, UPDATE, or DELETE. Row-Level Security (RLS) adds another authorization layer: which rows the role may see, create, change, or delete.

```text
object privilege
      |
      v
RLS state
      |
      v
applicable policies
      |
      v
row-level authorization
```

Therefore, `has_table_privilege(..., 'SELECT') = true` does not prove that all rows are visible. RLS should be treated as production authorization code.

## 2. Authorization Model

A useful production model is:

```text
execution identity
+ table privileges
+ RLS enabled/forced state
+ ownership
+ SUPERUSER/BYPASSRLS
+ applicable policies
+ policy composition
+ policy expressions
+ trusted runtime context
= RLS authorization evidence
```

No single catalog flag proves effective row visibility.

## 3. Enabling RLS and Default Deny

RLS is enabled with:

```sql
ALTER TABLE clinical.patient ENABLE ROW LEVEL SECURITY;
```

Catalog evidence appears in `pg_class.relrowsecurity`. Enabling RLS and defining a policy are separate operations.

For ordinary RLS-subject access:

```text
RLS enabled
+ no applicable permissive policy
= default deny
```

Do not reduce this to `policy_count = 0 = everyone denied`. Policies can exist without applying to a particular role or command. Ownership, `FORCE ROW LEVEL SECURITY`, superuser status, and `BYPASSRLS` also matter.

## 4. Creating Policies

Example:

```sql
CREATE POLICY patient_select_policy
ON clinical.patient
FOR SELECT
TO app_runtime
USING (tenant_id = current_setting('app.tenant_id')::bigint);
```

A policy does not grant table privileges. The role still needs the corresponding object privilege.

## 5. USING and WITH CHECK

`USING` evaluates existing-row eligibility. `WITH CHECK` evaluates proposed/new-row eligibility.

For example:

```sql
CREATE POLICY patient_update_policy
ON clinical.patient
FOR UPDATE
TO app_runtime
USING (tenant_id = current_setting('app.tenant_id')::bigint)
WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);
```

For policy forms where both expressions can apply, PostgreSQL can use `USING` as the effective row check when an explicit `WITH CHECK` is omitted. Therefore `polwithcheck IS NULL` does not mean there is no effective write restriction.

Command-specific forms are:

```text
SELECT  → USING
INSERT  → WITH CHECK
UPDATE  → USING + WITH CHECK
DELETE  → USING
ALL     → USING + WITH CHECK
```

For UPDATE, review both the existing-row boundary and resulting-row boundary. Tenant-changing updates are an important negative test.

## 6. Command Interactions and MERGE

Do not assume an UPDATE statement involves only an UPDATE policy. Row retrieval, `RETURNING`, locking, conflict handling, and other SQL behavior can involve additional privilege and policy paths.

PostgreSQL 18 has no independent `FOR MERGE` policy category. `MERGE` can interact with SELECT-related access and INSERT, UPDATE, or DELETE policies according to the actions actually executed. Production validation should test the application's actual MERGE branches.

## 7. Policy Roles and Applicability

Policies can target `PUBLIC` or specific roles. Applicability can also depend on role membership. Therefore a role name appearing in `polroles`, or a nonzero total policy count, is not a complete current-user applicability test.

## 8. pg_policy and pg_policies

`pg_policy` exposes lower-level policy metadata including `polname`, `polrelid`, `polcmd`, `polpermissive`, `polroles`, `polqual`, and `polwithcheck`.

PostgreSQL 18 command codes include:

```text
r → SELECT
a → INSERT
w → UPDATE
d → DELETE
* → ALL
```

Role OID 0 in `polroles` represents `PUBLIC`.

The `pg_policies` view provides operator-friendly evidence including schema, table, policy name, permissive/restrictive mode, roles, command, `qual`, and `with_check`.

## 9. Policy Defaults and Composition

Policy defaults matter when clauses are omitted; operators should inspect resolved metadata rather than infer behavior only from abbreviated DDL.

Applicable permissive policies combine conceptually with OR. Applicable restrictive policies combine with AND:

```text
(permissive A OR permissive B OR ...)
                 AND
restrictive A
                 AND
restrictive B
                 ...
```

Restrictive policies alone do not create access. Review the complete applicable policy set.

## 10. Table Owners, FORCE RLS, Superusers, and BYPASSRLS

Record table ownership for every RLS-protected table under investigation. Table owners normally have special RLS behavior compared with ordinary application roles.

`ALTER TABLE ... FORCE ROW LEVEL SECURITY` changes owner-related assumptions and is represented by `pg_class.relforcerowsecurity`. Audit both `relrowsecurity` and `relforcerowsecurity`.

Always inspect `rolsuper` and `rolbypassrls`. Do not validate application RLS behavior only from privileged sessions, and never solve an RLS outage casually by granting `BYPASSRLS` or moving the application to a superuser-equivalent identity.

## 11. row_security_active()

`row_security_active(regclass)` provides SAFE-READ evidence about whether row security is active for the specified table in the current execution context.

```text
row_security_active() = true
!= proof of which rows are visible
```

Combine it with ownership, role attributes, RLS state, policy configuration, and runtime context.

## 12. SECURITY DEFINER and RLS

A privileged routine can cross an authorization boundary:

```text
app_runtime
   → SECURITY DEFINER routine
   → routine owner
   → RLS-protected table
```

Review routine owner, table owner, `rolsuper`, `rolbypassrls`, FORCE RLS, and policy configuration together. Do not assume the caller's RLS behavior automatically survives a privileged execution boundary. See Part 4.10 for privileged-routine hardening.

## 13. Policy Helper Functions

If an RLS expression calls a helper function, that function becomes part of the authorization boundary. Review its owner, security mode, EXECUTE exposure, `search_path`, dependencies, dynamic SQL, and implementation.

## 14. Tenant Context and Connection Pooling

An expression such as `current_setting('app.tenant_id')` does not automatically represent trusted identity. Review who sets it, who can change it, whether it is transaction-local, when it is reset, error handling, and whether a client can select another tenant.

Connection reuse makes this particularly important:

```text
request A sets tenant 100
→ connection returned
→ context remains
→ request B reuses connection
```

Correct RLS policy logic does not prove that tenant context is trustworthy.

## 15. BEFORE Triggers

For writes, a simplified path can include:

```text
incoming row
→ BEFORE ROW trigger
→ possibly modified row
→ WITH CHECK
```

Unexpected INSERT/UPDATE behavior can therefore require trigger review as well as policy review.

## 16. Partitioned Tables

The canonical audit includes ordinary tables and partitioned tables (`relkind IN ('r','p')`). For partitioned designs, review the parent and partitions deliberately. Do not assume one catalog row represents the complete security state of every object in the hierarchy.

## 17. Least Privilege

RLS does not replace object-level least privilege. Strong design combines least-privilege table/schema access with RLS, appropriate ownership, controlled role membership, and secure routines.

## 18. Backup and Restore

Application RLS behavior and backup behavior are separate concerns. Validate backup identity, `pg_dump` options, RLS behavior, restore identity, and restore results independently. Do not assume an application's row visibility determines backup contents.

## 19. Production Investigation Workflow

1. Record `current_database()`, `session_user`, `current_user`, and `current_role`.
2. Find RLS-enabled tables and record `relrowsecurity` and `relforcerowsecurity`.
3. Record table ownership.
4. Record current-role `rolsuper` and `rolbypassrls`.
5. Inspect relevant table privileges with `has_table_privilege()`.
6. Inventory policy names, commands, roles, permissive/restrictive state, `USING`, and `WITH CHECK`.
7. Use `row_security_active()` where appropriate.
8. Review helper functions, session settings, tenant context, triggers, and partition hierarchy.
9. Perform controlled behavioral validation with synthetic identities/data.
10. Record facts separately from conclusions.

## 20. Controlled Allow/Deny Testing

Production RLS changes require both positive and negative tests. For multi-tenant systems, validate same-tenant and cross-tenant SELECT/INSERT/UPDATE, tenant-changing UPDATE, DELETE, and relevant MERGE branches.

Use synthetic identities and rows. The generic acceptance artifact must not perform these behavioral tests automatically.

## 21. Production Change Safety and Rollback

Security-sensitive changes include enabling/disabling RLS, FORCE/NO FORCE RLS, and creating/altering/dropping policies. Failure modes include unexpected denial, access expansion, cross-tenant exposure, failed writes, outages, and changed owner behavior.

Before remediation, capture RLS/FORCE state, owner, policy definitions, commands, roles, permissive/restrictive state, expressions, helper dependencies, and runtime-context mechanism. Rollback should restore a known authorization state.

During incidents, preserve evidence before emergency changes where practical.

## 22. Managed Services and Security Maintenance

Managed PostgreSQL services can expose provider-specific administrative roles. Report PostgreSQL-visible evidence without automatically equating provider administrators with unrestricted native PostgreSQL superusers.

RLS is security-sensitive functionality. Keep PostgreSQL 18 on a supported and appropriately patched minor release according to organizational maintenance policy.

## 23. Audit Evidence Is Sensitive

RLS inventory can reveal table names, owners, security roles, tenant architecture, policy expressions, session-setting names, BYPASSRLS identities, and authorization logic.

```text
SAFE-READ != safe to publish
```

Protect production evidence appropriately.

## 24. SAFE-READ Acceptance Strategy

The canonical acceptance artifact inspects execution context, current-role security attributes, RLS-enabled tables, FORCE RLS, ownership, current-user table privileges, `row_security_active()`, `pg_policies`, `pg_policy`, policy roles/commands, composition metadata, expressions, counts, and review signals.

It does not read application rows; execute INSERT/UPDATE/DELETE/MERGE; switch identity; change RLS/FORCE state; create/alter/drop policies; grant/revoke privileges; change ownership; or modify application data.

```text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
```

## 25. Production Checklist

- Record execution identity, RLS/FORCE state, and owner.
- Inspect `rolsuper`, `rolbypassrls`, and table privileges.
- Inventory all policies, commands, roles, membership implications, composition mode, `USING`, and effective `WITH CHECK` semantics.
- Review tenant/session context and connection pooling.
- Review helper functions, triggers, partition hierarchy, and SECURITY DEFINER interactions.
- Test the actual application identity with expected allow and deny cases using synthetic data.
- Test relevant MERGE actions and backup/restore behavior separately.
- Capture rollback state and protect audit evidence.
- Keep PostgreSQL security fixes current.

## 26. Key Takeaways

```text
object privilege
+ RLS state
+ execution identity
+ ownership/bypass state
+ applicable policies
+ policy composition
+ policy expressions
+ trusted runtime context
= row-security authorization
```

Remember:

```text
table SELECT = true                 != all rows visible
RLS enabled                         != every identity restricted identically
policies exist                      != an applicable policy exists
policy_count                        != effective authorization
polwithcheck IS NULL                != no effective row check
one policy                          != complete policy behavior
row_security_active() = true        != proof of visible rows
correct policy                      != trusted tenant context
SAFE-READ                           != safe to publish
```

For DBRE/SRE teams, manage RLS as production authorization code: explicit, least-privileged, observable, testable, patch-maintained, and recoverable.
