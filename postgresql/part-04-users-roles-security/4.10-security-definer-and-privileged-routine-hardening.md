# Part 4.10 — `SECURITY DEFINER` and Privileged Routine Hardening

**Target:** PostgreSQL 18
**Status:** Revised Final / Canonical Edition
**Track:** Part 4 — Users, Roles & Security

## Purpose

`SECURITY DEFINER` deliberately crosses a PostgreSQL authorization boundary. The caller executes a routine using the function owner's privileges. This can provide controlled privilege delegation, but ownership, `EXECUTE` exposure, name resolution, routine implementation, dynamic SQL, and RLS context must be reviewed together.

## Core model

```text
caller
   |
   | EXECUTE
   v
SECURITY DEFINER routine
   |
   | owner authority
   v
protected operation
```

`SECURITY INVOKER` is the normal/default execution model. `SECURITY DEFINER` executes with the function owner's authority.

## Owner authority

Prefer a dedicated, minimally privileged owner, preferably `NOLOGIN` where practical. Review `rolsuper`, `rolcreaterole`, `rolcreatedb`, `rolreplication`, `rolbypassrls`, and `rolcanlogin`. Powerful attributes are review signals, not automatic vulnerability declarations.

## EXECUTE exposure

Audit effective `EXECUTE`, `EXECUTE WITH GRANT OPTION`, PUBLIC access, and explicit ACL evidence. For deliberately restricted routines, create and restrict privileges atomically:

```sql
BEGIN;
CREATE FUNCTION clinical.privileged_operation(bigint)
RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = clinical, pg_temp
AS $$
BEGIN
    -- controlled operation
END;
$$;
REVOKE ALL ON FUNCTION clinical.privileged_operation(bigint) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION clinical.privileged_operation(bigint) TO app_runtime;
COMMIT;
```

## Secure `search_path`

Use an intentionally controlled resolution path. A typical hardened pattern is:

```text
trusted schema(s), pg_temp
```

with `pg_temp` last. The concern is whether an untrusted role can create objects in a schema participating in privileged name resolution, not the schema name itself.

Schema qualification is defense-in-depth but does not replace controlled `search_path`, because functions, operators, types, casts, and other objects can participate in resolution.

A missing routine-level `search_path` means **REVIEW REQUIRED**, not automatically a confirmed vulnerability.

## Exact routine identity

Preserve database, schema, routine name, identity arguments, routine kind, and owner. Use `pg_get_function_identity_arguments(p.oid)` for overloaded routines.

## Routine configuration

`pg_proc.proconfig` exposes routine-local configuration. Capture it and extract configured `search_path` separately. Checking only the routine's own schema does not validate every schema in its effective resolution path.

## Dynamic SQL

`SECURITY DEFINER` plus dynamic SQL requires manual source review. Caller-controlled identifiers must be safely constructed. Do not use `pg_proc.prosrc` as a universal security scanner.

## Identity inside privileged code

During a `SECURITY DEFINER` function, `current_user` reflects the function-owner execution context while `session_user` continues to identify the session identity. Do not assume `current_user` is the original caller.

## Role administration and RLS

Privileged routines that administer roles require elevated review, including PostgreSQL 18 `createrole_self_grant` behavior where applicable. If the owner has `BYPASSRLS`, record that fact; detailed RLS policy evaluation belongs in Part 4.11.

## Production workflow

1. Record database and execution identity.
2. Discover `pg_proc.prosecdef = true`.
3. Record exact routine identity and kind.
4. Record owner and owner attributes.
5. Inspect `proconfig` and routine `search_path`.
6. Review schemas participating in privileged resolution.
7. Check current-user and PUBLIC `EXECUTE`, grant options, and explicit ACLs.
8. Review source for dynamic SQL, unqualified references, caller-controlled identifiers, and privileged operations.
9. Record facts separately from conclusions.

## Production remediation and rollback

Do not automatically remediate audit findings. `REVOKE`, `GRANT`, ownership changes, routine `search_path` changes, and schema CREATE changes are security-sensitive. Capture the current owner, ACL, `proconfig`, effective EXECUTE state, schema privileges, and dependencies first. Define rollback before making changes.

## Managed services and evidence sensitivity

Managed services can expose provider-specific administrative roles. Report PostgreSQL-visible attributes without automatically equating provider administrators with native PostgreSQL superusers.

Privileged-routine evidence can expose security-sensitive entry points and role information:

```text
SAFE-READ != safe to publish
```

## SAFE-READ acceptance

The canonical artifact inspects metadata only. It does not execute discovered routines, switch roles, change privileges/configuration/ownership, create or drop objects, or modify application data.

```text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
```

## Production checklist

- Record exact routine identity and kind.
- Confirm `SECURITY DEFINER`.
- Review owner authority.
- Inspect `proconfig` and routine `search_path`.
- Keep trusted schemas before `pg_temp`.
- Review writable schemas and schema qualification.
- Check PUBLIC and intended-role EXECUTE.
- Check grant-option exposure and explicit ACL evidence.
- Review dynamic SQL and caller-controlled identifiers.
- Review role-administration and BYPASSRLS implications.
- Validate allow/deny cases in a controlled environment.
- Define rollback before remediation.
- Protect audit evidence.

## Key takeaways

A defensible privileged routine combines minimal owner authority, restricted `EXECUTE`, controlled `search_path`, trusted schemas, `pg_temp` last, qualified security-sensitive references, safe dynamic SQL, and a small privileged surface.

`SECURITY DEFINER`, PUBLIC EXECUTE, or a missing routine-level `search_path` are important evidence, but none alone proves exploitability. Metadata review does not replace source-code security review.
