# Part 4.14 — Security Baseline, Drift Detection, and Access Validation

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Track:** Part 4 — Users, Roles & Security

## 1. Purpose

A PostgreSQL security baseline is a reviewed evidence set describing expected security-relevant state. Re-running the same bounded evidence allows DBRE/SRE teams to detect changes and decide whether they are expected, approved exceptions, unexpected drift, or insufficiently understood.

```text
approved known-good state
        ↓
repeatable evidence
        ↓
deterministic comparison
        ↓
classified drift
        ↓
investigation / approval
        ↓
controlled remediation or baseline update
```

A difference is not automatically a vulnerability, and the current state is not automatically the desired state.

## 2. Evidence Hierarchy

Use multiple evidence layers:

```text
Level 1 — Identity
roles + attributes

Level 2 — Delegation
role memberships + membership options

Level 3 — Authority
ownership

Level 4 — Explicit access
ACLs + column privileges + default privileges

Level 5 — Broad/effective access
PUBLIC + privilege-check functions

Level 6 — Privileged execution
SECURITY DEFINER

Level 7 — Row filtering
RLS state + policies

Level 8 — Connection security
Part 4.12 authentication + Part 4.13 TLS evidence

Level 9 — Behavioral validation
controlled expected-allow / expected-deny tests
```

No single catalog row proves the complete effective-access model.

## 3. Role Attribute Baseline

Use `pg_roles` for SAFE-READ role-attribute evidence. Useful attributes include login capability, inheritance, role/database creation, replication, superuser, BYPASSRLS, connection limit, and password-validity metadata.

`rolvaliduntil` concerns password validity; it is not a general account-expiration timestamp. `rolconnlimit` is useful operational evidence but is not an ACL-style authorization boundary.

Do not collect password verifiers from `pg_authid`.

## 4. Role Membership Baseline

Membership can create effective access that direct object ACLs do not show.

For PostgreSQL 18, preserve evidence for:

```text
member
granted role
grantor
ADMIN option
INHERIT option
SET option
```

Also review membership in PostgreSQL predefined roles. Do not hard-code a timeless list of “dangerous” roles; predefined roles and their capabilities are version-sensitive and managed services can add provider-specific roles.

## 5. Ownership Baseline

Ownership conveys authority beyond ordinary ACL grants. Track owners of security-relevant databases, schemas, relations, sequences, and routines.

Unexpected ownership transfer is important drift, but it still requires investigation before remediation.

## 6. Database and Schema Baseline

Database evidence can include owner, connection policy metadata, and ACLs. Schema evidence should distinguish `USAGE` from `CREATE`.

`PUBLIC` represents all PostgreSQL roles. PUBLIC access must be reviewed against the intended model rather than automatically labeled insecure.

## 7. Relation and Column Baseline

Tables, partitioned tables, views, materialized views, foreign tables, and sequences do not all share identical privilege semantics.

Track object type, owner, ACL, and relevant RLS state. Track explicit column ACLs separately where present.

For large environments, scope collection to approved application schemas.

## 8. Sequence Baseline

Sequences have distinct privilege semantics and deserve explicit evidence. Baseline sequence identity, ownership, and ACL independently from ordinary table access.

## 9. Routine Baseline

Routine evidence must be overload-safe. Identify routines using schema, name, and identity arguments.

Also preserve routine kind, owner, security mode, ACL, and routine-local configuration.

`SECURITY DEFINER` is a review signal, not proof of a vulnerability. Review owner, executable exposure, routine behavior, and hardened `search_path` design.

## 10. Default Privilege Baseline

Default privileges affect future objects and depend on creator-role and schema context.

```text
default privileges
        !=
privileges on existing objects
```

Baseline creator role, schema scope, object type, and ACL.

## 11. PUBLIC and Effective-Privilege Evidence

Raw ACL arrays are useful evidence but should be complemented by PostgreSQL privilege-check functions.

Useful bounded checks include:

```text
has_database_privilege(...)
has_schema_privilege(...)
has_table_privilege(...)
has_sequence_privilege(...)
has_function_privilege(...)
```

Privilege-check functions are still not a complete security verdict. Ownership, membership, RLS, privileged routines, authentication, TLS, and provider controls remain relevant.

## 12. Row-Level Security Baseline

For RLS-enabled objects, capture table RLS state and policy metadata including policy name, command, applicable roles, permissive/restrictive behavior, `USING`, and `WITH CHECK`.

Policy expressions can expose business/security logic.

```text
RLS enabled != policy correctness proven
```

Owners, `BYPASSRLS`, FORCE RLS, applicable policies, and runtime role identity must be considered.

## 13. Authentication and TLS Boundaries

Do not duplicate the complete authentication/TLS collectors here.

Use:

- Part 4.12 for authentication/HBA evidence.
- Part 4.13 for TLS/client-certificate evidence.

Preserve the distinction among file/configuration state, runtime behavior, client policy, and external proxy/load-balancer behavior.

## 14. Effective Access Expectations

Security baselines are stronger when tied to explicit expectations.

Example:

```text
app_runtime

expected allow:
  CONNECT appdb
  USAGE app
  SELECT / INSERT / UPDATE approved tables

expected deny:
  CREATE in protected schemas
  role administration
  ownership changes
  privileged maintenance outside approved scope
```

Catalog evidence should be complemented by controlled behavioral tests where appropriate.

The generic SAFE-READ collector does not use `SET ROLE` or impersonate application identities.

## 15. Drift Disposition

Use four dispositions:

```text
EXPECTED_CHANGE
APPROVED_EXCEPTION
UNEXPECTED_DRIFT
INSUFFICIENT_EVIDENCE
```

None automatically authorizes remediation.

## 16. Deterministic Snapshot Design

Prefer:

- stable ordering,
- qualified identities,
- overload-safe routine identities,
- explicit object type,
- bounded schema scope,
- normalized privilege rows for mature systems,
- no secrets,
- PostgreSQL version/context metadata,
- timestamps stored outside canonical comparison payloads when appropriate.

Raw ACL arrays are acceptable educational evidence, but normalized grants are usually easier to compare at production scale.

## 17. Intentional Scope Exclusion

The canonical lab excludes `pg_%` schemas and `information_schema` from application-object inventories.

This reduces noise for application-focused review. It does **not** make the result a complete cluster-wide security audit.

Extensions and providers can also create objects in non-system schemas; non-system does not automatically mean application-owned.

## 18. Evidence Sensitivity

Security snapshots can expose:

- role and service-account names,
- membership topology,
- database/schema/object names,
- ACLs,
- routine configuration,
- RLS expressions,
- certificate/authentication architecture when combined with other artifacts.

```text
SAFE-READ != safe to publish
```

Store baseline evidence with access control, integrity protection, version history, and change control.

## 19. Managed Services and Extensions

Managed PostgreSQL platforms may introduce provider-owned roles, objects, grants, schemas, extensions, and security controls. Service maintenance or extension upgrades can legitimately change baseline evidence.

Classify ownership and provenance before remediation.

## 20. Break-Glass Access

Emergency access can legitimately create temporary drift.

Break-glass access should be time-bounded, audited, reviewed, and removed when no longer required. Do not silently redefine the permanent baseline around emergency access.

## 21. Production Drift Workflow

```text
detect
  ↓
classify
  ↓
investigate
  ↓
validate impact
  ↓
approve
  ↓
remediate
  ↓
verify
  ↓
update baseline only if approved
```

Do not auto-remediate catalog differences.

## 22. Production Performance

SAFE-READ means no intentional state mutation; it does not mean zero load.

Large role/object inventories and privilege-check matrices can be expensive. Bound schema scope, avoid unnecessary role × object Cartesian products, and schedule large evidence collections appropriately.

## 23. Remediation and Rollback

Before changing roles, memberships, ACLs, ownership, routines, default privileges, or RLS:

1. capture the relevant pre-change state,
2. identify dependent applications and operational tooling,
3. obtain approval,
4. define rollback,
5. apply the smallest intended change,
6. validate expected allow and expected deny behavior,
7. monitor,
8. update the approved baseline only after verification.

## 24. SAFE-READ Acceptance Artifact

The canonical lab collects database/catalog security evidence only.

It performs no:

- role or membership mutation,
- `GRANT` / `REVOKE`,
- ownership transfer,
- RLS mutation,
- `ALTER SYSTEM`,
- HBA/TLS modification,
- configuration reload,
- password-verifier inspection,
- `SET ROLE`,
- external authentication testing,
- automatic remediation,
- session termination.

```text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
```

## 25. Key Takeaways

```text
ACL row                  != complete effective access
difference               != vulnerability
current state            != approved desired state
baseline                 != approved unless reviewed
owner authority          != ordinary ACL privilege
PUBLIC                   != automatically unsafe
SECURITY DEFINER exists  != automatically vulnerable
RLS enabled              != policy correctness proven
SAFE-READ                != zero performance impact
SAFE-READ                != safe to publish
```

Security baselining is an evidence-and-review discipline: define intended access, collect repeatable bounded evidence, detect and classify drift, validate effective behavior, and change production only through controlled remediation.
