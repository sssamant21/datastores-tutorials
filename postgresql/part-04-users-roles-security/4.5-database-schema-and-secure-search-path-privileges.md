# Part 4.5 — Database, Schema, and Secure `search_path` Privileges

**Status:** Revised Final / Canonical Edition
**Target:** PostgreSQL 18
**Audience:** PostgreSQL administrators, DBREs, SREs, platform engineers
**Companion Lab:** `labs/database-schema-privilege-check.sql`

---

## 1. Learning Objectives

By the end of this tutorial, you should be able to:

- distinguish database privileges from schema and object privileges;
- explain `CONNECT`, `TEMPORARY`, database `CREATE`, schema `USAGE`, and schema `CREATE`;
- account for owner authority, direct grants, role membership, and `PUBLIC`;
- explain how PostgreSQL resolves unqualified names through `search_path`;
- recognize writable search-path schemas as a code-execution boundary;
- account for the special behavior of `pg_catalog` and temporary schemas;
- design a restricted application namespace;
- collect read-only evidence before changing privileges or session policy.

---

## 2. Access Is a Chain of Gates

A successful query can depend on several independent controls:

1. authentication and host policy permit a connection attempt;
2. the role has `CONNECT` on the selected database;
3. the role has `USAGE` on the containing schema;
4. the role has the required privilege on the target object;
5. row-level security, if enabled, permits the rows;
6. the statement resolves the intended object name.

Passing one gate does not imply passing the others. For example, `CONNECT` does not grant access to tables, and schema `USAGE` does not grant `SELECT`.

Superusers bypass ordinary object privilege checks. A privilege report for a superuser can therefore return broad access even when no matching ACL entry exists. Treat unexpected `SUPERUSER` status as an authority finding, not as proof that the ACL design is correct.

---

## 3. Database Privileges

PostgreSQL exposes three ordinary database privileges:

| Privilege | Meaning | Important limit |
| --- | --- | --- |
| `CONNECT` | Permits connection to the database | Checked at connection startup, in addition to `pg_hba.conf` |
| `TEMPORARY` (`TEMP`) | Permits creation of temporary tables while using the database | Does not grant durable schema creation |
| `CREATE` | Permits creation of schemas and publications and installation of trusted extensions | Does not grant `CREATE` in every existing schema |

`CONNECT` is evaluated at connection startup together with authentication policy. It does not override `pg_hba.conf`, a database with connections disabled, or a reached connection limit. Conversely, `CONNECT` revocation is not a session-termination mechanism. Existing sessions must be handled explicitly under a reviewed operational plan, and connection pools can otherwise preserve or re-establish access through identities that still qualify.

By default, a newly created database grants `CONNECT` and `TEMPORARY` to `PUBLIC`; it does not grant database `CREATE` to `PUBLIC`. Actual ACLs may differ because of explicit grants, revokes, template history, or default-privilege policy.

Database owners retain owner authority. An ACL view alone is therefore not a complete authorization model.

---

## 4. Schema Privileges

Schemas are namespaces inside a database. Their two ordinary privileges have different purposes:

| Privilege | Meaning |
| --- | --- |
| `USAGE` | Allows object lookup in the schema, subject to each object's privileges |
| `CREATE` | Allows creation of new objects in the schema |

`USAGE` does not reveal secret object names: catalog visibility is a separate concern, and names can remain visible without access. Revoking `USAGE` is also not an instant invalidation guarantee for lookups already performed by existing sessions.

Schema `CREATE` is security-sensitive. A role that can create objects in a schema can introduce tables, types, functions, or operators whose names collide with unqualified references.

---

## 5. `PUBLIC` and Effective Privileges

`PUBLIC` is the implicit group of every current and future role. Effective access can be obtained through:

- a direct grant;
- membership in another role;
- a grant to `PUBLIC`;
- object ownership;
- superuser authority.

Revoking one direct grant does not remove access supplied by another path. Use PostgreSQL's privilege inquiry functions to test effective access for a declared role, then retain raw ACL and ownership evidence to explain why that access exists.

`NULL` in an ACL column does not mean that nobody has access. It means the object's default ACL applies. For databases, the default includes `CONNECT` and `TEMPORARY` for `PUBLIC`; for schemas generally, no privileges are granted to `PUBLIC` by the generic object default.

---

## 6. The `public` Schema Is Not the `PUBLIC` Group

The lowercase `public` schema is an ordinary schema created in new databases. Uppercase `PUBLIC` in privilege syntax means every role.

PostgreSQL grants `USAGE` on the `public` schema to everyone by default. In PostgreSQL 15 and later, a newly initialized database supports the safer pattern in which ordinary users do not receive `CREATE` there. Databases upgraded from PostgreSQL 14 or earlier can retain public `CREATE` and must be inspected rather than assumed safe.

A common hardening change is:

```sql
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
```

That statement changes authorization state. Before running it, inventory existing objects and owners, application behavior, migrations, extensions, repair steps, and rollback requirements. Revocation does not relocate or remove objects already created.

---

## 7. How `search_path` Resolves Names

`search_path` is the ordered list PostgreSQL uses for unqualified object names. The first matching object wins. If no match exists, the reference fails even if an object with that name exists outside the effective path.

The default setting is commonly:

```text
"$user", public
```

`$user` means a schema named after `current_user`; it is ignored if that schema does not exist or is not usable. Other nonexistent or inaccessible path entries are also ignored. `current_schemas(false)` reports resolved explicit entries, while `current_schemas(true)` includes implicit system schemas.

For unqualified creation, PostgreSQL uses the first valid schema in the effective path. If there is no valid target schema, creation fails. Therefore, a path controls both lookup and the default destination of new objects.

---

## 8. A Writable Path Is a Trust Boundary

Adding a schema to `search_path` effectively trusts every role that can create objects in that schema. A malicious or accidental object can capture an unqualified reference and change query behavior. Depending on the reference and execution context, this can lead to arbitrary SQL function execution with the invoking role's authority.

A secure design therefore requires both:

- a deliberately ordered path; and
- no untrusted `CREATE` authority in searched schemas.

Checking only the text of `search_path` is insufficient. Review the resolved path, schema owners, effective `CREATE` privileges, inherited access, `PUBLIC`, and session identity. A safe path for one role can be unsafe for another.

Security-sensitive code should schema-qualify trusted objects. Privileged routines need additional `search_path` hardening, covered in Part 4.10.

---

## 9. `pg_catalog` and Temporary Schema Nuances

`pg_catalog` is always effectively searched. If it is not explicitly listed, PostgreSQL searches it before explicit path entries. Explicitly placing it later allows earlier user schemas to override built-in names and requires exceptional scrutiny.

When a session has a temporary schema, PostgreSQL searches it first if it is not explicitly listed. This implicit temporary-schema lookup applies to relation and data-type names, not function or operator names. Temporary schemas therefore still matter to unqualified table and type references. Database `TEMPORARY` permits creation of temporary tables; it is distinct from durable schema `CREATE` and from ordinary creation in an application schema.

Do not infer the complete lookup order from `SHOW search_path` alone. Compare the configured value with `current_schemas(true)` and understand the object class being resolved.

## 10. Recommended Application Pattern

A typical restricted design uses:

- a dedicated database;
- a `NOLOGIN` application owner;
- a controlled deployment identity;
- a runtime login or group role;
- a dedicated application schema owned by the owner;
- `USAGE`, but normally not `CREATE`, for runtime roles;
- object privileges granted separately;
- an explicit, reviewed runtime `search_path`;
- no untrusted writable schema before trusted namespaces.

Example policy intent:

```text
database: clinical
schema: clinical_app
owner: clinical_owner (NOLOGIN)
runtime: clinical_runtime (LOGIN)

clinical_runtime:
  CONNECT on database clinical
  USAGE on schema clinical_app
  no database CREATE
  no CREATE on schema clinical_app
  only required object privileges
```

The example is a design target, not executable production authorization. Object privileges and future-object defaults are covered in Parts 4.6 through 4.8.

## 11. Change Planning and Rollback

Privilege and path changes can break connection pools, migrations, extension installation, temporary-table workloads, monitoring, maintenance jobs, and unqualified SQL. Before a change:

1. capture database and schema owners plus raw ACLs;
2. test effective privileges for every service and administrative identity;
3. inventory `PUBLIC` and inherited access;
4. capture configured and resolved search paths;
5. identify every writable searched schema;
6. test in a representative non-production environment;
7. define session-drain, pool-restart, stop, and rollback criteria;
8. retain exact reverse statements only after validating that they do not restore unsafe access.

Never copy a blanket `GRANT ... TO PUBLIC` into rollback merely to restore service quickly. Restore the smallest known-good authorization state.

Run production inspection from an approved administrative path with a least-privileged auditor. Prefer evidence from the authoritative target database. Results collected from a hot standby can lag the primary and must be labeled with recovery state, collection time, and replica-lag context. A clean report is point-in-time evidence, not proof that later grants, role memberships, session settings, or provider controls remain unchanged.

Privilege remediation can affect connection startup, temporary-table workloads, migrations, extension installation, object creation, and unqualified SQL. Use a reviewed maintenance plan, observe error rates and pool behavior, and define abort thresholds before applying changes. Do not terminate sessions, restart pools, or change `search_path` merely because this inspection reports a review signal.

## 12. Hands-On Lab — SAFE-READ Privilege and Path Audit

Run from the `postgresql/part-04-users-roles-security` directory:

```bash
umask 077
psql --no-psqlrc \
  --dbname=appdb \
  --set=expected_database=appdb \
  --set=expected_session_user=security_auditor \
  --set=application_role=clinical_runtime \
  --set=application_schema=clinical_app \
  --file=labs/database-schema-privilege-check.sql \
  --output=database-schema-privilege-check.out
```

The lab:

- hard-gates PostgreSQL 18, database, session identity, role, and schema;
- reports database owner, connection controls, and ACL state;
- reports the declared application's role attributes;
- tests application-role and `PUBLIC` database privileges;
- reports schema owner and ACL state;
- tests application-role and `PUBLIC` schema privileges;
- expands database and application-schema ACL entries;
- compares configured and resolved search paths;
- inventories effective path schemas and current-user writability;
- inventories application-role access across non-system schemas;
- runs in a repeatable-read, read-only transaction and rolls back.

The artifact does not impersonate the application role. `current_schemas(...)` describes the connected session, whereas `has_database_privilege` and `has_schema_privilege` evaluate the declared application role. Validate the application's actual session settings separately under approved test conditions.

Output contains security-sensitive role, owner, ACL, and namespace details. Protect it with restrictive permissions, approved retention, and redaction before external sharing. Catalog evidence does not cover cloud IAM, proxies, secret managers, federation, or provider control-plane access.

The queries are bounded to one database row, declared schemas, resolved path entries, ACL entries, and the database's non-system schema inventory. Even so, use an approved production connection, avoid repeated high-frequency execution, and stop if the platform reports unexpected catalog contention or latency. The lab does not terminate sessions, prove application connectivity, inspect object-level access, or validate the SQL text actually used by an application.

## 13. Production Review Checklist

- [ ] Every application identity has only required database privileges.
- [ ] `PUBLIC` database privileges are explicitly understood.
- [ ] Runtime roles lack database `CREATE` unless justified.
- [ ] Runtime roles have required schema `USAGE` but normally not schema `CREATE`.
- [ ] The `public` schema's owner and ACL reflect its history and intended policy.
- [ ] Upgraded databases have been checked for legacy public `CREATE`.
- [ ] Configured and effective search paths are both reviewed.
- [ ] No searched schema is writable by an untrusted role.
- [ ] `pg_catalog` ordering is deliberate.
- [ ] Temporary-schema lookup behavior is included in threat analysis.
- [ ] Security-sensitive SQL uses qualified trusted object names.
- [ ] Existing sessions and connection pools are included in revocation plans.
- [ ] Evidence was collected from the intended primary or a clearly labeled standby.
- [ ] Collection time, retention, access, and redaction requirements are recorded.
- [ ] Migrations, extensions, monitoring, and temporary-table workloads are tested.
- [ ] Change, rollback, stop, and recovery criteria are approved.
- [ ] External identity and provider control planes are reviewed separately.
- [ ] Audit evidence is protected and sanitized.

---

## 14. Key Takeaways

1. Database, schema, and object privileges are separate gates.
2. Effective access can arrive through ownership, membership, direct grants, or `PUBLIC`.
3. Schema `CREATE` turns namespace ordering into a security boundary.
4. A configured `search_path` string is not the complete effective lookup path.
5. PostgreSQL 15+ defaults do not prove that an upgraded or customized database is safe.
6. Inspect actual owners, ACLs, effective privileges, and resolved paths before changing production access.
