# Part 4.6 — Table, View, and Column Privileges

**Status:** Revised Final / Canonical Edition
**Target:** PostgreSQL 18
**Audience:** PostgreSQL administrators, DBREs, SREs, platform engineers
**Companion Lab:** `labs/table-column-privilege-check.sql`

---

## 1. Learning Objectives

By the end of this tutorial, you should be able to:

- distinguish table-level and column-level privileges;
- design least-privilege read, write, and referential-access roles;
- explain the additional privileges required by realistic `UPDATE` and `DELETE` statements;
- administer access to tables, views, materialized views, partitioned tables, and foreign tables;
- explain owner, membership, `PUBLIC`, and grant-option effects;
- identify why a column revoke cannot override a table-level grant;
- review view invoker/owner boundaries without exposing view definitions;
- collect effective privilege and ACL evidence without executing application SQL.

---

## 2. Relation Privileges Are Operation-Specific

PostgreSQL table-like relations can carry these privileges:

| Privilege | Primary capability | Operational note |
| --- | --- | --- |
| `SELECT` | Read relation or permitted columns | Also required when existing values are referenced by write statements |
| `INSERT` | Add rows or assign permitted columns | Omitted columns receive defaults or `NULL`, subject to constraints |
| `UPDATE` | Modify rows or permitted columns | Usually also needs `SELECT` on columns used in predicates or expressions |
| `DELETE` | Remove rows | Usually also needs `SELECT` on columns used to choose rows |
| `TRUNCATE` | Remove all rows through `TRUNCATE` | Separate from `DELETE`; high-impact and table-level only |
| `REFERENCES` | Create a foreign key referencing the relation or columns | Can create dependencies and has security implications |
| `TRIGGER` | Create a trigger on the relation | Trigger code executes during later writes and requires separate review |
| `MAINTAIN` | Run supported maintenance operations | Covered fully in Part 4.7 |

Avoid `ALL PRIVILEGES` as a shortcut. It grants every privilege applicable to the object type at that time, which is rarely the same as an application's access contract.

---

## 3. Reading Is Often Required During Writes

An `UPDATE` grant alone does not authorize every update. PostgreSQL checks `SELECT` when a statement reads existing values, including values used in:

- a `WHERE` predicate;
- a computed assignment such as `balance = balance + 10`;
- a `RETURNING` list;
- joins or subqueries used by the statement.

Likewise, a typical conditional `DELETE` needs `SELECT` on columns used to locate rows. Grant the exact read columns required by the approved statement shapes rather than adding blanket table `SELECT` merely to silence permission errors.

Privileges do not bypass constraints, triggers, generated-column rules, view updatability, or row-level security. Authorization is one gate in statement execution, not a guarantee of success.

---

## 4. Column-Level Privileges

PostgreSQL supports column-level `SELECT`, `INSERT`, `UPDATE`, and `REFERENCES`. It does not provide column-level `DELETE`, `TRUNCATE`, `TRIGGER`, or `MAINTAIN`.

Example design intent:

```sql
GRANT SELECT (patient_id, display_name, care_region)
ON clinical.patient_directory
TO clinical_support;
```

This is a security-mutating example, not part of the SAFE-READ lab.

Do not paste tutorial grants into production. Resolve the exact database, schema, relation, role, owner, existing ACL paths, and rollback plan through an approved change before applying any privilege mutation.

A role can use a column if it has the needed privilege either on that column or on the entire table. Therefore this sequence does not hide one column:

```sql
GRANT SELECT ON clinical.patient_directory TO clinical_support;
REVOKE SELECT (sensitive_note)
ON clinical.patient_directory
FROM clinical_support;
```

The table-level `SELECT` remains effective. To build a column allowlist, avoid the broader table grant and grant only the approved columns. Then verify membership and `PUBLIC`, because either can restore table-level access.

Column grants are not a complete data-masking system. Expressions, functions, views, inference paths, joins, and application behavior require separate threat analysis.

---

## 5. `INSERT` and `UPDATE` Column Contracts

Column-level write grants are useful when an application should assign only a defined subset of columns.

For `INSERT`, every explicitly assigned column needs `INSERT`; omitted columns must be satisfiable through defaults, identity behavior, generated expressions, or nullable definitions. Sequence privileges are separate, even when a sequence supplies a table default.

For `UPDATE`, assigned columns need `UPDATE`, while referenced old values need `SELECT`. A role with `UPDATE (status)` and `SELECT (patient_id, status)` can support a narrow status transition pattern without receiving update access to every column.

Privilege checks do not validate business transitions. Use constraints, triggers, views, or application policy where values must follow a state machine.

---

## 6. Views Are Authorization Boundaries, Not Automatic Masks

A caller must have the required privilege on the view itself. By default, access to underlying base relations is checked with the view owner's privileges. This can expose a deliberately restricted projection without granting the caller direct access to the base table.

When a view has `security_invoker=true`, the caller must also hold the relevant privileges on the underlying base relations. Schema lookup has a nuance: the caller needs `USAGE` on the schema containing the view, while base-schema lookup was performed when the view was created or replaced.

Views are not automatically safe row filters. A view intended to provide row-level security may require `security_barrier`, and row-level security policies introduce additional owner/invoker behavior covered in Part 4.11. Functions called by a view retain their own `SECURITY INVOKER` or `SECURITY DEFINER` semantics and require `EXECUTE` as applicable.

Do not confuse a regular view with a `SECURITY DEFINER` function. A normal owner-rights view changes base-relation privilege checks; it does not universally execute every expression as the view owner.

---

## 7. Updatable Views

Some simple views are automatically updatable. A role performing `INSERT`, `UPDATE`, or `DELETE` needs the corresponding privilege on the view. By default, the view owner needs the underlying relation privileges; for a security-invoker view, the caller needs them.

Whether a view is structurally updatable is independent of its ACL. A granted `UPDATE` privilege does not make a grouped, aggregated, or otherwise non-updatable view writable. `CHECK OPTION`, triggers, rules, generated columns, constraints, and row security can further affect the operation.

Grant view write privileges only after reviewing:

- structural updatability;
- owner and `security_invoker` behavior;
- row visibility and `CHECK OPTION`;
- triggers and rewrite rules;
- called functions and their security mode;
- underlying row-level security behavior.

---

## 8. Materialized Views

A materialized view stores query results and supports `SELECT` as a table-like object. Its data is not updated through ordinary `INSERT`, `UPDATE`, or `DELETE` against the materialized view.

Refreshing a materialized view is a maintenance boundary. PostgreSQL 18 `MAINTAIN` and ownership considerations are handled in Part 4.7. A runtime reader normally needs only schema `USAGE` and `SELECT` on the materialized view.

Materialized data can be stale. Authorization evidence does not prove refresh freshness, source consistency, or correct data classification.

---

## 9. Partitioned and Foreign Tables

Partitioned tables require privilege review at the access path applications actually use. Queries through a partitioned parent are checked against the parent, while direct references to individual partitions are separate relation accesses. Inventory parent and child ACLs instead of assuming one grant describes every entry point.

Foreign-table privileges control the PostgreSQL relation boundary. Successful access can additionally depend on the foreign server, user mapping, remote identity, remote privileges, and network path. Catalog evidence in the local database cannot prove remote authorization is safe.

---

## 10. Ownership, `PUBLIC`, Membership, and Grant Options

Effective access can come from direct grants, inherited roles, `PUBLIC`, ownership, or superuser authority. A raw ACL entry is only one part of the explanation.

`WITH GRANT OPTION` permits a recipient to grant that object privilege onward. It cannot be granted to `PUBLIC`. Revoking a grant option can encounter dependent grants and requires deliberate `RESTRICT`/`CASCADE` analysis.

Owners retain implicit grant authority even if their displayed ordinary ACL entries are reduced. Keep runtime roles from owning application relations, and treat unexpected grant options as privileged delegation paths.

New tables and columns receive their creation-time privilege state from built-in and configured defaults. Part 4.8 handles future-object access; a correct grant on today's relations does not cover tomorrow's objects automatically.

---

## 11. Safe Change Workflow

Before changing a table, view, or column ACL:

1. identify the exact application role and relation OID;
2. capture owner, relation kind, schema, raw relation ACL, and explicit column ACLs;
3. test effective access through supported inquiry functions;
4. inventory membership and `PUBLIC` paths;
5. review grant options and dependent grants;
6. map required SQL statement shapes to required columns;
7. include sequences, functions, RLS, views, partitions, and foreign systems as applicable;
8. test allow and deny cases in an isolated environment;
9. define rollout, observation, abort, and rollback criteria;
10. retain a least-privilege reverse plan rather than a blanket grant.

Privilege revocation can break prepared statements, connection pools, background workers, reports, migrations, or infrequent workflows. Observe permission errors and business outcomes after change, and do not use production data for tutorial testing.

## 12. Hands-On Lab — SAFE-READ Relation and Column Audit

Run from the `postgresql/part-04-users-roles-security` directory:

```bash
umask 077
psql --no-psqlrc \
  --dbname=appdb \
  --set=expected_database=appdb \
  --set=expected_session_user=security_auditor \
  --set=application_role=clinical_runtime \
  --set=application_schema=clinical_app \
  --set=target_relation=patient_directory \
  --file=labs/table-column-privilege-check.sql \
  --output=table-column-privilege-check.out
```

The lab:

- hard-gates PostgreSQL 18, database, session identity, role, schema, and target relation;
- reports target ownership, kind, ACL, RLS, and partition signals;
- tests effective relation privileges for the application role and `PUBLIC`;
- expands target relation and explicit column ACL entries;
- produces an effective privilege matrix for every live target column;
- inventories application-role access across table-like relations in the schema;
- reports effective grant options without changing grants;
- reports catalog-only view security and write-path signals without printing view definitions;
- revalidates all execution hard gates before rollback.

The artifact does not execute the target relation, impersonate the application role, enumerate row data, print view definitions, call foreign-data-wrapper updatability hooks, or validate remote foreign-table access. Its catalog-only view signals do not determine whether a view is structurally updatable. Effective privilege results include ownership, membership, `PUBLIC`, and superuser behavior; use the reported role attributes and raw ACL evidence to investigate why a result is true.

Output contains security-sensitive role, owner, object, column, ACL, and authentication-identity metadata. Run with the least-privileged auditor that provides required visibility, store output with restrictive permissions, and sanitize it before sharing.

## 13. Production Review Checklist

- [ ] Required SQL operations and referenced columns are documented.
- [ ] Runtime roles receive no blanket `ALL PRIVILEGES` shortcut.
- [ ] Table-level grants do not defeat intended column restrictions.
- [ ] `PUBLIC` and inherited table-level privileges are reviewed.
- [ ] Grant options are justified and their downstream grants are known.
- [ ] Runtime roles do not own application relations.
- [ ] Conditional writes have the required narrow `SELECT` access.
- [ ] Sequence privileges are reviewed separately.
- [ ] View owner, invoker, barrier, function, and RLS behavior is reviewed.
- [ ] Writable views have explicit `CHECK OPTION` and trigger/rule analysis.
- [ ] Materialized-view refresh authority is separated from read access.
- [ ] Parent and directly addressable partition privileges are reviewed.
- [ ] Foreign server, user mapping, remote ACL, and network controls are reviewed.
- [ ] Existing and future-object privileges are validated separately.
- [ ] Explicit allow and deny tests use synthetic non-production data.
- [ ] Rollout, monitoring, abort, and least-privilege rollback are approved.
- [ ] Audit evidence is protected and sanitized.

---

## 14. Key Takeaways

1. Relation privileges authorize operations; they do not guarantee statement success.
2. A table-level grant satisfies column access and cannot be narrowed by a column revoke.
3. Realistic writes often need both write privileges and narrow read privileges.
4. View ACLs, base-relation checks, functions, RLS, and structural updatability are separate gates.
5. Materialized views, partitions, and foreign tables require object-specific operational review.
6. Effective inquiry functions and raw ACLs should be reviewed together.
