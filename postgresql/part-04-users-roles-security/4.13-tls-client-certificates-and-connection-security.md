# Part 4.13 — TLS, Client Certificates, and Connection Security

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Track:** Part 4 — Users, Roles & Security

## 1. Connection-Security Architecture

PostgreSQL connection security is layered:

```text
network reachability
  ↓
TLS transport
  ↓
server identity verification
  ↓
optional client-certificate identity
  ↓
PostgreSQL authentication
  ↓
CONNECT privilege
  ↓
object privileges / RLS / routines
```

These controls are related but are not interchangeable.

```text
encrypted connection      != verified server identity
verified server identity  != verified client identity
authenticated role        != authorized object access
```

## 2. Server TLS

PostgreSQL can accept TLS connections when server SSL support is enabled and suitable certificate/key material is configured.

`ssl = on` means TLS is available. It does not by itself prove that every client is required to use TLS.

Private keys are secrets. Never place server/client private keys in repositories, screenshots, tickets, logs, tutorial evidence, or acceptance output.

## 3. HBA Transport Policy

Important HBA connection types include:

```text
hostssl    TLS TCP/IP path
hostnossl  non-TLS TCP/IP path
host       TCP/IP path without an inherent TLS requirement
```

HBA remains ordered first-match policy. A later `hostssl` rule does not protect a connection already matched by an earlier applicable rule.

## 4. Client `sslmode`

libpq clients support modes including:

```text
disable
allow
prefer
require
verify-ca
verify-full
```

The security properties differ.

```text
require      → require encrypted TLS
verify-ca    → TLS + validate certificate chain against trusted CA
verify-full  → TLS + CA validation + server-name verification
```

For security-sensitive deployments requiring server identity verification, use an explicit verification policy such as `verify-full` rather than treating encryption alone as identity assurance.

## 5. `sslmode=prefer`

libpq commonly defaults to `sslmode=prefer`: it attempts TLS first but can use a non-TLS connection when TLS cannot be established and the server permits a non-TLS path.

Therefore:

```text
one observed encrypted session
    !=
client configured to require TLS
```

Production connection strings should express the intended security policy explicitly.

## 6. `sslmode=require` Compatibility Nuance

Do not teach `require` as equivalent to hostname verification.

Some libpq configurations involving a root CA can make `require` perform additional certificate validation for compatibility reasons. Do not depend on that side effect. Use `verify-ca` or `verify-full` explicitly when verification is required.

## 7. Root CA Trust and `sslrootcert=system`

Clients performing certificate verification require an appropriate trust source. PostgreSQL/libpq can use configured CA material, and supported configurations can use the system trust store with:

```text
sslrootcert=system
```

Treat trust-store selection as security policy, not merely connectivity configuration.

## 8. Hostname Verification

`verify-full` verifies the certificate chain and checks the requested server identity.

Operational dependencies can include DNS, certificate SAN/CN identity, load-balancer names, failover endpoints, and connection strings.

A TLS handshake succeeding is not sufficient evidence that a client verified the intended server.

## 9. Client Certificates

TLS can also authenticate client certificate identity:

```text
client private key + certificate
              ↓
TLS handshake
              ↓
certificate validation
              ↓
identity matching / mapping
              ↓
PostgreSQL role
```

Client certificate authentication is distinct from simply encrypting the connection.

## 10. `cert` Authentication vs `clientcert=`

PostgreSQL supports certificate-oriented HBA designs such as:

```text
hostssl ... cert
```

and certificate validation combined with another authentication method through `clientcert=` options.

`cert` authentication inherently uses client-certificate validation. Avoid redundant examples that imply an additional `clientcert=` option is required merely to make `cert` validate the certificate.

When certificate validation is combined with another authentication method, options such as `clientcert=verify-ca` or `clientcert=verify-full` can impose certificate requirements.

## 11. `clientname=CN|DN`

Certificate identity matching can use:

```text
clientname=CN
clientname=DN
```

`CN` is the normal/default certificate-name basis; `DN` enables full distinguished-name matching where appropriate.

Certificate identities can also participate in username maps. Treat certificate-to-role mappings as security-sensitive authorization-adjacent configuration.

## 12. Server-Side CA Configuration

Server-side `ssl_ca_file` is relevant when PostgreSQL validates client certificates. Do not confuse this with the client's trust configuration used to verify the PostgreSQL server.

Keep these trust directions explicit:

```text
client trust store → verifies server certificate
server CA config   → verifies client certificate
```

## 13. Certificate Revocation

PostgreSQL supports certificate revocation configuration through settings including:

```text
ssl_crl_file
ssl_crl_dir
```

Revocation configuration belongs to certificate lifecycle management. Changes can cause previously accepted client certificates to stop authenticating and therefore require controlled testing and rollback.

## 14. Certificate Lifecycle

Production PKI design must account for issuance, trust hierarchy, expiration, renewal, rotation, revocation, key protection, deployment, overlap, monitoring, and rollback.

A TLS deployment without an operational renewal plan is incomplete.

## 15. TLS Protocol and Cipher Policy

PostgreSQL exposes TLS policy settings such as:

```text
ssl_min_protocol_version
ssl_max_protocol_version
ssl_ciphers
ssl_tls13_ciphers
ssl_groups
```

PostgreSQL 18 provides `ssl_tls13_ciphers` for TLS 1.3 cipher-suite configuration and uses `ssl_groups` as the current terminology for the setting historically named `ssl_ecdh_curve`.

Do not prescribe one universal cipher configuration. Client compatibility, PostgreSQL/OpenSSL versions, operating systems, compliance policy, and managed-service controls differ.

## 16. Runtime TLS Evidence — `pg_stat_ssl`

`pg_stat_ssl` provides runtime SSL information for backend/WAL-sender processes, including evidence such as:

```text
ssl
version
cipher
bits
client_dn
client_serial
issuer_dn
```

It can be correlated with backend information using PID.

This evidence is valuable but bounded:

```text
current session uses TLS
    !=
every connection must use TLS

current session uses TLS
    !=
client verified server identity
```

Certificate DN, serial, issuer, role, address, and related evidence can be security-sensitive.

## 17. Configuration vs Runtime vs Client Policy

Always separate:

```text
server configuration
HBA transport/authentication policy
runtime session evidence
client verification policy
external proxy/load-balancer TLS
```

No single layer proves the others.

## 18. SCRAM Channel Binding

Where supported by the client and architecture, SCRAM channel binding can bind authentication to the TLS channel.

A client policy such as:

```text
channel_binding=require
```

can provide stronger protection against certain server-spoofing scenarios.

Before requiring it, validate driver/library support across applications, administrative tools, pools, automation, and recovery paths.

## 19. `sslinfo`

The optional `sslinfo` extension can expose additional information about the current SSL connection.

The canonical acceptance artifact does not require it because built-in `pg_stat_ssl` provides sufficient generic runtime evidence and avoiding an extension dependency keeps the lab broadly usable.

## 20. Proxies and Load Balancers

TLS may terminate or restart at infrastructure boundaries:

```text
client ──TLS?──> proxy/LB ──TLS?──> PostgreSQL
```

PostgreSQL can directly report only the connection hop it observes.

Therefore:

```text
PostgreSQL reports TLS
    !=
proof of end-to-end client-to-database TLS
```

Review every transport boundary independently.

## 21. Managed PostgreSQL Services

Managed platforms may own server certificates, certificate rotation, endpoints, protocol controls, and TLS enforcement mechanisms.

Do not assume filesystem-level certificate administration or self-managed reload procedures apply to RDS/Aurora PostgreSQL, Azure Database for PostgreSQL, Cloud SQL, or other managed services.

## 22. Production Investigation Workflow

1. Record execution identity.
2. Inspect TLS-related PostgreSQL settings.
3. Inspect the current session's `pg_stat_ssl` evidence.
4. Review aggregate runtime evidence only where appropriate.
5. Correlate HBA `hostssl`/`hostnossl` policy.
6. Review `cert`, `clientcert=`, `clientname=`, and identity mappings.
7. Review client `sslmode`, CA trust, hostname verification, and channel binding separately.
8. Identify proxy/load-balancer TLS boundaries.
9. Review certificate expiration, rotation, revocation, and monitoring.
10. Inventory applications, pools, replication, backups, monitoring, ETL, automation, and administrative clients.
11. Validate expected secure connections and controlled expected-deny cases.
12. Preserve an independently tested recovery path.

## 23. Production Change Gate

Use a controlled sequence:

```text
capture known-good configuration
        ↓
inventory clients and dependencies
        ↓
validate certificates and trust
        ↓
validate driver compatibility
        ↓
confirm independent recovery path
        ↓
apply approved change
        ↓
create genuinely new connections
        ↓
test expected allow + expected deny
        ↓
validate applications / pools / replication / backup / monitoring
        ↓
observe
        ↓
retain rollback
```

Existing pooled sessions can hide failures affecting new TLS handshakes.

## 24. Rollback

Rollback must restore a known-good connection-security state. Preserve previous configuration and required certificate/trust material according to organizational secret-handling policy.

Do not reconstruct HBA rules, certificates, or connection parameters from memory during an outage.

## 25. SAFE-READ Acceptance Strategy

The canonical acceptance artifact inspects:

- execution identity,
- TLS configuration metadata,
- PostgreSQL 18 TLS settings,
- current-session SSL state,
- bounded aggregate `pg_stat_ssl` evidence,
- TLS-related HBA rules,
- client-certificate-related HBA options,
- identity-map indicators.

It does not:

- modify TLS settings,
- reload PostgreSQL,
- edit HBA/ident configuration,
- read certificate/private-key contents,
- rotate certificates,
- inspect credentials,
- perform external TLS probes,
- change roles/privileges,
- terminate sessions.

```text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
```

## 26. Evidence Sensitivity

Connection-security evidence can expose internal addresses, database/role names, certificate DNs and issuers, filesystem paths, PKI design, and authentication architecture.

```text
SAFE-READ != safe to publish
```

Protect collected evidence appropriately.

## 27. Key Takeaways

```text
ssl = on                 != TLS mandatory
TLS required             != server identity verified
encrypted session        != authenticated database identity
authenticated identity   != authorized object access
current-session TLS      != every client requires TLS
pg_stat_ssl evidence     != client verification policy
PostgreSQL-hop TLS       != necessarily end-to-end TLS
certificate auth         != ordinary TLS encryption
existing pooled session  != new connections will succeed
SAFE-READ                != safe to publish
```

The production objective is not simply to enable SSL. It is to operate a verifiable, maintainable connection-security architecture with explicit transport, identity, certificate lifecycle, client compatibility, monitoring, recovery, and rollback controls.
