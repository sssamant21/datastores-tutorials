# Part 4.1 — PostgreSQL Security Model Fundamentals

**Status:** Revised Final / Canonical Edition
**Target:** PostgreSQL 18
**Audience:** PostgreSQL administrators, DBREs, SREs, platform engineers
**Companion Lab:** `labs/security-model-check.sql`

---

## 1. Learning Objectives

By the end of this tutorial, you should be able to:

- distinguish authentication from authorization;
- explain PostgreSQL roles, login roles, group roles, and `PUBLIC`;
- distinguish `session_user`, `current_user`, and `current_role`;
- describe how ownership, ACLs, membership, and role attributes affect access;
- recognize superuser, `BYPASSRLS`, and predefined-role risk;
- interpret `NULL` ACL values correctly;
- inventory security metadata without changing database state;
- identify questions that require deeper role, privilege, RLS, or authentication review.

---

## 2. The Security Model in One Sentence

PostgreSQL accepts a connection through **authentication**, establishes a role identity, and then uses **authorization** rules—role attributes, membership, ownership, object privileges, row-security policies, and execution context—to decide what that session may do.

These layers answer different questions:

| Layer | Primary question |
| --- | --- |
| Authentication | Is this client allowed to connect as the requested role? |
| Role identity | Which role began the session, and which role is currently effective? |
| Authorization | May the effective role perform this operation on this object? |
| Ownership | Who controls the object and its grants? |
| Row-level security | Which rows may an otherwise-authorized command access? |
| External controls | What do the network, operating system, secrets platform, and proxy permit? |

Passing authentication does not imply broad database access. Conversely, a carefully designed ACL cannot compensate for an authentication rule that lets the wrong principal assume a powerful login role.

---

## 3. Roles Are Cluster-Wide Principals

PostgreSQL uses **roles** for both people and groups. There is no separate internal object type for a “user”: a role with `LOGIN` can be used as the initial identity of a connection and is commonly called a user.

Roles exist across the PostgreSQL cluster, not independently inside each database. Object ownership and most object privileges, however, concern objects inside a particular database. A role discovered in one database can therefore exist cluster-wide while owning different objects or holding different privileges in other databases.

Practical consequences include:

- inspect every database relevant to the role;
- do not assume that dropping or renaming a role is a database-local operation;
- distinguish a login role from a non-login group or ownership role;
- do not equate a PostgreSQL role automatically with an operating-system account.

---

## 4. Authentication Is Not Authorization

Authentication selects and verifies the requested initial role. PostgreSQL host-based authentication rules, certificates, passwords, operating-system integration, and external identity systems can participate in that decision.

Authorization happens after identity is established. PostgreSQL then considers the effective role and the requested action. For example, connecting to a database can require both:

1. a matching authentication path; and
2. the database `CONNECT` privilege.

Part 4.12 covers authentication and `pg_hba.conf` in depth. This tutorial deliberately inventories database-visible security state; it does not claim to validate the complete authentication path.

---

## 5. Session Identity and Effective Identity

Three values are essential during an investigation:

```sql
SELECT system_user, session_user, current_user, current_role;
```

- `system_user` reports the authentication method and presented identity when PostgreSQL has one; it can be `NULL`, including for `trust` authentication.
- `session_user` is the session authorization identifier: normally the role used to establish the connection.
- `current_user` is the effective role used for permission checks.
- `current_role` is equivalent to `current_user` in PostgreSQL.

The three role-valued expressions are often identical, but they need not remain so. `SET ROLE`, `SET SESSION AUTHORIZATION`, and execution of a `SECURITY DEFINER` function can change the relevant execution identity. `system_user` serves a different purpose: it describes the identity presented during authentication, not the effective SQL role. A security report that records only the login name may therefore miss the identity used for an operation.

When troubleshooting access, capture both the session and effective identities before changing role state.

---

## 6. Role Attributes Are Exceptional Capabilities

Important role attributes include:

| Attribute | Security meaning |
| --- | --- |
| `LOGIN` | May be used as the initial role for a connection |
| `SUPERUSER` | Bypasses nearly all permission checks; login itself still requires authentication |
| `CREATEDB` | May create databases |
| `CREATEROLE` | May create roles and administer roles within PostgreSQL's delegation rules |
| `REPLICATION` | May initiate replication when the remaining requirements are met |
| `BYPASSRLS` | Bypasses all row-level security policies |
| `CONNECTION LIMIT` | Limits concurrent connections for the role; `-1` means no role-specific limit |

These attributes are not ordinary object privileges. Membership inheritance does not make special attributes such as `SUPERUSER`, `CREATEDB`, or `CREATEROLE` active in the same way that an inherited table privilege becomes available. A session must become the role that holds the attribute where PostgreSQL permits that behavior.

Treat any powerful attribute as a review signal, not proof of misuse. Production design should minimize standing privilege and make administration paths explicit and auditable.

---

## 7. Membership Has Three Independent Options

A role can be a member of another role. PostgreSQL 18 records three options on each membership edge:

- `INHERIT`: whether the member automatically receives inheritable privileges through that edge;
- `SET`: whether the member may use `SET ROLE` through that edge;
- `ADMIN`: whether the member may grant or revoke membership in the target role under the applicable rules.

Do not reduce a membership review to “role A belongs to role B.” Two edges between similarly named roles can have materially different security behavior.

The role-level `INHERIT` attribute supplies the default for new membership grants; the membership edge's `inherit_option` records the actual choice. Membership chains can be indirect, and a false option can stop the corresponding path. PostgreSQL prevents circular membership loops.

Part 4.3 develops membership and `SET ROLE` in detail.

---

## 8. Ownership Is Authority, Not Just Metadata

Every securable database object has an owner. Ownership normally belongs to the role that created the object, although it can later be transferred.

The owner has inherent authority to alter or drop the object. The owner is also treated as holding all grant options and can re-grant ordinary privileges even after revoking an ordinary privilege from itself. These owner powers are not fully represented as ordinary ACL entries.

This produces an important audit rule:

> An ACL inventory without an ownership inventory is incomplete.

For production systems, consider separating:

- login roles used by people or workloads;
- group roles that collect privileges;
- owner roles used by controlled deployment paths;
- administrative break-glass roles.

Part 4.4 covers ownership and deployment/runtime separation.

## 9. ACLs and Object Privileges

Access control lists (ACLs) record grants on securable objects. Applicable privileges depend on object type. Examples include:

- database: `CONNECT`, `CREATE`, `TEMPORARY`;
- schema: `USAGE`, `CREATE`;
- table: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, `TRIGGER`, `MAINTAIN`;
- sequence: `USAGE`, `SELECT`, `UPDATE`;
- function or procedure: `EXECUTE`.

Privileges can arrive through several paths:

1. a direct grant to the effective role;
2. an inherited membership;
3. a grant to `PUBLIC`;
4. ownership;
5. superuser authority;
6. execution inside a security-sensitive routine or other delegated mechanism.

Seeing no direct grant is therefore not enough to conclude that access is absent.

### `NULL` does not mean “no privileges”

Catalog ACL columns such as `relacl`, `nspacl`, and `datacl` can be `NULL`. A `NULL` ACL means that explicit ACL state has not replaced the object's built-in default privileges. It does **not** mean that nobody has privileges.

For example, built-in defaults grant some privileges to `PUBLIC` on databases, routines, types, and languages. Always interpret ACL data using the rules for that object type and consider `ALTER DEFAULT PRIVILEGES` for subsequently created objects.

---

## 10. `PUBLIC` Is Every Role

`PUBLIC` is a special grantee representing every role, including roles created later. It is not a normal role row, cannot own objects, and cannot receive role membership.

A grant to `PUBLIC` is sometimes intentional—for example, the built-in ability to execute newly created routines unless that default is changed. But it expands the access path beyond named principals, so it should be visible in security reviews.

Revoking a `PUBLIC` grant does not remove access obtained through ownership, direct grants, memberships, or superuser authority.

---

## 11. Predefined Roles and Elevated Paths

PostgreSQL supplies predefined roles whose names generally begin with `pg_`. They can provide monitoring, settings, server-file, signaling, or other capabilities. Their exact definitions can evolve between PostgreSQL releases.

`pg_database_owner` is a special case: its one implicit member is the owner of the current database. Ordinary membership rows do not represent that relationship, so a `pg_auth_members` query alone cannot reveal it.

Do not classify every predefined role as harmless merely because PostgreSQL created it. Review the PostgreSQL 18 documentation for the specific role and inventory both direct and indirect membership.

Also review these boundaries:

- superusers bypass nearly all permission checks;
- roles with `BYPASSRLS` bypass every row-security policy;
- table owners normally bypass RLS unless the table is configured with `FORCE ROW LEVEL SECURITY`;
- `SECURITY DEFINER` routines execute with the function owner's privileges and require hardened design;
- database-visible metadata does not fully describe operating-system, cloud, proxy, or secrets access.

Part 4.10 covers `SECURITY DEFINER`; Part 4.11 covers RLS.

---

## 12. A Practical Effective-Access Model

For an access question, evaluate at least:

```text
authenticated session role
  + effective current role
  + role attributes
  + membership paths and options
  + object ownership
  + direct and PUBLIC ACLs
  + schema and database privileges
  + RLS policy behavior
  + delegated routine execution
  + external controls
```

This is why an effective-access investigation is broader than reading one ACL column. PostgreSQL's `has_*_privilege` functions can answer specific effective-privilege questions, but they should be paired with provenance: *why* does the role have that access?

## 13. Hands-On Lab — SAFE-READ Security Inventory

The companion artifact is intentionally read-only. It validates the PostgreSQL major version and declared session context before inventorying metadata.

Run it from the repository root:

```bash
umask 077
psql --no-psqlrc \
  --dbname=appdb \
  --set=expected_database=appdb \
  --set=expected_session_user=app_runtime \
  --file=labs/security-model-check.sql \
  --output=security-model-check.out
```

Run the lab as the exact login role being assessed. Do not substitute a superuser merely to make the inventory succeed: doing so changes both the identity evidence and effective-privilege results. When a connection pooler is present, use a session path whose backend identity and session state are understood; a pooler's shared service role is not evidence for an end user's direct database identity.

The output contains security-sensitive metadata, including role names, memberships, owners, ACLs, authentication identity, RLS status, and `SECURITY DEFINER` configuration. The `umask 077` example restricts a newly created output file to the invoking account on typical Unix-like systems. Store the evidence only in an approved location, redact it before ticket or chat attachment, apply retention policy, and securely remove it when no longer required.

Although the lab reads catalogs rather than application rows, it is not “zero impact.” Runtime and output volume grow with the number of schemas, relations, routines, ACL entries, and memberships. On unusually large catalogs, first estimate scope, use a lower-traffic window, observe database health, and stop if catalog contention, replica lag, latency, or excessive output appears. Do not run it repeatedly from monitoring automation at a high frequency.

The two expected values are mandatory safety inputs. This first version accepts simple unquoted lowercase PostgreSQL identifiers (`a-z`, digits, and underscores, beginning with a letter or underscore). If your naming policy uses quoted, mixed-case, dotted, or email-style role names, adapt the input-validation policy through review rather than weakening it ad hoc.

The lab:

- opens a repeatable-read, read-only transaction;
- verifies PostgreSQL 18;
- verifies the database and original session role;
- reports the presented authentication identity plus session and effective role identities;
- reports role attributes and direct membership edges;
- inventories ownership, raw ACL state, `PUBLIC` exposure, RLS, and `SECURITY DEFINER` signals;
- evaluates a small set of database/schema privileges using built-in inspection functions;
- rolls back and exits nonzero if a hard gate fails.

It does not inspect application table contents, execute arbitrary user-defined functions, change roles, call procedures, or modify configuration.

The report is point-in-time evidence from one database and one session. Role membership is cluster-wide, but relation, routine, schema, ACL, and RLS results are limited to the connected database and the query scope. Empty output never proves that a control exists elsewhere or that the whole cluster is secure.

### Exercise 1 — Identity

Compare `session_user` with `current_user`. If they differ, document the approved mechanism that changed the effective identity.

### Exercise 2 — Capability

Review the session role's attributes and direct memberships. For every powerful attribute or predefined role, identify its owner, purpose, approval path, and monitoring control.

### Exercise 3 — Ownership and ACLs

Select one non-system schema. Record its owner, raw ACL state, effective `USAGE` and `CREATE` results, and any `PUBLIC` grants. Explain every path that contributes to access.

### Exercise 4 — Policy Signals

Review the RLS and `SECURITY DEFINER` inventories. Empty output means those features were not found in the inspected scope; it does not certify the complete cluster or external environment.

## 14. Production Review Checklist

- [ ] Authentication and authorization are documented separately.
- [ ] Human, workload, group, and owner roles have distinct purposes.
- [ ] Session and effective identities are captured in investigations.
- [ ] Superuser, `CREATEROLE`, replication, and `BYPASSRLS` access is minimized.
- [ ] Membership reviews include `ADMIN`, `INHERIT`, and `SET` options.
- [ ] Ownership is inventoried together with ACLs.
- [ ] `NULL` ACLs are interpreted as defaults, not absence of access.
- [ ] `PUBLIC` grants are explicitly reviewed.
- [ ] Predefined-role memberships are evaluated against PostgreSQL 18 behavior.
- [ ] RLS and `SECURITY DEFINER` paths receive dedicated review.
- [ ] Every relevant database is included in the review scope.
- [ ] External authentication, network, operating-system, and secrets controls are reviewed separately.
- [ ] The lab runs as the intended login role, not an unnecessary superuser.
- [ ] Output is access-restricted, redacted before sharing, and retained only as required.
- [ ] Catalog size and operational timing are appropriate for the environment.

---

## 15. Key Takeaways

1. Authentication proves or accepts an initial identity; authorization decides what it can do.
2. PostgreSQL roles are cluster-wide, while object ownership and most ACLs are database-specific.
3. `session_user` and `current_user` answer different security questions.
4. Effective access can arise through ownership, direct grants, membership, `PUBLIC`, elevated attributes, RLS behavior, and delegated execution.
5. `NULL` ACL does not mean no privileges.
6. A catalog inventory is evidence for review, not an automatic security certification.
