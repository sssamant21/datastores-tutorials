# Part 4.4 — Ownership and Deployment/Runtime Role Separation

**Status:** Revised Final / Canonical Edition
**Target:** PostgreSQL 18
**Audience:** PostgreSQL administrators, DBREs, SREs, platform engineers
**Companion Lab:** `labs/ownership-boundary-check.sql`

---

## 1. Learning Objectives

By the end of this tutorial, you should be able to:

- distinguish ownership from ordinary object privileges;
- separate owner, deployment, runtime, read-only, and administrative identities;
- explain why application login roles should not own application objects;
- design a controlled `SET ROLE` path for deployment;
- inspect ownership across schemas, relations, routines, and types;
- identify runtime-owned objects and privileged routines as review signals;
- plan ownership reassignment and role retirement safely;
- validate an ownership boundary without changing database state.

---

## 2. Ownership Is Authority, Not Just an ACL

PostgreSQL assigns an owner when an object is created. The owner is normally the role that executed the creation statement.

Ownership carries authority that is not represented as an ordinary grantable privilege. The owner can generally alter or drop the object and is treated as holding all grant options for it. Revoking ordinary privileges from the owner does not remove the owner's ability to grant them again.

Consequently, this is not a safe production design:

```text
application login = table owner = migration identity
```

Compromise of the runtime credential would expose both data-plane access and schema-changing owner authority.

---

## 3. Recommended Separation

| Role category | Login | Intended authority |
| --- | --- | --- |
| Owner role | Usually `NOLOGIN` | Owns schemas and application objects |
| Deployment role | Controlled login or federated identity | Can deliberately become the owner during reviewed deployment |
| Runtime role | `LOGIN` | Uses only required object privileges |
| Read-only role | Usually `NOLOGIN` access bundle | Carries approved read privileges |
| Administrative role | Controlled separately | Performs database administration, not normal application work |

Example names:

```text
clinical_owner
clinical_deployer
clinical_runtime
clinical_readonly
```

Names do not enforce boundaries. Role attributes, memberships, ownership, object privileges, schema privileges, default privileges, and authentication controls must implement the design.

---

## 4. Owner Role

A dedicated owner role should normally:

- be `NOLOGIN`;
- have no routine application credential;
- own the application schema and durable application objects;
- avoid unnecessary powerful attributes;
- be reachable only through approved deployment and recovery paths;
- not be used as the ordinary connection identity.

A non-login role can still be reached through `SET ROLE` when membership permits it. `NOLOGIN` prevents direct initial login; it does not neutralize membership or ownership authority.

---

## 5. Deployment Role

The deployment identity needs a deliberate path to create and alter objects under the owner role. A common lab-only pattern is:

```sql
GRANT clinical_owner TO clinical_deployer
    WITH INHERIT FALSE, SET TRUE, ADMIN FALSE;
```

The deployer connects as itself and explicitly executes:

```sql
SET ROLE clinical_owner;
```

Objects created in that execution context are owned by `clinical_owner`, not by the personal or automation login.

The deployment role should not remain active in routine application traffic. Protect its credential or federation path, constrain where it can connect from, monitor its use, and ensure migrations restore the original role state.

These statements mutate security state and belong only in an isolated lab or approved change.

---

## 6. Runtime Role

The runtime login should receive only the privileges the workload needs, usually through one or more non-login access roles.

It should not:

- own application schemas, tables, sequences, routines, or types;
- hold a `SET TRUE` path to the owner;
- hold `CREATE` on an application schema unless runtime object creation is an explicit design;
- receive `CREATEROLE`, `CREATEDB`, `BYPASSRLS`, replication, or superuser authority;
- be able to replace owner-controlled routines or alter security boundaries.

Runtime ownership is a high-priority drift signal. It often indicates that a migration ran under the wrong identity or that application code created durable objects unexpectedly.

Temporary objects are a separate session-scoped concern and are not a reason to grant durable application ownership.

---

## 7. Transferring Ownership

For a single object, PostgreSQL provides object-specific `ALTER ... OWNER TO` commands:

```sql
ALTER TABLE clinical.patient OWNER TO clinical_owner;
```

An ordinary role generally must both control the current owner and be able to `SET ROLE` to the new owner. Ownership changes can require strong locks and can affect operational behavior; validate the exact command and object type.

`REASSIGN OWNED` transfers objects owned by one or more roles to a new role:

```sql
REASSIGN OWNED BY old_owner TO clinical_owner;
```

This is database-scoped for objects in the current database, while certain shared objects can also be affected. It does not remove privileges granted to the old role, and it does not change default privileges created with `ALTER DEFAULT PRIVILEGES`. Execute it only from an approved, database-by-database retirement plan.

Before changing ownership, capture an exact object-to-current-owner-to-successor-owner manifest, dependency evidence, expected locks, maintenance timing, validation queries, and the reverse ownership mapping. Test the plan on a representative non-production copy. A broad reassignment is not a substitute for an object-class-specific migration decision.

---

## 8. `DROP OWNED` Is Not a Generic Cleanup Command

`DROP OWNED BY role` drops objects owned by the role in the current database and revokes privileges granted to that role on objects in the current database and shared objects.

It is destructive. Default `RESTRICT` behavior can stop when dependencies exist; `CASCADE` can remove dependent objects owned by other roles.

After commit, objects removed by `DROP OWNED` are not recovered by an ownership reassignment or a reverse grant. Recovery can require restoring schema definitions and data from tested backups or rebuilding objects from version-controlled deployment artifacts. Treat backup validation and restore testing as entry criteria, not post-failure tasks.

Do not combine `REASSIGN OWNED` and `DROP OWNED` mechanically without a reviewed manifest. First identify:

- databases containing owned objects or grants;
- successor owners by object class;
- extensions and extension-owned objects;
- schemas, routines, policies, default privileges, and shared objects;
- dependent applications and maintenance jobs;
- rollback and recovery constraints.

---

## 9. Ownership and Privileges Must Be Reviewed Together

Separating ownership does not automatically grant runtime access. The owner or a controlled grantor must establish:

- database `CONNECT`;
- schema `USAGE`;
- object-specific privileges;
- sequence privileges where required;
- routine `EXECUTE`;
- correct default privileges for future objects.

Conversely, a runtime role can have broad data access without owning objects. This is the intended separation: usable application access without schema-control authority.

Owner authority can also be reachable through membership. Review both catalog owner columns and `pg_has_role(..., 'SET')`/membership evidence.

---

## 10. Privileged Routine Boundary

`SECURITY DEFINER` routines execute with the function owner's privileges. If an application owner owns such a routine, its definition, `search_path`, `EXECUTE` ACL, referenced objects, and replace/alter permissions become part of the ownership boundary.

PostgreSQL grants `EXECUTE` on new functions and procedures to `PUBLIC` by default unless the owner-specific default privileges or an immediate revoke changes that behavior. Treat routine creation and privilege restriction as one reviewed change; when maximum security is required, perform them in the same transaction.

A runtime role should not be able to replace a routine that executes with owner authority. Part 4.10 provides the full hardening workflow; this section inventories owner-associated routines as review signals.

## 11. Hands-On Lab — SAFE-READ Ownership Boundary Audit

Run from the repository root:

```bash
umask 077
psql --no-psqlrc \
  --dbname=appdb \
  --set=expected_database=appdb \
  --set=expected_session_user=security_auditor \
  --set=owner_role=clinical_owner \
  --set=deployment_role=clinical_deployer \
  --set=runtime_role=clinical_runtime \
  --file=labs/ownership-boundary-check.sql \
  --output=ownership-boundary-check.out
```

The lab:

- hard-gates PostgreSQL 18, database, session identity, and all three roles;
- reports role attributes;
- evaluates deployment/runtime membership relationships to the owner;
- inventories current-database ownership counts by role and object class;
- lists runtime-owned durable objects;
- summarizes owner-owned schemas and relations;
- inventories owner-associated `SECURITY DEFINER` routines;
- summarizes shared dependency records;
- reports review signals without changing ownership or privileges;
- runs in a repeatable-read, read-only transaction and rolls back.

The output is point-in-time security evidence. It is not authorization to run `ALTER ... OWNER`, `REASSIGN OWNED`, `DROP OWNED`, or membership changes.

Run the audit with the least-privileged inspection identity that still provides the required catalog visibility. Schedule it conservatively on clusters with unusually large catalogs, protect the output with restrictive permissions and approved retention, and redact role, object, grantor, and authentication-identity details before sharing outside the authorized review group. The lab intentionally prints neither routine bodies nor raw routine-configuration values.

Catalog inventories have limits. The lab focuses its user-object listing on schemas, independently ownable relation kinds, routines, and explicit types; it suppresses generated array types, table row types, indexes, and TOAST relations to reduce duplicate signals. Extension-managed objects, temporary objects, large objects, publications, subscriptions, foreign objects, database-level objects, and platform integrations can require separate review. Repeat ownership and dependency inspection in every relevant database.

Managed PostgreSQL services can separate PostgreSQL roles from cloud IAM, federation, proxy, secret-manager, and platform-administrator controls. Catalog evidence does not prove those external paths are safe or absent. Include provider control-plane policy and connection-path review in the production decision.

## 12. Production Review Checklist

- [ ] Owner, deployment, runtime, and read-only responsibilities are documented.
- [ ] The owner is `NOLOGIN` unless an exception is approved.
- [ ] Runtime identities own no durable application objects.
- [ ] Runtime identities cannot `SET ROLE` to the owner.
- [ ] Deployment access to the owner is explicit, controlled, and monitored.
- [ ] Personal roles do not own application objects.
- [ ] Schema `CREATE` is restricted.
- [ ] Runtime access is supplied through reviewed privileges.
- [ ] Future-object access is covered by owner-specific default privileges.
- [ ] `SECURITY DEFINER` routines receive separate hardening review.
- [ ] Ownership is inventoried in every relevant database.
- [ ] Shared objects and dependencies are included in retirement planning.
- [ ] `REASSIGN OWNED` and `DROP OWNED` have reviewed manifests and rollback plans.
- [ ] Required backups and version-controlled deployment artifacts have been restore-tested.
- [ ] Expected locks, workload impact, maintenance timing, and stop conditions are approved.
- [ ] `CASCADE` is not used without proven dependency impact.
- [ ] Cloud IAM, federation, proxy, and platform-administrator paths are reviewed separately.
- [ ] Evidence files are protected and sanitized before sharing.

---

## 13. Key Takeaways

1. Ownership grants alter/drop and grant authority that ordinary ACL revocation cannot remove.
2. Non-login owner roles prevent routine direct authentication but remain reachable through membership.
3. Deployment identities may need controlled `SET ROLE`; runtime identities normally must not have it.
4. Runtime-owned durable objects are production drift.
5. Ownership transfer and cleanup are database-by-database change workflows.
6. Ownership, membership, schema privileges, object ACLs, and default privileges must be reviewed together.
