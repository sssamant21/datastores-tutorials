# Part 4.3 — Role Membership, Inheritance, and `SET ROLE`

**Status:** Revised Final / Canonical Edition
**Target:** PostgreSQL 18
**Audience:** PostgreSQL administrators, DBREs, SREs, platform engineers
**Companion Lab:** `labs/role-membership-check.sql`

---

## 1. Learning Objectives

By the end of this tutorial, you should be able to:

- model access with login roles and non-login group roles;
- distinguish role membership from object privileges and ownership;
- interpret PostgreSQL 18 `ADMIN`, `INHERIT`, and `SET` membership options;
- trace direct and indirect membership paths;
- explain why role-level `INHERIT` is only a default for new membership grants;
- use `SET ROLE`, `SET ROLE NONE`, and `RESET ROLE` deliberately;
- identify dangerous ownership and delegation combinations;
- inspect membership reachability without changing session identity;
- design explicit allow-and-deny validation for role hierarchies.

---

## 2. Membership Is an Access Path

PostgreSQL uses roles for login identities, groups, object owners, deployment identities, and administrative capabilities. A role membership is a directed relationship:

```text
member role  --membership options-->  granted role
```

For example:

```sql
GRANT app_readwrite TO app_runtime;
```

`app_runtime` is the member; `app_readwrite` is the granted role. The membership can provide:

- automatic use of the granted role's ordinary privileges through `INHERIT`;
- permission to become the granted role through `SET ROLE`;
- authority to grant or revoke membership in the granted role through `ADMIN`.

These are separate controls. A membership row is not equivalent to an object ACL, and it does not automatically make every privilege reachable in every way.

Role memberships are cluster-wide. Object privileges and ownership usually belong to objects inside individual databases, so a cluster-wide membership change can alter access across multiple databases.

---

## 3. A Production-Oriented Role Model

A common application pattern separates identity, access, and ownership:

| Role | Login | Purpose |
| --- | --- | --- |
| `app_runtime_login` | Yes | Authenticates the workload |
| `app_readwrite` | No | Carries runtime object privileges |
| `app_readonly` | No | Carries read-only privileges |
| `app_owner` | Usually no | Owns application objects |
| `app_deployer` | Login or federated | Performs reviewed deployments |

Example lab-only memberships:

```sql
GRANT app_readwrite TO app_runtime_login
    WITH INHERIT TRUE, SET FALSE;

GRANT app_owner TO app_deployer
    WITH INHERIT FALSE, SET TRUE;
```

The first relationship lets the workload use runtime privileges automatically but prevents it from becoming `app_readwrite`. The second keeps owner authority inactive until the deployer explicitly uses `SET ROLE app_owner`.

These commands mutate security state. Use synthetic roles in an isolated lab or execute them through an approved production change.

## 4. PostgreSQL 18 Membership Options

### `ADMIN`

`ADMIN TRUE` allows the member to grant membership in the granted role to other roles and revoke such membership. It defaults to `FALSE`.

`ADMIN` is delegation authority, not automatic use of the granted role's object privileges. A role is not considered to hold `ADMIN OPTION` on itself. Superusers can administer any membership.

Grants made by a non-bootstrap grantor depend on that grantor retaining the required `ADMIN OPTION`. Revoking the supporting option can require dependent memberships to be revoked.

### `INHERIT`

`INHERIT TRUE` makes the granted role's ordinary privileges available automatically. For indirect membership, every edge in the path must have `INHERIT TRUE`; inheritance stops at the first false edge.

When a new membership omits `INHERIT`, PostgreSQL uses the new member role's role-level `INHERIT` attribute as the default. Changing the role attribute later does not rewrite existing membership edges.

### `SET`

`SET TRUE` permits `SET ROLE` to the granted role. It defaults to `TRUE`. For an indirect target, every membership edge in at least one path must have `SET TRUE`.

The options may be changed on an existing membership by granting the same relationship with explicit values. Omitted options retain their existing values.

## 5. Direct and Indirect Membership

PostgreSQL permits roles to be members of other roles:

```text
app_runtime_login → app_readwrite → app_data_access
```

The database rejects circular membership loops, but long or branching graphs can still be difficult to review.

For automatic inheritance:

```text
app_runtime_login --INHERIT TRUE--> app_readwrite
app_readwrite     --INHERIT FALSE-> app_data_access
```

`app_runtime_login` automatically receives `app_readwrite` privileges but not `app_data_access` privileges through that path.

For role switching, the same graph is evaluated independently using `SET`. A role may inherit another role without being allowed to become it, or may be allowed to become it without inheriting its privileges beforehand.

Review the full graph rather than only direct memberships. Multiple paths matter: one blocked path does not prove access is blocked if another path remains fully reachable.

---

## 6. What Is and Is Not Inherited

Ordinary object privileges can flow through `INHERIT TRUE` membership paths. Examples include `SELECT`, `INSERT`, schema `USAGE`, routine `EXECUTE`, and privileges granted through additional roles.

Role attributes such as these are not inherited as ordinary object privileges:

- `LOGIN`;
- `SUPERUSER`;
- `CREATEDB`;
- `CREATEROLE`;
- `REPLICATION`;
- `BYPASSRLS`.

To exercise a granted role's special attribute, the session generally must actually become that role through an authorized `SET ROLE` path. Never treat `INHERIT TRUE` as proof that a member can use every capability shown in `pg_roles`.

Ownership is also distinct. Membership can make owner authority reachable, especially through `SET ROLE`, but ownership is not an ordinary grantable ACL privilege.

---

## 7. `SET ROLE` Semantics

`SET ROLE role_name` changes `current_user`, which PostgreSQL uses for most permission checks. It does not change `session_user`, the original login identity.

```sql
SELECT session_user, current_user, current_role;
SET ROLE app_owner;
SELECT session_user, current_user, current_role;
RESET ROLE;
```

After switching:

- permissions are evaluated as the selected role;
- privileges held only by the original login role are not combined automatically;
- objects created in that state are normally owned by the selected role;
- the set of roles selectable by later `SET ROLE` commands remains based on the session user's authorized paths, not on the most recently selected role.

`SET ROLE NONE` restores the current user to `session_user`. `RESET ROLE` restores the connection-time role setting, which can differ when startup or role/database settings established one.

`SET LOCAL ROLE` lasts only for the current transaction. `SET ROLE` does not apply `ALTER ROLE ... SET` configuration defaults; those are processed at login. PostgreSQL also prohibits `SET ROLE` inside a `SECURITY DEFINER` function.

The companion acceptance lab does not execute `SET ROLE`.

---

## 8. Ownership Makes `SET` Design Critical

PostgreSQL requires the ability to `SET ROLE` to a target owner for operations such as assigning object ownership. That makes `SET TRUE` appropriate for a controlled deployment identity that must create objects under a non-login owner.

However, `INHERIT TRUE, SET FALSE` is not a safe ownership boundary when the granted role owns modifiable SQL objects. A member that inherits powerful privileges over owner-controlled objects may be able to alter an existing routine or another object and create an escalation path.

Practical rules:

- keep runtime access roles from owning SQL objects;
- keep owner roles `NOLOGIN`;
- give deployment identities an explicit, reviewed `SET TRUE` path to the owner;
- avoid giving runtime identities that path;
- separate access bundles from ownership identities;
- validate who can alter owner-controlled routines, schemas, and objects;
- treat membership changes involving owner or administrative roles as privileged changes.

Part 4.4 develops the ownership boundary in depth.

---

## 9. Delegation and Grantor Review

`ADMIN TRUE` can expand who is able to join a privileged role. Review:

- the granted role's direct and indirect capabilities;
- every member holding `ADMIN TRUE`;
- the recorded grantor;
- dependent membership grants;
- whether `CREATEROLE` or superuser authority changes the administration boundary;
- whether automation can grant memberships outside its intended scope.

Do not confuse `ADMIN OPTION` on a role membership with `WITH GRANT OPTION` on an object privilege. They govern different relationships.

Security changes should identify the intended grantor explicitly in evidence. Ambiguous delegation paths complicate revocation, incident response, and audit interpretation.

---

## 10. Revocation and Session Reality

`REVOKE role FROM member` removes a membership edge, but production impact assessment must cover more than the catalog change.

Before revocation:

1. enumerate all direct and indirect paths;
2. identify inherited and `SET ROLE` reachability separately;
3. inspect ownership and object ACLs;
4. identify active sessions and connection pools;
5. test replacement access and rollback;
6. plan application error monitoring.

Catalog revocation changes subsequent PostgreSQL permission checks, but existing sessions still require operational review: a session might already be running work under a selected role, holding locks, or participating in a pool whose application behavior must be validated. Prepared work, cached application behavior, and external authentication controls also require separate handling. Revoking one path does not remove direct object grants, ownership, `PUBLIC` access, superuser behavior, another membership path, or access mediated by a privileged routine.

Use default `RESTRICT` behavior when revoking delegation relationships unless dependent impact has been proven and approved. Do not use `CASCADE` as a convenience.

## 11. Hands-On Lab — SAFE-READ Membership Inspection

The companion lab examines one target role without granting, revoking, or switching roles.

Run from the repository root:

```bash
umask 077
psql --no-psqlrc \
  --dbname=appdb \
  --set=expected_database=appdb \
  --set=expected_session_user=security_auditor \
  --set=target_role=app_runtime_login \
  --set=max_path_depth=16 \
  --file=labs/role-membership-check.sql \
  --output=role-membership-check.out
```

The lab:

- hard-gates PostgreSQL 18, database, session identity, and target existence;
- reports direct parent roles and direct members;
- recursively traces all upward membership paths;
- classifies automatic inheritance and `SET ROLE` reachability per path;
- reports direct delegation edges involving the target;
- uses supported `pg_has_role` checks for the current session's relationship to the target;
- flags reachable roles with powerful attributes;
- runs inside a repeatable-read, read-only transaction and rolls back.

The recursive traversal is explicitly bounded by `max_path_depth`, which must be between 1 and 32. The default operational example uses 16. A `deeper_path_possible` result means a role at the configured boundary has another parent membership and the evidence is incomplete beyond that point; investigate the graph through a separately controlled review instead of assuming that no deeper path exists. Depth bounding limits path length, not the number of branches, so schedule the query conservatively on unusually large role graphs and stop if output or catalog workload becomes excessive.

The recursive inventory is a catalog interpretation, not authorization to execute `SET ROLE`, `GRANT`, or `REVOKE`. A superuser can select any role even without a normal all-`SET TRUE` membership path, so the catalog path report and the supported `pg_has_role(..., 'SET')` result must be interpreted together. `pg_has_role` reports database membership semantics, but it does not prove that an application, pooler, external identity provider, or secret distribution path behaves as intended.

Output contains role names, grantors, hierarchy paths, and capability signals. Protect it as security evidence.

## 12. Production Review Checklist

- [ ] Every login, access, owner, deployment, and administrative role has a documented purpose.
- [ ] Each membership specifies the intended `ADMIN`, `INHERIT`, and `SET` behavior.
- [ ] Existing edges were inspected rather than inferred from role-level `INHERIT`.
- [ ] Direct and indirect paths were reviewed.
- [ ] Traversal depth was chosen deliberately and no boundary hit was mistaken for completeness.
- [ ] Alternate paths do not defeat a deny decision.
- [ ] Runtime roles cannot become owner or administrative roles.
- [ ] Roles granted with `INHERIT TRUE, SET FALSE` do not own exploitable SQL objects.
- [ ] `ADMIN TRUE` is limited, monitored, and justified.
- [ ] Grantors and dependent memberships are understood.
- [ ] Powerful attributes are not assumed to flow through inheritance.
- [ ] `session_user` and `current_user` are captured during validation.
- [ ] Both successful and denied `SET ROLE` cases are tested in an isolated validation plan.
- [ ] Revocation considers pools, existing sessions, direct ACLs, ownership, and external controls.
- [ ] Independent administrative recovery access remains available.
- [ ] Evidence output is access-controlled and sanitized before sharing.

---

## 13. Key Takeaways

1. Membership is a directed, cluster-wide access relationship.
2. `ADMIN`, `INHERIT`, and `SET` control different capabilities.
3. PostgreSQL 18 stores inheritance and role-switching behavior on each membership edge.
4. Indirect access requires reviewing every edge and every alternate path.
5. `SET ROLE` changes `current_user`, not the authenticated `session_user`.
6. Powerful role attributes do not flow as ordinary inherited object privileges.
7. Ownership and delegation make membership design a production security boundary.
