# Part 5.6 — WAL Fundamentals for Backup and Recovery

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Track:** Part 5 — Backup, Recovery & Disaster Recovery

## 1. Purpose

Write-Ahead Logging (WAL) is fundamental to PostgreSQL durability, crash recovery, physical replication, physical backup consistency, continuous archiving, and point-in-time recovery.

```text
data change
    ↓
WAL record generated
    ↓
required WAL durability
    ↓
data-page persistence
```

For backup engineering:

```text
base backup exists != required WAL available
```

## 2. WAL Recovery Architecture

```text
                       PostgreSQL workload
                              ↓
                         WAL generation
                              ↓
                           pg_wal
                ┌─────────────┼─────────────┐
                ↓             ↓             ↓
          crash recovery  replication   WAL archive
                                           ↓
                                      PITR / DR
```

WAL is not merely an activity log. It is part of PostgreSQL's recovery architecture.

## 3. WAL Records and Segments

A WAL record represents recovery information for a change. WAL records are stored in WAL segment files.

```text
WAL record  != WAL segment
```

The normal PostgreSQL WAL segment size is 16 MB. Segment size is a cluster initialization property rather than an ordinary runtime tuning parameter.

## 4. `pg_wal`

PostgreSQL normally maintains WAL beneath the cluster data directory in `pg_wal`.

Never treat `pg_wal` as an ordinary log directory.

```text
pg_wal pressure
      ↓
identify cause

NOT

delete files
```

Manual removal can destroy recoverability or make PostgreSQL unusable.

## 5. Log Sequence Numbers

An LSN identifies a byte position in the WAL stream. LSNs can be compared to measure WAL movement.

```text
LSN at T1
    ↓
workload interval
    ↓
LSN at T2
    ↓
pg_wal_lsn_diff(T2,T1)
    ↓
WAL bytes generated
```

An LSN is not a timestamp.

## 6. WAL Generation

WAL generation depends on workload and configuration, including inserts, updates, deletes, index activity, bulk operations, maintenance, checkpoints, and full-page images.

Measure both normal and peak workload periods rather than planning from averages alone.

## 7. Checkpoints

Checkpoints establish recovery boundaries and coordinate persistence of dirty pages. Checkpoints can be triggered by time and WAL-volume-related conditions.

A critical distinction:

```text
max_wal_size != hard maximum size of pg_wal
```

Other requirements can cause PostgreSQL to retain more WAL.

## 8. Full-Page Writes

With full-page writes enabled, the first modification of a page after a checkpoint can require a full-page image in WAL.

```text
more frequent checkpoints
        ↓
more first modifications after checkpoints
        ↓
potentially more full-page images
        ↓
potentially more WAL + I/O
```

Do not disable `full_page_writes` as a WAL-capacity workaround.

## 9. Durability-Sensitive Parameters

Parameters such as `fsync`, `full_page_writes`, and `synchronous_commit` affect durability semantics.

They must not be casually weakened to address WAL growth, storage pressure, or backup performance.

## 10. `wal_buffers`

`wal_buffers` concerns WAL buffering/performance.

```text
wal_buffers → buffering/performance consideration
wal_buffers != WAL-retention solution
```

## 11. Physical Backup Dependency

A physical backup taken while PostgreSQL is changing requires appropriate WAL to produce a recoverable physical state.

```text
base files + required WAL = physical recovery foundation
```

This directly connects Part 5.5 physical backups to the WAL recovery model.

## 12. Continuous WAL Archiving

Continuous archiving preserves completed WAL segments in durable archive storage.

```text
pg_wal
   ↓
archive mechanism
   ↓
protected WAL archive
   ↓
recovery / PITR
```

But:

```text
archive_mode enabled
       !=
archive healthy
       !=
WAL recoverable
```

## 13. Archive Failure

Archive failure creates both capacity and recovery risk.

```text
             archive failure
              /          \
             /            \
      local capacity    recovery
          risk            risk
           ↓               ↓
      pg_wal growth    archive gaps
```

Monitor both PostgreSQL archiver statistics and the external archive destination.

## 14. WAL Retention Sources

WAL may be retained because of:
- crash-recovery/checkpoint requirements;
- `wal_keep_size`;
- replication;
- replication slots;
- archiving requirements;
- backup/recovery activity.

Always determine the retention reason before changing configuration.

## 15. `wal_keep_size`

`wal_keep_size` provides minimum WAL retention assistance for standby operation.

```text
wal_keep_size != maximum pg_wal size
```

PostgreSQL can retain more WAL for other requirements.

## 16. Replication Slots

Replication slots can retain WAL needed by consumers.

```text
consumer stalled
      ↓
slot retains WAL
      ↓
continued WAL generation
      ↓
pg_wal growth
      ↓
storage/availability risk
```

Before changing a slot, identify its consumer, business purpose, state, `restart_lsn`, `wal_status`, and retention exposure.

## 17. `max_slot_wal_keep_size`

A value of `-1` means the configured slot-WAL retention limit is not restricting retained WAL.

```text
max_slot_wal_keep_size = -1
          +
stalled consumer
          +
continued WAL generation
          ↓
potentially very large retention
```

Do not blindly drop a slot to recover disk space.

## 18. PostgreSQL 18 Slot Evidence

Useful `pg_replication_slots` evidence includes:

```text
slot_name
slot_type
active
restart_lsn
wal_status
safe_wal_size
```

These help operators understand retention state and risk.

## 19. WAL Recycling and Removal

PostgreSQL can recycle WAL segment files rather than continually create and remove files. Filesystem file counts alone are therefore insufficient for diagnosing WAL behavior.

Use PostgreSQL statistics, replication/archive state, and storage telemetry together.

## 20. Safe WAL-Rate Measurement

Measure WAL byte movement over a known interval.

```text
WAL rate =
pg_wal_lsn_diff(new_lsn, old_lsn)
÷ elapsed time
```

Capture representative windows for:
- normal workload;
- peak traffic;
- ETL/batch processing;
- bulk ingestion;
- maintenance;
- index operations;
- physical backup windows.

## 21. WAL Capacity Planning

Plan for:

```text
normal WAL rate
+ peak WAL rate
+ archive outage tolerance
+ replica outage tolerance
+ slot retention exposure
+ backup duration
+ checkpoint behavior
+ operational safety margin
```

Average daily WAL alone is insufficient for burst-heavy systems.

## 22. PostgreSQL Monitoring

Important SAFE-READ sources include:
- `pg_stat_wal`;
- `pg_stat_archiver`;
- `pg_stat_checkpointer`;
- `pg_stat_replication`;
- `pg_replication_slots`;
- `pg_settings`;
- current/replay LSN functions.

PostgreSQL 18 `pg_stat_checkpointer` should be interpreted using its PostgreSQL 18 fields, including `num_done`, rather than assuming requested/timed counts equal completed checkpoints.

## 23. WAL Incident Triage

```text
pg_wal growth / disk alert
        ↓
1. Confirm storage headroom
        ↓
2. Measure WAL generation
        ↓
3. Check archive health
        ↓
4. Check replication lag/state
        ↓
5. Check replication slots
        ↓
6. Check checkpoint behavior
        ↓
7. Check backup/recovery activity
        ↓
8. Identify generation/retention cause
        ↓
9. Perform controlled remediation
        ↓
10. Validate recovery posture
```

## 24. Prohibited Shortcuts

```text
DO NOT manually delete pg_wal files
DO NOT use pg_resetwal as disk cleanup
DO NOT blindly drop replication slots
DO NOT disable archive_mode as emergency cleanup
DO NOT disable fsync
DO NOT disable full_page_writes
DO NOT weaken durability casually
DO NOT repeatedly force CHECKPOINT
DO NOT repeatedly force pg_switch_wal()
```

Treat `pg_resetwal` as specialized recovery tooling, not normal operations.

## 25. Managed-Service Boundary

```text
self-managed PostgreSQL
    → PostgreSQL statistics + OS/storage telemetry

managed PostgreSQL
    → PostgreSQL-visible statistics
      + provider metrics
      + provider backup/replication controls
```

Do not assume filesystem access or parameter control exists in managed services.

## 26. Security

WAL can contain representations of changed database data. Protect WAL archives, transport, storage, encryption keys, access controls, retention, and deletion with the same seriousness as other recovery artifacts.

## 27. Recovery Evidence

```text
WAL generated
      ↓
WAL retained
      ↓
WAL archived
      ↓
archive protected
      ↓
required WAL located
      ↓
recovery replay succeeds
      ↓
database validation
      ↓
application validation
      ↓
RPO/RTO measured
```

```text
WAL archived != recovery validated
```

## 29. Acceptance Boundary

The SAFE-READ lab can inspect PostgreSQL metadata and statistics. It cannot prove archive durability, filesystem capacity, PITR completeness, backup completeness, or recovery success.

```text
SAFE-READ != WAL-RECOVERY-VALIDATED
```

## 30. Key Takeaways

```text
WAL is recovery infrastructure
WAL record != WAL segment
LSN != timestamp
base backup != complete without required WAL
archive configured != archive healthy
wal_keep_size != maximum pg_wal size
max_wal_size != maximum pg_wal size
slot protection can become disk risk
pg_wal pressure requires root-cause analysis
WAL archived != recovery validated
SAFE-READ != WAL-RECOVERY-VALIDATED
```
