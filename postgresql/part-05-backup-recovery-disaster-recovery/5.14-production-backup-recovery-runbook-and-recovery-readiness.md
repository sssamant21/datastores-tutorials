# Part 5.14 — Production Backup/Recovery Runbook and Recovery Readiness

**Part:** 5 — Backup, Recovery & Disaster Recovery
**Target:** PostgreSQL 18
**Status:** Revised Final / Canonical Edition
**Acceptance artifact:** `labs/recovery-readiness-check.sql`

## Purpose

Production recovery is a controlled operating process: classify the incident, preserve evidence and recovery assets, select and verify the recovery target, recover into an appropriate isolated target, validate PostgreSQL/data/security/application behavior, measure RPO/RTO, control cutover, preserve fallback, and restore protection.

## Governing Principles

- Backup success does not prove recoverability.
- Replication is not backup; HA failover is not historical recovery.
- Missing/inaccessible/stale required evidence is **UNKNOWN**, not PASS or zero.
- Protect the only known-good backup/WAL/timeline chain.
- Prefer isolated recovery when historical correctness is uncertain.
- Production recovery requires explicit authority.
- Application acceptance is part of recovery acceptance.
- SAFE-READ does not mean PUBLIC-SAFE.

## Recovery Roles

Define Incident Commander, Database Recovery Lead, Infrastructure Lead, Application Lead, Security/Compliance, Service Owner, Communications, and Evidence Owner. Data-loss acceptance belongs to authorized service/business ownership; DBAs/SREs provide technical evidence.

## Incident Classification

Classify availability failure, logical loss, physical corruption, regional/platform disaster, or security compromise before selecting failover, logical restore, physical restore/PITR, or DR activation.

## Recovery Lifecycle

1. Detect and stabilize.
2. Declare and classify.
3. Preserve evidence and recovery assets.
4. Determine recovery objective.
5. Select recovery source.
6. Prepare isolated recovery target.
7. Execute recovery.
8. Validate PostgreSQL.
9. Validate data/security/application.
10. Cut over.
11. Observe and stabilize.
12. Close and improve.

## PostgreSQL Recovery-Target Semantics

For PITR, relevant PostgreSQL concepts can include `recovery_target_time`, `recovery_target_lsn`, `recovery_target_xid`, `recovery_target_name`, `recovery_target = 'immediate'`, `recovery_target_inclusive`, `recovery_target_timeline`, and `recovery_target_action`.

Before execution freeze and independently verify:

```text
target type
target value
timezone/UTC offset for time targets
inclusive/exclusive decision
target timeline
expected target action
evidence source
operator
approver
```

Alert time is not automatically the corruption boundary. A configured target is not necessarily reachable; the required base backup, WAL, and timeline-history chain must exist.

Received WAL is not necessarily replayed WAL. `pg_last_xact_replay_timestamp()` is not a universal real-time lag metric, especially on quiet systems.

## Recovery Source Gate

Require readable recovery artifacts, integrity/structure evidence, required WAL, required timeline history, reachable target, encryption/KMS access, version/extensions, tablespace dependencies, approved target, protected original source, and a fallback source where required.

`pg_verifybackup PASS != restore rehearsal PASS`.

PostgreSQL 18 incremental physical-backup designs must preserve their dependency/reconstruction chain; the newest incremental artifact must not be assumed independently restorable.

## Logical vs Physical Recovery

| Requirement | Logical | Physical/PITR |
|---|---|---|
| Selective object restore | Strong fit | Usually not primary mechanism |
| Whole-cluster physical state | No | Strong fit |
| PITR | No | Yes with required WAL |
| Cross-major migration | Potentially, validate compatibility | Not a general mechanism |
| Roles/global objects | Separate dependency | Cluster-dependent |
| Tablespaces | Mapping/dependency considerations | Physical dependency |
| WAL/timeline dependency | No | Yes |

Individual database dumps do not necessarily include cluster-wide roles/tablespace definitions. Physical backups are subject to PostgreSQL physical-format/version compatibility.

## Isolated Recovery Target and Safety

Validate compute, storage, workspace, binaries, extensions/packages/shared libraries, locale/collation, tablespaces, permissions, network, secrets, KMS, backup access, monitoring, and logging.

Restored production data remains production-sensitive. Fence side-effecting integrations until approved: email, Kafka, webhooks, external APIs, payments, CDC/logical replication, ETL, schedulers, `pg_cron`, and application workers.

## Capacity Gate

Plan for backup size + restore expansion + WAL replay + workspace + rebuild overhead + operational reserve. Validate storage throughput, IOPS, CPU, decompression, WAL replay, network throughput, and application startup. Do not size recovery to consume all available capacity.

## Recovery Execution and Automation

Production state-changing commands come from architecture-specific approved procedures. Automation must stop when a dependency/WAL segment is missing, target is ambiguous, timeline unexpected, KMS/secrets unavailable, capacity insufficient, or validation fails. Never silently try another recovery source.

For each state-changing operation record timestamp, operator, approval, before-state evidence, action, target, expected result, actual result, after-state evidence, and evidence location. Never log plaintext secrets.

## Validation

Validate PostgreSQL version/startup/recovery state, databases, tablespaces, extensions and required software, critical objects/data, deterministic business checks, roles/ownership/grants, logging, monitoring, backup/archive/replication, and jobs.

Application owners validate connectivity, authentication, critical reads, approved writes, business workflows, workers, integrations, schedules, reporting, and monitoring.

If PostgreSQL starts but critical application validation fails, recovery is **NOT ACCEPTED** unless authorized ownership explicitly accepts documented degraded service.

## RPO and RTO

Measure RPO from workload/business evidence where possible, not solely backup frequency, replication lag, or archive timestamps. Record target RPO, observed recovery point, measured/estimated loss, evidence, and MET/NOT MET/UNKNOWN.

Measure end-to-end RTO using defined boundaries such as incident, declaration, decision, recovery start, PostgreSQL startup, DB validation, application validation, and service restoration. Restore duration alone is not necessarily RTO.

## Cutover Gate

Before cutover confirm authoritative target, DB/application/security acceptance, monitoring, renewed backup protection, routing approval, fencing of the old/incorrect target where required, fallback path, service-owner approval, and communications. Prevent dual authoritative writers.

## Stabilization, Fallback, and Cleanup

Observe errors, connections, latency, locks, CPU/memory/storage, WAL, replication, archive health, jobs, and business metrics. Preserve fallback through the defined acceptance window.

Rollback reverses a reversible change; fallback uses another preserved recovery path. PITR cannot generally be treated as simple rollback.

Cleanup of old environments, snapshots, temporary restores, backup/WAL artifacts, temporary IAM/secrets, or fallback infrastructure requires an explicit cleanup gate after acceptance and evidence-preservation requirements.

## Security-Incident Recovery

Coordinate with security response, preserve forensic evidence, establish trusted recovery artifacts and compromise timeline, verify credential/key trust, recover into a trusted isolated environment, rotate compromised access as required, validate security/application state, and reconnect only with approval. A technically valid backup can still contain compromised state.

## Managed Services and Kubernetes

Document provider backup/PITR semantics, retention, destination behavior, encryption/KMS, region/account/control-plane dependencies, quotas, failover semantics, and restore testing. Provider-managed backup is not proof of recoverability.

For Kubernetes distinguish pod/node replacement, PVC recovery, DB failover, backup restore, cluster recreation, and regional DR. Avoid conflicting manual and operator-driven recovery.

## Evidence Interpretation

Configuration evidence is not recoverability evidence: `archive_mode = on` does not prove a complete readable WAL archive. `pg_stat_archiver` and `pg_stat_wal` counters require compatible `stats_reset` baselines for deltas.

For slots, inactive does not mean abandoned. PostgreSQL 18 `max_slot_wal_keep_size = -1` means **UNBOUNDED SLOT WAL RETENTION**, not automatically failure.

## Recovery Readiness Record

Track service/environment/version/architecture; approved RPO/RTO; backup method/repository/retention/PITR coverage; last backup/integrity/restore/application/failover/DR/failback tests; recovery/application/incident owners; IAM/KMS/secrets and alternate infrastructure; exceptions/owners; next rehearsal.

Evidence ages. Material architecture/version changes can require earlier rehearsal.

## Acceptance Boundary

The companion `labs/recovery-readiness-check.sql` is **[TUTORIAL-ACCEPTANCE — SAFE-READ]**. A successful run does not prove backup existence/integrity, restore/PITR, RPO/RTO, DR, application recovery, KMS access, or external recovery infrastructure.

It must never perform backup/restore, promotion, replay control, checkpoints, WAL switches, restore points, slot mutations, retention deletion, routing changes, configuration changes, or application-data mutation.

## Closure

Capture timeline, source/target, actions, validation, observed RPO/RTO, exceptions, data-loss statement, final topology, risks, owners, and due dates. Confirm backups, WAL archive, replication, monitoring, retention, and protected recovery copies are restored. Track emergency IAM/firewall/DNS/storage/manual workarounds to closure.
