# Part 5.14 — Production Backup/Recovery Runbook and Recovery Readiness

**Part:** 5 — Backup, Recovery & Disaster Recovery  
**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Acceptance artifact:** `labs/recovery-readiness-check.sql`

## 1. Purpose

A production recovery capability is more than a successful backup job. It is a controlled operating process that identifies the incident, protects evidence, selects the correct recovery path, validates dependencies, restores into the correct target, proves database and application usability, records RPO/RTO evidence, and preserves a fallback path.

This tutorial turns the technical material from Parts 5.1–5.13 into a production-oriented recovery runbook.

> The companion SQL artifact is **SAFE-READ**. It gathers PostgreSQL-visible readiness evidence. It does not perform backup, restore, PITR, promotion, failover, configuration changes, or destructive cleanup.

## 2. Recovery Operating Principles

1. **Backup success does not prove recoverability.**
2. **Replication is not a substitute for backup.**
3. **HA failover is not the same as historical recovery.**
4. **Do not destroy the only known-good recovery path while responding to an incident.**
5. **Recovery targets must be isolated until authority and correctness are established.**
6. **RPO and RTO must be measured from evidence, not assumed from configuration.**
7. **Missing evidence is UNKNOWN, not PASS and not zero.**
8. **Recovery artifacts and evidence are sensitive operational data.**
9. **Production recovery requires explicit ownership and decision authority.**
10. **Application acceptance is part of recovery acceptance.**

## 3. Recovery Runbook Roles

Define roles before an incident.

| Role | Responsibility |
|---|---|
| Incident Commander | Coordinates incident and decisions |
| Database Recovery Lead | Owns PostgreSQL recovery execution |
| Infrastructure Lead | Compute, storage, network, IAM, KMS |
| Application Lead | Application validation and write control |
| Security/Compliance | Evidence, compromise scope, retention requirements |
| Business/Service Owner | RPO/RTO and data-loss acceptance authority |
| Communications Lead | Stakeholder communication |
| Scribe/Evidence Owner | Timeline, commands, outputs, approvals |

One person can fill multiple roles in a smaller organization, but responsibilities must remain explicit.

## 4. Recovery Classification

Before choosing commands, classify the event.

### 4.1 Availability failure

Examples:

- primary host failure;
- instance failure;
- AZ failure;
- PostgreSQL process failure.

Possible response:

```text
HA failover / switchover
```

### 4.2 Logical data-loss event

Examples:

- accidental DELETE;
- DROP TABLE;
- incorrect application update;
- bad batch processing.

Possible response:

```text
backup restore / PITR / selective logical restore
```

### 4.3 Physical corruption

Examples:

- storage corruption;
- unreadable relation;
- damaged cluster files.

Possible response depends on scope:

```text
standby/failover
backup restore
PITR
object-level recovery
```

### 4.4 Regional/platform disaster

Examples:

- region unavailable;
- account/control-plane outage;
- widespread infrastructure failure.

Possible response:

```text
DR activation
```

### 4.5 Security incident

Examples:

- ransomware;
- stolen administrative credentials;
- malicious data modification;
- backup deletion attempt.

Recovery must coordinate with security response. Do not reconnect recovered systems into a compromised control plane without approval.

## 5. Recovery Decision Tree

```text
Incident detected
      |
      v
Stop uncontrolled change / preserve evidence
      |
      v
Is this primarily an availability failure?
      | yes
      +----> evaluate HA failover path
      |
      no
      v
Is historical data state required?
      | yes
      +----> evaluate logical restore / physical restore / PITR
      |
      no
      v
Is the primary failure domain unavailable or untrusted?
      | yes
      +----> evaluate DR activation
      |
      no
      v
Continue scoped recovery investigation
```

The decision tree supports triage. It does not replace architecture-specific procedures or authorization.

## 6. Recovery Phases

Use a consistent lifecycle:

```text
Phase 0  Detect and stabilize
Phase 1  Declare and classify
Phase 2  Preserve evidence and recovery assets
Phase 3  Determine recovery objective
Phase 4  Select recovery source
Phase 5  Prepare isolated recovery target
Phase 6  Execute recovery
Phase 7  Validate PostgreSQL
Phase 8  Validate data/application
Phase 9  Cut over
Phase 10 Observe and stabilize
Phase 11 Close, preserve evidence, improve
```

## 7. Phase 0 — Detect and Stabilize

Capture:

- incident start/detection time;
- affected service;
- symptoms;
- current database role/topology;
- active writes;
- known destructive event time;
- monitoring evidence;
- relevant WAL/LSN positions where available.

Avoid making irreversible changes before the recovery path is understood.

Potential stabilization actions require incident authority and can include application write controls, traffic isolation, or fencing. They are outside the SAFE-READ lab.

## 8. Phase 1 — Declare and Classify

Record:

```text
Incident ID:
Severity:
Incident Commander:
Database Recovery Lead:
Application Lead:
Recovery class:
Affected environment:
Known/estimated event time:
Approved RPO:
Approved RTO:
```

If RPO/RTO cannot be established, record them as **UNKNOWN** and escalate to the service owner rather than inventing values.

## 9. Phase 2 — Preserve Evidence and Recovery Assets

Protect:

- backup catalogs/manifests;
- logical dumps;
- physical backups;
- WAL archive;
- timeline history;
- monitoring;
- PostgreSQL logs;
- audit logs;
- cloud events;
- relevant configuration;
- recovery commands/output.

Do not delete old backups, WAL, snapshots, replicas, or logs merely to create space without understanding recovery dependencies.

If storage pressure threatens production, use the controlled capacity process from Parts 5.10 and 5.12.

## 10. Phase 3 — Determine the Recovery Objective

For historical recovery, establish the target using the best available evidence.

Potential recovery target:

```text
timestamp
LSN
transaction ID
named restore point
end of available WAL
```

Do not select a recovery time solely from when an alert fired.

The destructive or incorrect event may have occurred earlier.

Correlate:

- application logs;
- audit records;
- transaction evidence;
- database logs;
- business event timestamps.

When uncertainty exists, prefer isolated candidate restores rather than overwriting the current production environment.

## 10A. PostgreSQL Recovery-Target Semantics

For PITR, distinguish the operational target from PostgreSQL recovery settings. Depending
on the recovery design, relevant PostgreSQL concepts include `recovery_target_time`,
`recovery_target_lsn`, `recovery_target_xid`, `recovery_target_name`,
`recovery_target = 'immediate'`, `recovery_target_inclusive`,
`recovery_target_timeline`, and `recovery_target_action`.

Before execution, freeze and independently verify the approved target record:

```text
target type:
target value:
timezone/UTC offset when time-based:
inclusive/exclusive decision:
target timeline:
expected target action:
evidence used:
operator:
approver:
```

Use an unambiguous timestamp with timezone/offset. Alert time is not automatically the
corruption boundary. A configured target is not necessarily reachable: the required
base backup, WAL, and timeline-history chain must exist.

`pg_last_wal_receive_lsn()` and `pg_last_wal_replay_lsn()` represent different states:
received WAL is not necessarily replayed WAL. `pg_last_xact_replay_timestamp()` is the
timestamp of the last replayed transaction commit/abort and must not be treated as a
universal real-time replication-lag metric, especially on quiet systems.

## 11. Phase 4 — Select the Recovery Source

Evaluate candidate recovery sets for:

- creation time;
- backup type;
- PostgreSQL version compatibility;
- integrity verification;
- manifest availability;
- required WAL coverage;
- timeline dependencies;
- encryption/key availability;
- storage accessibility;
- retention state;
- last restore-test evidence.

A backup should not be selected merely because it is the newest.

The newest usable recovery set that satisfies the desired recovery target and operational constraints may be appropriate, but selection requires evidence.

## 11A. Logical vs Physical Recovery Boundary

| Requirement | Logical restore | Physical restore/PITR |
|---|---|---|
| Selective object restore | Strong fit | Usually not primary mechanism |
| Whole-cluster physical state | No | Strong fit |
| PITR | No | Yes, with required WAL |
| Cross-major migration use | Potentially, with compatibility validation | Not a general cross-major mechanism |
| Roles/global objects | Separate dependency | Cluster-dependent |
| Tablespaces | Mapping/dependency considerations | Physical dependency |
| WAL/timeline dependency | No | Yes |

An individual logical database dump does not necessarily contain cluster-wide objects
such as roles and tablespace definitions. Physical backups are tied to PostgreSQL
physical-format/version requirements. PostgreSQL 18 incremental physical backup designs
must preserve and understand the dependency/reconstruction chain; the newest
incremental artifact must not be assumed independently restorable.

`pg_verifybackup` evidence is valuable, but:

```text
pg_verifybackup PASS != restore rehearsal PASS
```

## 12. Recovery Source Gate

Before execution, answer:

```text
[ ] Recovery source identified
[ ] Backup is readable
[ ] Integrity/structure verification available
[ ] Required WAL is available
[ ] Required timeline-history dependencies are available
[ ] Recovery target is reachable from the selected chain
[ ] Encryption keys accessible
[ ] PostgreSQL version/extensions identified
[ ] Tablespace dependencies identified
[ ] Recovery target approved
[ ] Original recovery source protected
[ ] Fallback recovery source identified where required
```

Any unresolved item is an exception, not an implicit PASS.

## 13. Phase 5 — Prepare an Isolated Recovery Target

Prefer an isolated target for restore/PITR validation.

Validate:

- compute capacity;
- storage capacity;
- restore workspace;
- filesystem permissions;
- PostgreSQL binaries;
- extensions;
- locale/collation dependencies;
- tablespaces;
- networking;
- secrets;
- KMS;
- backup access;
- monitoring;
- log destination.

Do not point production applications at the recovery target before acceptance.

## 13A. Recovery-Environment Safety Gate

A restored production dataset remains production-sensitive. Before starting services,
control network access, encryption, audit/logging, secrets, and data-retention behavior.
Fence side-effecting integrations until explicitly approved, including email, Kafka,
webhooks, external APIs, payments, CDC/logical replication, ETL, schedulers, `pg_cron`,
and application workers. A historical restore must not silently republish old events
into current downstream systems.

## 14. Capacity Gate

Estimate:

```text
backup size
+ restore expansion
+ WAL replay requirement
+ temporary workspace
+ indexes/rebuild overhead where relevant
+ operational reserve
```

The restore target must have enough free capacity for the entire operation and stabilization period.

Do not consume the emergency reserve merely because the restore technically fits at the start.

## 15. Phase 6 — Execute Recovery

The exact command path depends on recovery type.

### Logical recovery

Possible tools:

```text
psql
pg_restore
```

### Physical recovery

Possible components:

```text
validated base backup
required WAL
recovery configuration
recovery target
timeline selection
```

### HA recovery

May involve:

```text
fencing
promotion
routing
application reconnect
```

### Managed service recovery

May involve provider-native restore/PITR workflows.

Production commands must come from the architecture-specific runbook and approved change/incident procedure. This tutorial intentionally does not provide a universal destructive recovery command sequence.

## 15A. Recovery Automation Stop Conditions

Automation must stop and escalate when a required backup dependency or WAL segment is
missing, the target is ambiguous, an unexpected timeline is encountered, KMS/secrets
are unavailable, capacity is insufficient, or validation fails. Do not automatically
move to another recovery source without preserving evidence and understanding the
failure.

## 16. Recovery Command Logging

For each state-changing operation record:

```text
timestamp
operator
approval/change/incident reference
command/action
target
before-state evidence
expected result
actual result
after-state evidence
evidence location
```

Do not store plaintext secrets in the command log.

## 16A. Recovery Dependency Validation

Capture PostgreSQL major version, extensions and versions, required extension
binaries/packages/shared libraries, locale/collation dependencies, tablespaces,
permissions, mounts, capacity, and configuration dependencies. An extension catalog
entry alone does not prove that its software exists on a newly built recovery host.
An empty `pg_tablespace_location()` for a built-in tablespace is not itself a missing
dependency.

## 17. Phase 7 — PostgreSQL Validation

After recovery, validate at minimum:

### Server

- PostgreSQL version;
- startup status;
- expected recovery state;
- database inventory;
- tablespaces;
- extensions.

### Data

- critical schemas/tables;
- expected object presence;
- critical row-count baselines where meaningful;
- deterministic business checks;
- sequence/identity considerations;
- recent expected transactions.

### Security

- roles;
- ownership;
- grants;
- authentication behavior;
- required service identities.

### Operational

- logging;
- monitoring;
- backup configuration;
- archive behavior;
- replication architecture;
- scheduled jobs.

Do not treat `SELECT 1;` as recovery acceptance.

## 18. Phase 8 — Application Validation

Application owners should validate:

```text
connectivity
authentication
critical reads
critical writes where approved
business workflow
background workers
queues/integrations
scheduled jobs
reporting
monitoring
```

Write testing should use an approved method and must not accidentally create conflicting authoritative data before cutover.

## 19. RPO Measurement

Measure RPO from workload/business evidence when possible.

Example:

```text
last confirmed required transaction before incident
versus
latest confirmed transaction present after recovery
```

Do not derive business RPO solely from:

- backup interval;
- replication lag;
- WAL archive timestamp;
- recovery target configuration.

Record:

```text
Target RPO:
Observed recovery point:
Measured/estimated data loss:
Evidence:
Status: MET / NOT MET / UNKNOWN
```

## 20. RTO Measurement

Define timestamps such as:

```text
T0 incident begins/detected
T1 incident declared
T2 recovery decision
T3 recovery starts
T4 PostgreSQL starts
T5 database validation passes
T6 application validation passes
T7 service restored
```

RTO should use the organization's defined start/end boundaries.

Database restore duration alone is not necessarily service RTO.

## 20A. Recovery Acceptance Rule

If PostgreSQL starts but critical application validation fails, the recovery state is
**NOT ACCEPTED** unless authorized incident/service ownership explicitly accepts a
documented degraded mode. DBAs/SREs provide technical data-loss evidence; acceptable
business data loss must be decided by the designated service/business authority.

## 21. Phase 9 — Cutover Gate

Before production cutover:

```text
[ ] Correct authoritative recovery target confirmed
[ ] Database validation passed
[ ] Application acceptance passed
[ ] Security validation passed
[ ] Monitoring active
[ ] Backup/recovery protection active
[ ] Routing plan approved
[ ] Former primary/incorrect target fenced where required
[ ] Rollback/fallback path documented
[ ] Business/service owner approval obtained
[ ] Communications prepared
```

Do not cut over simply because PostgreSQL started successfully.

## 22. Phase 10 — Stabilization

After cutover, observe:

- errors;
- connection rates;
- latency;
- locks;
- CPU/memory;
- storage;
- WAL generation;
- replication;
- archive health;
- background jobs;
- application business metrics.

Avoid immediately destroying the pre-cutover environment or recovery artifacts.

Maintain the fallback window defined by the recovery plan.

## 22A. Recovery Cleanup Gate

Do not delete the old environment, temporary restore, snapshots, backup/WAL artifacts,
temporary access, or fallback infrastructure merely because initial validation passed.
Cleanup requires defined ownership/approval after the full acceptance and fallback
window. Preserve forensic evidence when a security investigation requires it.

## 23. Phase 11 — Closure

Capture:

```text
incident timeline
recovery source used
recovery target
commands/actions
validation evidence
observed RPO
observed RTO
exceptions
data-loss statement
final topology
backup status
open risks
owners
due dates
```

Confirm that recovery protection has also been restored: backups are running, required
WAL archiving is healthy, replication is restored where designed, monitoring is active,
and retention/protected recovery copies remain effective. Track temporary emergency
IAM, firewall, DNS, storage, instances, and manual workarounds to closure.

Then conduct a post-incident review.

## 24. Rollback vs Fallback

Recovery often cannot be "rolled back" like a configuration change.

Use precise terminology.

**Rollback** may apply to reversible configuration/routing changes.

**Fallback** means retaining another known recovery path if the selected recovery attempt fails.

Examples:

- preserve original backup;
- preserve pre-recovery snapshots where safe;
- retain old environment while isolated;
- retain alternate candidate restore;
- keep required WAL.

Never destroy fallback merely to simplify cleanup before recovery acceptance.

## 25. Recovery Readiness Before an Incident

A production service should maintain a readiness record containing:

```text
backup method
backup schedule
retention
WAL/PITR coverage
last backup verification
last restore test
last DR test
last failover test
last failback test
approved RPO
approved RTO
recovery owners
backup repository
encryption/KMS dependency
alternate infrastructure
runbook location
known exceptions
```

## 26. Readiness Evidence Freshness

Evidence ages.

A restore test from an obsolete PostgreSQL version or architecture may not represent current readiness.

Track:

```text
evidence date
architecture/version at test time
current architecture/version
material changes since test
next rehearsal due
```

Material changes can trigger an earlier rehearsal.

## 27. Backup Monitoring Is Not Recovery Monitoring

Backup dashboards answer questions such as:

```text
Did the job run?
Did the artifact upload?
Did archiving succeed recently?
```

Recovery readiness asks:

```text
Can we restore?
Can we reach the required recovery point?
Can the application use the restored service?
Can we do it within RTO?
Can authorized operators access every dependency?
```

Monitor both.

## 27A. Managed-Service and DR Control-Plane Dependency

A managed service's automated backups or Multi-AZ capability do not eliminate
control-plane, account, region, IAM, or KMS dependencies. Document how recovery works
if the normal service API/control plane or primary account is unavailable. Evaluate
whether provider backups share administrative deletion permissions or other correlated
failure domains with production.

## 28. Security and Evidence Handling

Recovery evidence may contain:

- database names;
- role names;
- topology;
- IP addresses;
- backup paths;
- bucket/repository identifiers;
- timestamps;
- object names;
- operational commands.

**SAFE-READ does not mean PUBLIC-SAFE.**

Protect evidence according to organizational security requirements.

Never include plaintext passwords, tokens, secret keys, or private encryption material in the runbook evidence.

## 29. Security-Incident Recovery

If compromise is suspected:

1. coordinate with the security incident process;
2. preserve forensic evidence;
3. identify trusted recovery artifacts;
4. verify credential/key trust;
5. recover into an isolated/trusted environment;
6. rotate compromised credentials as required;
7. validate application and security state;
8. reconnect only with approval.

Do not allow normal availability pressure to destroy forensic or recovery evidence. A backup may pass technical integrity checks yet still contain compromised or malicious state; source trust must consider the compromise timeline.

## 30. Managed PostgreSQL

For managed services, document:

- backup/PITR semantics;
- retention limits;
- restore destination behavior;
- snapshot scope;
- encryption/key dependencies;
- cross-region capability;
- failover semantics;
- extension limitations;
- provider quotas;
- recovery API/control-plane dependencies.

Provider-managed backup does not remove the need for restore testing and application acceptance.

## 31. Kubernetes PostgreSQL

Document separately:

```text
operator recovery
pod/node replacement
PVC recovery
database failover
backup restore
cluster recreation
regional DR
```

Know which controller is authoritative during recovery.

Avoid simultaneous manual and operator-driven recovery actions that can conflict.

## 32. Recovery Readiness Acceptance Levels

A useful maturity model:

### Level 0 — Unknown

No trustworthy recovery evidence.

### Level 1 — Backup Observed

Backup jobs appear successful.

### Level 2 — Backup Validated

Artifacts have integrity/structure evidence.

### Level 3 — Restore Tested

Isolated restore has succeeded.

### Level 4 — Application Recovery Tested

Application acceptance has succeeded against recovered data.

### Level 5 — Operational Recovery Rehearsed

End-to-end recovery/DR exercise measured against approved RPO/RTO with documented exceptions.

These levels describe evidence maturity; they are not a universal compliance framework.

## 34. Acceptance Boundary

A successful SQL run does **not** prove:

```text
BACKUP EXISTS
BACKUP IS VALID
RESTORE WORKS
PITR WORKS
RPO IS MET
RTO IS MET
DR IS READY
APPLICATION IS RECOVERED
```

Those conclusions require external artifacts and controlled exercises.

## 34A. Evidence Interpretation Rules

Configuration evidence is not recoverability evidence. For example,
`archive_mode = on` does not prove a complete readable WAL archive. `pg_stat_archiver`
and `pg_stat_wal` counters must be interpreted relative to their `stats_reset`
baselines; deltas across incompatible reset baselines are UNKNOWN. Inaccessible,
missing, or stale required evidence is **UNKNOWN**, never silently zero or PASS.

For replication slots, `inactive` does not mean abandoned. PostgreSQL 18
`max_slot_wal_keep_size = -1` means **UNBOUNDED SLOT WAL RETENTION** and is an
exposure characteristic, not automatically a failure.

## 35. Production Safety

The acceptance artifact must not:

- create/drop databases;
- change configuration;
- force checkpoints;
- switch WAL;
- create restore points;
- promote standbys;
- pause/resume replay;
- create/drop/advance slots;
- execute backup/restore;
- modify backup retention;
- delete WAL/backups;
- change routing;
- modify application data.

## 37. Key Takeaways

1. Recovery is an operating process, not a backup command.
2. Preserve evidence and recovery options before destructive action.
3. Classify the incident before choosing failover, restore, PITR, or DR.
4. Protect the known-good recovery source.
5. Recover into isolation when historical correctness is uncertain.
6. Validate PostgreSQL, data, security, and the application.
7. Measure RPO/RTO from evidence.
8. Maintain a fallback path through acceptance.
9. Treat recovery evidence as sensitive.
10. Rehearse the complete process before an actual disaster.
