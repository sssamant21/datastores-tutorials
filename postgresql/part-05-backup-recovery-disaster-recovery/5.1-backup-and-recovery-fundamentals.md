# Part 5.1 — Backup and Recovery Fundamentals

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Track:** Part 5 — Backup, Recovery & Disaster Recovery

## 1. Purpose

A PostgreSQL backup program is successful only when it can produce an acceptable recovery.

This tutorial establishes the production model used throughout Part 5: identify failure scenarios, define recovery scope and objectives, select appropriate PostgreSQL backup/recovery mechanisms, protect recovery artifacts, collect operational evidence, and rehearse recovery.

The governing principle is:

```text
backup success != recovery success
```

## 2. Learning Objectives

After completing this tutorial, you should be able to:

- distinguish backup, replication, high availability, and disaster recovery;
- distinguish SQL dumps, filesystem-level backup, and continuous-archive/base-backup approaches;
- explain the role of WAL in physical recovery and PITR;
- distinguish RPO from RTO;
- choose backup approaches based on failure and recovery scope;
- identify WAL/archive and replication-slot capacity risks;
- describe an evidence hierarchy for recovery readiness;
- explain why backup verification does not replace restore testing;
- collect safe PostgreSQL evidence without changing recovery state.

## 3. Start with the Failure Model

Do not begin with a command such as `pg_dump` or `pg_basebackup`.

Begin with:

```text
What can fail?
        ↓
What must be recovered?
        ↓
To what point?
        ↓
Within what time?
        ↓
From which independent recovery artifacts?
        ↓
How will recovery be validated?
```

Examples:

| Failure | Recovery question |
|---|---|
| Row deleted | Can historical data be reconstructed? |
| Table dropped | Can the object/data be recovered without unnecessary loss? |
| Database dropped | Can the database be recreated and validated? |
| Cluster lost | Can the PostgreSQL cluster be rebuilt? |
| Storage corrupted | Is an independent trusted recovery copy available? |
| Bad release | Can an acceptable earlier state be recovered? |
| Site/region unavailable | Can service recover in another failure domain? |
| Credential compromise | Are recovery artifacts independently protected? |

## 4. Backup, Replication, HA, and DR

### Backup

A backup preserves information needed to recover database state.

Useful recovery scenarios include accidental deletion, logical corruption, cluster loss, historical recovery, and disaster recovery.

### Replication

Replication transfers database changes to another system.

It can improve availability and recovery options, but unwanted changes can also propagate:

```text
destructive change
      ↓
primary
      ↓
replication
      ↓
replica receives the change
```

Therefore:

```text
replication != independent backup
```

### High Availability

HA primarily addresses service continuity and failover after component failure.

Typical HA questions are:

```text
How is failure detected?
Which instance takes over?
How quickly can traffic resume?
```

### Disaster Recovery

DR addresses recovery after a significant failure domain or destructive event.

HA and DR can complement each other, but:

```text
HA != DR
```

## 5. PostgreSQL Backup Approach Boundaries

PostgreSQL backup architecture includes distinct approaches that must not be blurred together.

### SQL Dumps

Logical tools include:

```text
pg_dump
pg_dumpall
```

`pg_dump` operates on one database. `pg_dumpall` can also capture cluster-wide/global logical objects such as roles and tablespaces.

Logical backups are useful for selective recovery and portability, but large restores can be time-consuming and ownership/dependency handling matters.

### Filesystem-Level Backup

A raw copy of PostgreSQL files has strict consistency requirements.

Do **not** teach or assume:

```text
cp -r $PGDATA /backup
```

against an ordinary running server as a generally valid PostgreSQL backup procedure.

A correctly coordinated filesystem snapshot or another PostgreSQL-supported backup/recovery technique must preserve the required consistency semantics.

### Continuous Archiving and Base Backups

Physical recovery commonly combines a base backup with the WAL needed to recover from that base state.

Conceptually:

```text
base backup
    +
required WAL
    =
recoverable physical state
```

`pg_basebackup` is PostgreSQL's utility for taking a base backup from a running server using the replication protocol.

## 6. WAL and Recovery

Write-Ahead Logging is fundamental to PostgreSQL durability and recovery.

WAL participates in:

```text
crash recovery
physical replication
continuous archiving
point-in-time recovery
```

For PITR, PostgreSQL restores a physical starting point and replays the required WAL toward a selected recovery target.

If required WAL is unavailable, the intended recovery point may become unreachable.

## 7. Continuous WAL Archiving

Continuous archiving preserves completed WAL segments outside ordinary `pg_wal` recycling.

PostgreSQL supports archive mechanisms including:

```text
archive_command
archive_library
```

The implementation must be designed so that successful archival is durable and safe to retry.

Archive failure is operationally important because WAL that cannot be successfully archived can accumulate.

Monitoring therefore needs to cover both:

```text
archive health
WAL storage consumption
```

## 8. Replication Slots and WAL Retention

Replication slots can require PostgreSQL to retain WAL needed by a consumer.

Important evidence includes:

```text
active
restart_lsn
confirmed_flush_lsn
wal_status
safe_wal_size
inactive_since
invalidation_reason
```

An inactive or lagging slot can become a storage-risk signal.

A particularly important configuration boundary is:

```text
max_slot_wal_keep_size = -1
```

which permits slots to retain an unbounded amount of WAL relative to that setting.

The correct response is **not** to automatically drop or advance a slot. First identify its owner, consumer, recovery consequences, and approved remediation.

## 9. Point-in-Time Recovery

PITR conceptually follows:

```text
restore suitable base backup
        ↓
make required WAL available
        ↓
replay WAL
        ↓
reach selected recovery target
        ↓
complete recovery
        ↓
validate PostgreSQL
        ↓
validate application
```

PITR should be rehearsed on isolated infrastructure.

A tutorial must never perform destructive recovery against the production data directory merely to prove that recovery works.

## 10. RPO — Recovery Point Objective

RPO defines the approved data-loss objective.

For example:

```text
RPO = 15 minutes
```

does not simply mean:

```text
run a backup every 15 minutes
```

The recovery architecture must demonstrate that an acceptable recovery point can actually be reached within the approved loss window.

RPO can depend on:

- backup frequency;
- WAL archival;
- artifact availability;
- retention;
- replication/recovery design;
- failure mode;
- recovery testing.

## 11. RTO — Recovery Time Objective

RTO is the targeted recovery duration for a qualifying disruption.

Operational recovery time can include:

```text
detection
+ incident decision
+ infrastructure provisioning
+ credential/recovery access
+ backup retrieval
+ restore
+ WAL replay
+ PostgreSQL validation
+ application validation
+ traffic cutover
```

A benchmark of restore throughput alone is not the full operational RTO.

## 12. Retention Is Not Recoverability

Retention answers how long artifacts remain available.

It does not answer whether they are valid or sufficient.

```text
retained artifact
      !=
validated recovery point
```

Retention planning should account for business requirements, storage capacity, compliance, WAL dependencies, lifecycle controls, security, and recovery-test cadence.

## 13. Backup Security and Independence

Treat recovery artifacts as sensitive production assets:

```text
SQL dumps
base backups
WAL archives
backup manifests
role definitions
configuration evidence
restore logs
recovery reports
```

Apply controls appropriate to the environment, including access restriction, encryption, auditability, lifecycle protection, and independent recovery access.

Never embed plaintext passwords, cloud access keys, tokens, private keys, or similar secrets in tutorial artifacts.

Ask:

```text
Can the same failure destroy production and its backups?
Can compromised application credentials reach backups?
Can one administrator accidentally delete every recovery point?
Does recovery depend on credentials stored only in the failed environment?
Is there an independent recovery path?
```

## 14. Backup Verification

Physical backup manifests and tools such as `pg_verifybackup` can provide valuable integrity evidence.

But verification has a boundary:

```text
artifact verification
        !=
successful PostgreSQL recovery
```

A backup can pass structural/integrity checks while other recovery dependencies or application requirements still prevent successful service restoration.

## 15. Restore Testing

A mature backup program includes isolated restore testing.

A useful recovery rehearsal progresses through:

```text
artifact available
      ↓
integrity evidence passes
      ↓
restore/recovery completes
      ↓
PostgreSQL starts correctly
      ↓
expected databases/objects exist
      ↓
database validation passes
      ↓
application validation passes
      ↓
measured recovery satisfies approved objectives
```

Never overwrite the only known-good recovery artifact during testing.

## 16. Recovery Evidence Hierarchy

Use this hierarchy when evaluating backup/recovery maturity:

```text
Level 1 — Configuration exists
Level 2 — Backup job succeeded
Level 3 — Recovery artifact exists
Level 4 — Artifact integrity validated
Level 5 — Restore/recovery completed
Level 6 — PostgreSQL validation passed
Level 7 — Application validation passed
Level 8 — Measured recovery satisfied approved RPO/RTO
```

Lower levels are useful evidence, but they do not imply the higher levels.

## 17. Monitoring and Operational Evidence

Depending on architecture and permissions, useful PostgreSQL evidence can include:

- PostgreSQL version and recovery state;
- archive configuration;
- archive statistics;
- WAL position;
- replication-slot retention state;
- database sizes;
- tablespace inventory;
- base-backup progress during an active backup;
- backup manifest/verification evidence outside SQL;
- storage and backup-platform evidence.

No single catalog query proves recoverability.

## 18. Managed PostgreSQL Services

Managed services can implement backup, snapshot, retention, PITR, encryption, and recovery through provider-specific control planes.

Keep these layers separate:

```text
PostgreSQL recovery concepts
        +
managed-service implementation
```

Do not assume a self-managed filesystem, archive-command, credential, or recovery procedure maps directly to Amazon RDS/Aurora PostgreSQL, Azure Database for PostgreSQL, Cloud SQL, or another managed platform.

Provider documentation and organizational recovery procedures must be validated separately.

## 19. Production Change Safety

Backup/recovery configuration changes require the same operational discipline as other production changes.

Before a risky change:

```text
capture current state
        ↓
identify recovery dependency
        ↓
assess capacity/security impact
        ↓
define rollback or fallback
        ↓
preserve independent recovery path
        ↓
apply approved change
        ↓
validate
```

Never use these as tutorial shortcuts:

- dropping/advancing replication slots;
- deleting WAL to reclaim space;
- disabling durability controls;
- forcing recovery on production;
- replacing a known-good backup;
- granting superuser merely to make a lab work;
- exposing recovery credentials;
- automatically modifying archive configuration.

## 20. Canonical Hands-On Acceptance Artifact

The canonical companion artifact is:

```text
labs/backup-recovery-fundamentals-check.sql
```

It is labeled:

```text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
```

It collects bounded server-side evidence only.

It does **not**:

- start a backup;
- restore data;
- initiate PITR;
- force a checkpoint;
- create/drop/advance a replication slot;
- delete WAL;
- modify archive configuration;
- change server settings;
- terminate sessions;
- read backup files;
- inspect secrets;
- perform automatic remediation.

## 21. What the Acceptance Artifact Cannot Prove

Its output cannot prove:

```text
that an off-host backup exists
that the backup is complete
that required WAL exists externally
that a manifest has passed verification
that a restore will succeed
that application validation will pass
that RPO is achievable
that RTO is achievable
```

Those claims require evidence from the backup platform and isolated recovery rehearsals.

Therefore:

```text
SAFE-READ != RECOVERY-READY
```

## 22. Recovery Readiness Questions

A production owner should be able to answer:

```text
What failures are we protecting against?
What recovery scope is required?
What are the approved RPO and RTO?
Which logical and/or physical backup mechanisms are used?
Where is required WAL protected?
How long are recovery artifacts retained?
Can archive or slot retention exhaust storage?
Who can access and delete backups?
Is recovery independent from the primary failure domain?
When was the last integrity verification?
When was the last successful restore/PITR rehearsal?
Did PostgreSQL validation pass?
Did application validation pass?
How long did the complete recovery take?
```

## 23. Key Takeaways

```text
backup success != recovery success
replication    != backup
HA             != DR
RPO            != RTO
retention      != recoverability
verification   != restore
restore        != application recovery
documentation  != rehearsal
SAFE-READ      != RECOVERY-READY
```
