# Part 5.4 — Cluster-Wide Logical Backup with `pg_dumpall`

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Track:** Part 5 — Backup, Recovery & Disaster Recovery

## 1. Purpose

`pg_dumpall` provides cluster-wide logical dump capability. Unlike `pg_dump`, which protects one database, `pg_dumpall` can cover all databases and cluster-wide objects such as roles and tablespaces.

```text
all database dumps != complete cluster recovery
```

A production recovery strategy combines database artifacts, global state, external dependencies, secure retention, and tested recovery evidence.

## 2. Scope and Selection Modes

```text
pg_dump
    → one database

pg_dumpall
    → cluster-wide logical SQL dump

pg_dumpall --globals-only
    → global objects

pg_dumpall --roles-only
    → roles

pg_dumpall --tablespaces-only
    → tablespaces
```

Roles and tablespaces are cluster-wide rather than belonging to one application database.

## 3. Internal Execution Model

`pg_dumpall` coordinates cluster dumping and uses `pg_dump` for individual databases. Backup planning therefore includes connectivity and authentication across the databases being processed.

Inventory connectable databases, exclusions, permissions, authentication, network reachability, and provider restrictions before execution.

## 4. Output and Restore Model

`pg_dumpall` produces a SQL script:

```text
pg_dumpall → cluster.sql → psql
```

It is not a custom/directory archive consumed by `pg_restore`.

For controlled restoration, `psql -X` prevents local startup-file customization from unexpectedly influencing the recovery session:

```bash
psql -X -f cluster.sql postgres
```

This is illustrative; a cluster restore is state-changing and belongs in an approved isolated recovery workflow.

## 5. Production Recovery-Set Strategy

A flexible pattern is:

```text
pg_dumpall --globals-only
             +
pg_dump -Fc appdb
             +
pg_dump -Fc reporting
             +
pg_dump -Fc analytics
```

This protects global objects while retaining `pg_restore` flexibility for individual databases.

## 6. Global Objects and Recovery Ordering

Conceptually:

```text
prepare target
    ↓
storage/tablespace prerequisites
    ↓
required roles and memberships
    ↓
database definitions
    ↓
database objects/data
    ↓
ownership and ACL validation
```

Exact ordering depends on the approved recovery design.

## 7. Roles and Sensitive Security Metadata

Roles can own objects, receive grants, and participate in memberships. Recovery planning must identify required roles, login requirements, memberships, owners, and environment-specific privileges.

A cluster/global dump may contain sensitive security and application metadata. Do not place complete dumps in Git, tickets, chat, documentation examples, public logs, or uncontrolled shared storage.

## 8. Tablespaces

Tablespace definitions can reference filesystem locations.

```text
tablespace definition captured
        !=
directory exists
        !=
permissions correct
        !=
capacity sufficient
        !=
destination architecture compatible
```

Recovery to VMs, containers/Kubernetes, managed PostgreSQL, or another cloud may require a different storage model.

## 9. Privilege Planning

```text
backup privilege requirement != restore privilege requirement
```

Faithfully reconstructing roles, databases, ownership, memberships, and tablespaces may require administrative privileges. This does not mean every unattended backup process should permanently run with unrestricted superuser access.

## 10. Database Exclusions

```text
excluded database = outside that artifact's recovery scope
```

Every exclusion should be recorded in the recovery manifest and have an explicit protection decision.

## 11. Cross-Version Recovery

Record the `pg_dumpall` client version, source and target PostgreSQL versions, extensions, collations/locales, and platform/provider constraints.

For cross-major workflows, `--quote-all-identifiers` can reduce reserved-word compatibility problems. A generated SQL script is not proof of portable recovery; test it.

## 12. Statistics and Post-Restore Maintenance

Logical restoration may not reproduce every useful optimizer statistic. Recovery validation should therefore include an explicit decision on post-restore `ANALYZE`.

## 13. Capacity Planning

Plan for:

```text
sum of protected database sizes
source CPU/I/O
network throughput
destination capacity
backup duration
retention copies
restore workspace
restore duration
```

For large clusters, globals plus independently managed per-database archive backups can provide greater operational control.

## 14. Multi-Database Failure Handling

```text
cluster.sql exists != every database successfully protected
```

Record source cluster identity, server/client versions, timestamps, included/excluded databases, options, exit status, artifact size/checksum, destination, protection state, retention identity, and validation outcome.

Failed or incomplete output must not silently replace the last known-good recovery set.

## 15. Restore Error Classification

Cluster SQL replay can encounter expected and unexpected errors.

```text
restore emitted error != automatically unrecoverable
ignored error != automatically harmless
```

Classify and document errors instead of blindly suppressing them.

## 16. Credential Handling

```text
NO password in command line
NO password in URI examples
NO credential in shell history
NO credential in Git
NO credential in backup filename
NO credential in logs/tickets
```

Use approved authentication and secret-management mechanisms.

## 17. Last-Known-Good Protection

```text
new backup started != old backup deletable
new backup completed != old backup deletable
new artifact validated != retention policy satisfied
```

Deletion follows the approved retention lifecycle.

## 18. Isolated Recovery Rehearsal

```text
protected recovery set
       ↓
isolated target
       ↓
restore globals/prerequisites
       ↓
restore databases
       ↓
PostgreSQL validation
       ↓
application validation
       ↓
measure RPO/RTO evidence
```

Never use the production cluster as the routine restore-test environment.

## 19. Complete Recovery-Set Model

```text
PostgreSQL recovery set
├── globals
│   ├── roles
│   ├── memberships
│   └── tablespaces
├── database backups
├── external/provider configuration
├── extensions/software prerequisites
├── protected recovery access
├── recovery procedure
└── restore-test evidence
```

```text
globals + databases != complete service recovery

complete service recovery =
artifacts + dependencies + procedure + tested evidence
```

## 20. Canonical Acceptance Artifact

Companion artifact:

```text
labs/pg-dumpall-readiness-check.sql
```

It is labeled `[TUTORIAL-ACCEPTANCE — SAFE-READ]` and performs metadata inventory only:

```text
NO pg_dumpall
NO pg_dump
NO psql restore
NO CREATE/DROP DATABASE
NO CREATE/ALTER/DROP ROLE
NO role-membership changes
NO tablespace changes
NO ACL/ownership changes
NO authentication-secret inspection
NO filesystem manipulation
NO backup deletion
NO automatic remediation
```

## 21. What SAFE-READ Cannot Prove

It cannot prove client/server compatibility, backup authentication, external tablespace readiness, artifact completeness/integrity, secure retention, successful cluster restore, application recovery, or RPO/RTO achievement.

```text
SAFE-READ != CLUSTER-BACKUP-VALIDATED
```

## 22. Recovery Evidence Hierarchy

```text
backup job succeeded
       ↓
artifact protected
       ↓
artifact integrity checked
       ↓
isolated restore completed
       ↓
PostgreSQL validation passed
       ↓
application validation passed
       ↓
RPO/RTO measured
```

## 23. Key Takeaways

```text
pg_dump = one database
pg_dumpall = cluster-wide logical dump capability
globals-only = global state
pg_dumpall output = SQL/psql workflow
tablespace definition != destination storage readiness
cluster.sql exists != every database protected
backup set != recovery until restore-tested
SAFE-READ != CLUSTER-BACKUP-VALIDATED
```
