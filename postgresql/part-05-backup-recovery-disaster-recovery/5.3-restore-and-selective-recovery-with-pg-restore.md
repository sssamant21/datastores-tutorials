# Part 5.3 — Restore and Selective Recovery with `pg_restore`

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Track:** Part 5 — Backup, Recovery & Disaster Recovery

## 1. Purpose
`pg_restore` restores non-plain archives produced by `pg_dump`. Production recovery requires more than running a command: inspect the archive, verify the target, understand dependencies and destructive options, control resource usage, validate PostgreSQL, validate the application, and preserve fallback.

```text
archive exists != recovery proven
```

## 2. `pg_restore` vs `psql`
```text
custom archive    ─┐
directory archive ├─→ pg_restore
tar archive       ─┘

plain SQL script ───→ psql
```
Archive format is normally detected automatically. Plain SQL is restored with `psql`.

## 3. Inspect Before Restore
Inspect the archive table of contents (TOC):

```bash
pg_restore --list appdb.dump
```

For controlled selection/order:

```bash
pg_restore --list appdb.dump > restore.list
pg_restore --use-list=restore.list --dbname=appdb_restore appdb.dump
```

An edited TOC list is a controlled recovery artifact. Review and retain it with recovery evidence.

## 4. Mandatory Target-Identity Gate
Before any state-changing restore, verify:

```text
archive identity
source context
target host/service
target database
environment
current role
PostgreSQL versions
extensions
roles
tablespaces
capacity
fallback/recovery point
change authorization
```

Never infer the target merely from a shell prompt or terminal tab.

## 5. Full Restore
Representative restore into a prepared database:

```bash
pg_restore --dbname=appdb_restore appdb.dump
```

This example does not replace target preflight, capacity planning, privilege planning, logging, or validation.

## 6. `--create`
A representative create-mode restore is:

```bash
pg_restore --create --dbname=postgres appdb.dump
```

The database supplied with `--dbname` is initially used as the connection database so creation commands can run; the archive's database identity then controls the database created/restored.

Treat this behavior explicitly during change review.

## 7. `--clean` and Destructive Recovery
`--clean` drops objects that will be restored before recreating them.

```text
--clean          = destructive
--create         = database-creation semantics
--clean --create = potentially database-destructive
```

`--if-exists` can reduce expected missing-object errors when used with clean operations, but it does not make a destructive restore safe.

Do not use destructive options until target identity, scope, fallback, and approval are verified.

## 8. Restore Sections
Archive content can be restored by logical sections:

```text
pre-data
data
post-data
```

Conceptually:
- **pre-data** — definitions needed before table data;
- **data** — table/sequence/large-object data;
- **post-data** — indexes, triggers, constraints, and related objects created after data.

Section-only recovery is not automatically application-complete.

## 9. Selective Restore
Examples:

```bash
pg_restore --dbname=appdb_restore --schema=reporting appdb.dump
pg_restore --dbname=appdb_restore --table=orders appdb.dump
```

Selection has dependency boundaries. In particular, table selection does not mean all subsidiary/dependent objects are automatically included.

```text
selected object restored != dependency-complete recovery
```

Validate the resulting object graph and application behavior.

## 10. Large Objects
Large objects require explicit recovery awareness. Selective table recovery cannot be assumed to select only the large objects logically associated with that table.

Inventory and validate large-object requirements separately.

## 11. Ownership and Privileges
Decide before restore:

```text
Do source roles exist?
Should original ownership be preserved?
Should ACLs be restored?
Which recovery/deployment role owns objects?
Does the target security model differ?
```

`--no-owner` and `--no-privileges` can be appropriate for migrations or isolated rehearsals, but security changes must be intentional and validated afterward.

## 12. Error Handling
Without an explicit stop-on-error strategy, restore can continue after SQL errors and report errors later.

For recovery automation define:

```text
error policy
process exit handling
logs/evidence
validation gate
fallback
```

`--exit-on-error` stops after an SQL error.

A successful process exit still does not prove application recovery.

## 13. Single-Transaction Restore
For compatible workflows:

```bash
pg_restore --single-transaction --dbname=appdb_restore appdb.dump
```

This provides all-or-nothing transaction behavior and implies exit-on-error behavior.

But:

```text
--single-transaction + --jobs = not supported
```

One large transaction can also increase transaction duration, lock pressure, WAL/resource pressure, and operational risk.

## 14. Transaction Sizing
PostgreSQL 18 provides transaction-size control for archive restore workflows. This can bound the number of archive objects processed per transaction and can help avoid an unnecessarily enormous single transaction or excessive lock-table consumption.

Choose transaction strategy from workload and recovery requirements; do not mechanically apply one setting to every restore.

## 15. Parallel Restore
Custom and directory archives can use parallel restore:

```bash
pg_restore --dbname=appdb_restore --jobs=4 appdb.dump
```

Parallel restore is not a tar-archive parallel workflow and is not a stdin/pipe workflow.

Plan for increased:

```text
connections
CPU
I/O
WAL generation
lock concurrency
```

Define a target resource budget before increasing workers.

## 16. Extensions and External Dependencies
Before restore, verify:
- target PostgreSQL version;
- extension availability/version compatibility;
- required roles;
- tablespaces;
- collation/locale dependencies;
- target storage;
- external/provider configuration.

A logical archive cannot make unsupported extension software appear on a target.

## 17. Tablespaces
Source objects can reference non-default tablespaces. Never assume source filesystem layout exists on the recovery target.

Decide whether tablespaces will be recreated, mapped, or otherwise handled according to the approved recovery design.

## 18. Security — Archive as Executable Input
A dump archive is not merely passive data. Restoring it can execute SQL/code originating from the source database.

```text
archive retained != archive trusted
```

For untrusted or uncertain material:
1. inspect the TOC;
2. render/review SQL where appropriate;
3. restore only into an isolated environment;
4. validate before promoting any recovered state.

Do not expose archive contents in public logs or tickets.

## 19. Privileged/Enforcement-Bypass Options
Options that disable triggers or alter normal enforcement can have major integrity/security implications.

Do not use them as generic troubleshooting shortcuts. Require explicit justification, appropriate privileges, controlled execution, and post-restore validation.

## 20. Restore Credentials
```text
NO plaintext password in command
NO credential in Git
NO credential in ticket/log
NO unnecessary superuser
```

Use approved credential mechanisms and the minimum privileges compatible with the recovery plan.

## 21. Restore Isolation
Recovery rehearsal belongs on an isolated target:

```text
validated artifact
      ↓
isolated target
      ↓
restore
      ↓
PostgreSQL validation
      ↓
application validation
      ↓
record duration/evidence
```

Do not overwrite production merely to prove a backup can be restored.

## 22. Fallback Rule
Never destroy:
- the only usable current state; or
- the only known-good recovery artifact

before establishing the approved fallback/recovery path.

## 23. Post-Restore Validation
A complete validation plan can include:

```text
expected schemas/objects
data reconciliation
constraints
indexes
sequences/identities
extensions
large objects
ownership/ACLs
application connectivity
functional checks
recovery duration
```

Define these checks before the incident.

## 24. PostgreSQL 18 Restore Controls
PostgreSQL 18 includes additional archive restore controls for scenarios such as statistics, data/schema selection, and policy handling. Use these only with a defined recovery purpose and test their effect in isolation before production adoption.

## 25. Canonical Acceptance Artifact
Companion artifact:

```text
labs/pg-restore-readiness-check.sql
```

Label:

```text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
```

It performs target-side inspection only:

```text
NO pg_restore
NO CREATE/DROP DATABASE
NO DROP objects
NO DDL/DML
NO ownership/ACL changes
NO trigger/RLS changes
NO tablespace changes
NO session termination
NO archive/filesystem manipulation
NO credential inspection
NO automatic remediation
```

## 26. What SAFE-READ Cannot Prove
The acceptance artifact cannot prove:
- archive integrity;
- archive/source trust;
- dependency completeness;
- source/target compatibility;
- external capacity;
- restore success;
- PostgreSQL correctness after restore;
- application recovery;
- achievable RPO/RTO.

Those require archive evidence and isolated recovery rehearsal.

## 27. Recovery Evidence Chain
```text
archive inspected
      ↓
target preflight passed
      ↓
restore completed
      ↓
PostgreSQL validation passed
      ↓
application validation passed
      ↓
recovery duration recorded
```

## 28. Key Takeaways
```text
plain SQL → psql
archive dump → pg_restore
archive exists != restore proven
--clean = destructive
--clean --create = potentially database-destructive
selective restore != dependency-complete recovery
parallel restore != free capacity
restore success != application recovery
SAFE-READ != RESTORE-VALIDATED
```
