# Part 5.11 — Backup Validation, Integrity, and Restore Testing

**Part:** 5 — Backup, Recovery & Disaster Recovery  
**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Audience:** PostgreSQL Administrators, DBREs, SREs, Platform Engineers

---

## 1. Purpose

A backup is useful only if it can participate in a successful recovery.

A job status such as:

```text
BACKUP COMPLETED
```

proves only that a backup workflow reached its completion condition. It does
not independently prove that:

- every expected artifact exists;
- the artifact is readable;
- a physical backup matches its manifest;
- a logical archive can be inspected;
- required WAL is available;
- roles, extensions, tablespaces, and dependencies are recoverable;
- a restored database starts;
- the application can use the restored data;
- recovery meets the required RPO and RTO.

Part 5.11 establishes a layered validation model that separates **artifact
validation** from **actual restore testing**.

The governing principle is:

> Backup success is evidence of backup execution. Restore testing is evidence
> of recoverability.

---

## 2. Learning Objectives

After this tutorial, you should be able to:

- distinguish backup completion, integrity validation, restore validation, and
  application validation;
- understand the role of PostgreSQL backup manifests;
- use `pg_verifybackup` appropriately for physical backups produced by
  `pg_basebackup`;
- inspect logical custom/directory/tar archives before restore;
- understand the validation boundaries of `pg_restore --list`;
- design isolated restore rehearsals;
- capture evidence from a restored PostgreSQL instance;
- validate schema, object, row, and application-level expectations;
- recognize dependencies that may exist outside the backup artifact;
- define pass/fail criteria for recovery drills;
- keep routine production acceptance checks SAFE-READ.

---

## 3. The Validation Ladder

Backup assurance should be layered:

```text
Layer 1 — Backup job evidence
        |
        v
Layer 2 — Artifact existence/readability
        |
        v
Layer 3 — Artifact integrity/structure validation
        |
        v
Layer 4 — Restore execution in isolated target
        |
        v
Layer 5 — PostgreSQL-level validation
        |
        v
Layer 6 — Application/data validation
        |
        v
Layer 7 — RPO/RTO and operational evidence
```

Passing a lower layer does not automatically prove the layers above it.

For example:

```text
pg_verifybackup PASS
```

is valuable evidence for an applicable physical backup, but it is not a
substitute for periodically starting and validating a restored database.

---

## 4. Backup Validation vs. Restore Testing

### Backup validation

Backup validation asks questions such as:

- Is the backup artifact present?
- Can the artifact be read?
- Does its structure appear valid?
- Does a physical backup agree with its manifest?
- Can a logical archive's table of contents be inspected?
- Are required companion artifacts present?

### Restore testing

Restore testing asks:

- Can the backup actually be restored?
- Can PostgreSQL start from the restored physical backup?
- Can the logical archive be loaded into a clean target?
- Are expected objects present?
- Are permissions and ownership acceptable?
- Can the application execute critical workflows?
- How long does recovery take?

Both are required for a mature backup program.

---

## 5. Physical Backup Manifests

A physical backup produced by supported `pg_basebackup` workflows can contain:

```text
backup_manifest
```

The manifest records metadata about files in the backup and WAL ranges needed
for backup consistency.

A manifest provides an integrity-validation mechanism. It does not transform
the backup into a complete disaster-recovery test.

Operationally protect the manifest with the backup. Losing or altering backup
metadata weakens your ability to validate the artifact.

---

## 6. `pg_verifybackup`

`pg_verifybackup` validates an applicable PostgreSQL base backup against its
backup manifest.

Conceptual offline workflow:

```bash
pg_verifybackup /backup/postgresql/basebackup-YYYYMMDD
```

This command belongs on the backup artifact or its controlled validation copy,
not inside the SQL acceptance lab.

Validation can detect problems such as:

- files missing from the backup;
- unexpected files where relevant;
- size mismatches;
- checksum mismatches against the manifest;
- WAL requirements that cannot be validated as expected.

### Important boundary

A successful verification does **not** prove:

- PostgreSQL can start;
- configuration outside the backup is correct;
- external secrets are available;
- required extensions/packages exist;
- applications can connect;
- logical/business data is correct;
- RTO is achievable.

Therefore:

```text
pg_verifybackup PASS != restore rehearsal PASS
```

---


## 6A. PostgreSQL 18 `pg_verifybackup` Verification Model

For an applicable PostgreSQL base backup, think of verification as four
distinct stages:

```text
1. Validate backup_manifest
        |
        v
2. Compare backup file inventory
        |
        v
3. Verify file checksums recorded by the manifest
        |
        v
4. Verify required WAL can be parsed where supported
```

The manifest itself is validated before it is trusted as the description of
the backup. Verification also checks backup identity information where
applicable.

### Tar-format WAL-verification boundary

PostgreSQL 18 can verify supported base-backup formats, but WAL parsing has an
important format boundary: WAL verification is supported for plain-format
backups. When verifying a tar-format backup, use the documented
`--no-parse-wal` (`-n`) mode as appropriate and do not represent the result as
proof that the required WAL stream was parsed successfully.

### WAL verification is version-specific

For WAL parsing, use `pg_verifybackup`/`pg_waldump` tooling corresponding to
the PostgreSQL version of the backup. Record the source server version and the
verification-tool version in recovery evidence.

### Manifest checksums are not database page checksums

Keep these controls conceptually separate:

```text
backup-manifest file checksum
        !=
PostgreSQL data-page checksum
```

A manifest checksum validates backup-file evidence according to the manifest.
PostgreSQL data checksums protect database pages according to a different
mechanism. One must not be presented as proof of the other.


## 7. Logical Backup Inspection

For archive-format logical backups supported by `pg_restore`, inspect the
archive before attempting a restore.

Example:

```bash
pg_restore --list appdb.dump
```

The output can help verify that expected archive entries exist.

It is useful for:

- inventory;
- selective-restore planning;
- basic archive readability;
- identifying object dependencies and archive contents.

But:

```text
pg_restore --list PASS != restore PASS
```

The archive may still encounter problems during restore involving ownership,
privileges, extensions, target conflicts, resource exhaustion, or other
environmental dependencies.

---

## 8. Plain SQL Dumps

Plain SQL output from `pg_dump` is not a `pg_restore` archive.

It is typically restored with `psql`.

Validation must therefore use a different model:

```text
secure artifact existence/readability
        +
controlled metadata/checksum evidence
        +
isolated restore with psql
        +
post-restore validation
```

Do not attempt:

```bash
pg_restore --list backup.sql
```

and treat failure as corruption. The tool is simply inappropriate for that
backup format.

---

## 9. Cluster-Wide Logical Backup Considerations

`pg_dumpall` commonly produces plain SQL.

It may include cluster-level definitions such as:

- roles;
- role memberships;
- tablespaces;
- databases.

These can have security implications.

Validation evidence must therefore avoid casually publishing:

- password verifier material;
- sensitive role names where restricted;
- privileged memberships;
- environment-specific filesystem paths;
- secrets embedded by unsafe external procedures.

Treat cluster-wide dump artifacts as sensitive.

---

## 10. Restore Rehearsal Architecture

Never validate a production backup by destructively restoring over the
production database.

Use an isolated target:

```text
production
    |
    | backup
    v
backup repository
    |
    | controlled restore copy/access
    v
isolated restore environment
    |
    +--> restore
    +--> PostgreSQL validation
    +--> application validation
    +--> evidence capture
    +--> destroy/sanitize environment
```

Possible targets include:

- disposable VM;
- isolated PostgreSQL cluster;
- temporary managed-service instance;
- ephemeral lab environment;
- dedicated recovery-test environment.

The target must not accidentally receive production traffic.

---


## 10A. Restore Trust Boundary

Treat a database restore as execution of trusted recovery material, not merely
as copying passive files.

```text
backup provenance known?
        |
        +-- no --> quarantine/review
        |
        +-- yes
               |
               v
        authorized source?
               |
               v
        isolated target
               |
               v
        controlled restore
```

Do not restore untrusted dump content into a privileged recovery environment
simply to test whether it works.

## 10B. Restored Data Sensitivity

A temporary recovery environment can contain the same sensitive information
as the source system. Backup and restored data retain the sensitivity of their
source data unless an approved process has transformed or sanitized them.

Apply appropriate controls for:

- access;
- encryption;
- network isolation;
- audit logging;
- credentials;
- evidence retention;
- cleanup and sanitization.


## 11. Restore-Rehearsal Safety Gates

Before restoring:

1. identify the backup set;
2. identify its source system and timestamp;
3. confirm authorization to access the data;
4. verify target isolation;
5. verify sufficient target storage;
6. verify PostgreSQL version compatibility;
7. identify required extensions;
8. identify tablespaces and filesystem dependencies;
9. identify required WAL/archive dependencies;
10. protect credentials and secrets;
11. define validation queries;
12. define cleanup/data-destruction requirements;
13. record the rehearsal start time.

For sensitive production data, recovery-test environments must receive the
same security consideration as other systems holding that data.

---

## 12. Physical Restore Validation

After a physical restore has been performed using the appropriate recovery
procedure, validate PostgreSQL itself.

Useful evidence includes:

```sql
SELECT version();

SELECT
    current_database(),
    current_user,
    pg_is_in_recovery();

SELECT
    pg_postmaster_start_time();
```

Then validate:

- expected databases;
- expected schemas;
- extensions;
- critical relations;
- tablespaces;
- roles/ownership where appropriate;
- replication/recovery state;
- application connectivity.

A running postmaster alone is not sufficient evidence of a successful
business recovery.

---

## 13. Logical Restore Validation

After a logical restore, inspect expected objects.

Examples:

```sql
SELECT datname
FROM pg_catalog.pg_database
WHERE datallowconn
ORDER BY datname;
```

```sql
SELECT
    n.nspname AS schema_name,
    count(*) AS relation_count
FROM pg_catalog.pg_class AS c
JOIN pg_catalog.pg_namespace AS n
    ON n.oid = c.relnamespace
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema')
GROUP BY n.nspname
ORDER BY n.nspname;
```

These provide inventory evidence, not semantic application validation.

---

## 14. Row Counts: Useful but Limited

Teams often validate recovery with:

```sql
SELECT count(*) FROM critical_table;
```

This can be useful when compared with a trusted source-time expectation.

But a matching row count does not prove:

- every row is correct;
- every column is correct;
- relationships are valid;
- the recovery point is correct;
- recent required transactions exist;
- application behavior is correct.

Use row counts as one validation layer, not the final acceptance criterion.

---

## 15. Data-Level Validation

A recovery plan should define deterministic business/data checks.

Examples:

```text
expected latest business date
expected high-watermark ID
expected transaction checkpoint
expected number of active tenants
known reference records
critical aggregate totals
```

Where appropriate, compare the restored state with evidence captured at or
near the backup/recovery point.

Avoid exposing sensitive row-level data in broadly accessible recovery logs.

---

## 16. Schema Validation

Validate critical schema expectations such as:

- required tables;
- indexes;
- primary keys;
- foreign keys;
- sequences;
- views/materialized views;
- functions/procedures;
- extensions.

A restore can technically complete while important post-restore dependencies
remain unavailable.

For critical systems, maintain a machine-readable recovery acceptance
specification rather than relying solely on manual inspection.

---


## 16A. Source Baseline vs. Restored State

Recovery acceptance should compare known source expectations with the restored
state:

```text
SOURCE BASELINE
      |
      v
RESTORED STATE
      |
      v
DIFFERENCE ANALYSIS
```

Apply this model to critical schemas, tables, indexes, constraints, extensions,
ownership, privileges, tablespaces, and workload-specific reference data.

An invalid index or an unvalidated constraint found after recovery is not, by
itself, proof that the restore caused the condition. The condition may have
existed at the selected recovery point.


## 17. Ownership and Privilege Validation

Logical restores frequently surface environment-specific ownership or
privilege problems.

Validate:

- object owners;
- application login ability;
- required role memberships;
- schema privileges;
- sequence privileges;
- default privileges where applicable.

Do not solve restore-test failures by granting superuser broadly.

The goal is to prove the recovery procedure reproduces the required security
model.

---

## 18. Extension Validation

A dump can reference extensions that require software to exist on the target.

Before declaring recovery successful, validate expected extensions:

```sql
SELECT
    extname,
    extversion
FROM pg_catalog.pg_extension
ORDER BY extname;
```

A backup does not necessarily package operating-system extension binaries or
managed-service extension availability.

Document these as external recovery dependencies.

---

## 19. Tablespace Validation

Tablespaces can introduce recovery dependencies outside the default data
directory.

Inspect:

```sql
SELECT
    spcname,
    pg_catalog.pg_tablespace_location(oid) AS location
FROM pg_catalog.pg_tablespace
ORDER BY spcname;
```

Physical and logical recovery procedures treat tablespaces differently.

A recovery plan must account for:

- target storage;
- paths or provider abstractions;
- permissions;
- capacity;
- remapping requirements.

---

## 20. WAL and PITR Validation

When the recovery strategy depends on continuous archiving, validation must
include more than the base backup.

You need evidence that:

```text
base backup
    +
required WAL sequence
    +
recovery configuration
    =
target recovery capability
```

The strongest validation is a controlled PITR rehearsal to a known target.

Merely observing successful WAL archiving does not prove that the complete
required WAL chain can be retrieved and replayed.

---

## 21. RPO Validation

RPO asks how much data loss is acceptable.

A recovery rehearsal should determine the actual restored recovery point and
compare it with the objective.

Example:

```text
Required RPO: <= 15 minutes

Incident/recovery reference: 10:00
Recovered data point:        09:52

Observed recovery-point gap: 8 minutes

RPO result: within defined objective
```

The method must use trustworthy workload evidence, not merely filesystem
timestamps.

---

## 22. RTO Validation

RTO concerns how quickly service must be restored.

Capture timestamps for major phases:

```text
T0 incident/recovery declaration
T1 backup selected
T2 infrastructure ready
T3 restore started
T4 PostgreSQL available
T5 database validation passed
T6 application validation passed
T7 service recovery accepted
```

Do not define RTO as only the duration of `pg_restore` or base-backup copying.

Operational recovery includes decision, provisioning, restore, validation,
and service acceptance.

---

## 23. Evidence Capture

Each recovery rehearsal should produce a record containing at least:

```text
rehearsal ID
source system
backup identifier
backup timestamp
backup type
PostgreSQL source version
PostgreSQL restore version
restore target
restore start/end
validation start/end
RPO result
RTO result
artifact verification result
database validation result
application validation result
exceptions
owner
reviewer
cleanup confirmation
```

Avoid recording secrets or unnecessarily sensitive production data.

---


## 23A. Recovery-Rehearsal Cleanup

A recovery rehearsal is not complete when database validation finishes.

```text
validation complete
       |
       v
evidence secured
       |
       v
temporary credentials revoked
       |
       v
restored sensitive data sanitized/destroyed
       |
       v
temporary infrastructure removed
       |
       v
cleanup confirmed
       |
       v
rehearsal closed
```

Cleanup must follow organizational retention, legal, security, and audit
requirements. Do not destroy evidence or backup artifacts that must be
retained.


## 24. Corruption Boundaries

Different checks detect different failure classes.

| Check | Useful evidence | Does not prove |
|---|---|---|
| Backup job success | workflow completed | artifact recoverability |
| Storage checksum | object unchanged since checksum | PostgreSQL semantic validity |
| Backup manifest verification | physical files agree with manifest | application recovery |
| `pg_restore --list` | archive can be inspected | restore succeeds |
| Restore completion | tool completed | application correctness |
| PostgreSQL starts | engine can start | business data is correct |
| Row-count check | approximate dataset expectation | row/transaction correctness |
| Application smoke test | critical behavior works | every workflow is healthy |

Defense in depth is the goal.

---

## 25. Failure Handling

If validation fails:

```text
STOP
  |
  +--> preserve evidence
  +--> identify failed layer
  +--> determine whether backup set is unusable or procedure/environment failed
  +--> protect other known-good backups
  +--> investigate root cause
  +--> repair backup/recovery process
  +--> create/select new candidate backup if required
  +--> repeat restore rehearsal
```

Never overwrite or delete the only known-good backup merely because a newer
backup failed validation.

---

## 26. Automation Strategy

Automate repeatable checks such as:

- artifact inventory;
- checksum verification;
- `pg_verifybackup`;
- `pg_restore --list`;
- restore duration capture;
- schema inventory;
- extension inventory;
- expected-object checks;
- selected aggregates;
- recovery evidence generation.

Automation must stop at clearly defined safety boundaries.

Production acceptance automation should not:

- restore over production;
- drop production databases;
- alter production backup configuration;
- delete backup artifacts;
- expose secrets;
- declare business recovery solely from infrastructure checks.

---

## 27. Managed-Service Considerations

Managed PostgreSQL services can change the recovery interface substantially.

Depending on the provider, you may have:

- provider-managed snapshots;
- automated backups;
- PITR through provider APIs;
- restricted filesystem access;
- no direct physical backup directory;
- provider-managed WAL retention;
- temporary restore instances;
- service-specific backup retention.

The validation principle remains unchanged:

```text
provider says backup succeeded
            !=
you have demonstrated application recovery
```

Use the provider-supported restore mechanism, then perform database and
application validation on the restored target.

## 28. Hands-On Lab

Companion artifact:

```text
labs/backup-validation-check.sql
```

The acceptance artifact is deliberately SAFE-READ.

It gathers PostgreSQL-visible evidence useful when validating either:

- a source system before backup; or
- an isolated restored system after recovery.

It checks:

1. server identity;
2. recovery state;
3. databases;
4. user schemas and relation inventory;
5. installed extensions;
6. tablespaces;
7. critical object inventory framework;
8. invalid indexes;
9. unvalidated constraints;
10. summary evidence.

It does not execute a restore.

Restore execution belongs in a controlled, isolated recovery rehearsal.

## 29. Lab Usage

Run:

```bash
psql \
  --dbname=postgres \
  --file=labs/backup-validation-check.sql
```

For a restored application database, connect directly to that database when
performing database-specific object validation.

Example:

```bash
psql \
  --dbname=restored_appdb \
  --file=labs/backup-validation-check.sql
```

Capture output into the recovery evidence system according to local security
policy.

## 30. Production Safety Rules

### SAFE-READ

The canonical acceptance check may:

- query catalogs;
- query statistics views;
- inspect recovery state;
- inventory schemas/relations;
- inspect extensions;
- inspect tablespaces;
- identify invalid indexes;
- identify constraints not yet validated.

### ISOLATED RECOVERY ENVIRONMENT

Restore exercises may perform destructive operations only against explicitly
approved disposable/recovery-test targets.

### NEVER

Do not:

- restore a tutorial backup over production;
- delete the only known-good backup;
- expose credentials in evidence;
- assume successful backup equals successful restore;
- assume successful restore equals successful application recovery;
- grant broad superuser rights merely to bypass recovery errors.

## 31. Recovery Acceptance Criteria

A production recovery strategy should define explicit acceptance criteria.

Example:

```text
Artifact validation       PASS
Restore execution         PASS
PostgreSQL startup        PASS
Critical schemas          PASS
Critical extensions       PASS
Critical object inventory PASS
Security validation       PASS
Application smoke test    PASS
Observed RPO              within objective
Observed RTO              within objective
Evidence archived         PASS
Cleanup completed         PASS
```

The exact checks must be workload-specific.

## 32. Key Takeaways

1. A completed backup job is not proof of recoverability.
2. Artifact validation and restore testing solve different problems.
3. `pg_verifybackup` is important physical-backup evidence where applicable.
4. `pg_restore --list` validates archive inspectability, not restore success.
5. Plain SQL dumps require a different validation workflow.
6. Restore tests belong in isolated targets.
7. PostgreSQL startup is only one recovery milestone.
8. Application/data validation is required for meaningful recovery evidence.
9. RPO and RTO should be measured during rehearsals.
10. Recovery evidence must be retained and reviewed.
11. External dependencies such as extensions, secrets, tablespaces, and
    infrastructure belong in the recovery plan.
12. Backup operations are incomplete without recurring restore testing.

---

## 33. Canonical Acceptance Boundary

This canonical tutorial and SAFE-READ acceptance artifact provide a
production-safe framework for collecting database-side recovery evidence.

It does not prove:

- that a specific backup artifact is intact;
- that a backup can be restored;
- that all required WAL can be retrieved;
- that applications can use a restored database;
- that required RPO/RTO is met;
- that external dependencies are recoverable.

Those claims require controlled artifact validation and restore rehearsal.
