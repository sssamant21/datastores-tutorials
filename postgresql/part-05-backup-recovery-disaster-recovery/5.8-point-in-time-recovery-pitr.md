# Part 5.8 — Point-in-Time Recovery (PITR)

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Track:** Part 5 — Backup, Recovery & Disaster Recovery

## 1. Purpose

Point-in-Time Recovery (PITR) restores a physical PostgreSQL backup and replays the required WAL to an intentionally selected recovery target.

```text
physical backup
      +
required continuous WAL
      +
evidence-based recovery target
      ↓
isolated PITR
      ↓
database validation
      ↓
application/business validation
      ↓
controlled cutover
```

Core rule:

```text
backup exists != PITR ready
PITR completed != application recovery validated
```

## 2. When PITR Is Useful

Typical cases include accidental destructive SQL, bad deployments, unwanted bulk changes, logical corruption discovered after the event, disaster recovery, or returning to a known business checkpoint.

PITR does not identify the correct recovery point automatically. Target selection is an incident-evidence problem.

## 3. Recovery Chain

A usable recovery chain requires a compatible physical backup and every required WAL record from that backup through the selected target.

```text
backup B1
  ↓
WAL 001
  ↓
WAL 002
  ↓
WAL 003
  ↓
target
```

A required WAL gap can make the requested target unreachable.

## 4. PostgreSQL 18 Recovery Model

Modern PostgreSQL does not use the historical `recovery.conf` workflow.

Conceptually:

```text
restored PGDATA
      +
normal PostgreSQL recovery parameters
      +
recovery.signal
      ↓
server startup
      ↓
archive recovery / WAL replay
```

A `standby.signal` is associated with standby operation and must not be confused casually with an isolated PITR procedure.

## 5. Archive vs Restore Direction

```text
archive_command / archive_library
          ↓
      stores WAL

restore_command
          ↓
 retrieves required WAL
    during recovery
```

The restore mechanism must retrieve the requested WAL correctly, distinguish success from failure, protect credentials, tolerate expected retries, and provide operational evidence.

## 6. Recovery Targets

PostgreSQL recovery targeting includes concepts such as:

```text
recovery_target_time
recovery_target_xid
recovery_target_name
recovery_target_lsn
recovery_target = 'immediate'
```

Detailed target/timeline administration is covered in Part 5.9.

## 7. Target Selection Is Evidence-Based

For an accidental destructive event:

```text
T1 — last known-good business state
T2 — destructive event
T3 — detection
```

Do not assume:

```text
target = T3 - arbitrary number of minutes
```

Use application/database/audit logs, deployment timestamps, transaction evidence, operator activity, business events, and the incident timeline.

## 8. Target Inclusion Semantics

A target value alone is not the complete recovery decision.

Record before recovery:

```text
target type
target value
timezone where applicable
inclusive/exclusive requirement
expected business state
supporting evidence
approver
```

For target types where inclusion semantics apply, `recovery_target_inclusive` must be understood before starting recovery.

## 9. Recovery Target Action

The operator must know what PostgreSQL should do after the recovery target is reached.

`recovery_target_action` controls post-target behavior such as pausing, promotion, or shutdown according to the configured mode.

Do not discover this behavior accidentally during a production incident.

## 10. Named Restore Points

A named restore point can provide a deliberate WAL marker for later recovery targeting.

```text
known change boundary
      ↓
named restore point
      ↓
change/deployment
      ↓
incident
      ↓
candidate recovery target
```

Creating a restore point writes WAL and is therefore prohibited in the SAFE-READ acceptance artifact.

## 11. Recovery Progress

Useful read-only recovery evidence includes:
- `pg_is_in_recovery()`;
- `pg_last_wal_receive_lsn()`;
- `pg_last_wal_replay_lsn()`;
- `pg_last_xact_replay_timestamp()`.

Important:

```text
WAL received != WAL replayed
```

Also:

```text
pg_last_xact_replay_timestamp()
!= wall-clock time
!= guaranteed business recovery point
```

It reflects replayed transaction commit/abort evidence and requires careful interpretation.

## 12. Recovery Consistency

A running PostgreSQL process does not necessarily mean the database is ready for validation.

Conceptually:

```text
server starts
    ↓
recovery progresses
    ↓
consistent state reached
    ↓
read-only validation may become possible
    ↓
target reached
    ↓
final recovery validation
```

## 13. Timeline Awareness

PITR can introduce a new recovery history/timeline.

```text
original timeline
       ↓
PITR
       ↓
new recovery history
```

A WAL file existing in storage does not by itself prove that it belongs to the intended recovery history.

Detailed timeline management belongs to Part 5.9.

## 14. Latest Recoverable Point vs Desired Point

```text
latest recoverable point != desired business recovery point
```

If a destructive transaction has already been archived, replaying all available WAL can reproduce that destructive event. This is why intentional recovery targeting matters.

## 15. Preserve the Source

Production rule:

```text
Preserve the source.
Recover in isolation.
Validate the target.
Fence writes.
Cut over only after approval.
```

Avoid overwriting the only remaining source environment or incident evidence.

## 16. Identity Gate

Before recovery, verify:
- source environment;
- backup identity;
- PostgreSQL system identifier where available;
- recovery host/cluster;
- PostgreSQL major version;
- PGDATA;
- tablespaces;
- destination environment.

A correct procedure against the wrong environment is still a serious incident.

## 17. Pre-Recovery Gate

```text
[ ] incident/change approval
[ ] source identity confirmed
[ ] destination identity confirmed
[ ] backup selected
[ ] backup integrity evidence reviewed
[ ] required WAL continuity assessed
[ ] recovery target documented
[ ] timezone interpretation confirmed
[ ] inclusion/exclusion decision documented
[ ] expected business state documented
[ ] timeline awareness confirmed
[ ] storage capacity validated
[ ] tablespaces accounted for
[ ] software/extensions prerequisites validated
[ ] credentials prepared securely
[ ] recovery network isolation defined
[ ] application/background writes fenced
[ ] fallback defined
[ ] validation owners identified
```

## 18. Missing or Corrupt WAL

Never attempt to bypass a required WAL gap using arbitrary file renaming, fabricated content, metadata manipulation, or `pg_resetwal`.

For corruption or retrieval failure:

```text
preserve error evidence
      ↓
verify requested WAL identity
      ↓
verify archive artifact integrity
      ↓
verify retrieval mechanism
      ↓
verify backup/version/timeline compatibility
      ↓
use alternate known-good artifact if available
```

## 19. Capacity Planning

Plan capacity for:

```text
PGDATA
+ tablespaces
+ retrieved/staged WAL
+ recovery logs
+ temporary operational headroom
+ validation workload
+ expected growth
+ safety margin
```

Monitor filesystem/PVC utilization throughout recovery.

## 20. Recovery Isolation

A restored production database can trigger external side effects if applications or jobs connect to it.

Fence or disable as appropriate:
- application writes;
- scheduled jobs;
- ETL;
- Kafka producers/consumers;
- CDC;
- notifications;
- payment integrations;
- external APIs;
- background workers.

## 21. Recovery Monitoring

Monitor:
- startup/recovery logs;
- WAL retrieval;
- receive/replay positions where relevant;
- storage utilization;
- CPU/I/O;
- recovery errors;
- target attainment;
- timeline behavior;
- recovery completion.

Monitoring is evidence, not proof of business correctness.

## 22. Recovery Pause Safety

If recovery is intentionally paused, define:
- why it is paused;
- owner;
- storage/WAL monitoring;
- validation actions;
- condition for resume/promotion/shutdown.

Do not leave a critical recovery indefinitely paused without ownership and monitoring.

## 23. Layered Validation

```text
Level 1 — PostgreSQL process healthy
Level 2 — expected recovery target reached
Level 3 — cluster/database identity correct
Level 4 — schemas/objects present
Level 5 — critical data validated
Level 6 — roles/security validated
Level 7 — application smoke tests pass
Level 8 — integrations validated
Level 9 — business owner validates recovered state
Level 10 — measured RPO/RTO recorded
```

```text
PostgreSQL started != recovery validated
```

## 24. Split-Brain Prevention

Before enabling writes:

```text
original writer
      ↓
FENCED
      ↓
recovered cluster validated
      ↓
routing changed
      ↓
new writer enabled
```

Never allow original and recovered clusters to accept independent production writes.

## 25. Cutover Gate

```text
[ ] recovery target documented
[ ] target evidence retained
[ ] recovery completion confirmed
[ ] identity verified
[ ] database validation PASS
[ ] business-data validation PASS
[ ] application validation PASS
[ ] security validation PASS
[ ] integrations validated
[ ] old writer fenced
[ ] fallback decision documented
[ ] monitoring ready
[ ] application owner approval
[ ] database owner approval
[ ] incident/change owner approval
```

## 26. Fallback vs Post-Cutover Recovery

Before cutover, returning to another known-good recovery candidate may be a fallback.

After the recovered system accepts new production writes:

```text
recovered cluster
      ↓
new writes
      ↓
state divergence
```

Switching back can lose those writes. A post-cutover reversal therefore requires a new data-consistency/recovery decision.

## 27. Managed Services

Managed PostgreSQL platforms may expose PITR as provider-managed restore operations rather than native filesystem recovery.

```text
self-managed
    → backup + WAL + native recovery controls

managed service
    → provider PITR/restore workflow
      + provider retention window
      + provider-specific validation/cutover
```

Provider-reported restore success does not replace database/application validation.

## 28. Kubernetes

For Kubernetes-hosted PostgreSQL:
- understand operator recovery semantics;
- use isolated cluster/PVC identity;
- prevent accidental service routing;
- validate secret handling;
- understand object-storage WAL retrieval;
- monitor PVC capacity;
- rehearse operator-specific recovery before an incident.

## 29. Security

Protect:
- backup/WAL access;
- restore credentials;
- database passwords;
- TLS private keys;
- encryption keys;
- cloud tokens;
- restored production data;
- recovery logs;
- temporary recovery storage.

Do not place secrets in Git, screenshots, tickets, shell history, or routine acceptance evidence.

## 30. Recovery Evidence Record

Preserve:
- incident timeline;
- backup identifier/timestamp;
- integrity result;
- system/recovery identity;
- target type/value/timezone;
- target inclusion choice;
- timeline evidence;
- WAL evidence;
- recovery start/end;
- errors;
- validation results;
- cutover time;
- approvals;
- measured RPO/RTO.

## 32. Acceptance Boundary

The lab inspects selected PostgreSQL-visible readiness and identity evidence only.

It does not prove:
- backup integrity;
- required WAL continuity;
- restore-command correctness;
- recovery target correctness;
- timeline correctness;
- successful replay;
- database recovery;
- application recovery;
- safe cutover;
- achieved RPO/RTO.

```text
SAFE-READ != PITR-VALIDATED
```

## 33. Key Takeaways

```text
PITR = physical backup + required WAL + intentional target + validation
latest recoverable point != desired recovery point
target selection is an evidence problem
WAL received != WAL replayed
wrong-target PITR can be technically successful and operationally wrong
preserve source evidence
recover in isolation
fence writes before cutover
PostgreSQL started != recovery validated
SAFE-READ != PITR-VALIDATED
```
