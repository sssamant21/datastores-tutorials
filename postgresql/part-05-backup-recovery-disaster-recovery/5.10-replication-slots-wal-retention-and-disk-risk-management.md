# Part 5.10 — Replication Slots, WAL Retention, and Disk-Risk Management

**Part:** 5 — Backup, Recovery & Disaster Recovery  
**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Audience:** PostgreSQL DBAs, DBREs, SREs, platform engineers, and production support engineers

---

## 1. Purpose

Replication slots solve an important durability problem: they allow PostgreSQL to retain resources that a replication consumer still needs.

That protection also creates an operational risk.

A physical or logical replication slot that stops advancing can retain WAL for an extended period. If the retained WAL grows without a bounded operational response, `pg_wal` can consume the filesystem and eventually threaten database availability.

This tutorial builds a production-oriented method for answering five questions:

1. Which replication slots exist?
2. Which slots are active, inactive, invalid, or no longer advancing?
3. How much WAL is each slot potentially retaining?
4. How close is a bounded slot to exhausting its safe WAL allowance?
5. What must be investigated before any slot is advanced, invalidated, or dropped?

The central rule is:

> A replication slot is a durability contract with a consumer, not merely a PostgreSQL object.

Never remove or advance a slot solely because it appears old or because it is retaining a large amount of WAL.

After completing Part 5.10, you should be able to:

- understand why slot deletion, forced advancement, and forced checkpoints
  require explicit operational approval.

## 3. Why Replication Slots Exist

Without a replication slot, a disconnected downstream consumer can fall far
enough behind that WAL it still needs is recycled or removed.

Replication slots provide PostgreSQL-visible retention state for a consumer.

For physical replication, the slot protects WAL needed by a standby.

For logical replication, the slot protects WAL required for logical decoding.
Logical slots can also maintain transaction/catalog cleanup horizons through
`xmin` and `catalog_xmin`.

This protection is valuable, but it transfers part of the downstream
consumer's availability problem to the publisher or primary:

```text
consumer stops advancing
        |
        v
slot restart_lsn stops advancing
        |
        v
old WAL remains required
        |
        v
pg_wal grows
        |
        v
filesystem free space falls
        |
        v
database availability risk
```

A slot therefore requires lifecycle ownership, monitoring, and an incident
response policy.

## 4. Physical vs. Logical Replication Slots

### 4.1 Physical slots

A physical slot is normally associated with physical streaming replication.

Important evidence includes:

- `slot_name`
- `slot_type`
- `active`
- `active_pid`
- `restart_lsn`
- `wal_status`
- `safe_wal_size`
- `inactive_since`
- `invalidation_reason`

A physical slot does not have `confirmed_flush_lsn`.

### 4.2 Logical slots

A logical slot supports logical decoding and logical replication.

In addition to `restart_lsn`, a logical slot can expose:

- `plugin`
- `database`
- `confirmed_flush_lsn`
- `catalog_xmin`
- `two_phase`
- `failover`
- `synced`

`confirmed_flush_lsn` describes how far a logical consumer has acknowledged
receipt. It is not interchangeable with `restart_lsn`.

`restart_lsn` is the key retention boundary for WAL that PostgreSQL still may
need for that slot.

## 5. The Primary Inspection View: `pg_replication_slots`

Start with cluster-visible slot state:

```sql
SELECT
    slot_name,
    slot_type,
    database,
    plugin,
    temporary,
    active,
    active_pid,
    restart_lsn,
    confirmed_flush_lsn,
    wal_status,
    safe_wal_size,
    inactive_since,
    invalidation_reason
FROM pg_catalog.pg_replication_slots
ORDER BY slot_type, slot_name;
```

PostgreSQL 18 exposes enough state here to separate several very different
conditions:

- active and healthy-looking;
- inactive but recently disconnected;
- inactive for a long period;
- retaining WAL beyond normal `max_wal_size` behavior;
- approaching a configured slot-retention limit;
- no longer retaining all required WAL;
- already invalidated or unusable.

Do not reduce these states to a single `active = false` alert.

## 6. Estimating WAL Retained by a Slot

LSNs represent positions in the WAL stream. PostgreSQL can calculate the byte
distance between two LSNs with `pg_wal_lsn_diff()`.

A useful operational estimate is:

```sql
SELECT
    slot_name,
    slot_type,
    active,
    restart_lsn,
    pg_current_wal_lsn() AS current_wal_lsn,
    CASE
        WHEN restart_lsn IS NULL THEN NULL
        ELSE pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)
    END AS retained_wal_bytes,
    CASE
        WHEN restart_lsn IS NULL THEN NULL
        ELSE pg_size_pretty(
            pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)
        )
    END AS retained_wal_pretty
FROM pg_catalog.pg_replication_slots
ORDER BY
    pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)
        DESC NULLS LAST;
```

### Important interpretation boundary

This is an LSN-distance estimate.

It does **not** mean:

> exactly this many bytes currently exist on disk only because of this slot.

Actual `pg_wal` occupancy is influenced by multiple mechanisms, including
checkpoint/WAL recycling behavior, WAL archiving state, `wal_keep_size`, and
slot retention.

Use LSN distance as retention-pressure evidence, not as a substitute for
filesystem monitoring.

---

## 7. `wal_status`: A Better Signal Than Slot Age Alone

PostgreSQL exposes `wal_status` for each slot.

Operationally important states are:

| `wal_status` | Interpretation |
|---|---|
| `reserved` | Required WAL is retained within normal WAL sizing behavior. |
| `extended` | WAL beyond `max_wal_size` is being retained because a slot or `wal_keep_size` still requires it. |
| `unreserved` | Required WAL is no longer guaranteed to remain retained and may be removed at a checkpoint. This state is not necessarily irreversible; it can return to `reserved` or `extended` if conditions permit. |
| `lost` | Required WAL has been lost and the slot is no longer usable. Consumer recovery or reinitialization may be required. |

An `extended` state is not automatically an incident, but it is a strong
reason to inspect retention size, consumer health, WAL rate, and filesystem
runway.

`unreserved` and `lost` require urgent investigation because downstream
continuity may already be at risk.

---

## 8. `safe_wal_size`: Remaining WAL Budget Before Slot Loss

When `max_slot_wal_keep_size` is configured with a finite value,
`safe_wal_size` can report how many additional WAL bytes may be generated
before a slot is in danger of becoming `lost`.

Example:

```sql
SELECT
    slot_name,
    wal_status,
    safe_wal_size,
    pg_size_pretty(safe_wal_size) AS safe_wal_pretty
FROM pg_catalog.pg_replication_slots
ORDER BY safe_wal_size NULLS LAST;
```

A `NULL` value needs interpretation. For example, `safe_wal_size` is `NULL`
for a lost slot and when slot WAL retention is unlimited.

Therefore:

```text
safe_wal_size IS NULL
```

must not automatically be interpreted as safe.

---

## 9. `max_slot_wal_keep_size`

`max_slot_wal_keep_size` limits how much WAL replication slots are allowed to
retain in `pg_wal` at checkpoint time.

Inspect it with:

```sql
SELECT
    name,
    setting,
    unit,
    source,
    pending_restart
FROM pg_catalog.pg_settings
WHERE name = 'max_slot_wal_keep_size';
```

The PostgreSQL default is `-1`, meaning slot WAL retention is unlimited.

That default preserves consumer recoverability but can expose the primary to
unbounded WAL growth if a slot stops advancing.

### Production tradeoff

A finite value protects primary disk capacity, but it changes the failure
mode:

```text
unlimited slot retention
    -> protects lagging consumer
    -> can threaten primary disk

finite max_slot_wal_keep_size
    -> bounds slot WAL retention
    -> sufficiently lagging consumer can lose required WAL
    -> consumer may require reinitialization
```

There is no universally correct value.

Capacity planning must consider:

- peak WAL generation rate;
- expected consumer outage duration;
- recovery objectives;
- archive availability;
- reinitialization time;
- `pg_wal` filesystem capacity;
- alerting and response time.

## 10. `wal_keep_size` Is Not a Replication-Slot Limit

Inspect both settings together:

```sql
SELECT
    name,
    setting,
    unit,
    source
FROM pg_catalog.pg_settings
WHERE name IN (
    'wal_keep_size',
    'max_slot_wal_keep_size'
)
ORDER BY name;
```

They solve different problems.

### `wal_keep_size`

`wal_keep_size` establishes a minimum amount of old WAL to retain for
streaming standby needs.

### `max_slot_wal_keep_size`

`max_slot_wal_keep_size` establishes a maximum slot-driven WAL-retention
allowance evaluated at checkpoint time.

Do not assume that increasing `wal_keep_size` fixes an unhealthy replication
slot. It can increase WAL retained locally and therefore worsen disk pressure.

## 11. PostgreSQL 18: Idle Slot Invalidation

PostgreSQL 18 also exposes `idle_replication_slot_timeout`.

Inspect it safely:

```sql
SELECT
    name,
    setting,
    unit,
    source
FROM pg_catalog.pg_settings
WHERE name = 'idle_replication_slot_timeout';
```

A nonzero value can invalidate eligible replication slots that remain
inactive beyond the configured duration.

The invalidation is checkpoint-dependent. This matters operationally:
crossing the configured inactivity duration does not mean the slot is
invalidated at that exact second.

Idle-timeout invalidation does not apply to slots that have not reserved WAL
or to synchronized standby slots where `synced = true`.

If invalidated for this reason, PostgreSQL can expose:

```text
invalidation_reason = 'idle_timeout'
```

PostgreSQL 18 can expose these important invalidation reasons:

| Reason | Operational interpretation |
|---|---|
| `wal_removed` | Required WAL was removed. |
| `rows_removed` | Required rows were removed, affecting logical decoding. |
| `wal_level_insufficient` | WAL level became insufficient for the slot's requirements. |
| `idle_timeout` | The slot exceeded the configured idle timeout and was invalidated. |

Treat an invalidation reason as evidence requiring topology-aware recovery
analysis. Do not assume that recreating a slot preserves consumer continuity.

Do not force a checkpoint from a routine health-check script merely to make
timeout invalidation happen sooner.

## 12. Inactive Does Not Mean Abandoned

This query helps identify slots requiring investigation:

```sql
SELECT
    slot_name,
    slot_type,
    database,
    active,
    inactive_since,
    restart_lsn,
    wal_status,
    invalidation_reason
FROM pg_catalog.pg_replication_slots
WHERE NOT active
ORDER BY inactive_since NULLS LAST, slot_name;
```

Possible explanations include:

- planned maintenance;
- subscriber restart;
- standby outage;
- network interruption;
- disaster-recovery system intentionally powered down;
- deployment problem;
- logical replication worker failure;
- consumer decommissioning that never removed its slot;
- an abandoned test integration.

The database cannot tell you which business explanation is correct.

That requires ownership evidence.

## 13. Slot Ownership Is an Operational Requirement

Maintain an inventory outside the database containing at least:

| Field | Example purpose |
|---|---|
| Slot name | Correlate database state |
| Slot type | Physical/logical |
| Consumer | Standby, subscriber, CDC platform |
| Environment | Production/staging/etc. |
| Service owner | Team accountable for consumer |
| Criticality | DR, reporting, integration, migration |
| Expected disconnect tolerance | Capacity planning |
| Reinitialization procedure | Recovery path |
| Decommission approval | Prevent orphan slots |

A slot with no known owner should be treated as an operational defect.

It should **not** be automatically treated as disposable.

## 14. WAL Archiving and Slot Retention Are Different Mechanisms

A WAL archive and a replication slot serve different purposes.

A healthy archive may provide an alternate source of WAL for some physical
recovery scenarios, but it does not mean that an unhealthy replication slot
can simply be ignored.

For logical decoding, do not assume archived WAL provides a transparent
replacement for a lost logical slot.

Operationally, inspect archiving separately:

```sql
SELECT
    archived_count,
    failed_count,
    last_archived_wal,
    last_archived_time,
    last_failed_wal,
    last_failed_time
FROM pg_catalog.pg_stat_archiver;
```

Also inspect configuration:

```sql
SELECT
    name,
    setting,
    source
FROM pg_catalog.pg_settings
WHERE name IN (
    'archive_mode',
    'archive_command',
    'archive_library'
)
ORDER BY name;
```

Do not expose secret-bearing command text in broad monitoring systems without
reviewing how archive commands are configured in your environment.

## 15. Why Disk Risk Can Become a Database Availability Incident

WAL is fundamental to PostgreSQL durability.

If the filesystem containing `pg_wal` approaches exhaustion, the correct
response is not to delete WAL files manually.

Never run commands such as:

```text
rm .../pg_wal/...
```

Manual deletion from `pg_wal` can destroy the database's ability to recover
or continue safely.

Instead, identify the retention mechanism and restore capacity or consumer
progress through a controlled response.

### Evidence chain

A useful incident investigation follows:

```text
filesystem usage rising
        |
        +--> WAL generation rate increased?
        |
        +--> archive failing/backlogged?
        |
        +--> replication slot restart_lsn stalled?
        |
        +--> wal_keep_size unusually large?
        |
        +--> checkpoint/WAL sizing behavior?
```

Do not diagnose slot retention from filesystem usage alone.

## 16. Measuring Slot Retention Pressure

A read-only fleet query:

```sql
WITH current_position AS (
    SELECT pg_current_wal_lsn() AS current_lsn
)
SELECT
    s.slot_name,
    s.slot_type,
    s.database,
    s.active,
    s.inactive_since,
    s.restart_lsn,
    s.wal_status,
    s.safe_wal_size,
    s.invalidation_reason,
    CASE
        WHEN s.restart_lsn IS NULL THEN NULL
        ELSE pg_wal_lsn_diff(c.current_lsn, s.restart_lsn)
    END AS retained_wal_bytes
FROM pg_catalog.pg_replication_slots AS s
CROSS JOIN current_position AS c
ORDER BY retained_wal_bytes DESC NULLS LAST;
```

Use this together with infrastructure metrics for:

- filesystem size;
- filesystem used bytes;
- filesystem free bytes;
- WAL generation bytes/second;
- archive success/failure;
- replication lag;
- consumer availability.

## 17. Disk Runway

A useful SRE concept is **disk runway**.

If WAL-driven disk consumption is increasing, estimate:

```text
runway_seconds =
    usable_free_bytes / net_disk_growth_bytes_per_second
```

A second useful estimate is consumer catch-up exposure:

```text
retained_wal_bytes / recent_wal_generation_bytes_per_second
```

These are estimates, not guarantees.

WAL generation can be bursty. Checkpoints, archiving, recycling, and consumer
catch-up can change disk behavior.

Alerting should therefore use both:

- absolute thresholds; and
- rate/runway thresholds.

Example policy concepts:

```text
warning:
  slot retention > environment threshold
  OR free-space runway < operational response target

critical:
  wal_status in ('unreserved', 'lost')
  OR safe_wal_size approaching exhaustion
  OR filesystem runway below emergency threshold
```

Exact thresholds must be derived from the environment's WAL rate, disk size,
RTO/RPO, and staffing response time.

## 18. Correlating Slots With Active Replication

A slot can be compared with current WAL sender activity:

```sql
SELECT
    s.slot_name,
    s.slot_type,
    s.active,
    s.active_pid,
    r.application_name,
    r.client_addr,
    r.state,
    r.sent_lsn,
    r.write_lsn,
    r.flush_lsn,
    r.replay_lsn
FROM pg_catalog.pg_replication_slots AS s
LEFT JOIN pg_catalog.pg_stat_replication AS r
    ON r.pid = s.active_pid
ORDER BY s.slot_name;
```

This can help answer:

- Is the physical consumer connected?
- Which application/session is using the slot?
- Is the slot active but the downstream system still lagging?

Logical replication topologies may require additional publisher/subscriber
evidence. A single query should not be treated as a complete topology map.

## 19. Logical Slots and Cleanup Horizons

Logical slots can also expose:

```sql
SELECT
    slot_name,
    database,
    active,
    xmin,
    catalog_xmin,
    restart_lsn,
    confirmed_flush_lsn
FROM pg_catalog.pg_replication_slots
WHERE slot_type = 'logical'
ORDER BY slot_name;
```

This matters because a logical slot can create risk beyond `pg_wal` growth.

An old cleanup horizon can contribute to retention of row/catalog versions
that PostgreSQL would otherwise be able to clean.

Therefore logical-slot monitoring should include both:

```text
WAL retention risk
+
cleanup-horizon / bloat risk
```

Do not focus only on filesystem consumption.

## 20. Production Incident Pattern

### Scenario

Monitoring reports rapid growth on the filesystem containing `pg_wal`.

### Step 1 — Confirm storage pressure

Use infrastructure/storage telemetry to establish:

- total capacity;
- used capacity;
- free capacity;
- recent growth rate;
- projected runway.

### Step 2 — Inspect slot state

```sql
SELECT
    slot_name,
    slot_type,
    active,
    inactive_since,
    restart_lsn,
    wal_status,
    safe_wal_size,
    invalidation_reason,
    pg_size_pretty(
        pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)
    ) AS retained_wal
FROM pg_catalog.pg_replication_slots
WHERE restart_lsn IS NOT NULL
ORDER BY
    pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)
        DESC;
```

### Step 3 — Inspect retention configuration

```sql
SELECT
    name,
    setting,
    unit,
    source
FROM pg_catalog.pg_settings
WHERE name IN (
    'max_slot_wal_keep_size',
    'wal_keep_size',
    'idle_replication_slot_timeout',
    'max_wal_size'
)
ORDER BY name;
```

### Step 4 — Check archive health

```sql
SELECT *
FROM pg_catalog.pg_stat_archiver;
```

### Step 5 — Identify the consumer and owner

Determine:

- what uses the slot;
- whether the consumer is intentionally offline;
- when it last worked;
- whether it can safely resume;
- whether reinitialization is possible;
- whether the slot is still required.

### Step 6 — Choose a controlled response

Potential responses depend on the topology and incident:

- restore the consumer;
- repair network/connectivity;
- repair archive failures;
- add emergency storage capacity;
- reduce unrelated WAL-generating workload where operationally appropriate;
- reinitialize a failed consumer;
- decommission an obsolete slot after explicit approval.

The inspection lab in this tutorial performs none of these actions.

## 21. Controlled Remediation: Approval Required

The following operations are intentionally excluded from automated health
checks.

### 21.1 Dropping a slot

A slot can be dropped with PostgreSQL functions, but doing so can break the
consumer's ability to continue from its prior position.

Slot deletion requires:

1. verified owner;
2. verified consumer state;
3. impact assessment;
4. recovery/reinitialization plan;
5. change or incident approval;
6. post-change validation.

### 21.2 Advancing a slot

Forcing a slot forward can discard WAL/changes the consumer has not processed.

Treat slot advancement as a data-continuity decision, not a disk-cleanup
shortcut.

### 21.3 Forcing a checkpoint

Some slot-retention limits and timeout invalidations are evaluated at
checkpoint time.

That does not make `CHECKPOINT` an appropriate routine monitoring action.

A forced checkpoint changes I/O behavior and must remain outside the
SAFE-READ acceptance artifact.

### 21.4 Manually deleting WAL

Never manually remove files from `pg_wal` as a response to slot retention.

## 21A. Emergency `pg_wal` Disk-Pressure Response

When the filesystem containing `pg_wal` is approaching exhaustion, use a
controlled hierarchy rather than immediately modifying replication slots:

```text
pg_wal disk pressure detected
        |
        v
1. Measure remaining capacity and estimated runway
        |
        v
2. Identify the retention mechanism
        |
        v
3. Identify affected slot, consumer, and owner
        |
        v
4. Restore consumer progress when possible
        |
        v
5. Repair archive or connectivity failures
        |
        v
6. Add emergency storage when supported and approved
        |
        v
7. Reduce avoidable WAL-generating workload when justified
        |
        v
8. Evaluate consumer recovery/reinitialization
        |
        v
9. Drop or advance a slot only after explicit approval
```

Slot removal or advancement must not be the default first response to disk
pressure.

## 22. Monitoring Model

A production dashboard should combine database and infrastructure evidence.

### Slot state

- slot count;
- active/inactive count;
- inactive duration;
- slot type;
- `wal_status`;
- invalidation reason.

### Retention

- current LSN;
- slot `restart_lsn`;
- retained WAL estimate;
- `safe_wal_size`;
- `max_slot_wal_keep_size`.

### Consumer health

- streaming connection state;
- replication lag;
- subscriber/CDC health;
- consumer restart/reconnect events.

### WAL/archive health

- WAL generation rate;
- archive successes/failures;
- time since last successful archive;
- `wal_keep_size`;
- `max_wal_size`.

### Storage

- `pg_wal` filesystem used/free;
- growth rate;
- estimated runway;
- volume saturation/latency where relevant.

No single metric is sufficient.

## 23. Suggested Alert Logic

Avoid alerting only on:

```text
active = false
```

A stronger policy combines state, duration, retention, and disk impact.

Example conceptual logic:

```text
IF slot is inactive
AND retained WAL is increasing
AND inactivity exceeds expected consumer outage tolerance
THEN investigate owner and consumer
```

Escalate when:

```text
wal_status = unreserved
OR wal_status = lost
OR safe_wal_size is close to exhaustion
OR disk runway is below emergency response time
```

For unlimited slot retention:

```text
max_slot_wal_keep_size = -1
```

classify the condition operationally as:

```text
UNBOUNDED SLOT WAL RETENTION
```

This is an exposure characteristic, not proof of a bad configuration. It may
be intentional when consumer recoverability is prioritized. Disk-capacity,
WAL-rate, retention-growth, consumer-health, and response-time monitoring then
become especially important.

## 24. Managed-Service Considerations

Managed PostgreSQL platforms may:

- restrict superuser capabilities;
- manage physical replication slots internally;
- expose storage through provider metrics rather than host commands;
- provide automatic storage growth;
- use service-specific logical replication procedures;
- restrict direct filesystem access;
- change how failover affects logical slots or consumers.

The PostgreSQL catalog evidence in this tutorial remains useful, but the
remediation procedure must follow the provider's supported workflow.

Never assume a self-managed slot-deletion or storage-remediation procedure is
valid for a managed service.

## 25. Production Safety Rules

### SAFE-READ

Allowed in the standard lab:

- `SHOW`;
- reads from `pg_settings`;
- reads from `pg_replication_slots`;
- reads from `pg_stat_replication`;
- reads from `pg_stat_archiver`;
- current WAL LSN inspection;
- LSN-distance calculations.

### APPROVAL REQUIRED

Examples:

- changing `max_slot_wal_keep_size`;
- changing `wal_keep_size`;
- changing `idle_replication_slot_timeout`;
- creating or dropping persistent slots;
- advancing a slot;
- reinitializing a standby/subscriber;
- forcing a checkpoint;
- modifying archive configuration;
- storage expansion.

### NEVER AS AUTOMATED REMEDIATION

- deleting files from `pg_wal`;
- dropping a slot merely because it is inactive;
- advancing a slot merely to reclaim space;
- disabling archiving to reduce storage pressure;
- hiding a disk alert without fixing the retention cause.

## 27. Operational Checklist

Before declaring slot retention healthy, verify:

- [ ] every persistent slot has an identified consumer;
- [ ] every production slot has an accountable owner;
- [ ] inactive slots are understood;
- [ ] retained-WAL growth is monitored;
- [ ] `wal_status` is monitored;
- [ ] finite-limit deployments monitor `safe_wal_size`;
- [ ] unlimited-retention deployments have strong disk/runway alerts;
- [ ] archive health is monitored independently;
- [ ] `pg_wal` filesystem capacity is monitored externally;
- [ ] WAL generation rate is understood;
- [ ] reinitialization procedures exist for important consumers;
- [ ] slot deletion requires approval;
- [ ] manual WAL deletion is prohibited;
- [ ] alert thresholds are based on capacity and response time.

## 28. Key Takeaways

1. Replication slots protect consumers by retaining required WAL and, for some
   logical workloads, cleanup horizons.
2. The same protection can threaten primary availability when a consumer
   stops advancing.
3. `restart_lsn` is a central WAL-retention boundary.
4. `wal_status` and `safe_wal_size` provide stronger operational evidence than
   slot age alone.
5. `max_slot_wal_keep_size = -1` permits unlimited slot-driven WAL retention.
6. `wal_keep_size` and `max_slot_wal_keep_size` have different semantics.
7. An inactive slot is an investigation trigger, not proof that the slot is
   abandoned.
8. Disk-risk management requires database evidence plus filesystem capacity,
   WAL-rate, archive, and consumer telemetry.
9. Dropping or advancing a slot is a data-continuity decision.
10. Never manually delete WAL files to resolve a replication-slot incident.

## 29. Canonical Acceptance Boundary

This canonical tutorial and SAFE-READ lab demonstrate inspection and risk
identification.

It does **not** prove:

- that every replication consumer is healthy;
- that retained WAL exists in an external archive;
- that a standby/subscriber can reconnect;
- that a logical consumer can resume without data loss;
- that filesystem capacity is sufficient;
- that a configured retention limit is appropriate;
- that disaster recovery objectives are met.

Those require topology-aware operational validation.
