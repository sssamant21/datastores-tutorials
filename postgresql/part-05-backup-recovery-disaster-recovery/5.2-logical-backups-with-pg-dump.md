# Part 5.2 — Logical Backups with `pg_dump`

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Track:** Part 5 — Backup, Recovery & Disaster Recovery

## 1. Purpose

`pg_dump` creates a logical export of one PostgreSQL database. A production-grade workflow must address source consistency, dump format, dependencies, ownership and privileges, capacity, security, version compatibility, artifact handling, and tested recovery.

```text
pg_dump succeeded != recovery demonstrated
```

## 2. Learning Objectives

After this tutorial, you should be able to:

- define the single-database scope of `pg_dump`;
- distinguish logical from physical backup;
- choose plain, custom, directory, or tar format from recovery requirements;
- understand parallel dump connection/load implications;
- plan selective, schema-only, and data-only exports safely;
- account for roles, ownership, ACLs, extensions, large objects, and tablespaces;
- evaluate cross-version compatibility;
- protect and validate dump artifacts;
- perform a SAFE-READ preflight assessment.

## 3. Scope — One Database

`pg_dump` operates on one database.

```text
PostgreSQL cluster
├── appdb       ← pg_dump
├── reporting
└── postgres
```

Cluster-wide objects such as roles and tablespaces require separate planning, commonly with `pg_dumpall` for globals.

A complete recovery design therefore asks:

```text
database objects/data?
cluster-wide roles/globals?
extensions/software?
external configuration?
provider configuration?
credentials and recovery access?
```

## 4. Logical vs Physical Backup

```text
pg_dump
  → logical representation of database objects/data

physical/base backup
  → physical cluster state used with required WAL
```

Logical backup is valuable for portability and selective recovery. Physical backup is foundational for other recovery patterns such as PITR. Neither replaces every use case of the other.

## 5. Consistent Export Does Not Mean Zero Impact

`pg_dump` obtains a consistent logical view while ordinary concurrent database activity can continue.

Production planning must still consider:

- metadata locks;
- concurrent DDL;
- dump duration;
- source CPU and I/O;
- connection usage;
- network throughput;
- destination capacity.

```text
consistent snapshot != zero operational impact
```

## 6. Dump Formats

### Plain

```bash
pg_dump --dbname=appdb --format=plain --file=appdb.sql
```

Plain output is a SQL script and is normally restored with `psql`.

For controlled plain-script restore, account for local `psql` customization; `psql -X` prevents startup-file settings from unexpectedly influencing the session.

### Custom

```bash
pg_dump --dbname=appdb --format=custom --file=appdb.dump
```

Custom format is an archive consumed by `pg_restore` and supports selective and parallel restore.

### Directory

```bash
pg_dump --dbname=appdb --format=directory --file=appdb_dir
```

Directory format is consumed by `pg_restore` and is the archive format that supports parallel dump.

### Tar

```bash
pg_dump --dbname=appdb --format=tar --file=appdb.tar
```

Tar is another `pg_restore` archive format, with different compression/parallel-dump characteristics.

Choose format from recovery requirements, not habit.

## 7. Compression

PostgreSQL 18 provides compression choices for supported dump formats/options. Compression affects CPU, storage, transfer, and restore behavior.

Do not assume:

```text
database logical size == final dump size
```

Measure representative workloads when backup windows or storage limits matter.

## 8. Parallel Dump

Directory format supports parallel dump:

```bash
pg_dump   --dbname=appdb   --format=directory   --jobs=4   --file=appdb_dump
```

With `--jobs=N`, plan for **N+1 database connections**.

Parallel workers use synchronized snapshots to preserve a consistent view. Parallel dump also increases concurrency against the source and can encounter locking conflicts involving concurrent exclusive-lock requests.

Before increasing jobs, validate:

```text
connection budget
CPU
I/O
largest relations
concurrent workload
DDL/change window
backup duration target
```

More workers are not automatically safer or faster.

## 9. Selective Dumps and Dependency Boundaries

Examples:

```bash
pg_dump --dbname=appdb --schema=reporting --format=custom --file=reporting.dump
```

```bash
pg_dump --dbname=appdb --table=app.orders --format=custom --file=orders.dump
```

Selection does not guarantee that every dependency required to restore the selected objects into an empty database is included.

Therefore:

```text
selected objects != self-contained application recovery
```

Validate dependencies explicitly.

## 10. Schema-Only and Data-Only

```bash
pg_dump --dbname=appdb --schema-only --file=schema.sql
```

```bash
pg_dump --dbname=appdb --data-only --format=custom --file=data.dump
```

These modes solve specific operational problems. They should not be mislabeled as complete recovery strategies without accounting for missing dependencies and cluster/global state.

## 11. Large Objects

Full logical dumps normally account for large objects according to `pg_dump` semantics, but selective object/schema workflows can change what is included.

Applications using large objects require explicit inventory and recovery validation.

Do not infer complete logical data coverage from table inventory alone.

## 12. Ownership and Privileges

Recovery planning must determine:

```text
Will original owners exist?
Should ownership be preserved?
Should ACLs be restored?
Which deployment/recovery role performs restore?
Does the destination use the same security model?
```

Ownership/ACL suppression options can be useful for migration scenarios, but must be deliberate.

For archive formats, important ownership decisions can also be made at `pg_restore` time.

## 13. Roles and Cluster-Wide Objects

Database-level `pg_dump` does not create a complete cluster identity backup.

A logical recovery strategy may require:

```text
database dump
     +
cluster/global object backup
     +
external/provider configuration
```

Part 5.4 covers `pg_dumpall`.

## 14. Extensions

Inventory extensions and versions before recovery.

The destination must have compatible extension support. A dump cannot install unavailable operating-system packages or make an unsupported managed-service extension available.

## 15. Cross-Version Compatibility

Version compatibility is an explicit preflight gate.

Record:

```text
pg_dump client version
source server version
target server version
required extensions
collation/locale dependencies
target platform constraints
```

A `pg_dump` client cannot be assumed to dump a server from a newer major version than the client understands.

Dump output is designed primarily for migration toward newer PostgreSQL versions; loading into older major versions is not guaranteed.

Cross-major workflows require testing rather than assumptions.

## 16. Capacity Planning

Before production execution, determine:

- logical database size;
- largest relations;
- expected compression;
- source resource headroom;
- connection budget;
- network path;
- staging capacity;
- final destination capacity;
- retention copies;
- restore workspace;
- backup window;
- restore-time target.

Do not size storage from a single optimistic compression estimate.

## 17. Security

Logical dumps can contain sensitive production data.

Protect:

```text
dump files/directories
temporary/staging locations
backup logs
object-storage destinations
credentials
restore environments
```

Never embed passwords, cloud keys, tokens, or private keys in tutorial commands or repositories.

A dump should also be treated as executable recovery input. Restoring database content from an untrusted source can execute SQL or code controlled by source-side privileged users.

Therefore:

```text
database trusted != dump automatically safe to restore
```

Untrusted recovery material requires inspection and an isolated destination.

## 18. Production Execution Pattern

Representative example:

```bash
pg_dump   --dbname=appdb   --format=custom   --file=appdb.dump
```

This is not a command to run blindly in production.

A controlled workflow defines:

```text
source identity
client/server compatibility
authentication
format
output destination
connection/load budget
capacity
monitoring
retention
failure handling
artifact protection
restore test
```

## 19. Failure and Artifact Handling

A nonzero `pg_dump` exit status is failure.

A robust wrapper should avoid presenting incomplete output as a valid backup.

Conceptually:

```text
write staging/incomplete artifact
        ↓
pg_dump succeeds?
     no ──→ quarantine/remove according to policy
     yes
        ↓
apply validation/protection gates
        ↓
promote to valid backup inventory
```

Do not destroy older known-good recovery points simply because a new dump started.

## 20. Recovery Lifecycle

```text
preflight
   ↓
pg_dump
   ↓
artifact protection
   ↓
archive/list inspection where applicable
   ↓
isolated restore
   ↓
PostgreSQL validation
   ↓
application validation
   ↓
record measured recovery evidence
```

The evidence hierarchy remains:

```text
dump command succeeded
      !=
artifact safely retained

artifact retained
      !=
restore successful

restore successful
      !=
application recovered

application recovered
      !=
approved RPO/RTO demonstrated
```

## 21. Canonical Acceptance Artifact

The canonical companion artifact is:

```text
labs/pg-dump-readiness-check.sql
```

Label:

```text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
```

It inspects database-side source readiness only.

It performs:

```text
NO pg_dump
NO restore
NO DDL/DML
NO role/ACL changes
NO configuration changes
NO filesystem writes
NO credential inspection
NO automatic parallelism selection
NO backup deletion
NO automatic remediation
```

## 22. What SAFE-READ Cannot Prove

The acceptance artifact cannot prove:

- destination capacity;
- network throughput;
- `pg_dump` client compatibility;
- external/global backup completeness;
- artifact integrity;
- secure retention;
- restore success;
- application recovery;
- achievable RPO/RTO.

Those require external operational evidence and recovery rehearsal.

## 23. Production Readiness Questions

Before approving a logical backup workflow, answer:

```text
Which database is being protected?
Which cluster-wide objects are separately protected?
Which pg_dump version is used?
Which format is used and why?
What is the connection/load budget?
How much destination capacity is available?
Which extensions and large objects exist?
How are ownership and ACLs handled?
How are credentials protected?
How are incomplete artifacts handled?
Where are completed dumps retained?
When was the last isolated restore?
Did application validation pass?
How long did complete recovery take?
```

## 24. Key Takeaways

```text
pg_dump = one database
logical backup != physical backup
consistent snapshot != zero operational impact
-j N => plan N+1 connections
selective dump != dependency-complete recovery
dump succeeded != artifact protected
artifact protected != restore tested
restore tested != application validated
SAFE-READ != BACKUP-VALIDATED
```
