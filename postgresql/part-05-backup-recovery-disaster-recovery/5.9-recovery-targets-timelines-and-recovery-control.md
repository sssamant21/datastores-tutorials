# Part 5.9 — Recovery Targets, Timelines, and Recovery Control

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Track:** Part 5 — Backup, Recovery & Disaster Recovery

## 1. Purpose

This tutorial extends PITR into controlled target selection, timeline interpretation, recovery pause behavior, and promotion/cutover control.

```text
recovery set
+ evidence-backed target
+ inclusion semantics
+ correct timeline/history
+ target action
+ validation
= controlled recovery
```

Precision alone is not correctness.

## 2. Production Principle

```text
Recovery precision != recovery correctness

Target evidence
+ timeline correctness
+ validation
+ write fencing
= controlled recovery
```

A technically successful recovery can still restore the wrong business state.

## 3. PostgreSQL Recovery Targets

PostgreSQL 18 recovery targeting includes:

```text
recovery_target_time
recovery_target_xid
recovery_target_name
recovery_target_lsn
recovery_target = 'immediate'
```

Select a target because incident evidence supports it, not because it is convenient.

## 4. Time Target

`recovery_target_time` is appropriate when reliable evidence identifies a desired time boundary.

Always record the timezone or UTC offset explicitly.

```text
target timestamp
+ timezone/offset
+ source of timestamp
+ event being included/excluded
+ expected business state
```

Detection time is not automatically event time. Ambiguous timestamps are unacceptable for production recovery decisions.

## 5. Transaction-ID Target

`recovery_target_xid` can target a transaction boundary when the relevant XID is known.

Critical warning:

```text
XID order != commit order
```

Transactions receive IDs as they begin, but concurrent transactions can complete in a different order. Never infer business commit ordering solely from XID magnitude.

## 6. Named Restore Point

`recovery_target_name` targets a named restore point previously written into WAL.

Useful model:

```text
pre-change validation
      ↓
unique restore point
      ↓
major change/deployment
      ↓
incident
      ↓
candidate recovery boundary
```

Restore-point names should be unique and operationally meaningful. Duplicate names create ambiguity because recovery can encounter the first matching marker.

`pg_create_restore_point()` writes WAL and is prohibited in the SAFE-READ lab.

## 7. LSN Target

`recovery_target_lsn` targets a WAL location.

```text
business evidence
      +
database/WAL evidence
      ↓
validated target LSN
```

An exact LSN is technically precise but can still represent the wrong business state.

## 8. Immediate Target

`recovery_target = 'immediate'` targets the earliest point at which recovery reaches a consistent state for the applicable recovery workflow.

It does **not** mean “replay to the latest available WAL.”

## 9. Inclusive vs Exclusive Recovery

`recovery_target_inclusive` applies to time, XID, and LSN targets.

The default is `on`.

Operationally:

```text
target type
+ target value
+ inclusive/exclusive decision
= intended recovery boundary
```

Do not imply that this setting applies to a named restore point.

Before recovery, document whether the target event/transaction must be included or excluded and what data state is expected.

## 10. Recovery Target Action

PostgreSQL 18 supports:

```text
recovery_target_action = 'pause'
recovery_target_action = 'promote'
recovery_target_action = 'shutdown'
```

The default is `pause`.

This decision must be intentional:
- `pause` supports inspection before proceeding;
- `promote` transitions authority toward a writable primary;
- `shutdown` stops the server after reaching the target according to PostgreSQL recovery semantics.

Never leave target action to assumptions during an incident.

## 11. Recovery Pause State

Distinguish a requested pause from actual replay state.

Useful read-only functions include:

```text
pg_is_wal_replay_paused()
pg_get_wal_replay_pause_state()
```

Conceptually:

```text
not paused
pause requested
paused
```

A pause request does not prove replay has already stopped.

## 12. Prolonged Pause Risk

If WAL continues to arrive while replay remains paused:

```text
WAL reception continues
       +
replay paused
       ↓
receive/replay gap grows
       ↓
storage consumption grows
       ↓
filesystem/PVC risk
```

Every production pause requires an owner, reason, start time, storage monitoring, validation task, exit condition, and tolerated duration.

## 13. Timeline Fundamentals

A PostgreSQL timeline represents a branch of WAL history.

```text
Timeline 1: A → B → C → D
                                           recovery to C
                           ↓
Timeline 2:           C → X → Y
```

After recovery/failover and subsequent activity, the new branch is a different recovery history.

```text
same-looking WAL position != necessarily same recovery history
```

## 14. Timeline History

Timeline-history files record branching relationships needed to interpret WAL histories.

Treat them as recovery artifacts:

```text
WAL segments
      +
timeline history
      ↓
interpretable recovery history
```

Do not fabricate, edit, rename, or casually delete timeline-history evidence to force recovery.

## 15. `recovery_target_timeline`

PostgreSQL 18 accepts:
- a numeric timeline ID;
- `current`;
- `latest`.

Conceptually:

```text
current
→ timeline that was current when the base backup was taken

latest
→ latest timeline found in the archive
```

`latest` is the default.

A numeric timeline can also be represented in supported hexadecimal form when appropriate.

Important:

```text
latest timeline != automatically desired business history
```

Re-recovery after an earlier PITR or failover requires deliberate timeline review.

## 16. Re-Recovery Example

```text
Timeline 1
   |
   +---- failure
          ↓
      Timeline 2
          |
          +---- later incident
                   ↓
                new PITR
```

Before the new recovery, review:
- backup origin;
- system identifier;
- prior PITR/failover history;
- timeline-history files;
- available WAL;
- desired recovery branch.

## 17. Observation vs Control

Observation:

```text
pg_is_in_recovery()
pg_last_wal_receive_lsn()
pg_last_wal_replay_lsn()
pg_last_xact_replay_timestamp()
pg_is_wal_replay_paused()
pg_get_wal_replay_pause_state()
pg_control_system()
pg_control_checkpoint()
pg_control_recovery()
```

Control:

```text
pg_wal_replay_pause()
pg_wal_replay_resume()
pg_promote()
```

Control functions do not belong in a SAFE-READ acceptance artifact.

## 18. Promotion Is an Authority Transition

```text
recovery / standby
      ↓
PROMOTION
      ↓
primary authority
```

Promotion must be gated by:
- correct target validation;
- timeline validation;
- old-writer fencing;
- application readiness;
- monitoring readiness;
- explicit approval.

Never use `pg_promote()` merely as a validation command.

## 19. Split-Brain Prevention

Correct sequence:

```text
old writer
    ↓
FENCE
    ↓
recovered target validated
    ↓
timeline/recovery state understood
    ↓
promotion authorized
    ↓
routing changed
    ↓
new writer enabled
```

Do not promote first and solve fencing later.

## 20. Target Evidence Gate

Before target-controlled recovery:

```text
[ ] incident/change ID
[ ] source system identifier
[ ] backup identifier
[ ] target type
[ ] target value
[ ] timezone/offset where applicable
[ ] inclusion/exclusion decision
[ ] recovery_target_action
[ ] timeline selection
[ ] timeline history reviewed
[ ] required WAL continuity assessed
[ ] expected business state documented
[ ] evidence supporting target retained
[ ] application owner identified
[ ] DB owner identified
[ ] approver identified
```

## 21. Validation at the Target

```text
target reached
   ↓
recovery/timeline identity
   ↓
database state
   ↓
critical data
   ↓
security
   ↓
business state
   ↓
application/integration behavior
```

`target reached` does not mean `recovery validated`.

## 22. Wrong-Target Handling

If validation shows the wrong business state:

```text
DO NOT open writes
DO NOT promote just because recovery completed
DO NOT patch the candidate merely to make validation pass
```

Instead:

```text
preserve evidence
      ↓
record observed state
      ↓
reassess target/timeline
      ↓
select evidence-backed target
      ↓
perform controlled recovery again as required
```

## 23. Timeline Mistake Handling

If an unexpected history is followed:
- stop the cutover path;
- preserve logs;
- verify system identifier;
- verify backup origin;
- inspect timeline history;
- verify archived WAL;
- verify configured timeline selection;
- reassess the recovery plan.

## 24. Fallback vs Post-Cutover Recovery

Before writes begin, a failed candidate can normally remain fenced while another recovery candidate is created.

After new production writes:

```text
recovered system
      ↓
new writes
      ↓
state divergence
```

Returning to an earlier system is no longer a simple rollback. It requires a new data-consistency/recovery decision.

## 25. Managed Services

Managed PostgreSQL platforms may hide native target and timeline mechanics behind provider PITR APIs/workflows.

Operators still need:
- target correctness;
- timezone correctness;
- restored-instance identity;
- business validation;
- write fencing;
- controlled cutover;
- RPO/RTO evidence.

## 26. Kubernetes / Operator-Managed PostgreSQL

Operators may orchestrate restore, timeline selection, promotion, service routing, and archive access.

Do not mix manual native recovery-control commands with operator automation unless the documented recovery procedure explicitly requires it.

## 27. Security and Evidence

Protect:
- archive paths/credentials;
- backup identifiers when sensitive;
- cloud credentials;
- database credentials;
- infrastructure identity;
- incident data;
- restored production data.

Preserve:
- incident/change ID;
- system identifier;
- backup identifier;
- target type/value;
- timezone;
- inclusion choice;
- target action;
- selected timeline;
- timeline history;
- WAL evidence;
- pause/resume events;
- promotion/cutover evidence;
- validation results;
- measured RPO/RTO;
- approvals.
