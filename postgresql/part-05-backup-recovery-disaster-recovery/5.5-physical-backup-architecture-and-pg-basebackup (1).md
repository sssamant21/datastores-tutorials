# Part 5.5 — Physical Backup Architecture and `pg_basebackup`

**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Track:** Part 5 — Backup, Recovery & Disaster Recovery

## 1. Purpose
`pg_basebackup` takes a physical base backup of a running PostgreSQL cluster through the replication protocol. Physical backup protects PostgreSQL's physical cluster state rather than exporting logical SQL objects.

```text
pg_dump / pg_dumpall → logical backup
pg_basebackup        → physical backup
```

A completed backup is only the first recovery-evidence gate.

## 2. Physical vs Logical Recovery
```text
logical backup  → object-oriented/selective recovery
physical backup → cluster-oriented physical recovery
```
Physical backup is not the normal method for restoring one arbitrary table into an existing database and is not a cross-major-version migration shortcut.

## 3. Recovery Foundation
```text
PGDATA
+ tablespaces
+ required WAL
+ backup metadata/manifest
        ↓
physical recovery foundation
```
External/provider configuration, secrets, software dependencies, DNS, networking, and application recovery remain separate concerns.

## 4. Source Prerequisites
Validate the approved backup identity, replication-protocol access, authentication rules, network reachability, `max_wal_senders` capacity, PostgreSQL/client versions, destination, and provider restrictions. Use least privilege appropriate to the environment.

## 5. Online Backup Impact
`pg_basebackup` can operate against a running PostgreSQL server, but online does not mean zero-impact. Monitor source read I/O, latency, CPU, network throughput, WAL generation, replication connections, destination throughput, and expected completion time.

## 6. WAL and Recoverability
```text
base backup exists != required WAL available
base files + required WAL = physical recovery foundation
```
The backup plan must define how required WAL is obtained, retained, monitored, and recovered.

## 7. Output Formats
Plain output resembles a PostgreSQL data-directory backup layout. Tar output packages backup content into archive files. Format selection affects transport, compression, tablespace handling, verification, and recovery operations.

## 8. Tablespaces
Every tablespace needs explicit storage and recovery planning.

```text
tablespace recorded
   != destination path exists
   != permissions correct
   != capacity sufficient
   != target topology compatible
```

## 9. Destination and Failure Domains
The destination must be large enough, writable, monitored, protected, encrypted where required, and governed by retention.

```text
only backup copy + source failure domain = unacceptable DR dependency
```
Maintain appropriately independent recovery copies according to policy.

## 10. Compression and Resource Control
Compression can reduce storage/network consumption while increasing CPU or elapsed time. Define backup windows, I/O/network budgets, throughput expectations, monitoring thresholds, and escalation/abort conditions.

## 11. PostgreSQL 18 Incremental Physical Backups
PostgreSQL 18 supports incremental physical backup workflows. An incremental backup depends on prior backup state and is not automatically an independently recoverable full backup.

```text
Full F0
  ↓
Incremental I1
  ↓
Incremental I2
  ↓
pg_combinebackup
  ↓
reconstructed full backup
  ↓
recovery
```

```text
incremental backup exists != independently recoverable backup
```

Retention must understand the dependency graph before deleting any predecessor.

## 12. Incremental Retention Safety
```text
backup age alone != safe deletion decision

retention
+ dependency graph
+ recovery policy
= safe deletion decision
```
Never delete a full or incremental artifact until downstream dependencies and approved recovery points have been evaluated.

## 13. `pg_combinebackup`
`pg_combinebackup` reconstructs a full backup from a compatible incremental chain. Use preflight/dry-run capability where appropriate before creating output.

Hard-link reconstruction (`--link`) requires special care:

```text
input files ↔ hard links ↔ combined output
```

Mutation of linked files can affect backup independence. Do not make hard-link mode the default without an architecture that explicitly accounts for those semantics.

Tablespace mappings must also be designed for the recovery target.

## 14. Backup Manifest
A backup manifest provides structured evidence about the backup, including file metadata/checksums as configured and WAL-related information.

```text
manifest exists != recovery succeeds
```

Protect the manifest as part of the recovery system.

## 15. `pg_verifybackup`
Use `pg_verifybackup` as an integrity-validation gate for supported PostgreSQL base backups.

```text
backup created
    ↓
manifest available
    ↓
pg_verifybackup
    ↓
integrity evidence
```

Integrity validation still does not replace a restore rehearsal. PostgreSQL 18 verification behavior differs by backup representation; procedures must use options appropriate to plain/tar and compression choices.

## 16. Progress Monitoring
PostgreSQL exposes active base-backup progress through `pg_stat_progress_basebackup`. Production monitoring should use server-side progress evidence in addition to client logs.

## 17. Capacity Planning
Estimate:
```text
PGDATA
+ tablespaces
+ WAL allowance
+ metadata/manifest
+ temporary workspace
+ incremental reconstruction workspace
+ retention copies
+ growth
+ safety margin
```

## 18. Version Compatibility
Physical backups are tied to PostgreSQL's physical storage format. Record source server version, client version, recovery target version, platform constraints, and software/extension prerequisites. Do not use a physical base backup as an unsupported major-version upgrade mechanism.

## 19. Security
Protect backup files, manifests, WAL, encryption keys, replication credentials, storage credentials, backup logs, and sensitive locations. Never embed credentials in commands, URIs, Git, tickets, filenames, or documentation.

## 20. Failure and Promotion States
A failed/incomplete backup must not be promoted as valid.

```text
IN_PROGRESS
    ↓
TRANSFER_COMPLETE
    ↓
INTEGRITY_VALIDATED
    ↓
RECOVERY_TESTED
    ↓
APPROVED_RECOVERY_POINT
```

Preserve the last known-good recovery point according to policy.

## 21. Recovery Evidence Hierarchy
```text
Level 1 — pg_basebackup exited successfully
Level 2 — expected artifacts exist
Level 3 — backup manifest present
Level 4 — pg_verifybackup PASS
Level 5 — incremental chain reconstructable, if applicable
Level 6 — isolated PostgreSQL recovery PASS
Level 7 — database validation PASS
Level 8 — application validation PASS
Level 9 — measured RPO/RTO within approved targets
```

```text
backup success != recovery success
```

## 22. Isolated Recovery Rehearsal
```text
protected backup
      ↓
isolated target
      ↓
reconstruct chain if required
      ↓
integrity validation
      ↓
restore base
      ↓
required WAL/recovery
      ↓
PostgreSQL validation
      ↓
application validation
      ↓
RPO/RTO evidence
```
Routine recovery testing must not use production as the restore target.

## 23. Canonical Acceptance Artifact
Companion file:
```text
labs/basebackup-readiness-check.sql
```

Boundary:
```text
[TUTORIAL-ACCEPTANCE — SAFE-READ]

NO pg_basebackup
NO pg_combinebackup
NO pg_verifybackup
NO backup start/stop
NO replication-slot mutation
NO forced WAL switch
NO forced checkpoint
NO configuration mutation
NO role/pg_hba mutation
NO filesystem or backup-file operations
NO automatic remediation
```

The lab may inspect settings, tablespaces, roles, slots, replication activity, database-size metadata, and `pg_stat_progress_basebackup`.

## 24. What SAFE-READ Cannot Prove
It cannot prove network/authentication readiness, destination capacity, WAL availability, artifact integrity, incremental-chain reconstruction, manifest validity, restore success, application recovery, or RPO/RTO compliance.

```text
SAFE-READ != PHYSICAL-BACKUP-VALIDATED
```

## 25. Key Takeaways
```text
pg_basebackup = physical base backup
online backup != zero impact
base backup != required WAL
incremental backup != independent full backup
retention must understand dependencies
pg_verifybackup != restore test
manifest validation != recovery validation
backup success != recovery success
SAFE-READ != PHYSICAL-BACKUP-VALIDATED
```
