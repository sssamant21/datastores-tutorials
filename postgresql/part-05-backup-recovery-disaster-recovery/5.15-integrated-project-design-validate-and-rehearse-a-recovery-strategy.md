# Part 5.15 — Integrated Project: Design, Validate, and Rehearse a Recovery Strategy

**Part:** 5 — Backup, Recovery & Disaster Recovery  
**Target:** PostgreSQL 18  
**Status:** Revised Final / Canonical Edition  
**Acceptance artifact:** `labs/disaster-recovery-acceptance.sql`

## 1. Project Goal

Design and rehearse an evidence-driven PostgreSQL recovery strategy that integrates the controls developed throughout Part 5: logical and physical backup, WAL archiving, PITR, replication/WAL retention, backup validation, RPO/RTO and capacity planning, HA/DR boundaries, and the production recovery runbook.

The project is complete only when the team can explain **what it can recover, from which failure, to which point, using which artifacts, under whose authority, with what measured result**.

> The companion SQL artifact is `[TUTORIAL-ACCEPTANCE — SAFE-READ]`. It collects PostgreSQL-visible evidence only. The actual restore/DR rehearsal must use an approved isolated/disposable target and architecture-specific procedures.

## 2. Scenario

Assume a production PostgreSQL service supports a critical application.

Design for at least these events:

| Scenario | Expected protection path |
|---|---|
| Primary instance failure | HA/failover where designed |
| Availability-zone failure | HA or DR according to architecture |
| Accidental table deletion | Logical recovery or PITR |
| Bad application batch | PITR/candidate restore |
| Storage corruption | Failover or validated backup recovery |
| Stalled replication consumer | Slot/WAL-retention response |
| Region/site loss | DR |
| Administrative/security compromise | Independent trusted recovery path |
| Delayed discovery of bad data | Retention + historical recovery |

Do not assume one mechanism solves every scenario.

## 8. Backup Trust and Independence

Evaluate whether a recovery source shares:

- production credentials;
- administrative deletion permissions;
- cloud account/project/subscription;
- region;
- KMS key;
- storage control plane;
- automation;
- security compromise domain.

A copy in another bucket is not automatically independent.

## 8A. Recovery Evidence Hierarchy

Treat each layer as distinct:

```text
BACKUP EXISTS
      !=
BACKUP VALIDATED
      !=
RESTORE TESTED
      !=
APPLICATION RECOVERED
      !=
DR REHEARSED
      !=
RECOVERY READY
```

For physical backups, `pg_verifybackup` evidence does not replace an isolated restore
rehearsal, and an isolated restore does not replace application acceptance.

## 9. WAL and PITR Design

Document:

```text
archive mechanism:
archive destination:
archive monitoring:
base-backup relationship:
WAL retention:
timeline-history handling:
PITR target types supported:
last PITR rehearsal:
```

A valid PITR path requires a usable base backup, every required WAL segment, required
timeline history, a reachable recovery target, and a compatible recovery environment.

For PostgreSQL PITR, explicitly document the applicable recovery target semantics,
including `recovery_target_time`, `recovery_target_lsn`, `recovery_target_xid`,
`recovery_target_name`, or `recovery_target = 'immediate'`, plus
`recovery_target_inclusive`, `recovery_target_timeline`, and
`recovery_target_action`. Promotion can create a new timeline; the existence of WAL
alone does not prove that the required timeline chain is complete.

`archive_mode = on` is configuration evidence, not proof of a complete recovery chain.

## 9A. PostgreSQL 18 Evidence Semantics

- Received WAL is not necessarily replayed WAL.
- `pg_last_xact_replay_timestamp()` is not a universal real-time lag metric.
- Replication lag is not direct business RPO evidence.
- Synchronous replication configuration does not prove the expected synchronous
  standby is currently available.
- Replication-slot inactivity does not mean abandonment.
- `max_slot_wal_keep_size = -1` means **UNBOUNDED SLOT WAL RETENTION**.
- WAL/archive statistics must be interpreted relative to their `stats_reset` baseline.
- Missing, stale, or inaccessible evidence is **UNKNOWN**, not zero or PASS.

## 10. HA Design

Document:

- primary/standby topology;
- synchronous/asynchronous behavior;
- expected failover mechanism;
- fencing;
- endpoint/routing behavior;
- replication slots;
- expected lag;
- failover authority;
- last failover rehearsal.

Replication is not an independent historical backup.

## 10A. Recovery Artifact Compatibility

Physical backup recovery must respect PostgreSQL physical-format/major-version
requirements; it is not a general cross-major upgrade mechanism. Logical recovery has
different portability characteristics, but still requires compatibility validation.
Per-database logical dumps do not automatically provide every cluster-global dependency,
such as roles and tablespace definitions.

If PostgreSQL 18 incremental physical backups are used, record the complete
dependency/reconstruction chain rather than treating the newest incremental artifact as
necessarily standalone.

## 12A. Recovery Dependency Package

Maintain protected recovery details for non-default tablespaces (storage destination,
mount, capacity, permissions/ownership, and mapping) and extensions (catalog version,
compatible package/binary, shared libraries, and configuration). The generic SAFE-READ
artifact intentionally minimizes sensitive filesystem/network topology.

## 13A. Rehearsal Authority and Isolation

The default rehearsal target is isolated/disposable. SAFE-READ evidence collection,
isolated recovery rehearsal, and production recovery are separate authority boundaries.
The SQL acceptance artifact never authorizes promotion, restore, routing, slot mutation,
or cutover.

Before starting restored applications, fence side effects including Kafka/CDC,
Debezium, email/SMS, webhooks, payments, external APIs, ETL, search indexing,
application workers, cron/`pg_cron`, Kubernetes CronJobs, and other schedulers.

Restored production data remains production-sensitive and requires appropriate
encryption, IAM, network isolation, audit/logging, retention, and approved cleanup.

## 14. Rehearsal Safety Boundary

The rehearsal must not:

- overwrite production;
- promote a production standby unless the exercise explicitly authorizes it;
- create dual writable authoritative databases;
- delete the only recovery copy;
- manually delete files from `pg_wal`;
- automatically drop/advance replication slots;
- expose restored sensitive data unnecessarily;
- reconnect historical data to live Kafka/CDC/email/webhooks/payments without approval.

## 14A. Split-Brain and Control-Plane Gate

DNS or routing changes are not sufficient fencing. Before enabling a new authoritative
writer, ensure the old writer and alternate write paths are fenced. In Kubernetes or
GitOps-managed systems, coordinate PostgreSQL operators, StatefulSets/PVC automation,
health probes, Argo CD/Flux, Terraform/configuration automation, and other reconcilers.
Any suspension of reconciliation must be authorized, recorded, and restored afterward.

## 22. Failback Rehearsal

Failback must be treated as a separate lifecycle.

Confirm:

1. authoritative source;
2. timeline/divergence state;
3. rebuild/reseed method;
4. replication established;
5. synchronization validated;
6. routing plan;
7. approved switchover;
8. application validation;
9. monitoring;
10. cleanup.

Never assume the former primary remains authoritative.

## 22A. Evidence Classification and Exception Authority

Recovery evidence is **[SENSITIVE OPERATIONAL EVIDENCE]**. Protect database names,
replication/application identifiers, slot names, architecture, backup locations,
failure domains, and recovery procedures. Never store passwords, tokens, private keys,
cloud access keys, credential-bearing connection strings, or KMS key material.

`N/A` requires an explicit architectural reason; not tested is normally `UNKNOWN`.
Material exceptions require risk, owner, remediation, target date, temporary control
where applicable, and authorized acceptance. Technical operators must not silently turn
FAIL into READY WITH EXCEPTIONS.

## 23. Security-Incident Variant

For compromise scenarios:

- preserve forensic evidence;
- determine compromise window;
- identify trusted recovery artifacts;
- validate KMS/IAM/secrets trust;
- rotate compromised credentials where required;
- recover into trusted isolation;
- validate data and security state;
- reconnect only after authorization.

A technically intact backup may still contain compromised data.

## 24. Managed PostgreSQL Variant

Document provider-specific:

- backup/PITR behavior;
- snapshot scope;
- retention;
- cross-region recovery;
- restore destination behavior;
- KMS;
- quotas;
- control-plane dependency;
- failover semantics;
- extension restrictions.

Provider HA labels do not prove organizational DR requirements.

## 28A. Fail-Closed Automation

Recovery automation must stop on ambiguity or failed prerequisites: missing WAL,
unexpected timeline, failed backup verification, ambiguous target, unavailable
KMS/secrets, insufficient capacity, missing extension dependency, or failed application
validation. It must not silently select another recovery source or perform destructive
cleanup.

## 29. Cleanup Gate

After acceptance:

```text
[ ] evidence preserved
[ ] authoritative topology confirmed
[ ] fallback window completed/approved
[ ] temporary restored sensitive data sanitized/destroyed
[ ] temporary infrastructure removed
[ ] temporary IAM/secrets revoked
[ ] temporary routing/firewall changes removed
[ ] backup protection confirmed
[ ] WAL archiving confirmed
[ ] replication confirmed where designed
[ ] monitoring confirmed
[ ] exceptions assigned
[ ] emergency privileges revoked or returned to normal policy
[ ] GitOps/operator reconciliation restored
[ ] alerts active
[ ] protected recovery copy remains available
```

Do not clean up evidence needed for an active security or forensic investigation.

## 29A. Evidence Freshness Triggers

Reassess or rehearse after material changes such as PostgreSQL major upgrades, major
data growth, extension changes, backup-system changes, KMS changes, cloud
account/region changes, HA/DR topology changes, Kubernetes/operator changes, or major
application architecture changes. Historical PASS evidence must not be assumed to
represent a materially changed architecture.

## 33. Key Takeaways

- Recovery readiness is demonstrated, not assumed.
- HA, backup, PITR, and DR solve different failure classes.
- A usable recovery chain includes artifacts, dependencies, infrastructure, credentials, people, and application validation.
- Missing evidence is UNKNOWN.
- Preserve fallback until acceptance.
- Measure RPO/RTO using evidence.
- Protect restored production data.
- Rehearse before a real disaster.
- Track exceptions to closure.
- Recovery readiness decays as architecture changes and evidence ages.
