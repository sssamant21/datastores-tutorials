# Part 3.5 — Building Bronze Ingestion Pipelines

**Track:** Databricks Production Tutorials  
**Part:** 3 — Data Ingestion & ETL/ELT Pipelines  
**Status:** Revised Final / Canonical Edition

## Learning objectives

By the end of this tutorial, you should be able to:

- explain the role of Bronze in a medallion architecture;
- distinguish a landing zone from a Bronze table;
- build a bounded Auto Loader ingestion pipeline into Delta;
- preserve selected file provenance and ingestion time;
- protect checkpoint and schema state;
- explain the scope of Auto Loader file-processing guarantees;
- reason about backlog, rescued data, corrupt input, and replay;
- reconcile source evidence with Bronze results;
- separate ingestion operations from Silver/Gold transformations;
- safely test a Bronze pipeline with synthetic data.

## 1. Bronze is the durable ingestion layer

A production ingestion design needs more than a successful file read.

~~~text
SOURCE SYSTEM
      |
      v
LANDING ZONE
      |
      v
AUTO LOADER
      |
      v
BRONZE
      |
      v
RECONCILIATION
      |
      v
MONITORING
~~~

Bronze should preserve relatively raw source fidelity and enough operational evidence to investigate, replay, and audit ingestion.

~~~text
Bronze
   =
durable source capture
+
provenance
+
ingestion evidence
+
replay/audit foundation
~~~

Bronze is not normally the place for complex joins, business aggregations, final deduplication policy, dimension enrichment, or final analytical models.

## 2. Landing zone is not Bronze

Keep these layers separate:

~~~text
LANDING ZONE
      |
      v
source files

BRONZE
      |
      v
durable lakehouse representation
~~~

A source file successfully arriving in storage does not prove it was successfully ingested into Bronze.

Likewise, a successful Bronze write does not prove every expected source file arrived.

## 3. Canonical architecture

~~~text
SOURCE SYSTEM
      |
      v
LANDING ZONE
UC Volume / governed cloud storage
      |
      v
AUTO LOADER
      |
      +-- discovery
      +-- schema handling
      +-- rescued-data handling
      +-- schema state
      +-- checkpoint
      |
      v
MINIMAL BRONZE ENRICHMENT
      |
      +-- source provenance
      +-- ingestion timestamp
      |
      v
UC MANAGED BRONZE DELTA
      |
      v
RECONCILIATION
      |
      +-- source/file evidence
      +-- Auto Loader state
      +-- outstanding files/bytes
      +-- Bronze rows
      +-- rescued/corrupt evidence
      +-- source control totals
      |
      v
MONITORING

--------- independent operational boundary ---------

BRONZE
   |
   v
SILVER
   |
   v
GOLD
~~~

For the generic architecture, prefer a Unity Catalog managed Delta table for Bronze unless there is a specific requirement for externally managed table storage.

## 4. Bronze transformation policy

Bronze should favor preservation.

Appropriate Bronze additions include:

~~~text
source fields
+
selected provenance
+
ingestion timestamp
+
rescued-data evidence
~~~

Avoid turning Bronze into:

~~~text
complex joins
business aggregations
final business filtering
final deduplication policy
dimension enrichment
final analytical model
~~~

Those concerns primarily belong downstream.

## 5. Synthetic source

The lab uses synthetic healthcare-style events only.

~~~csv
event_id,patient_id,event_type,event_time,facility_code
EVT-001,P001,ADMISSION,2026-09-19T10:00:00Z,FAC-01
EVT-002,P002,DISCHARGE,2026-09-19T10:05:00Z,FAC-01
~~~

Never substitute real production or patient data into this training exercise.

## 6. Centralize configuration

Keep environment-specific paths and targets together.

~~~python
source_path = "/Volumes/training/bronze/patient_activity/source/"

schema_path = (
    "/Volumes/training/bronze/"
    "patient_activity/state/schema/"
)

checkpoint_path = (
    "/Volumes/training/bronze/"
    "patient_activity/state/checkpoint/"
)

target_table = "training.bronze.patient_activity"
~~~

These are illustrative training paths. Adapt them to an approved disposable environment.

Production implementations should externalize environment-specific configuration rather than embed production resource names throughout application logic.

## 7. Read with Auto Loader

~~~python
raw_df = (
    spark.readStream
         .format("cloudFiles")
         .option("cloudFiles.format", "csv")
         .option("cloudFiles.schemaLocation", schema_path)
         .option("header", "true")
         .load(source_path)
)
~~~

Schema inference/evolution decisions should follow the contract and governance model established in Part 3.4.

## 8. Add selected provenance

Preserve the source evidence needed by your operational contract.

~~~python
from pyspark.sql import functions as F

bronze_df = (
    raw_df.select(
        "*",
        F.col("_metadata.file_name")
         .alias("_source_file_name"),
        F.col("_metadata.file_path")
         .alias("_source_file_path"),
        F.col("_metadata.file_size")
         .alias("_source_file_size"),
        F.col("_metadata.file_modification_time")
         .alias("_source_file_modification_time"),
        F.current_timestamp()
         .alias("_ingested_at"),
    )
)
~~~

The names beginning with `_source_` and `_ingested_at` above are tutorial-designed Bronze columns.

Select metadata intentionally instead of treating every available metadata field as a permanent business contract.

## 9. Keep timestamp meanings separate

~~~text
event_time
     |
     +--> when the business event occurred

_source_file_modification_time
     |
     +--> file/object metadata time

_ingested_at
     |
     +--> when Bronze processed the record
~~~

Therefore:

~~~text
event_time
   !=
file modification time
   !=
ingestion time
~~~

This distinction is important for late-arriving data.

## 10. Write to Bronze

For the bounded lab:

~~~python
query = (
    bronze_df.writeStream
             .format("delta")
             .option(
                 "checkpointLocation",
                 checkpoint_path
             )
             .trigger(availableNow=True)
             .toTable(target_table)
)

query.awaitTermination()
~~~

Conceptually:

~~~text
files available
     |
     v
job starts
     |
     v
AvailableNow
     |
     v
process bounded incremental input
     |
     v
persist progress
     |
     v
write Bronze
     |
     v
stop
~~~

## 11. AvailableNow boundary

A completed bounded execution should not be interpreted as proof that no newer source objects currently exist.

~~~text
10:00 execution starts
       |
       +--> process input belonging to that execution

10:03 new file arrives
       |
       +--> can remain for a later execution
~~~

Therefore:

~~~text
AvailableNow SUCCESS
        !=
no new files currently exist
~~~

## 12. Checkpoint and schema state

Two state locations serve different purposes:

~~~text
checkpoint
     |
     +--> streaming/file progress

schemaLocation
     |
     +--> Auto Loader schema state
~~~

Both should be treated as durable operational state.

Do not make checkpoint or schema-state deletion the first response to a failed pipeline.

## 13. Lifecycle-policy hazard

Landing data and operational state can require different retention rules.

~~~text
landing files
     |
     +--> explicit source retention policy

checkpoint/schema state
     |
     +--> durable pipeline state
~~~

Do not apply ordinary landing-zone expiration policies to checkpoint storage without understanding the consequences. Expiring required state can break recovery or force a new ingestion history.

## 14. File-processing guarantee boundary

Auto Loader tracks file processing using checkpoint state, but its file-processing semantics do not imply business uniqueness.

~~~text
file-processing guarantee
        !=
source-row uniqueness
        !=
business-event uniqueness
        !=
arbitrary downstream side-effect guarantee
~~~

Example:

~~~text
file-A.csv
    |
    +--> EVT-100

file-B.csv
    |
    +--> EVT-100
~~~

Both files can be processed correctly while the same logical business event appears twice.

Business-level deduplication policy belongs downstream unless the ingestion contract explicitly requires otherwise.

## 15. Duplicate source files

Consider:

~~~text
file-001.csv
file-001-copy.csv
~~~

If both contain the same business rows:

~~~text
different file identity
        !=
different business event
~~~

Bronze provenance should preserve enough evidence to investigate.

## 16. Late-arriving data

Example:

~~~text
business event:
10:00

file arrives:
14:00

Bronze ingestion:
14:05
~~~

Preserve:

~~~text
event_time   = 10:00
_ingested_at = 14:05
~~~

Do not overwrite business-event semantics with ingestion time.

## 17. Prefer immutable delivered source objects

A safer ingestion contract generally favors:

~~~text
new correction file/version
~~~

over silently overwriting an object already delivered to an ingestion system.

Immutability makes replay, audit, and incident investigation easier to reason about.

## 18. Rescued data is an operational signal

A job can be successful while data quality is deteriorating.

~~~text
job SUCCESS
     +
rescued data increasing
     =
possible ingestion incident
~~~

Where rescued-data handling is used, monitor:

- whether rescued data exists;
- its rate and trend;
- affected source files;
- unexpected fields/types;
- downstream impact.

Do not use rescued data as a permanent dumping ground.

## 19. Corrupt records are a different failure class

~~~text
unexpected field/type/case
        |
        v
rescued-data handling
~~~

versus:

~~~text
structurally malformed input
        |
        v
parser/corrupt-record handling
~~~

Monitor both rather than silently dropping either class.

## 20. Control work per trigger

Where workload control is required, Auto Loader supports options such as:

~~~python
.option("cloudFiles.maxFilesPerTrigger", ...)
~~~

and:

~~~python
.option("cloudFiles.maxBytesPerTrigger", ...)
~~~

Treat these as workload controls, not automatic fixes for every ingestion problem.

Before changing them, determine whether the bottleneck is discovery, schema processing, compute, storage, the Delta sink, or another dependency.

## 21. Inspect file state operationally

Where supported, operators can inspect Auto Loader file state from the checkpoint:

~~~sql
SELECT *
FROM cloud_files_state('<checkpoint-path>');
~~~

This can help answer which files Auto Loader knows about and what state has been recorded.

But:

~~~text
cloud_files_state()
       !=
business reconciliation
~~~

Runtime/version-dependent fields must not be assumed to exist or have identical semantics in every environment.

## 22. Monitor backlog

Useful Auto Loader backlog signals can include:

~~~text
numFilesOutstanding
numBytesOutstanding
processing duration
file-level state
~~~

An organization can also derive operational measures such as oldest outstanding input age when sufficient file-state timestamps are available.

Keep the distinction clear:

~~~text
native metric
     !=
derived operational signal
~~~

A non-zero backlog alone is not necessarily an incident. Trend, age, workload expectations, and service objectives matter.

## 23. Do not scale before diagnosing

~~~text
backlog growing
      |
      +--> arrival spike?
      +--> discovery issue?
      +--> permission problem?
      +--> schema failure?
      +--> configured rate limit?
      +--> sink latency?
      +--> compute saturation?
~~~

Only scale compute when evidence identifies compute as the limiting resource.

## 24. Running is not caught up

~~~text
stream RUNNING
      !=
pipeline caught up
~~~

For example:

~~~text
RUNNING
  +
numFilesOutstanding increasing
  +
numBytesOutstanding increasing
  =
pipeline may be falling behind
~~~

Health requires multiple signals.

## 25. Reconciliation

A production acceptance model should be layered:

~~~text
EXPECTED SOURCE
      |
      v
FILE EVIDENCE
      |
      v
AUTO LOADER STATE
      |
      v
BRONZE
      |
      v
PROVENANCE
      |
      v
RESCUED/CORRUPT EVIDENCE
      |
      v
CONTROL TOTALS
      |
      v
ACCEPT
~~~

A successful job is not enough.

~~~text
JOB SUCCESS
      !=
INGESTION COMPLETE
~~~

## 26. Row counts are one control, not proof

If the producer supplies a reliable row count, comparing it with Bronze can be useful.

But:

~~~text
source rows = Bronze rows
       !=
everything correct
~~~

Depending on the source contract, reconciliation can also use:

- manifests;
- expected file counts;
- checksums;
- source batch IDs;
- producer control totals;
- business keys;
- other domain-specific controls.

## 27. Source retention

Do not make this the generic policy:

~~~text
file processed
      |
      v
delete immediately
~~~

Prefer:

~~~text
processed source
      |
      v
reconciliation
      |
      v
approved retention/archive policy
      |
      v
eventual disposition
~~~

Replay, audit, incident investigation, disaster recovery, or regulatory requirements can require longer retention.

## 28. Separate ingestion and transformation operations

A useful production boundary is:

~~~text
INGESTION PIPELINE

Source
  |
  v
Bronze

--------- operational boundary ---------

TRANSFORMATION PIPELINE

Bronze
  |
  v
Silver
  |
  v
Gold
~~~

A Silver transformation failure should not automatically prevent safe raw-data capture into Bronze.

## 29. Bronze governance

Bronze can contain a higher-fidelity version of sensitive source information than downstream curated datasets.

~~~text
SOURCE
   |
   v
BRONZE
   |
   +--> raw-ish source values
   +--> unexpected fields
   +--> provenance
~~~

Apply least privilege and Unity Catalog governance.

Do not assume Bronze is low risk because it is an early layer.

## 30. Unexpected sensitive fields

Suppose the expected source is:

~~~text
patient_id
event_type
~~~

but a producer unexpectedly adds:

~~~text
ssn
~~~

The field may be technically ingestible while violating the intended governance contract.

~~~text
preserve source fidelity
        !=
ignore governance
~~~

Unexpected sensitive information requires appropriate classification, containment, access review, and escalation.

## 31. Provenance can also be sensitive

Values such as source file names and paths can expose:

- customer names;
- environment identifiers;
- storage layout;
- dates;
- project names;
- operational structure.

Restrict access according to the information they reveal.

## 32. Replay safety

Do not use this as the default recovery pattern:

~~~text
problem
   |
   v
new checkpoint
   |
   v
reprocess everything
~~~

The Bronze target may already contain records.

Before replay:

~~~text
checkpoint state
      +
source state
      +
Bronze state
      |
      v
determine replay consequences
~~~

Then choose a deliberate correction/replay strategy.

## 33. Recovery workflow

~~~text
Bronze ingestion problem
        |
        v
Preserve evidence
        |
        v
Preserve checkpoint
        |
        v
Preserve schema state
        |
        v
Determine last successful progress
        |
        v
Classify failure domain
        |
        +--> source
        +--> discovery
        +--> schema
        +--> state
        +--> processing
        +--> Delta sink
        |
        v
Inspect existing Bronze state
        |
        v
Determine replay consequences
        |
        v
Recover deliberately
        |
        v
Reconcile source -> Bronze
        |
        v
Verify backlog recovery
~~~

## 34. Environment isolation

Each environment owns independent resources:

~~~text
DEV
+-- source
+-- schema state
+-- checkpoint
+-- Bronze

STAGING
+-- source
+-- schema state
+-- checkpoint
+-- Bronze

PROD
+-- source
+-- schema state
+-- checkpoint
+-- Bronze
~~~

Never point a training pipeline at production source or operational state.

## 37. Cleanup

Cleanup must target only exact disposable resources created for this lab.

Do not recursively delete:

- shared Volume roots;
- shared external locations;
- parent checkpoint directories;
- parent schema-state directories;
- catalogs;
- shared schemas;
- unrelated Bronze data.

Cleanup is intentionally outside the canonical SAFE-READ acceptance artifact.

## 38. SAFE-READ acceptance

The companion artifact is:

~~~text
labs/bronze-ingestion-pipeline-check.sql
~~~

and is classified:

~~~text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
~~~

It performs namespace and metadata inspection only.

It intentionally does not:

- start Auto Loader;
- execute `readStream` or `writeStream`;
- start a streaming query;
- ingest files;
- modify checkpoints;
- modify Auto Loader schema state;
- execute DDL or DML;
- modify credentials or external locations;
- modify privileges;
- write/delete storage;
- perform cleanup.

Pipeline-specific `cloud_files_state()` inspection belongs in separately approved operational validation because it requires a real checkpoint identity.

Remember:

~~~text
SAFE-READ PASS
      !=
pipeline ingestion proven
      !=
all expected files processed
      !=
source-to-Bronze reconciliation proven
~~~

## 39. Key takeaways

1. A landing zone and Bronze are different layers.
2. Bronze should preserve source fidelity and operational evidence.
3. Keep Bronze transformations minimal and move business refinement downstream.
4. Add selected provenance intentionally.
5. Keep event, file, and ingestion timestamps semantically separate.
6. Checkpoint and schema state are durable operational state.
7. Protect operational state from inappropriate lifecycle expiration.
8. Auto Loader file-processing semantics do not guarantee business-event uniqueness.
9. `AvailableNow` completion does not prove that no newer files currently exist.
10. A running or successful job does not prove the pipeline is caught up or complete.
11. Monitor backlog, rescued data, corrupt data, and processing behavior.
12. Diagnose backlog before scaling compute.
13. Use file-state inspection as operational evidence, not as a replacement for business reconciliation.
14. Row counts are one reconciliation control, not universal proof.
15. Bronze can contain sensitive raw information and requires strong governance.
16. Replay decisions must consider checkpoint, source, and existing Bronze state.
17. Keep Bronze ingestion operationally separable from Silver/Gold transformations.
18. Preserve evidence first, recover deliberately, and reconcile after recovery.
