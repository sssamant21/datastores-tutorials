# Part 3.4 — Schema Inference & Schema Evolution

**Track:** Databricks Production Tutorials  
**Part:** 3 — Data Ingestion & ETL/ELT Pipelines  
**Status:** Revised Final / Canonical Edition

## Learning objectives

By the end of this tutorial, you should be able to:

- distinguish schema inference, enforcement, evolution, and governance;
- explain how Auto Loader tracks schema information;
- understand inferred schemas, explicit schemas, and schema hints;
- explain the major `cloudFiles.schemaEvolutionMode` behaviors;
- distinguish additive evolution from type widening;
- use rescued data as operational evidence;
- distinguish rescued-data conditions from structurally corrupt records;
- recognize type drift, case drift, missing columns, and rename ambiguity;
- protect checkpoint and schema state during recovery;
- evaluate downstream impact before approving schema changes;
- safely exercise schema evolution using synthetic data.

## 1. Why schema evolution matters

Production file structures change.

~~~text
DAY 1

event_id
patient_id
event_type
event_time

        |
        v

DAY 30

event_id
patient_id
event_type
event_time
facility_code       <- NEW

        |
        v

DAY 60

event_id
patient_id
event_type
event_time
facility_code
provider_id         <- NEW
~~~

An ingestion system therefore needs an explicit policy for schema change.

The primary production rule is:

~~~text
schema change
      !=
schema approval
~~~

A technical system can detect a field without knowing whether the organization intended, approved, or is permitted to ingest it.

## 2. Four different schema concepts

Do not treat these concepts as synonyms.

~~~text
Schema inference
      |
      +--> What structure and types appear to exist?

Schema enforcement
      |
      +--> Does incoming data satisfy the expected contract?

Schema evolution
      |
      +--> How can the technical schema change over time?

Schema governance
      |
      +--> Which changes should the organization approve?
~~~

A production design usually needs all four perspectives.

## 4. Schema inference

Auto Loader can infer a schema when a complete explicit schema is not supplied.

For formats such as CSV, JSON, and XML, Auto Loader normally infers fields as strings unless column-type inference is enabled.

~~~python
df = (
    spark.readStream
         .format("cloudFiles")
         .option("cloudFiles.format", "csv")
         .option("cloudFiles.schemaLocation", schema_path)
         .option("header", "true")
         .load(source_path)
)
~~~

To request sampled column-type inference:

~~~python
.option("cloudFiles.inferColumnTypes", "true")
~~~

Keep this distinction visible:

~~~text
Auto Loader inference
       !=
ordinary DataFrameReader inference
~~~

Formats that carry schema information, such as Parquet and Avro, can provide native type information to the reader.

## 5. Schema state

When Auto Loader manages schema information, `cloudFiles.schemaLocation` is operational state.

~~~text
schemaLocation
      |
      +--> tracked schema information
      +--> evolution state/history
      +--> recovery evidence
~~~

Therefore:

~~~text
schemaLocation != temporary cache
~~~

Do not delete it merely because a pipeline encounters a schema-related failure.

## 6. Inferred versus explicit schemas

### Inferred schema

~~~python
df = (
    spark.readStream
         .format("cloudFiles")
         .option("cloudFiles.format", "csv")
         .option("cloudFiles.schemaLocation", schema_path)
         .load(source_path)
)
~~~

### Explicit schema

~~~python
from pyspark.sql.types import (
    StructType,
    StructField,
    StringType,
    TimestampType,
)

schema = StructType([
    StructField("event_id", StringType(), False),
    StructField("patient_id", StringType(), True),
    StructField("event_type", StringType(), True),
    StructField("event_time", TimestampType(), True),
])

df = (
    spark.readStream
         .format("cloudFiles")
         .option("cloudFiles.format", "csv")
         .schema(schema)
         .load(source_path)
)
~~~

An explicit schema provides a stronger technical contract, but it does not guarantee that the producer is correct.

## 7. Default evolution behavior

A critical distinction is:

~~~text
Auto Loader inferred schema
          |
          v
default evolution:
addNewColumns
~~~

versus:

~~~text
explicit .schema(...)
          |
          v
default evolution:
none
~~~

Do not assume that every Auto Loader pipeline has the same schema-evolution default.

Ordinary `addNewColumns` is not used directly with a fully explicit stream schema. When selected expected types are needed while retaining inference/evolution behavior, schema hints can provide a better fit.

## 8. Schema hints

Schema hints provide partial knowledge without replacing all inference.

~~~python
df = (
    spark.readStream
         .format("cloudFiles")
         .option("cloudFiles.format", "csv")
         .option("cloudFiles.schemaLocation", schema_path)
         .option(
             "cloudFiles.schemaHints",
             "event_time TIMESTAMP, patient_id STRING"
         )
         .load(source_path)
)
~~~

Conceptually:

~~~text
fully inferred
      |
      +---- schema hints ----+
                             |
                             v
                      selected expectations

fully explicit
      |
      +--> complete supplied schema
~~~

A hint is not simply permission to cast arbitrary source values. Incompatible values can still require rescue or failure handling.

## 9. Schema evolution modes

Relevant evolution behaviors include:

~~~text
cloudFiles.schemaEvolutionMode

+-- addNewColumns
+-- addNewColumnsWithTypeWidening
+-- rescue
+-- failOnNewColumns
+-- none
~~~

The correct choice depends on the source contract and governance requirements.

## 10. addNewColumns

For an inferred schema, additive evolution can behave conceptually as:

~~~text
new column detected
       |
       v
tracked schema updated
       |
       v
new column appended
       |
       v
stream can stop
       |
       v
restart
       |
       v
continue with evolved schema
~~~

A stream stopping during an expected additive evolution event is not necessarily an infrastructure failure.

However:

~~~text
schema evolved
     !=
schema approved
~~~

Automation can restart execution; it cannot determine business intent.

## 11. Type widening

Ordinary `addNewColumns` is about additive schema evolution. It does not generally mean that existing column types automatically change.

A newer mode, `addNewColumnsWithTypeWidening`, supports compatible type widening in supported Databricks Runtime environments.

Conceptually:

~~~text
INT
 |
 v
LONG
~~~

may be widenable where supported.

Treat this capability according to the current runtime/support status. Do not assume it is available or appropriate in every workspace.

And:

~~~text
technically widenable
       !=
business-compatible
~~~

Downstream tables, transformations, BI models, APIs, validation rules, and exports can still be affected.

## 12. rescue

A rescue-oriented policy preserves unexpected information rather than automatically changing the structured schema.

~~~text
unexpected field/type
       |
       v
_rescued_data
       |
       v
pipeline can continue
       |
       v
evidence retained
       |
       v
investigate
~~~

Rescued data is operational evidence, not a dumping ground.

## 13. failOnNewColumns

A strict source contract may intentionally stop when a new field appears.

~~~text
unexpected column
       |
       v
FAIL
       |
       v
preserve evidence
       |
       v
investigate contract
       |
       v
approve / reject / remediate
~~~

A controlled failure can be safer than uncontrolled evolution.

## 14. none

With evolution mode `none`:

~~~text
new column
     |
     v
schema does not evolve
     |
     v
stream does not fail merely because
the new column appeared
~~~

But:

~~~text
none != rescue
~~~

Unexpected data is retained through rescued-data handling only when that handling is appropriately configured.

Therefore:

~~~text
pipeline succeeded
      !=
all source information preserved
~~~

## 15. Rescued data

The rescued-data column can preserve evidence associated with conditions such as:

- a column absent from the expected schema;
- a type mismatch;
- a case mismatch.

The evidence can also help associate unexpected content with its source file.

Operationally:

~~~text
unexpected input
      |
      v
_rescued_data
      |
      +--> what was unexpected?
      +--> where did it originate?
      |
      v
investigate
~~~

Monitor rescued-data volume and rate.

~~~text
stream = RUNNING
      +
rescued data increasing
      =
possible data-quality incident
~~~

## 16. Rescued data versus corrupt records

Do not combine these failure classes.

~~~text
unexpected field/type/case
        |
        v
rescued-data handling
~~~

versus:

~~~text
structurally malformed CSV/JSON
        |
        v
parser/corrupt-record handling
~~~

A type mismatch is not automatically the same thing as a structurally malformed record.

## 17. Type drift

A column can keep the same name while its source representation changes.

~~~text
DAY 1

patient_id = "P100"

DAY 30

patient_id = 100
~~~

Or:

~~~text
DAY 1

event_time = 2026-09-19T10:00:00Z

DAY 30

event_time = 09/19/2026 10:00 AM
~~~

Therefore:

~~~text
same column name
       !=
same data contract
~~~

## 18. Case drift

Examples:

~~~text
patient_id
Patient_ID
PATIENT_ID
~~~

can represent upstream contract drift.

Where applicable, reader case behavior can be configured with `readerCaseSensitive`, but changing case behavior merely to make a pipeline run can hide a producer problem.

Treat case policy as a contract decision.

## 19. Missing columns

Suppose yesterday's input contained:

~~~text
event_id
patient_id
facility_code
~~~

and today's contains:

~~~text
event_id
patient_id
~~~

Do not automatically conclude that `facility_code` was intentionally retired.

Possible causes include:

- an intentional producer change;
- an upstream defect;
- a partial export;
- a wrong dataset;
- an unexpected producer version;
- a deployment problem.

~~~text
missing field
     !=
approved deletion
~~~

## 20. Rename ambiguity

Consider:

~~~text
facility_code
      |
      v
facility_id
~~~

The ingestion system cannot safely determine that this is a business rename.

Technically it can appear as:

~~~text
old field stops arriving
+
new field appears
~~~

Only the producer/business contract can establish whether the meanings are equivalent.

## 21. Sensitive-column guardrail

Automatic additive evolution also has a security/governance dimension.

~~~text
expected:
patient_id
event_type

unexpected:
patient_id
event_type
ssn
~~~

A new field might be technically ingestible while violating the intended data contract.

~~~text
schema-compatible
      !=
security-approved
~~~

Unexpected sensitive fields require appropriate classification, access control, escalation, and remediation.

## 22. Variant for highly unpredictable structures

Structured schema evolution is not always the best solution.

Conceptually:

~~~text
stable contract
      |
      v
structured schema

controlled additive changes
      |
      v
schema evolution

highly unpredictable semi-structured data
      |
      v
consider Variant
~~~

Variant design is an advanced topic and is not developed further in this tutorial.

## 23. Downstream blast radius

Schema changes can propagate beyond Bronze.

~~~text
SOURCE
  |
  v
BRONZE
  |
  v
SILVER
  |
  v
GOLD
  |
  +--> BI
  +--> APIs
  +--> ML
  +--> exports
~~~

A Bronze pipeline successfully accepting a change does not prove downstream compatibility.

Before approving a production schema change, determine affected consumers.

## 24. Decision model

~~~text
Do we know the source contract?
          |
     +----+----+
     |         |
    YES        NO
     |         |
 explicit    inference
 schema        |
     |         +--> controlled additive changes
     |         |          |
     |         |          v
     |         |    addNewColumns
     |         |
     |         +--> strict producer contract
     |         |          |
     |         |          v
     |         |    failOnNewColumns
     |         |
     |         +--> unpredictable fields
     |                    |
     |                    v
     |              rescue / consider Variant
     |
     +--> partial type knowledge?
                  |
                  v
             schema hints
~~~

This is a starting decision model, not a substitute for organizational governance.

## 25. Hands-on lab — observe schema change

> **STATE-CHANGING TRAINING LAB:** Run only in an approved disposable environment.

Use synthetic data only.

### Lab architecture

~~~text
RUN 1
baseline.csv
      |
      v
initial schema
      |
      v
Bronze baseline

RUN 2
additive-change.csv
      |
      v
facility_code appears
      |
      v
observe evolution behavior

RUN 3
unexpected-data.csv
      |
      v
unexpected/type-drift data
      |
      v
observe rescue behavior
~~~

The goal is to understand:

~~~text
schema evolution
      !=
rescued data
      !=
corrupt records
~~~

### Pre-flight

~~~text
[ ] Correct workspace
[ ] Correct catalog/schema
[ ] Synthetic data only
[ ] Approved training Volume
[ ] Unique source path
[ ] Unique schemaLocation
[ ] Unique checkpointLocation
[ ] Disposable Bronze target
[ ] No production state
[ ] No embedded credentials
~~~

### Run 1 — establish a baseline

Example `baseline.csv`:

~~~csv
event_id,patient_id,event_type,event_time
EVT-001,P001,ADMISSION,2026-09-19T10:00:00Z
EVT-002,P002,DISCHARGE,2026-09-19T10:05:00Z
~~~

Run the approved Auto Loader `AvailableNow` pipeline and capture:

- source file name;
- observed Bronze schema;
- row count;
- selected provenance;
- checkpoint identity;
- schema-state identity.

### Run 2 — introduce an additive column

Example `additive-change.csv`:

~~~csv
event_id,patient_id,event_type,event_time,facility_code
EVT-003,P003,LAB_RESULT,2026-09-19T10:10:00Z,FAC-01
EVT-004,P004,TRANSFER,2026-09-19T10:15:00Z,FAC-02
~~~

Run the same pipeline using the same approved checkpoint and schema state.

Observe:

~~~text
baseline schema
      |
      v
new source file
      |
      v
facility_code detected
      |
      v
configured evolution behavior
      |
      v
tracked schema/result
~~~

If the selected evolution mode intentionally stops the stream, capture that evidence before restarting.

### Run 3 — introduce unexpected data

Create a synthetic input that demonstrates a controlled mismatch appropriate for the configured schema.

Observe:

- whether the structured field is populated;
- whether unexpected information appears in rescued data;
- the associated source-file evidence;
- whether the stream continues or fails according to policy.

Do not intentionally place real sensitive data into the lab.

### Reconcile

Capture:

~~~text
source files
     |
     v
observed source schemas
     |
     v
tracked schema changes
     |
     v
rescued/corrupt evidence
     |
     v
Bronze rows
     |
     v
expected outcome
~~~

A successful streaming query is not sufficient reconciliation evidence.

## 26. Recovery workflow

For a schema-related incident:

~~~text
Schema-related failure
        |
        v
Preserve checkpoint
        |
        v
Preserve schema state
        |
        v
Identify triggering file
        |
        v
Compare expected vs observed schema
        |
        v
Classify
        |
        +--> new field
        +--> type drift
        +--> case drift
        +--> missing field
        +--> rename ambiguity
        +--> malformed record
        |
        v
Determine business intent
        |
        v
Approve / reject / remediate
        |
        v
Recover deliberately
        |
        v
Reconcile
        |
        v
Validate downstream consumers
~~~

Never make checkpoint/schema-state deletion the default response to a schema problem.

## 27. Rollback considerations

A schema change may already have affected persistent Delta metadata or downstream consumers.

Therefore:

~~~text
bad schema change
      |
      X
delete schema state
~~~

is not a complete rollback strategy.

Instead determine:

1. which source object introduced the change;
2. which schema state was recorded;
3. which records were already ingested;
4. whether Bronze metadata/data changed;
5. which downstream objects consumed the change;
6. whether correction, replay, migration, or downstream remediation is required.

Then reconcile after recovery.

## 28. Environment isolation

Each environment owns its state.

~~~text
DEV
+-- source
+-- schema state
+-- checkpoint
+-- target

STAGING
+-- source
+-- schema state
+-- checkpoint
+-- target

PROD
+-- source
+-- schema state
+-- checkpoint
+-- target
~~~

Do not point training or development pipelines at production state.

## 29. SAFE-READ acceptance

The companion artifact is:

~~~text
labs/schema-inference-evolution-check.sql
~~~

and is classified:

~~~text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
~~~

It performs metadata/read-only checks only.

It intentionally does not:

- start Auto Loader;
- start a streaming query;
- ingest files;
- modify checkpoint state;
- modify schema state;
- execute DDL or DML;
- change credentials or external locations;
- change privileges;
- write/delete cloud storage;
- perform cleanup.

Remember:

~~~text
SAFE-READ PASS
      !=
schema evolution proven
      !=
rescued data validated
      !=
source-to-Bronze reconciliation proven
~~~

Those require separately approved state-changing execution and evidence.

## 30. Key takeaways

1. Schema inference, enforcement, evolution, and governance solve different problems.
2. Auto Loader schema state is operational state, not disposable cache.
3. CSV/JSON/XML inference normally starts with string fields unless type inference is requested.
4. Inferred and fully explicit schemas have different default evolution behavior.
5. Schema hints provide controlled partial expectations.
6. `addNewColumns` supports additive evolution but does not mean arbitrary existing types are widened.
7. Type widening is a separate capability and must be validated for the target runtime.
8. Rescue mode preserves unexpected information for investigation.
9. `failOnNewColumns` can intentionally enforce a strict producer contract.
10. `none` is not the same as rescue.
11. Rescued data and structurally corrupt records are different conditions.
12. Type drift and case drift are source-contract changes worth investigating.
13. Missing columns and apparent renames cannot be interpreted safely without business context.
14. A technically acceptable new column can still violate security or governance policy.
15. Successful Bronze evolution does not prove downstream compatibility.
16. Preserve checkpoint and schema state during incidents.
17. Recover deliberately and reconcile after every material schema incident.
