# Part 3.6 — Silver Transformation Pipelines

**Track:** Databricks Production Tutorials  
**Part:** 3 — Data Ingestion & ETL/ELT Pipelines  
**Status:** Revised Final / Canonical Edition

## Learning objectives

By the end of this tutorial, you should be able to:

- explain the operational boundary between Bronze and Silver;
- create an explicit Silver contract instead of inheriting every Bronze field;
- preserve raw values while safely converting data types;
- normalize values without changing business meaning;
- classify invalid data instead of silently dropping it;
- design a controlled quarantine/rejection path;
- explain why deduplication requires a business contract;
- understand how watermarks affect streaming correctness;
- protect checkpoint/state compatibility when stateful logic changes;
- design replay and idempotency deliberately;
- reconcile every meaningful Bronze input outcome;
- keep transformation validation separate from SAFE-READ acceptance.

## 1. Bronze and Silver have different responsibilities

Bronze primarily preserves source fidelity and ingestion evidence. Silver turns that evidence into validated, standardized, domain-usable data.

~~~text
BRONZE
   |
   v
EXPLICIT PROJECTION
   |
   v
PRESERVE RAW VALUES
   |
   v
SAFE TYPE CONVERSION
   |
   v
NORMALIZATION
   |
   v
QUALITY CLASSIFICATION
   +-------------------+
   |                   |
   v                   v
 VALID               INVALID
   |                   |
   v                   v
DETERMINISTIC       QUARANTINE
DEDUPLICATION           |
   |                 investigation
   |                 remediation
   |                 replay
   v
SILVER
   |
   v
RECONCILIATION
   |
   v
MONITORING
~~~

The governing principle is:

~~~text
Bronze = preserve
Silver = validate + standardize + resolve
~~~

Silver can also integrate related validated datasets when the domain design requires joins. Heavy business-facing aggregation normally belongs in Gold, while Silver should retain a detailed validated representation.

## 2. Synthetic Bronze input

The hands-on lab uses synthetic data only.

~~~text
event_id | patient_id | event_type | event_time             | facility_code
---------+------------+------------+------------------------+--------------
EVT-001  | P001       | ADMISSION  | 2026-09-19T10:00:00Z   | FAC-01
EVT-002  | P002       | discharge  | 2026-09-19T10:05:00Z   | FAC-01
EVT-003  | P003       | TRANSFER   | invalid-time           | FAC-02
EVT-004  | NULL       | ADMISSION  | 2026-09-19T10:15:00Z   | FAC-02
EVT-005  | P005       | LAB_RESULT | 2026-09-19T10:20:00Z   | FAC-03
EVT-001  | P001       | ADMISSION  | 2026-09-19T10:00:00Z   | FAC-01
~~~

The intended accounting is:

~~~text
6 Bronze records
|
+-- 3 valid unique
+-- 1 malformed timestamp
+-- 1 missing required value
+-- 1 duplicate business event
~~~

The duplicate is deliberate so that the lab can demonstrate outcome accounting.

## 3. Create an explicit Silver contract

Avoid making every Bronze field part of the Silver contract by default.

~~~python
silver_input = bronze_df.select(
    "event_id",
    "patient_id",
    "event_type",
    "event_time",
    "facility_code",
    "_source_file_name",
    "_ingested_at",
)
~~~

This protects Silver from accidental schema propagation.

~~~text
Bronze schema evolves
       |
       v
Silver explicit contract
       |
       v
review
       |
       v
approved Silver change
~~~

Therefore:

~~~text
Bronze evolution
      !=
Silver approval
~~~

## 4. Preserve the raw value before conversion

When a value requires interpretation, preserving its original representation makes failures explainable.

~~~python
from pyspark.sql import functions as F

typed_df = (
    silver_input
    .withColumnRenamed(
        "event_time",
        "event_time_raw"
    )
    .withColumn(
        "event_timestamp",
        F.try_to_timestamp("event_time_raw")
    )
)
~~~

The conceptual contract is:

~~~text
event_time_raw
      +
event_timestamp
~~~

A malformed source value can then remain observable while its typed representation becomes null and is handled by quality classification.

## 5. Normalize only where the contract permits it

For values whose contract defines case and surrounding whitespace as non-semantic:

~~~python
normalized_df = (
    typed_df
    .withColumn(
        "event_type",
        F.upper(F.trim(F.col("event_type")))
    )
    .withColumn(
        "facility_code",
        F.upper(F.trim(F.col("facility_code")))
    )
)
~~~

This can normalize values such as:

~~~text
" admission "
"Admission"
"ADMISSION"
~~~

to:

~~~text
ADMISSION
~~~

But:

~~~text
technical normalization
       !=
permission to change business meaning
~~~

Do not invent equivalence rules merely because two strings look similar.

## 6. Safe conversion is not the end of validation

A tolerant conversion function can prevent a malformed value from failing the entire transformation, but a null result still needs an explicit quality decision.

~~~text
malformed value
      |
      v
safe conversion
      |
      v
NULL
      |
      v
quality classification
~~~

Otherwise a visible parsing error can become silent downstream data loss.

## 7. Classify quality outcomes

One simple training pattern is:

~~~python
classified_df = normalized_df.withColumn(
    "_quality_status",
    F.when(
        F.col("event_id").isNull(),
        F.lit("INVALID_EVENT_ID")
    )
    .when(
        F.col("patient_id").isNull(),
        F.lit("INVALID_PATIENT_ID")
    )
    .when(
        F.col("event_timestamp").isNull(),
        F.lit("INVALID_EVENT_TIME")
    )
    .otherwise(
        F.lit("VALID")
    )
)
~~~

The architecture is:

~~~text
record
   |
   v
quality decision
   |
   +--> VALID
   |
   +--> explicit rejection reason
~~~

The rule is:

~~~text
invalid
   !=
invisible
~~~

## 8. Split accepted and rejected data

~~~python
valid_df = classified_df.filter(
    F.col("_quality_status") == "VALID"
)

rejected_df = classified_df.filter(
    F.col("_quality_status") != "VALID"
)
~~~

Do not use a filter that silently discards bad rows without measuring or retaining the rejected population.

## 9. Quarantine is an operational workflow

A quarantine or rejection table is not useful merely because it exists.

~~~text
QUARANTINE
    |
    v
owner
    |
    v
reason
    |
    v
age
    |
    v
remediation policy / SLA
    |
    v
correct / replay / approved disposition
~~~

Monitor at least:

- rejected count;
- rejection rate;
- rejection reason;
- affected source;
- age;
- trend.

Rejected data can contain sensitive raw values and must be governed accordingly.

## 10. Deduplication needs a business contract

Avoid treating this as universally correct:

~~~python
dropDuplicates(["event_id"])
~~~

A production design requires:

~~~text
business key
    +
duplicate definition
    +
ordering rule
    +
late-arrival policy
    +
state-retention boundary
    |
    v
deterministic result
~~~

Two records with the same key do not automatically tell you which record represents business truth.

## 11. Event time is not ingestion time

Consider:

~~~text
record A
event_timestamp = 09:00
_ingested_at    = 14:00

record B
event_timestamp = 11:00
_ingested_at    = 12:00
~~~

Therefore:

~~~text
latest ingestion
      !=
latest business truth
~~~

Choose a winner only according to the documented source/business contract.

## 12. Watermark-aware streaming deduplication

For streaming workloads on a supported Databricks Runtime, a business-approved time-bounded deduplication design can use a watermark and `dropDuplicatesWithinWatermark`.

~~~python
deduped_df = (
    valid_df
    .withWatermark(
        "event_timestamp",
        "<business-approved-threshold>"
    )
    .dropDuplicatesWithinWatermark(
        ["event_id"]
    )
)
~~~

The API is runtime-dependent; validate the runtime used by the target environment before adopting the pattern.

Do not copy an arbitrary watermark value from this tutorial.

## 13. A watermark is a correctness boundary

~~~text
watermark
    !=
performance-only setting
~~~

Instead:

~~~text
producer behavior
      +
maximum expected lateness
      +
duplicate-arrival characteristics
      +
business SLA
      |
      v
watermark threshold
      |
      v
state retention
      |
      v
late-data behavior
~~~

A threshold that is too short can allow a legitimately late duplicate to arrive after the relevant state has been removed.

Changing a watermark is therefore a correctness-affecting production change.

## 14. Stateful checkpoint compatibility

Changing stateful logic can change the checkpoint/state contract.

Do not use:

~~~text
change deduplication logic
        |
        v
blindly reuse checkpoint
~~~

and do not use:

~~~text
problem
   |
   v
delete checkpoint
~~~

as routine recovery.

Instead:

~~~text
transformation change
       |
       v
identify stateful impact
       |
       v
review checkpoint compatibility
       |
       v
choose migration/restart strategy
       |
       v
validate
       |
       v
reconcile
~~~

## 15. Silver schema governance

Suppose Bronze previously contained:

~~~text
facility_code
~~~

and later contains:

~~~text
facility_id
~~~

Do not automatically infer a rename.

The change could represent:

- a true rename;
- a different identifier;
- migration overlap;
- producer defect;
- two separate business concepts.

Use:

~~~text
Bronze change
      |
      v
Silver contract mismatch
      |
      v
review
      |
      v
business/schema decision
      |
      v
controlled Silver change
~~~

## 16. Preserve transformation traceability

Operationally important transformations should retain enough evidence to identify:

~~~text
Bronze/source identity
transformation version
quality-rule version
deduplication policy
execution identity
target version
~~~

The exact implementation is environment-specific. The requirement is that responders can answer:

> Which transformation logic produced this Silver data?

## 17. Replay from Bronze

A strong design aims for:

~~~text
Bronze history
     +
known transformation version
     +
quality rules
     +
deduplication contract
     |
     v
rebuild Silver
~~~

This is one reason Bronze should not be casually deleted during a Silver incident.

## 18. Replay must consider the existing target

Avoid:

~~~text
reprocess Bronze
      |
      v
blind append
      |
      v
duplicate Silver
~~~

The replay strategy depends on the target model.

~~~text
immutable events
     |
     +--> controlled append/dedup strategy

current-state entities
     |
     +--> controlled upsert/MERGE strategy
~~~

Detailed MERGE design is covered later in Part 3.11.

## 19. Idempotency is a design property

Do not assume:

~~~text
Structured Streaming
        =
business idempotency
~~~

Instead:

~~~text
source semantics
      +
transformation logic
      +
checkpoint/state
      +
target write semantics
      +
deduplication contract
      |
      v
idempotent logical outcome
~~~

Rerunning a pipeline safely is therefore an architectural requirement, not simply a runtime feature.

## 20. Reconcile every meaningful outcome

The canonical accounting equation is:

~~~text
BRONZE INPUT
      =
SILVER ACCEPTED
+
INVALID / QUARANTINED
+
DUPLICATE LOSERS
+
OTHER EXPLICITLY CLASSIFIED OUTCOMES
~~~

For the lab:

~~~text
Bronze input       6
Silver accepted    3
Rejected           2
Duplicate loser    1
                  ---
Accounted          6
~~~

So:

~~~text
6 = 3 + 2 + 1
~~~

This explains where records went. It does not by itself prove semantic correctness.

## 21. Reconciliation is more than row counts

Depending on the source contract, stronger evidence can include:

- business keys;
- source batch identifiers;
- source partitions;
- event-time ranges;
- checksums or producer control totals;
- quality-reason distributions;
- duplicate classifications;
- lineage.

Therefore:

~~~text
counts match
    !=
data proven correct
~~~

## 22. Separate Silver failure domains

~~~text
BRONZE
  |
  v
PROJECTION
  +--> missing/renamed field
  |
  v
CASTING
  +--> malformed value
  |
  v
NORMALIZATION
  +--> semantic mapping issue
  |
  v
QUALITY
  +--> contract violation
  |
  v
DEDUPLICATION
  +--> key/order/watermark/state issue
  |
  v
SILVER WRITE
  +--> permissions
  +--> schema
  +--> Delta/storage failure
~~~

Identify the failed layer before remediation.

## 23. Silver incident recovery

~~~text
Silver failure
      |
      v
PRESERVE BRONZE
      |
      v
capture failing input/evidence
      |
      v
identify failure domain
      |
      v
fix transformation/rule
      |
      v
review state/replay consequences
      |
      v
reprocess deliberately
      |
      v
reconcile
      |
      v
accept
~~~

Do not mutate or delete Bronze evidence merely to make a Silver job succeed.

## 24. Sensitive-data boundary

Silver can intentionally reduce exposure compared with Bronze:

~~~text
Bronze
  |
  +--> raw sensitive attributes
  |
  v
approved transformation
  |
  v
Silver
  +--> approved subset/protected representation
~~~

But Silver is not inherently non-sensitive. Apply least privilege and Unity Catalog governance according to the resulting dataset.

Do not use ad-hoc masking as a substitute for approved security controls.

## 27. Cleanup

Cleanup must target only exact disposable resources created by the lab.

Do not broadly delete:

- production or shared Bronze data;
- catalogs;
- shared schemas;
- shared Volume roots;
- external locations;
- unrelated Silver tables;
- shared checkpoints/state;
- security configuration.

Cleanup is intentionally outside the canonical SAFE-READ artifact.

## 28. SAFE-READ acceptance

The companion artifact is:

~~~text
labs/silver-transformation-pipeline-check.sql
~~~

and is classified:

~~~text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
~~~

It performs namespace and metadata inspection only.

It intentionally does not:

- execute transformations;
- create or modify Bronze/Silver/quarantine tables;
- insert, update, delete, or merge records;
- start a streaming query;
- manipulate checkpoints or state;
- modify schemas;
- change credentials or external locations;
- modify privileges;
- write/delete storage;
- perform cleanup.

Remember:

~~~text
SAFE-READ PASS
      !=
transformation correctness proven
      !=
quality rules validated
      !=
deduplication correctness proven
      !=
watermark correctness proven
      !=
Bronze-to-Silver reconciliation proven
~~~

## 29. Key takeaways

1. Bronze preserves evidence; Silver validates and standardizes it.
2. Silver needs an explicit schema/column contract.
3. Preserve raw values when type interpretation can fail.
4. Safe conversion still requires explicit quality classification.
5. Invalid data must remain observable.
6. Quarantine requires ownership, monitoring, and remediation.
7. Deduplication requires a documented business key and deterministic policy.
8. Latest ingestion time is not automatically latest business truth.
9. Watermarks affect correctness, not only performance.
10. Stateful transformation changes require checkpoint compatibility review.
11. Bronze schema evolution does not automatically approve Silver evolution.
12. Transformation versions and quality rules should be traceable.
13. Replay must account for existing Silver state.
14. Idempotency is a pipeline design property.
15. Every meaningful input outcome should be reconciled.
16. Matching row counts alone do not prove correctness.
17. Preserve Bronze during Silver incidents.
18. SAFE-READ metadata validation does not prove transformation correctness.
