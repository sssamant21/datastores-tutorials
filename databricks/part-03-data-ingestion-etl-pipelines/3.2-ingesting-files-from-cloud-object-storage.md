# Part 3.2 — Ingesting Files from Cloud Object Storage

**Track:** Databricks Production Tutorials  
**Part:** 3 — Data Ingestion & ETL/ELT Pipelines  
**Status:** Revised Final / Canonical Edition

## Learning objectives

By the end of this tutorial, you should be able to:

- explain how cloud object storage participates in Databricks ingestion;
- recognize S3, ADLS, and GCS path concepts without embedding cloud credentials;
- distinguish a Unity Catalog storage credential, external location, external volume, and external table;
- use governed paths such as Unity Catalog volumes for training file access;
- perform a bounded file read with an explicit schema;
- understand SQL `read_files` at a high level;
- capture selected file provenance from `_metadata`;
- recognize malformed-record, schema, path, permission, and incomplete-delivery failures;
- reconcile source files and records with Bronze results;
- explain why bounded `spark.read` is not a production incremental file-discovery solution.

## 1. Architecture

~~~text
SOURCE SYSTEM
      |
      v
CLOUD OBJECT STORAGE
      |
      +-- AWS S3
      +-- Azure ADLS
      +-- Google Cloud Storage
      |
      v
UNITY CATALOG GOVERNANCE
      |
      +-- Storage Credential
      +-- External Location
      +-- Volume / Governed Path
      |
      v
FILE ACCESS
      |
      +-- spark.read
      +-- read_files
      |

      |

      +-- selected _metadata provenance
      |
      v
BRONZE DELTA
      |
      +-- source data
      +-- ingestion metadata
      +-- reconciliation evidence
~~~

A path being readable does not prove that it is the correct source for the intended environment.

## 2. Cloud storage path concepts

Common provider URI forms include:

~~~text
AWS
s3://bucket/path/

Azure
abfss://container@account.dfs.core.windows.net/path/

GCP
gs://bucket/path/
~~~

These URI forms are useful infrastructure concepts. Production notebooks should not embed provider credentials merely to make them readable.

Prefer governed access patterns approved by the platform team.

## 3. Unity Catalog storage governance

A production design commonly separates identity, governed path, and data object.

~~~text
Cloud identity
      |
      v
Storage credential
      |
      v
External location
      |
      +--> External volume / governed files
      |
      +--> External table location
~~~

Keep these concepts distinct:

~~~text
storage credential != external location
external location  != external table
external location  != external volume
~~~

A storage credential represents an authentication mechanism. An external location associates a governed cloud path with a storage credential. Tables and volumes are higher-level data/file objects governed through Unity Catalog.

Detailed provisioning and cloud IAM configuration belong in administration/security material, not in this ingestion lab.

## 4. Prefer governed training paths

For hands-on training, prefer a Unity Catalog volume already provisioned by an administrator.

A volume path follows this general form:

~~~text
/Volumes/<catalog>/<schema>/<volume>/<path>
~~~

For example:

~~~text
/Volumes/training/bronze/ingestion_lab/patient_activity/
~~~

The example names are illustrative. Never assume that a catalog, schema, volume, or production path exists.

## 5. File formats

Databricks workloads commonly encounter formats such as:

- CSV;
- JSON;
- Parquet;
- Avro;
- ORC;
- text;
- binary files.

Formats do not have identical schema or parsing behavior.

~~~text
file format
    |
    +--> parsing rules
    +--> type information
    +--> schema behavior
    +--> malformed-record options
~~~

A CSV file, for example, does not provide the same embedded type information as a typed format such as Parquet.

## 6. Synthetic source

Use synthetic data only.

Example CSV:

~~~csv
event_id,patient_id,event_type,event_time,facility_code
EVT-001,P001,ADMISSION,2026-09-19T10:00:00Z,FAC-01
EVT-002,P002,DISCHARGE,2026-09-19T10:05:00Z,FAC-02
EVT-003,P003,LAB_RESULT,2026-09-19T10:07:00Z,FAC-01
~~~

These values are fictional and contain no real patient information.

## 7. Explicit schema

Understand the source contract before reading production data.

~~~python
from pyspark.sql.types import (
    StructType,
    StructField,
    StringType,
    TimestampType,
)

schema = StructType([
    StructField("event_id", StringType(), True),
    StructField("patient_id", StringType(), True),
    StructField("event_type", StringType(), True),
    StructField("event_time", TimestampType(), True),
    StructField("facility_code", StringType(), True),
])
~~~

Schema inference can be useful, but it is not schema governance.

## 8. Bounded PySpark file read

With an approved training path:

~~~python
source_path = (
    "/Volumes/training/bronze/"
    "ingestion_lab/patient_activity/"
)

df = (
    spark.read
         .format("csv")
         .option("header", "true")
         .schema(schema)
         .load(source_path)
)

display(df)
~~~

This is a bounded file read.

~~~text
spark.read
    |
    v
read the selected bounded input

spark.read
    !=
production incremental file discovery
~~~

Part 3.3 introduces Auto Loader for incremental file ingestion.

## 9. SQL file access with read_files

Where supported in the runtime and environment, SQL users can query files with `read_files`.

~~~sql
SELECT *
FROM read_files(
  '/Volumes/training/bronze/ingestion_lab/patient_activity/',
  format => 'csv'
);
~~~

This tutorial introduces the pattern only. Production use still requires deliberate schema, parsing, governance, and reconciliation decisions.

## 10. File provenance with _metadata

File-based reads can expose a hidden `_metadata` struct.

Useful fields include:

~~~text
_metadata.file_name
_metadata.file_path
_metadata.file_size
_metadata.file_modification_time
~~~

Select only the fields required by the pipeline.

~~~python
from pyspark.sql import functions as F

df_with_metadata = (
    df.select(
        "*",
        F.col("_metadata.file_name").alias("source_file_name"),
        F.col("_metadata.file_path").alias("source_file_path"),
        F.col("_metadata.file_size").alias("source_file_size"),
        F.col("_metadata.file_modification_time")
         .alias("source_file_modification_time"),
    )
)
~~~

Do not make the entire `_metadata` struct a permanent schema contract merely for convenience. The available metadata structure can evolve.

If the source itself contains a column named `_metadata`, investigate the naming collision rather than assuming the hidden metadata column is being returned.

File paths can also reveal sensitive environment, customer, tenant, or dataset names. Treat captured metadata as operational information.

## 11. Malformed records

Malformed input must not disappear silently.

~~~text
malformed record
       |
       v
preserve evidence
       |
       v
measure
       |
       v
investigate
       |
       v
approved handling
~~~

CSV parsing supports configurable malformed-record behavior. Production pipelines should select behavior deliberately and ensure reconciliation can explain rejected or rescued input.

Do not teach silent dropping of malformed records as a default recovery strategy.

## 12. Source immutability

Prefer an ingestion contract where delivered source objects are immutable.

~~~text
original file
      |
already processed
      |
silent overwrite
      |
replay/reconciliation ambiguity
~~~

If source corrections are required, define how corrected or versioned files are delivered and how downstream processing identifies them.

## 13. Directory layout

Source systems sometimes organize data using directory structures such as:

~~~text
patient_activity/
└── year=2026/
    └── month=09/
        ├── day=18/
        │   └── activity_001.parquet
        └── day=19/
            └── activity_002.parquet
~~~

Do not conclude that every dataset should be manually partitioned by year/month/day. Directory design should follow source, scale, governance, and workload requirements.

## 14. File arrival order

Do not use path or discovery order as business ordering.

~~~text
file arrival order
        !=
business event order
~~~

A late file can contain an earlier event. Preserve an explicit event-time field when event ordering matters.

## 15. Small-file operational impact

Equal byte volume does not imply equal operational cost.

~~~text
100 GB
  |
  +-- a reasonable number of larger files
  |
  +-- hundreds of thousands of tiny files
~~~

Large numbers of small files can increase discovery, metadata, scheduling, and processing overhead.

This tutorial identifies the risk; detailed file-size optimization belongs in later performance material.

## 16. Access troubleshooting

Do not respond to every read failure by expanding cloud permissions.

Use a layered diagnosis:

~~~text
Cannot read source
      |
      v
Does path/object exist?
      |
      v
Correct environment?
      |
      v
Cloud identity authorized?
      |
      v
Storage credential valid?
      |
      v
External location correct?
      |
      v
Unity Catalog privilege granted?
      |
      v
File format correct?
      |
      v
Schema compatible?
      |
      v
Malformed/corrupt input?
      |
      v
Complete source delivery?
~~~

Preserve the original error before making changes.

## 17. Common failure categories

Keep these distinct:

~~~text
PATH_NOT_FOUND
      !=
PERMISSION_DENIED
      !=
FORMAT/PARSING_ERROR
      !=
SCHEMA_ERROR
      !=
EMPTY/INCOMPLETE SOURCE
~~~

A permission change cannot repair a corrupt CSV. A schema change cannot repair a nonexistent path.

## 18. Cross-environment protection

A dangerous failure can be valid access to the wrong environment.

~~~text
DEV compute ----X----> PROD storage
TEST job   ----X----> PROD Bronze
~~~

Before any writable exercise or production execution, verify:

~~~text
[ ] Correct workspace
[ ] Correct catalog
[ ] Correct schema
[ ] Correct governed source
[ ] Correct target
[ ] Correct identity
~~~

Environment isolation should be enforced through governance and identity design, not only naming conventions.

## 19. Least privilege

An ingestion identity should receive only the access required for its job.

~~~text
ingestion identity
      |
      +-- required source read access
      +-- required target write access
      +-- required operational state access
~~~

Do not request ownership or administrative privileges merely to solve a file-read problem.

Never hard-code AWS keys, Azure secrets, GCP service credentials, passwords, or tokens in notebooks or repository files.

## 20. Source-to-Bronze reconciliation

A successful Spark action does not prove complete ingestion.

~~~text
Expected source files
        |
        v
Discovered files
        |
        v
Readable files
        |
        v
Parsed records
        |
        +--> malformed/rejected evidence
        |
        v
Bronze records
        |
        v
RECONCILE
~~~

Useful evidence can include:

- expected and observed file counts;
- file names or controlled file identifiers;
- source file sizes;
- parsed row counts;
- malformed/rejected counts;
- Bronze row counts;
- ingestion run identifiers;
- timestamps;
- validation results.

The exact reconciliation equation depends on the source contract.

## 21. Hands-on lab — state-changing training exercise

> **STATE-CHANGING TRAINING LAB:** Run only in an approved disposable environment.

### Pre-flight

~~~text
[ ] Correct workspace?
[ ] Correct catalog?
[ ] Correct schema?
[ ] Approved training volume/path?
[ ] Synthetic source?
[ ] No production checkpoint/state?
[ ] No embedded credentials?
~~~

### Exercise flow

~~~text
Synthetic CSV
      |
      v
approved training Volume
      |
      v
explicit schema
      |
      v
spark.read
      |
      v
selected _metadata
      |
      v
disposable Bronze Delta table
      |
      v
source-to-Bronze validation
~~~

### Example transformation before the write

~~~python
from pyspark.sql import functions as F

bronze_df = (
    df.select(
        "*",
        F.col("_metadata.file_name").alias("source_file_name"),
        F.col("_metadata.file_path").alias("source_file_path"),
        F.current_timestamp().alias("ingested_at"),
    )
)
~~~

`ingested_at` is processing-time audit metadata. It is not the business event time.

### Example disposable write

Use an administrator-approved training catalog/schema and a lab-specific table name.

~~~python
target_table = "training.bronze.patient_activity_file_lab"

(
    bronze_df.write
             .format("delta")
             .mode("overwrite")
             .saveAsTable(target_table)
)
~~~

Do not substitute a production table.

Before using overwrite mode, confirm that the target is the disposable lab object created for this exercise.

### Validation

Validate at least:

~~~text
source rows
    |
    v
parsed rows
    |
    v
Bronze rows
~~~

Also inspect the selected source-file provenance.

Cleanup may remove only resources explicitly created by this lab and only after confirming their exact identity.

## 22. Production recovery sequence

~~~text
File-ingestion failure
        |
        v
1. Preserve error evidence
2. Confirm workspace/environment
3. Confirm source path/object existence
4. Verify identity and governance
5. Verify source delivery completeness
6. Verify format and schema
7. Inspect malformed input
8. Determine partial target state
9. Identify safe replay range
10. Assess duplicate risk
11. Recover deliberately
12. Reconcile source -> Bronze
13. Validate downstream impact
~~~

Do not declare recovery complete merely because a rerun becomes green.

## 23. SAFE-READ acceptance

The companion artifact is:

~~~text
labs/cloud-object-storage-ingestion-check.sql
~~~

and is classified:

~~~text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
~~~

It performs metadata/read-only discovery only.

It intentionally does not execute:

- CREATE, ALTER, or DROP;
- INSERT, UPDATE, DELETE, or MERGE;
- COPY INTO;
- file ingestion;
- streaming-query creation;
- checkpoint manipulation;
- storage credential changes;
- external-location changes;
- GRANT or REVOKE;
- cloud-storage writes/deletes;
- cleanup.

## 24. Key takeaways

1. Cloud object storage is a common ingestion boundary for S3, ADLS, and GCS.
2. Prefer governed access rather than embedded cloud credentials.
3. Storage credentials, external locations, tables, and volumes are different concepts.
4. Unity Catalog volumes provide a useful governed file-access abstraction.
5. `spark.read` is a bounded file read, not a production incremental discovery mechanism.
6. SQL `read_files` provides another file-reading interface where supported.
7. Explicit schemas are valuable when the source contract is known.
8. Preserve selected file provenance using `_metadata`.
9. Do not silently discard malformed records.
10. Prefer immutable delivered source files.
11. File arrival order is not business event order.
12. Large numbers of tiny files can create operational overhead.
13. Troubleshoot path, permission, format, schema, and source completeness separately.
14. Verify environment before writing.
15. Reconcile source evidence with Bronze outcomes.
16. Keep state-changing training separate from SAFE-READ acceptance.
