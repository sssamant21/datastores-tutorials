# Part 3.1 — Data Ingestion Fundamentals

**Track:** Databricks Production Tutorials  
**Part:** 3 — Data Ingestion & ETL/ELT Pipelines  
**Status:** Revised Final / Canonical Edition

## Learning objectives

By the end of this tutorial, you should be able to:

- explain the role of ingestion in a Databricks data platform;
- distinguish full-load, incremental, and streaming ingestion patterns;
- separate ingestion responsibilities from downstream transformation;
- explain why Bronze should preserve sufficient source fidelity and audit evidence;
- recognize Auto Loader, Lakeflow Connect, CDC, and custom ingestion approaches at a high level;
- understand schema drift, rescued data, replay, idempotency, and reconciliation;
- identify common production ingestion failure modes;
- design a safe recovery workflow.

## 1. What is data ingestion?

Data ingestion moves data from a source system into the data platform while preserving enough information to understand, validate, audit, and, where required, replay what happened.

~~~text
SOURCE SYSTEMS
      |
      +-- Cloud files
      +-- Databases / CDC
      +-- Kafka / event streams
      +-- SaaS
      +-- APIs
      |
      v
INGESTION
      |
      +-- identity / permissions
      +-- source discovery
      +-- schema handling
      +-- incremental state
      +-- malformed/rescued records
      +-- ingestion metadata
      +-- idempotency
      +-- replay/recovery
      |
      v
BRONZE DELTA
      |
      +-- source fidelity
      +-- history
      +-- audit evidence
      +-- reconciliation
      |
      v
SILVER
validation + cleansing + transformation
~~~

Ingestion is not merely copying rows. A production pipeline needs to know what arrived, what was accepted, what failed, whether data can be replayed, and how completeness is demonstrated.

## 2. Ingestion is not transformation

Keep the responsibilities conceptually separate.

~~~text
INGESTION
source -> Bronze

TRANSFORMATION
Bronze -> Silver -> Gold
~~~

Bronze commonly preserves source fidelity and history. Silver is normally where stronger validation, normalization, deduplication, and business transformations occur.

Some ingestion-time technical normalization may be unavoidable, but significant business cleansing should not be hidden inside an ingestion step.

## 3. Common ingestion patterns

### Full load

A full load processes a complete bounded source snapshot.

~~~text
complete source snapshot
          |
          v
       target
~~~

Typical examples include an initial historical load or a small reference dataset refreshed as a complete snapshot.

### Incremental ingestion

Incremental ingestion processes only data that is new or changed relative to previously processed state.

~~~text
new / changed data
        |
        v
      target
~~~

Incremental identity can come from files, source offsets, CDC positions, event identifiers, timestamps, or connector-managed state.

### Streaming ingestion

Streaming ingestion processes continuously arriving data incrementally.

~~~text
events
  |
  v
incremental processing
  |
  v
target
~~~

These categories are not always mutually exclusive operationally. For example, Structured Streaming semantics can be used with AvailableNow to process available incremental data and then stop.

## 4. Databricks ingestion mechanisms

Databricks supports multiple ingestion approaches. Selection depends on the source and operational requirements.

At a high level:

~~~text
Cloud files ----------> Auto Loader / file ingestion
Databases ------------> connectors / CDC
SaaS -----------------> managed connectors where supported
Event systems --------> streaming connectors
Other sources --------> Spark readers / approved custom integration
                         |
                         v
                       Delta
~~~

Lakeflow Connect provides managed ingestion capabilities for supported sources.

Auto Loader is particularly important for incremental ingestion of files arriving in cloud object storage. It should not be treated as a universal ingestion mechanism for every source.

## 5. Cloud-file ingestion

A common pattern is:

~~~text
Cloud object storage
        |
        v
    Auto Loader
        |
        v
    Bronze Delta
~~~

Auto Loader uses the cloudFiles source with Structured Streaming semantics to discover and process new files incrementally.

Detailed Auto Loader implementation belongs in Part 3.3.

## 6. Database ingestion and CDC

Database ingestion often begins with an initial snapshot and then captures subsequent changes.

~~~text
Database
   |
initial snapshot
   +
CDC changes
   |
   v
Delta
~~~

CDC can represent inserts, updates, and deletes. Correctly applying those changes requires source-specific ordering, identity, and replay semantics.

CDC implementation is covered later in Part 3.

## 7. Bronze responsibilities

A Bronze layer should retain enough information to support:

- traceability;
- auditing;
- replay;
- debugging;
- reconciliation;
- downstream rebuilding.

Do not teach:

~~~text
Bronze = external table
~~~

Managed versus external storage is an independent architecture and lifecycle decision.

Likewise, Bronze does not mean "unprotected." Raw data can contain the most sensitive representation of source information.

## 8. Ingestion metadata

Useful tutorial-designed audit metadata can include:

~~~text
source_system
source_file
ingested_at
ingestion_run_id
~~~

These are design examples, not columns automatically guaranteed by every Databricks connector.

Depending on the source, other useful identifiers can include event IDs, source record IDs, source timestamps, CDC positions, file metadata, or connector-specific progress information.

## 9. Schema handling

Production ingestion needs an explicit schema policy.

~~~text
source
  |
  v
schema inference / supplied schema
  |
  v
schema policy
  |
  v
Bronze
~~~

Schema inference is convenient, but it should not be confused with schema governance.

Different formats and ingestion mechanisms have different inference behavior. A production pipeline should know whether the schema is supplied, inferred, evolved, rescued, or rejected.

## 10. Schema drift and evolution

Unexpected schema change is an operational event.

~~~text
schema change detected
        |
      expected?
     /        \
   yes         no
    |           |
 validate   contain/fail/rescue
     \         /
      downstream impact
            |
            v
   controlled evolution
~~~

Do not rely on automatic schema evolution as a substitute for understanding downstream compatibility.

## 11. Rescued and malformed data

Where supported, unexpected fields or type mismatches can be preserved for investigation rather than silently discarded.

Auto Loader can use a rescued-data column, commonly named `_rescued_data`, depending on configuration.

~~~text
unexpected field/type
        |
        v
preserve evidence
        |
        v
investigate
        |
        +-- correct source
        +-- approve evolution
        +-- quarantine
        +-- other approved handling
~~~

A growing rescued-data population is a data-quality signal.

## 12. File arrival order is not business order

Never assume discovery order represents business event order.

~~~text
file arrival order
        !=
business event order
~~~

Files can arrive late or out of order. Business event time should be represented explicitly when ordering matters.

## 13. Idempotency

A critical production question is:

~~~text
same input
   |
pipeline rerun
   |
will duplicate logical data appear?
~~~

Job retry is not automatically safe replay.

Possible identity mechanisms include:

- source record ID;
- event ID;
- business key;
- source file identity;
- CDC position;
- ingestion-run metadata.

No single key is correct for every source.

Do not use generic `DISTINCT` as the universal solution for ingestion duplicates.

## 14. Duplicate and changed source files

Treat these as different cases:

~~~text
new file
   !=
duplicate old file
   !=
modified old file
~~~

A source contract should define whether delivered files are immutable and how corrections are published.

Do not assume changing an already processed object will automatically produce the desired correction in Bronze.

## 15. Reconciliation

A successful job does not prove complete ingestion.

A useful conceptual model is:

~~~text
EXPECTED SOURCE
      |
      v
discovered / read
      |
      v
accepted
+ rescued
+ rejected
+ duplicates
      |
      v
BRONZE RESULT
~~~

The exact reconciliation equation depends on the source and pipeline semantics.

Row count alone may be insufficient for CDC, deduplication, malformed records, or intentionally rescued data.

## 16. Partial loads

A job can finish while the source is incomplete, or fail after some target work has already occurred.

For each ingestion pipeline, determine:

- what defines source completeness;
- how partial processing is detected;
- whether target writes are transactional;
- what progress evidence exists;
- what happens on retry;
- how duplicate effects are prevented;
- how source-to-target reconciliation is performed.

## 17. Replayability

A recoverable architecture should answer:

~~~text
Production failure
      |
Can source be replayed?
      |
Can Bronze be rebuilt?
      |
Can Silver be rebuilt?
      |
Can Gold be rebuilt?
~~~

Source retention, Bronze retention, checkpoint/state retention, and downstream reproducibility all influence the answer.

## 18. Checkpoint and state protection

Incremental ingestion mechanisms can maintain persistent state.

Do not use this as a default troubleshooting pattern:

~~~text
ingestion failed
      |
delete checkpoint
      |
restart
~~~

Instead:

~~~text
failure
  |
preserve state
  |
inspect source + schema + checkpoint + sink
  |
understand replay consequences
  |
recover deliberately
~~~

Deleting or replacing state can change what the pipeline believes has already been processed.

## 19. Credentials and permissions

Never hard-code cloud access keys, passwords, or tokens into tutorial notebooks, repository files, or production pipeline code.

Use approved identity and secret-management mechanisms.

Follow least privilege:

~~~text
ingestion identity
      |
      +-- required source access
      +-- required target access
      +-- required checkpoint/schema access
~~~

Broad storage permissions should not be the default response to an authorization error.

## 21. Hands-on lab — writable ingestion exercise

> **STATE-CHANGING LAB:** Run only in an approved disposable training environment.

The writable exercise should:

1. create or use an approved training namespace;
2. create a tiny synthetic source dataset;
3. ingest it into a disposable Bronze Delta table;
4. add explicitly designed ingestion metadata;
5. validate source and target counts;
6. demonstrate how duplicate/replay behavior would be detected;
7. clean up only resources created by the exercise.

The exercise must not use production storage, production checkpoints, real patient data, or embedded credentials.

## 22. Production failure recovery

Use this sequence:

~~~text
Ingestion failure
      |
      v
1. Preserve error evidence
2. Identify last successful progress
3. Verify source availability
4. Verify identity / permissions
5. Inspect schema changes
6. Inspect malformed / rescued data
7. Inspect checkpoint / state
8. Determine partial-write status
9. Determine replay range
10. Assess duplicate risk
11. Recover
12. Reconcile source -> Bronze
13. Validate downstream impact
~~~

Recovery is not complete until the resulting data has been validated.

## 23. Operational troubleshooting checklist

~~~text
[ ] Is the expected source data present?
[ ] Can the ingestion identity access it?
[ ] Is the expected source scope correct?
[ ] Did source schema change?
[ ] Are malformed/rescued records increasing?
[ ] What was the last successful progress point?
[ ] Is checkpoint/state storage healthy?
[ ] Did any target write partially succeed?
[ ] Can the source be replayed?
[ ] What range requires replay?
[ ] Can replay produce duplicates?
[ ] Are source files immutable?
[ ] Does reconciliation balance?
[ ] Did downstream Silver/Gold processing run?
[ ] Is sensitive data appearing in logs?
~~~

- storage changes;
- cleanup.

## 25. Key takeaways

1. Ingestion is a production data movement and evidence problem, not just a copy operation.
2. Separate ingestion from downstream business transformation.
3. Full, incremental, and streaming patterns solve different requirements and can overlap operationally.
4. Auto Loader is important for incremental cloud-file ingestion but is not the universal ingestion mechanism.
5. Database ingestion can combine an initial snapshot with CDC.
6. Bronze should preserve enough fidelity and history for traceability and replay.
7. Managed versus external storage is independent of Bronze/Silver/Gold role.
8. Schema inference is not schema governance.
9. Unexpected schema and rescued records require monitoring.
10. File arrival order must not be assumed to equal event order.
11. Job retry is not automatically idempotent replay.
12. Successful execution does not prove complete ingestion.
13. Reconciliation should explain accepted, rescued, rejected, duplicate, and target outcomes.
14. Protect checkpoint and ingestion state.
15. Recovery requires post-replay reconciliation.
16. Use least privilege and never embed credentials.
17. Keep writable ingestion labs separate from SAFE-READ acceptance.
