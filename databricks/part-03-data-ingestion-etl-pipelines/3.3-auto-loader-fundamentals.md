# Part 3.3 — Auto Loader Fundamentals

**Track:** Databricks Production Tutorials  
**Part:** 3 — Data Ingestion & ETL/ELT Pipelines  
**Status:** Revised Final / Canonical Edition

## Learning objectives

By the end of this tutorial, you should be able to:

- explain what Databricks Auto Loader does;
- distinguish bounded file reads from incremental file ingestion;
- configure the `cloudFiles` Structured Streaming source;
- understand directory listing, managed file events, and classic file-notification concepts;
- use `AvailableNow` for scheduled incremental ingestion;
- distinguish checkpoint state from Auto Loader schema state;
- explain basic schema inference/evolution behavior;
- recognize rescued data versus structurally corrupt records;
- preserve selected file provenance;
- reason correctly about file-processing guarantees;
- troubleshoot ingestion lag without immediately deleting state or scaling compute;
- perform a synthetic incremental source-to-Bronze lab safely.

## 1. Why Auto Loader?

Part 3.2 demonstrated bounded reads from cloud object storage. Production sources commonly continue delivering new files after the first read.

~~~text
Time 1                     Time 2

source/                    source/
├── file-001.csv           ├── file-001.csv
└── file-002.csv           ├── file-002.csv
                           └── file-003.csv
~~~

A production ingestion system needs to identify new input while preserving durable progress.

~~~text
Cloud object storage
        |
        v
Auto Loader
cloudFiles
        |
        +-- file discovery
        +-- schema handling
        +-- ingestion state
        +-- checkpoint-backed progress
        |
        v
Bronze Delta
~~~

## 2. Bounded read versus incremental ingestion

Keep these models distinct.

~~~text
spark.read
    |
    v
bounded file read

spark.readStream
+ cloudFiles
    |
    v
incremental file ingestion
~~~

Auto Loader integrates with Apache Spark Structured Streaming through the `cloudFiles` source.

## 4. Governed training paths

Use administrator-approved training storage.

Example:

~~~text
/Volumes/training/bronze/autoloader_lab/
├── source/
└── state/
    ├── schema/
    └── checkpoint/
~~~

These names are illustrative. Never assume they exist.

Operational state must be durable and must not be casually reused between pipelines or environments.

## 5. Basic Auto Loader source

A minimal CSV source can look like:

~~~python
source_path = "/Volumes/training/bronze/autoloader_lab/source/"
schema_path = "/Volumes/training/bronze/autoloader_lab/state/schema/"

df = (
    spark.readStream
         .format("cloudFiles")
         .option("cloudFiles.format", "csv")
         .option("cloudFiles.schemaLocation", schema_path)
         .option("header", "true")
         .load(source_path)
)
~~~

The important element is:

~~~text
format("cloudFiles")
~~~

The underlying source format is specified separately:

~~~text
cloudFiles.format = csv
~~~

## 6. File discovery

Auto Loader must determine which source files are available for processing.

At a high level, relevant discovery approaches include:

~~~text
Managed file events
        |
        +--> preferred for many suitable modern workloads

Directory listing
        |
        +--> supported/default discovery behavior

Classic file notification
        |
        +--> existing alternative architecture
~~~

Do not introduce deprecated incremental-listing behavior as a recommended new production design.

### Managed file events

Managed file events can reduce repeated storage listing work for suitable workloads.

The operational model is:

~~~text
Cloud storage
      |
      v
managed file-event cache
      |
      v
Auto Loader
      |
      v
checkpoint
~~~

The first run can still require a full listing to establish the initial position.

For pipelines using managed file events, account for the documented operational recommendation to run the pipeline at least once every seven days. Long inactivity can require additional listing/resynchronization work.

Discovery optimization does not eliminate the need for checkpoint protection.

## 7. AvailableNow

Structured Streaming does not mean that compute must run forever.

A scheduled incremental pipeline can use `AvailableNow`:

~~~python
checkpoint_path = (
    "/Volumes/training/bronze/"
    "autoloader_lab/state/checkpoint/"
)

target_table = "training.bronze.patient_activity_autoloader_lab"

query = (
    df.writeStream
      .format("delta")
      .option("checkpointLocation", checkpoint_path)
      .trigger(availableNow=True)
      .toTable(target_table)
)

query.awaitTermination()
~~~

Conceptually:

~~~text
Start
  |
  v
Process currently available incremental input
  |
  v
Persist progress
  |
  v
Stop
~~~

The next execution reuses durable state and processes newly available input.

## 8. Checkpoint state

Checkpoint state is part of the pipeline's operational identity.

~~~text
checkpoint
    |
    +-- streaming progress
    +-- processed-input tracking
    +-- recovery information
~~~

Therefore:

~~~text
checkpoint != temporary scratch directory
~~~

A production incident should not begin with checkpoint deletion.

~~~text
Failure
  |
  v
Preserve checkpoint
  |
  v
Capture evidence
  |
  v
Determine last successful progress
  |
  v
Inspect source + schema + target
  |
  v
Understand replay consequences
  |
  v
Recover deliberately
  |
  v
Reconcile
~~~

## 9. Schema state

Auto Loader can maintain schema information using `cloudFiles.schemaLocation`.

~~~text
checkpointLocation
       |
       +--> streaming progress/state

cloudFiles.schemaLocation
       |
       +--> Auto Loader schema tracking
~~~

These are different logical responsibilities even when an approved design places their data beneath a common governed state root.

Do not nest operational state underneath a table's data directory merely for convenience.

## 10. Schema inference and evolution

Auto Loader can infer schema and track schema changes.

A critical distinction:

~~~text
Schema inferred by Auto Loader
          |
          v
default evolution:
addNewColumns

Explicit schema supplied
          |
          v
default evolution:
none
~~~

Schema evolution is not the same as schema governance.

~~~text
new field
    |
    v
detected
    |
    v
configured evolution behavior
    |
    v
operator/governance decision
~~~

With `addNewColumns`, a newly detected column can update tracked schema and cause the stream to stop so that a restart can continue with the evolved schema.

Automatic restart must not be confused with automatic approval of every source-contract change.

Part 3.4 covers schema inference and evolution in depth.

## 11. Rescued data

Unexpected schema/type information can be preserved in rescued data rather than silently discarded.

~~~text
unexpected field/type
        |
        v
_rescued_data
        |
        v
observable evidence
        |
        v
investigate
~~~

Operators should monitor rescued-data behavior.

An increasing rescued-data population can indicate source-contract drift, type mismatches, case mismatches, or unexpected fields.

## 12. Rescued data versus corrupt records

Keep these failure classes distinct:

~~~text
unexpected schema/type
        !=
structurally corrupt record
~~~

A field that does not match the expected schema and a CSV record that cannot be structurally parsed are different conditions and can require different remediation.

Neither should disappear without evidence.

## 13. File provenance

Preserve selected source provenance.

~~~python
from pyspark.sql import functions as F

bronze_df = (
    df.select(
        "*",
        F.col("_metadata.file_name").alias("source_file_name"),
        F.col("_metadata.file_path").alias("source_file_path"),
        F.col("_metadata.file_size").alias("source_file_size"),
        F.col("_metadata.file_modification_time")
         .alias("source_file_modification_time"),
        F.current_timestamp().alias("ingested_at"),
    )
)
~~~

Remember:

~~~text
ingested_at
    !=
event_time
~~~

And:

~~~text
file arrival order
      !=
discovery order
      !=
processing order
      !=
business event order
~~~

Business ordering must come from an appropriate source/event-time contract.

## 14. File-processing guarantees

Do not expand a file-processing guarantee into a business-level guarantee.

~~~text
Auto Loader
file-processing semantics
        |
        +-- incremental
        +-- checkpoint-backed
        |
        !=
business-record uniqueness
        !=
source contains no duplicate records
        !=
arbitrary external side effects exactly once
~~~

For example, one source file can contain the same logical business record twice.

## 15. Source immutability

Prefer immutable delivered source objects.

~~~text
already ingested file
        |
        v
silently modified/replaced
        |
        v
incremental ambiguity
        |
        v
reconciliation risk
~~~

Source corrections should follow an explicit correction/versioning contract.

## 16. Changing discovery modes

Changing how files are discovered does not inherently mean that ingestion history should be reset.

~~~text
discovery mechanism
      !=
checkpoint identity
~~~

When migrating an existing pipeline between supported discovery approaches, preserve and validate the established checkpoint according to the approved migration procedure.

Do not create a new checkpoint merely because a discovery option changes.

## 17. Backlog and ingestion lag

A healthy production ingestion system needs more than a green stream status.

~~~text
files arriving
      |
      v
files discovered
      |
      v
files processed
      |
      v
files outstanding
      |
      v
oldest outstanding age
      |
      v
Bronze
~~~

If:

~~~text
arrival rate > sustainable processing rate
~~~

then backlog and ingestion lag can grow.

## 18. Troubleshooting lag

Do not scale compute before identifying the bottleneck.

~~~text
Lag increasing
      |
      v
Arrival-rate change?
      |
      v
Discovery issue?
      |
      v
Storage/permission issue?
      |
      v
Schema failure?
      |
      v
Malformed/rescued data?
      |
      v
Checkpoint/state latency?
      |
      v
Processing slowdown?
      |
      v
Delta sink latency?
      |
      v
Compute saturation?
~~~

Scale compute when evidence indicates compute is the relevant constraint.

## 19. Environment isolation

Never reuse operational state casually across environments.

~~~text
DEV checkpoint  ----X----> PROD
TEST schemaState ----X----> PROD
~~~

Before a writable execution, verify:

~~~text
[ ] Correct workspace
[ ] Correct catalog
[ ] Correct schema
[ ] Correct source
[ ] Correct target
[ ] Unique checkpoint
[ ] Correct schema state
[ ] No production state reused
~~~

## 20. Hands-on lab — incremental ingestion

> **STATE-CHANGING TRAINING LAB:** Run only in an approved disposable environment.

Use synthetic data only.

### Lab architecture

~~~text
Synthetic file #1
       |
       v
Training Volume
       |
       v
Auto Loader
       |
       +-- schema state
       +-- checkpoint
       |
       v
AvailableNow
       |
       v
Disposable Bronze
       |
       v
Validate
       |
Add synthetic file #2
       |
       v
Run same pipeline again
       |
       v
Incremental input processed
       |
       v
Reconcile
~~~

### Step 1 — Pre-flight

~~~text
[ ] Correct workspace?
[ ] Correct catalog/schema?
[ ] Synthetic data only?
[ ] Approved training source?
[ ] Disposable target?
[ ] Unique checkpoint?
[ ] Unique schema state?
[ ] No production credentials/state?
~~~

### Step 2 — Initial synthetic file

Example:

~~~csv
event_id,patient_id,event_type,event_time
EVT-001,P001,ADMISSION,2026-09-19T10:00:00Z
EVT-002,P002,DISCHARGE,2026-09-19T10:05:00Z
~~~

Place it in the approved lab source using the environment's approved file-delivery mechanism.

### Step 3 — Run Auto Loader

Use the `cloudFiles` source and `AvailableNow` pattern shown earlier.

Wait for termination before validating the first run.

### Step 4 — Validate Bronze

Check:

~~~text
source file #1
      |
      v
expected records
      |
      v
Bronze records
      |
      v
selected provenance
~~~

Do not use stream completion alone as acceptance evidence.

### Step 5 — Add another synthetic file

Example:

~~~csv
event_id,patient_id,event_type,event_time
EVT-003,P003,LAB_RESULT,2026-09-19T10:10:00Z
EVT-004,P004,TRANSFER,2026-09-19T10:15:00Z
~~~

Use a new file name. Do not overwrite the first source object.

### Step 6 — Run the same pipeline again

Reuse the same approved checkpoint and schema state.

The exercise should demonstrate that durable state allows the pipeline to identify incremental input.

### Step 7 — Reconcile

Validate:

~~~text
expected source files
        |
        v
processed source files
        |
        v
expected source records
        |
        v
Bronze records
        |
        v
rescued/corrupt evidence
~~~

Any unexplained difference requires investigation.

## 21. Recovery workflow

~~~text
Auto Loader delayed/stopped
        |
        v
1. Preserve checkpoint/schema state
2. Capture error and query evidence
3. Confirm source files are arriving
4. Confirm source access
5. Inspect discovery behavior
6. Inspect schema evolution
7. Inspect rescued/corrupt data
8. Determine last successful progress
9. Inspect target state
10. Determine replay/duplicate consequences
11. Recover deliberately
12. Reconcile source -> Bronze
13. Validate backlog recovery
~~~

Do not declare recovery complete merely because the next execution succeeds.

## 22. Production principles

Keep these relationships visible:

~~~text
readStream                  != must run forever
checkpoint                  != temporary scratch storage
schema inference            != schema governance
schema evolution            != automatic schema approval
rescued data                != corrupt record
file processed once         != unique business records
stream RUNNING              != ingestion healthy
new discovery mechanism     != new ingestion history
file arrival order          != business event order
successful retry            != proven reconciliation
~~~

## 23. SAFE-READ acceptance

The companion artifact is:

~~~text
labs/auto-loader-check.sql
~~~

and is classified:

~~~text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
~~~

It performs namespace/metadata discovery only.

It intentionally does not:

- start Auto Loader;
- create a streaming query;
- execute `readStream` or `writeStream`;
- ingest files;
- manipulate checkpoints;
- manipulate Auto Loader schema state;
- create or alter credentials/external locations;
- execute DDL or DML;
- change privileges;
- modify cloud storage;
- perform cleanup.

## 24. Key takeaways

1. Auto Loader provides incremental cloud-file ingestion through the `cloudFiles` Structured Streaming source.
2. Bounded `spark.read` and Auto Loader solve different ingestion problems.
3. Managed file events are preferred for many suitable modern workloads; directory listing remains supported.
4. Do not teach deprecated incremental listing for new designs.
5. `AvailableNow` supports scheduled incremental processing without an always-running stream.
6. Checkpoint state is durable operational state, not disposable scratch data.
7. Schema tracking and streaming progress have different responsibilities.
8. Schema inference/evolution does not replace schema governance.
9. Rescued data and structurally corrupt records are different conditions.
10. Preserve selected file provenance.
11. Scope exactly-once statements to the documented file-processing behavior.
12. File order is not business event order.
13. Prefer immutable delivered source objects.
14. Do not reset checkpoints merely to change discovery mode.
15. Monitor backlog and oldest outstanding input, not only stream status.
16. Diagnose lag before scaling compute.
17. Never casually share checkpoint/schema state across environments.
18. Reconcile source evidence with Bronze outcomes.
