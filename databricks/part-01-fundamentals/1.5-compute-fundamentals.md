## 1. Purpose

Every Databricks workload needs compute resources somewhere to perform processing. A notebook, Lakeflow Job, or SQL query is a workload or interface, not compute itself.

```text
User / Application
        │
        ▼
Databricks Workload
        │
        ├── Notebook
        ├── Lakeflow Job
        ├── Lakeflow Pipeline
        └── SQL Query
        │
        ▼
Compute
        │
        ├── Serverless Compute
        ├── Classic Compute
        └── SQL Warehouse
        │
        ▼
Processing → Unity Catalog → Governed Data
```

Compute selection affects performance, scalability, startup behavior, security, workload isolation, operational responsibility, reliability, cloud infrastructure, and cost.

## 2. Learning Objectives

After completing this tutorial, you should be able to explain compute vs persistent storage; serverless vs classic; interactive vs automated compute; SQL warehouses; Auto, Standard, and Dedicated access modes; driver/worker concepts; single-node vs distributed classic compute; autoscaling and auto-termination; Databricks Runtime; Photon; compute policies and permissions; Unity Catalog authorization vs compute authorization; lifecycle, workload isolation, ephemeral local storage, performance troubleshooting, cost fundamentals, and AWS/Azure/GCP differences.

## 3. Compute vs Storage

Compute executes workloads. Persistent business data should live in approved durable storage and be governed appropriately.

```text
Compute ≠ Persistent Storage
```

Stopping or replacing compute must not destroy authoritative governed datasets.

## 4. Major Compute Categories

```text
Databricks Compute
├── Serverless Compute
│   ├── Interactive workloads
│   ├── Automated jobs
│   └── Lakeflow pipelines
├── Classic Compute
│   ├── Interactive workloads
│   ├── Jobs
│   └── Other supported workloads
└── SQL Warehouses
    ├── Serverless
    ├── Pro
    └── Classic
```

Availability depends on cloud, region, workspace configuration, workload, permissions, product capability, and organizational policy.

## 5. Serverless Compute

Serverless reduces the infrastructure application and platform teams configure directly. Databricks manages provisioning, platform-managed scaling, runtime management, and infrastructure optimization. Serverless does not remove security, governance, networking, cost, or operational responsibility; it changes responsibility boundaries.

For supported modern workloads, serverless should generally be evaluated first. This is a recommendation, not a universal rule. Classic remains important where requirements need capabilities or configurations unavailable through serverless.

## 6. Interactive vs Automated Serverless

```text
Serverless
├── Interactive Compute
│   └── Notebook / interactive execution
└── Automated Compute
    ├── Lakeflow Jobs
    └── Lakeflow pipelines
```

Databricks provides separate serverless access controls for default interactive and default automated compute. Removing either can interrupt dependent users or workloads.

### Serverless access change gate

```text
[ ] Interactive or automated?
[ ] Which users/groups/service principals?
[ ] Which notebooks depend on it?
[ ] Which jobs/pipelines depend on it?
[ ] Is alternate compute available?
[ ] Has non-production validation completed?
[ ] Is rollback defined?
[ ] Has approval been obtained?
```

For supported automated serverless workloads, performance modes can include Performance Optimized and Standard. Validate current behavior and availability for the target cloud, region, workspace, and workload.

## 7. Classic Compute

Classic compute provides greater configuration control over runtime, access mode, driver/worker configuration, worker count, autoscaling, policies, and supported advanced settings. Greater configurability creates greater operational responsibility, including instance selection, networking, identity, quotas, regional capacity, runtime compatibility, startup failures, and cost.

## 8. Serverless vs Classic

| Area | Serverless | Classic |
|---|---|---|
| Infrastructure management | Primarily Databricks managed | More customer configurable |
| VM/instance selection | Generally abstracted | Configurable |
| Scaling | Platform managed | Configurable |
| Runtime management | More abstracted | Runtime selected/configured |
| Infrastructure customization | Supported serverless capabilities | Greater flexibility |
| Operational burden | Lower | Higher |

Select based on workload requirements, not a blanket rule.

## 9. Interactive vs Automated Workloads

Interactive compute supports development, exploration, learning, troubleshooting, experimentation, and notebook execution. Automated production workloads commonly run through Lakeflow Jobs or pipelines with explicit ownership, lifecycle, scheduling, retry behavior, monitoring, security, and cost controls.

Production automation should not casually depend on manually maintained interactive compute.

## 10. SQL Warehouses

SQL warehouses are optimized for SQL analytics workloads such as dashboards, reporting, BI tools, exploratory SQL, and applications. Major types include Serverless, Pro, and Classic. Serverless should generally be evaluated first for supported modern SQL workloads.

A stopped SQL warehouse can automatically start when an authorized query or workload uses it. Therefore:

```text
Read-only SQL ≠ No compute action
Read-only SQL ≠ Zero cost
```

Do not start stopped compute solely to complete a SAFE-READ lab unless explicitly approved. Before manually stopping SQL compute, check scheduled jobs, dashboards, alerts, JDBC/ODBC clients, applications, analysts, and other dependencies.

## 11. Classic Distributed Spark Compute

```text
              Driver
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
    Worker   Worker   Worker
```

The driver coordinates the Spark application. Workers perform distributed tasks and provide CPU, memory, execution capacity, and temporary local storage. This model applies to classic distributed Spark compute and should not be generalized to every serverless product.

More workers do not automatically make a workload faster. Performance also depends on parallelism, query plan, skew, shuffle, data layout, file sizes, source/downstream performance, and application design.

## 12. Single-Node Classic Compute

Single-node classic compute can suit workloads that do not benefit from distributed processing. Do not choose it merely because it appears cheaper; the workload must fit the architecture.

## 13. Autoscaling and Auto-Termination

Classic autoscaling operates within configured worker bounds and remains constrained by cloud quotas, capacity, workload characteristics, and platform behavior. Classic autoscaling is not the same operational mechanism as serverless platform-managed scaling.

Auto-termination is particularly useful for idle interactive classic compute. Automated job compute follows workload execution lifecycle more directly.

## 14. Databricks Runtime

Databricks Runtime is particularly important for classic compute and can affect Spark/language versions, compatibility, features, libraries, security support, and performance. Serverless abstracts runtime management differently.

Runtime upgrades are production changes. Validate application code, dependencies, Spark behavior, connectors, JDBC/ODBC dependencies, data correctness, performance, schedules, and rollback before production rollout.

## 15. Photon

Photon is Databricks' vectorized execution engine for supported SQL and DataFrame workloads. It can improve supported workload performance but does not replace sound query and data design.

```text
Photon ≠ Replacement for good engineering
```

## 16. Classic Access Modes

```text
Access Mode
├── Auto
├── Standard
└── Dedicated
```

Auto allows Databricks to select an appropriate supported mode. Standard is recommended for most supported classic workloads and provides multi-user isolation and governance capabilities. Dedicated is intended for workloads requiring functionality Standard does not support, including certain specialized APIs, R, GPU/distributed ML, privileged machine access, or runtime-specific functionality.

Do not select Dedicated merely as a workaround for an unexplained permission failure. Unity Catalog capabilities on Dedicated can depend on runtime, workspace configuration, operation type, and supported functionality.

Changing Standard ↔ Dedicated is a production change. Validate runtime, libraries, Unity Catalog behavior, identity behavior, security impact, workload compatibility, and rollback.

## 17. Compute Policies

Compute policies govern classic compute configuration, including approved runtimes, instance restrictions, worker limits, autoscaling bounds, tags, configuration requirements, cost controls, and security standards.

Policy changes can affect many compute resources and workloads, and some enforcement actions can involve restart. Identify attached compute and active workloads, test outside production, assess restart impact, define rollback, obtain approval, and validate after rollout.

## 18. Compute Permissions vs Data Permissions

Compute authorization and Unity Catalog authorization are separate layers.

```text
User
├── Workspace access
├── Compute access
└── Unity Catalog
    ├── Catalog privilege
    ├── Schema privilege
    └── Object privilege
```

Can use compute ≠ can query every table. Can SELECT a table ≠ can manage compute. Do not solve permission problems by granting broad administration.

## 19. Compute Lifecycle

Classic compute conceptually moves through Create → Provision → Start → Running → Active/Idle → Terminate. Failures can occur because of permissions, policy, invalid configuration, cloud quota/capacity, networking, identity, runtime startup, initialization, or libraries. Identify the failing lifecycle stage before changing configuration.

## 20. Compute Is Ephemeral

Compute-local storage is appropriate for cache, shuffle, temporary execution state, and temporary files. It is not appropriate for the only copy of business data, backups, recovery data, or authoritative production datasets.

```text
Authoritative Data → Approved Persistent Storage → Governance
```

## 21. Credential and Metadata Safety

Never hardcode long-lived cloud credentials, passwords, tokens, or private keys in compute configuration. Use approved identity, workload identity, secret-management, storage-credential, and cloud-native mechanisms.

Do not put PHI, PII, secrets, credentials, or confidential identifiers in compute names, policy names, job names, tags, environment variables, Spark configuration, logs, screenshots, or tutorial examples.

## 22. Cost and FinOps Fundamentals

A useful mental model is:

```text
Compute Cost ≈ Resource Consumption × Execution Duration × Execution Frequency
```

Cost problems commonly involve oversized compute, idle interactive resources, excessive job frequency, repeated failures/retries, inefficient SQL, poor workload design, inappropriate scaling, duplicate pipelines, unnecessary processing, or unsuitable compute selection.

Diagnose slow workloads before scaling. Inspect CPU, memory, spill, shuffle, skew, parallelism, query plans, file layout, source/downstream latency, and concurrency.

### Compute FinOps check

```text
[ ] Correct compute type?
[ ] Correct workload isolation?
[ ] Right-sized?
[ ] Autoscaling appropriate?
[ ] Auto-stop/termination appropriate?
[ ] Schedule appropriate?
[ ] Retry behavior controlled?
[ ] Duplicate workloads absent?
[ ] Cost attribution available?
[ ] Tags appropriate and non-sensitive?
[ ] Serverless usage controls considered?
[ ] Cost monitoring available?
```

Serverless controls should not be treated as a guaranteed maximum bill. Use appropriate usage policies, budgets, monitoring, attribution, and operational review.

## 23. Cloud-Aware Compute

Core Databricks compute concepts are common across AWS, Azure, and GCP, while infrastructure implementation differs.

AWS classic implementations can involve EC2, VPC, subnets, security groups, IAM, quotas, and regional capacity. Azure implementations can involve Azure VMs, VNets, subnets, network controls, Microsoft Entra/Azure identity, quotas, and regional capacity. GCP implementations can involve Compute Engine, VPC, subnets, Google Cloud IAM, service accounts, quotas, and regional capacity.

Do not copy provider-specific infrastructure runbooks across clouds without validating the target architecture.

## 24. Troubleshooting

### Compute will not start

Check permission, policy, configuration, cloud quota, capacity, networking, identity, runtime, and initialization. Do not change multiple layers simultaneously.

### Notebook will not execute

Check selected/available compute, user authorization, runtime compatibility, code, libraries, data authorization, and dependencies. Notebook failure and compute failure are not synonymous.

### Job is slow

Check query plan, data volume/skew, shuffle, file layout, utilization, sizing, scaling, source/dependency performance, and concurrency before resizing.

### Compute works but table access fails

Investigate Unity Catalog principal, catalog/schema/object privileges, workspace binding, and related storage/identity path. Compute can be healthy while authorization fails.

### Works on one compute but not another

Compare compute type, runtime, access mode, libraries, Spark configuration, environment, identity, network path, Unity Catalog compatibility, policy, and cloud architecture.

## 25. Observability Before Remediation

Prefer Evidence → Diagnosis → Minimum Change over Restart → Hope. Where practical, capture errors, event history, driver/worker evidence, job-run information, metrics, and workload state before disruptive remediation.

Before restarting or terminating production compute, identify active users, notebooks, jobs/tasks, streaming workloads, dependent services; capture evidence; determine impact; define recovery/rollback; obtain approval; and validate afterward.

## 26. Production Compute Change Method

```text
Observe
  ↓
Identify requirement / bottleneck
  ↓
Collect evidence
  ↓
Define minimum change
  ↓
Assess blast radius
  ↓
Define expected result and rollback
  ↓
Approve
  ↓
Change
  ↓
Validate
  ↓
Monitor
```

This applies to runtime, access mode, worker sizing, autoscaling, policies, networking, identity, initialization, libraries, and serverless authorization.

## 27. Production Compute Safety

```text
┌──────────────────────────────────────────────────────────────┐
│ PRODUCTION COMPUTE SAFETY                                    │
│ • Capture evidence before disruptive remediation.            │
│ • Check active workloads before restart/termination.         │
│ • Treat policy/serverless-access changes as production       │
│   authorization/configuration changes.                       │
│ • Test runtime and access-mode changes before production.    │
│ • Never store authoritative data only on local compute.      │
│ • Never hardcode credentials in compute configuration.       │
│ • Do not solve permission failures with broad admin access.  │
│ • Diagnose performance before increasing compute size.       │
│ • Treat SQL auto-start as a potential cost-producing action. │
│ • Keep sensitive data out of names, tags, logs, and config.  │

│ • Assess security, reliability, and cost blast radius.       │
│ • Define validation and rollback before production changes.  │
└──────────────────────────────────────────────────────────────┘
```

## 29. Key Takeaways

1. Compute executes workloads; it is not persistent governed storage.
2. Serverless and classic have different operational responsibility models.
3. Evaluate serverless first for supported modern workloads; use classic where requirements justify it.
4. Interactive and automated compute have distinct lifecycle and permission considerations.
5. SQL warehouses are SQL-oriented compute and can auto-start, producing cost even for read-only queries.
6. Driver/worker architecture applies to classic distributed Spark compute.
7. Classic autoscaling and serverless scaling are different operational models.
8. Databricks Runtime selection is primarily a classic-compute concept.
9. Auto, Standard, and Dedicated are key classic access-mode concepts; Standard is recommended for most supported classic workloads.
10. Policies can have broad blast radius.
11. Compute and Unity Catalog authorization are separate.
12. Compute should be ephemeral; authoritative data must not exist only on local disk.
13. Never hardcode credentials or expose sensitive metadata.
14. Bigger compute does not automatically fix performance.
15. Capture evidence before disruptive remediation and apply controlled production change practices.
16. AWS, Azure, and GCP share core concepts while differing in implementation.
