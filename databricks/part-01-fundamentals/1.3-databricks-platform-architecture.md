## 1. Purpose

A production Databricks platform is more than a workspace connected to cloud storage. Teams need to understand the boundaries among the Databricks account, workspaces, control plane, serverless and classic compute planes, Unity Catalog governance, customer data, cloud storage, identity, and networking. Exact implementation depends on cloud provider, region, workspace configuration, compute type, networking model, governance configuration, and enabled features.

## 2. Learning Objectives

After this tutorial, learners should be able to explain account vs workspace, control vs compute plane, serverless vs classic compute, workspace system data vs customer data, Unity Catalog, storage credentials and external locations, major network paths, AWS/Azure/GCP implementation differences, and architecture-led production troubleshooting.

## 3. Account and Workspace

The Databricks account is the top-level administrative context. It can contain account administration, identity, workspaces, Unity Catalog metastores, policies, governance, and account-level services. Organizations can use multiple workspaces for development, staging, production, business boundaries, regions, security requirements, or cloud boundaries.

A workspace exposes capabilities such as notebooks, SQL, jobs/workflows, compute, queries, data exploration, and administration. Do not use the mental model `Workspace = Cluster + Storage`; it hides important production boundaries.

## 4. High-Level Architecture

```text
Databricks Account
├── Control Plane
├── Serverless Compute Plane
├── Workspaces
└── Unity Catalog Governance
          │
          ▼
     Governed Data
          │
          ▼
     Cloud Storage

Customer Cloud Environment
├── Classic Compute Plane
├── Networking
├── Cloud Identity
└── Customer Resources
```

This is a learning model, not a complete physical or network diagram.

## 5. Control Plane

The control plane contains Databricks-managed backend/platform services, including workspace services, the web application, platform APIs, compute orchestration, job orchestration, and management services. Control-plane availability and workload data-access failures are different failure domains.

## 6. Compute Plane

The compute plane executes Spark, SQL, Python, data engineering, ML, and streaming workloads. Two important models are serverless and classic compute.

### Serverless compute

Databricks manages the underlying serverless compute infrastructure. Serverless reduces customer infrastructure lifecycle management but does not eliminate responsibility for workload design, authorization, governance, data handling, supported connectivity, observability, performance, cost, and organizational controls.

`Serverless ≠ no operations`; it represents a different operational boundary. Where supported and appropriate, current Databricks architectural guidance generally favors evaluating serverless first. This is vendor direction, not a universal rule; validate workload support, networking, region, security, features, organizational standards, and cost.

### Classic compute

Classic compute uses a different infrastructure responsibility model and can expose more cloud concerns to platform/SRE teams, including subnets, routes, security controls, private connectivity, DNS, quotas, VM availability, cloud identity, and storage connectivity. Classic does not inherently mean publicly exposed compute.

Classic and serverless networking require different operational procedures. Serverless workloads can still require secure connectivity to storage, databases, APIs, messaging systems, and private customer resources.

## 7. Compute vs Durable Data

Do not treat compute nodes as the authoritative durable storage layer. Governed data should persist independently of compute lifecycle so compute can be started, stopped, scaled, replaced, upgraded, or recreated safely.

## 8. Workspace System Data vs Customer Data

Distinguish workspace system data from customer data assets. Workspace system data can include platform-managed information such as notebook revisions, job results, query information, and platform artifacts. Customer data assets can include Delta tables, external data, governed files, and volumes.

> **CRITICAL — WORKSPACE STORAGE:** Never delete, rename, move, empty, repurpose, or manually modify Databricks workspace storage as an ad-hoc troubleshooting action. Treat workspace-storage changes as controlled infrastructure operations requiring architecture review, impact assessment, recovery planning, approval, controlled execution, and validation.

## 9. Modern Storage Guidance

Do not design new production workloads around legacy DBFS root or DBFS mount patterns such as `dbfs:/FileStore` or `dbfs:/mnt/...`. Prefer modern governed storage patterns appropriate to the workload. Treat existing DBFS-based implementations as migration/compatibility scenarios rather than the preferred design for new workloads.

## 10. Unity Catalog

Unity Catalog provides centralized governance for supported data and AI assets. A simplified hierarchy is:

```text
Metastore
└── Catalog
    └── Schema
        ├── Table
        ├── View
        ├── Volume
        ├── Function
        └── Other governed objects
```

The common namespace is `<catalog>.<schema>.<object>`, for example `training.clinical.patient_activity`.

Unity Catalog governs objects; it is not itself cloud object storage. Keep governance and durable storage responsibilities distinct.

## 11. Managed and External Tables

Managed tables provide greater Databricks-managed lifecycle behavior. External tables reference data whose underlying storage lifecycle remains externally managed. This distinction matters for deletion behavior, migration, disaster recovery, interoperability, access troubleshooting, retention, and governance.

## 12. Storage Credentials and External Locations

External cloud-storage access should use governed identity mechanisms. Conceptually: `Unity Catalog → Storage Credential → External Location → Cloud Object Storage`. Authentication implementation differs by cloud provider.

## 13. Credential and Sensitive-Metadata Safety

Never embed AWS access keys, Azure client secrets, GCP private keys, Databricks tokens, database passwords, Kafka credentials, or similar secrets in notebooks, SQL scripts, Git, Confluence, screenshots, or tutorial examples.

Do not place PHI, PII, secrets, or confidential identifiers in workspace names, compute names, job names, run names, tags, catalogs, schemas, demo tables, credential names, storage names, network names, repository names, notebook titles, comments, or screenshots. Use synthetic identifiers such as `training.clinical.patient_activity`, `patient_000001`, `training_job`, and `example_dataset`.

Compliance is a shared responsibility involving platform capabilities, cloud configuration, identity, networking, governance, data handling, operational controls, agreements, and organizational procedures. Platform compliance capabilities do not automatically make a customer architecture compliant.

## 14. Major Network Paths

Troubleshoot network paths separately:

1. User/application inbound connectivity to Databricks.
2. Control-plane/classic-compute connectivity and classic compute access to customer resources.
3. Serverless compute connectivity to customer resources.

Do not treat these as one generic network path.

## 15. Data Access and Troubleshooting Model

A simplified access path is `User/Workload → Workspace → Compute → Unity Catalog Authorization → Governed Object → Storage/External Resource`. Exact paths vary with compute type, table type, cloud, identity, networking, governance, and storage configuration.

Troubleshoot by layer: user/application → workspace → control plane → compute → Unity Catalog/authorization → cloud identity → network → storage/external service. Identify the failing layer before changing configuration.

If workspace, notebook, and compute all work but an external-table SELECT fails, investigate catalog/schema/table privileges, storage credential, external location, cloud identity, storage policy, network connectivity, and object/path availability. Do not simply grant broader access.

For classic compute launch failures, investigate compute policy, cloud quota, VM availability, subnet capacity, cloud permissions, network configuration, and workspace configuration as applicable.

## 16. Production Change Method

Use the sequence: diagnose → identify failing layer → collect evidence → determine minimum change → assess blast radius → define validation → define rollback → approve → change → validate. Avoid trial-and-error production configuration changes.

## 17. Cloud Notes

### AWS

AWS implementations can involve Amazon S3, AWS IAM, VPCs, subnets, security groups, PrivateLink/private connectivity, storage credentials, and external locations. Detailed implementation belongs under `databricks/cloud/aws/`.

### Azure

Azure implementations can involve Azure Storage/ADLS Gen2, Microsoft Entra ID and Azure identity mechanisms, VNets, network security controls, Private Link/private endpoints, storage credentials, and external locations. Detailed implementation belongs under `databricks/cloud/azure/`.

### GCP

GCP implementations can involve Google Cloud Storage, Google Cloud IAM/service accounts, VPCs, firewall controls, Private Service Connect, storage credentials, and external locations. Detailed implementation belongs under `databricks/cloud/gcp/`.

Teach common Databricks concepts once and cloud implementation only where it materially differs. Validate provider, region, workspace type, and classic/serverless behavior before production use.

## 18. Architecture, Cost, and Reliability

Architecture affects Databricks usage, compute, storage, data transfer, private connectivity, cross-region traffic, streaming, logging/retention, and duplicate-data cost. Use current pricing for the actual cloud, region, workload, and compute model.

Production workloads should expect compute termination, worker failure, retries, network failures, source unavailability, credential rotation, cloud throttling, and schema change. Design for idempotency, retry behavior, replay, checkpointing where appropriate, observability, failure isolation, deployment safety, and recovery.

## 20. Team Responsibilities

Platform/cloud teams commonly own cloud architecture, networking, identity integration, and provisioning. Databricks administrators commonly own workspace administration, compute policies, platform configuration, and governance integration. Data engineers own pipelines, Delta design, streaming, and data quality. DBRE/SRE teams focus on reliability, observability, troubleshooting, capacity, and incident response. Developers/analysts own application logic, queries, notebooks, and workload behavior. Exact ownership must be documented by the organization.

## 23. Key Takeaways

The Databricks account is the top-level administrative context. Workspaces are user/workload environments, not the entire architecture. Control and compute planes have different responsibilities. Serverless and classic compute have different operational boundaries. Compute is separate from durable data. Workspace system storage and customer data are different concepts. Workspace storage must not be casually modified. New designs should avoid legacy DBFS root/mount patterns. Unity Catalog governs supported assets but is not cloud storage. IAM, Unity Catalog, networking, compute, and storage are separate troubleshooting layers. Never broaden permissions merely to test. Never expose credentials or sensitive data in tutorial artifacts or metadata. AWS, Azure, and GCP share core concepts but differ materially in infrastructure implementation. Production changes require evidence, impact assessment, validation, and rollback planning.
