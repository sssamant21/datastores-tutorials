## 1. Purpose

A Databricks workspace is where teams develop, analyze, orchestrate, and operate many Databricks workloads. Developers may create notebooks and code; data engineers may develop pipelines and jobs; analysts may execute SQL; and DBRE/SRE and platform teams may troubleshoot compute, permissions, integrations, performance, reliability, and workspace configuration.

A workspace is not the entire Databricks platform. A better model is:

```text
Databricks Account
        │
        ├── Workspace A
        ├── Workspace B
        └── Workspace C
                │
                ├── Workspace assets
                ├── Notebooks
                ├── Git folders
                ├── Jobs / Workflows
                ├── SQL
                └── Compute interaction

Unity Catalog and account-level capabilities operate across or alongside workspace boundaries according to platform configuration.
```

This tutorial explains the workspace as an operational boundary while keeping workspace assets, compute, governance, storage, and cloud infrastructure conceptually separate.

## 2. Learning Objectives

After completing this tutorial, you should be able to explain Databricks account vs workspace; workspace browser, folders, files, notebooks, Git folders, jobs/workflows, SQL and compute interaction; user home folders and `Shared`; workspace permissions vs Unity Catalog privileges; workspace-catalog binding; workspace vs metastore; environment isolation; workspace storage safety; and production troubleshooting.

## 3. Databricks Account vs Workspace

The Databricks account is the top-level administrative context. It can contain account administration, identity, workspaces, and Unity Catalog metastore(s). A workspace exists within this broader platform context. The account and workspace are different architectural concepts.

## 4. What Is a Workspace?

A workspace is an operational environment in a cloud region where teams can develop and run Databricks workloads. It provides an execution and collaboration environment, workspace assets, and workspace-scoped configuration. Exact capabilities depend on configuration, permissions, cloud, region, and enabled features.

## 5. Multiple Workspaces

A Databricks account can contain multiple workspaces. Organizations may separate workspaces based on environment, business domain, geography, security boundary, regulatory requirement, cloud architecture, organizational ownership, or network architecture. `DEV → STAGE → PROD` is a common pattern, not a universal requirement.

## 6. Different Workspace Does Not Mean Complete Isolation

```text
Different Workspace ≠ Automatically Complete Isolation
```

Environment isolation can involve workspace, identity, Unity Catalog, workspace bindings, compute controls, cloud infrastructure, networking, storage, and deployment controls. The exact combination depends on organizational architecture.

## 7. Workspace Browser

The workspace browser is used to navigate supported workspace assets such as notebooks, workspace files, folders, SQL assets, dashboards, alerts, libraries, Git folders, and other supported assets. The UI can evolve, so operational documentation should teach the capability model rather than fixed button locations.

## 8. Workspace Assets vs Governed Data Objects

Workspace assets such as notebooks, workspace files, folders, Git folders, and queries are different from Unity Catalog objects such as catalogs, schemas, tables, views, volumes, and functions. A workspace folder is not a Unity Catalog schema.

## 9. Workspace Folders

Workspace folders organize workspace assets. They do not replace source control, Unity Catalog, or environment isolation.

## 10. Workspace Files

Workspace files can include supported formats such as `.py`, `.sql`, `.ipynb`, `.md`, `.yaml`, `.yml`, and `.txt`. Workspace files are not Unity Catalog tables or volumes.

## 11. Notebooks

Notebooks provide an interactive development environment and can contain executable code, SQL, Markdown, documentation, query results, and visualizations. Typical uses include learning, exploration, development, troubleshooting, experimentation, and prototyping.

## 12. Notebook Is Not Compute

A notebook submits work to compute; it is not itself the compute engine. A notebook opening does not prove compute is healthy, and healthy compute does not prove data access is authorized.

## 13. Notebook Is Not a Deployment Strategy

A notebook can contain production code, but manually clicking Run is not a production deployment strategy. Prefer `Source Control → Review → Validation → Deployment → Job/Workflow → Production`.

## 14. Databricks Git Folders

Current Databricks terminology is **Databricks Git folders**. Older environments and documentation might refer to this capability as **Repos**. New tutorials should use Git folders.

## 15. Git Development Model

A production-oriented model is `Developer → Git Folder → Remote Repository → Review → CI/Validation → Controlled Deployment`. Avoid manual filename versioning. The remote repository and approved deployment process should provide durable version control.

## 16. Git Permission Layers

```text
Git Folder Permission ≠ Git Provider Permission ≠ Unity Catalog Permission
```

A user might access a workspace Git folder but lack permission for a remote Git operation. Git access also does not provide governed-data access.

## 17. Git Credential Safety

Never place Git PATs, OAuth tokens, passwords, client secrets, or SSH private keys in notebook source, workspace files, committed source code, screenshots, Confluence, exposed job parameters, comments, or tutorial examples. Use approved authentication mechanisms.

## 18. Human vs Automation Identity

Interactive development and automated deployment should not automatically share the same identity. Use approved developer identities for interactive work and approved workload identities for CI/CD and automation. Avoid unnecessary dependency on an employee's personal credentials.

## 19. Least Privilege for Git

Use only the Git privileges required for the workflow. If read-only access is sufficient, use read-only credentials rather than granting write access for convenience.

## 20. Git State Is Not Production Evidence

Interactive notebook state should not be treated as durable production evidence. Use source-control history, deployment records, job history, logs, monitoring, and audit information as appropriate.

## 21. Jobs and Workflows

Jobs/workflows support repeatable execution. Production workflows eventually need controls for retries, dependencies, failure handling, timeout, notifications, concurrency, identity, compute, and observability. Those topics are covered later in the series.

## 22. SQL Capabilities

Databricks provides SQL-oriented capabilities for querying governed data. Conceptually: `SQL User → SQL Interface → SQL Compute → Unity Catalog → Table/View`. Avoid tying operational documentation to a particular sidebar position.

## 23. Compute Interaction

Workspace users may interact with serverless, classic, and SQL compute. Do not assume every user should create arbitrary compute. Production organizations commonly control compute types, runtimes, instance types, autoscaling, policies, tags, idle termination, resource limits, and workload types. Compute is covered in Part 1.5.

## 24. User Home Folders

Databricks provides user home folders for individual workspace users. These are useful for individual workspace activity, but `User Home Folder ≠ Production Source of Truth`.

## 25. Production Ownership

Critical production assets should have source control, team ownership, a deployment process, a recovery path, and operational visibility. User lifecycle changes should not make production code unmanageable.

## 26. Shared Workspace Content

Do not interpret `Shared` as secure production sharing. `Shared ≠ secure data sharing`, `Shared ≠ production source control`, and `Shared ≠ Unity Catalog governance`. Review folder permissions, secrets/sensitive-data exposure, team ownership, and source-control requirements before using it.

## 27. Workspace Permissions

Workspace permissions can govern workspace membership, folders, notebooks/files, Git folders, and compute. These controls are different from Unity Catalog privileges.

## 28. Workspace Access vs Data Access

A user can have workspace access while `SELECT production.table` is denied because workspace authorization and Unity Catalog authorization are separate.

## 29. Authorization Layers

Troubleshoot account identity, workspace membership, workspace-object permission, compute permission/policy, Unity Catalog privilege, and workspace binding separately. Do not respond to every `PERMISSION_DENIED` error by granting broader access.

## 30. Unity Catalog Metastore and Workspaces

Multiple workspaces can use a Unity Catalog metastore where supported. The workspace/metastore relationship is region-scoped. Workspace boundaries and governance boundaries should not be assumed to be identical.

## 31. Workspace-Catalog Binding

Unity Catalog workspace-catalog bindings can control which workspaces access catalogs and can provide another layer of environment isolation.

## 32. Privilege Does Not Override Workspace Binding

A principal can have a catalog privilege and still be denied if the workspace is not authorized. Investigate the principal, Unity Catalog privileges, workspace-catalog binding, storage credential, external location, cloud identity, and network/storage as applicable. Do not blindly add `SELECT`, IAM, or storage permissions.

## 33. Binding Changes Are Production Changes

Never modify workspace-catalog bindings experimentally in production. Identify affected catalogs, workspaces, jobs, users/workloads, current configuration and privileges; determine required access; test outside production where possible; define rollback; obtain approval; apply the minimum change; and validate workloads.

## 34. Default Workspace Catalog

Depending on workspace history and Unity Catalog configuration, a workspace may have a default workspace catalog. Do not assume every historical or manually configured workspace has identical default-catalog behavior.

## 35. Workspace Storage

Workspace storage and governed customer-data storage are different concepts. Workspace files and system data can persist independently of individual compute resources.

## 36. Critical — Workspace Storage

```text
CRITICAL — WORKSPACE STORAGE

Never delete, empty, rename, repurpose, or manually modify Databricks workspace storage as a troubleshooting action.

Treat workspace-storage changes as controlled infrastructure operations requiring architecture review, impact analysis, recovery planning, approval, and post-change validation.
```

Workspace-managed platform state is not disposable temporary data.

## 37. DBFS Is Not the Modern Workspace Storage Model

Do not design new production workloads around DBFS root, DBFS mounts, `dbfs:/FileStore`, or `dbfs:/mnt/...`. These are legacy patterns. Use modern governed storage mechanisms appropriate to the workload. Legacy environments may still require migration or compatibility procedures.

## 38. Sensitive Metadata

Never put PHI, PII, secrets, credentials, or confidential identifiers in workspace names, folder/notebook/Git-folder names, Git URLs, job names, compute names, tags, comments, Markdown, screenshots, catalog/schema examples, or demo object names. Use synthetic identifiers.

## 39. Workspace Troubleshooting Model

Break a generic "Databricks isn't working" report into layers: authentication → workspace access → workspace-object access → compute access → workload execution → governed-data access. Do not change configuration until the failing layer is identified.

## 40. Notebook Permission Failure

If workspace login and folder access pass but notebook access fails, start with workspace-object permissions. Do not immediately modify Unity Catalog, storage credentials, cloud IAM, networking, or storage policies.

## 41. Notebook Opens but Data Access Fails

If workspace login, notebook access, and compute pass but `SELECT` fails, investigate principal, Unity Catalog privilege, workspace binding, storage credential, external location, cloud identity, and network/storage as applicable. Do not simply grant administrator privileges.

## 42. Notebook Opens but Compute Cannot Start

Potential investigation areas include compute policy/configuration, cloud capacity, quota, networking, cloud identity, and workspace configuration. The exact path depends on serverless vs classic compute.

## 43. Workspace Administrator Safety

Administrative access should not be a generic troubleshooting mechanism. Identify the authorization layer, determine the minimum required permission, review impact, and apply a controlled change.

## 44. Production Workspace Change Gate

```text
[ ] Identify workspace and environment
[ ] Identify affected object/resource
[ ] Identify failing architectural layer
[ ] Capture current state and evidence
[ ] Check workspace permissions
[ ] Check UC privileges/bindings where relevant
[ ] Identify dependent jobs/users
[ ] Assess security and cost impact
[ ] Assess blast radius
[ ] Validate in non-production where possible
[ ] Define rollback/recovery
[ ] Obtain required approval
[ ] Execute minimum necessary change
[ ] Validate after the change
```

## 45. Cloud-Aware Workspace Architecture

The workspace concept is common across supported Databricks clouds, while infrastructure implementation differs. Cloud-specific implementation belongs under `databricks/cloud/aws/`, `databricks/cloud/azure/`, and `databricks/cloud/gcp/`.

## 46. AWS Notes

AWS workspace architecture can involve AWS accounts, Amazon S3, AWS IAM, VPCs, subnets, security groups, and private connectivity. Exact implementation depends on workspace, compute, network, region, and security configuration.

## 47. Azure Notes

Azure workspace architecture can involve Azure subscriptions, resource groups, Azure Storage/ADLS Gen2, Microsoft Entra ID, VNets, subnets, and private connectivity. Exact implementation depends on the Azure Databricks architecture selected by the organization.

## 48. GCP Notes

GCP workspace architecture can involve GCP projects, Google Cloud Storage, Google Cloud IAM, service accounts, VPCs, subnets, and private connectivity. Do not copy provider-specific runbooks between clouds without validation.

## 49. Cost Awareness

Workspace activity can trigger compute and infrastructure costs through compute, SQL compute, jobs, streaming, storage, and data transfer. Before running a workload, consider what compute executes it, duration, autoscaling, idle termination, data volume, and cross-region/external transfer.

## 50. Hands-On Lab

### Goal

Explore an approved Databricks workspace while making **no intentional data, object, permission, compute, network, or storage changes**.

### Lab Safety

- Use an approved development/training workspace.
- Use approved existing compute only.
- Do not create or delete workspace objects.
- Do not start, stop, resize, or modify compute.
- Do not change permissions or workspace bindings.
- Do not modify workspace configuration.
- Never expose credentials, tokens, PHI, or PII.
- Do not record confidential infrastructure identifiers.

## 51. Lab Step 1 — Observe Workspace Capabilities

Using the workspace browser, locate—without changing anything—areas corresponding to workspace assets, jobs/workflows, SQL, compute, and catalog/data. The exact UI can vary.

## 52. Lab Step 2 — Current Identity and Namespace

```sql
SELECT
    current_user() AS current_user,
    current_catalog() AS current_catalog,
    current_schema() AS current_schema;
```

Identify identity, catalog, and schema without changing context.

## 53. Lab Step 3 — Visible Catalogs

```sql
SHOW CATALOGS;
```

Observe only. A catalog not shown to your identity should not automatically be assumed not to exist.

## 54. Lab Step 4 — Visible Schemas

```sql
SHOW SCHEMAS;
```

No `USE CATALOG` command is required for the acceptance lab.

## 55. Lab Step 5 — Visible Tables

```sql
SHOW TABLES;
```

No `USE SCHEMA` command is required.

## 56. Lab Step 6 — Verify Context

```sql
SELECT
    current_user() AS current_user,
    current_catalog() AS current_catalog,
    current_schema() AS current_schema;
```

Confirm the context remains unchanged.

## 57. Lab Step 7 — Observe Existing Compute

If authorized, inspect an existing approved compute resource. Observe compute type, runtime if applicable, state, autoscaling if visible, and idle termination if visible. Do not create, start, stop, restart, resize, edit, or delete compute.

## 58. Lab Architecture Exercise

Map `Databricks Account → Workspace → Workspace Asset → Compute → Unity Catalog → Catalog → Schema → Table`. If approved and visible, identify cloud (AWS/Azure/GCP) and compute type (Serverless/Classic/SQL).

## 59. Lab Acceptance Criteria

The learner should be able to explain account vs workspace; workspace browser; workspace asset vs governed object; workspace folder vs schema; workspace file vs Unity Catalog volume; notebook vs compute; Git folders; Git vs data permissions; user home folders; Shared-folder safety; workspace permission vs UC privilege; workspace-catalog binding; same-region workspace/metastore relationship; development vs production behavior; workspace storage safety; and AWS/Azure/GCP differences.

Safety acceptance requires no workspace objects created/deleted, no data or context changes, no permission/binding/compute/storage/network changes, no credentials exposed, and no PHI/PII used.

## 61. Key Takeaways

1. A workspace is an operational environment within the broader Databricks account.
2. A Databricks account can contain multiple workspaces.
3. Separate workspaces alone do not guarantee complete isolation.
4. The workspace browser contains workspace assets; it is not the Unity Catalog namespace.
5. Workspace folders are not schemas, and workspace files are not Unity Catalog tables or volumes.
6. A notebook is not compute or a production deployment strategy by itself.
7. Current terminology is **Git folders**; older material may refer to Repos.
8. Git-folder, Git-provider, and Unity Catalog permissions are separate.
9. Production automation should use approved workload identities rather than unmanaged personal credentials.
10. User home folders should not hold the only authoritative copy of critical production code.
11. `Shared` should not be treated as secure data sharing or source control.
12. Workspace access does not automatically provide governed-data access.
13. Multiple same-region workspaces can interact with a Unity Catalog metastore where configured.
14. Workspace-catalog bindings provide another governance/isolation control.
15. Workspace-binding changes require production change control.
16. Workspace storage must never be casually deleted or modified for troubleshooting.
17. DBFS root and mounts should not be the default for new production workloads.
18. Sensitive information must not appear in workspace metadata or tutorial artifacts.
19. AWS, Azure, and GCP share common workspace concepts but differ in infrastructure implementation.
20. Production workspace changes require evidence, blast-radius analysis, validation, approval, and rollback/recovery planning.
