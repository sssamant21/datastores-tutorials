## Purpose

A production Databricks implementation should begin with understanding how data moves through the platform—not simply with creating notebooks or compute.

A production architecture should answer where data originates, how it enters the platform, where ingested data is retained, how it is validated and transformed, how unexpected records are handled, how assets are governed and consumed, and how downstream data can be recovered or reprocessed.

## Data lake, warehouse, and lakehouse

A data lake provides scalable storage for large quantities of structured, semi-structured, and unstructured data. Cloud object storage commonly provides the underlying durable storage. Storage alone does not automatically provide all capabilities needed for production analytics, so transactions, schema management, data quality, governance, security, discoverability, lineage, reliable processing, and recovery still need deliberate design.

A data warehouse traditionally focuses on structured analytical workloads, SQL analytics, reporting, and business-oriented data models.

A lakehouse architecture aims to provide reliable, governed data assets over scalable lake-oriented storage while supporting analytical and data-processing workloads. It should not be understood merely as a data lake plus a separate warehouse. A useful mental model is scalable storage + reliable table semantics + governance + multiple processing workloads.

## Databricks lakehouse mental model

```text
DATA SOURCES
    │
    ├── Databases
    ├── Kafka
    └── Files / APIs
    │
    ▼
INGESTION
    │
    ▼
BRONZE — raw / ingested
    │
    │ validation / quality
    ▼
SILVER — validated / refined
    │
    │ business logic
    ▼
GOLD — business-ready
    │
    ├── BI
    ├── ML
    └── Applications

<──── UNITY CATALOG GOVERNANCE ────>

Delta Lake / governed data
    │
Cloud storage
```

This is a conceptual model. Implementations vary according to workload, cloud, governance, latency, cost, recovery, and organizational requirements.

## Compute

Compute executes SQL, Python, Spark, ETL, streaming, and machine-learning processing. Databricks offers different compute models, including serverless and classic compute. Compute should not be confused with durable data storage, and different services can have different operational responsibilities.

## Delta Lake

Delta Lake is an open-source storage framework used extensively by Databricks lakehouse workloads. It provides capabilities including ACID transactions, schema enforcement, schema evolution capabilities, scalable table metadata, and support for batch and streaming processing.

Conceptually, a Delta table combines transaction metadata with data files stored in durable storage. Delta Lake does not replace governance; governance belongs to the architecture surrounding the data assets.

## Unity Catalog

Unity Catalog provides centralized governance for supported data and AI assets, including capabilities in areas such as access control, discovery, lineage, and auditing.

Governance should span Bronze, Silver, and Gold rather than being introduced only after Gold data is created.

## Managed and external tables

Unity Catalog supports managed and external tables. With managed tables, Unity Catalog manages the table and storage lifecycle. With external tables, Unity Catalog governs the table while the underlying storage lifecycle remains externally managed.

For most new lakehouse workloads, Databricks recommends managed tables. External tables remain useful for requirements such as externally managed storage, existing data layouts, interoperability, or other architecture constraints.

Managed does not mean Databricks owns the organization's data. The underlying data remains in the organization's configured cloud-storage environment. Managed versus external is an architecture and lifecycle-management distinction.

## Governed files and volumes

Not all assets are tabular. Images, documents, libraries, model artifacts, raw files, and other non-tabular assets can require governance. Unity Catalog volumes provide a governed mechanism for working with files. Volumes are covered in greater depth later in this series.

## Medallion architecture

Databricks recommends the medallion architectural pattern for many lakehouse pipelines:

```text
BRONZE → SILVER → GOLD
```

These are logical refinement stages. They do not inherently mean three Databricks accounts, workspaces, storage accounts, or compute resources. Medallion architecture is a recommended design pattern, not a mandatory requirement for every workload.

## Bronze layer

Bronze typically represents the initial persistent ingestion layer. Possible sources include PostgreSQL, MySQL, Oracle, Kafka, cloud storage, files, APIs, and application events.

Bronze commonly preserves source fidelity and sufficient history to support reprocessing, auditing, troubleshooting, recovery, and downstream transformation.

### Bronze does not mean retain forever

Raw-data retention should be explicitly designed around recovery requirements, source replay capability, compliance, privacy/deletion requirements, storage cost, and operational requirements. "Keep Bronze" must not be interpreted as keeping every raw record forever.

## Silver layer

Silver contains validated and refined data. Typical processing can include schema validation, type conversion, null handling, deduplication, data-quality checks, normalization, joins, and enrichment.

In the medallion pattern, Bronze provides a useful ingestion boundary before potentially changing or malformed source data is promoted into validated Silver datasets.

## Gold layer

Gold contains highly refined data aligned to downstream business requirements. Processing can include business rules, semantic models, metrics, aggregations, dimensional models, and domain-specific datasets. Gold should not be defined only as aggregated data; its defining characteristic is refinement for intended consumers.

## Batch and streaming

Batch workloads process bounded sets of data, while streaming workloads process continuously or incrementally arriving data. The same logical Bronze → Silver → Gold refinement model can support both, although their implementation and operational characteristics can differ.

Production platforms frequently use both batch and streaming. Governance should remain consistent across appropriate assets regardless of ingestion mode.

## Schema drift

Production sources change. Columns can be added or removed, data types can change, unexpected fields can arrive, records can be malformed, and producer versions can change.

A production pipeline should detect and deliberately handle these changes:

```text
SOURCE SCHEMA CHANGE
        │
        ▼
      Detect
        │
        ├── Expected → controlled schema evolution
        │
        └── Unexpected → rescue / quarantine / investigate
```

Never assume every schema change should automatically be accepted.

## Unexpected and invalid data

Production pipelines should define what happens when data does not satisfy expectations. Depending on the ingestion technology and requirements, invalid or unexpected records might be rescued, quarantined, alerted on, or investigated. Silently dropping unexpected data can hide source and data-quality problems.

## Streaming checkpoints

Streaming systems maintain operational state. Checkpoint information can include processed offsets, commit information, stateful-processing information, and recovery metadata. A checkpoint is part of the operational state of a streaming pipeline and should not be treated as disposable temporary data.

### Checkpoint safety

Never delete, replace, reuse, or reset a production streaming checkpoint merely to clear a pipeline failure.

Before changing checkpoint state:

1. Identify the actual failure.
2. Determine source replay behavior.
3. Evaluate duplicate-processing risk.
4. Validate sink idempotency.
5. Review stateful-processing impact.
6. Define recovery and rollback.
7. Follow the production change process.

Checkpoint manipulation belongs in an operational runbook, not an introductory lab.

## Replay and reprocessing

A recoverable ingestion layer can allow downstream data to be rebuilt, but replay is not automatically safe. Production designs should account for duplicate records, repeated side effects, incorrect merge keys, streaming state, downstream consumers, and historical corrections.

Pipelines should consider stable record identifiers, deduplication, idempotent processing, appropriate transactional writes, controlled backfills, checkpoint/state behavior, and downstream impact.

## Failure recovery example

If a transformation bug produces incorrect Silver and Gold data, retained Bronze data may allow a controlled replay after the transformation is corrected. Recovery should be planned and tested rather than improvised during an incident.

## Unity Catalog and storage access

Governance can be weakened if teams bypass approved access patterns. Avoid giving ordinary workloads unnecessary broad direct access to cloud object storage. Cloud IAM and Unity Catalog controls should be designed together so users and workloads access governed objects through approved patterns.

## Credential safety

Never place AWS access keys, Azure secrets, service-principal secrets, Databricks tokens, database passwords, Kafka credentials, or storage credentials directly in Git repositories, notebooks, Confluence, screenshots, tutorials, SQL files, Python files, logs, or architecture diagrams. Use approved identity and secret-management mechanisms.

## Team responsibilities

Application teams commonly own producer contracts and source behavior. Data engineering commonly owns ingestion, transformation, data quality, and pipeline logic. Platform/SRE teams commonly own platform reliability, compute, networking, observability, and operational controls. Security/governance teams commonly own identity, permissions, and governance policies. Analytics/business teams commonly own semantic models, metrics, and dashboards. Exact ownership depends on the organization and should be documented rather than assumed.

## Key takeaways

1. A lakehouse is more than a data lake connected to a warehouse.
2. Delta Lake provides reliable table capabilities over scalable storage.
3. Unity Catalog provides governance across lakehouse assets.
4. Bronze, Silver, and Gold are logical refinement layers.
5. Medallion architecture is recommended, not mandatory for every workload.
6. Bronze retention must be explicitly designed.
7. Silver provides an important validation and quality boundary.
8. Gold represents consumer-oriented refined data, not merely aggregations.
9. Managed tables are generally preferred for new lakehouse workloads, while external tables serve specific lifecycle/interoperability requirements.
10. Schema drift and invalid data require deliberate handling.
11. Streaming checkpoints are operational state and must be protected.
12. Reprocessing must account for duplicates, state, and idempotency.
13. Governance, security, reliability, recovery, and cost belong in the architecture from the beginning.
