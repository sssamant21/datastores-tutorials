## 1. Purpose

Databricks notebooks provide an interactive environment for developing, documenting, executing, testing, and troubleshooting data workloads. A notebook can combine executable code, SQL, Markdown documentation, parameters, visualizations, and execution results.

```text
User
 │
 ▼
Databricks Notebook
 │
 ├── Code
 ├── SQL
 ├── Markdown
 ├── Parameters
 └── Results
 │
 ▼
Compute
 │
 ▼
Unity Catalog
 │
 ▼
Governed Data
```

The first principle is **Notebook ≠ Compute**. A notebook contains code, documentation, and interactive state; compute executes the workload.

## 2. Learning objectives

After completing this tutorial, learners should understand notebooks vs compute, cells, executable languages, default language and magic commands, Markdown, execution order and hidden state, language REPL isolation, clean-session reproducibility, widgets and parameter validation, dependencies and `%run`, reusable modules, Git folders, notebook history, notebook/compute/Unity Catalog authorization, serverless execution, Lakeflow Jobs notebook tasks, secret and sensitive-data safety, production notebook design, troubleshooting, and cloud-specific integration boundaries.

## 3. Notebook structure

A notebook is an interactive document containing executable commands, documentation, and results. Cells can be executed interactively, so visual cell order does not prove execution history.

```text
Notebook
├── Markdown
├── Python
├── SQL
├── Scala
└── R
```

Python, SQL, Scala, and R are executable language contexts where supported. Markdown is documentation, not another programming language.

## 4. Notebook vs compute

The notebook itself does not provide processing resources.

```text
Notebook → Supported Compute → Execution
```

Depending on workspace and workload capabilities, execution can use serverless interactive compute or another appropriate supported compute option. A notebook can exist while compute is unavailable, and notebook permission does not imply compute permission.

## 5. Default language and magic commands

A notebook has a default language. Individual cells can select another supported language context with magic commands such as `%python`, `%sql`, `%scala`, and `%r`; `%md` renders Markdown. This list is not exhaustive. A cell magic belongs at the beginning of its cell. Keep each cell's execution intent clear.

Changing the default language can affect how existing cells are interpreted and should be treated carefully in production notebooks.

## 6. Execution order and hidden state

Interactive execution can occur in an order different from visual source order. Hidden state can include variables, imports, temporary views, cached data, widget values, configuration, previously executed cells, and session namespace.

```text
Notebook Source → Looks Correct → Hidden Session State → Unexpected Behavior
```

A successful interactive run is not sufficient evidence that a notebook is production-reproducible.

## 7. Language REPL isolation

Do not assume variables created in one language execution context automatically exist in another. Python, Scala, R, and SQL execution contexts can have distinct state. Cross-language workflows should use supported mechanisms rather than assuming shared variables.

## 8. Clean-session reproducibility

Production-oriented notebooks should execute through their intended path from a known state with known parameters and produce the expected logical result.

```text
Clean Session → Known Parameters → Intended Execution Path → Validate Result
```

Do not restart shared production compute merely to clear notebook state. Restart can interrupt users/jobs/streams, destroy troubleshooting evidence, and create startup time or cost. Perform clean-session testing using approved development or validation resources.

## 9. Variables and production configuration

Notebook variables are convenient during development but should not become undocumented production configuration. Avoid operational procedures that require opening a notebook, manually changing `dev` to `prod`, and pressing Run. Production configuration should use controlled mechanisms.

## 10. SQL and explicit object names

SQL execution still depends on identity, notebook access, compute access, Unity Catalog authorization, and object privileges. Opening a notebook does not grant access to referenced data.

Where it improves clarity and production safety, prefer explicit three-level object names such as `catalog.schema.table`. This is a recommendation, not an absolute requirement; controlled session context can also be intentional.

## 11. Widgets and parameters

Common widget types include text, dropdown, combobox, and multiselect. Widget values should be treated as strings until validated and converted. Widget capabilities can differ by execution environment, including cluster-backed notebooks and SQL warehouse execution.

```text
Widget/Parameter
      ↓
Validate
 ├─ required?
 ├─ type?
 ├─ format?
 ├─ allowed value?
 ├─ range?
 └─ environment?
      ↓
Convert
      ↓
Application Logic
```

A parameter such as `environment=prod` is not an authorization mechanism. Security still comes from identity, workspace authorization, compute authorization, Unity Catalog privileges, and cloud/external-resource authorization.

When parameters influence catalogs, schemas, tables, paths, or filters, do not blindly concatenate arbitrary values into executable SQL. Validate identifiers against approved values and use supported parameterization mechanisms where applicable.

## 12. Dependencies, `%run`, and reusable code

Notebooks can depend on libraries, modules, other notebooks, tables, volumes, files, secrets, external APIs, and runtime capabilities. Important dependencies should be explicit.

Databricks supports `%run` for executing another notebook in a notebook execution flow, but avoid deep chains such as `A → B → C → D → E`. They create hidden dependencies, state coupling, versioning difficulty, unclear ownership, and troubleshooting complexity.

Prefer reusable modules/packages and explicit workflow dependencies where appropriate:

```text
Reusable Module / Package → Notebook → Workflow
```

## 13. Git-backed development and history

Use Databricks **Git folders** and remote source control where appropriate for production engineering.

```text
Developer → Git Folder → Remote Git → Review → Validation/CI → Versioned Change → Controlled Deployment
```

The workspace copy should not become the only production source of truth. Notebook history is useful for inspection and recovery but is not a replacement for source control, peer review, testing, release traceability, or deployment controls.

Production rollback should identify a known-good controlled version, perform a controlled rollback, and validate it rather than relying on manual cell editing.

## 14. Authorization layers

Notebook permissions, compute permissions, and Unity Catalog privileges are separate layers.

```text
Identity
  ↓
Workspace / Notebook Permission
  ↓
Compute Authorization
  ↓
Unity Catalog Authorization
  ↓
External Resource Authorization
```

Being able to edit a notebook does not grant access to every table. Being able to query a table does not grant notebook-management rights. Fix authorization failures at the failing layer and follow least privilege.

Notebook permission changes are production security changes because they can expose code, results, execution capability, and modification capability.

## 15. Serverless notebook execution

Where supported and configured, notebooks can execute using serverless interactive compute. Do not teach the outdated assumption that every notebook must first be manually attached to a classic cluster. Serverless notebook availability depends on applicable workspace capabilities and Unity Catalog requirements.

Serverless reduces infrastructure-management work but does not remove security, governance, reliability, networking, or FinOps responsibilities. Read-only notebook execution can still consume compute and incur cost.

## 16. SQL warehouses and notebooks

SQL notebooks can use SQL warehouse capabilities where supported. A stopped SQL warehouse can automatically start when an authorized query requires it, so read-only SQL does not mean no compute action or zero cost.

For Lakeflow Jobs notebook tasks, SQL warehouse suitability depends on notebook content: a SQL-only notebook with SQL as its default language can use an appropriate SQL warehouse where supported, while Python, Scala, R, or mixed-language notebook tasks require appropriate supported compute.

Do not start a stopped SQL warehouse solely to complete the hands-on lab.

## 17. Lakeflow Jobs and production execution

Notebooks can run as tasks in Lakeflow Jobs:

```text
Schedule/Trigger → Lakeflow Job → Notebook Task → Compute → Execution
```

For repeatable production workloads, prefer controlled workflows with explicit parameters, dependencies, retries, execution identity, monitoring, and failure handling rather than relying on a person to open a notebook and press Run.

## 18. Rerun and idempotency safety

A failed notebook does not imply that nothing changed. Before rerunning a failed task, determine whether partial writes occurred, understand transaction boundaries and retry behavior, assess partial state, and determine whether processing is idempotent.

```text
Task Failed → Partial writes? → Assess state → Controlled rerun
```

Never assume `Failure = No Data Change`.

## 19. Secrets and credentials

Never hardcode secrets, passwords, tokens, long-lived cloud keys, or private keys in notebook source, Markdown, widgets, parameters, comments, Git, or screenshots. Use approved identity and secret-management mechanisms.

Secure retrieval is not the same as safe handling. A securely retrieved secret can still be leaked through `print`, logs, exceptions, notebook output, debugging, screenshots, or copied incident evidence.

## 20. Sensitive data and notebook output

Minimize PHI, PII, credentials, tokens, and confidential data in notebook results. Use synthetic data for training. Production troubleshooting should retrieve only the minimum information needed.

Avoid broad `SELECT *` inspection of sensitive tables when targeted aggregates or selected non-sensitive columns answer the operational question. The same principle applies to DataFrame previews and `display(df)`.

Notebook results can persist or become stale. A visible result does not prove that code just ran. Before treating notebook output as evidence, understand execution time, identity, compute, parameters, catalog/schema, and relevant input state.

Notebook cell output is not the authoritative operational system of record. Use appropriate job-run history, application logs, audit logs, metrics, monitoring, and observability systems.

## 21. Sensitive metadata

Keep PHI, PII, secrets, and confidential identifiers out of notebook names, folder names, Markdown, comments, widget labels, parameter defaults, job names, tags, and screenshots. Use non-sensitive operational naming.

## 22. Temporary state is not authoritative state

Variables, temporary views, caches, local temporary files, and session configuration are execution state, not authoritative persistent state. Critical production data belongs in approved persistent storage governed through the appropriate platform controls.

## 23. Performance troubleshooting

A slow notebook does not automatically mean the notebook object or compute size is the problem. Investigate the slow cell and determine whether the bottleneck is SQL, Spark, Python, compute, data volume, shuffle, skew, source latency, networking, or an external dependency.

```text
Observe → Find slow cell → Identify operation → Collect evidence → Fix appropriate layer
```

Do not immediately increase workers, switch access mode, restart compute, change runtime, or weaken governance without evidence.

## 24. Troubleshooting patterns

**Cannot run:** check notebook permission, compute availability/permission, language/runtime compatibility, libraries, data authorization, and external dependencies.

**Undefined variable:** check initialization, language context, session state, execution order, and imports.

**Works interactively but fails as a job:** compare identity, parameters, compute, runtime, libraries, environment, paths, Unity Catalog privileges, networking, secrets, external dependencies, and hidden state.

**Works for one user only:** compare notebook permission, compute permission, execution identity, Unity Catalog privileges, workspace bindings, secrets, external identity, and environment.

**Different result after rerun:** investigate cell order, session state, language context, changed input data, parameters, catalog/schema, caches, temporary views, time-dependent logic, randomness, and external dependencies.

## 25. Cloud-aware model

Notebook fundamentals are largely common across AWS, Azure, and GCP. Cloud differences become important when notebook workloads interact with storage, identity, networking, secrets, external services, or cloud SDKs.

- **AWS:** integrations can include Amazon S3, AWS IAM, AWS services, private networking, and AWS SDKs. Never hardcode long-lived AWS keys.
- **Azure:** integrations can include ADLS/Azure Storage, Microsoft Entra identity, Azure services, private networking, and Azure SDKs. Never hardcode client secrets or storage keys.
- **GCP:** integrations can include Google Cloud Storage, Google Cloud IAM, service accounts, private networking, and Google Cloud SDKs. Never put service-account private keys in notebook source.

Teach common notebook concepts once and add cloud-specific implementation only where materially different.

## 27. Production notebook safety

```text
┌──────────────────────────────────────────────────────────────┐
│ PRODUCTION NOTEBOOK SAFETY                                   │
│ • Do not depend on undocumented interactive state.           │
│ • Do not treat visual cell order as execution evidence.      │
│ • Validate production logic from a known clean session.      │
│ • Avoid deep notebook-to-notebook dependency chains.         │
│ • Validate and constrain all parameters/widgets.             │
│ • Never treat a parameter as an authorization control.       │
│ • Never hardcode, print, log, or commit secrets.             │
│ • Minimize PHI/PII/confidential data in notebook output.     │
│ • Keep notebook, compute, and data permissions separate.     │
│ • Use source control and review for production changes.      │
│ • Prefer controlled workflows for repeatable production.     │
│ • Check partial writes before rerunning failed workloads.    │
│ • Treat read-only execution as potentially cost-producing.   │
│ • Diagnose performance before changing compute.              │
│ • Define validation and rollback before deployment.          │
└──────────────────────────────────────────────────────────────┘
```

## 28. Team responsibility model

Developers should understand notebook state, execution order, languages, dependencies, modules, Git, and parameters. Data engineers should understand notebook tasks, workflow execution, idempotency, data dependencies, parameters, and performance. Analysts should understand SQL notebooks, SQL warehouses, query cost, and output exposure. DBRE/SRE should understand execution evidence, hidden state, failure isolation, compute dependencies, job-run troubleshooting, and operational safety. Platform administrators should understand notebook/compute permissions, serverless access, runtime capabilities, Git governance, security, and FinOps controls.

## 29. Hands-on lab

Use `labs/notebook-fundamentals-check.sql` in an approved training/development workspace on approved existing compute. The lab inspects current session identity/context and visible catalogs/schemas/tables, executes deterministic stateless SQL, and verifies context again. It intentionally performs no data, object, permission, compute, runtime, policy, storage, networking, or namespace mutation.

Manual observation may include notebook default language, cell types, existing compute type, serverless/classic/SQL Warehouse classification, execution status, and existing notebook permissions if authorized. Observation must not change those settings.

## 31. Key takeaways

1. Notebook and compute are separate concepts.
2. Notebook, compute, and data authorization are separate layers.
3. Python, SQL, Scala, and R are supported notebook language contexts where applicable; Markdown documents the notebook.
4. Visual cell order does not prove execution order.
5. Hidden state and cross-language state assumptions are reliability risks.
6. Production notebooks should be reproducible from a known clean state.
7. Parameters/widgets must be validated and are not security boundaries.
8. Avoid deep `%run` chains; prefer reusable modules and explicit workflows.
9. Use Git folders, remote source control, review, validation, and controlled deployment.
10. Notebook history is not a replacement for production source control.
11. Serverless execution reduces infrastructure management but does not remove governance, security, reliability, or cost responsibility.
12. Read-only SQL/notebook execution can still create compute activity and cost.
13. Production reruns require partial-state and idempotency analysis.
14. Never hardcode or expose secrets.
15. Minimize sensitive data in results, logs, metadata, and screenshots.
16. Notebook output can be stale and is not the authoritative operational record.
17. Diagnose the actual slow operation before changing compute.
18. AWS, Azure, and GCP share notebook fundamentals while external integrations differ.
