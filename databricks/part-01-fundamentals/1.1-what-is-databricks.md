## Purpose

Databricks is an integrated data and AI platform used for workloads including data engineering, SQL analytics, batch and streaming processing, machine learning, AI, governance, and workflow orchestration. This tutorial establishes the architectural foundation needed before working with notebooks, compute, Delta Lake, Unity Catalog, Databricks SQL, jobs, or production pipelines.

## Learning objectives

After completing this tutorial, you should be able to:

- Explain what Databricks and a lakehouse are.
- Identify the major Databricks platform components.
- Distinguish account and workspace scopes.
- Explain the conceptual separation of durable storage and compute.
- Describe the purposes of Delta Lake and Unity Catalog.
- Understand the `catalog.schema.object` namespace.
- Explain the conceptual difference between serverless and classic compute.
- Navigate catalogs and schemas safely with the companion read-only lab.

          |                |                |
    Data Engineers      SQL / BI         ML / AI

                  DATABRICKS PLATFORM
                           |

The exact architecture depends on the cloud provider, networking model, compute type, security configuration, and services in use.

## Lakehouse architecture

A lakehouse combines characteristics traditionally associated with data lakes and data warehouses so that data engineering, analytics, BI, ML, and AI workloads can operate against governed data assets.

A common organizational pattern is the medallion architecture:

```text
Sources
   |
   v
+--------+      +--------+      +--------+
| BRONZE | ---> | SILVER | ---> |  GOLD  |
| raw    |      | clean  |      | ready  |
+--------+      +--------+      +--------+
                                    |
                              +-----+-----+
                              |     |     |
                             BI    ML    Apps
```

Bronze typically preserves ingested/source-oriented data, Silver refines and validates it, and Gold prepares data for business or downstream consumption. Medallion is a design pattern, not a requirement that every workload contain exactly three physical layers.

## Account and workspace

A Databricks account and a Databricks workspace represent different administrative scopes.

```text
Databricks Account
       |
       +-- Account-level administration
       +-- Identity/governance configuration
       +-- Workspaces
              |
              +-- Notebooks
              +-- Jobs
              +-- SQL
              +-- Compute
```

A workspace is a collaborative environment for working with Databricks resources and workloads.

## Control plane and compute plane

At a high level, Databricks separates platform management services from workload execution.

```text
                  DATABRICKS
                      |
          +-----------+-----------+
          |                       |
     CONTROL PLANE           COMPUTE PLANE
          |                       |
 Platform management        Workload execution
                                  |
                          +-------+-------+
                          |               |
                     Serverless        Classic
```

Exact placement and responsibility boundaries differ by cloud provider and compute model. This distinction matters later for networking, private connectivity, security, data access, and troubleshooting.

## Compute fundamentals

Do not assume `Databricks compute = cluster` is the complete modern model. A useful introductory model is:

```text
Compute
   |
   +-- Serverless compute
   +-- Classic compute
```

Serverless allows Databricks to manage more of the underlying compute infrastructure. Classic compute exposes a different infrastructure and operational model. The appropriate choice depends on workload support, security, networking, organizational policies, and platform architecture.

## Storage and compute

Durable data and workload compute are separate architectural concerns.

```text
Compute
   |
   | reads/writes
   v
Data Assets
   |
   v
Durable Storage
```

This separation supports workload isolation, scaling, reliability, and cost management. It is a conceptual model; not every Databricks service follows one identical physical data path.

## Delta Lake

Delta Lake provides a table/storage foundation for many Databricks lakehouse workloads. Later tutorials cover transactional table operations, schema enforcement and evolution, `MERGE`, updates/deletes, time travel, maintenance, data layout, and optimization.

```text
Application / SQL / Spark
          |
          v
      Delta Table
          |
          v
      Data Storage
```

## Unity Catalog

Unity Catalog provides centralized governance for data and AI assets, including access control, discovery, auditing, lineage, and object organization.

```text
Unity Catalog
      |
   Metastore
      |
    Catalog
      |
    Schema
      |
      +-- Table
      +-- View
      +-- Volume
      +-- Function
      +-- Other governed objects
```

The important namespace is:

```text
<catalog>.<schema>.<object>
```

For a table, for example:

```sql
SELECT *
FROM healthcare_prod.patient.encounters;
```

The names are synthetic examples only.

## Catalogs and governance

A catalog should not simply be treated as a folder. Catalog design can participate in data isolation, organizational boundaries, environment separation, access management, and governance. There is no single naming model appropriate for every organization; catalog structure should be an explicit governance decision.

## Permissions

Access to Databricks does not automatically mean access to every data object. Conceptually, an identity may need privileges that allow it to navigate the catalog/schema hierarchy and separate privileges to perform actions on objects.

```text
USE CATALOG != SELECT everything
USE SCHEMA  != SELECT everything
```

Production permissions should follow least privilege.

## Databricks SQL, notebooks, and workflows

Databricks SQL provides SQL-oriented analytics capabilities and SQL warehouses for supported workloads. Notebooks provide interactive development environments. Jobs/workflows provide automation and orchestration for production execution.

A production pipeline should not depend on an engineer manually opening a notebook and pressing Run. Production designs also need source control, testing, deployment, monitoring, failure handling, access controls, secret management, and cost controls.

## Production safety principles

From the beginning, use:

```text
Least privilege
      +
Governed data
      +
Approved compute
      +
Secure credentials
      +
Auditability
      +
Environment isolation
```

Do not assume that placing data in Databricks automatically makes a workload secure or compliant.

### Sensitive data

Tutorials must use synthetic or explicitly approved non-production data. Do not put real PHI, PII, credentials, tokens, or other sensitive information in tutorial notebooks, repository files, Confluence pages, screenshots, SQL comments, job names, tags, or compute names.

### Credential safety

Never hard-code passwords or access tokens in notebooks, Git, Confluence, or example code. Use organization-approved identity and secret-management mechanisms.

### Legacy DBFS patterns

Do not automatically adopt older examples built around DBFS root or DBFS mounts for new Unity Catalog-oriented architectures. Evaluate current supported storage patterns, including Unity Catalog-governed options, according to the use case and current vendor guidance.

### Cost safety

Databricks workloads can incur Databricks and cloud costs. Use only approved compute for tutorial exercises. Production cost management should include appropriate policies, workload sizing, autoscaling/termination controls where applicable, tagging, budgets, and usage monitoring. Budget notifications should not be treated as a hard spending stop unless a separately implemented control provides that behavior.
