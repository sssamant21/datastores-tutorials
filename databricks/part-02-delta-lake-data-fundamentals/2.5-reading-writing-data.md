# Part 2.5 — Reading/Writing Data

**Track:** Databricks Production Tutorials  
**Part:** 2 — Delta Lake & Data Fundamentals  
**Status:** Revised Final / Canonical Edition

## Learning objectives

By the end of this tutorial, you should be able to:

- read Delta tables safely using fully qualified names;
- use explicit projections, filters, ordering, and limits;
- distinguish append, update, delete, merge, and replacement operations;
- understand Delta transaction guarantees without confusing ACID with business idempotency;
- use explicit column lists and recognize schema-enforcement failures;
- treat schema evolution as a controlled contract change;
- design deterministic merge/upsert logic;
- reason about concurrent-write conflicts and safe retries;
- plan bounded, recoverable backfills;
- validate data before and after production writes.

## 1. Reading data

A fully qualified Unity Catalog table reference uses:

```text
catalog.schema.table
```

For production troubleshooting, prefer explicit qualification when ambiguity is possible.

A basic read:

```sql
SELECT
    event_id,
    patient_id,
    event_timestamp,
    event_type
FROM clinical.silver.patient_activity
WHERE event_timestamp >= TIMESTAMP '2026-09-18 00:00:00'
ORDER BY event_timestamp
LIMIT 100;
```

Explicit projection is usually safer than `SELECT *` when only a subset of fields is needed, especially for wide or sensitive datasets.

## 2. Delta transaction model

Delta tables provide transactional reads and writes.

Conceptually:

```text
Reader
  |
  +----> consistent table snapshot

Writer
  |
  +----> Delta transaction
              |
              +---- commit
              |
              +---- fail/conflict
```

A successful transaction protects table consistency. It does not automatically guarantee that repeating the same business operation is safe.

Remember:

```text
ACID transaction != idempotent pipeline
```

## 3. INSERT — append data

A simple insert can append rows:

```sql
INSERT INTO clinical.silver.patient_activity (
    event_id,
    patient_id,
    event_timestamp,
    event_type
)
VALUES (
    'EVT-1001',
    'P-100',
    TIMESTAMP '2026-09-18 14:10:00',
    'VISIT'
);
```

Prefer explicit target columns.

An insert from another relation can use:

```sql
INSERT INTO clinical.silver.patient_activity (
    event_id,
    patient_id,
    event_timestamp,
    event_type
)
SELECT
    event_id,
    patient_id,
    event_timestamp,
    event_type
FROM approved_source;
```

An append is transactional, but repeating it can still duplicate business records.

## 4. UPDATE — modify existing rows

Before a production update, validate its predicate with a read.

```sql
SELECT
    event_id,
    event_type
FROM clinical.silver.patient_activity
WHERE event_id = 'EVT-1001';
```

Then, after confirming the intended scope:

```sql
UPDATE clinical.silver.patient_activity
SET event_type = 'OUTPATIENT_VISIT'
WHERE event_id = 'EVT-1001';
```

A missing or incorrect predicate can affect far more rows than intended.

## 5. DELETE — remove rows deliberately

Use the same read-before-write discipline.

```sql
SELECT event_id
FROM clinical.silver.patient_activity
WHERE event_id = 'EVT-TEST-DELETE';
```

Only after validating scope should a corresponding delete be considered:

```sql
DELETE FROM clinical.silver.patient_activity
WHERE event_id = 'EVT-TEST-DELETE';
```

Production deletion should also account for retention, downstream consumers, audit requirements, and recovery options.

## 6. MERGE — keyed change processing

Delta `MERGE` can combine matching and non-matching actions.

Conceptually:

```sql
MERGE INTO target AS t
USING source AS s
ON t.event_id = s.event_id
WHEN MATCHED THEN
  UPDATE SET ...
WHEN NOT MATCHED THEN
  INSERT ...;
```

The operation is not automatically correct merely because `MERGE` is used.

Before a production merge, verify:

```text
source uniqueness
      |
correct business/source key
      |
expected matched rows
      |
expected unmatched rows
      |
MERGE
      |
post-write validation
```

If multiple source records represent the same business event, define deterministic winner logic before writing.

## 7. Idempotency

An idempotent pipeline can be repeated without producing unintended additional business effects.

For example, a stable source event identifier can support deterministic change processing.

Ask:

- What uniquely identifies the event?
- Can the source resend it?
- What happens if the client loses its connection after commit?
- Can the operation safely run twice?
- How will the pipeline detect that the event was already processed?

Do not treat a network error as proof that the server transaction did not commit.

## 8. Schema enforcement

Delta validates writes against table schema.

Prefer explicit columns:

```sql
INSERT INTO target (
    event_id,
    patient_id,
    event_timestamp
)
SELECT
    event_id,
    patient_id,
    event_timestamp
FROM source;
```

This makes the intended contract more visible than an unrestricted positional assumption.

A schema mismatch should be investigated rather than automatically bypassed.

## 9. Schema evolution

Schema evolution is useful when the source contract legitimately changes, but automatic evolution can also propagate upstream mistakes.

Use this operational sequence:

```text
schema mismatch
      |
      v
investigate source
      |
      v
confirm intended contract change
      |
      v
approve evolution
      |
      v
apply controlled change
      |
      v
validate consumers
```

The exact syntax and available schema-evolution features depend on the Databricks Runtime and write operation. Verify the runtime behavior before production changes.

## 10. Append versus replacement

Think of write modes by blast radius:

```text
append
  -> add records

bounded/selective replacement
  -> replace an explicitly identified subset

full replacement
  -> replace broad table contents
     -> high-impact operation
```

Do not treat full overwrite as a routine equivalent of append.

Before replacement:

```text
[ ] Confirm target.
[ ] Confirm environment.
[ ] Confirm replacement scope.
[ ] Validate source.
[ ] Understand schema impact.
[ ] Identify downstream consumers.
[ ] Establish recovery path.
```

## 11. Concurrent writes

Concurrent Delta operations do not imply that every writer will always commit successfully.

Conceptually:

```text
transaction starts
      |
read snapshot
      |
perform work
      |
attempt commit
      |
      +---- success
      |
      +---- conflict
               |
               v
         evaluate retry safety
```

If a conflict occurs, refresh state and determine whether retrying is valid.

Never implement an unbounded blind retry loop.

## 12. Safe retry model

A production retry strategy should consider:

- operation identity;
- stable business/source key;
- current target state;
- maximum attempts;
- backoff behavior;
- whether the previous attempt may already have committed;
- whether re-reading is required;
- post-retry validation.

Transactional integrity and retry correctness are different problems.

## 13. Backfills

A backfill is a production data change and should have an explicit scope.

Before execution:

```text
[ ] source date/range
[ ] target catalog/schema/table
[ ] target date/partition/range
[ ] expected source count
[ ] current target state
[ ] duplicate behavior
[ ] write strategy
[ ] downstream impact
[ ] validation queries
[ ] recovery procedure
```

Blind repeated inserts are not a safe general backfill strategy.

## 14. Validation pattern

A useful workflow is:

```text
Pre-write validation
        |
        v
Bounded write
        |
        v
Post-write validation
        |
        +---- expected -> complete
        |
        +---- unexpected -> stop/investigate/recover
```

Validation can include:

- affected key/range;
- expected versus actual row counts;
- duplicate checks;
- null checks;
- schema verification;
- downstream reconciliation;
- transaction/job evidence.

## 15. Sensitive data

Reading is not automatically risk-free.

A broad query can expose columns that are unnecessary for the task. Prefer the minimum data required.

All patient-oriented examples in this tutorial are synthetic.

Production access must follow organizational requirements for least privilege, auditing, retention, and protected data.

## 16. Do not manipulate Delta storage directly

Do not manually delete or modify data files or transaction-log files underneath a Delta table as a substitute for supported table operations.

Use supported Databricks and Delta operations so transactional metadata remains consistent with table state.

## 17. SQL and DataFrame APIs

Delta tables can be accessed through SQL and Spark/DataFrame APIs.

Conceptually:

```text
SQL operations
      |
      v
  Delta table
      ^
      |
Spark/DataFrame APIs
```

The interface can differ, but production concerns remain the same: schema, scope, idempotency, concurrency, validation, and recovery.

Detailed DataFrame pipeline development is outside this introductory section.

## 18. Batch and streaming

Delta can participate in both batch and streaming pipelines.

Part 2.6 covers this distinction in detail.

For now, remember that streaming adds additional concerns such as checkpoints, state, event time, watermarks, and continuously arriving records.

## 19. Hands-on lab — writable training exercise

> **STATE-CHANGING LAB:** Run this only in an approved disposable training namespace with synthetic data. Do not copy the object names blindly into production.

The exercise should follow this sequence:

```text
create disposable Delta table
        |
insert synthetic rows
        |
read and validate
        |
bounded update
        |
bounded delete
        |
deterministic merge
        |
validate final state
        |
controlled cleanup
```

Example table design:

```sql
CREATE TABLE <training_catalog>.<training_schema>.patient_activity_write_lab (
    event_id STRING,
    patient_id STRING,
    event_timestamp TIMESTAMP,
    event_type STRING
)
USING DELTA;
```

Insert synthetic rows with explicit columns, query them, and validate the intended scope before each state-changing operation.

For the merge portion, create or use a disposable source relation in which `event_id` is unique. Verify source uniqueness before executing the merge.

Cleanup is part of the writable exercise only and must target the exact disposable object created for the lab.

## 20. Production write gate

Before a production write:

```text
TARGET
  -> exact catalog.schema.table

SCOPE
  -> exact keys/date/range

IDEMPOTENCY
  -> safe behavior if repeated

VALIDATION
  -> pre-write + post-write evidence

RECOVERY
  -> known response if result is wrong
```

If any of those are unclear, stop before writing.

## 22. Key takeaways

1. Use fully qualified names when production namespace ambiguity matters.
2. Prefer explicit projections and target columns.
3. Delta transactions provide consistency but not automatic business idempotency.
4. Validate predicates before `UPDATE` and `DELETE`.
5. `MERGE` correctness depends on its match key and source uniqueness.
6. Treat schema changes as data-contract changes.
7. Full overwrite has a much larger blast radius than append.
8. Concurrent writes can conflict.
9. Retry only after determining that retry is safe.
10. Backfills require explicit boundaries and recovery planning.
11. Validate writes before and after execution.
12. Never bypass Delta semantics by manually manipulating table storage.
13. Protect sensitive data during reads as well as writes.
14. Keep state-changing training exercises separate from SAFE-READ acceptance.
