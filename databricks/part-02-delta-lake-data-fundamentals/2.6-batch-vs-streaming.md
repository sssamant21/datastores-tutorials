# Part 2.6 — Batch vs Streaming

**Track:** Databricks Production Tutorials  
**Part:** 2 — Delta Lake & Data Fundamentals  
**Status:** Revised Final / Canonical Edition

## Learning objectives

By the end of this tutorial, you should be able to:

- distinguish bounded batch processing from incremental streaming processing;
- explain why streaming does not necessarily mean permanently running compute;
- understand Structured Streaming micro-batches and AvailableNow;
- distinguish event time, ingestion time, and processing time;
- explain checkpoints, watermarks, late data, and stateful processing;
- use Delta tables conceptually as streaming sources and sinks;
- understand restart and checkpoint compatibility risks;
- diagnose streaming lag using evidence;
- recognize idempotency risks in custom streaming sinks;
- operate streaming workloads with production safety and cost awareness.

## 1. Batch processing

Batch processing operates on a bounded set of data.

~~~text
Data accumulates
      |
      v
Job starts
      |
      v
Process bounded input
      |
      v
Job completes
~~~

Typical batch workloads include scheduled transformations, historical backfills, daily aggregates, and finite file loads.

~~~python
df = spark.table("training.bronze.patient_activity")
~~~

## 2. Streaming processing

Structured Streaming processes data incrementally.

~~~text
New events
    |
    v
incremental processing
    |
    v
new output
    |
    v
progress/checkpoint
    |
    v
next increment
~~~

Streaming does not necessarily mean compute must run forever. Incremental execution can run continuously or process currently available unprocessed data and stop.

## 3. Micro-batch model

For typical analytical and ETL workloads, micro-batch processing is the primary introductory model.

~~~text
events
  |
  v
micro-batch 1
  |
checkpoint/progress
  |
  v
micro-batch 2
  |
checkpoint/progress
  |
  v
...
~~~

Very-low-latency real-time processing is a more advanced design and should not be assumed necessary for ordinary data-engineering workloads.

## 4. AvailableNow

AvailableNow bridges scheduled execution and incremental processing.

~~~text
unprocessed data
      |
      v
AvailableNow starts
      |
      v
one or more micro-batches
      |
      v
caught up
      |
      v
query stops
~~~

This can provide incremental semantics without continuously running compute.

## 5. Choosing batch or streaming

Do not select streaming simply because it sounds more modern. Consider required business latency, source arrival behavior, volume, operational complexity, state requirements, failure and replay behavior, downstream expectations, compute cost, and support maturity.

A daily workload with no near-real-time requirement can often remain batch.

## 6. Delta as streaming source and sink

Conceptually:

~~~text
Bronze Delta
     |
 readStream
     |
     v
Structured Streaming
     |
 writeStream
     |
     v
Silver Delta
~~~

Example:

~~~python
stream_df = (
    spark.readStream
         .table("training.bronze.patient_activity")
)
~~~

A streaming write needs an appropriate sink and dedicated checkpoint location.

## 7. Checkpoints

A checkpoint is persistent streaming-query state. It can track query progress, commits, source positions, and state associated with stateful processing.

Use one checkpoint location per query:

~~~text
Query A ----> Checkpoint A
Query B ----> Checkpoint B
~~~

Do not point unrelated queries at the same checkpoint. Treat checkpoints as production state, not temporary scratch storage.

## 8. Do not delete checkpoints as routine troubleshooting

A failed stream does not automatically mean its checkpoint should be deleted.

~~~text
stream failed
     |
preserve evidence
     |
inspect failure
     |
verify checkpoint compatibility
     |
recover deliberately
~~~

Starting with a new checkpoint can make the workload behave as a new query and can change replay or duplicate behavior.

Before intentionally resetting a checkpoint:

~~~text
[ ] identify root failure
[ ] preserve logs and progress evidence
[ ] understand source restart position
[ ] assess replay/duplicate impact
[ ] assess stateful-operation impact
[ ] verify sink idempotency
[ ] establish validation plan
[ ] obtain required production approval
~~~

## 9. Restart versus reset

~~~text
restart + compatible existing checkpoint
              !=
start with a new checkpoint
~~~

A normal restart should preserve compatible progress. A checkpoint reset is a recovery or migration decision with correctness implications.

## 10. Event, ingestion, and processing time

~~~text
event_time
    !=
ingestion_time
    !=
processing_time
~~~

Example:

~~~text
event occurred:       09:00
arrived in platform:  09:07
processed:            09:08
~~~

Event-time windows should be designed around the appropriate business timestamp rather than assuming processing time represents when the event occurred.

## 11. Late-arriving data

Events can arrive after their expected time window. Production design should answer:

- How late can records normally arrive?
- Should late records update prior aggregates?
- When is a business window considered complete?
- How are rejected or excessively late records observed?
- Can downstream Gold results be corrected?

## 12. Watermarks

Watermarks help stateful event-time processing reason about lateness and retained state.

~~~text
latest observed event time
          |
minus lateness threshold
          |
          v
watermark
~~~

Do not describe a watermark merely as how long Spark waits.

~~~text
shorter lateness threshold
├── less retained state
└── lower tolerance for late data

longer lateness threshold
├── greater late-data tolerance
└── potentially larger retained state
~~~

Watermark changes can affect correctness as well as resource usage.

## 13. Stateful processing

Aggregations, deduplication, and some joins can retain state across processing increments.

~~~text
more keys
+ longer retained history
+ greater lateness tolerance
        |
        v
larger state
        |
        v
more memory/storage/checkpoint work
        |
        v
potential processing delay
~~~

State growth should be monitored.

## 14. Streaming lag

Use evidence-driven diagnosis:

~~~text
stream falling behind
        |
source arrival rate
        |
input / micro-batch size
        |
processing duration
        |
state growth
        |
checkpoint/storage latency
        |
sink latency/errors
        |
compute pressure
~~~

Distinguish a slow source, slow processing, and a slow sink. Adding compute without identifying the bottleneck can increase cost without fixing the problem.

## 15. Input controls

Some streaming sources provide controls that bound input per trigger. These can help manage micro-batch size, but they do not replace capacity planning.

Changing limits can affect processing latency, backlog recovery time, batch duration, resource utilization, and downstream write pressure.

Tune from measured evidence.

## 16. Query and schema evolution

A streaming code change can affect checkpoint compatibility.

Before changing sources, sinks, stateful operations, grouping keys, joins, schemas, or query structure:

~~~text
code/schema change
      |
classify streaming impact
      |
verify checkpoint compatibility
      |
plan migration/recovery
      |
deploy
      |
validate progress and output
~~~

Do not discover incompatibility for the first time during an uncontrolled production restart.

## 17. foreachBatch and side effects

Custom foreachBatch logic can execute operations for each micro-batch. External effects need their own correctness controls.

~~~text
micro-batch
   |
   +--> Delta operation
   +--> external database
   +--> API call
   +--> message publication
~~~

These systems do not automatically become one atomic transaction.

Use deterministic identifiers, batch identity where appropriate, and idempotent downstream behavior. Checkpointing does not automatically make arbitrary external side effects exactly once.

## 18. Safe restart procedure

When a production stream fails:

1. Preserve error and query-progress evidence.
2. Confirm source health.
3. Confirm sink health.
4. Inspect checkpoint/storage accessibility.
5. Identify schema or code changes.
6. Determine whether stateful processing is involved.
7. Verify checkpoint compatibility.
8. Decide whether normal restart is safe.
9. Reset or migrate the checkpoint only through an explicit recovery plan.
10. Validate output and backlog after recovery.

## 19. Compute and cost

A continuously scheduled stream can consume compute indefinitely.

~~~text
[ ] execution mode
[ ] expected latency
[ ] compute sizing
[ ] autoscaling behavior
[ ] failure/retry policy
[ ] alerting
[ ] backlog monitoring
[ ] state monitoring
[ ] cost monitoring
[ ] on-call ownership
~~~

Where continuous execution is unnecessary, scheduled incremental processing such as AvailableNow can be appropriate.

## 20. Scheduling terminology

Do not confuse job scheduling terminology with streaming processing semantics. A job-level continuous scheduling option and a Structured Streaming processing mode describe different concerns.

## 22. Hands-on lab — writable streaming exercise

> **STATE-CHANGING LAB:** Run only in an approved disposable training environment. It creates or writes training data and checkpoint state.

Conceptual example:

~~~python
stream_df = (
    spark.readStream
         .table("training.bronze.patient_activity")
)

(
    stream_df.writeStream
             .option(
                 "checkpointLocation",
                 "<approved-dedicated-training-checkpoint>"
             )
             .toTable("training.silver.patient_activity_stream")
)
~~~

Compare with:

~~~python
batch_df = spark.table("training.bronze.patient_activity")
~~~

The checkpoint must be dedicated to that query. Cleanup must target only training resources. Never reuse production checkpoints for training.

## 23. Production troubleshooting checklist

~~~text
[ ] Is the source producing expected data?
[ ] Is the query running?
[ ] Is backlog increasing?
[ ] What is the input rate?
[ ] What is the processing rate?
[ ] How long are micro-batches taking?
[ ] Is state growing?
[ ] Is the watermark progressing as expected?
[ ] Is checkpoint storage healthy?
[ ] Is the sink healthy?
[ ] Are schema changes involved?
[ ] Was code recently changed?
[ ] Is the existing checkpoint compatible?
[ ] Are retries repeating external side effects?
[ ] Is compute saturated?
[ ] Is cost increasing unexpectedly?
~~~

## 25. Key takeaways

1. Batch processes bounded data; Structured Streaming provides incremental semantics.
2. Streaming does not necessarily require continuously running compute.
3. Micro-batch is the primary introductory model for typical ETL.
4. AvailableNow can process available unprocessed data incrementally and stop.
5. Delta can participate as a streaming source and sink.
6. A checkpoint is persistent query state and should be protected.
7. Each query should use its own checkpoint.
8. Restarting from a compatible checkpoint differs from resetting it.
9. Event, ingestion, and processing time are different.
10. Watermarks affect late-data handling and state retention.
11. Stateful workloads require state-growth monitoring.
12. Lag should be diagnosed across source, processing, state, checkpoint, sink, and compute.
13. Query changes can affect checkpoint compatibility.
14. External side effects require idempotency controls.
15. Continuous workloads require cost and ownership controls.
16. Keep writable streaming exercises separate from SAFE-READ acceptance.
