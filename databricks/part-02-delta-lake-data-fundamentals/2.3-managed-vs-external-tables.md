# Part 2.3 — Managed vs External Tables

**Track:** Databricks Production Tutorials
**Part:** 2 — Delta Lake & Data Fundamentals
**Status:** Revised Final / Canonical Edition

## Learning objectives

By the end of this tutorial, you should be able to:

- explain the difference between Unity Catalog managed and external tables;
- distinguish table metadata management from underlying data-file lifecycle;
- understand managed storage, external locations, and `LOCATION`;
- create managed and external Delta tables in an approved training environment;
- inspect table metadata and storage information safely;
- understand the operational consequences of `DROP TABLE`;
- recognize why Unity Catalog and legacy `hive_metastore` deletion behavior must not be treated as equivalent;
- identify common DBRE/SRE risks involving permissions, storage paths, orphaned data, and destructive cleanup.

## 1. Why table type matters

A table has both governed metadata and underlying data files. The distinction between a managed table and an external table is especially important during creation, migration, recovery, deletion, storage cleanup, permission troubleshooting, and incident response.

## 2. Managed tables

With a Unity Catalog managed table, Unity Catalog governs the table and manages its underlying storage lifecycle.

A managed Delta table normally does not specify a storage `LOCATION`:

```sql
CREATE TABLE tutorial_catalog.training.patient_managed (
    patient_id BIGINT,
    first_name STRING,
    last_name STRING,
    created_at TIMESTAMP
)
USING DELTA;
```

Unity Catalog determines the appropriate managed storage location. Applications should normally interact with the table by name rather than depend on its physical path.

## 3. External tables

An external table is governed in Unity Catalog while its underlying data resides at externally managed storage.

```sql
CREATE TABLE tutorial_catalog.training.patient_external (
    patient_id BIGINT,
    first_name STRING,
    last_name STRING,
    created_at TIMESTAMP
)
USING DELTA
LOCATION '<approved-external-location>/patient_external';
```

The path is intentionally a placeholder. Never replace it with an arbitrary production S3, ADLS, or GCS path.

## 4. Core comparison

| Characteristic | Managed table | External table |
|---|---|---|
| Unity Catalog metadata | Governed | Governed |
| Table permissions | Governed | Governed |
| Underlying storage | Managed storage | Explicit external storage |
| `LOCATION` normally supplied by user | No | Yes |
| Data lifecycle managed with table | Yes | No |
| External systems expected to manage files | Generally no | Possible |
| Dropping registration can leave files | Not the normal lifecycle | Yes |

## 5. External locations and storage credentials

Unity Catalog external locations provide governed access to cloud storage and are backed by storage credentials. Their exact cloud implementation differs across AWS, Azure, and GCP.

Storage credentials and external locations are infrastructure/governance objects. Learners should not assume permission to create them. A platform team may provision these prerequisites and authorize data engineers to create external tables at approved locations.

## 6. Three-part naming

Managed and external tables use the same Unity Catalog namespace:

```text
catalog.schema.table
```

Examples:

```text
tutorial_catalog.training.patient_managed
tutorial_catalog.training.patient_external
```

Use explicit three-part names for production lifecycle operations whenever practical.

## 7. Hands-on managed table

> **LAB SAFETY:** These examples change database state. Run them only in an approved disposable training environment.

Confirm context:

```sql
SELECT current_catalog(), current_schema();
```

Create a managed table:

```sql
CREATE TABLE IF NOT EXISTS tutorial_catalog.training.patient_managed (
    patient_id BIGINT,
    patient_name STRING,
    created_at TIMESTAMP
)
USING DELTA;
```

Inspect it:

```sql
DESCRIBE TABLE tutorial_catalog.training.patient_managed;
DESCRIBE DETAIL tutorial_catalog.training.patient_managed;
```

## 8. Hands-on external table

Continue only if an administrator has supplied an approved external location/path and the required privileges.

```sql
CREATE TABLE tutorial_catalog.training.patient_external (
    patient_id BIGINT,
    patient_name STRING,
    created_at TIMESTAMP
)
USING DELTA
LOCATION '<approved-training-path>/patient_external';
```

Before creating it, verify the approved path, privilege model, storage ownership, lifecycle expectations, and that the path does not conflict with another governed object.

## 9. The lifecycle distinction

For a Unity Catalog external table, dropping the table registration removes catalog metadata but does not mean that the externally managed data files have been deleted.

For a Unity Catalog managed table, Unity Catalog manages the underlying data lifecycle. Current Databricks behavior includes a retention/recovery lifecycle for dropped Unity Catalog managed tables before permanent file deletion. Production recovery procedures should always validate the behavior supported by the current environment.

Never assume either:

```text
DROP TABLE = delete files
```

or:

```text
DROP TABLE = keep files
```

Identify the governance model, table type, storage ownership, physical location, recovery requirement, and intended lifecycle first.

## 10. Re-registering existing external Delta data

When external Delta data remains at an approved path after a table registration is removed, an authorized operator can potentially register that existing data again.

Before doing so, validate the path, Delta format, intended owner and namespace, access model, overlap with existing governed objects, and dataset identity.

Do not recreate a missing table blindly during an incident.

## 11. Storage-path safety

Use clearly separated directories for governed datasets. Avoid deliberately designing overlapping paths or placing tutorial tables at the root of a shared external location.

Prefer a dedicated subdirectory such as:

```text
<approved-external-location>/training/patient_external/
```

Storage-path ownership should be clear enough that cleanup cannot accidentally affect another dataset.

## 12. Direct cloud-storage modification

External data may also be reachable by identities or systems outside Databricks. Direct deletion, overwrite, movement, or incompatible modification of files can damage the table even when Unity Catalog permissions are correct.

Unity Catalog governance and cloud IAM therefore need to be designed together.

## 13. Orphaned external data

Dropping an external table can leave storage files without a table registration. This may be intentional, but forgotten external data can also become a storage-cost, ownership, retention, governance, or security problem.

Treat metadata cleanup and external-storage cleanup as separate controlled decisions.

## 14. Permission troubleshooting

An external-table failure can involve multiple layers:

1. active catalog and schema;
2. table-creation privileges;
3. external-location authorization;
4. cloud-storage access;
5. storage/path governance.

A permission error does not prove that the path or data is missing. Avoid responding with broad grants before identifying the failing authorization layer.

## 15. Unity Catalog vs hive_metastore

Unity Catalog and legacy `hive_metastore` do not have identical governance and deletion semantics.

Do not apply a Unity Catalog lifecycle rule to `hive_metastore` without separate validation. Legacy schema-level destructive operations can have materially different storage consequences.

## 16. Production deletion gate

Before destructive table operations:

```text
[ ] Confirm workspace/environment.
[ ] Confirm current catalog and schema.
[ ] Resolve the exact catalog.schema.table.
[ ] Identify Unity Catalog vs hive_metastore.
[ ] Identify managed vs external.
[ ] Inspect storage information.
[ ] Confirm storage ownership.
[ ] Determine whether data must survive.
[ ] Confirm required privileges.
[ ] Check for path overlap/conflict.
[ ] Confirm recovery/rollback strategy.
[ ] Obtain required approval.
```

Only then should a destructive operation proceed.

## 17. DBRE/SRE troubleshooting scenario

If an application reports `TABLE_OR_VIEW_NOT_FOUND` after deployment, do not immediately recreate the table.

Investigate the workspace, current catalog/schema, fully qualified expected name, governance model, managed/external classification, recent metadata changes, underlying storage existence, discovery privileges, and deployment namespace changes.

For an external Delta table, intact files can turn an apparent data-loss incident into a metadata-recovery problem—but verify evidence before re-registering anything.

## 18. Cleanup boundary

Cleanup changes state and is intentionally excluded from the canonical acceptance artifact.

Before removing an external training table or its storage, independently determine whether both table-registration removal and cloud-file deletion are intended. They are separate decisions.

## 19. Canonical acceptance check

The repository artifact `labs/managed-external-tables-check.sql` is classified as:

```text
[TUTORIAL-ACCEPTANCE — SAFE-READ]
```

It performs namespace and metadata discovery only. It does not create, alter, drop, modify rows, vacuum, delete files, create external locations, modify storage credentials, grant, revoke, or clean up objects.

Object-specific inspection is operator-supplied rather than hard-coded against an arbitrary environment.

## 20. Key takeaways

1. Unity Catalog managed and external tables are governed objects, but their data lifecycles differ.
2. Managed tables use a Unity Catalog-managed storage lifecycle.
3. External tables reference externally managed storage.
4. External tables normally use an explicit approved `LOCATION`.
5. Dropping an external table does not imply deletion of its underlying files.
6. Managed-table deletion has Databricks-managed lifecycle and recovery considerations.
7. Never generalize Unity Catalog deletion behavior to legacy `hive_metastore`.
8. Storage credentials and external locations are governed infrastructure.
9. Direct storage access can bypass Unity Catalog controls and must be governed separately.
10. Destructive production operations require namespace, table-type, storage-ownership, and recovery validation.
11. SAFE-READ acceptance testing remains separate from cleanup.
