# Part 2.2 — Catalog → Schema → Table

**Track:** Databricks Production Tutorials  
**Part:** 2 — Delta Lake & Data Fundamentals  
**Status:** Revised Final / Canonical Edition

## Learning objectives

By the end of this tutorial, you should be able to:

- explain the metastore → catalog → schema → table hierarchy;
- identify a table by its three-part name: `catalog.schema.table`;
- inspect the current catalog and schema safely;
- navigate catalogs and schemas with Databricks SQL;
- create disposable learning objects in an approved non-production location;
- explain why fully qualified names reduce wrong-environment mistakes;
- distinguish Unity Catalog namespaces from the legacy `hive_metastore` at an introductory level;
- recognize where ownership and privileges affect object discovery and creation.

## 1. Why the namespace matters

A Databricks table does not exist as an isolated name. In a Unity Catalog-enabled environment, data objects are organized in a hierarchy:

```text
Metastore
└── Catalog
    └── Schema
        └── Table
            ├── Columns
            └── Rows
```

A fully qualified table name therefore has three parts:

```text
catalog.schema.table
```

For example:

```text
tutorial_catalog.training.patient_demo
```

Here:

- `tutorial_catalog` is the catalog;
- `training` is the schema;
- `patient_demo` is the table.

This hierarchy is important for governance, access control, environment separation, discovery, and production safety.

## 2. Metastore

The metastore is the top-level governance boundary for Unity Catalog objects available to attached workspaces. It contains catalogs.

Most application developers and data engineers do not create or administer metastores as part of normal table development. Metastore configuration is normally a platform or account administration responsibility.

Do not confuse the Unity Catalog metastore with an individual catalog.

## 3. Catalog

A catalog is the first level of the three-part namespace.

Organizations commonly use catalogs to establish broad data boundaries. The exact design is organization-specific. A catalog might represent an environment, business domain, governance boundary, or another platform convention.

Examples might include:

```text
dev_clinical
staging_clinical
prod_clinical
```

These names are examples only. Do not assume that a production workspace uses this convention.

### Inspect catalogs

```sql
SHOW CATALOGS;
```

To inspect the active catalog:

```sql
SELECT current_catalog();
```

Before performing production work, confirm the active namespace instead of assuming it from a notebook name, compute name, or workspace.

## 4. Schema

A schema is a namespace inside a catalog.

The hierarchy is:

```text
catalog
└── schema
    └── table
```

For example:

```text
prod_clinical
└── patient360
    └── patient_activity
```

The table's fully qualified name is:

```text
prod_clinical.patient360.patient_activity
```

Inspect schemas in the current catalog:

```sql
SHOW SCHEMAS;
```

Inspect the active schema:

```sql
SELECT current_schema();
```

## 5. Table

A table is an object inside a schema.

For example:

```text
tutorial_catalog.training.patient_demo
```

A table contains columns and represents rows of data. In this tutorial track, Delta is the primary table format.

List tables visible in the current schema:

```sql
SHOW TABLES;
```

When you know an approved table name, inspect its definition explicitly:

```sql
DESCRIBE TABLE tutorial_catalog.training.patient_demo;
```

Do not substitute an arbitrary production table merely to complete a lab.

## 6. Session context

Databricks SQL can resolve partially qualified names using the current catalog and schema.

Inspect the current context:

```sql
SELECT current_catalog(), current_schema();
```

Change the catalog:

```sql
USE CATALOG tutorial_catalog;
```

Change the schema:

```sql
USE SCHEMA training;
```

Afterward, a reference such as:

```sql
SELECT * FROM patient_demo;
```

can resolve using session context.

That convenience can become an operational risk. Production automation should prefer an explicit three-part name when practical:

```sql
SELECT *
FROM prod_clinical.patient360.patient_activity;
```

A fully qualified name makes the target visible in code review and reduces dependence on inherited session state.

## 7. Hands-on learning exercise

> **Safety boundary:** The commands in this section change database state. Run them only in a disposable training environment or another location explicitly approved for the exercise. They are intentionally excluded from the canonical SAFE-READ acceptance artifact.

### Step 1 — Confirm context

```sql
SELECT current_catalog(), current_schema();
SHOW CATALOGS;
```

Confirm that you are not targeting an unintended production namespace.

### Step 2 — Create a disposable catalog

Only learners with appropriate privileges should perform this step:

```sql
CREATE CATALOG IF NOT EXISTS tutorial_catalog;
```

If catalog creation is centrally managed, use the training catalog supplied by your platform administrator instead.

### Step 3 — Create a schema

```sql
CREATE SCHEMA IF NOT EXISTS tutorial_catalog.training;
```

### Step 4 — Create a Delta table

```sql
CREATE TABLE IF NOT EXISTS tutorial_catalog.training.patient_demo (
    patient_id BIGINT,
    first_name STRING,
    last_name STRING,
    created_at TIMESTAMP
)
USING DELTA;
```

The resulting hierarchy is:

```text
tutorial_catalog
└── training
    └── patient_demo
        ├── patient_id
        ├── first_name
        ├── last_name
        └── created_at
```

### Step 5 — Inspect the object

```sql
SHOW TABLES IN tutorial_catalog.training;

DESCRIBE TABLE tutorial_catalog.training.patient_demo;
```

### Step 6 — Cleanup

Cleanup is deliberately not part of the SAFE-READ acceptance script.

If your training environment requires cleanup, confirm the target and follow the environment's approved cleanup procedure. A `DROP` operation changes state and can have data-lifecycle consequences.

## 8. Unity Catalog and hive_metastore

Unity Catalog provides the governed three-level namespace used throughout this tutorial.

Some workspaces can also expose `hive_metastore`, particularly for legacy workspace-local objects. Do not assume that an object in `hive_metastore` has the same governance, isolation, or operational characteristics as a Unity Catalog object.

When migrating or troubleshooting legacy workloads, identify which metastore/catalog model the workload actually uses before changing code or permissions.

## 9. Ownership and privileges

Seeing an object and being allowed to create or modify an object are separate concerns.

Operations can require privileges on multiple levels of the hierarchy. A permission error does not prove that a catalog, schema, or table is absent.

For troubleshooting, separate these questions:

1. What catalog and schema are active?
2. Does the object exist?
3. Can the current principal discover it?
4. Does the principal have the privileges required for the requested operation?
5. Is the operation being attempted in the correct environment?

Do not respond to an authorization failure by broadly granting privileges without understanding the intended access model.

## 10. Managed and external tables — introduction

Databricks supports managed and external data objects. Their storage ownership and lifecycle behavior differ.

Part 2.3 covers this topic in detail. For now, remember:

- do not infer data-deletion behavior from the word "table" alone;
- do not run destructive cleanup against an external location simply because a lab used disposable managed objects;
- verify object type, storage ownership, location, and organizational policy before destructive operations.

## 11. Production naming practices

A short name is easy to read:

```text
patient_demo
```

A two-part name provides more context:

```text
training.patient_demo
```

A three-part name makes the namespace explicit:

```text
prod_clinical.training.patient_demo
```

For production jobs, migrations, runbooks, and administrative procedures, explicit qualification is usually safer than relying on mutable session defaults.

## 12. Common operational mistakes

### Wrong catalog

A session points to a development catalog while the operator assumes it is production, or the reverse.

**Prevention:** inspect `current_catalog()` and use explicit object names.

### Wrong schema

The correct table name exists in multiple schemas.

**Prevention:** verify `current_schema()` and qualify the object.

### Permission failure interpreted as missing data

The current principal cannot discover or access an object.

**Prevention:** investigate namespace and privileges independently.

### Catalog creation attempted by an ordinary learner

`CREATE CATALOG` can be restricted by the organization's governance model.

**Prevention:** use an administrator-provided training catalog when catalog creation is not delegated.

### Destructive cleanup copied into production

A tutorial `DROP` command is reused without checking the target.

**Prevention:** keep destructive cleanup out of acceptance checks and require explicit environment validation.

## 13. DBRE/SRE production checklist

Before an object-changing operation:

```text
[ ] Confirm workspace/environment.
[ ] Confirm current_catalog().
[ ] Confirm current_schema().
[ ] Resolve the intended three-part object name.
[ ] Confirm the object type and ownership model.
[ ] Confirm the executing principal.
[ ] Confirm required privileges.
[ ] Review storage/data-lifecycle impact.
[ ] Define validation and rollback/recovery steps.
[ ] Capture only metadata appropriate for operational records.
```

The repository artifact:

```text
labs/catalog-schema-table-check.sql
```

is intentionally SAFE-READ.

It validates namespace visibility without creating, modifying, granting, revoking, or deleting anything.

The acceptance artifact and the hands-on creation exercise have different purposes:

```text
Hands-on learning

Canonical acceptance
└── metadata/context reads only
```

## 15. Key takeaways

1. Unity Catalog organizes governed objects as metastore → catalog → schema → table.
2. A table can be identified explicitly with `catalog.schema.table`.
3. Session context is convenient but can hide the real target.
4. Production procedures should make namespace selection explicit.
5. Authorization failures and object absence are not the same thing.
6. Object creation belongs in controlled learning or approved operational workflows.
7. Acceptance checks should remain read-only unless a state-changing test is explicitly required and reviewed.
8. Managed versus external table lifecycle behavior deserves separate treatment and is covered in Part 2.3.
